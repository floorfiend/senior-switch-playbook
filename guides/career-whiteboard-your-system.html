Whiteboard your own system

The hiring-manager project deep-dive is where many SDE-2 candidates who cleared coding get rejected. This lesson gives you a 10-minute walkthrough structure, the numbers you must know, the diagrams to draw, and prepared answers to "what breaks at 100×" and "what would you do differently", using a generic e-signing service as the worked example.

01What the interviewer is grading

  • Depth of understanding: can you go from the API down to the index, the transaction boundary and the Kafka partition key without hand-waving?
  • Ownership: did you make the decisions or just implement them? They test this with "why" questions on each box.
  • Judgement: alternatives you considered and why you rejected them.
  • Scale thinking: real numbers now, and a credible view of what fails at 10× and 100×.
  • Self-critique: honest answers on what you would change. Defensiveness is a red flag.
  • Communication: a clear structure, a diagram, no internal jargon the interviewer cannot follow.
Why candidates fail this round

Reports from Blinkit, CRED, Slice and Freshworks show the same pattern: candidates describe features instead of architecture, cannot give a single scale number, say "the team decided" for every choice, or freeze on "what would you change?". All four are fixable in a weekend of preparation.

02The 10-minute structure

0:00–1:00Context. The business problem, who uses it, your role ("I own this service and am on call for it").
1:00–3:00Architecture. Draw the boxes: clients, gateway, your services, datastores, queues, external vendors. Point at your part.
3:00–4:30APIs. 3–4 key endpoints and one event, with idempotency where it matters.
4:30–6:00Data model. The 3–4 core tables, keys, indexes, partitioning, tenant isolation.
6:00–7:30Async flows. One end-to-end flow through queues, retries, DLQ, consistency guarantees.
7:30–8:30Scale numbers. RPS, p99, data size, tenants, availability, cost.
8:30–10:00Your decisions. Two or three choices you made, the alternatives, and the outcome. End with "happy to go deeper anywhere".

Practise until you can do it in 10 minutes without notes. Many interviewers interrupt after 3–4 minutes; the structure lets you resume cleanly.

Back-of-envelope sanity check

15K documents/day ÷ 86,400 s ≈ 0.17 docs/s on average. Each document creates ~3 signers × ~8 API calls + ~20 audit events, so ~80 writes/document ≈ 14 writes/s average. A month-end peak of 10× is 140 writes/s: comfortable for one Postgres primary. Being able to do this live shows you understand your own system's headroom.

04Worked example: a generic e-signing service

Context (1 minute)

"We run a multi-tenant e-signing platform for banks, NBFCs and enterprises. A tenant uploads a document, defines signers and order, signers receive links, sign with OTP/Aadhaar e-sign/DSC, and every action is recorded in a tamper-evident audit trail that serves as legal evidence. I own the signing workflow and audit services and I'm on call for both."

Architecture

Tenant app / API client→ API GatewayJWT, tenant, rate limit→ Document Serviceupload, pre-signed URL→ S3originals + signed PDFs
Signing Workflow Servicestate machine, owner→ PostgreSQLworkflows, signers, outbox→relay Kafkaworkflow-events
Kafkaworkflow-events→ Audit Servicehash-chained log Notification Serviceemail, SMS, WhatsApp Webhook Dispatchertenant callbacks Billingusage events

Figure: document upload → signer workflow → events fan out to audit, notifications, webhooks and billing. Highlighted boxes are "mine".

APIs

POST /v1/documents                       -> 201 {documentId, uploadUrl}   (pre-signed S3 PUT)
POST /v1/workflows                       Idempotency-Key: <uuid>
     {documentId, signers:[{name, email, order, authMode}], expiresAt}
     -> 201 {workflowId, status:"IN_PROGRESS"}
POST /v1/workflows/{id}/signers/{sid}/sign   {otpToken, signatureImage, position}
     -> 200 {status, nextSigner}
GET  /v1/workflows/{id}/audit           -> 200 [{seq, event, actor, ip, ts, hash, prevHash}]

Event: workflow-events (key = workflowId)
     {eventId, tenantId, workflowId, type:"SIGNER_COMPLETED", signerId, version, ts}

Data model

TableKey fieldsIndexes / notes
workflowid, tenant_id, document_id, status, version, expires_at(tenant_id, status, created_at); version for optimistic locking
signerid, workflow_id, order_no, status, auth_mode, signed_at(workflow_id, order_no) unique
audit_eventid, tenant_id, workflow_id, seq, type, actor, payload, hash, prev_hashmonthly range partitions on created_at; (tenant_id, workflow_id, seq); append-only, no UPDATE grant
outboxid, aggregate_id, type, payload, created_at, published_atpartial index where published_at is null
idempotency_keytenant_id, key, request_hash, response, expires_atPK (tenant_id, key); TTL cleanup job

Async flow: signer completes

  1. Sign request validates the OTP token, then in one DB transaction: update signer status, bump workflow version (optimistic lock: UPDATE … WHERE id=? AND version=?), insert the outbox row.
  2. The outbox relay (polling every 200ms, or Debezium CDC) publishes to Kafka with key = workflowId so all events of a workflow stay ordered on one partition.
  3. Audit service consumes, computes hash = SHA-256(prevHash + event), appends; deduplicates on eventId.
  4. Notification service notifies the next signer; vendor failures go to retry topics with backoff (1m, 5m, 30m), then a DLQ with an alert.
  5. When the last signer completes, a PDF-stamping job applies the final signature and certificate, stores the signed PDF in S3, and emits WORKFLOW_COMPLETED for webhooks and billing.

05Diagrams to draw

1. Component diagram

Always. Boxes and arrows, sync vs async marked, datastores dashed, your ownership highlighted.

2. Sequence of one flow

Signer completes → DB txn → outbox → Kafka → consumers. Shows you understand ordering and failure points.

3. State machine

CREATED → IN_PROGRESS → (SIGNER_n_DONE)* → COMPLETED / EXPIRED / DECLINED / VOIDED. Interviewers love asking about illegal transitions.

4. Data model sketch

3–4 tables with keys and the one or two indexes that matter.

Practise drawing them in Excalidraw (most virtual rounds) and on paper. Use a consistent legend: solid arrow = sync HTTP, dashed arrow = async event.

06"At 100× scale, what breaks first?"

A senior answer ranks the bottlenecks by when they bite and names the fix for each. For the example: 100× means ~1.5M documents/day and ~14K writes/s at peak.

OrderWhat breaksSymptomFix
1Postgres primary write throughput and connection countPool exhaustion, replication lag, p99 spikesPgBouncer; move audit to its own DB/cluster; shard workflows by tenant_id (Citus or app-level) with large tenants isolated.
2Audit table sizeIndex bloat, slow vacuum, slow audit readsShorter partitions, cold partitions to S3 (Parquet) with a query path; or a write-optimised store for audit.
3Outbox relayGrowing outbox lag, delayed notificationsSwitch polling to CDC (Debezium), multiple relays partitioned by aggregate hash.
4External vendors (SMS/e-sign/Aadhaar)Throttling, 429s, cost explosionPer-vendor rate limits, multi-vendor routing with fallback, batching where allowed.
5PDF processing CPUStamping queue backlog at month-endSeparate autoscaled worker pool off a queue, KEDA on lag; pre-render templates.
6Noisy-neighbour tenantsOne bank's bulk job hurts allPer-tenant quotas at every tier, separate Kafka topics/consumer groups for bulk, cell-based isolation for top tenants.
Phrase it like this

"The first thing to break is the Postgres primary: at 14K writes/s we'd be beyond a comfortable single-node envelope and well beyond our connection budget. I'd first split audit onto its own cluster because it's 70% of writes and append-only, then shard workflows by tenant. Kafka would be fine with more partitions. The vendors would be the next real constraint, and that's a commercial as much as a technical problem."

07"What would you do differently?"

Have three honest answers ready: one design choice, one process choice, one thing you would keep. Never say "nothing".

  • Design: "I'd have introduced the outbox from day one. We spent six months debugging lost events from dual writes."
  • Design: "I'd model the workflow as an explicit state machine with a transitions table from the start; ad hoc status checks caused illegal transitions."
  • Operability: "We added per-tenant metrics late. Today I'd tag every metric and log with tenantId from the first commit."
  • Process: "I'd write a one-page design doc even for 'small' changes. The Redis rate limiter had a race we'd have caught in review of a doc."
  • What I'd keep: "Hash-chained audit. Cheap, simple, and it held up in a customer's legal review."

08Probing questions to rehearse

How do you guarantee a signer can't sign twice?

Signer row status check plus optimistic lock on the workflow version inside one transaction; the sign endpoint also accepts an idempotency key, so retries return the original response rather than a conflict.

How do you make consumers idempotent?

Each event carries a unique eventId; consumers record processed IDs in a table with a unique constraint in the same transaction as their side effect (or use natural keys like (workflowId, seq) for audit). Duplicates hit the constraint and are skipped.

What if Kafka is down?

The sign request still commits because the outbox row is in the same DB transaction. The relay retries; events are delayed, not lost. We alert on outbox age above 60 seconds.

How is tenant isolation enforced?

tenantId comes from the JWT, never from request parameters; repositories always filter by tenant (Hibernate filter or explicit clause), and integration tests assert cross-tenant reads return 404. For the largest tenants, separate rate limits and in future separate cells.

How would anyone detect audit tampering?

Each row stores hash(prevHash + canonical event). A nightly job recomputes chains per workflow; any mismatch alerts. Periodic anchoring of daily root hashes to an external timestamping service makes even DBA-level tampering detectable.

Why Postgres and not MongoDB/DynamoDB?

Strong transactional guarantees for the state change + outbox, relational queries for tenant reporting, and team expertise. Volume is well within Postgres limits. DynamoDB becomes interesting only if we shard massively and can live without cross-entity transactions.

What's the p99 dominated by?

Answer from your dashboards. In the example: the OTP verification call to the vendor (~150ms) and the transaction commit. We moved non-critical work (notifications, webhooks) off the request path.

What was your personal contribution versus the team's?

Be exact: "I designed and built the outbox and the audit chain, led the rate-limiter design; Priya built the notification consumers; the platform team owns the gateway."
