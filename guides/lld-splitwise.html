Splitwise / Expense Sharing

Users, groups, expenses split equally, by exact amounts, by percentage or by shares, and a balance sheet showing who owes whom. It looks easy, and that is the trap. Interviewers grade money handling (no double, remainders that add up to the paisa), a Strategy seam for split types, consistent balances under concurrent writes, and a clear answer on debt simplification.

01What the interviewer is grading

Groww's SDE-II machine coding round was two hours to "build Splitwise"; the candidate who got the offer implemented the core features and verified them with multiple test cases from a main class. Navi gave 90 minutes onsite for an expense tracker "similar to Splitwise", with the focus on classes, interfaces and extensibility before the core implementation. Walmart's SDE-III LLD round had the candidate open an IDE: requirements covered users, groups, expenses, balances and settle-up, with equal / percentage / exact split types, of which only equal had to be coded. Split was modelled as an abstract class with a Strategy per type; feedback was positive, with "focus more on service completion" because the service was 70% done. Swiggy asked for splits by user percentage. Uber took it to HLD with debt minimisation. Rippling's AI-allowed coding rounds stressed clean classes and optimal complexity, and a delivery-cost problem there is a reminder that money in double breaks at the paisa.

Money correctness

Integer paise or BigDecimal; shares always sum exactly to the total; deterministic remainder allocation.

Extensibility

New split type = one new strategy class. Validation lives with the strategy that needs it.

Balance model

One net number per pair, not a growing list of IOUs; O(1) update per participant.

Completeness

The service runs end to end with a driver; Walmart's only critique was an unfinished service.

Concurrency

Applying an expense is atomic: a reader never sees half of a multi-person split.

Algorithms

Simplify debts: greedy in O(n log n); know that the true minimum is NP-hard.

03Requirements

Functional

  • Create users and groups; add members.
  • Add an expense: payer, total, participants, split type and values.
  • Show balances for all, for one user, or for one group; only non-zero entries.
  • Settle up (record a payment) fully or partially.
  • Simplify group debts on request.
  • Expense history per group / user.

Non-functional

  • Exact to the paisa; the sum of all balances in a group is always zero.
  • Thread-safe expense application; idempotent expense creation.
  • O(participants) per expense; O(1) pair lookup.

Out of scope (say so)

  • Real payments (UPI integration), notifications, auth.
  • Persistence (repository interfaces only).
  • FX rates (keep per-currency balances if asked).

Walmart's candidate used an abstract Split class plus Strategy; either is accepted as long as adding a type touches one class. 05Core code

Money: parse once, compute in paise

public final class Money {
    private Money() {}

    /** "1000.5" -> 100050. Throws on more than 2 decimals or overflow; never goes through double. */
    public static long parse(String rupees) {
        return new BigDecimal(rupees).setScale(2, RoundingMode.UNNECESSARY).movePointRight(2).longValueExact();
    }

    public static String format(long paise) {
        return BigDecimal.valueOf(paise, 2).toPlainString();   // 100050 -> "1000.50"
    }
}

long paise is exact, fast and has no equals traps. If the interviewer prefers BigDecimal throughout, that is fine too; know the pitfalls listed in section 06.

Split strategies with exact remainder allocation

public record Participant(String userId, BigDecimal value) {
    public static Participant of(String userId) { return new Participant(userId, BigDecimal.ONE); }
}

public interface SplitStrategy {
    Map<String, Long> split(long totalPaise, List<Participant> participants);
}

final class Allocation {
    /**
     * Largest-remainder method: floor each weighted share, then hand leftover paise to the largest
     * fractional parts (ties broken by input order). The result always sums to total.
     */
    static Map<String, Long> byWeights(long total, List<Participant> ps) {
        BigDecimal sum = ps.stream().map(Participant::value).reduce(BigDecimal.ZERO, BigDecimal::add);
        if (sum.signum() <= 0) throw new IllegalArgumentException("weights must be positive");
        long[] floor = new long[ps.size()];
        BigDecimal[] frac = new BigDecimal[ps.size()];
        long allocated = 0;
        for (int i = 0; i < ps.size(); i++) {
            BigDecimal exact = BigDecimal.valueOf(total).multiply(ps.get(i).value())
                    .divide(sum, 10, RoundingMode.DOWN);
            floor[i] = exact.setScale(0, RoundingMode.DOWN).longValueExact();
            frac[i] = exact.subtract(BigDecimal.valueOf(floor[i]));
            allocated += floor[i];
        }
        Integer[] order = IntStream.range(0, ps.size()).boxed().toArray(Integer[]::new);
        Arrays.sort(order, (a, b) -> frac[b].compareTo(frac[a]));   // stable: ties keep input order
        for (int k = 0; k < total - allocated; k++) floor[order[k]]++;
        Map<String, Long> out = new LinkedHashMap<>();
        for (int i = 0; i < ps.size(); i++) out.merge(ps.get(i).userId(), floor[i], Long::sum);
        return out;
    }
}

public final class EqualSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<Participant> ps) {
        return Allocation.byWeights(total, ps.stream().map(p -> Participant.of(p.userId())).toList());
    }
}

public final class PercentSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<Participant> ps) {
        BigDecimal sum = ps.stream().map(Participant::value).reduce(BigDecimal.ZERO, BigDecimal::add);
        if (sum.compareTo(BigDecimal.valueOf(100)) != 0) throw new InvalidSplit("percentages sum to " + sum);
        return Allocation.byWeights(total, ps);
    }
}

public final class ShareSplit implements SplitStrategy {      // "2 shares for u1, 1 for u2"
    public Map<String, Long> split(long total, List<Participant> ps) { return Allocation.byWeights(total, ps); }
}

public final class ExactSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<Participant> ps) {
        Map<String, Long> out = new LinkedHashMap<>();
        for (Participant p : ps) out.merge(p.userId(), Money.parse(p.value().toPlainString()), Long::sum);
        long sum = out.values().stream().mapToLong(Long::longValue).sum();
        if (sum != total) throw new InvalidSplit("exact amounts sum to " + Money.format(sum));
        return out;
    }
}

Balance sheet: one signed number per pair

public final class BalanceSheet {
    /** Key (a, b) with a < b. Positive value: a owes b. Negative: b owes a. */
    private record Pair(String a, String b) {}
    private final Map<Pair, Long> pairs = new HashMap<>();
    private final Map<String, Long> net = new HashMap<>();   // positive = is owed money

    void addDebt(String debtor, String creditor, long paise) {
        if (debtor.equals(creditor) || paise == 0) return;
        boolean ordered = debtor.compareTo(creditor) < 0;
        Pair key = ordered ? new Pair(debtor, creditor) : new Pair(creditor, debtor);
        pairs.merge(key, ordered ? paise : -paise, Long::sum);
        pairs.remove(key, 0L);                                  // keep only non-zero balances
        net.merge(creditor, paise, Long::sum);
        net.merge(debtor, -paise, Long::sum);
    }

    /** Lines like "u2 owes u1: 250.00" involving the user, or all when user is null. */
    List<String> describe(String user) {
        List<String> lines = new ArrayList<>();
        pairs.forEach((k, v) -> {
            if (user != null && !k.a().equals(user) && !k.b().equals(user)) return;
            String debtor = v > 0 ? k.a() : k.b();
            String creditor = v > 0 ? k.b() : k.a();
            lines.add(debtor + " owes " + creditor + ": " + Money.format(Math.abs(v)));
        });
        return lines;
    }

    Map<String, Long> netByUser() { return Map.copyOf(net); }
}

Service: validate, split, apply atomically, idempotent

public record Expense(String id, String groupId, String paidBy, long total,
                      SplitType type, Map<String, Long> shares, String description, Instant createdAt) {}

public record Group(String id, String name, Set<String> members, BalanceSheet balances) {}

public final class ExpenseService {
    private final Map<SplitType, SplitStrategy> strategies;
    private final Map<String, Group> groups = new ConcurrentHashMap<>();
    private final Map<String, Expense> expenses = new ConcurrentHashMap<>();
    private final Clock clock;

    public ExpenseService(Map<SplitType, SplitStrategy> strategies, Clock clock) {
        this.strategies = Map.copyOf(strategies); this.clock = clock;
    }

    /** expenseId is client-supplied, so a retried request does not record the expense twice. */
    public Expense addExpense(String expenseId, String groupId, String paidBy, String amount,
                              SplitType type, List<Participant> participants, String description) {
        Group g = group(groupId);
        long total = Money.parse(amount);
        if (total <= 0) throw new InvalidSplit("amount must be positive");
        if (participants.isEmpty()) throw new InvalidSplit("no participants");
        Set<String> involved = new HashSet<>();
        involved.add(paidBy);
        participants.forEach(p -> involved.add(p.userId()));
        if (!g.members().containsAll(involved)) throw new InvalidSplit("non-member in expense");

        Map<String, Long> shares = strategies.get(type).split(total, participants);
        // Belt and braces: every strategy must conserve money.
        if (shares.values().stream().mapToLong(Long::longValue).sum() != total) throw new IllegalStateException();

        synchronized (g) {                                  // per-group: one expense applies fully or not at all
            Expense existing = expenses.get(expenseId);
            if (existing != null) return existing;
            Expense e = new Expense(expenseId, groupId, paidBy, total, type, Map.copyOf(shares), description, clock.instant());
            shares.forEach((user, share) -> g.balances().addDebt(user, paidBy, share));
            expenses.put(expenseId, e);
            return e;
        }
    }

    public void settle(String groupId, String from, String to, String amount) {
        Group g = group(groupId);
        long paise = Money.parse(amount);
        synchronized (g) { g.balances().addDebt(to, from, paise); }   // a payment is a debt in reverse
    }

    public void deleteExpense(String expenseId) {
        Expense e = Optional.ofNullable(expenses.get(expenseId)).orElseThrow();
        Group g = group(e.groupId());
        synchronized (g) {
            if (expenses.remove(expenseId) == null) return;
            e.shares().forEach((user, share) -> g.balances().addDebt(e.paidBy(), user, share));  // reverse
        }
    }

    public List<String> show(String groupId, String userOrNull) {
        Group g = group(groupId);
        synchronized (g) { return g.balances().describe(userOrNull); }
    }

    private Group group(String id) {
        return Optional.ofNullable(groups.get(id)).orElseThrow(() -> new NoSuchElementException("group " + id));
    }
}

Simplify debts: greedy with two heaps

public record Transfer(String from, String to, long paise) {}

public final class DebtSimplifier {
    /** At most n-1 transfers. Not always the global minimum (that problem is NP-hard). */
    public List<Transfer> simplify(Map<String, Long> net) {
        Comparator<Map.Entry<String, Long>> byAmountDesc =
                Comparator.comparingLong((Map.Entry<String, Long> e) -> Math.abs(e.getValue())).reversed()
                          .thenComparing(Map.Entry::getKey);                       // deterministic output
        PriorityQueue<Map.Entry<String, Long>> creditors = new PriorityQueue<>(byAmountDesc);
        PriorityQueue<Map.Entry<String, Long>> debtors = new PriorityQueue<>(byAmountDesc);
        net.forEach((u, v) -> {
            if (v > 0) creditors.add(Map.entry(u, v));
            else if (v < 0) debtors.add(Map.entry(u, v));
        });
        List<Transfer> out = new ArrayList<>();
        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            var c = creditors.poll();
            var d = debtors.poll();
            long amt = Math.min(c.getValue(), -d.getValue());
            out.add(new Transfer(d.getKey(), c.getKey(), amt));
            if (c.getValue() - amt > 0) creditors.add(Map.entry(c.getKey(), c.getValue() - amt));
            if (d.getValue() + amt < 0) debtors.add(Map.entry(d.getKey(), d.getValue() + amt));
        }
        return out;
    }
}

06Concurrency and edge cases

  • Atomic application. An expense among five people updates four pairs and five nets. With per-key ConcurrentHashMap.merge each update is atomic but the expense is not: a concurrent show can see two of four debts. A per-group lock (or a ReadWriteLock if reads dominate) fixes it. Non-group expenses between friends use a lock per user pair, taken in sorted order.
  • Idempotency. A client-generated expense id (or Idempotency-Key header) checked under the same lock as the write. A mobile app retrying on a timeout must not add the dinner twice.
  • Money invariants. Sum of shares == total, checked after every strategy. Sum of nets in a group == 0; assert it in tests.
  • double is wrong. 0.1 + 0.2 != 0.3, and 100.0 / 3 * 3 loses a paisa. Errors accumulate across thousands of expenses and balances stop netting to zero.
  • BigDecimal traps. new BigDecimal(0.1) captures the binary error, so use BigDecimal.valueOf or the String constructor. equals compares scale (2.0 ≠ 2.00); use compareTo. divide without a scale and rounding mode throws ArithmeticException on 1/3. Do not use BigDecimal as a HashMap key without normalising scale.
  • Validation. Percentages sum to exactly 100; exact amounts sum to the total; no negative values; payer and participants are group members; duplicate participants merged or rejected.
  • Self-share. The payer's own share creates no debt (addDebt ignores debtor == creditor).
  • Over-settlement. Settling more than owed flips the direction. Either reject it or allow it explicitly (some apps do).
  • Time. Inject Clock for createdAt so history ordering is testable.

07Extensions interviewers add mid-round

Add a new split type (shares, adjustment, "everyone equal except +₹200 for u1")

One new SplitStrategy registered in the map. Adjustment split = exact adjustments first, the remainder via EqualSplit; reuse Allocation. No change to the service or the balance sheet.

Simplify debts / minimise transactions (Uber)

Net each user's balance, then greedy-match the largest creditor with the largest debtor: at most n−1 transfers, O(n log n). The true minimum is NP-hard (it reduces to partitioning users into the most zero-sum subsets); LeetCode 465 solves it by backtracking for about a dozen people. Mention that simplification changes who pays whom, which is why Splitwise makes it a group setting users opt into.

Multiple payers

Map<String, Long> paid on the expense. Each user's net effect = paid − share. Apply it by creating debts from users with negative effect to users with positive effect (a small greedy match within the expense), or keep only per-user net if pairwise detail is not required.

Edit an expense

Under the group lock: reverse the old shares, compute and apply the new ones, store a new version. Keep the ledger append-only (an edit is a reversal plus a new entry) so history and audit stay correct.

Multi-currency

Balances keyed by (pair, currency). Never auto-convert inside the ledger. Convert only at settle-up with a recorded FX rate.

Persist it / scale it (HLD follow-up)

Tables: expense, expense_share(expense_id, user_id, amount_paise), balance(group_id, user_a, user_b, amount_paise) with a primary key on (group, a, b). Insert the expense and update the balances in one transaction with UPDATE … SET amount = amount + ? (row locks per pair, taken in sorted order to avoid deadlocks). Or keep only the ledger and derive balances, caching them per group. Shard by group id; non-group friend balances by the sorted user pair.

Notifications and activity feed

Publish an ExpenseAdded event after commit (outbox → Kafka); the notification and feed services consume it. Keep the core service synchronous and small.

09Mistakes that got candidates rejected

Rejected for this
  • double for money, or BigDecimal with equals and unbounded divide. Rounding bugs show up in the first demo.
  • Equal split that drops the leftover paisa, so shares do not sum to the total.
  • A growing list of IOUs per user instead of a netted balance per pair; output shows "u1 owes u2 100" and "u2 owes u1 40" at the same time.
  • if (type == EQUAL) … else if (type == PERCENT) … inside the service: the extensibility question fails immediately.
  • Unfinished service layer with nice entities (Walmart feedback: "focus more on service completion").
  • Claiming the greedy simplification is optimal.
  • No driver or tests: the interviewer cannot see it work.

Code-review viva

Why long paise instead of BigDecimal?

Exact, fast, no scale or equals traps, and Long::sum works with merge. BigDecimal is still used at the edges, for parsing and for weighted division. With multiple currencies the minor unit varies (JPY has 0 decimals, KWD has 3), so store the currency's exponent with the amount.

Why store per-pair balances and per-user nets?

Pairs answer "who owes whom" in O(1) per pair. Nets feed simplification and the "you are owed ₹X in total" summary without scanning pairs.

Is your per-group synchronized a bottleneck?

Only for one group, and a group sees a few writes per minute. Different groups run in parallel. A database version would take row locks per pair instead.

Who gets the extra paisa, and is that fair?

It is deterministic (input order, or the payer), documented, and at most one paisa per person. The real requirement is that the sum is exact and the result is reproducible.

What is the time complexity of addExpense and simplify?

addExpense is O(p log p) for p participants (the sort in largest-remainder); equal split can be O(p). Simplify is O(n log n) for n users with non-zero balances.
