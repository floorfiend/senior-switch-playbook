Splitwise / Expense Sharing

Splitwise tracks who owes whom after shared spending, like a Goa trip with friends. By the end, you can code an expense-sharing service that is exact to the paisa. You can add new ways to split a bill without touching the service. And the balances stay correct when many people add expenses at once.

Time-box: 90 min (Navi) to 2 h (Groww) Seen: about 7 interview reports, 2025–26 Format: shared IDE, a main() driver, or command-line commands
GrowwNaviWalmartSwiggySalesforceUberRippling
In 30 seconds
  • Store money as a whole number of paise in a long. The shares must always add up exactly to the total.
  • Each way of splitting is its own Strategy class. The service never checks "which split type is this?".
  • Keep one signed number per pair of users. Update it while holding the group's lock.
  • Simplify debts with a greedy method. Finding the true minimum is NP-hard, meaning too slow for big groups.
Picture it

Think of a shared notebook in a hostel room. Nobody writes every IOU. Each pair of roommates keeps one running number instead. Split ₹100 three ways and you get 33.34 + 33.33 + 33.33. Someone has to take the extra paisa.

Words you'll see
Paise
1/100 of a rupee. We store ₹100.50 as the whole number 10050, so there are no rounding errors.
Split type
How a bill is shared: equally, by exact amounts, by percentage, or by shares (like 2 shares for one person, 1 for another).
Balance / net
After all expenses, how much one person owes another. A positive net means you are owed money overall.
Settle up
Recording a real payment, like a UPI transfer, that reduces what someone owes.
Debt simplification
Reducing the number of payments needed. Instead of A pays B and B pays C, A pays C directly.
Idempotent
Doing it twice has the same effect as once. If the app retries "add dinner", the dinner is still added once.
Invariant
A rule that must always be true. Here, shares add up to the total, and a group's balances add up to zero.
NP-hard
A problem with no known fast exact solution. The time explodes as the input grows.

01What the interviewer is grading

Money correctness

Whole-number paise. Shares add up exactly. The extra paisa always goes to the same person by a fixed rule.

Extensibility

A new split type is one new strategy class.

Balance model

One net number per pair, not an ever-growing list of IOUs.

Completeness

It runs end to end. Walmart's only criticism was an unfinished service.

Go deeper: how the rounds ran and the full grading list

Groww's SDE-II machine coding round gave two hours to "build Splitwise". The candidate who got the offer built the core features. They checked them with several test cases run from a main class. Navi gave 90 minutes onsite for an expense tracker "similar to Splitwise". The focus was on classes, interfaces and extensibility, before the core code. Walmart's SDE-III LLD round had the candidate open an IDE. The requirements covered users, groups, expenses, balances and settle-up. Split types were equal, percentage and exact, but only equal had to be coded. The candidate modelled Split as an abstract class, with a Strategy per type. Feedback was positive, with "focus more on service completion", because the service was only 70% done. Swiggy asked for splits by user percentage. Uber took it into high-level design with debt minimisation. Rippling's coding rounds allowed AI tools and stressed clean classes and the best complexity. A delivery-cost problem there is a reminder that money in a double breaks at the paisa.

The task covers users and groups, and expenses split equally, by exact amounts, by percentage or by shares. It also needs a balance sheet showing who owes whom. It looks easy, and that is the trap. Interviewers grade money handling. That means no double, and remainders that add up to the paisa. They grade a Strategy interface for split types, and balances that stay correct with writes at the same time. They also want a clear answer on debt simplification.

  • Money correctness. Use whole-number paise or BigDecimal. Shares always add up exactly to the total. Hand out leftover paise by a fixed rule.
  • Extensibility. A new split type is one new strategy class. Each strategy checks its own inputs.
  • Balance model. One net number per pair, not a growing list of IOUs. Each participant costs O(1) to update.
  • Completeness. The service runs end to end with a driver. Walmart's only criticism was an unfinished service.
  • Concurrency. Adding an expense happens as one step. A reader never sees half of a split among several people.
  • Algorithms. Simplify debts greedily in O(n log n). Know that the true minimum is NP-hard.

03Requirements

Functional

  • Users, groups and members.
  • Add an expense with payer, total and split.
  • Show balances that are not zero.
  • Settle up, simplify, and show history.

Non-functional

  • Exact to the paisa. A group's nets add up to zero.
  • Thread-safe. Retries don't add an expense twice.
  • Work grows only with the number of participants.

Out of scope

  • UPI payments, notifications, login.
  • Saving to a database, exchange rates.
Go deeper: full requirement list
  • Create users and groups. Add members.
  • Add an expense: payer, total, participants, split type and values.
  • Show balances for everyone, for one user, or for one group. Show only entries that are not zero.
  • Settle up (record a payment), fully or partly.
  • Simplify group debts when asked.
  • Expense history per group and per user.
  • Exact to the paisa. All balances in a group always add up to zero. Adding an expense is thread-safe and idempotent. Each expense costs O(participants). Looking up a pair costs O(1).
  • Out of scope (say so): real payments (UPI integration), notifications and login. Also saving data, so only repository interfaces. Also exchange rates, but keep balances per currency if asked.

06The race and the fix

The bug: BalanceSheet uses a plain HashMap, and two expenses update the same pair at the same time:

TimeThread A (u2 owes u1 100)Thread B (u2 owes u1 50)pair(u1,u2)
t1reads 00
t2reads 00
t3writes −100−100
t4writes −50−50: ₹100 lost

The fix is to apply the whole expense inside synchronized (group). Only one expense per group is applied at a time.

TimeThread AThread Bpair(u1,u2)
t1enters group lock, reads 0blocks on group lock0
t2writes −100, nets, exitswaiting−100
t3enters, reads −100−100
t4writes −150, exits−150: both counted
Why per-key atomics are not enough
  • ConcurrentHashMap.merge makes each pair's update safe. But a five-person expense touches four pairs and five nets. A show running at the same time could see only half.
  • The "already added?" check must sit under the same lock as the write.
  • For expenses between friends outside a group, lock the pair of users, in sorted order.
Go deeper: every concurrency and edge case
  • Apply as one step. An expense among five people updates four pairs and five nets. With ConcurrentHashMap.merge per key, each update is safe, but the expense as a whole is not. A show running at the same time can see two of four debts. A lock per group fixes it. If reads are much more common than writes, use a ReadWriteLock. Expenses between friends outside a group use a lock per pair of users, taken in sorted order.
  • Idempotency. The app creates the expense id (or sends an Idempotency-Key header). Check it under the same lock as the write. A phone app that retries after a timeout must not add the dinner twice.
  • Money invariants. After every strategy, check that the shares add up to the total. A group's nets must add up to 0. Assert this in tests.
  • double is wrong. 0.1 + 0.2 != 0.3, and 100.0 / 3 * 3 loses a paisa. Errors pile up over thousands of expenses, and balances stop adding up to zero.
  • BigDecimal traps. new BigDecimal(0.1) copies the tiny binary error of the double. Use BigDecimal.valueOf or the String constructor. equals also compares the number of decimal places, so 2.0 ≠ 2.00. Use compareTo. divide without a scale and rounding mode throws ArithmeticException on 1/3. Don't use BigDecimal as a HashMap key unless you first normalise the decimal places.
  • Validation. Percentages add up to exactly 100. Exact amounts add up to the total. No negative values. The payer and participants are group members. A participant listed twice is merged or refused.
  • Own share. The payer's own share creates no debt. addDebt ignores the case where debtor and creditor are the same.
  • Paying too much. Settling more than you owe flips the direction of the debt. Either refuse it, or allow it on purpose (some apps do).
  • Time. Pass in a Clock for createdAt, so the order of history can be tested.

Show Money (parse once, compute in paise) 
public final class Money {
    private Money() {}

    /** "1000.5" -> 100050. Throws on more than 2 decimals or overflow; never goes through double. */
    public static long parse(String rupees) {
        return new BigDecimal(rupees).setScale(2, RoundingMode.UNNECESSARY).movePointRight(2).longValueExact();
    }

    public static String format(long paise) {
        return BigDecimal.valueOf(paise, 2).toPlainString();   // 100050 -> "1000.50"
    }
}

long paise are exact and fast, with no equals traps. If the interviewer prefers BigDecimal everywhere, that is fine too. Just know the traps listed in section 06.

Show split strategies (exact remainder allocation) 
public record Participant(String userId, BigDecimal value) {
    public static Participant of(String userId) { return new Participant(userId, BigDecimal.ONE); }
}

public interface SplitStrategy {
    Map<String, Long> split(long totalPaise, List<Participant> participants);
}

final class Allocation {
    /**
     * Largest-remainder method: floor each weighted share, then hand leftover paise to the largest
     * fractional parts (ties broken by input order). The result always sums to total.
     */
    static Map<String, Long> byWeights(long total, List<Participant> ps) {
        BigDecimal sum = ps.stream().map(Participant::value).reduce(BigDecimal.ZERO, BigDecimal::add);
        if (sum.signum() <= 0) throw new IllegalArgumentException("weights must be positive");
        long[] floor = new long[ps.size()];
        BigDecimal[] frac = new BigDecimal[ps.size()];
        long allocated = 0;
        for (int i = 0; i < ps.size(); i++) {
            BigDecimal exact = BigDecimal.valueOf(total).multiply(ps.get(i).value())
                    .divide(sum, 10, RoundingMode.DOWN);
            floor[i] = exact.setScale(0, RoundingMode.DOWN).longValueExact();
            frac[i] = exact.subtract(BigDecimal.valueOf(floor[i]));
            allocated += floor[i];
        }
        Integer[] order = IntStream.range(0, ps.size()).boxed().toArray(Integer[]::new);
        Arrays.sort(order, (a, b) -> frac[b].compareTo(frac[a]));   // stable: ties keep input order
        for (int k = 0; k < total - allocated; k++) floor[order[k]]++;
        Map<String, Long> out = new LinkedHashMap<>();
        for (int i = 0; i < ps.size(); i++) out.merge(ps.get(i).userId(), floor[i], Long::sum);
        return out;
    }
}

public final class EqualSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<Participant> ps) {
        return Allocation.byWeights(total, ps.stream().map(p -> Participant.of(p.userId())).toList());
    }
}

public final class PercentSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<Participant> ps) {
        BigDecimal sum = ps.stream().map(Participant::value).reduce(BigDecimal.ZERO, BigDecimal::add);
        if (sum.compareTo(BigDecimal.valueOf(100)) != 0) throw new InvalidSplit("percentages sum to " + sum);
        return Allocation.byWeights(total, ps);
    }
}

public final class ShareSplit implements SplitStrategy {      // "2 shares for u1, 1 for u2"
    public Map<String, Long> split(long total, List<Participant> ps) { return Allocation.byWeights(total, ps); }
}

public final class ExactSplit implements SplitStrategy {
    public Map<String, Long> split(long total, List<Participant> ps) {
        Map<String, Long> out = new LinkedHashMap<>();
        for (Participant p : ps) out.merge(p.userId(), Money.parse(p.value().toPlainString()), Long::sum);
        long sum = out.values().stream().mapToLong(Long::longValue).sum();
        if (sum != total) throw new InvalidSplit("exact amounts sum to " + Money.format(sum));
        return out;
    }
}
Show BalanceSheet (one signed number per pair) 
public final class BalanceSheet {
    /** Key (a, b) with a < b. Positive value: a owes b. Negative: b owes a. */
    private record Pair(String a, String b) {}
    private final Map<Pair, Long> pairs = new HashMap<>();
    private final Map<String, Long> net = new HashMap<>();   // positive = is owed money

    void addDebt(String debtor, String creditor, long paise) {
        if (debtor.equals(creditor) || paise == 0) return;
        boolean ordered = debtor.compareTo(creditor) < 0;
        Pair key = ordered ? new Pair(debtor, creditor) : new Pair(creditor, debtor);
        pairs.merge(key, ordered ? paise : -paise, Long::sum);
        pairs.remove(key, 0L);                                  // keep only non-zero balances
        net.merge(creditor, paise, Long::sum);
        net.merge(debtor, -paise, Long::sum);
    }

    /** Lines like "u2 owes u1: 250.00" involving the user, or all when user is null. */
    List<String> describe(String user) {
        List<String> lines = new ArrayList<>();
        pairs.forEach((k, v) -> {
            if (user != null && !k.a().equals(user) && !k.b().equals(user)) return;
            String debtor = v > 0 ? k.a() : k.b();
            String creditor = v > 0 ? k.b() : k.a();
            lines.add(debtor + " owes " + creditor + ": " + Money.format(Math.abs(v)));
        });
        return lines;
    }

    Map<String, Long> netByUser() { return Map.copyOf(net); }
}
Show ExpenseService (validate, split, apply atomically, idempotent) 
public record Expense(String id, String groupId, String paidBy, long total,
                      SplitType type, Map<String, Long> shares, String description, Instant createdAt) {}

public record Group(String id, String name, Set<String> members, BalanceSheet balances) {}

public final class ExpenseService {
    private final Map<SplitType, SplitStrategy> strategies;
    private final Map<String, Group> groups = new ConcurrentHashMap<>();
    private final Map<String, Expense> expenses = new ConcurrentHashMap<>();
    private final Clock clock;

    public ExpenseService(Map<SplitType, SplitStrategy> strategies, Clock clock) {
        this.strategies = Map.copyOf(strategies); this.clock = clock;
    }

    /** expenseId is client-supplied, so a retried request does not record the expense twice. */
    public Expense addExpense(String expenseId, String groupId, String paidBy, String amount,
                              SplitType type, List<Participant> participants, String description) {
        Group g = group(groupId);
        long total = Money.parse(amount);
        if (total <= 0) throw new InvalidSplit("amount must be positive");
        if (participants.isEmpty()) throw new InvalidSplit("no participants");
        Set<String> involved = new HashSet<>();
        involved.add(paidBy);
        participants.forEach(p -> involved.add(p.userId()));
        if (!g.members().containsAll(involved)) throw new InvalidSplit("non-member in expense");

        Map<String, Long> shares = strategies.get(type).split(total, participants);
        // Belt and braces: every strategy must conserve money.
        if (shares.values().stream().mapToLong(Long::longValue).sum() != total) throw new IllegalStateException();

        synchronized (g) {                                  // per-group: one expense applies fully or not at all
            Expense existing = expenses.get(expenseId);
            if (existing != null) return existing;
            Expense e = new Expense(expenseId, groupId, paidBy, total, type, Map.copyOf(shares), description, clock.instant());
            shares.forEach((user, share) -> g.balances().addDebt(user, paidBy, share));
            expenses.put(expenseId, e);
            return e;
        }
    }

    public void settle(String groupId, String from, String to, String amount) {
        Group g = group(groupId);
        long paise = Money.parse(amount);
        synchronized (g) { g.balances().addDebt(to, from, paise); }   // a payment is a debt in reverse
    }

    public void deleteExpense(String expenseId) {
        Expense e = Optional.ofNullable(expenses.get(expenseId)).orElseThrow();
        Group g = group(e.groupId());
        synchronized (g) {
            if (expenses.remove(expenseId) == null) return;
            e.shares().forEach((user, share) -> g.balances().addDebt(e.paidBy(), user, share));  // reverse
        }
    }

    public List<String> show(String groupId, String userOrNull) {
        Group g = group(groupId);
        synchronized (g) { return g.balances().describe(userOrNull); }
    }

    private Group group(String id) {
        return Optional.ofNullable(groups.get(id)).orElseThrow(() -> new NoSuchElementException("group " + id));
    }
}
Show DebtSimplifier (greedy with two heaps) 
public record Transfer(String from, String to, long paise) {}

public final class DebtSimplifier {
    /** At most n-1 transfers. Not always the global minimum (that problem is NP-hard). */
    public List<Transfer> simplify(Map<String, Long> net) {
        Comparator<Map.Entry<String, Long>> byAmountDesc =
                Comparator.comparingLong((Map.Entry<String, Long> e) -> Math.abs(e.getValue())).reversed()
                          .thenComparing(Map.Entry::getKey);                       // deterministic output
        PriorityQueue<Map.Entry<String, Long>> creditors = new PriorityQueue<>(byAmountDesc);
        PriorityQueue<Map.Entry<String, Long>> debtors = new PriorityQueue<>(byAmountDesc);
        net.forEach((u, v) -> {
            if (v > 0) creditors.add(Map.entry(u, v));
            else if (v < 0) debtors.add(Map.entry(u, v));
        });
        List<Transfer> out = new ArrayList<>();
        while (!creditors.isEmpty() && !debtors.isEmpty()) {
            var c = creditors.poll();
            var d = debtors.poll();
            long amt = Math.min(c.getValue(), -d.getValue());
            out.add(new Transfer(d.getKey(), c.getKey(), amt));
            if (c.getValue() - amt > 0) creditors.add(Map.entry(c.getKey(), c.getValue() - amt));
            if (d.getValue() + amt < 0) debtors.add(Map.entry(d.getKey(), d.getValue() + amt));
        }
        return out;
    }
}

08Extensions interviewers add mid-round

Simplify debts (Uber)

Greedy usual pick

  • Match whoever is owed the most with whoever owes the most
  • At most n−1 payments, in O(n log n)
  • Not always the fewest payments

Exact minimum

  • The fewest payments possible
  • NP-hard: you must find the most groups of people whose debts cancel to zero
  • Backtracking works for about 12 people at most (LeetCode 465)

New split type

One new strategy. For an adjustment split, apply the fixed extras first, then split the rest equally.

Multiple payers

Store a Map of who paid what. Each person's effect is paid minus share.

Edit expense

Undo the old shares, then apply the new ones. The ledger only ever grows.

Multi-currency

Keep balances per pair and per currency. Convert only when settling up.

Persist and scale

Save the expense and balance rows in one transaction. Split data across databases by group.

Notifications

After saving, publish an ExpenseAdded event using the outbox pattern.

Go deeper: full answers for each extension
Add a new split type (shares, adjustment, "everyone equal except +₹200 for u1")

Add one new SplitStrategy and register it in the map. An adjustment split applies the exact extras first, then splits the rest with EqualSplit. Reuse Allocation. The service and the balance sheet don't change.

Simplify debts / minimise transactions (Uber)

Work out each user's net balance. Then greedily match whoever is owed the most with whoever owes the most. This needs at most n−1 payments and runs in O(n log n). The true minimum is NP-hard. It means splitting users into as many groups as possible whose debts cancel to zero. LeetCode 465 solves it by backtracking for about a dozen people. Mention that simplifying changes who pays whom. That is why Splitwise makes it a group setting users choose to turn on.

Multiple payers

Add a Map<String, Long> paid to the expense. Each user's net effect is paid minus share. Apply it by creating debts from users with a negative effect to users with a positive one, using a small greedy match within the expense. Or keep only each user's net, if you don't need per-pair detail.

Edit an expense

While holding the group lock, undo the old shares. Then work out and apply the new ones, and store a new version. Keep the ledger append-only, meaning you only add entries and never change old ones. An edit is an undo entry plus a new entry. This keeps history and audit correct.

Multi-currency

Key balances by pair and currency. Never convert automatically inside the ledger. Convert only at settle-up, and record the exchange rate used.

Persist it / scale it (HLD follow-up)

Tables: expense, expense_share(expense_id, user_id, amount_paise), and balance(group_id, user_a, user_b, amount_paise) with a primary key on (group, a, b). Insert the expense and update the balances in one transaction, with UPDATE … SET amount = amount + ?. This locks each pair's row. Take the rows in sorted order to avoid deadlocks. Or keep only the ledger, work out balances from it, and cache them per group. Shard (split the data across databases) by group id. Shard balances between friends outside groups by the sorted user pair.

Notifications and activity feed

After the save commits, publish an ExpenseAdded event. Use the outbox pattern: save the event in the same transaction, and a separate process sends it to Kafka. The notification and feed services read it from there. Keep the core service small and synchronous.

09Tests to write

Money

₹100 / 3 gives 33.34, 33.33, 33.33. Percentages that don't add up to 100 are refused. So is "10.005".

Balances

Pairs net out across expenses. Settling clears them. Delete undoes. Adding twice with one id counts once.

Invariants

Group nets add up to 0 for random expenses. 32 threads give the same result as running one by one.

12Quick check

You split ₹100 equally among 3 people. What must the shares be?

No money may appear or vanish, so the shares must add up to exactly ₹100. The rule for the extra paisa must be fixed, so you get the same answer every time.

The interviewer asks for an "adjustment" split. What should change?

If adding a split type means editing the service, your design fails the extensibility question. A new strategy class keeps the service untouched.

Pair updates already use ConcurrentHashMap.merge. Why still lock the group?

Each merge is safe on its own. But one expense makes several updates, and the group lock makes them happen as one step.

Does greedy debt simplification always give the fewest payments?

The true minimum needs the most groups of people whose debts cancel to zero. Searching for that only works for about a dozen people.

13Interview questions

Why long paise instead of BigDecimal?

Whole-number paise are exact and fast. There are no traps with decimal places or equals. And Long::sum works with merge. BigDecimal is still used at the edges, for reading input and for weighted division. With several currencies, the smallest unit differs. The Japanese yen (JPY) has 0 decimals and the Kuwaiti dinar (KWD) has 3. So store the currency's number of decimals with the amount.

Why store per-pair balances and per-user nets?

Pairs answer "who owes whom" in O(1) per pair. Nets feed simplification and the "you are owed ₹X in total" summary, without scanning every pair.

Is your per-group synchronized a bottleneck?

Only within one group, and a group sees a few writes per minute. Different groups run in parallel. A database version would lock each pair's row instead.

Who gets the extra paisa, and is that fair?

It follows a fixed, written rule, such as input order or the payer. It is at most one paisa per person. What really matters is that the total is exact and the result is the same every time.

What is the time complexity of addExpense and simplify?

addExpense is O(p log p) for p participants, because the largest-remainder method sorts. Equal split can be O(p). Simplify is O(n log n) for n users whose balance is not zero.

Cheat sheet
  • Store long paise. Read input with BigDecimal, never double.
  • Largest remainder: round everyone down, then hand leftover paise to the biggest fractions. Break ties by order.
  • Use a Map<SplitType, SplitStrategy>. Each strategy checks its own input.
  • BalanceSheet: one signed number per sorted pair, plus each user's net.
  • Settle is addDebt in reverse. Delete undoes the shares.
  • Put synchronized (group) around the "already added?" check and all updates.
  • Invariants: shares add up to the total, and a group's nets add up to 0.
  • Simplify: greedy with two heaps, at most n−1 payments. The true minimum is NP-hard.
