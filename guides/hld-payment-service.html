Payment Service

Design a payment service that never charges twice and never loses money, even when the bank times out.

Time-box: 45–60 min (Angel One ran 1 h+) Seen: Angel One, Paytm ×2, Kotak, PhonePe, Slice, Rippling, 2025–26
Angel OnePaytmPhonePeKotakSliceRipplingRazorpay
In 30 seconds
  • Idempotency key per hop: client → you → PSP.
  • A bank timeout is PENDING, never FAILED.
  • Outbox table, not "commit then publish to Kafka".
  • Double-entry ledger plus daily reconciliation catch everything else.
Picture it

You pay at a toll plaza with FASTag and the screen freezes. Did it deduct? You do not pay again in cash; you wait for the SMS or check the statement. A payment service does the same: "unknown" is a real state, resolved later.

01What the interviewer is grading

Idempotency end to end

Client → your API → PSP. Each hop needs its own key.

UNKNOWN / PENDING state

Treating a timeout as failure is the classic double-charge bug.

DB + Kafka atomicity

"Commit then publish" loses events; a transactional outbox fixes it.

Money correctness

Double-entry ledger, immutable entries, balances derived not overwritten.

Reconciliation

The daily process that catches what everything else missed.

Partner failure

Retry only where safe, circuit breakers, routing across PSPs.

Go deeper: what the reports said

The Angel One SDE-2 round (Sep 2026, selected) ran over an hour with deep dives on database commits and transaction handling, Kafka streams, partner bank failures, vendor payment flow, and payment failures and retries. Paytm asked a Shiprocket-like system (order management plus payments) and a Paytm risk management service with a database focus. Kotak's screening asked "what is an idempotency key and how would you use it for placing an order". PhonePe probes double payment, Slice wallet consistency, Rippling idempotent metrics ingestion.

02Clarify and scope

Functional

  • Create payment for an order, redirect / intent to PSP
  • Receive result via webhook and status poll
  • Refunds (full / partial), vendor payouts
  • Payment history, ledger, daily reconciliation

Non-functional

  • Zero double charges; zero lost payments
  • 99.99% availability for create; p99 < 300 ms (excluding PSP)
  • Every rupee traceable; immutable audit
  • PCI DSS: never store card data (tokenise at PSP); RBI data localisation

Out of scope

  • Building a card network or UPI switch
  • Full fraud ML (risk check is a hook)
  • Tax / invoicing
Go deeper: five questions to ask first
  • Are we a merchant integrating PSPs (Razorpay / Juspay / Stripe) or the PSP talking to banks / NPCI? Most rounds mean the former: an internal payment service for an app (broker, e-commerce).
  • Payment methods? UPI (async: collect / intent, result comes later), cards (3DS redirect), netbanking, wallet. UPI being asynchronous forces the PENDING state.
  • Flows? Pay-in (user pays), refunds, payouts to vendors (Angel One "vendor payment flow"), wallet top-up.
  • Authorise and capture separately? Cards support it; e-commerce often captures on shipment.
  • Consistency expectation? Money moves must be strongly consistent and auditable; read models (history screen) can lag.

The key is client-generated and scoped by caller (merchant_id + key). Tie it to the business intent: for an order, orderId plus attempt number. A random UUID per click is useless against a user tapping "Pay" twice; the order id is what makes the second tap a no-op (PhonePe's double-payment question).

Postgres (or MySQL) for the money path. You need ACID transactions across payment, ledger and outbox rows, unique constraints for idempotency, and row locks. Shard by merchant_id or user_id (Citus or app-level) when one primary is not enough. Kafka carries events to order, notification and analytics services; it is never the source of truth for balances. Amounts are integers in minor units (paise).

  • Payment service owns the state machine. All transitions go through one method with a conditional update on (status, version).
  • Risk check (the Paytm risk-management variant) runs synchronously before calling the PSP: velocity counters in Redis (payments per user per hour, per device, per card fingerprint), rule engine, ML score; it returns ALLOW / REVIEW / BLOCK within a hard timeout and fails open or closed by amount.
  • PSP router picks a gateway by method, success rate over the last 5 minutes, and cost. A circuit breaker per PSP (Resilience4j) removes a degraded bank from rotation.
  • Webhook receiver verifies the HMAC signature, stores the raw event, returns 200 in milliseconds, and processes asynchronously. PSPs retry webhooks for hours; dedupe by PSP event id.
  • Status poller queries the PSP for payments stuck in PENDING beyond a threshold (e.g. 2, 5, 15, 60 minutes).
  • Reconciliation ingests settlement files (T+1) and compares line by line.

06Deep dives

6.1 Idempotency done properly

  1. ClaimINSERT … 'IN_PROGRESS' ON CONFLICT DO NOTHING. 1 row → you own it. 0 rows → read the existing row.
  2. ReplayDONE + same hash → replay response. Different hash → 422. IN_PROGRESS → 409; stale locked_at → take over.
  3. Phase 1Create payment (CREATED) and commit.
  4. Phase 2Call the PSP with our payment id as its idempotency key.
  5. Phase 3Record result, ledger, outbox and final response on the key row, in one transaction.

Key in the DB, same txn usual pick

  • Correct under crashes
  • Extra write per request

Default for money.

Key in Redis (SETNX)

  • Fast, cheap
  • Not atomic with the DB commit; lost on eviction

Non-financial dedup (metrics, notifications).

Go deeper: the full idempotency algorithm
  1. INSERT INTO idempotency_keys (scope, key, request_hash, status) VALUES (..., 'IN_PROGRESS') ON CONFLICT DO NOTHING. Inserted one row → you own the request. Zero rows → read the existing row.
  2. Existing and DONE with the same hash → replay the stored response. Different hash → 422. IN_PROGRESS → 409, or wait briefly; if locked_at is stale (crash), take over.
  3. Do the work. Persist the payment row, ledger entries, outbox row and the final response on the key row in one transaction.
  4. External calls (PSP) cannot be in that transaction, so split the request into atomic phases with recovery points: phase 1 creates the payment (CREATED) and commits; phase 2 calls the PSP with our payment id as the PSP's idempotency key / merchant reference; phase 3 records the result. A retry resumes from the last committed phase. This is Stripe's (Brandur's) recovery-point pattern and Airbnb's Orpheus "pre-RPC, RPC, post-RPC" split.

Keep the key row 24 h to 7 days. Store it in the same database as the payment so the check and the write share a transaction; a Redis-only check has a window where Redis says "new" and the DB already committed.

6.2 The payment state machine

Legal moves only; terminal states never go back
Show Java transition method
// single place where status changes; webhook, poller and recon all call this
@Transactional
public boolean transition(String paymentId, Status from, Status to, Source src, String payload) {
    int rows = jdbc.update("""
        UPDATE payments SET status = ?, version = version + 1, updated_at = now()
        WHERE payment_id = ? AND status = ?""", to.name(), paymentId, from.name());
    if (rows == 0) return false;                 // someone else moved it: idempotent no-op
    events.append(paymentId, from, to, src, payload);
    if (to == Status.SUCCEEDED) ledger.postCapture(paymentId);   // same txn
    outbox.add(paymentId, "PAYMENT_" + to.name(), payload);       // same txn
    return true;
}
Go deeper: the UNKNOWN problem in full

Figure: PROCESSING and PENDING can also go to FAILED. Terminal states never move backwards.

When the bank call times out, you do not know whether money moved. Marking it FAILED and letting the user retry is how double payments happen: the first debit succeeds at the bank, the retry debits again. Instead move to PENDING, show "payment processing", and resolve it from the webhook, the status poller, or reconciliation. Only retry the PSP call with the same merchant reference, so the PSP deduplicates. If the user insists on paying again, create attempt 2 on the same order, and auto-refund whichever attempt succeeds second ("order already paid" check on success).

Webhook and poller can race to report success; the conditional update lets exactly one win. Out-of-order events (FAILED webhook after SUCCEEDED) are rejected by the allowed-transition table.

Go deeper: outbox and sagas

"Update the payment, then publish to Kafka" breaks in both orders: commit then crash before publish loses the event (order never ships); publish then rollback announces a payment that does not exist. Write the event to an outbox table in the same transaction, and have Debezium (CDC on the WAL) or a poller publish it to Kafka. Delivery is at-least-once, so consumers dedupe on event id. Kafka transactions do not help here, because they cannot span Postgres. For the Shiprocket-style order + payment flow, the order service consumes PAYMENT_SUCCEEDED and moves the order on; if the order cannot be fulfilled, it issues a refund command (a saga with compensation, not a 2PC).

6.4 Double-entry ledger and wallet consistency

Every money movement is at least two entries that sum to zero. ₹499 UPI payment, ₹5 gateway fee:

AccountDebitCredit
PSP_RECEIVABLE₹494
GATEWAY_FEES (expense)₹5
MERCHANT_PAYABLE / revenue₹499

Immutable

Corrections are new reversing entries, never edits.

Wallet debit

UPDATE … SET balance = balance - ? WHERE … AND balance >= ? plus the ledger insert, one transaction. Cannot overdraw.

Hot accounts

A merchant receiving thousands/s locks one row. Split into sub-accounts or batch credits.

Go deeper: ledger details

Entries are immutable; corrections are new reversing entries. Balances are the sum of entries, cached on the account row and updated in the same transaction. For a wallet (Slice), a debit does UPDATE accounts SET balance = balance - ? , version = version + 1 WHERE account_id = ? AND balance >= ?: one atomic statement that cannot overdraw, plus the ledger insert in the same transaction. For very hot accounts (a merchant receiving thousands per second), shard the account into sub-accounts or batch credits, since every write locks one row. Uber's payments platform follows the same zero-sum principle and stores ledgers in an immutable store (LedgerStore).

Go deeper: reconciliation in full

Every morning, download the PSP / bank settlement file for T−1 and match it against payments by psp_ref and amount. Outcomes:

  • MATCHED: nothing to do.
  • PSP says success, we say PENDING / FAILED: money was taken. Move to SUCCEEDED (fulfil) or auto-refund if the order is cancelled.
  • We say success, PSP has no record: high severity; investigate before settlement to merchant.
  • Amount mismatch: fee or partial capture issue; to the finance ops queue.

Reconciliation is why the design is allowed to be eventually consistent with the outside world: every mechanism before it can fail, and recon still catches it within a day.

08Scaling, failure handling and consistency

Partner bank down

Circuit breaker per PSP; route new payments elsewhere. Never re-route an in-flight payment: that can debit twice.

Retry policy

Only idempotent calls; backoff with jitter; cap; then DLQ and alert. No retry on 4xx business errors.

Timeouts

PSP timeout below the user timeout (10 s vs 30 s). Timeout = PENDING.

Database

Sync replica in another AZ (RPO 0). Monthly partitions; archive old ones.

10× / 100×

Shard by merchant or user; active-passive regions for money, active-active reads.

Go deeper: full scaling notes
  • Partner bank down (Angel One). Circuit breaker per PSP / bank with success-rate thresholds; router fails over new payments to a secondary PSP. In-flight payments at the failed PSP stay PENDING and resolve via poll / recon; never re-route an in-flight payment to another PSP (that can debit twice).
  • Retry policy. Retry only idempotent calls or calls with a PSP idempotency key; exponential backoff with jitter; cap attempts; then park in a DLQ topic and alert. Do not retry on 4xx business errors (insufficient funds).
  • Timeouts. Set PSP client timeouts below the user-facing timeout (e.g. 10 s vs 30 s), and treat timeout as PENDING.
  • Webhook storms. Receiver only persists and enqueues; consumers scale out; per-payment ordering via Kafka key = payment_id.
  • Database. Primary with synchronous replica in another AZ (RPO 0 for money), async replica for reads. Partition payments and ledger_entries by month; archive older partitions.
  • 10× / 100×. Shard by merchant or user; ledger hot accounts split; outbox relay scales per shard. Multi-region active-passive for the money path (avoid multi-master on balances); read APIs can be active-active.
  • Idempotent metrics (Rippling). Events carry ids; the aggregator keeps a dedup set per window (or uses upserts keyed by event id) so retried publishes do not double-count.

09Mistakes that got candidates rejected

Rejected for this
  • Treating a PSP timeout as failure and letting the user retry.
  • "Save to DB then publish to Kafka" with no outbox, or calling the PSP inside a DB transaction holding row locks for seconds.
  • Idempotency described as "check Redis if we saw this request" with no request hash, no in-flight state, and no link to the DB commit.
  • Floats for money; a single balance column with no ledger.
  • No reconciliation, or not knowing what a settlement file is.
  • Retrying everything, including non-idempotent bank calls, or re-routing an in-flight payment to a second PSP.

10Quick check

The bank call times out after 10 s. What status do you set?

You do not know if money moved. FAILED plus a retry is the classic double charge.

Which idempotency key best stops a double tap on "Pay"?

The key must represent the business intent. A new UUID per click makes the second tap look like a new payment.

You commit the payment and Kafka is down. With an outbox, what happens?

The outbox row was committed with the payment. Delivery is late and at-least-once; consumers dedupe.

PSP A is failing. A payment is in flight at PSP A. What do you do with it?

The in-flight one may still succeed at A. Re-routing it can debit the user twice.

11Follow-up questions interviewers asked

The bank call timed out. What do you show the user and what does the system do?

Show "processing, we will confirm shortly". Mark PENDING, never FAILED. Webhook, scheduled status polls at 2 / 5 / 15 / 60 minutes, and T+1 reconciliation each can resolve it. If it eventually fails, release the order; if it succeeds after the user paid again, refund the duplicate.

How exactly do you prevent a double payment when the user taps Pay twice?

The client sends the same idempotency key derived from the order id and attempt. The unique constraint on (scope, key) makes the second request read the first's state. Separately, unique (order_id) for a SUCCEEDED payment, checked when marking success, catches duplicates that arrive through different attempts and triggers an automatic refund.

You commit to the DB and then Kafka is down. What happens?

Nothing is lost: the event is in the outbox table in the same commit. The relay retries until Kafka recovers. Consumers see it late, possibly twice, and dedupe by event id.

How do you design the idempotency key for a food-delivery order (Kotak)?

Client generates it per user intent: userId + cartId + attempt or a UUID created when the checkout screen opens and reused on retries. Server scopes it by user, stores the request hash, and returns the original response on replay. Expire after 24 h.

Two webhooks arrive out of order: FAILED after SUCCEEDED.

The allowed-transition table forbids leaving a terminal state; the conditional update affects zero rows and the event is logged for audit. If the PSP genuinely reversed the payment, that arrives as a separate refund / chargeback event with its own flow.

How do you keep a wallet balance consistent under concurrent debits?

Single conditional update (balance >= amount) with the ledger insert in one transaction, or SELECT ... FOR UPDATE on the account row. Optimistic version checks work when contention is low. Never read-modify-write in application code without a lock.

What does reconciliation catch that webhooks and polling do not?

Lost webhooks after PSP retries expire, bugs in our state handling, PSP-side reversals, fee mismatches, and settlement amounts that differ from authorised amounts. It is the only check against the bank's own books.

13Cheat sheet

Cheat sheet
  • Idempotency key = orderId + attempt; unique (scope, key) row in the same DB.
  • Phases: create + commit → PSP call with our id → record result in one txn.
  • CREATED → PROCESSING → PENDING → SUCCEEDED / FAILED → REFUNDED; terminal never moves back.
  • Timeout = PENDING; resolve via webhook, poll (2/5/15/60 min), recon.
  • One transition() with conditional update; races become no-ops.
  • Outbox + Debezium; consumers dedupe by event id; saga, not 2PC.
  • Double-entry, integer paise, immutable entries, balance as cache.
  • Circuit breaker per PSP; never re-route in-flight payments.
