Words you'll see
Type hint
A label like x: int that says what type a value should be. Python does not enforce it while running. Tools and libraries read it.
Pydantic
A Python library that checks incoming data against a class you define. It fixes small mistakes and rejects bad data with clear errors.
Trust boundary
Any place where data comes from outside your code. Examples are an HTTP request, an LLM (large language model) answer or a config file.
Event loop
One thread that juggles many tasks. It runs a task until that task has to wait, then switches to another one.
Blocking call
A call that holds the thread until it finishes, like time.sleep. On an event loop, it stops every other task too.
Virtual environment
A private folder of libraries for one project. Two projects can then use different versions of the same library.
Jitter
A random extra wait before a retry. It stops many clients from all retrying at the exact same moment.
Idempotent
Doing it twice has the same effect as doing it once. Pressing "Pay" twice on a UPI app should charge you once.

Dataclass vs Pydantic

@dataclass

  • Like a Java record. Python writes __init__, __eq__ and __repr__ for you.
  • Almost no extra code to write
  • Checks nothing. page="three" is stored exactly as given.

Use for values your own code created and trusts.

Pydantic BaseModel at boundaries

  • Turns "3" into 3. Rejects 0 when you set ge=1 (greater than or equal to 1).
  • Gives clear error lists. Reads and writes JSON (model_validate, model_dump_json).
  • Costs a little speed and a little more code

Use for HTTP bodies, LLM outputs, config and Kafka messages.

Why AI engineers care

An LLM often answers in JSON. Pydantic turns that JSON into a typed object, and rejects it when it is broken. The Anthropic SDK's client.messages.parse(..., output_format=MyModel) takes a Pydantic class. FastAPI uses the same classes for request bodies. So one class describes your API input, the LLM's expected output and your OpenAPI docs.

Four idioms side by side

Comprehensions

They replace most Java streams: [c.clause_id for c in clauses if c.clause_type == "termination"]. Dicts and sets work too. Use at most one condition.

Exceptions

All are unchecked. Catch a specific type like except httpx.ConnectError, never a bare except:. raise New(...) from exc keeps the original cause.

Context managers

Python's try-with-resources is with (or async with). Write your own with @contextmanager and a single yield.

Generators

Functions that yield values one at a time. You can stream a 500-page contract piece by piece. Streamed LLM output works the same way.

Go deeper: type hints, exceptions, context managers, generators, uv, httpx

Python checks types only while the program runs. Modern Python code still carries type hints. Tools like mypy, pyright and your IDE check them before you run. Libraries like Pydantic and FastAPI read them while the program runs. Think of Java where the compiler is optional and acts like a linter. Frameworks use the hints the way Spring uses reflection. Python has no checked exceptions. It has no public or private keywords. A leading underscore means "internal, please don't use". Indentation is part of the syntax.

Type hints. The interpreter does not enforce hints. def f(x: int) -> str still accepts a string at runtime. Hints help in three places. The first is your IDE. The second is a checker in CI, mypy or pyright, which plays the role of the compiler. The third is libraries that read hints at runtime. FastAPI reads a parameter's hint to decide if it is a path variable, a query parameter or a JSON body. Pydantic reads field hints to build its checks. Annotated[int, Field(ge=1)] attaches extra rules to a type. That puts a rule on the type itself, much like a Bean Validation annotation.

Dataclasses vs Pydantic. A @dataclass is like a Java record. It is a plain container with generated __init__, __eq__ and __repr__. It does not check anything. Pass page="three" and it stores the string. A Pydantic BaseModel is a DTO with Bean Validation and Jackson built in. It turns "3" into 3. It rejects 0 when you declared ge=1. It gives structured error lists. It reads and writes JSON with model_validate and model_dump_json. The rule of thumb is simple. Use Pydantic where outside data comes in: HTTP bodies, LLM outputs, config and Kafka messages. Use dataclasses for internal values, where checks would only add cost and code.

Comprehensions replace most stream pipelines. [c.clause_id for c in clauses if c.clause_type == "termination"] builds a list. {k: v for ...} builds a dict, and {x for ...} builds a set. Keep them to one condition. If you need more, write a normal loop.

Exceptions are all unchecked. Catch the most specific type, such as except httpx.ConnectError. Never write a bare except:, because it hides every error. Use raise NewError(...) from exc to keep the chain of causes. In Java, you would pass the cause to the exception constructor. Python also has try/except/else/finally. The else part runs only when no exception happened.

Context managers are Python's try-with-resources. Any object with __enter__ and __exit__ works with with. The @contextmanager decorator lets you write one as a generator with a single yield. The async version is async with. FastAPI's lifespan is an async context manager.

Generators are functions that yield. Calling one gives you an iterator that makes values only when asked. So you can stream a 500-page contract piece by piece, without holding every piece in memory. Streamed LLM output in Python looks the same: for text in stream.text_stream:.

Packaging with uv and virtual environments. Each project gets its own virtual environment in .venv. It holds a private Python and its own installed libraries. So two projects can pin different versions of the same library. uv comes from a company called Astral. It replaces pip, venv, pip-tools and pyenv with one fast program. uv init creates pyproject.toml, your build.gradle. uv add adds a library and updates uv.lock, which you commit. uv run runs a command inside the project's environment, and creates it if needed. Some teams still use plain pip. Then the setup is python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt.

httpx: the HTTP client. httpx works like the popular requests library. It has both a normal client and an async client. Create one client for the whole application. It keeps a pool of open connections, like a single WebClient bean. Close it on shutdown, and always set a timeout. httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=1.0) sets each phase on its own. pool is how long to wait for a free connection from the pool. People forget it until the pool runs out under heavy load. Timeouts raise httpx.ConnectTimeout, httpx.ReadTimeout and similar errors. All of them are subclasses of httpx.TimeoutException. resp.raise_for_status() raises httpx.HTTPStatusError for any 4xx or 5xx status.

03async/await, one thread

Request Aawait upstream→ Event loop1 thread→ Request B runswhile A waits→ Socket readyA resumes

Figure: one event loop takes turns between many requests. It switches at each await. One blocking call anywhere stops all of them.

asyncio.gather(fetch a, fetch b, fetch c), each 100 ms

Python asyncio

  • One thread that switches tasks at each await. Work that mostly waits on the network runs fine, even with the GIL.
  • Between awaits, no locks are needed for data in memory
  • Any blocking call freezes the whole worker

Java CompletableFuture / Reactor

  • Thread pools can run heavy computing work in parallel
  • Blocking JDBC inside WebFlux has the same trap
Go deeper: asyncio vs CompletableFuture in full

Python's asyncio runs coroutines on one thread, the event loop. A coroutine is a function that can pause and resume later. This is like a Netty event loop or Reactor's non-blocking scheduler. It is not like a thread pool. await marks a point where the coroutine pauses until its input or output is ready. asyncio.gather(a(), b(), c()) is like CompletableFuture.allOf. Three HTTP calls wait at the same time, so the total time is about the slowest one. The trap is the same as a blocking JDBC driver inside a WebFlux handler. Some calls hold the thread until they finish, like requests.get, time.sleep or a non-async database driver. Inside an async def, such a call freezes every request on that worker. Use async libraries instead, like httpx.AsyncClient or the async modes of asyncpg/psycopg. Or declare the endpoint with plain def, and FastAPI will run it on a thread pool.

The GIL is the global interpreter lock. Because of it, heavy computing in Python does not run in parallel across threads. Most LLM gateways and RAG (retrieval-augmented generation) APIs spend their time waiting on the network. For that kind of service, asyncio or threads both work well. For heavy computing, use separate processes or send it to a worker. Examples are running embedding models locally or parsing many PDFs.

# Context managers: try-with-resources
@contextmanager
def timed(label: str):
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"{label} took {(time.perf_counter() - start) * 1000:.0f} ms")

Show app.py
"""Contract summary service: FastAPI + Pydantic + httpx with timeouts, retries and error mapping."""
import asyncio
import logging
import random
from contextlib import asynccontextmanager
from typing import Annotated

import httpx
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field, field_validator

log = logging.getLogger("contract-svc")

UPSTREAM_URL = "http://docs-service.internal"
RETRYABLE_STATUS = {429, 500, 502, 503, 504}


class SummaryRequest(BaseModel):
    contract_id: Annotated[str, Field(pattern=r"^CTR-\d{6}$")]
    max_clauses: Annotated[int, Field(ge=1, le=50)] = 10
    clause_types: list[str] = []

    @field_validator("clause_types")
    @classmethod
    def lower_and_dedupe(cls, v: list[str]) -> list[str]:
        return sorted({t.strip().lower() for t in v if t.strip()})


class Clause(BaseModel):
    clause_id: str
    clause_type: str
    text: str


class SummaryResponse(BaseModel):
    contract_id: str
    clause_count: int
    clauses: list[Clause]


class UpstreamError(Exception):
    def __init__(self, status: int, detail: str):
        self.status = status
        self.detail = detail


async def get_with_retry(client: httpx.AsyncClient, url: str, *, attempts: int = 3,
                         base_delay: float = 0.2) -> httpx.Response:
    """GET with exponential backoff + full jitter. Retries only transient failures."""
    for attempt in range(1, attempts + 1):
        try:
            resp = await client.get(url)
            if resp.status_code not in RETRYABLE_STATUS:
                return resp
            reason = f"HTTP {resp.status_code}"
        except (httpx.ConnectError, httpx.ReadTimeout, httpx.PoolTimeout) as exc:
            reason = type(exc).__name__
        if attempt == attempts:
            raise UpstreamError(504 if "Timeout" in reason else 502, f"upstream failed after {attempts} tries: {reason}")
        delay = random.uniform(0, base_delay * 2 ** (attempt - 1))
        log.warning("attempt %d failed (%s); retrying in %.2fs", attempt, reason, delay)
        await asyncio.sleep(delay)
    raise AssertionError("unreachable")


@asynccontextmanager
async def lifespan(app: FastAPI):
    # One pooled client for the whole app, like a singleton WebClient bean.
    timeout = httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=1.0)
    app.state.http = httpx.AsyncClient(base_url=UPSTREAM_URL, timeout=timeout)
    yield
    await app.state.http.aclose()


app = FastAPI(lifespan=lifespan)


@app.exception_handler(UpstreamError)
async def upstream_error_handler(request: Request, exc: UpstreamError) -> JSONResponse:
    return JSONResponse(status_code=exc.status, content={"error": "upstream_unavailable", "detail": exc.detail})


@app.post("/v1/summaries", response_model=SummaryResponse)
async def create_summary(req: SummaryRequest, request: Request) -> SummaryResponse:
    client: httpx.AsyncClient = request.app.state.http
    resp = await get_with_retry(client, f"/contracts/{req.contract_id}/clauses")
    if resp.status_code == 404:
        raise HTTPException(status_code=404, detail=f"contract {req.contract_id} not found")
    resp.raise_for_status()
    clauses = [Clause.model_validate(c) for c in resp.json()]
    if req.clause_types:
        clauses = [c for c in clauses if c.clause_type in req.clause_types]
    clauses = clauses[: req.max_clauses]
    return SummaryResponse(contract_id=req.contract_id, clause_count=len(clauses), clauses=clauses)
Retries need a budget

Three attempts with a 3-second read timeout can hold one request for over 9 seconds. In production, put one overall deadline around the whole call. In Python 3.11+ that is asyncio.timeout(5). The retries then never take longer than your own caller will wait. Also, only retry idempotent requests, ones that are safe to repeat. A GET is safe. A POST that creates something needs an idempotency key first, a unique ID that lets the server spot repeats.

Go deeper: each piece explained in Spring terms

The service takes a summary request for a contract and checks it. It fetches the contract's clauses from another service, the document service. It filters them and returns a typed response. The interviewer grades four parts. The first is the input model. The second is one shared client with a timeout for each phase. The third is a retry loop. It retries only short-lived failures, waits longer each time and adds a random wait. The fourth is an error handler. It turns a failure in the other service into a clean 502 or 504, not a stack trace.

  • SummaryRequest is your request DTO with Bean Validation. A bad contract_id never reaches your code. FastAPI returns 422 with a list of errors per field. It is like having MethodArgumentNotValidException handled for you. The field_validator cleans the input by trimming, lower-casing and removing duplicates. It is like a custom @JsonDeserialize or a compact constructor in a record.
  • lifespan is your @Bean plus @PreDestroy. It makes one AsyncClient for the whole process and closes it on shutdown.
  • get_with_retry does what @Retryable(maxRetries = 2, delay = 200, multiplier = 2, jitter = ...) would do. It retries 429, 5xx, connection errors and read timeouts. It never retries 400, 401 or 404, because those fail the same way every time. Full jitter means a random wait, random.uniform(0, cap). Many pods then retry at different moments, not all at once against a service that is just recovering.
  • UpstreamError plus @app.exception_handler is your @ControllerAdvice. A domain exception goes in and a consistent JSON error comes out. Timeouts become 504. Other failures in the downstream service become 502.
  • response_model=SummaryResponse checks and filters your own output. So you cannot leak a field by mistake.

Step 5: test without a network

httpx.MockTransport replaces the network with a plain function. It is like MockRestServiceServer or WireMock. TestClient calls the app inside the same process. Entering it runs the lifespan code.

Show test_app.py
import httpx
from fastapi.testclient import TestClient

import app as svc

calls = {"n": 0}


def flaky_upstream(request: httpx.Request) -> httpx.Response:
    calls["n"] += 1
    if "CTR-000404" in request.url.path:
        return httpx.Response(404)
    if "CTR-000503" in request.url.path:
        return httpx.Response(503)
    if calls["n"] == 1:  # first call fails, retry succeeds
        return httpx.Response(503)
    return httpx.Response(200, json=[
        {"clause_id": "c1", "clause_type": "termination", "text": "Either party may terminate..."},
        {"clause_id": "c2", "clause_type": "liability", "text": "Liability is capped at..."},
    ])


def make_client() -> TestClient:
    client = TestClient(svc.app)
    client.__enter__()  # runs lifespan
    svc.app.state.http = httpx.AsyncClient(base_url="http://test", transport=httpx.MockTransport(flaky_upstream))
    return client


def test_all():
    c = make_client()
    r = c.post("/v1/summaries", json={"contract_id": "CTR-000123", "clause_types": [" Termination "]})
    assert r.status_code == 200, r.text
    assert r.json()["clause_count"] == 1 and calls["n"] == 2
    assert c.post("/v1/summaries", json={"contract_id": "bad"}).status_code == 422
    assert c.post("/v1/summaries", json={"contract_id": "CTR-000404"}).status_code == 404
    r = c.post("/v1/summaries", json={"contract_id": "CTR-000503"})
    assert r.status_code == 502 and r.json()["error"] == "upstream_unavailable"
    print("200 ->", c.post("/v1/summaries", json={"contract_id": "CTR-000123"}).json()["clause_count"], "clauses")
    print("422 ->", c.post("/v1/summaries", json={"contract_id": "bad", "max_clauses": 0}).json()["detail"][0]["msg"])
    print("502 ->", r.json())


if __name__ == "__main__":
    test_all()
    print("all checks passed")

Go deeper: tenacity and SDK retries

In the interview, write the retry loop by hand. It shows you understand it. In a real codebase, the tenacity library does the same thing with a decorator. An example is @retry(stop=stop_after_attempt(3), wait=wait_random_exponential(multiplier=0.2, max=2), retry=retry_if_exception_type(...)). That is how Resilience4j works in Spring. The Anthropic SDK also retries 429, 5xx and connection errors on its own. It retries twice by default, and you can change that with max_retries. So do not add your own retry loop on top without thinking.

Common mistakes
  • Calling requests.get or time.sleep inside async def.
  • A new httpx client for every request. There is no connection reuse, so every call pays for a new secure (TLS) handshake.
  • Retrying 400 or 404. Or retrying a POST that is not safe to repeat, without an idempotency key.
  • No pool timeout, so requests wait in line forever under load.
  • A bare except: that hides the real cause.

05How this shows up in interviews

EPAM hired a Senior AI Engineer in April 2026. One round was hands-on. The task was to build "a FastAPI service with proper request validation using Pydantic, along with implementing retry logic, timeout handling, and robust error handling". The first round also had an async programming problem. Expect follow-up questions like these.

Why Pydantic for the request body and not a dataclass?

A dataclass does not check or convert anything. Bad input would flow straight into business logic. Pydantic checks types and rules where data enters. It returns structured errors, and FastAPI turns them into a 422. It also generates the JSON Schema shown in OpenAPI. Internal values that are already trusted can stay dataclasses.

Which failures do you retry, and which not?

Retry short-lived failures. These are connection errors, timeouts, 429 and 502/503/504. Add 500 if the other service is known to be flaky. Do not retry 400, 401, 403, 404 or 422, because they fail the same way every time. If a 429 or 503 has a Retry-After header, wait that long. Only retry idempotent operations. Or make them idempotent with a key that the other service uses to drop duplicates.

Why jitter?

Say many clients fail at the same moment. Without jitter, they all retry at the same moment too. These waves keep an overloaded service down. This is called the thundering herd. Full jitter picks a random wait between zero and the growing limit. That spreads the load out.

What timeouts do you set, and where?

I set one per phase on the client. The connect timeout is short, about 1 s. The read timeout matches the other service's p99 plus a margin. p99 means 99 out of 100 calls are faster than this. A pool timeout makes requests fail fast when no connection is free, instead of waiting forever. Around the whole retry loop I put one overall deadline. It is shorter than my own caller's timeout. For LLM calls, the read timeout is much longer, or I stream. A model can take tens of seconds to write an answer.

What happens if you call requests.get inside an async def endpoint?

It blocks the event loop thread. Every other request on that worker stalls until it returns. Under load, the number of requests you can serve collapses. There are three fixes. Use an async client like httpx.AsyncClient. Or declare the endpoint as plain def, so FastAPI runs it in a thread pool. Or call await asyncio.to_thread(blocking_fn).

asyncio.gather vs CompletableFuture.allOf: what's different?

Both wait for several operations that run at the same time. gather runs coroutines on one thread and switches at each await. So there is no parallel CPU work. You also need no locks around plain in-memory data between awaits. By default, the first exception goes to the caller, but the other coroutines keep running. Pass return_exceptions=True to collect failures as values. Or use asyncio.TaskGroup (3.11+), which cancels the others when one fails. That is called structured concurrency, and it is usually what you want.

How do you share an HTTP client across requests, and why?

Create it in the lifespan handler. Store it on app.state, or provide it through a dependency. Close it on shutdown. A new client per request throws away the connection pool. Every call then pays for a new TCP and TLS handshake, and you can run out of sockets.

How would you add observability?

Observability means being able to see what the service is doing. I would add structured JSON logs. Each request gets a request ID, which is also sent to the downstream service as a header. I would add Prometheus metrics for request time, retries and downstream status codes. OpenTelemetry auto-instrumentation for FastAPI and httpx can do this too. I would add a /healthz endpoint. For LLM calls, I would also log the model, input and output tokens, and time taken per request.

What is the GIL and does it matter here?

GIL stands for global interpreter lock. In standard CPython, it lets only one thread run Python bytecode at a time. It does not matter for services that mostly wait on the network. The lock is released while a thread waits on a socket. It does matter for heavy computing work. Move that work to processes, to native libraries, or to a separate worker. NumPy, for example, releases the GIL.

06Quick check

An async def FastAPI endpoint calls requests.get. The other service takes 2 seconds. What happens under load?

The call blocks the one event-loop thread, so nothing else can run. Use httpx.AsyncClient, a plain def endpoint, or asyncio.to_thread.

Which responses should get_with_retry retry?

Retry only short-lived failures. A 400 or 404 will fail the same way every time.

An LLM sends you JSON. It should contain risk and page >= 1. What do you parse it into?

The data comes from outside your code. Pydantic checks it, converts it and gives clear errors. A dataclass checks nothing.

Why add jitter to exponential backoff?

Without it, every pod that failed together also retries together. That flood is called the thundering herd.

08Cheat sheet

Cheat sheet
  • list[str], dict[str,int], str | None. mypy or pyright check the hints. Pydantic and FastAPI read them.
  • Dataclass is like a record, with no checks. Pydantic is a DTO with checks and JSON. Use Pydantic where outside data comes in.
  • A comprehension is a stream. with is try-with-resources. yield makes a lazy iterator.
  • asyncio.gather is close to allOf, but on one thread. Never block the loop.
  • Use uv init / add / run. Commit uv.lock.
  • Make one httpx.AsyncClient in lifespan. Timeouts: connect 1, read 3, write 3, pool 1.
  • Retry 429, 5xx and timeouts. Wait longer each time, with full jitter. Never retry other 4xx. Add an overall deadline.
  • Error handler: a timeout gives 504, other downstream failures give 502. Test with MockTransport.
