02Concepts explained from scratch, mapped to Java

The mental shift

Python is dynamically typed at runtime, but modern Python is written with type hints that tools (mypy, pyright, your IDE) check statically and libraries (Pydantic, FastAPI) read at runtime. Think of it as Java where the compiler is optional and runs as a linter, while frameworks use the annotations the way Spring uses reflection. There are no checked exceptions, no public/private keywords (a leading underscore means "internal, please don't"), and indentation is syntax.

Type hints

Hints are not enforced by the interpreter: def f(x: int) -> str still accepts a string at runtime. They earn their keep in three places: your IDE, a static checker in CI (mypy or pyright, the equivalent of compiling), and libraries that read them at runtime. FastAPI reads the hint on a parameter to decide whether it is a path variable, a query parameter or a JSON body; Pydantic reads field hints to build validators. Annotated[int, Field(ge=1)] attaches metadata to a type, which is how you put a constraint on a type rather than a field, much like a Bean Validation annotation.

Dataclasses vs Pydantic models

A @dataclass is a Java record: a plain container with generated __init__, __eq__ and __repr__. It does not validate anything. Pass page="three" and it stores the string. A Pydantic BaseModel is a DTO with Bean Validation and Jackson built in: it coerces "3" to 3, rejects 0 when you declared ge=1, produces structured error lists, and serialises to and from JSON (model_validate, model_dump_json). Rule of thumb: Pydantic at trust boundaries (HTTP bodies, LLM outputs, config, messages off Kafka), dataclasses for internal values where validation cost and ceremony buy nothing.

Why AI engineers care

Pydantic is how you turn an LLM's JSON into a typed object and reject it when it is malformed. The Anthropic SDK's client.messages.parse(..., output_format=MyModel) takes a Pydantic class, and FastAPI uses the same classes for request bodies. One model definition serves the API contract, the LLM output contract and the OpenAPI docs.

Comprehensions, exceptions, context managers, generators

Comprehensions replace most stream pipelines: [c.clause_id for c in clauses if c.clause_type == "termination"] for a list, {k: v for ...} for a dict, {x for ...} for a set. Keep them to one condition; past that, write a loop.

Exceptions are all unchecked. Catch the narrowest type (except httpx.ConnectError), never a bare except:, and use raise NewError(...) from exc to keep the cause chain, the equivalent of passing the cause to an exception constructor. try/except/else/finally exists; else runs only when no exception was raised.

Context managers are try-with-resources. Anything with __enter__/__exit__ works with with; the @contextmanager decorator lets you write one as a generator with a single yield. The async version is async with, and FastAPI's lifespan is an async context manager.

Generators are functions that yield. Calling one returns an iterator that produces values lazily, so you can stream a 500-page contract chunk by chunk without holding every chunk in memory. Streaming LLM output in Python is generator-shaped too: for text in stream.text_stream:.

async/await vs CompletableFuture

Python's asyncio runs coroutines on a single-threaded event loop, like a Netty event loop or Reactor's non-blocking scheduler, not like a thread pool. await is a point where the coroutine yields control until I/O completes. asyncio.gather(a(), b(), c()) is CompletableFuture.allOf: three HTTP calls overlap and the total time is roughly the slowest one. The trap is the same as calling a blocking JDBC driver inside a WebFlux handler: a synchronous call (requests.get, time.sleep, a sync database driver) inside an async def freezes every request on that worker. Use async libraries (httpx.AsyncClient, asyncpg/psycopg async), or declare the endpoint with plain def so FastAPI runs it on a thread pool.

Request Aawait upstream→ Event loop1 thread→ Request B runswhile A waits→ Socket readyA resumes

Figure: one event loop interleaves many requests at their await points. A blocking call anywhere stops all of them.

The GIL (global interpreter lock) means CPU-bound Python code does not run in parallel across threads; for I/O-bound services, which is what LLM gateways and RAG APIs are, asyncio or threads both work well. For CPU-heavy work (local embedding models, PDF parsing at scale) use processes or push it to a worker.

Packaging with uv and virtual environments

Each project gets its own virtual environment (.venv), an isolated interpreter plus site-packages, so two projects can pin different library versions. uv (from Astral) replaces pip, venv, pip-tools and pyenv with one fast binary: uv init creates pyproject.toml (your build.gradle), uv add adds a dependency and updates uv.lock (commit it), and uv run executes inside the project's environment, creating it if needed. If a team still uses plain pip: python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt.

httpx: the HTTP client

httpx has a requests-style API with sync and async clients. Create one client per application (it pools connections, like a single WebClient bean), close it on shutdown, and always set a timeout. httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=1.0) sets each phase separately; pool is how long to wait for a free connection from the pool, the setting people forget until the pool is exhausted under load. Timeouts raise httpx.ConnectTimeout, httpx.ReadTimeout and friends (all subclasses of httpx.TimeoutException); resp.raise_for_status() raises httpx.HTTPStatusError for 4xx/5xx.

def read_chunks(text: str, size: int) -> Iterator[str]:

print(list(read_chunks("abcdefghij", 4)))


# Context managers: try-with-resources
@contextmanager
def timed(label: str):
    start = time.perf_counter()
    try:
        yield
    finally:
        print(f"{label} took {(time.perf_counter() - start) * 1000:.0f} ms")

    await asyncio.sleep(delay)
    return name

        results = await asyncio.gather(fetch("a", 0.1), fetch("b", 0.1), fetch("c", 0.1))
    print(results)
    try:

    except TimeoutError:

Step 3: the service (the EPAM round)

The service accepts a summary request for a contract, validates it, fetches the contract's clauses from a downstream document service, filters them, and returns a typed response. The parts an interviewer grades are the validation model, the shared client with per-phase timeouts, a retry loop that retries only transient failures with exponential backoff and jitter, and an exception handler that turns downstream failure into a clean 502/504 instead of a stack trace.

"""Contract summary service: FastAPI + Pydantic + httpx with timeouts, retries and error mapping."""
import asyncio
import logging
import random
from contextlib import asynccontextmanager
from typing import Annotated

import httpx
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field, field_validator

log = logging.getLogger("contract-svc")

UPSTREAM_URL = "http://docs-service.internal"
RETRYABLE_STATUS = {429, 500, 502, 503, 504}


class SummaryRequest(BaseModel):
    contract_id: Annotated[str, Field(pattern=r"^CTR-\d{6}$")]
    max_clauses: Annotated[int, Field(ge=1, le=50)] = 10
    clause_types: list[str] = []

    @field_validator("clause_types")
    @classmethod
    def lower_and_dedupe(cls, v: list[str]) -> list[str]:
        return sorted({t.strip().lower() for t in v if t.strip()})


class Clause(BaseModel):
    clause_id: str
    clause_type: str
    text: str


class SummaryResponse(BaseModel):
    contract_id: str
    clause_count: int
    clauses: list[Clause]


class UpstreamError(Exception):
    def __init__(self, status: int, detail: str):
        self.status = status
        self.detail = detail


async def get_with_retry(client: httpx.AsyncClient, url: str, *, attempts: int = 3,
                         base_delay: float = 0.2) -> httpx.Response:
    """GET with exponential backoff + full jitter. Retries only transient failures."""
    for attempt in range(1, attempts + 1):
        try:
            resp = await client.get(url)
            if resp.status_code not in RETRYABLE_STATUS:
                return resp
            reason = f"HTTP {resp.status_code}"
        except (httpx.ConnectError, httpx.ReadTimeout, httpx.PoolTimeout) as exc:
            reason = type(exc).__name__
        if attempt == attempts:
            raise UpstreamError(504 if "Timeout" in reason else 502, f"upstream failed after {attempts} tries: {reason}")
        delay = random.uniform(0, base_delay * 2 ** (attempt - 1))
        log.warning("attempt %d failed (%s); retrying in %.2fs", attempt, reason, delay)
        await asyncio.sleep(delay)
    raise AssertionError("unreachable")


@asynccontextmanager
async def lifespan(app: FastAPI):
    # One pooled client for the whole app, like a singleton WebClient bean.
    timeout = httpx.Timeout(connect=1.0, read=3.0, write=3.0, pool=1.0)
    app.state.http = httpx.AsyncClient(base_url=UPSTREAM_URL, timeout=timeout)
    yield
    await app.state.http.aclose()


app = FastAPI(lifespan=lifespan)


@app.exception_handler(UpstreamError)
async def upstream_error_handler(request: Request, exc: UpstreamError) -> JSONResponse:
    return JSONResponse(status_code=exc.status, content={"error": "upstream_unavailable", "detail": exc.detail})


@app.post("/v1/summaries", response_model=SummaryResponse)
async def create_summary(req: SummaryRequest, request: Request) -> SummaryResponse:
    client: httpx.AsyncClient = request.app.state.http
    resp = await get_with_retry(client, f"/contracts/{req.contract_id}/clauses")
    if resp.status_code == 404:
        raise HTTPException(status_code=404, detail=f"contract {req.contract_id} not found")
    resp.raise_for_status()
    clauses = [Clause.model_validate(c) for c in resp.json()]
    if req.clause_types:
        clauses = [c for c in clauses if c.clause_type in req.clause_types]
    clauses = clauses[: req.max_clauses]
    return SummaryResponse(contract_id=req.contract_id, clause_count=len(clauses), clauses=clauses)

What each piece is doing, in Spring terms:

  • SummaryRequest is your request DTO with Bean Validation. A bad contract_id never reaches your code; FastAPI returns 422 with a field-level error list, like MethodArgumentNotValidException handled for you. The field_validator normalises input (trim, lower-case, de-duplicate), like a custom @JsonDeserialize or a compact-constructor in a record.
  • lifespan is your @Bean plus @PreDestroy: one AsyncClient for the whole process, closed on shutdown.
  • get_with_retry is what @Retryable(maxRetries = 2, delay = 200, multiplier = 2, jitter = ...) would do. It retries 429 and 5xx and connection or read timeouts, but never 400/401/404, which will fail identically on every attempt. Full jitter (random.uniform(0, cap)) spreads retries from many pods so they do not hit the recovering downstream in lockstep.
  • UpstreamError plus @app.exception_handler is @ControllerAdvice: domain exception in, consistent JSON error out. Timeouts map to 504, other upstream failures to 502.
  • response_model=SummaryResponse validates and filters your own output, so you cannot leak a field by accident.
Retries need a budget

Three attempts with a 3-second read timeout can hold a request for over 9 seconds. In production, wrap the whole call in an overall deadline (asyncio.timeout(5) in Python 3.11+) so retries never exceed what your own caller will wait, and only retry idempotent requests. A GET is safe; a POST that creates something needs an idempotency key first.

Step 5: test without a network

httpx.MockTransport swaps the network layer for a function, the same idea as MockRestServiceServer or WireMock. TestClient calls the app in-process, and entering it runs the lifespan.

import httpx
from fastapi.testclient import TestClient

import app as svc

calls = {"n": 0}


def flaky_upstream(request: httpx.Request) -> httpx.Response:
    calls["n"] += 1
    if "CTR-000404" in request.url.path:
        return httpx.Response(404)
    if "CTR-000503" in request.url.path:
        return httpx.Response(503)
    if calls["n"] == 1:  # first call fails, retry succeeds
        return httpx.Response(503)
    return httpx.Response(200, json=[
        {"clause_id": "c1", "clause_type": "termination", "text": "Either party may terminate..."},
        {"clause_id": "c2", "clause_type": "liability", "text": "Liability is capped at..."},
    ])


def make_client() -> TestClient:
    client = TestClient(svc.app)
    client.__enter__()  # runs lifespan
    svc.app.state.http = httpx.AsyncClient(base_url="http://test", transport=httpx.MockTransport(flaky_upstream))
    return client


def test_all():
    c = make_client()
    r = c.post("/v1/summaries", json={"contract_id": "CTR-000123", "clause_types": [" Termination "]})
    assert r.status_code == 200, r.text
    assert r.json()["clause_count"] == 1 and calls["n"] == 2
    assert c.post("/v1/summaries", json={"contract_id": "bad"}).status_code == 422
    assert c.post("/v1/summaries", json={"contract_id": "CTR-000404"}).status_code == 404
    r = c.post("/v1/summaries", json={"contract_id": "CTR-000503"})
    assert r.status_code == 502 and r.json()["error"] == "upstream_unavailable"
    print("200 ->", c.post("/v1/summaries", json={"contract_id": "CTR-000123"}).json()["clause_count"], "clauses")
    print("422 ->", c.post("/v1/summaries", json={"contract_id": "bad", "max_clauses": 0}).json()["detail"][0]["msg"])
    print("502 ->", r.json())


if __name__ == "__main__":
    test_all()
    print("all checks passed")

Run with uv run python test_app.py (or uv run pytest, which picks up test_all). Actual output:

attempt 1 failed (HTTP 503); retrying in 0.10s
attempt 1 failed (HTTP 503); retrying in 0.08s
attempt 2 failed (HTTP 503); retrying in 0.10s
200 -> 2 clauses
422 -> String should match pattern '^CTR-\d{6}$'
502 -> {'error': 'upstream_unavailable', 'detail': 'upstream failed after 3 tries: HTTP 503'}

The first line is the flaky first call being retried; the next two are the permanently failing contract exhausting its three attempts. The retry delays are random, so your numbers will differ.

Library option

For the interview, hand-writing the loop shows you understand it. In a codebase, tenacity gives you the same thing declaratively (@retry(stop=stop_after_attempt(3), wait=wait_random_exponential(multiplier=0.2, max=2), retry=retry_if_exception_type(...))), the way Resilience4j does in Spring. The Anthropic SDK also retries 429, 5xx and connection errors itself (twice by default, configurable with max_retries), so do not stack your own retry loop on top of it blindly.

04How this shows up in interviews

EPAM's Senior AI Engineer loop (April 2026) had a hands-on round to build "a FastAPI service with proper request validation using Pydantic, along with implementing retry logic, timeout handling, and robust error handling", and the first round included an async programming problem. Expect follow-ups like these.

Why Pydantic for the request body and not a dataclass?

A dataclass does not validate or coerce, so bad input would flow into business logic. Pydantic validates types and constraints at the boundary, returns structured errors that FastAPI turns into a 422, and generates the JSON Schema that appears in OpenAPI. Internal value objects that are already trusted can stay dataclasses.

Which failures do you retry, and which not?

Retry transient ones: connection errors, timeouts, 429 and 502/503/504 (and 500 if the downstream is known to be flaky). Do not retry 400, 401, 403, 404 or 422; they fail the same way every time. Honour Retry-After on 429/503 if present. Only retry idempotent operations, or make them idempotent with a key the downstream de-duplicates on.

Why jitter?

Without it, every client that failed at the same moment retries at the same moment, producing synchronised waves that keep an overloaded downstream down (the thundering herd). Full jitter, a random delay between zero and the exponential cap, spreads the load.

What timeouts do you set, and where?

Per phase on the client: a short connect timeout (about 1 s), a read timeout sized to the downstream's p99 plus margin, and a pool timeout so requests fail fast when the pool is exhausted instead of queueing forever. Then an overall deadline around the whole retry loop that is shorter than my own caller's timeout. For LLM calls the read timeout is much longer, or I stream, because generation can take tens of seconds.

What happens if you call requests.get inside an async def endpoint?

It blocks the event loop thread, so every other request on that worker stalls until it returns. Throughput collapses under load. Fix it with an async client (httpx.AsyncClient), by declaring the endpoint as plain def (FastAPI then runs it in a thread pool), or with await asyncio.to_thread(blocking_fn).

asyncio.gather vs CompletableFuture.allOf: what's different?

Both wait for several concurrent operations. gather runs coroutines on one thread and switches at await points, so there is no parallel CPU work and no need for locks around plain in-memory state between awaits. By default, the first exception propagates to the caller, but the other coroutines keep running; pass return_exceptions=True to collect failures as values, or use asyncio.TaskGroup (3.11+), which cancels the siblings when one fails, the structured-concurrency behaviour you usually want.

How do you share an HTTP client across requests, and why?

Create it in the lifespan handler, store it on app.state (or provide it through a dependency), and close it on shutdown. A client per request throws away the connection pool, so every call pays a TCP and TLS handshake and you can run out of sockets.

How would you add observability?

Structured JSON logs with a request ID propagated to the downstream as a header, Prometheus metrics for request latency, retries and upstream status codes (or OpenTelemetry auto-instrumentation for FastAPI and httpx), and a /healthz endpoint. For LLM calls, also log model, input/output tokens and latency per request.

What is the GIL and does it matter here?

The global interpreter lock lets only one thread execute Python bytecode at a time in the standard CPython build. It does not matter for I/O-bound services, because the lock is released while waiting on sockets. It matters for CPU-bound work, which you move to processes, native libraries (NumPy releases the GIL) or a separate worker.

05Exercise / checkpoint for the capstone

The capstone is a contract Q&A service plus a risky-clause flagger. This lesson's service becomes its skeleton. In 45–60 minutes:

  1. Add an overall deadline: wrap the retry loop in async with asyncio.timeout(5): and map TimeoutError to a 504.
  2. Honour Retry-After: if a 429 or 503 response carries the header, sleep for that many seconds (capped at 2) instead of the computed backoff. Add a MockTransport case that proves it.
  3. Add POST /v1/flags taking {"contract_id": ..., "clause_text": ...} with clause_text limited to 1–8,000 characters. For now return a hard-coded {"risk": "low", "reasons": []} from a Pydantic FlagResult model whose risk is a Literal["low","medium","high"]. In the prompt-engineering and first-LLM-calls lessons you will replace the stub with a Claude call that returns this same model.
  4. Propagate an X-Request-ID header (generate one if absent) to the downstream and include it in every log line.

Checkpoint: all tests pass offline, /docs shows both endpoints with their schemas, and you can explain every retry and timeout decision out loud in two minutes.
