In-Process Job / Task Scheduler

A job queue holds background work, like "send this email" or "resize this photo", for worker threads to pick up. By the end, you can code one where no two workers ever finish the same job. Failed jobs are retried, and jobs that keep failing are parked for a human. You will also be able to adapt it to the dependency and scheduler variants.

Time-box: 60–90 min (Razorpay: 75 min with an AI coding agent, then 15 min by hand) Seen: about 8 interview reports, 2025–26 Format: IDE, or AI-assisted with a PLAN.md file and the git log
RazorpayMedia.netUberWalmartRubrikGoldman Sachs
In 30 seconds
  • Write down every job status and the allowed moves between them. Every move happens under one lock.
  • Workers lease a job for a short time and keep renewing it. If the lease runs out, the job goes back in the queue.
  • Each lease gets a new number (a token). A slow, old worker can't finish a job that now belongs to someone else.
  • Retry after a growing, randomised wait. After the last retry, move the job to a dead-letter queue.
Picture it

Think of a Swiggy order board. A rider takes an order for 30 minutes and must check in to keep it. If they go silent, the order goes to another rider with a new ticket number. If the first rider later taps "delivered", the app ignores it, because their ticket number is old.

Words you'll see
Job
One piece of background work, like "send the welcome email to user 42".
Worker
A thread that takes jobs from the queue and runs them.
Lease
A worker borrows a job for a set time, say 30 seconds. It must renew the lease, or the job returns to the queue.
Fencing token
A number that goes up with every new lease. The queue rejects any call that carries an older number.
At-least-once
Every job runs at least one time, but may run twice. So the job's code must be safe to run twice.
Backoff with jitter
Wait longer after each failure (backoff), and pick a random wait inside that limit (jitter). Failed jobs then don't all retry at once.
DLQ (dead-letter queue)
A separate parking area for jobs that failed too many times. A human can look at them and send them back.
DAG
Directed acyclic graph. Tasks with "run B after A" arrows and no loops.

01What the interviewer is grading

State machine

Name every status change and guard it. A move that is not allowed throws an error. Draw this first.

Concurrency

No job is held by two workers. An old worker can't complete a job it has lost.

Failure semantics

Jobs may run twice, so handlers must be safe to repeat. Retry with random waits. Park repeat failures in the DLQ.

Process

In AI-assisted rounds: write PLAN.md, make small commits, keep tests passing, and handle the new feature at minute 70.

Go deeper: how the rounds ran and the full grading list

Razorpay's June 2026 round, done with an AI coding agent, is the clearest spec in the reports. You build a background job service inside one process. They described it as "a minimal Sidekiq / Celery / SQS-with-workers". It has submit(job_spec) -> job_id, priority 0–9 and max_retries. Workers register for job types. They pull jobs under a lease, also called a visibility timeout, which they must renew. The lifecycle is pending → claimed → succeeded | failed (DLQ) | retry_scheduled → pending. If a lease expires, the claimed job goes back to pending. There were process rules too. Write PLAN.md first and walk the interviewer through it. Commit in small steps, because the git log is part of what you hand in. Nothing counts as "done" without passing tests. Tests must exercise concurrency. A new feature arrives around minute 70. The candidate finished everything and was still rejected. Their own view was this. How you drive the agent (plan, run things in parallel, check the output) is graded as much as the result.

Media.net's version (Nov 2025) asked for dependencies, priority, and retry after failure (5 attempts). It also wanted cancel, parallel running, history, and protection against circular dependencies. The candidate could not get the code running and expected a reject. Walmart's SDE-III round wanted one-time and repeating jobs, status, retry, cancel, several workers and priority. They discussed PriorityBlockingQueue vs DelayQueue, and exponential backoff with jitter.

Three prompts share one skeleton. The first is a background job queue with leases and retries (Razorpay). The second is a task runner that respects dependencies, with priorities and loop detection (Media.net). The third is a ScheduledExecutorService built from scratch (Uber, Goldman Sachs, Rubrik). A senior answer has a clear state machine and one place where state changes under a lock. It has lease tokens that stop old workers, backoff with jitter, and tests that really exercise concurrency.

  • State machine. Name and guard every status change. Moves that are not allowed throw. Draw it before coding.
  • Correct under concurrency. Two workers never hold the same job. An old worker can't complete a job it lost.
  • Failure semantics. Say plainly that a job runs at least once, maybe twice. Handlers must be safe to repeat. Use backoff with jitter and a DLQ.
  • Testability. Pass in the clock and the random generator. Tests never call Thread.sleep, except the one concurrency test.
  • Observability. Track how many jobs are in each status and how long the oldest one has waited. Also track the DLQ size and how many leases expired (stuck jobs).
  • Process (AI-assisted rounds). Plan first, make small commits, and measure progress in passing tests. Fit the minute-70 feature in cleanly.

02Clarifying questions to ask

QuestionWhy it matters
Must each job run at least once, or at most once?"At least once" means handlers must be safe to run twice.
Does an expired lease count as an attempt?If not, a job that always crashes loops forever.
Strict priority, or do old jobs move up over time?With strict priority, low-priority jobs may never run.
First in, first out within one priority?You need a sequence number to break ties.
How fast does the retry wait grow, and what is the cap?Usually it doubles each time, with a random wait, up to a cap.
Can you cancel a running job?Either the job checks a cancel flag, or only queued jobs can be cancelled.
If a parent task fails, what happens to its children?Mark them, and their children, SKIPPED.
Repeating jobs: fixed rate or fixed delay?A fixed rate can pile up runs if a job is slow.
Go deeper: the full "why it matters" notes
  • At-least-once (leases plus re-delivery) means handlers must be idempotent, safe to run twice. Exactly-once is not possible in general. Say so.
  • A poison job crashes its worker every time. If an expired lease does not count as a failed attempt, that job loops forever.
  • Under steady heavy load, strict priority starves low-priority jobs. They never get a turn.
  • First in, first out within a priority needs a sequence number to break ties. PriorityQueue does not keep insertion order for equal items.
  • Backoff: grow the wait exponentially, add full jitter, and cap it. Make the base and the cap configurable.
  • Cancel: either cooperative cancel (set a flag and interrupt the thread), or only cancel queued jobs.
  • Dependencies: if a parent fails for good, usually mark all its descendants SKIPPED or UPSTREAM_FAILED.
  • Repeating jobs: with a fixed rate, runs can pile up if the job is slower than the period. Ask whether two runs may overlap.

03Requirements

Functional

  • submit(spec) returns a job id.
  • claim leases the best job that is due.
  • renew, complete and fail need the lease token.
  • Retry, DLQ, send back from DLQ, cancel, stats.

Non-functional

  • A job never has two live leases.
  • Claim in O(log n). Workers never spin in a loop waiting.
  • Clean shutdown. The clock is passed in.

Out of scope

  • Saving to disk, many processes.
  • Exactly-once, cron syntax.
Go deeper: full requirement list
  • submit(spec) returns an id. The spec has a type, payload, priority and maxRetries. It may also have runAt (a start time) and dependsOn.
  • Workers register the job types they handle. claim leases the highest-priority due job among those types.
  • renew, complete and fail all take the lease token.
  • Retry with backoff. Move to the DLQ once retries run out. Allow sending jobs back from the DLQ ("redrive").
  • Cancel. Status and history per job. Queue stats.
  • No job is held by two live leases. Claim runs in O(log n), with no busy-waiting. Shut down cleanly. Stop claiming, then finish or release jobs in progress. Make tests repeatable with a Clock and a seeded RandomGenerator.
  • Out of scope (say so): saving to disk and workers in many processes. Describe the Postgres SKIP LOCKED or SQS version instead. Also out of scope: side effects that happen exactly once, and cron expression parsing. Accept a fixed period instead.

06The race and the fix

The bug is a zombie worker. It completes a job it no longer owns.

TimeWorker W1Worker W2J1
t1claims J1CLAIMED by W1
t2GC pause, lease expiresPENDING
t3claims J1, starts workCLAIMED by W2
t4complete(J1)still runningSUCCEEDED, W2's run orphaned

The fix is a fencing token for each lease. The queue checks it while holding the lock.

t1claims J1, token 7CLAIMED, token 7
t2GC pause, lease expiresPENDING
t3claims J1, token 8CLAIMED, token 8
t4complete(J1, 7) → stalecompletes with token 8SUCCEEDED once, by W2
Other traps
  • Double claim: taking the job, changing its status and creating the lease must be one locked step. In Postgres, use FOR UPDATE SKIP LOCKED.
  • "At least once" means a handler can run twice. Make handlers safe to repeat.
  • Lost wake-ups: call awaitNanos in a loop, and signalAll on every change.
  • Never silently catch and ignore InterruptedException.
Go deeper: every concurrency and edge case
  • Double claim. This can't happen, because claiming, changing status and creating the lease all happen under one lock. In Postgres, the same idea is SELECT … FOR UPDATE SKIP LOCKED LIMIT 1, then an update in the same transaction. SKIP LOCKED makes each worker skip rows another worker has already locked.
  • Zombie worker. A worker pauses past its lease, for example during garbage collection or a network stall. The job is leased to someone else. Then the first worker calls complete. The token check rejects it. Without tokens, the late completion would overwrite the new attempt.
  • Renew after expiry. The same token check applies. Once the lease has gone to someone else, renewal fails, and the worker should stop.
  • Lost wake-ups. Call awaitNanos in a loop that checks the state again, and call signalAll on every change. Cap the wait time at the next due retry or lease expiry. Then due jobs move to ready without a separate cleanup thread.
  • At-least-once means duplicates. A handler can run twice, if its lease expired mid-run. Handlers must be idempotent. You can skip job ids you have already processed. You can pass idempotency keys to outside calls, such as a payment provider. Or you can make writes upserts (insert or update).
  • Poison jobs. An expired lease counts as an attempt. So a job that kills its worker reaches the DLQ instead of looping forever.
  • Starvation. Strict priority can stop priority 0 from ever running. Fix it with ageing, where a job's priority rises the longer it waits. Or pick across priorities with weights.
  • Thundering herd on retry. With plain exponential backoff, jobs that failed together retry together, in waves. Full jitter spreads them out (AWS Architecture Blog).
  • Time. Pass in a Clock for runAt and lease logic. In tests, use a clock you can move forward, plus a direct call that triggers promotion. Never use Thread.sleep to wait for a lease to expire.
  • Interrupts. Never silently catch InterruptedException. Set the interrupt flag again and leave the loop.

Show model: JobState, JobSpec, Job, Lease 
public enum JobState {
    PENDING, CLAIMED, SUCCEEDED, RETRY_SCHEDULED, FAILED, CANCELLED;

    private static final Map<JobState, Set<JobState>> ALLOWED = Map.of(
        PENDING, EnumSet.of(CLAIMED, CANCELLED),
        CLAIMED, EnumSet.of(SUCCEEDED, RETRY_SCHEDULED, FAILED, PENDING),   // PENDING = lease expired
        RETRY_SCHEDULED, EnumSet.of(PENDING, CANCELLED),
        SUCCEEDED, EnumSet.noneOf(JobState.class),
        FAILED, EnumSet.of(PENDING),                                         // redrive from DLQ
        CANCELLED, EnumSet.noneOf(JobState.class));

    boolean canMoveTo(JobState next) { return ALLOWED.get(this).contains(next); }
}

public record JobSpec(String type, Object payload, int priority, int maxRetries, Instant runAt) {
    public JobSpec {
        if (priority < 0 || priority > 9) throw new IllegalArgumentException("priority 0-9");
        if (maxRetries < 0) throw new IllegalArgumentException("maxRetries >= 0");
    }
    public static JobSpec of(String type, Object payload) { return new JobSpec(type, payload, 5, 3, null); }
}

public final class Job {
    final String id;
    final JobSpec spec;
    final long seq;                 // FIFO tie-break within a priority
    JobState state = JobState.PENDING;
    int attempts;
    Instant runAt;
    long leaseToken;
    Instant leaseExpiresAt;
    String lastError;
    final List<String> history = new ArrayList<>();

    Job(String id, JobSpec spec, long seq, Instant now) {
        this.id = id; this.spec = spec; this.seq = seq;
        this.runAt = spec.runAt() == null ? now : spec.runAt();
    }

    void moveTo(JobState next, Instant at, String note) {
        if (!state.canMoveTo(next)) throw new IllegalStateException(id + ": " + state + " -> " + next);
        history.add(at + " " + state + "->" + next + (note == null ? "" : " " + note));
        state = next;
    }
}

Show JobQueue (one lock, three indexes, lazy cleanup)

Every status change happens under one ReentrantLock. The priority queues are cleaned lazily. When an entry is taken out, the queue checks whether its job is still in the expected status. If not, it skips the entry. This makes cancel and lease renewal O(1).

public final class JobQueue {
    private record LeaseEntry(Instant expiresAt, String jobId, long token) {}

    private static final Comparator<Job> BY_PRIORITY =
        Comparator.comparingInt((Job j) -> -j.spec.priority()).thenComparingLong(j -> j.seq);

    private final ReentrantLock lock = new ReentrantLock();
    private final Condition changed = lock.newCondition();
    private final Map<String, Job> jobs = new HashMap<>();
    private final Map<String, PriorityQueue<Job>> ready = new HashMap<>();          // per type
    private final PriorityQueue<Job> delayed = new PriorityQueue<>(Comparator.comparing((Job j) -> j.runAt));
    private final PriorityQueue<LeaseEntry> leases = new PriorityQueue<>(Comparator.comparing(LeaseEntry::expiresAt));
    private final Deque<Job> dlq = new ArrayDeque<>();
    private final AtomicLong seq = new AtomicLong();
    private final AtomicLong tokens = new AtomicLong();
    private final Clock clock;
    private final BackoffPolicy backoff;

    public JobQueue(Clock clock, BackoffPolicy backoff) { this.clock = clock; this.backoff = backoff; }

    public String submit(JobSpec spec) {
        lock.lock();
        try {
            Instant now = clock.instant();
            Job job = new Job(UUID.randomUUID().toString(), spec, seq.incrementAndGet(), now);
            jobs.put(job.id, job);
            job.history.add(now + " submitted");
            if (job.runAt.isAfter(now)) delayed.add(job); else readyFor(spec.type()).add(job);
            changed.signalAll();
            return job.id;
        } finally { lock.unlock(); }
    }

    /** Blocks up to maxWait for a due job of one of the given types. */
    public Optional<Lease> claim(Set<String> types, Duration leaseFor, Duration maxWait) throws InterruptedException {
        long remaining = maxWait.toNanos();
        lock.lock();
        try {
            while (true) {
                Instant now = clock.instant();
                promoteDue(now);
                Job best = pollBest(types);
                if (best != null) {
                    best.attempts++;
                    best.leaseToken = tokens.incrementAndGet();
                    best.leaseExpiresAt = now.plus(leaseFor);
                    best.moveTo(JobState.CLAIMED, now, "attempt " + best.attempts);
                    leases.add(new LeaseEntry(best.leaseExpiresAt, best.id, best.leaseToken));
                    return Optional.of(new Lease(best.id, best.leaseToken, best.leaseExpiresAt,
                            best.spec.type(), best.spec.payload(), best.attempts));
                }
                if (remaining <= 0) return Optional.empty();
                // Sleep until the next retry or lease expiry is due, or until signalled, whichever is first.
                remaining = changed.awaitNanos(Math.min(remaining, nanosUntilNextDue(now)));
            }
        } finally { lock.unlock(); }
    }

    public void renew(String jobId, long token, Duration extendBy) {
        withLease(jobId, token, job -> {
            job.leaseExpiresAt = clock.instant().plus(extendBy);
            leases.add(new LeaseEntry(job.leaseExpiresAt, job.id, token));   // old entry ignored lazily
        });
    }

    public void complete(String jobId, long token) {
        withLease(jobId, token, job -> job.moveTo(JobState.SUCCEEDED, clock.instant(), null));
    }

    public void fail(String jobId, long token, String error) {
        withLease(jobId, token, job -> { job.lastError = error; retryOrDeadLetter(job, clock.instant(), error); });
    }

    public boolean cancel(String jobId) {
        lock.lock();
        try {
            Job job = jobs.get(jobId);
            if (job == null || !job.state.canMoveTo(JobState.CANCELLED)) return false;
            job.moveTo(JobState.CANCELLED, clock.instant(), null);   // queue entries are skipped lazily
            return true;
        } finally { lock.unlock(); }
    }

    // ---- internals, all called with lock held ----

    private void withLease(String jobId, long token, Consumer<Job> action) {
        lock.lock();
        try {
            Job job = jobs.get(jobId);
            // Fencing: a worker whose lease expired and was re-issued holds an old token.
            if (job == null || job.state != JobState.CLAIMED || job.leaseToken != token)
                throw new StaleLeaseException(jobId);
            action.accept(job);
            changed.signalAll();
        } finally { lock.unlock(); }
    }

    private void retryOrDeadLetter(Job job, Instant now, String reason) {
        if (job.attempts > job.spec.maxRetries()) {
            job.moveTo(JobState.FAILED, now, reason);
            dlq.add(job);
        } else {
            job.runAt = now.plus(backoff.delay(job.attempts));
            job.moveTo(JobState.RETRY_SCHEDULED, now, reason + ", retry at " + job.runAt);
            delayed.add(job);
        }
    }

    private void promoteDue(Instant now) {
        while (!delayed.isEmpty() && !delayed.peek().runAt.isAfter(now)) {
            Job j = delayed.poll();
            if (j.state == JobState.RETRY_SCHEDULED) j.moveTo(JobState.PENDING, now, null);
            if (j.state == JobState.PENDING) readyFor(j.spec.type()).add(j);
        }
        while (!leases.isEmpty() && !leases.peek().expiresAt().isAfter(now)) {
            LeaseEntry e = leases.poll();
            Job j = jobs.get(e.jobId());
            boolean live = j.state == JobState.CLAIMED && j.leaseToken == e.token()
                    && !j.leaseExpiresAt.isAfter(now);                       // not renewed since
            if (!live) continue;
            if (j.attempts > j.spec.maxRetries()) {                          // poison job: crashes every worker
                j.moveTo(JobState.FAILED, now, "lease expired, retries exhausted");
                dlq.add(j);
            } else {
                j.moveTo(JobState.PENDING, now, "lease expired");
                readyFor(j.spec.type()).add(j);
            }
        }
    }

    private Job pollBest(Set<String> types) {
        Job best = null;
        PriorityQueue<Job> from = null;
        for (String t : types) {
            PriorityQueue<Job> q = ready.get(t);
            if (q == null) continue;
            while (!q.isEmpty() && q.peek().state != JobState.PENDING) q.poll();   // drop cancelled
            if (!q.isEmpty() && (best == null || BY_PRIORITY.compare(q.peek(), best) < 0)) { best = q.peek(); from = q; }
        }
        return best == null ? null : from.poll();
    }

    private long nanosUntilNextDue(Instant now) {
        Instant next = Stream.of(delayed.peek() == null ? null : delayed.peek().runAt,
                                 leases.peek() == null ? null : leases.peek().expiresAt())
                .filter(Objects::nonNull).min(Comparator.naturalOrder()).orElse(now.plus(Duration.ofSeconds(1)));
        return Math.max(1, Duration.between(now, next).toNanos());
    }

    private PriorityQueue<Job> readyFor(String type) {
        return ready.computeIfAbsent(type, t -> new PriorityQueue<>(BY_PRIORITY));
    }
}

Using one lock is a deliberate simplification. Every operation is O(log n) in memory. So one lock can handle hundreds of thousands of operations per second. If asked, use a separate lock per job type.

Show BackoffPolicy (full jitter) 
public interface BackoffPolicy { Duration delay(int attempt); }

public record ExponentialFullJitter(Duration base, Duration cap, RandomGenerator random) implements BackoffPolicy {
    public Duration delay(int attempt) {
        long ceiling = Math.min(cap.toMillis(), base.toMillis() * (1L << Math.min(attempt, 20)));  // no overflow
        return Duration.ofMillis(random.nextLong(ceiling + 1));    // uniform in [0, ceiling]
    }
}
Show Worker (lease renewal) 
public final class Worker implements Runnable {
    private final JobQueue queue;
    private final Map<String, JobHandler> handlers;
    private final Duration leaseFor;
    private final ScheduledExecutorService renewer;
    private volatile boolean running = true;

    public Worker(JobQueue q, Map<String, JobHandler> handlers, Duration leaseFor, ScheduledExecutorService renewer) {
        this.queue = q; this.handlers = handlers; this.leaseFor = leaseFor; this.renewer = renewer;
    }

    @Override
    public void run() {
        while (running && !Thread.currentThread().isInterrupted()) {
            Optional<Lease> claimed;
            try {
                claimed = queue.claim(handlers.keySet(), leaseFor, Duration.ofSeconds(1));
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            claimed.ifPresent(this::execute);
        }
    }

    private void execute(Lease lease) {
        long every = leaseFor.toMillis() / 3;     // renew well before expiry
        ScheduledFuture<?> heartbeat = renewer.scheduleAtFixedRate(
                () -> queue.renew(lease.jobId(), lease.token(), leaseFor), every, every, TimeUnit.MILLISECONDS);
        try {
            handlers.get(lease.type()).handle(lease);
            queue.complete(lease.jobId(), lease.token());
        } catch (StaleLeaseException e) {
            // Lease was lost (GC pause, slow handler). Another worker owns the job now; drop our result.
        } catch (Exception e) {
            try { queue.fail(lease.jobId(), lease.token(), e.toString()); } catch (StaleLeaseException ignored) { }
        } finally {
            heartbeat.cancel(false);
        }
    }

    public void stop() { running = false; }
}

public final class TaskGraph {
    private final Map<String, Task> tasks = new HashMap<>();
    private final Map<String, Set<String>> dependents = new HashMap<>();

    /** Rejects the add if it would create a cycle. */
    public synchronized void add(String id, int priority, Set<String> dependsOn, Callable<?> body) {
        for (String d : dependsOn) if (!tasks.containsKey(d)) throw new IllegalArgumentException("unknown " + d);
        if (dependsOn.contains(id) || reachable(id, dependsOn)) throw new CycleException(id);
        tasks.put(id, new Task(id, priority, Set.copyOf(dependsOn), body));
        dependsOn.forEach(d -> dependents.computeIfAbsent(d, k -> new HashSet<>()).add(id));
    }

    /** DFS from the new task's parents up their own parents: does any path lead back to id? */
    private boolean reachable(String id, Set<String> start) {
        Deque<String> stack = new ArrayDeque<>(start);
        Set<String> seen = new HashSet<>();
        while (!stack.isEmpty()) {
            String cur = stack.pop();
            if (cur.equals(id)) return true;
            if (seen.add(cur)) stack.addAll(tasks.get(cur).dependsOn());
        }
        return false;
    }
}

// Runner: Kahn's algorithm with a priority queue of ready tasks and a fixed pool.
// remaining[id] = AtomicInteger(#deps). On success: for each dependent, if decrementAndGet() == 0, offer it.
// On permanent failure (5 attempts): mark it FAILED and every transitive dependent SKIPPED.
// cancel(id): mark CANCELLED and SKIP its transitive dependents; running tasks get Future.cancel(true).
// history: append-only ConcurrentLinkedQueue<TaskEvent(taskId, from, to, at, attempt)>.

If all tasks are known up front, run Kahn's algorithm once. It puts tasks in dependency order. If it orders fewer tasks than the total, there is a loop. The tasks it could not reach are on the loop or behind it. The Media.net report lists loop protection as the "last thing to check". Checking at add time means the runner never sees a loop.

final class ScheduledTask implements Delayed, Runnable {
    private static final AtomicLong SEQ = new AtomicLong();
    final Runnable body;
    final long periodNanos;          // 0 = one-shot, >0 fixed rate, <0 fixed delay
    final long seq = SEQ.incrementAndGet();
    volatile long triggerNanos;
    volatile boolean cancelled;

    ScheduledTask(Runnable body, long triggerNanos, long periodNanos) {
        this.body = body; this.triggerNanos = triggerNanos; this.periodNanos = periodNanos;
    }
    public long getDelay(TimeUnit unit) { return unit.convert(triggerNanos - System.nanoTime(), TimeUnit.NANOSECONDS); }
    public int compareTo(Delayed o) {
        ScheduledTask t = (ScheduledTask) o;
        int c = Long.compare(triggerNanos, t.triggerNanos);
        return c != 0 ? c : Long.compare(seq, t.seq);
    }
    public void run() { body.run(); }
}

public final class SimpleScheduler {
    private final DelayQueue<ScheduledTask> queue = new DelayQueue<>();
    private final List<Thread> workers = new ArrayList<>();
    private volatile boolean shutdown;

    public SimpleScheduler(int threads) {
        for (int i = 0; i < threads; i++) workers.add(Thread.ofPlatform().name("sched-" + i).start(this::loop));
    }

    public ScheduledTask scheduleAtFixedRate(Runnable r, Duration initial, Duration period) {
        return submit(new ScheduledTask(r, System.nanoTime() + initial.toNanos(), period.toNanos()));
    }
    public ScheduledTask scheduleWithFixedDelay(Runnable r, Duration initial, Duration delay) {
        return submit(new ScheduledTask(r, System.nanoTime() + initial.toNanos(), -delay.toNanos()));
    }

    private ScheduledTask submit(ScheduledTask t) {
        if (shutdown) throw new RejectedExecutionException();
        queue.put(t);
        return t;
    }

    private void loop() {
        while (!shutdown) {
            ScheduledTask t;
            try { t = queue.take(); } catch (InterruptedException e) { return; }   // blocks until due
            if (t.cancelled) continue;
            try { t.run(); }
            catch (RuntimeException e) { continue; }   // like the JDK: a throwing periodic task stops recurring
            if (t.periodNanos > 0) t.triggerNanos += t.periodNanos;                     // fixed rate
            else if (t.periodNanos < 0) t.triggerNanos = System.nanoTime() - t.periodNanos; // fixed delay
            else continue;
            if (!shutdown) queue.put(t);
        }
    }

    public void shutdownNow() { shutdown = true; workers.forEach(Thread::interrupt); queue.clear(); }
}

Rubrik also asks for a thread pool built on a bounded blocking queue. It needs submit, execute, shutdown and shutdownNow. One candidate got "Lean Hire", partly because of how shutdown() and exceptions were handled. Know the difference. shutdown stops taking new tasks and finishes the queued ones. shutdownNow interrupts the workers and returns the tasks that never started. Workers must set the interrupt flag again and exit. An exception inside a task must not kill the worker thread.

Survive restarts, run on many machines

Postgres SKIP LOCKED usual pick

  • Index on (state, type, priority DESC, run_at) so finding the next job is fast.
  • You need a cleanup job for expired leases.

SQS

  • The visibility timeout is the lease. The receipt handle is the token.
  • A redrive policy gives you the DLQ.
  • A lease can last at most 12 hours.

Kafka fits badly when each message needs its own retry wait.

DLQ redrive

Moving FAILED → PENDING is already allowed. Just reset the attempts.

Queue health

Count jobs by status. Track the oldest waiting job, stuck leases and the DLQ size.

Dedupe

Map each dedupeKey to the existing job id, and return that id.

Per-type limits

Check a running-jobs counter or a token bucket inside pollBest.

Recurring (Walmart)

Schedule the next run. Don't schedule one while the current run is CLAIMED.

Priority vs delay queue

Use both. Waiting jobs are sorted by time. Ready jobs are sorted by priority.

Go deeper: full answers for each extension
DLQ inspection and redrive

Moving FAILED → PENDING is already allowed. redrive(jobId) resets the attempts and puts the job back in the queue. Add listDlq(type, limit) to look at what failed.

Observability: queue health

stats() runs under the lock. It reports counts by status and type, and the age of the oldest pending job (the head of each ready queue). It counts leases that expired in the last minute (stuck jobs) and the DLQ size. It also reports p95 time from submit to claim, meaning 95 out of 100 jobs were claimed faster than this. In Spring, expose these as Micrometer gauges.

Unique / deduplicated jobs

Add an optional dedupeKey to the spec. Keep a map from key to job id for jobs that are not finished. If the key exists, submit returns the existing id.

Rate limit per job type, or max concurrency per type

Keep a running-jobs counter per type, and check it in pollBest. Skip any type that is at its limit. For a rate limit, check a token bucket per type before claiming.

Recurring and cron jobs (Walmart)

A schedule definition creates the next job. With fixed delay, it does so when the current run finishes. With fixed rate, it does so at each tick. To stop runs overlapping, don't schedule the next one while the current one is CLAIMED.

Why PriorityBlockingQueue and not DelayQueue? (Walmart)

Priority order and time order are different sort keys. PriorityBlockingQueue sorts ready jobs by priority. A DelayQueue, or the delayed heap above, holds jobs that are not due yet, sorted by time. Use both. Move a job from delayed to ready when it becomes due.

Make it survive restarts / run on many machines

Save jobs in Postgres: jobs(id, type, state, priority, run_at, attempts, lease_token, lease_expires_at, payload jsonb). Add an index on (state, type, priority DESC, run_at). Claim with FOR UPDATE SKIP LOCKED. A cleanup job (a "reaper") resets expired leases. Or use SQS. Its visibility timeout is the lease (at most 12 hours, and it can be extended). The receipt handle is the token. A redrive policy is the DLQ. Kafka fits badly for per-message retry with backoff, unless you add separate retry topics.

12Quick check

W1's lease ran out during a long pause, and W2 now holds the job. W1 calls complete. What should happen?

The token says which lease is the current one. W1's token is older than W2's, so the queue refuses W1's call.

A job crashes every worker that runs it. Why count an expired lease as an attempt?

The crashed worker never calls fail. So the expired lease is the only sign that an attempt was used up.

500 jobs fail at once when a service they call goes down. Why add full jitter to the retry wait?

Without jitter, the same attempt number gives the same wait. All 500 jobs would retry at the same moment, which is called a thundering herd.

Why does your system run each job at least once, and what follows from that?

Tokens stop an old worker from changing the job's status. They can't undo what the old run already did, like an email it already sent.

13Interview questions

Why lazy deletion in the heaps?

PriorityQueue.remove(Object) is O(n), a full scan. Cancel and renew happen often. Skipping outdated entries when you take them out keeps those calls O(1). Claim stays O(log n) on average. The cost is some leftover entries, at most one per renewal.

Why does lease expiry count as an attempt?

Otherwise a job that crashes or hangs every worker retries forever. Counting it sends poison jobs to the DLQ after maxRetries.

Why full jitter instead of equal jitter or none?

Without jitter, jobs that failed together retry together. They hit the recovering service at the same instant. AWS ran a simulation. Backoff with no jitter was the clear loser. Full jitter and decorrelated jitter both did well, and full jitter did the least client work.

What would you change for 10,000 job types?

pollBest looks through each of the worker's types. With many types per worker, that gets slow. Keep one heap per worker group, keyed by (priority, seq). Or use one global heap that filters by type. Then split locks by groups of types.

How do you shut down gracefully?

Stop claiming new jobs. Wait until a deadline for running handlers to finish, then interrupt them. Their leases expire, and the next process runs those jobs again. That is safe because handlers are idempotent.

Cheat sheet
  • PENDING → CLAIMED → SUCCEEDED | RETRY_SCHEDULED → PENDING | FAILED (DLQ).
  • One ReentrantLock with a Condition. Heaps: ready per type, delayed, and leases.
  • Ready order: highest priority first, then seq for first in, first out.
  • Lease plus token. Every renew, complete and fail checks the token.
  • An expired lease counts as an attempt, so poison jobs reach the DLQ.
  • Backoff: random(0, min(cap, base × 2^n)).
  • Jobs run at least once, so handlers must be safe to repeat.
  • At scale: Postgres SKIP LOCKED, or the SQS visibility timeout.
