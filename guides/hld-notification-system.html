Notification system

Design one platform that sends push, SMS, email and webhook messages. A login OTP must still arrive in seconds, even while a 50-million-message marketing campaign is going out.

Time-box: 45–60 min Seen: ~7 reports, 2025–26 Probes: priority, idempotent consumers, multi-DC
RazorpayPostmanVisaMicrosoftSalesforceAdobe
In 30 seconds
  • Other services just announce "this happened". The platform handles templates, user settings, routing and retries.
  • Urgent messages get their own Kafka queue and their own workers. So an OTP never waits behind marketing.
  • Kafka can deliver the same message twice. Give each notification one ID when it arrives, and skip repeats of that ID.
  • The slow part is the SMS and email vendors and slow merchant servers. Kafka is not the problem.
Picture it

Think of India Post with a separate Speed Post counter. Ordinary letters can pile up by the thousand. But Speed Post has its own clerk and its own van. So an urgent parcel never waits behind the ordinary letters.

One-time password. The 6-digit code your bank app texts you at login. It is useless after a few minutes.

A named queue in Kafka. Messages are written to the end and read in order.

01What the interviewer is grading

Decoupling

Business services announce an event and move on. The notification platform owns templates, user preferences, routing and retries. Each team does not rebuild them.

Priority isolation

An OTP must never wait behind a marketing campaign. Interviewers want truly separate queues and workers. A "priority" field on one shared queue is not enough.

At-least-once + idempotency

Kafka sometimes delivers a message again, so duplicates happen. Say exactly where in the flow you detect and skip them.

Vendor failure

SMS and email vendors go down, slow you down, and report wrong results. Use several vendors. Stop calling a failing one, and cap the speed for each vendor.

Webhooks done properly

Payment companies ask about this. Sign each call, retry with growing waits, explain ordering limits, and cope with merchant servers that are down for hours.

Multi-DC (Staff)

Multi-DC means more than one data centre. Copy data and queues to a second one. Duplicate-skipping must still work after switching to it.

Go deeper: how each company phrased it

The wording changes, but the follow-up questions repeat. Razorpay asked for "a scalable notification delivery system for a payment processing platform". Payment events had to reach customers by SMS and email, and merchants by webhook, reliably. Postman asked for many channels, then followed up on priority. Visa's Staff round started with "Kafka, producers and consumers". It then pushed on two things. First, keeping data consistent across data centres. Second, how you make sure an event is not processed twice. Salesforce framed it as Klaviyo-style intake of huge event volumes that feed marketing campaigns.

02Clarify and scope

Functional

  • Send to a user on one or more channels. The trigger is an event or an API call.
  • Message templates with fill-in variables and several languages.
  • User preferences, opt-outs, quiet hours, and a daily limit per user (a frequency cap).
  • Priority levels. Scheduled and bulk campaigns.
  • Merchant webhooks with retries, plus an API to send an old event again (replay).
  • Delivery status for every message.

Non-functional

  • Transactional (OTPs, receipts): 20M a day, up to 2,000 a second. 99 of 100 reach the vendor within 5 seconds (p99 < 5 s).
  • Promotional (marketing): 200M a day, with bursts of 50,000 a second.
  • No notification is ever lost. Duplicates are rare and harmless.
  • The intake API is up 99.99% of the time. The system survives losing a whole data centre (DC).

Out of scope

  • Building our own email server (SMTP) or SMS gateway.
  • The screen for picking campaign audiences. Also ML that picks the best send time. Mention them, but do not design them.
Go deeper: questions to ask the interviewer
  • Which channels? Push (via Google FCM or Apple APNs), SMS, email, WhatsApp, in-app and webhooks. Each has its own speed and cost.
  • How much is transactional vs promotional? This decides the priority levels. User preferences can never block an OTP.
  • Delivery guarantee? At-least-once, with duplicates skipped. Exactly-once delivery to a phone is impossible.
  • Speed target (SLO) per level? OTP: 99 of 100 reach the vendor in under 5 s. Marketing: anywhere inside the campaign window.
  • Status tracking? Sent, delivered, read, bounced, clicked. This needs a status store and callbacks from vendors.
  • Rules and regulation? In India, commercial SMS must use templates registered on DLT, TRAI's registry. Promotional SMS can only go out at certain times of day.

04API design

  1. ProducerA service asks us to send a message. It names the template, the priority and how long the message stays useful. It adds a unique key so a retry is not sent twice (POST /v1/notifications with an Idempotency-Key and a TTL).
  2. IngestWe save the request safely and answer "accepted, we will send it soon" (HTTP 202). The answer includes the message's ID (notificationId). Sending happens later.
  3. Producer retryIf the service sends the same request again, the database sees the key already exists (a unique constraint). So the caller gets the first ID back, and no second message is created.
  4. MerchantThe merchant's server gets a call from us, signed so they know it is real (a webhook). It carries an event ID they can use to spot repeats (X-Event-Id). They can ask us to send it again later (/replay).

Go deeper: why 202 and how the key is stored

Return 202 ("accepted"), not 200 ("done"). The request is safely saved, in Kafka or the outbox table, but sending happens later. The Idempotency-Key is a unique string the caller sends with each request. It is stored per producer with a unique constraint. So if the caller retries the same POST, it gets back the original notificationId instead of a second notification.

05Data model

Cassandra

Stores every message, every send attempt and the in-app inbox. Cassandra suits this: lots of writes, rows are only added, lookups are by key, and old rows delete themselves.

Postgres

Stores message templates (with versions), user settings, phone numbers, devices and merchant webhook addresses. This data is small and tables link to each other, which suits SQL.

Redis

A fast "already sent?" marker for each message and channel, kept for 24 hours (dedupe:{notificationId}:{channel}). Also a cache of user settings, and counters for the daily message limit per user.

Outbox at the producer

The payment service saves the payment and a "send a message" note together, in one transaction. Either both are saved or neither is. A background tool then copies the note into Kafka (CDC, change data capture). So "paid, but SMS lost" cannot happen.

Ingest

The front door. It checks the request and makes sure it is not a repeat (idempotency key). It gives the message a unique, time-sorted ID (a ULID), saves it and puts it in Kafka. It keeps no state, so you can run many copies.

Router

Works out what to send and where. It finds the template, the phone or email, and the user's settings, quiet hours and daily limit. Then it puts one message per channel into the right priority queue.

Workers + adapters

Each priority and channel pair, like "urgent SMS", has its own team of workers. Each vendor has an adapter. It splits traffic between vendors, stops calling a failing one, and limits speed.

Status service

Vendors tell us later whether a message arrived (a delivery receipt, DLR). This service reads those receipts, email bounces and push errors (FCM). It removes phones that uninstalled the app and email addresses that bounce.

Go deeper: each component in full
  • Transactional outbox at the producer. The payment service saves the payment row and an outbox row in one Postgres transaction. Debezium, a CDC tool, streams the outbox row to Kafka. So the database can never commit while the event gets lost. This answers "the payment succeeded, but the customer never got the SMS".
  • Ingest. It checks the request and the idempotency key, and assigns a ULID. It saves the notification row and publishes to the routing topic. It keeps no state, so you add more copies to handle more traffic.
  • Router. It finds the template version, user contacts, preferences, quiet hours and frequency caps. Caps are Redis counters. It then creates one message per channel on the right priority topic. A marketing message that lands in quiet hours goes to a delay topic with the time it may be sent.
  • Channel workers. Each priority and channel pair has its own worker group and thread pool. A worker fills in the template, calls the vendor adapter, and records the attempt.
  • Provider adapters. One per vendor: two SMS vendors, SES plus a backup for email, FCM and APNs. Each adapter splits traffic by weight. It has a circuit breaker, which stops calling a vendor that keeps failing. It also has a token-bucket speed limit per vendor account. PhonePe's machine-coding version of this question is exactly this layer. It asks you to choose an active provider per channel and keep separate accounts for OTPs.
  • Status service. It reads vendor delivery receipts (DLRs), bounces and FCM errors, and updates each attempt's status. It removes dead device tokens and emails that bounced permanently.
  • In-app gateway. It keeps open WebSocket or SSE connections to apps. SSE (server-sent events) lets the server keep pushing to an open HTTP connection. When a message arrives, the gateway writes it to the user's inbox and pushes it to any open connection. Uber's RAMEN system used SSE for this kind of push, at 600,000 open streams at once.

08Deep dives

8.1 Priority that actually works (the Postman follow-up)

Topic + workers per tier usual pick

  • Real separation. The urgent SMS queue has its own workers and its own vendor account (notif.critical.sms).
  • Each level can grow on its own
  • More topics and worker groups to run

Always, for any system that sends OTPs.

One topic + "priority" field

  • Simple
  • Kafka reads each lane strictly in arrival order. A label cannot let the OTP skip ahead, so it waits behind 5M promos.

Never. This answer gets candidates rejected.

  • Workers shared between levels? Read urgent messages first. When urgent ones start piling up, pause reading marketing (consumer.pause()).
  • Keep vendor capacity aside. Split the vendor speed limit. For example, keep 30% for critical. Marketing only gets what is left.
  • Expiry per message. Throw away an OTP that is older than its time limit (ttlSeconds). A late OTP is worse than none.
Go deeper: why Kafka needs this

Kafka has no priority per message. A partition is a log that is read strictly in order. So a "priority" field on a shared topic does nothing for an OTP stuck behind 5 million promo messages. Your options:

  • Separate topics per level (notif.critical.sms, notif.transactional.sms, notif.promo.sms). Each has its own worker group and capacity. Critical gets reserved workers and its own vendor account. This is the answer.
  • Weighted reading if workers are shared. Read critical first. Pause promo partitions (consumer.pause()) when the critical backlog passes a limit.
  • Reserve vendor capacity. Priority is useless if marketing has used up the vendor's messages-per-second (TPS) limit. Split the per-vendor token bucket. For example, keep 30% for critical, and let marketing use only what is left.
  • Expiry (TTL) per message. An OTP older than its ttlSeconds is dropped, not sent late. A late OTP is worse than none, because the user has already asked for a new one.

  • The message ID is created once, when the message first arrives (a ULID or Snowflake ID). The worker never creates it, so every repeat carries the same ID.
  • Redis is the fast "already sent?" check. The database row is the lasting record, and its unique key blocks a second copy.
  • The honest promise: every message arrives, and almost never twice ("at least once, effectively once").
Show Java worker
// Channel worker, per message
String key = "dedupe:" + msg.notificationId() + ":" + msg.channel();
Boolean first = redis.opsForValue().setIfAbsent(key, "SENDING", Duration.ofHours(24));
if (!Boolean.TRUE.equals(first)) {
    String state = redis.opsForValue().get(key);
    if ("SENT".equals(state)) { ack(msg); return; }            // duplicate, already delivered
    if (stuckForMoreThan(key, Duration.ofMinutes(2))) { /* fall through: earlier worker died mid-send */ }
    else { ack(msg); return; }                                    // another worker is on it
}
ProviderResult r = adapter.send(render(msg), msg.notificationId()); // pass id as vendor reference if supported
attemptRepo.insert(msg, r);                                         // unique (notification_id, channel, attempt_no)

Go deeper: why Kafka exactly-once does not help

A Kafka worker records its progress (commits the offset) only after it finishes a message. So if it crashes after "SMS sent" but before the commit, Kafka gives the message out again. Kafka's exactly-once feature only covers reading from Kafka and writing back to Kafka. It does not cover an HTTP call to an SMS vendor.

  • The unique ID is created once at ingest, as a ULID or Snowflake ID. The worker never creates it. So retries and replays carry the same ID.
  • Redis is the fast check. The lasting record is the attempt row with a unique constraint. If Redis loses the key, the database insert fails as a duplicate, and you skip.
  • One gap remains: a crash after the vendor accepted, but before we recorded it. This can cause one duplicate SMS. Say so. It is rare and harmless for notifications. It is why the promise is "at least once, effectively once".
  • Webhooks: send X-Event-Id, and tell merchants they must skip repeats of it. Stripe's webhook docs ask integrators to do exactly this.

8.3 Retries, backoff and webhooks to slow merchants

Retry topics with delays usual pick

  • A failed message moves to a "try again in 30 s" queue, then 5 min, then 1 hour. After that it goes to a parking area for messages that keep failing (DLQ). Queue names: retry.30s, retry.5m, retry.1h.
  • New messages in the main queue keep flowing
  • More topics

Spring Kafka's @RetryableTopic builds it for you.

Sleep and retry in the consumer

  • Easy to write
  • While it sleeps, every message behind it in the same lane waits

Never in a shared pipeline.

1 minWebhook retry 1. Each wait is longer than the last, plus a little randomness (exponential backoff with jitter).
5 minRetry 2
30 minRetry 3
2 h · 6 h · 12 hRetries 4–6, in a separate pool for slow merchants
~1 daySwitch off the endpoint and email the merchant. They can replay from the dashboard.
Go deeper: error classes, bulkheads, ordering
  • Sort errors into kinds. A 4xx from the vendor for an invalid number means do not retry. Mark it failed. A 429, 5xx or timeout means retry. FCM "unregistered" means delete the device token.
  • Retry topics with delays (retry.30s, retry.5m, retry.1h). Do not sleep inside the worker, because that blocks the whole partition. Spring Kafka's @RetryableTopic builds this pattern. After N attempts, move the message to the DLQ (dead-letter queue) and raise an alert.
  • Webhook schedule. Retry with growing waits plus jitter over about a day. For example: 1 min, 5 min, 30 min, 2 h, 6 h, 12 h. The merchant can replay from a dashboard. After failing for a long time, switch off the endpoint and email the merchant.
  • Bulkheads per merchant. A bulkhead is a wall that keeps one problem from flooding everything. One merchant with a 30 s timeout must not use up all shared HTTP connections. Limit calls per endpoint and use short timeouts (5–10 s). Move slow merchants to a separate "slow lane" pool.
  • Ordering. Partitioning by merchant ID keeps one merchant's events in order when all goes well. Retries break that order. Tell merchants to use the event timestamp. They should fetch the current state from the API, not trust the arrival order.

8.4 Multi-DC replication (the Visa Staff follow-up)

Mumbai data centre (home for user u_99)Ingest + workersKafkaSend records (Cassandra)
↕ copied in the background (Kafka MirrorMaker 2 · Cassandra multi-DC)
Hyderabad data centre (backup)Ingest + workersCopy of KafkaCopy of send records
  • Each user or merchant has a home data centre. Only that one sends their messages, so two centres never send the same one.
  • After a switch to the backup data centre (failover), some messages get handled again. Their ID is checked against the copied send records, so they are skipped.
  • Redis is only a local, fast check. The lasting "already sent" record lives in Cassandra, which is copied to both centres.
Go deeper: multi-DC details
  • Every DC accepts, the home region processes (active-active ingest). Each data centre accepts requests. But each user or merchant has a home region, and their events are processed only there. This stops two DCs from sending the same message.
  • Kafka copying. MirrorMaker 2, or Confluent Cluster Linking, copies topics to the other DC for failover. The copy runs in the background (async), so after failover some events are read again. The global notificationId check absorbs that. But the dedupe records must also exist in the surviving DC.
  • Dedupe store across DCs. Use Cassandra, copied to every DC, for attempt records. Write at LOCAL_QUORUM, which means a majority of copies in the local DC. That is fine, because a notification is only processed in its home DC. Redis is only a local cache.
  • Idempotency key check at ingest. During a failover, a client may retry into the other DC before the key has been copied there. Either accept the small risk of a duplicate, or send each producer to a home DC. Say which one you choose.
  • RPO and RTO. RPO is how much recent data you can lose. RTO is how long recovery takes. Background copying means a few seconds of RPO. The producer's outbox lets you publish again anything that was not confirmed. Together, these make "no lost notifications" true even if a whole DC is lost.

10Trade-offs

Kafka backbone usual pick

  • You can re-read old messages. It handles huge volume, keeps order within each lane, and keeps messages for days.
  • No priority or delay per message. Costly to operate.

The default at this scale.

RabbitMQ / SQS

  • Expiry, delay and priority per message. Simple acknowledgements.
  • Harder to re-read old messages. RabbitMQ handles less volume.

Smaller platforms, or ones with lots of delayed sends.

Redis dedupe + DB unique key usual pick

  • A fast "already sent?" check in Redis, plus a lasting record in the database
  • Two stores to think about

High volume.

DB unique key only

  • One source of truth
  • Every message needs a database write before it is sent, which is slower

Lower volume, simpler operations.

Push in-app (WebSocket/SSE)

  • Instant
  • You must keep a live connection open for each user, and each user is tied to one server

Users with the app open.

Pull (inbox API on app open) always as fallback

  • Simple and easy to cache
  • Not real-time

Users without the app open. Always keep it as a fallback.

11Interview questions

How do you make sure a notification event is not consumed twice?

With at-least-once Kafka, you cannot stop a message from being delivered again. Instead, you make processing idempotent, so a repeat does no harm. A globally unique notification ID is created at ingest. Before sending, the worker runs SET NX ("set if not exists") on id:channel. It records the attempt in a table with a unique constraint. After a crash or a data-centre failover, a replayed message finds the key and is skipped. A tiny gap remains between "vendor accepted" and "we recorded it". So the honest promise is "effectively once".

How do you keep data consistent across two data centres?

Process each user's notifications in one home DC. Copy Kafka (with MirrorMaker 2) and the attempt log (with Cassandra multi-DC) to the other DC in the background, for failover. After failover, replayed events are matched by their global ID against the copied attempt log, and skipped. Producers use an outbox, so nothing unconfirmed is lost.

An OTP is stuck behind a 10M-user campaign. Fix it.

That is a design bug. OTPs need their own topic, worker group and worker pool. They also need their own vendor account, or vendor capacity kept aside for them. Add an expiry (TTL) so old OTPs are dropped. When the backlog grows, tell promo producers to slow down (backpressure).

Payment succeeded, but the customer got no SMS. How do you debug and prevent it?

Trace it by payment ID. Was the outbox row written? Did CDC publish it? Did ingest accept it? Which vendor got it? What delivery receipt (DLR) came back? To prevent it, use an outbox so no event is lost. If a transactional SMS is not delivered, retry it on a backup vendor based on the DLR. Add dashboards for delivery rate per vendor and per mobile operator.

How do you prevent spamming users?

Keep preferences and opt-outs per channel and category. Add frequency caps, which are Redis counters per user per day. Respect quiet hours in the user's timezone, for promo only. In the router, wait a short time and merge similar messages into one, like "5 new comments".

Webhook endpoint is down for 6 hours. What happens?

Retries wait longer each time, for up to about a day. They run in a separate slow-lane pool, so other merchants are not affected. Events are stored, so the merchant can replay them from the dashboard. If it keeps failing, we switch off the endpoint and email them. Every webhook is signed with HMAC, a secret-key signature, plus a timestamp to block replayed fakes. Each also carries an event ID so the merchant can skip repeats.

How would you ingest 1M events per second, Klaviyo-style?

Use thin ingest servers that check each event and append to Kafka in batches. Use acks=all (wait for all copies), an idempotent producer, and compression. Partition by account. Everything else happens later in stream processing: profile updates, audience building, and triggering flows. Reply 202 as soon as Kafka confirms the write.

Why not let each service call Twilio or SES directly?

Every team would rebuild retries, vendor failover, preferences, DLT templates, speed limits and audit logs. A platform gives one place for compliance, and one bill to negotiate. The cost is that everyone depends on it. That is why ingest must be highly available, and must accept first and process later.

12Mistakes that got candidates rejected

Rejected for this
  • Using one queue with a "priority" column, then having no answer for how an OTP gets ahead of a campaign.
  • Claiming Kafka exactly-once means no duplicate SMS.
  • Calling the SMS vendor inside the payment request, so the payment waits on the SMS.
  • Waiting and retrying inside the worker. Every message behind it in the same lane is stuck.
  • No outbox. If you save the payment and then publish the event separately, a crash in between loses the SMS.
  • Ignoring vendor speed limits and failures, which are the real bottleneck.
  • In Visa-style Staff rounds: saying "copy everything to the other data centre" without saying where the "already sent" records live after a switch.

13A 45-minute plan

0–5 minAsk about channels, priority levels, guarantees, speed targets and rules (DLT). Write the non-functional requirements.
5–9 minCapacity: requests per second per level, and storage. Show that vendor speed is the bottleneck.
9–14 minAPI: answer "accepted" (202), not "done". Add a key that blocks repeats, an expiry and a priority. Show how webhooks are signed.
14–24 minArchitecture: save events safely (outbox), then the front door (ingest) and the router. Add a queue per level and channel, workers and vendor adapters. Finish with delivery receipts and the in-app gateway.
24–36 minDeep dives: priority separation, skipping duplicates, retries and webhooks.
36–42 minFailure: a vendor going down, switching data centres without double sends, slowing producers down, and monitoring.
42–45 minRecap the trade-offs. Say what you would build next, such as best send-time and daily digests.

14Quick check

OTPs are late during a big campaign. Every message has a "priority" field, and all share one Kafka topic. What fixes it?

A partition is read strictly in order. So the OTP still waits behind the promos that arrived before it. Only real separation, including the vendor's speed limit, protects it.

Kafka has an "exactly-once" feature. Does that stop duplicate SMS?

A crash after "vendor accepted" but before "offset committed" makes Kafka send the message again. You need your own duplicate check on the notification ID.

Where should the notification ID used for skipping duplicates be created?

Repeats and retries must carry the same ID. If the worker creates the ID, each repeat gets a new ID. Then nothing is ever recognised as a duplicate.

A merchant's webhook server takes 30 s and then times out. What stops it from hurting other merchants?

These limits (bulkheads) stop one slow server from using up the shared connections. Retries go to delayed topics, not a blocked thread.

Cheat sheet
  • Save the event with the payment (outbox), then copy it to Kafka (CDC). So "paid, but SMS lost" cannot happen.
  • Ingest answers "accepted" (202). A unique key in the database blocks repeat requests.
  • One topic per priority level and channel. Separate worker groups. Vendor capacity kept aside. Expiry on OTPs.
  • Skipping repeats: create the ID once at ingest. The worker claims it in Redis (SET NX), then writes a unique row. Promise "effectively once".
  • Failed messages go to delayed retry queues, then a parking area (DLQ). Never sleep inside the worker.
  • Webhooks: sign each call with a secret and a timestamp (HMAC). Send an event ID (X-Event-Id). Retry for about a day, in a slow lane. Offer a replay API.
  • The bottleneck is vendors and merchants. Use several vendors, circuit breakers and token-bucket limits.
  • Two data centres: a home centre per user, background copying, and "already sent" records in Cassandra, not Redis.
