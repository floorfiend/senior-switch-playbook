Notification system

Design a push/SMS/email/webhook platform that gets an OTP out in seconds while a 50-million-message campaign is running.

Time-box: 45–60 min Seen: ~7 reports, 2025–26 Probes: priority, idempotent consumers, multi-DC
RazorpayPostmanVisaMicrosoftSalesforceAdobe
In 30 seconds
  • Producers publish an event; the platform owns templates, preferences, routing, retries.
  • Separate Kafka topics and workers per priority tier, so OTPs never wait.
  • Kafka is at-least-once: dedupe on a notification ID minted at ingest.
  • The real bottleneck is vendors and slow merchants, not Kafka.
Picture it

India Post with a separate Speed Post counter. Ordinary letters can pile up by the thousand, but the Speed Post queue has its own clerk and its own van, so an urgent parcel never waits behind them.

01What the interviewer is grading

Decoupling

Business services publish an event and move on. The platform owns templates, preferences, routing and retries.

Priority isolation

An OTP must never queue behind a campaign. They want physical separation, not a "priority" field.

At-least-once + idempotency

Kafka redelivers, so duplicates happen. Name the exact dedupe point.

Vendor failure

SMS and email vendors fail, throttle and lie. Use multiple providers, circuit breakers, per-provider rate limits.

Webhooks done properly

For payments companies: signatures, backoff retries, ordering caveats, merchant endpoints down for hours.

Multi-DC (Staff)

Replicate state and queues; dedupe that still works after a region fails over.

Go deeper: how each company phrased it

The prompts vary but the probes repeat. Razorpay asked for "a scalable notification delivery system for a payment processing platform": payment events must reach customers (SMS, email) and merchants (webhooks) reliably. Postman asked for multi-channel support with a follow-up on priority-based notifications. Visa's Staff round started with "Kafka, producers and consumers" and then pushed on two things: consistency across data centres, and how you guarantee an event is not consumed twice. Salesforce framed it as Klaviyo-style high-volume event ingestion feeding campaigns.

02Clarify and scope

Functional

  • Send to a user over one or more channels from an event or an API call.
  • Templates with variables and localisation.
  • User preferences, opt-outs, quiet hours, frequency caps.
  • Priority tiers; scheduled and bulk campaigns.
  • Merchant webhooks with retries and a replay API.
  • Delivery status per message.

Non-functional

  • Transactional: 20M/day, peak 2k/s; p99 < 5 s event to vendor.
  • Promotional: 200M/day, bursts of 50k/s.
  • No lost notifications; duplicates rare and harmless.
  • 99.99% availability of the ingest API; survive a DC loss.

Out of scope

  • Building an SMTP server or SMS gateway.
  • Campaign segmentation UI and ML send-time optimisation (mention, do not design).
Go deeper: questions to ask the interviewer
  • Which channels? Push (FCM/APNs), SMS, email, WhatsApp, in-app, webhooks. Each has different latency and cost.
  • Transactional vs promotional mix? Decides priority tiers. Preferences can never suppress an OTP.
  • Delivery guarantee? At-least-once with dedupe. Exactly-once to a phone is impossible.
  • Latency SLO per tier? OTP p99 under 5 s to the vendor; marketing within the campaign window.
  • Status tracking? Sent, delivered, read, bounced, clicked. Drives a status store and vendor callbacks.
  • Regulatory? India: commercial SMS needs DLT-registered templates; promo has time-of-day limits.

Go deeper: why 202 and how the key is stored

Return 202, not 200: acceptance is durable (written to Kafka or the outbox), delivery is asynchronous. The Idempotency-Key is scoped per producer and stored with a unique constraint so a retried POST returns the original notificationId.

Outbox at the producer

Payment row and outbox row commit in one transaction; CDC publishes it. No "paid but SMS lost" gap.

Ingest

Stateless. Validates, checks the idempotency key, assigns a ULID, persists, publishes.

Router

Resolves template, contacts, preferences, quiet hours, frequency caps. Splits into one message per channel on the right tier topic.

Workers + adapters

One consumer group per (priority, channel). Adapters per vendor do weighted routing, circuit breaking and token-bucket limits.

Status service

Consumes vendor delivery receipts (DLRs), bounces, FCM errors. Kills dead tokens and bounced emails.

Go deeper: each component in full
  • Transactional outbox at the producer. The payment service writes the payment row and an outbox row in one Postgres transaction; Debezium streams it to Kafka. No "DB committed but event lost" gap. This is the answer to "payment succeeded but customer never got the SMS".
  • Ingest. Validates, checks the idempotency key, assigns a ULID, writes the notification row, publishes to the routing topic. Stateless; scales horizontally.
  • Router. Resolves template version, user contacts, preferences, quiet hours, frequency caps (Redis counters), and splits into one message per channel on the right priority topic. Promotional messages that hit quiet hours go to a delay topic with the release time.
  • Channel workers. Separate consumer groups and thread pools per (priority, channel). Render the template, call the provider adapter, record the attempt.
  • Provider adapters. One per vendor (two SMS vendors, SES plus a backup for email, FCM, APNs). Weighted routing, circuit breaker, token-bucket rate limit per vendor account. PhonePe's machine-coding variant of this question (choose an active provider per channel, segregate accounts for OTP) is exactly this layer.
  • Status service. Consumes vendor delivery receipts (DLRs), bounces, FCM errors; updates attempt status; invalidates dead tokens and hard-bounced emails.
  • In-app gateway. Holds WebSocket or SSE connections; on a message it writes to the user's inbox row and pushes to any live connection. Uber's RAMEN used SSE for exactly this kind of server-to-app push at 600k concurrent streams.

08Deep dives

8.1 Priority that actually works (the Postman follow-up)

Topic + workers per tier usual pick

  • Real isolation: notif.critical.sms has its own consumers and vendor account
  • Each tier scales alone
  • More topics and consumer groups

Always for systems that send OTPs.

One topic + "priority" field

  • Simple
  • A partition is FIFO; the OTP still waits behind 5M promos

Never. This is the rejection answer.

  • Shared workers? Poll critical first; consumer.pause() promo partitions when critical lag rises.
  • Reserve vendor capacity. Split the token bucket: e.g. 30% for critical; promo only gets what is left.
  • TTL per message. Drop an OTP older than ttlSeconds. A late OTP is worse than none.
Go deeper: why Kafka needs this

Kafka has no per-message priority; a partition is a FIFO log. A "priority" field on a shared topic does nothing for an OTP stuck behind 5 million promo messages. Options:

  • Separate topics per tier (notif.critical.sms, notif.transactional.sms, notif.promo.sms) with separate consumer groups and capacity. Critical gets reserved workers and its own vendor account. This is the answer.
  • Weighted consumption if workers are shared: poll critical first, pause promo partitions (consumer.pause()) when critical lag rises above a threshold.
  • Vendor capacity reservation. Priority is useless if promo traffic has consumed the vendor's TPS. Split the per-vendor token bucket: e.g. 30% reserved for critical, promo can only use what is left.
  • TTL per message. An OTP older than its ttlSeconds is dropped, not delivered late. A late OTP is worse than none because the user has already requested another.

  • The ID is minted once at ingest (ULID/Snowflake), never by the consumer.

  • Honest guarantee: "at least once, effectively once".
Show Java worker
// Channel worker, per message
String key = "dedupe:" + msg.notificationId() + ":" + msg.channel();
Boolean first = redis.opsForValue().setIfAbsent(key, "SENDING", Duration.ofHours(24));
if (!Boolean.TRUE.equals(first)) {
    String state = redis.opsForValue().get(key);
    if ("SENT".equals(state)) { ack(msg); return; }            // duplicate, already delivered
    if (stuckForMoreThan(key, Duration.ofMinutes(2))) { /* fall through: earlier worker died mid-send */ }
    else { ack(msg); return; }                                    // another worker is on it
}
ProviderResult r = adapter.send(render(msg), msg.notificationId()); // pass id as vendor reference if supported
attemptRepo.insert(msg, r);                                         // unique (notification_id, channel, attempt_no)
redis.opsForValue().set(key, "SENT", Duration.ofHours(24));
ack(msg);
Go deeper: why Kafka exactly-once does not help

Kafka consumers commit offsets after processing, so a crash between "SMS sent" and "offset committed" replays the message. Exactly-once semantics in Kafka cover Kafka-to-Kafka; they do not extend to an HTTP call to an SMS vendor.

  • The globally unique ID is generated once at ingest (ULID or Snowflake), never by the consumer, so retries and replays carry the same ID.
  • Redis is the fast path; the durable truth is the attempt row with a unique constraint. If Redis loses the key, the DB insert conflicts and you skip.
  • The remaining window (crash after the vendor accepted but before recording) can cause one duplicate SMS. Say so: it is rare and harmless for notifications, and it is why the guarantee is "at least once, effectively once".
  • Webhooks: send X-Event-Id and document that merchants must dedupe on it. Stripe's webhook docs ask integrators for exactly this.

8.3 Retries, backoff and webhooks to slow merchants

  • More topics

Sleep and retry in the consumer

  • Trivial to write
  • Blocks everything behind it on the partition

Never in a shared pipeline.

Go deeper: error classes, bulkheads, ordering
  • Classify errors. 4xx from a vendor for an invalid number: do not retry, mark failed. 429/5xx/timeouts: retry. FCM "unregistered": delete the token.
  • Retry topics with delays (retry.30s, retry.5m, retry.1h) instead of sleeping in the consumer, which would block the partition. Spring Kafka's @RetryableTopic builds this pattern. After N attempts, DLQ plus alert.
  • Webhook schedule. Exponential backoff with jitter over about a day (e.g. 1 min, 5 min, 30 min, 2 h, 6 h, 12 h). Merchant can replay from a dashboard. After sustained failures, disable the endpoint and email the merchant.
  • Bulkheads per merchant. One merchant with a 30 s timeout must not exhaust shared HTTP connections. Bound concurrency per endpoint and short timeouts (5–10 s). Slow merchants get moved to a separate "slow lane" pool.
  • Ordering. Partition by merchant ID keeps order per merchant on the happy path, but retries break order. Tell merchants to use the event timestamp and fetch current state from the API rather than trusting arrival order.

8.4 Multi-DC replication (the Visa Staff follow-up)

DC Mumbai (home for user u_99)Ingest + workersKafkaCassandra attempts
↕ MirrorMaker 2 · Cassandra multi-DC (async)
DC Hyderabad (failover)Ingest + workersKafka mirrorCassandra replica
  • Home region per user or merchant: only one DC processes them, so no double send.
  • On failover some events replay; the global ID dedupes against the replicated attempt log.
  • Redis is local cache only. The durable dedupe state lives in Cassandra.
Go deeper: multi-DC details
  • Active-active ingest, home-region processing. Each DC accepts requests. A user (or merchant) has a home region; events are processed there to avoid double-sending from two DCs.
  • Kafka replication. MirrorMaker 2 (or Confluent Cluster Linking) replicates topics to the other DC for failover. Replication is async, so on failover some events are re-consumed: the global notificationId dedupe absorbs that, provided the dedupe state is also available in the surviving DC.
  • Dedupe store across DCs. Cassandra with multi-DC replication for attempt records (write at LOCAL_QUORUM, which is fine because a notification is only processed in its home DC). Redis is a local cache only.
  • Idempotency key lookup on ingest. If a client retries into the other DC during a failover, the key may not yet be replicated: accept the small duplicate risk, or route by producer to a home DC. Say which.
  • RPO/RTO. Async replication means seconds of RPO; the outbox at the producer lets you re-publish anything not confirmed. That combination is what makes "no lost notifications" true across a DC loss.

11Interview questions

How do you make sure a notification event is not consumed twice?

You cannot prevent redelivery with at-least-once Kafka; you make consumption idempotent. A globally unique notification ID is minted at ingest. The worker does SET NX on id:channel before sending and records the attempt with a unique constraint. Replays after a crash or DC failover see the key and skip. A tiny window remains between vendor accept and recording, so the honest guarantee is effectively-once.

How do you keep data consistent across two data centres?

Process each user's notifications in one home DC; replicate Kafka (MirrorMaker 2) and the attempt log (Cassandra multi-DC) asynchronously for failover. On failover, replayed events are deduped by the global ID against the replicated attempt log. Producers use an outbox so nothing unconfirmed is lost.

An OTP is stuck behind a 10M-user campaign. Fix it.

That is a design bug: OTPs need their own topic, consumer group, worker pool and vendor account or reserved vendor capacity. Add a TTL so stale OTPs are dropped. Promo producers get backpressure when lag rises.

Payment succeeded, but the customer got no SMS. How do you debug and prevent it?

Trace by payment ID: was the outbox row written, did CDC publish, did ingest accept, which vendor, what DLR came back. Prevention: outbox (no lost events), DLR-driven retries on a secondary vendor for undelivered transactional SMS, and dashboards on delivered-rate per vendor and operator.

How do you prevent spamming users?

Preferences and opt-outs per channel and category, frequency caps as Redis counters per user per day, quiet hours in the user's timezone (promo only), and collapsing similar notifications ("5 new comments") in the router with a short aggregation window.

Webhook endpoint is down for 6 hours. What happens?

Retries back off up to about a day, in a slow-lane pool so other merchants are unaffected. Events are stored, so the merchant can replay from the dashboard. After sustained failure, we disable and email them. Every webhook is signed (HMAC with timestamp to block replays) and carries an event ID for dedupe.

How would you ingest 1M events per second, Klaviyo-style?

Thin ingest nodes that validate and append to Kafka in batches (acks=all, idempotent producer, compression), partitioned by account. Everything else, profile updates, segmentation and triggering flows, is downstream stream processing. Return 202 as soon as Kafka acknowledges.

Why not let each service call Twilio or SES directly?

Every team would re-implement retries, vendor failover, preferences, DLT templates, rate limits and audit. A platform gives one place for compliance and one bill to negotiate. The cost is a central dependency, which is why ingest must be highly available and accept-then-process.

12Mistakes that got candidates rejected

Rejected for this
  • A single queue with a "priority" column, then no answer when asked how an OTP gets ahead of a campaign.
  • Claiming Kafka exactly-once means no duplicate SMS.
  • Calling the vendor synchronously from the payment request path.
  • Sleeping or retrying in the consumer thread, blocking the partition for everyone behind it.
  • No outbox: "save payment, then publish event" with a gap where the process can die.
  • Ignoring vendor rate limits and failures, the real bottleneck.
  • For Visa-style Staff rounds: hand-waving "replicate everything" without saying where dedupe state lives after failover.

14Quick check

OTPs are delayed during a big campaign. Every message carries a "priority" field on one Kafka topic. What fixes it?

A partition is a FIFO log, so the OTP still waits behind earlier promos. Only physical separation, including vendor TPS, isolates it.

Kafka offers exactly-once semantics. Does that stop duplicate SMS?

A crash between "vendor accepted" and "offset committed" replays the message. You need your own dedupe on the notification ID.

Where should the notification ID used for dedupe be generated?

Replays and retries must carry the same ID. An ID minted by the consumer is new on every redelivery and dedupes nothing.

A merchant's webhook endpoint times out after 30 s. What stops it hurting other merchants?

Bulkheads keep one slow endpoint from exhausting shared connections; retries go to delayed topics, not a blocked thread.

Cheat sheet
  • Outbox + CDC at the producer: no "paid but SMS lost".
  • Ingest returns 202; idempotency key with a unique constraint.
  • Topics per (tier × channel), separate consumer groups, reserved vendor TPS, TTL on OTPs.
  • Dedupe: ID minted at ingest → Redis SET NX → attempt row unique key. "Effectively once".
  • Retry topics with delays → DLQ. Never sleep in the consumer.
  • Webhooks: HMAC + timestamp, X-Event-Id, ~1 day backoff, slow lane, replay API.
  • Bottleneck = vendors and merchants. Multiple vendors, circuit breakers, token buckets.
  • Multi-DC: home region per user, async mirror, dedupe in Cassandra not Redis.
