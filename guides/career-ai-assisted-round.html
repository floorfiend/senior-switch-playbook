AI-assisted and agentic coding rounds

A growing number of companies now hand you an AI coding assistant during the interview and grade how you drive it: your design, how precisely you prompt, how critically you review its diffs, whether you commit in small green steps, and how calmly you absorb a new requirement late in the round. This lesson covers the reported formats, a minute-by-minute playbook, a PLAN.md template and a practice routine with Claude Code.

Time-box: 60–90 min (CRED: 24 h take-home) Seen: Razorpay, Flipkart, Amazon, LinkedIn, CRED, Postman, Microsoft, Meta

The common thread

None of these rounds reward "the AI wrote it all". They reward an engineer who decides, delegates the typing, verifies everything, and can explain every line afterwards. Treat the AI as a fast junior pair you are responsible for.

02What's graded

Design first

You produce the entities, interfaces and the plan before asking for code. The agent implements your design, not its own.

Prompting precision

Small, scoped prompts with explicit constraints, file names, signatures and acceptance tests. Vague "build the system" prompts score poorly.

Reviewing diffs

You read each diff, catch wrong assumptions, invented APIs, missing synchronisation, over-engineering, and say so out loud.

Incremental commits

A git history of small, green steps: "add Cache interface + tests", "LRU eviction", "TTL extension".

Tests green

Tests written (or specified by you) early, run after every step, never deleted to make things pass.

Absorbing change

When a new requirement arrives late (around minute 70 of 90), you update the plan, make a targeted change, keep tests green, and explain the impact.

Rejected for this
  • Pasting the whole problem into the agent and accepting a 600-line dump you cannot explain.
  • Letting the AI weaken or delete failing tests (especially in "fix the failing tests" tasks).
  • Long silences while the agent works. Narrate what you expect it to produce and what you will check.
  • No commits until the end; one broken commit at minute 88.
  • Not knowing your tool: fumbling with plan mode, permissions or the test command in the first 10 minutes.

03Step-by-step playbook (90-minute round)

0–10 minClarify with the interviewer, not the AI. Write requirements, out-of-scope, and 3–5 acceptance examples into PLAN.md.
10–20 minDesign: entities, interfaces, package layout, concurrency approach. Optionally ask the agent (in plan mode) to critique your design; accept or reject each suggestion out loud.
20–25 minSkeleton + tests: ask for interfaces and failing tests for the acceptance examples. Run them. Commit "skeleton + failing tests".
25–60 minImplement in slices: one prompt per class or behaviour. Review diff → run tests → commit. 4–6 commits.
60–70 minHarden: edge cases, thread-safety, input validation, a small demo main or integration test.
70–85 minNew requirement: update PLAN.md, identify the extension point, implement with a test first, commit.
85–90 minWalkthrough: git log, design choices, what you rejected from the AI and why, what you would do with more time.

04PLAN.md template

Create this file first. It anchors the agent (point it at the file in every prompt), shows the interviewer your thinking, and makes the minute-70 change easy.

# PLAN: Parking Lot (example)

## Requirements (confirmed with interviewer)
- Park/unpark vehicles (BIKE, CAR, TRUCK) in matching spot sizes
- Multiple floors; nearest free spot first
- Fee: hourly by vehicle type, injectable Clock
- Thread-safe: concurrent park calls must never double-allocate a spot

## Out of scope
- Persistence, REST API, payments gateway

## Acceptance examples
1. Empty lot, park CAR -> ticket on floor 0, spot C1
2. Lot full for CAR -> ParkingFullException
3. Park at 10:00, unpark at 12:30, CAR rate 40/h -> fee 120 (ceil hours)
4. 100 threads park concurrently into 50 spots -> exactly 50 tickets, no duplicates

## Design
- Vehicle(type, plate), Spot(id, size, floor), Ticket(id, spot, vehicle, entryTime)
- SpotAllocator interface -> NearestFirstAllocator (ConcurrentSkipListSet per size)
- FeeCalculator interface -> HourlyFeeCalculator(Map<Type, rate>, Clock)
- ParkingLot facade: park(), unpark()
- Concurrency: allocation via pollFirst() on the free-set (atomic removal)

## Steps (commit after each, tests green)
- [ ] 1. Domain records + interfaces + failing tests for examples 1-4
- [ ] 2. NearestFirstAllocator
- [ ] 3. HourlyFeeCalculator
- [ ] 4. ParkingLot facade
- [ ] 5. Concurrency test (example 4)

## Decisions / rejected AI suggestions
- Rejected: synchronized on whole ParkingLot (kills throughput); using pollFirst instead

## Changes after minute 70
- (filled in live)

05Prompting patterns that work

1. Plan-only prompt

Read PLAN.md. Do not write code yet. List the files you would create for step 1,
with each class's public methods and the test names. Flag anything in the plan
that is ambiguous or that you disagree with.

2. Scoped implementation prompt

Implement step 2 from PLAN.md only: NearestFirstAllocator in
src/main/java/lot/NearestFirstAllocator.java implementing SpotAllocator.
Constraints: Java 21, no new dependencies, thread-safe via ConcurrentSkipListSet
per SpotSize ordered by (floor, spotNo). Do not modify tests or other classes.
Then run ./gradlew test and show me the result.

3. Test-first prompt

Write a JUnit 5 test for acceptance example 4: 100 threads via an ExecutorService
and a CountDownLatch start gate, parking into 50 CAR spots. Assert exactly 50
tickets, 50 ParkingFullException, and no duplicate spot ids. Don't implement
anything else.

4. Review-request prompt

Review your last diff for: race conditions, unhandled nulls, behaviour not in
PLAN.md, and any API you used that does not exist in the JDK 21 standard library.
List issues only; don't change code.

5. Failing-tests task prompt (Amazon-style)

Run the test suite and summarise each failing test: the assertion, the expected vs
actual value, and the production method involved. Do not modify any file under
src/test. Propose the smallest production-code fix for the first failure only.
Patterns that keep you in control
  • Name files, signatures and constraints. Say what not to touch.
  • One behaviour per prompt; ask it to run tests at the end.
  • Ask for a plan or a list of issues before code when the change spans 3+ files.
  • When it drifts, stop it, restate constraints, and point it back to PLAN.md.
  • Type small fixes yourself. Prompting a one-line change takes longer than writing it.

06Reviewing diffs out loud

Interviewers want to hear your review. Use a fixed checklist so it sounds deliberate:

  1. Scope: did it change only what I asked? Any new files or dependencies?
  2. Correctness: off-by-one, null handling, rounding (fees), time zones (Clock injected?).
  3. Concurrency: check-then-act races, non-atomic compound operations on ConcurrentHashMap, locks held during I/O.
  4. Invented APIs: methods that do not exist in the JDK or the library version.
  5. Tests: do they assert behaviour, or just "not null"? Were any tests modified?
  6. Readability: names, size of methods, needless abstraction (factories for one class).

Example narration: "It used map.get then put for the counter. That's a race under concurrent calls, so I'll change it to merge. It also added a Builder for Ticket that we don't need; removing it."

07The minute-70 requirement

Most AI-assisted rounds add a requirement late: "now support TTL in the LRU", "add a reserved-spot type for EVs", "make fees configurable per tenant". It tests whether your design was extensible and whether you stay disciplined under time pressure.

  1. Repeat the requirement and ask one clarifying question.
  2. Add it to PLAN.md under "Changes after minute 70" with the extension point you will use.
  3. Write or prompt the failing test first.
  4. Prompt a scoped change to that extension point only.
  5. Run all tests, commit, and say what other code was untouched — that's the evidence your design was good.

For the LinkedIn-style LRU → extension: if your LRU uses a HashMap + doubly linked list behind a Cache<K,V> interface with an EvictionPolicy, adding TTL is a decorator or an expiry check on get plus a timestamp in the node, with a Clock for tests. See Cache library LLD.

08Practice routine with Claude Code

Do this three times before your first AI-assisted round. Pick problems from the LLD guides in this playbook.

Setup (once)Install Claude Code, create a Gradle Java 21 template repo with JUnit 5 and AssertJ, verify ./gradlew test runs in under 20 s. Learn plan mode (Shift+Tab to cycle modes, or /plan), and how to approve or reject edits.
Session 1Parking lot, 90 min clock, with the PLAN.md template. Add the "EV reserved spots" requirement at minute 70.
Session 2LRU cache, 60 min, LinkedIn-style: LRU first, then TTL extension at minute 40.
Session 3Fix-failing-tests: ask a friend (or an LLM in a separate chat) to plant 4 bugs in your rate limiter solution. 45 min, tests are the spec, no test edits.
After eachRead your git log. Score yourself with the rubric in Mock interviews. Count: prompts sent, diffs rejected, commits, minutes of silence.
Know the environment you'll get

Some companies let you use your own setup (screen-shared), others give you a browser IDE with a built-in assistant and a model picker (Meta's format). Ask the recruiter which tool, which language runtime, and whether internet search is allowed. If it's your own machine, test the screen share and the full test run the day before.

09Questions interviewers ask during or after

"Why did you reject that suggestion?"

Give the concrete reason: "It synchronised the whole facade, which serialises unrelated floors; atomic pollFirst on a concurrent set gives correctness without the global lock."

"How do you know the AI's code is correct?"

Tests derived from acceptance examples written before the code, a concurrency test with a start latch, reading every diff, and checking that no tests were modified. For security-sensitive code, a second targeted test for the abuse case.

"What would you have done without the AI?"

The same design and tests; the AI saved typing time on boilerplate and test scaffolding. Being able to say this convincingly shows the design was yours.

"How do you use AI in your day job?"

Use the STAR story from STAR stories: workflow, validation rules, a concrete catch.

"What are the risks of AI-generated code in production?"

Plausible-but-wrong logic, invented APIs, subtle concurrency and security bugs, licence contamination, and reviewers rubber-stamping large diffs. Mitigations: small diffs, mandatory tests, human review of security paths, static analysis, and limiting agent permissions.
