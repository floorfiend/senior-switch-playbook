Atomicity

A compound action (read, add, write) is not interleaved with another thread's.

Visibility

A write by one thread is actually seen by another.

Ordering

The compiler and CPU do not reorder steps in a way that breaks you.

Go deeper: why every backend engineer gets this

Backend services are concurrent whether you think about it or not: every Tomcat request thread, Kafka listener, @Async method and scheduled job shares beans and caches. Interviewers use concurrency to separate engineers who have debugged a production race from those who have only read about one. What the reports show:

  • Media.net, Nykaa, Goldman Sachs, Walmart: write a thread-safe Singleton with double-checked locking, then explain why volatile is required.
  • Freshworks: "tell me about deadlocks you have seen in production", how you found them and how you fixed them.
  • Google (L5): implement your own CompletableFuture with chaining.
  • Rubrik: build a bounded blocking queue, then a thread pool on top of it.
  • Goldman Sachs: two threads print odd and even numbers in order.
  • CleverTap: allow at most two threads into a section at once (Semaphore).

These all test the same three ideas: atomicity (a compound action is not interleaved), visibility (a write by one thread is seen by another) and ordering (the compiler and CPU do not reorder in a way that breaks you). Learn those and every question becomes a variation.

Show Java: DCL, holder idiom and enum Singleton
final class ConfigRegistry {
    private static volatile ConfigRegistry instance;   // volatile is what makes DCL correct

    private ConfigRegistry() { }

    static ConfigRegistry getInstance() {
        ConfigRegistry local = instance;                // one volatile read on the fast path
        if (local == null) {
            synchronized (ConfigRegistry.class) {
                local = instance;
                if (local == null) {
                    local = new ConfigRegistry();
                    instance = local;                   // volatile write publishes a fully built object
                }
            }
        }
        return local;
    }
}

final class LazyHolderSingleton {                       // preferred: the JVM's class-init lock does the work
    private LazyHolderSingleton() { }

    private static final class Holder {
        static final LazyHolderSingleton INSTANCE = new LazyHolderSingleton();
    }

    static LazyHolderSingleton getInstance() { return Holder.INSTANCE; }
}

enum EnumSingleton {                                    // also safe against reflection and serialization
    INSTANCE;
}

Go deeper: the memory model and DCL in full

volatile int count; count++ is still three steps (read, add, write) and loses updates. For a counter use AtomicInteger/LongAdder.

Each core has caches and store buffers; the JIT keeps values in registers, hoists reads out of loops and reorders independent statements. Without synchronisation, a thread may never see another thread's write, or may see writes in a different order than they were made. The JMM (JLS chapter 17) defines when a write is guaranteed visible: if write W happens-before read R, R sees W (or something later). The edges you use daily:

Why volatile: instance = new ConfigRegistry() is allocate, run constructor, assign reference. Without volatile the JIT or CPU may publish the reference before the constructor's writes are visible. A second thread passes the first null check without locking and uses a half-built object. The volatile write creates a happens-before edge to the unlocked read, which forbids that. Copying to a local (local) means one volatile read on the hot path instead of two. In an interview, write DCL because they asked, then say the holder idiom is simpler (class initialisation is lazy and guarded by the JVM), and the enum is the only form that survives reflection and serialisation attacks. In Spring, the container already gives you singletons; you rarely write any of these.

03Locks and deadlock

Two transfers, two accounts, one deadlock
Show Java: Deadlock demo
class Account {
    final long id;
    long balance;

    Account(long id, long balance) { this.id = id; this.balance = balance; }
}

class Deadlock {
    static void transferUnsafe(Account from, Account to, long amount) {
        synchronized (from) {                  // T1 locks A then wants B; T2 locks B then wants A
            sleep(50);
            synchronized (to) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    static void transferSafe(Account from, Account to, long amount) {
        Account first = from.id < to.id ? from : to;     // global lock order by id
        Account second = first == from ? to : from;
        synchronized (first) {
            synchronized (second) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    public static void main(String[] args) throws Exception {
        Account a = new Account(1, 100);
        Account b = new Account(2, 100);
        boolean unsafe = args.length > 0;
        Thread t1 = new Thread(() -> { if (unsafe) transferUnsafe(a, b, 10); else transferSafe(a, b, 10); }, "transfer-a-to-b");
        Thread t2 = new Thread(() -> { if (unsafe) transferUnsafe(b, a, 20); else transferSafe(b, a, 20); }, "transfer-b-to-a");
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println(a.balance + " " + b.balance);  // 110 90 with transferSafe
    }
}

Show Java: ReentrantLock, ReadWriteLock and tryLock
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

class RateCardCache {                                       // read-mostly: many readers, rare writer
    private final Map<String, Long> rates = new HashMap<>();
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

    Long get(String plan) {
        rw.readLock().lock();
        try {
            return rates.get(plan);
        } finally {
            rw.readLock().unlock();
        }
    }

    void reload(Map<String, Long> fresh) {
        rw.writeLock().lock();
        try {
            rates.clear();
            rates.putAll(fresh);
        } finally {
            rw.writeLock().unlock();
        }
    }
}

class Wallet {
    private final ReentrantLock lock = new ReentrantLock();
    private long balance = 100;

    boolean tryDebit(long amount) throws InterruptedException {
        if (!lock.tryLock(200, TimeUnit.MILLISECONDS)) {    // give up instead of waiting forever
            return false;                                    // caller retries or returns 409/503
        }
        try {
            if (balance < amount) {
                return false;
            }
            balance -= amount;
            return true;
        } finally {
            lock.unlock();                                   // always in finally
        }
    }
}

class Locks {
    public static void main(String[] args) throws Exception {
        RateCardCache c = new RateCardCache();
        c.reload(Map.of("pro", 999L));
        Wallet w = new Wallet();
        System.out.println(c.get("pro") + " " + w.tryDebit(60) + " " + w.tryDebit(60)); // 999 true false
    }
}
Go deeper: monitors, AQS, ReadWriteLock and reading dumps

synchronized and monitors

Every object can act as a monitor. HotSpot starts with a cheap lightweight lock (a CAS on the object header's mark word) and inflates to a heavyweight ObjectMonitor with an OS-level wait queue only under contention or when wait() is called. Biased locking was disabled by default in JDK 15 (JEP 374) and later removed. synchronized is reentrant, cannot be interrupted while waiting for the lock, has no timeout and no fairness option. wait/notify must be called while holding the monitor, and wait must always sit inside a while loop because of spurious wake-ups and because another thread may have changed the condition before you reacquired the lock.

ReentrantLock, ReadWriteLock, Condition, tryLock

ReentrantLock is built on AbstractQueuedSynchronizer (AQS): an int state changed by CAS (0 = free, n = hold count) and a FIFO queue of parked waiter nodes. Semaphore, CountDownLatch and ReentrantReadWriteLock are the same AQS with a different meaning for state. What ReentrantLock adds over synchronized:

  • tryLock() and tryLock(timeout): give up instead of waiting forever. The standard tool against deadlock in code paths you cannot order.
  • lockInterruptibly(): a blocked thread can be cancelled.
  • Fairness option (new ReentrantLock(true)): FIFO handoff, lower throughput.
  • Multiple Conditions per lock (notFull, notEmpty), so you wake only the right waiters instead of notifyAll.

The cost: you must unlock() in finally. ReentrantReadWriteLock lets many readers in at once and gives writers exclusive access; it pays off only for read-heavy data where reads are not trivially short. It is not upgradable (holding the read lock and asking for the write lock deadlocks); StampedLock adds optimistic reads.

Deadlock: causes and how to find one

A deadlock needs all four Coffman conditions: mutual exclusion, hold-and-wait, no pre-emption, circular wait. Break any one. In practice you break circular wait with a global lock order, or hold-and-wait with tryLock and back-off. The classic production causes: two transfers locking accounts in opposite order; nested synchronized calls across two services' beans; a thread holding a lock while blocking on a bounded pool whose threads need that lock; database row locks taken in different orders by two transactions (Postgres detects and aborts one with deadlock detected).

Run it with an argument to use transferUnsafe and it hangs. Take a thread dump with jstack <pid>, jcmd <pid> Thread.print, kill -3 <pid> (prints to stdout), or Spring Boot Actuator's /actuator/threaddump. The JVM detects monitor and ReentrantLock cycles and prints them at the end. This is real output from the program above (shown in "Show the real thread dump").

Read it as: thread state BLOCKED (on object monitor), "locked X, waiting to lock Y", and another thread "locked Y, waiting to lock X". For ReentrantLock the threads show WAITING (parking) and the dump lists "Locked ownable synchronizers". Take three dumps 5 seconds apart: threads stuck on the same frame in all three are your suspects, which also catches livelocks and pool starvation that the JVM does not flag as deadlocks. A good Freshworks-style answer names the symptom (request latency climbing, Tomcat threads exhausted, CPU near zero), the evidence (thread dump), the fix (lock ordering or tryLock with timeout) and the guard (an alert on busy thread count).

Show Java: atomics demo
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.LongAdder;

class Atomics {
    static final AtomicLong maxSeen = new AtomicLong();

    static void recordLatency(long ms) {                     // the CAS loop behind every atomic
        long cur;
        do {
            cur = maxSeen.get();
            if (ms <= cur) {
                return;
            }
        } while (!maxSeen.compareAndSet(cur, ms));           // retry if another thread won the race
    }

    public static void main(String[] args) throws Exception {
        LongAdder requests = new LongAdder();                // striped counter: better under heavy contention
        Thread[] ts = new Thread[8];
        for (int t = 0; t < ts.length; t++) {
            final int seed = t;
            ts[t] = new Thread(() -> {
                for (int i = 0; i < 10_000; i++) {
                    requests.increment();
                    recordLatency((i * 31L + seed) % 997);
                }
            });
            ts[t].start();
        }
        for (Thread t : ts) t.join();
        System.out.println(requests.sum() + " " + maxSeen.get()); // 80000 996
        maxSeen.accumulateAndGet(1500, Math::max);           // same thing, library-provided
        System.out.println(maxSeen.get());                    // 1500
    }
}
Go deeper: CAS instructions and ABA

compareAndSet(expected, new) is one CPU instruction (LOCK CMPXCHG on x86, LSE CAS or LL/SC on ARM): it writes only if the current value is still expected. Atomics loop until their CAS wins, so they never block, but under heavy contention many threads spin and retry. LongAdder fixes contention by spreading increments across cells and summing on read: use it for metrics counters, use AtomicLong when you need the exact value on each update (ID generators, compare-and-set state machines). The ABA problem (value goes A to B to A and a CAS wrongly succeeds) matters for lock-free stacks; AtomicStampedReference adds a version.

Show Java: a production ThreadPoolExecutor
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

class PoolConfig {
    static ThreadPoolExecutor pdfRenderPool() {
        int cores = Runtime.getRuntime().availableProcessors();
        return new ThreadPoolExecutor(
                cores, cores,                                // CPU-bound: about one thread per core
                60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(500),               // bounded: memory cannot grow without limit
                r -> {
                    Thread t = new Thread(r, "pdf-render");
                    t.setDaemon(true);
                    return t;
                },
                new ThreadPoolExecutor.CallerRunsPolicy());  // backpressure: the submitter does the work
    }

    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor p = pdfRenderPool();
        System.out.println(p.submit(() -> 6 * 7).get());
        p.shutdown();
    }
}
Go deeper: pool defaults and the sizing formula

Consequences seniors are expected to know: Executors.newFixedThreadPool uses an unbounded LinkedBlockingQueue, so under overload it queues until OutOfMemoryError and maximumPoolSize never applies. newCachedThreadPool uses a SynchronousQueue and can create unbounded threads. In production build ThreadPoolExecutor yourself with a bounded queue, named threads, and a rejection policy that applies backpressure.

Sizing (Goetz): threads = cores × target utilisation × (1 + wait time / compute time). CPU-bound work: about one thread per core. A task that waits 90 ms on HTTP for every 10 ms of CPU on 8 cores: 8 × 1 × (1 + 9) = 80 threads. Then check the real limit, which is usually downstream: a Hikari pool of 20 connections means more than 20 threads doing DB work just queue on the pool. Little's law (concurrency = throughput × latency) gives the same number from the other direction: 400 req/s × 0.2 s = 80 in flight.

06CompletableFuture

Show Java: CompletableFuture demo
import java.util.List;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.CompletionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

class CfDemo {
    record Doc(String id, String ownerId) { }
    record User(String id, String email) { }

    static final ExecutorService IO = Executors.newFixedThreadPool(8);

    static CompletableFuture<Doc> fetchDoc(String id) {
        return CompletableFuture.supplyAsync(() -> new Doc(id, "u-" + id), IO);
    }

    static CompletableFuture<User> fetchUser(String id) {
        return CompletableFuture.supplyAsync(() -> {
            if (id.endsWith("bad")) throw new IllegalStateException("user service 500");
            return new User(id, id + "@example.com");
        }, IO);
    }

    public static void main(String[] args) {
        // thenApply: synchronous transform T -> U
        CompletableFuture<String> owner = fetchDoc("d1").thenApply(Doc::ownerId);

        // thenCompose: T -> CompletableFuture<U>, flattened (thenApply would give CF<CF<User>>)
        CompletableFuture<User> user = fetchDoc("d1").thenCompose(d -> fetchUser(d.ownerId()));

        // allOf: fan out, then join results; allOf itself returns CompletableFuture<Void>
        List<CompletableFuture<User>> calls = List.of(fetchUser("a"), fetchUser("b"), fetchUser("c"));
        CompletableFuture<List<String>> emails = CompletableFuture.allOf(calls.toArray(CompletableFuture[]::new))
                .thenApply(v -> calls.stream().map(CompletableFuture::join).map(User::email).toList());

        // exceptionally / handle: recover; orTimeout: never wait forever on a remote call
        CompletableFuture<String> safe = fetchUser("x-bad")
                .thenApply(User::email)
                .orTimeout(2, TimeUnit.SECONDS)
                .exceptionally(ex -> "fallback: " + (ex instanceof CompletionException ? ex.getCause() : ex).getMessage());

        System.out.println(owner.join());
        System.out.println(user.join().email());
        System.out.println(emails.join());
        System.out.println(safe.join());
        IO.shutdown();
    }
}
Go deeper: CompletableFuture rules in full
  • thenApply(fn): transform the value with a synchronous function (map). thenCompose(fn): fn returns another CompletableFuture and the result is flattened (flatMap). Using thenApply with an async call gives CompletableFuture<CompletableFuture<T>>.
  • thenCombine: two independent futures to one value. allOf: returns CompletableFuture<Void>; read the results with join() on each input inside a following stage. anyOf: first to finish.
  • Exceptions: exceptionally (recover), handle (value or exception, always runs), whenComplete (side effect, does not change the result). An exception from an upstream stage arrives wrapped in CompletionException; get() wraps in ExecutionException, join() throws CompletionException.
  • Threads: the non-Async variants run on whichever thread completes the previous stage (or the caller, if already complete). supplyAsync without an executor uses ForkJoinPool.commonPool(), sized to cores minus one and shared JVM-wide: never do blocking I/O there. Always pass your own executor.
  • Timeouts: orTimeout(d) and completeOnTimeout(value, d) (Java 9+). Cancelling a CompletableFuture does not interrupt the running task.

A virtual thread runs on a carrier thread. When it blocks on I/O, the JVM parks its stack on the heap and frees the carrier.

Blocking inside synchronized holds the carrier. Use ReentrantLock; JDK 24 (JEP 491) fixes it.

They help I/O-bound thread-per-request code only.

Show Java: 10,000 virtual threads
import java.time.Duration;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.stream.IntStream;

class VirtualThreads {
    public static void main(String[] args) {
        long start = System.nanoTime();
        try (ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor()) {   // one cheap thread per task
            IntStream.range(0, 10_000).forEach(i -> ex.submit(() -> {
                Thread.sleep(Duration.ofSeconds(1));    // blocking call: unmounts, frees the carrier thread
                return i;
            }));
        }                                                // close() waits for all tasks
        System.out.printf("10000 blocking tasks in %d ms%n", (System.nanoTime() - start) / 1_000_000);
    }
}
Go deeper: how virtual threads work, pinning and ThreadLocal

A virtual thread (JEP 444) is a Thread scheduled by the JVM, not the OS. It runs mounted on a carrier platform thread from a ForkJoinPool (parallelism = cores). When it blocks on I/O, a lock in java.util.concurrent, sleep or a queue, the JVM copies its stack to the heap and unmounts it, freeing the carrier. A million virtual threads cost a few hundred MB of heap; a million platform threads are impossible. The point is throughput for I/O-bound thread-per-request code without reactive rewrites.

This printed 10000 blocking tasks in 1064 ms. With a 200-thread pool the same work takes about 50 seconds.

  • Pinning: on Java 21–23, a virtual thread that blocks inside a synchronized block or method cannot unmount, so it holds its carrier. Enough of those and the whole scheduler stalls. Fixes on 21: replace synchronized around blocking calls with ReentrantLock; diagnose with -Djdk.tracePinnedThreads=full or the JFR event jdk.VirtualThreadPinned. JDK 24 (JEP 491) lets virtual threads unmount inside synchronized and removed the trace property; native frames (JNI) still pin.
  • Do not pool virtual threads; create one per task. To limit concurrency against a downstream (DB, vendor API), use a Semaphore, not a small pool.
  • They do not make CPU-bound work faster. They do not remove the DB connection limit: 10,000 virtual threads still share 20 Hikari connections.
  • ThreadLocal works but each of a million threads gets its own copy; avoid caching heavy objects in ThreadLocals. Scoped values are the forward-looking replacement.
  • In Spring Boot 3.2+, spring.threads.virtual.enabled=true runs Tomcat request handling, @Async and scheduling on virtual threads.

08Company questions, solved

Rubrik: bounded blocking queue, then a thread pool

Task
A blocking queue with a capacity, then worker threads that run tasks from it.
Insight
One lock, two conditions: producers wait on notFull, consumers on notEmpty. Shut down with one poison pill per worker.

Show Java solution
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.List;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

final class BoundedBlockingQueue<T> {
    private final Deque<T> items = new ArrayDeque<>();
    private final int capacity;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    BoundedBlockingQueue(int capacity) { this.capacity = capacity; }

    void put(T item) throws InterruptedException {
        lock.lock();
        try {
            while (items.size() == capacity) {      // while, not if: spurious wake-ups and competing producers
                notFull.await();
            }
            items.addLast(item);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    T take() throws InterruptedException {
        lock.lock();
        try {
            while (items.isEmpty()) {
                notEmpty.await();
            }
            T item = items.removeFirst();
            notFull.signal();
            return item;
        } finally {
            lock.unlock();
        }
    }
}

final class SimpleThreadPool {
    private static final Runnable POISON = () -> { };
    private final BoundedBlockingQueue<Runnable> queue;
    private final List<Thread> workers = new ArrayList<>();
    private volatile boolean shutdown;

    SimpleThreadPool(int threads, int queueCapacity) {
        queue = new BoundedBlockingQueue<>(queueCapacity);
        for (int i = 0; i < threads; i++) {
            Thread t = new Thread(this::workLoop, "worker-" + i);
            workers.add(t);
            t.start();
        }
    }

    void submit(Runnable task) throws InterruptedException {
        if (shutdown) {
            throw new IllegalStateException("pool is shut down");
        }
        queue.put(task);                             // blocks when full: natural backpressure
    }

    private void workLoop() {
        try {
            while (true) {
                Runnable task = queue.take();
                if (task == POISON) {
                    return;
                }
                try {
                    task.run();
                } catch (RuntimeException e) {       // one bad task must not kill the worker
                    System.err.println("task failed: " + e);
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    void shutdownAndAwait() throws InterruptedException {
        shutdown = true;
        for (int i = 0; i < workers.size(); i++) {
            queue.put(POISON);                       // one pill per worker, queued after real tasks
        }
        for (Thread t : workers) {
            t.join();
        }
    }
}
Viva follow-ups

One lock, two conditions. Producers wait on notFull, consumers on notEmpty; each operation signals the other side. Then workers loop on take(). Shutdown with a "poison pill" per worker so queued tasks finish first; catch exceptions per task so one failure does not kill a worker.

Viva follow-ups: why while not if around await (spurious wake-ups and another consumer taking the item first); why signal not signalAll (each put frees exactly one slot, and conditions separate producers from consumers); how to add submit returning a Future (wrap in FutureTask); how to reject instead of block (offer with timeout).

class OddEvenPrinter {
    private final int max;
    private int next = 1;                             // guarded by this

    OddEvenPrinter(int max) { this.max = max; }

    void print(boolean odd) {
        synchronized (this) {
            while (true) {
                while (next <= max && (next % 2 == 1) != odd) {
                    try {
                        wait();                       // not my turn: release the monitor and sleep
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                if (next > max) {
                    notifyAll();                      // let the other thread see we are done
                    return;
                }
                System.out.println(Thread.currentThread().getName() + ": " + next);
                next++;
                notifyAll();
            }
        }
    }

    public static void main(String[] args) throws InterruptedException {
        OddEvenPrinter p = new OddEvenPrinter(10);
        Thread odd = new Thread(() -> p.print(true), "odd");
        Thread even = new Thread(() -> p.print(false), "even");
        even.start();                                 // start order does not matter
        odd.start();
        odd.join();
        even.join();
    }
}
Alternative

A shared counter guarded by one monitor. Each thread waits while it is not its turn, prints, increments and notifies. Exit condition is checked inside the lock so neither thread waits forever after the last number. Alternative: two semaphores handing a baton back and forth (the FooBar pattern below). Mention both; the semaphore version generalises to N threads in round robin with N semaphores.

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Semaphore;
import java.util.concurrent.atomic.AtomicInteger;

class AtMostTwo {
    private final Semaphore permits = new Semaphore(2, true);   // fair: FIFO among waiters
    private final AtomicInteger inside = new AtomicInteger();
    private final AtomicInteger peak = new AtomicInteger();

    void callVendor(int id) throws InterruptedException {
        permits.acquire();
        try {
            int now = inside.incrementAndGet();
            peak.accumulateAndGet(now, Math::max);
            Thread.sleep(20);                                    // the guarded work
            inside.decrementAndGet();
        } finally {
            permits.release();                                   // release even if the work throws
        }
    }

    public static void main(String[] args) throws Exception {
        AtMostTwo gate = new AtMostTwo();
        try (ExecutorService ex = Executors.newFixedThreadPool(10)) {
            for (int i = 0; i < 50; i++) {
                final int id = i;
                ex.submit(() -> { gate.callVendor(id); return null; });
            }
        }
        System.out.println("peak concurrency = " + gate.peak.get());   // 2
        if (gate.peak.get() != 2) throw new AssertionError();
    }
}
Where this shows up in production

Release in finally, or a thrown exception leaks a permit and the gate slowly closes. A fair semaphore avoids starvation. This is exactly how you cap calls to a rate-limited vendor (e-sign, SMS, KYC) from a pool of virtual threads.

Google L5: your own CompletableFuture

Task
Complete once, blocking get, callbacks, error propagation, thenCompose.
Insight
Callbacks registered before completion run on completion; after, they run immediately. Run them outside the lock.
Cost
O(callbacks) on completion
Show Java solution
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutionException;
import java.util.concurrent.Executor;
import java.util.function.Function;
import java.util.function.Supplier;

final class MiniFuture<T> {
    private T value;
    private Throwable error;
    private boolean done;
    private final List<Runnable> callbacks = new ArrayList<>();

    static <T> MiniFuture<T> supplyAsync(Supplier<T> task, Executor executor) {
        MiniFuture<T> f = new MiniFuture<>();
        executor.execute(() -> {
            try {
                f.complete(task.get());
            } catch (Throwable t) {
                f.completeExceptionally(t);
            }
        });
        return f;
    }

    boolean complete(T v) { return finish(v, null); }

    boolean completeExceptionally(Throwable t) { return finish(null, t); }

    private boolean finish(T v, Throwable t) {
        List<Runnable> toRun;
        synchronized (this) {
            if (done) {
                return false;                       // first completion wins
            }
            value = v;
            error = t;
            done = true;
            notifyAll();                            // wake threads blocked in get()
            toRun = new ArrayList<>(callbacks);
            callbacks.clear();
        }
        toRun.forEach(Runnable::run);               // run callbacks outside the lock
        return true;
    }

    synchronized T get() throws InterruptedException, ExecutionException {
        while (!done) {
            wait();                                 // loop guards against spurious wake-ups
        }
        if (error != null) {
            throw new ExecutionException(error);
        }
        return value;
    }

    private void onComplete(Runnable r) {
        synchronized (this) {
            if (!done) {
                callbacks.add(r);
                return;
            }
        }
        r.run();                                    // already complete: run now, on the caller's thread
    }

    <U> MiniFuture<U> thenApply(Function<? super T, ? extends U> fn) {
        MiniFuture<U> next = new MiniFuture<>();
        onComplete(() -> {
            if (error != null) {
                next.completeExceptionally(error); // propagate failure down the chain
                return;
            }
            try {
                next.complete(fn.apply(value));
            } catch (Throwable t) {
                next.completeExceptionally(t);
            }
        });
        return next;
    }

    <U> MiniFuture<U> thenCompose(Function<? super T, MiniFuture<U>> fn) {
        MiniFuture<U> next = new MiniFuture<>();
        onComplete(() -> {
            if (error != null) {
                next.completeExceptionally(error);
                return;
            }
            try {
                MiniFuture<U> inner = fn.apply(value);
                inner.onComplete(() -> {
                    if (inner.error != null) {
                        next.completeExceptionally(inner.error);
                    } else {
                        next.complete(inner.value);
                    }
                });
            } catch (Throwable t) {
                next.completeExceptionally(t);
            }
        });
        return next;
    }

    MiniFuture<T> exceptionally(Function<Throwable, ? extends T> fn) {
        MiniFuture<T> next = new MiniFuture<>();
        onComplete(() -> {
            if (error == null) {
                next.complete(value);
            } else {
                next.complete(fn.apply(error));
            }
        });
        return next;
    }
}
What was tested and extensions

The interviewer wants: a completion that happens once, blocking get with wait/notifyAll, callbacks registered before completion run on completion, callbacks registered after completion run immediately, errors propagate down the chain, and thenCompose flattens. Run callbacks outside the lock to avoid deadlocks with user code.

Tested: chain of thenApply and thenCompose gives 42, a thrown exception surfaces from get as ExecutionException, exceptionally recovers, and the second complete returns false. Extensions to discuss: thenApplyAsync(fn, executor) (submit the callback instead of running it inline), allOf with an AtomicInteger countdown, timeouts with a ScheduledExecutorService, and a lock-free version using an AtomicReference to a result or a stack of callbacks (what the JDK does).

import java.util.concurrent.Semaphore;

class FooBar {
    private final int n;
    private final Semaphore fooTurn = new Semaphore(1);   // foo goes first
    private final Semaphore barTurn = new Semaphore(0);

    public FooBar(int n) {
        this.n = n;
    }

    public void foo(Runnable printFoo) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            fooTurn.acquire();
            printFoo.run();
            barTurn.release();                             // hand the baton to bar
        }
    }

    public void bar(Runnable printBar) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            barTurn.acquire();
            printBar.run();
            fooTurn.release();
        }
    }
}
Problem statement and notes

leetcode.com/problems/print-foobar-alternately. Two threads call foo and bar; output must be "foobar" n times. Insight: a baton passed between two semaphores, one starting with a permit.

Each thread blocks at most once per iteration; no busy-waiting. Edge case: whichever thread starts first, the permits force foo first.

import java.util.concurrent.Semaphore;
import java.util.function.IntConsumer;

class ZeroEvenOdd {
    private final int n;
    private final Semaphore zeroTurn = new Semaphore(1);
    private final Semaphore oddTurn = new Semaphore(0);
    private final Semaphore evenTurn = new Semaphore(0);

    public ZeroEvenOdd(int n) {
        this.n = n;
    }

    public void zero(IntConsumer printNumber) throws InterruptedException {
        for (int i = 1; i <= n; i++) {
            zeroTurn.acquire();
            printNumber.accept(0);
            if (i % 2 == 1) {
                oddTurn.release();                     // zero decides who prints next
            } else {
                evenTurn.release();
            }
        }
    }

    public void even(IntConsumer printNumber) throws InterruptedException {
        for (int i = 2; i <= n; i += 2) {
            evenTurn.acquire();
            printNumber.accept(i);
            zeroTurn.release();
        }
    }

    public void odd(IntConsumer printNumber) throws InterruptedException {
        for (int i = 1; i <= n; i += 2) {
            oddTurn.acquire();
            printNumber.accept(i);
            zeroTurn.release();
        }
    }
}
Problem statement and notes

leetcode.com/problems/print-zero-even-odd. Three threads print "0102030405..." up to n. Insight: zero is the scheduler; after each 0 it releases odd or even based on the next number, and those threads hand control back to zero.

Edge case: n = 1 means the even thread's loop never runs, which is correct since it never receives a permit.

    }

        }

import java.util.concurrent.locks.ReentrantLock;

class DiningPhilosophers {
    private final ReentrantLock[] forks = new ReentrantLock[5];

    public DiningPhilosophers() {
        for (int i = 0; i < 5; i++) {
            forks[i] = new ReentrantLock();
        }
    }

    public void wantsToEat(int philosopher, Runnable pickLeftFork, Runnable pickRightFork, Runnable eat,
                           Runnable putLeftFork, Runnable putRightFork) throws InterruptedException {
        int left = philosopher;
        int right = (philosopher + 1) % 5;
        ReentrantLock first = forks[Math.min(left, right)];  // everyone grabs the lower-numbered fork first,
        ReentrantLock second = forks[Math.max(left, right)]; // so a wait-for cycle is impossible
        first.lock();
        second.lock();
        try {
            pickLeftFork.run();
            pickRightFork.run();
            eat.run();
            putLeftFork.run();
            putRightFork.run();
        } finally {
            second.unlock();
            first.unlock();
        }
    }
}
Problem statement and notes

leetcode.com/problems/the-dining-philosophers. Five philosophers, five forks; each needs both neighbouring forks to eat. Avoid deadlock. Insight: deadlock needs a cycle in the wait-for graph; acquiring forks in a global order (lower index first) makes a cycle impossible. Alternatives: a Semaphore(4) so at most four try at once, or tryLock and back off.

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

class BoundedBlockingQueue {
    private final Deque<Integer> items = new ArrayDeque<>();
    private final int capacity;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBlockingQueue(int capacity) {
        this.capacity = capacity;
    }

    public void enqueue(int element) throws InterruptedException {
        lock.lock();
        try {
            while (items.size() == capacity) {
                notFull.await();
            }
            items.addLast(element);
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public int dequeue() throws InterruptedException {
        lock.lock();
        try {
            while (items.isEmpty()) {
                notEmpty.await();
            }
            int x = items.removeFirst();
            notFull.signal();
            return x;
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return items.size();
        } finally {
            lock.unlock();
        }
    }
}

11Interview questions with crisp answers

What is a race condition versus a data race?

A data race is two threads accessing the same variable without happens-before, at least one writing: the JMM gives no guarantee about the value read. A race condition is a correctness bug from timing, such as check-then-act, and can happen even with every access synchronised individually (ConcurrentHashMap get-then-put).

Can volatile replace synchronized?

Only when there is a single writer or each write does not depend on the current value, and the variable is not part of an invariant with other variables. A stop flag, yes; a counter or a balance, no.

Why does double-checked locking need volatile?

Construction and publication can be reordered, so another thread may see a non-null reference to an object whose fields are still defaults. The volatile write/read pair creates the happens-before edge that forbids it.

synchronized or ReentrantLock?

synchronized by default: simpler, cannot forget to unlock, and on JDK 24+ friendly to virtual threads. ReentrantLock when you need tryLock with timeout, interruptible waits, fairness, or several conditions, or on Java 21 when blocking I/O happens under the lock on virtual threads.

How do you detect and fix a deadlock in production?

Symptoms: throughput drops to zero for some endpoints, request threads pile up, CPU is idle. Take thread dumps (jstack, jcmd Thread.print, actuator threaddump); the JVM reports "Found one Java-level deadlock" for monitor and ReentrantLock cycles. Fix with a global lock order, tryLock with timeout, or by not holding a lock while calling out. For DB deadlocks, order row updates consistently (for example by primary key) and retry on the deadlock error.

What is the difference between wait/sleep, and notify/notifyAll?

wait releases the monitor and must be called holding it; sleep keeps every lock it holds. notify wakes one arbitrary waiter, which is only safe when all waiters wait for the same condition; otherwise use notifyAll or separate Conditions.

How do you size a thread pool?

cores × (1 + wait/compute) for blocking work, about cores for CPU-bound work, then cap it by the downstream (DB pool size, vendor rate limit) and verify with a load test. Always bound the queue and pick a rejection policy.

thenApply versus thenCompose?

thenApply maps a value with a plain function. thenCompose chains a function that itself returns a CompletableFuture and flattens it, like flatMap. Use thenCompose for dependent async calls (fetch doc, then fetch its owner).

Why should you not use the common pool for I/O in CompletableFuture?

It has cores − 1 threads shared by the whole JVM, including parallel streams. Blocking I/O starves every other user. Pass a dedicated executor, or on Java 21 a virtual-thread-per-task executor.

What is pinning in virtual threads, and is it still a problem?

A virtual thread that cannot unmount from its carrier while blocked: on Java 21–23 inside synchronized, and on all versions inside native frames. It reduces the scheduler's capacity and can deadlock it. JDK 24 (JEP 491) fixed the synchronized case. On Java 21 LTS, use ReentrantLock around blocking calls and check JFR jdk.VirtualThreadPinned events.

AtomicLong or LongAdder?

LongAdder for high-contention counters read rarely (metrics); AtomicLong when each update needs the exact current value or you need compareAndSet.

What does ConcurrentHashMap give you that Collections.synchronizedMap does not?

Per-bin locking with lock-free reads, atomic compute/merge/putIfAbsent, and weakly consistent iterators that do not throw. synchronizedMap has one lock for everything and requires manual locking while iterating.

How would you make a method run at most once across threads?

An AtomicBoolean with compareAndSet(false, true) guarding the body, or the holder idiom for lazy initialisation. Across instances of a service, a database unique constraint or a distributed lock, because JVM-level tools stop at the process boundary.

12Cheat sheet

Cheat sheet
  • Atomicity, visibility, ordering. Happens-before: unlock→lock, volatile write→read, start, join.
  • volatile: flags and publication. count++ needs a lock or AtomicInteger/LongAdder.
  • DCL needs volatile; holder idiom is simpler; enum survives reflection.
  • Deadlock: 4 conditions; fix with global lock order or tryLock + back-off; find with jcmd Thread.print.
  • wait/await always in while; unlock/release in finally.
  • Pool: bounded queue, named threads, rejection policy. threads = cores × (1 + wait/compute).
  • CF: thenCompose for async chains, own executor, orTimeout.
  • Virtual threads: I/O only, never pooled, Semaphore for limits, avoid synchronized pinning on 21.
