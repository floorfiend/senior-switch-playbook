pgvector, hands-on

You will store small pieces of contracts in Postgres, together with a list of numbers that captures their meaning. Then you will search them by meaning, fast, and only inside one customer's data. You will do it from Python and from Spring AI.

Time: 3–4 hours Stack: Docker, Postgres 18 + pgvector 0.8.7, Python (psycopg 3), Spring AI 2.0 Asked at: Adobe (pgvector vs Pinecone vs Qdrant)
AdobeRAG rounds generally
In 30 seconds
  • pgvector is a Postgres add-on. It gives you a vector(n) column type and operators that measure how far apart two vectors are.
  • To search, you sort the rows by distance to the question and keep the closest five. In SQL that is ORDER BY embedding <=> :q LIMIT 5.
  • An HNSW index makes this fast, but the answer is approximate. A WHERE filter can then quietly return fewer rows than you asked for.
  • Text pieces, customers (tenants) and access rules (ACLs) live in one database. So one transaction can change all of them together.
Picture it

You are looking for a house in a new city. You take the highway to the right area, then a main road, then the lane. You never check every house, so you are fast. Once in a while you miss a house that was slightly closer. That is how HNSW works.

Words you'll see
Embedding
A list of numbers (for example 1,024 of them) that captures what a piece of text means. Texts with similar meaning get similar numbers, like two shops on the same street having close addresses.
Vector
Just a fixed-length list of numbers. An embedding is stored as a vector. Think of it as a point on a map with many directions instead of two.
Distance
How far apart two vectors are. Small distance means similar meaning. Every pgvector operator follows the rule "smaller is closer".
Cosine distance
Measures whether two vectors point in the same direction, ignoring their length. 0 means same direction (same meaning). It is the usual choice for text.
ANN (approximate nearest neighbour)
A search that checks only part of the data to be fast. It may miss a few of the true closest matches.
HNSW
Hierarchical Navigable Small World. An index shaped like a road map with layers: highways on top, lanes at the bottom. The usual index choice.
IVFFlat
A different index. It groups vectors into clusters, like shelves in a library. A search only reads the nearest few shelves.
Recall
Out of the truly closest rows, how many the search actually found. Recall@5 = 0.8 means 4 of the right 5 came back.

01Key ideas

A vector is just a column

An embedding is, for example, 1,024 numbers from the voyage-4 model. You store it in a vector(1024) column, next to the text.

Distance works like a Comparator

Sort the rows by how far they are from the question, then keep the closest five. In SQL: ORDER BY embedding <=> :query LIMIT 5.

No index means exact

Postgres measures the distance to every row. It never misses a match. This is fine up to tens of thousands of rows.

An index means approximate

ANN search is much faster. But it may return different rows than an exact search. Most pgvector bugs start here.

The extra columns matter most

Columns for customer, document, page and model change "similar text" into "text this user may see, with a page number to quote".

You already run Postgres in production. pgvector adds three things: a vector column type, distance operators, and two approximate indexes. So the text pieces, their embeddings, the customer ids and the full-text index can all live in one table. One transaction can change them together. This lesson runs it in Docker and designs the table. Then it loads PDFs from Python. Finally it does the same thing with Spring AI's PgVectorStore.

An embedding is a fixed-length list of decimal numbers. For example, voyage-4 gives 1,024 numbers. pgvector adds a type, vector(n), to store it. It also adds operators that measure the distance between two vectors. Think of it as adding a new Comparator to Postgres. ORDER BY embedding <=> :query LIMIT 5 means "sort rows by how far their embedding is from the question's embedding, and give me the closest five".

Without an index, this is an exact scan. Postgres measures the distance for every row, so it never misses a match (perfect recall). That is fine up to tens of thousands of rows, and it can use several CPU workers in parallel. With an index, it becomes approximate nearest-neighbour (ANN) search. It is much faster. But the README warns that "you will see different results for queries after adding an approximate index". That one sentence causes most pgvector bugs in production.

02Distance operators

OperatorMeaningIndex opclass (which index type serves it)Use when
<->L2 (Euclidean) distance: the straight-line distance, like a rulervector_l2_opsThe model's docs say L2, or the embeddings come from images
<#>Negative inner productvector_ip_opsVectors are normalised (scaled to length 1). It ranks the same as cosine, and is cheaper to compute.
<=>Cosine distance (1 − cosine similarity): do the two point the same way?vector_cosine_opsThe default for text. Safe when you are not sure the vectors are normalised.
<+>L1 (Manhattan) distance: walking along city blocksvector_l1_opsRare in RAG (retrieval-augmented generation)
<~>, <%>Hamming, Jaccard: count differing or shared bitsbit_hamming_ops, bit_jaccard_opsBinary vectors, or binary quantisation (squeezing each number into one bit)
  • Every operator follows "smaller is closer". That is why <#> returns the negative inner product.
  • An index only works with one kind of distance (its opclass). A cosine HNSW index cannot help ORDER BY <->.
  • Voyage embeddings have length 1. So cosine, inner product and L2 all give the same order.

03How HNSW finds neighbours

HNSW is a graph with layers. The top layer has a few points. The bottom layer has every point. The search starts at the top. At each step it moves to whichever neighbour is closer to the question. When it cannot get closer, it drops one layer down.

Query "Can the customer terminate early?" (LIMIT 2, ef_search = 3)

HNSW (graph) usual pick

  • Better balance of speed and accuracy
  • No training step, so you can build it on an empty table
  • Slower to build, and uses more memory

m = links per point (16) · ef_construction = shortlist size while building (64) · hnsw.ef_search = shortlist size per search (40)

IVFFlat (clusters)

  • Faster to build, uses less memory
  • Finds fewer of the true matches at the same speed
  • Build it after the data is loaded, because it learns its groups (k-means centroids) from the data

lists = rows/1000 (up to 1M rows), sqrt(rows) above that · ivfflat.probes is 1 by default; start at sqrt(lists)

Default choice

Use HNSW with cosine for contracts. An index can hold at most 2,000 dimensions (numbers per vector) for vector, and 4,000 for halfvec.

Go deeper: HNSW and IVFFlat in more detail
Default choice

Use HNSW with cosine for a collection of contracts. Use IVFFlat only when build time or memory is the main problem. An example is rebuilding the index for tens of millions of vectors every night. Both index types allow at most 2,000 dimensions for vector. halfvec (half-size numbers) allows up to 4,000. Binary quantisation allows up to 64,000.

HNSW (graph). Think of it as a "skip list of neighbours" with many layers. The search starts at a thin top layer. It keeps moving to the neighbour closest to the question, and drops one layer at a time. It is like finding a house by motorway, then main road, then lane. It balances speed and accuracy better. It builds more slowly and uses more memory. It has no training step, so you can create it on an empty table.

IVFFlat (clusters). A method called k-means splits the vectors into groups. The number of groups is lists. A search only reads the nearest few groups, and that number is probes. It is like a library: walk to the right shelves, then read every book on them. It builds faster and uses less memory. At the same speed, it finds fewer of the true matches. You must build it after the data exists, because the group centres (centroids) are learned from the data.

04The filtering trap (the senior question)

40rows the index hands back (ef_search)
10%of all rows belong to customer acme
~4rows left after WHERE tenant_id
10rows you asked for with LIMIT

With an ANN index, the WHERE filter runs after the index picks its rows. You asked for 10 rows and quietly got 4. No error tells you. Here are the fixes, in the order to try them.

  1. Iterative scanTell the index to keep searching until enough rows pass the filter. It gives up after 20,000 rows (hnsw.max_scan_tuples). Needs version 0.8.0 or later: SET hnsw.iterative_scan = strict_order or relaxed_order.
  2. B-tree on filterAdd a normal index on the filter column. For a small customer, Postgres may then just check all their rows. That is exact and still fast.
  3. Partial indexWhen a column has only a few values, build a separate small index for each value. For example, one only for termination clauses: ... WHERE (clause_type = 'termination').
  4. PartitionSplit the table by customer, or use separate tables. With one shared ANN index, one customer's data can hurt another customer's accuracy and speed.
Go deeper: the README's numbers, and why use Postgres at all

With an approximate index, Postgres applies the WHERE clause after the index returns its rows. The README gives the numbers. Say tenant_id = 'acme' matches 10% of rows and ef_search is 40. The index hands back about 40 rows. Only around 4 of them pass the filter. You asked for LIMIT 10 and quietly got 4.

Why Postgres instead of a separate vector database. For a Spring Boot team, the reason is ease of running it. The text pieces can join to the documents, tenants and access-rule (ACL) tables you already have. Inserts and deletes share a transaction with the rest of your data. So when you delete a contract, its pieces disappear in the same commit. Replication (WAL), point-in-time restore (PITR), backups and Flyway migrations already work. You give up a managed ANN service that spreads data over many machines for you. You only need that at a size most legal-tech customers never reach.

Step 2: design the table

  • Use real columns for anything you filter on. A jsonb column is fine for the rest.
  • embedding_model records which model made the vector. You can then re-embed with a new model side by side. Never compare vectors from two different models.
  • UNIQUE (document_id, chunk_index), plus "delete old rows, then insert" in one transaction, makes re-loading a document safe.
  • content_tsv is for hybrid search (meaning plus keywords) in the next lesson.

CREATE TABLE contract_chunks (
    id              bigserial PRIMARY KEY,
    tenant_id       text        NOT NULL,          -- from the JWT, never the request body
    document_id     uuid        NOT NULL,
    chunk_index     int         NOT NULL,
    clause_type     text,                          -- termination, indemnity, ...
    page            int,                           -- for citations
    content         text        NOT NULL,
    content_tsv     tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    embedding       vector(3)   NOT NULL,          -- vector(1024) for voyage-4; 3 here so you can read it
    embedding_model text        NOT NULL DEFAULT 'toy-3d',
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (document_id, chunk_index)              -- makes re-ingestion idempotent

Step 4: make sure the index is used

The planner is the part of Postgres that decides how to run a query. It uses a vector index only for ORDER BY <distance operator> ASC together with LIMIT. If you sort by a calculation instead, it skips the index.

EXPLAIN (COSTS OFF) SELECT id FROM contract_chunks ORDER BY embedding <=> '[1,0,0]' LIMIT 5;
--  Limit
--    ->  Index Scan using contract_chunks_embedding_idx on contract_chunks
--          Order By: (embedding <=> '[1,0,0]'::vector)

EXPLAIN (COSTS OFF) SELECT id FROM contract_chunks ORDER BY 1 - (embedding <=> '[1,0,0]') DESC LIMIT 5;
--  Limit
--    ->  Sort
--          Sort Key: (('1'::double precision - (embedding <=> '[1,0,0]'::vector))) DESC
--          ->  Seq Scan on contract_chunks

Show similarity in the SELECT list if you want it on screen. But sort by the plain distance.

Go deeper: how this was checked

The planner only uses a vector index when the query has ORDER BY <distance operator> ASC and a LIMIT. Sorting by a calculation, such as similarity, turns the index off. This was checked on the container above. It used enable_seqscan = off, so even a 5-row table shows the planner's choice. Show similarity in the SELECT list, and sort by the plain distance. In production, use EXPLAIN (ANALYZE, BUFFERS).

Step 5: tune recall per query, and filter safely

  • Use SET LOCAL, not SET. Behind a connection pool like HikariCP, a plain SET stays on the connection. The next request that borrows it gets your setting too.
  • relaxed_order can return rows slightly out of distance order.
Show SQL: ef_search, iterative scan, IVFFlat, partitions
BEGIN;
SET LOCAL hnsw.ef_search = 100;              -- more candidates: better recall, slower (default 40)
SET LOCAL hnsw.iterative_scan = relaxed_order; -- keep scanning until LIMIT rows pass the WHERE
SELECT id, page FROM contract_chunks
WHERE tenant_id = 'acme' AND clause_type = 'termination'
ORDER BY embedding <=> '[1,0,0]' LIMIT 10;
COMMIT;

-- IVFFlat alternative (build after loading data):
CREATE INDEX ON contract_chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
SET ivfflat.probes = 10;                     -- default 1; start near sqrt(lists)

-- Hard tenant isolation: one partition (and one ANN index) per large tenant
CREATE TABLE chunks_p (tenant_id text NOT NULL, embedding vector(1024), content text)
    PARTITION BY LIST (tenant_id);
CREATE TABLE chunks_acme PARTITION OF chunks_p FOR VALUES IN ('acme');
Go deeper: SET LOCAL and strict ordering

SET LOCAL keeps the setting inside the current transaction only. This matters behind a connection pool such as HikariCP. A plain SET stays on the connection and reaches the next code that borrows it. With relaxed_order, results can be slightly out of distance order. If you need strict order, wrap the query in a MATERIALIZED CTE and sort again. On Postgres 17 and later, use ORDER BY distance + 0 for that.

Show Python: ingest_pdfs.py
"""Ingest contract PDFs into pgvector: python ingest_pdfs.py acme contracts/*.pdf"""
import sys
import uuid
from pathlib import Path

import psycopg
import voyageai
from pgvector.psycopg import register_vector
from pypdf import PdfReader

DSN = "postgresql://postgres:postgres@localhost:5432/postgres"
MODEL, DIM = "voyage-4", 1024
CHUNK_CHARS, OVERLAP = 2000, 200  # ~500 tokens, 10% overlap

SCHEMA = f"""
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE IF NOT EXISTS contract_chunks (
    id              bigserial PRIMARY KEY,
    tenant_id       text        NOT NULL,
    document_id     uuid        NOT NULL,
    chunk_index     int         NOT NULL,
    page            int         NOT NULL,
    source          text        NOT NULL,
    content         text        NOT NULL,
    content_tsv     tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    embedding       vector({DIM}) NOT NULL,
    embedding_model text        NOT NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (document_id, chunk_index)
);
CREATE INDEX IF NOT EXISTS contract_chunks_hnsw ON contract_chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX IF NOT EXISTS contract_chunks_tenant ON contract_chunks (tenant_id);
CREATE INDEX IF NOT EXISTS contract_chunks_tsv ON contract_chunks USING gin (content_tsv);
"""


def chunk_page(text: str) -> list[str]:
    """Split one page into overlapping windows, preferring paragraph breaks."""
    text = " ".join(text.split("\n\n")).strip()
    chunks, start = [], 0
    while start < len(text):
        end = min(start + CHUNK_CHARS, len(text))
        if end < len(text):  # back off to the last sentence end inside the window
            cut = text.rfind(". ", start + CHUNK_CHARS // 2, end)
            end = cut + 1 if cut != -1 else end
        chunks.append(text[start:end].strip())
        if end == len(text):
            break
        start = end - OVERLAP
    return [c for c in chunks if c]


def load_pdf(path: Path) -> list[tuple[int, str]]:
    """Return (page_number, chunk_text) pairs; page numbers are 1-based for citations."""
    out = []
    for page_no, page in enumerate(PdfReader(path).pages, start=1):
        for chunk in chunk_page(page.extract_text() or ""):
            out.append((page_no, chunk))
    return out


def ingest(conn: psycopg.Connection, vo: voyageai.Client, tenant_id: str, path: Path) -> int:
    chunks = load_pdf(path)
    if not chunks:
        print(f"skip {path}: no extractable text (scanned PDF? run OCR first)")
        return 0
    # uuid5 of tenant + file name: re-ingesting the same file replaces its rows instead of duplicating them
    doc_id = uuid.uuid5(uuid.NAMESPACE_URL, f"{tenant_id}/{path.name}")
    vectors = []
    for i in range(0, len(chunks), 128):  # batch the embedding calls
        batch = [text for _, text in chunks[i:i + 128]]
        vectors += vo.embed(batch, model=MODEL, input_type="document").embeddings
    with conn.transaction():
        conn.execute("DELETE FROM contract_chunks WHERE document_id = %s", (doc_id,))
        with conn.cursor() as cur:
            cur.executemany(
                "INSERT INTO contract_chunks (tenant_id, document_id, chunk_index, page, source, content, "
                "embedding, embedding_model) VALUES (%s, %s, %s, %s, %s, %s, %s, %s)",
                [(tenant_id, doc_id, i, page, path.name, text, vec, MODEL)
                 for i, ((page, text), vec) in enumerate(zip(chunks, vectors))],
            )
    return len(chunks)


def main() -> None:
    tenant_id, files = sys.argv[1], [Path(p) for p in sys.argv[2:]]
    vo = voyageai.Client()  # reads VOYAGE_API_KEY
    with psycopg.connect(DSN, autocommit=True) as conn:
        conn.execute(SCHEMA)
        register_vector(conn)  # after CREATE EXTENSION, so the vector type exists
        for f in files:
            print(f"{f.name}: {ingest(conn, vo, tenant_id, f)} chunks")


if __name__ == "__main__":
    main()

import numpy as np
import psycopg
import voyageai
from pgvector.psycopg import register_vector

DSN = "postgresql://postgres:postgres@localhost:5432/postgres"


def search(conn, vo, tenant_id: str, question: str, k: int = 5):
    q = np.array(vo.embed([question], model="voyage-4", input_type="query").embeddings[0])
    return conn.execute(
        """
        SELECT source, page, left(content, 120), embedding <=> %s AS distance
        FROM contract_chunks
        WHERE tenant_id = %s
        ORDER BY embedding <=> %s
        LIMIT %s
        """,
        (q, tenant_id, q, k),
    ).fetchall()


if __name__ == "__main__":
    with psycopg.connect(DSN) as conn:
        register_vector(conn)
        for row in search(conn, voyageai.Client(), "acme", "Can the customer terminate early?"):
            print(row)
Go deeper: what the script does and how it was tested

What it does. It writes one row per window of about 500 tokens, with 10% overlap. It keeps page numbers for quoting. It asks for embeddings 128 at a time with input_type="document". The document id comes from uuid5, so it is the same every time. That means running the script twice replaces rows instead of duplicating them. I tested the splitting and database steps against the container with a fake embedding model. It produced 3 pieces of 1,979, 1,964 and 1,856 characters, and still 3 rows after two runs. For a big first load, the README recommends COPY ... WITH (FORMAT BINARY). It also says to create indexes after loading. In production, use CREATE INDEX CONCURRENTLY. Give it enough maintenance_work_mem so the whole HNSW graph fits in memory.

On the search side, note input_type="query". You should see tuples like ('msa.pdf', 4, 'Either party may terminate ...', 0.21...), closest first. The distances depend on your documents.

Show Java: ingestion service and tenant-scoped search
@Service
public class ContractIngestionService {

    private final VectorStore vectorStore;

    public ContractIngestionService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    public void ingest(String tenantId, String documentId, Resource pdf) {
        List<Document> pages = new PagePdfDocumentReader(pdf).read();
        List<Document> chunks = TokenTextSplitter.builder().withChunkSize(500).build().apply(pages);
        List<Document> tagged = chunks.stream().map(d -> {
            Map<String, Object> meta = new HashMap<>(d.getMetadata());
            meta.put("tenantId", tenantId);
            meta.put("documentId", documentId);
            return new Document(d.getText(), meta);
        }).toList();
        vectorStore.add(tagged); // embeds via the EmbeddingModel bean, then inserts
    }
}

@RestController
class ContractSearchController {

    private final VectorStore vectorStore;

    ContractSearchController(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    @GetMapping("/contracts/search")
    @PreAuthorize("hasAuthority('SCOPE_contracts:read')")
    List<Document> search(@RequestParam String q, @AuthenticationPrincipal Jwt jwt) {
        FilterExpressionBuilder b = new FilterExpressionBuilder();
        return vectorStore.similaritySearch(SearchRequest.builder()
                .query(q)
                .topK(5)
                .similarityThreshold(0.5)
                .filterExpression(b.eq("tenantId", jwt.getClaimAsString("tenant_id")).build())
                .build());
    }
}

Use FilterExpressionBuilder. Never build the filter as "tenantId == '" + x + "'". A customer name containing a quote mark would break out of the string, like SQL injection. The text form is fine for fixed values: "clause_type in ['termination','indemnity'] && year >= 2024".

Production gotchas of the default store
  • All extra fields live in one json column. So customer filters dig into JSON instead of using a fast B-tree index. At scale, create your own table.
  • dimensions must match the model. A new model means a new column and re-embedding everything.
  • Turn initialize-schema off in production. Create tables with Flyway instead.

06pgvector vs Pinecone vs Qdrant (the Adobe question)

pgvector usual pick

  • Joins and safe transactions (ACID) with your business data
  • One backup and failover setup, plus SQL keyword search
  • Runs on one machine by default. The index uses memory your normal app queries (OLTP) also need.

Up to tens of millions of text pieces, and the team already runs Postgres.

Pinecone

  • Nothing to run yourself. It grows for you.
  • Data leaves your private network (VPC). That raises questions under India's DPDP data law.
  • Costly at large volume. A second store to keep in sync.

Small team, no wish to run servers, huge or very bursty data.

Qdrant

  • Filtering built into the search, and compression (quantisation)
  • Another database cluster to run, plus syncing

Hundreds of millions of vectors, with lots of filtered searches.

Senior framing

"I'd start with pgvector. The hard part of enterprise RAG is permissions and fresh data, and those are joins and transactions. I'd move to a dedicated engine when search gets slow or the index uses too much memory. Slow here means p95 ANN latency: the time 95 out of 100 searches finish within. Too much memory means it starts hurting the normal app queries (OLTP). I'd measure recall@k on a fixed set of test questions (a golden set) before and after."

Common mistakes
  • Sorting by 1 - distance DESC. Postgres then skips the index.
  • The query's operator does not match the index's opclass.
  • A customer filter with an ANN index but no iterative scan. You get fewer rows than LIMIT.
  • A plain SET behind a connection pool.
  • Mixing vectors from two embedding models.
  • Taking the customer id from a request parameter instead of the JWT (the signed login token).

07Interview questions

HNSW or IVFFlat for 5M contract chunks?

HNSW. It balances speed and recall better. It needs no training step, so it stays correct as data grows. The cost is a slower build and more memory. So set maintenance_work_mem high enough for the graph during builds, and build CONCURRENTLY so writes are not blocked. Pick IVFFlat if nightly rebuild time or RAM is the limit. Then use lists ≈ sqrt(5M) ≈ 2,236 and probes ≈ 47.

After adding an HNSW index, a tenant's search returns 3 results instead of 10. Why?

Post-filtering, meaning the filter runs after the search. The index returns about ef_search (40) rows. Then the WHERE tenant_id filter throws most of them away. Fixes: turn on hnsw.iterative_scan. Raise ef_search with SET LOCAL. Add a B-tree on tenant_id, so small customers get an exact scan. Or partition the table by customer.

What do m, ef_construction and ef_search control?

m is the number of neighbours each point links to. It sets how dense the graph is, and how much memory it uses. ef_construction is the shortlist size while building. It sets graph quality and build time. ef_search is the shortlist size per search. It trades recall against speed (latency). It is the only one you can change without rebuilding. The defaults are 16, 64 and 40.

Cosine, inner product or L2?

Use whatever the embedding model was trained for, usually cosine. If vectors are unit-normalised (scaled to length 1, as Voyage's are), all three give the same order. Then inner product (<#>) is the cheapest. The index opclass must match the operator in the query.

Why is my vector query doing a sequential scan?

A sequential scan means reading every row. Common causes: no LIMIT. Sorting by a calculation, like 1 - distance DESC. An operator that does not match the index opclass. Or the table is so small that reading it all really is faster. Check with EXPLAIN (ANALYZE, BUFFERS).

How do you isolate tenants in a shared vector table?

The repository layer adds the customer id from the JWT to every query. It never takes it from request parameters. Add row-level security (Postgres rules that hide other customers' rows) as a second safety layer. For large customers, use list partitions so each has its own ANN index. That also stops one customer's data shape from hurting another's recall. Test it with an automated cross-customer query that must return zero rows.

Your embedding model has 3,072 dimensions. Can pgvector index it?

Not as vector, because the index limit is 2,000 dimensions. You have three options. Index it as halfvec (up to 4,000) with an expression index. Use binary quantisation and then re-rank the top results with full vectors. Or ask the model for fewer dimensions. Matryoshka models such as voyage-4 offer 256 to 2048.

How do you re-embed the corpus with a new model with zero downtime?

Add a new column or table with the new dimension and embedding_model value. Fill it in batches (backfill). Build its index concurrently. Write new documents to both old and new (dual-write). Switch reads behind a feature flag once recall@k on the golden set is equal or better. Then drop the old column. Never compare vectors across models.

Deletes and updates: anything special?

They are ordinary rows under MVCC (Postgres keeps old row versions until cleanup). That is the advantage: deleting a contract removes its pieces in the same transaction. But dead rows (dead tuples) can reduce results, and vacuuming an HNSW index can be slow. After large deletes, the README suggests REINDEX INDEX CONCURRENTLY and then VACUUM.

When would you leave pgvector?

When vector search load or index memory starts slowing the normal transactional work. Or when the data outgrows one machine, and splitting it Citus-style is more work than a dedicated engine. Before that point, you have cheaper options. Send search traffic to read replicas (read-only copies). Use halfvec and binary quantisation to shrink the index.

08Quick check

You add an HNSW index. Now a customer's search with LIMIT 10 returns only 4 rows. What is the most likely cause?

The filter runs after the search. The index hands back about ef_search rows, and only the acme ones survive. Turn on hnsw.iterative_scan, or partition by customer.

Which query can use a vector_cosine_ops HNSW index?

The index needs three things. The plain distance operator that matches its opclass. Ascending order. And a LIMIT.

Which HNSW setting can you change per query without rebuilding the index?

m and ef_construction shape the graph when it is built. ef_search is read at search time. Set it with SET LOCAL.

Why must you build IVFFlat after loading data, but not HNSW?

Its lists are groups learned from the data. An empty table gives useless group centres (centroids). HNSW has no training step.

Cheat sheet
  • Run docker run pgvector/pgvector:pg18-trixie, then CREATE EXTENSION vector.
  • For text embeddings, use cosine <=> with vector_cosine_ops. If vectors have length 1, <#> is the cheapest.
  • The index is used only for ORDER BY distance ASC LIMIT k.
  • Default to HNSW (m 16, ef_construction 64, ef_search 40). Use IVFFlat when build time or RAM is the main limit.
  • Filtered search fixes, in order: iterative scan, then B-tree, then partial index, then partition by customer.
  • Use SET LOCAL behind a connection pool. Take the customer from the JWT.
  • Index limit is 2,000 dimensions (halfvec: 4,000).
  • One model per column. To switch models, add a new column and flip a flag.
  • Stay on pgvector until search load hurts normal app queries. Then look at Qdrant or Pinecone.
