pgvector, hands-on

You already run Postgres in production. pgvector adds a vector column type, distance operators and two approximate indexes, so contract chunks, their embeddings, tenant ids and full-text index can live in one table under one transaction. This lesson runs it in Docker, designs the table, ingests PDFs from Python, and then does the same thing with Spring AI's PgVectorStore.

02Concepts explained from scratch

A vector column is just another column

An embedding is a fixed-length array of floats, for example 1,024 numbers from voyage-4. pgvector adds a type vector(n) that stores it, plus operators that compute the distance between two vectors. Think of it as adding a new Comparator to Postgres: ORDER BY embedding <=> :query LIMIT 5 means "sort rows by how far their embedding is from the query embedding and give me the closest five".

Without an index this is an exact scan: Postgres computes the distance for every row, which gives perfect recall and is fine up to tens of thousands of rows (and can use parallel workers). With an index it becomes approximate nearest-neighbour (ANN) search: much faster, but the README warns that "you will see different results for queries after adding an approximate index". That sentence is the root of most pgvector production bugs.

Distance operators

OperatorMeaningIndex opclassUse when
<->L2 (Euclidean) distancevector_l2_opsModel docs say L2, or image-style embeddings
<#>Negative inner productvector_ip_opsVectors are normalised to length 1: same ranking as cosine, cheaper
<=>Cosine distance (1 − cosine similarity)vector_cosine_opsDefault for text embeddings; safe if you are not sure vectors are normalised
<+>L1 (Manhattan) distancevector_l1_opsRare in RAG
<~>, <%>Hamming, Jaccardbit_hamming_ops, bit_jaccard_opsBinary vectors / binary quantisation

Two traps. <#> returns the negative inner product so that "smaller is closer" holds for every operator (multiply by −1 to display it). And an index is built for one opclass: an HNSW index on vector_cosine_ops is useless for a query that orders by <->. Voyage embeddings are normalised to length 1, so cosine, inner product and L2 all give the same ranking for them.

HNSW vs IVFFlat, intuitively

HNSW (graph)

A multi-layer "skip list of neighbours". Search starts at a sparse top layer, greedily walks towards the query, and drops a layer at a time. Like finding a house by motorway, then main road, then lane.

  • m = links per node (default 16)
  • ef_construction = candidate list while building (default 64)
  • hnsw.ef_search = candidate list while querying (default 40)

Better speed/recall trade-off, slower build, more memory, no training step, so you can create it on an empty table.

IVFFlat (clusters)

k-means splits vectors into lists clusters. A query only scans the probes nearest clusters. Like a library: go to the right shelves, then read every book on them.

  • lists: start at rows/1000 (up to 1M rows), sqrt(rows) above that
  • ivfflat.probes: default 1; start at sqrt(lists)

Faster build, less memory, lower recall at the same speed. Must be built after data exists (centroids are trained from it).

Default choice

Use HNSW with cosine for a contract corpus. Use IVFFlat only when build time or memory dominates, for example re-indexing tens of millions of vectors nightly. Both are limited to 2,000 dimensions for vector; halfvec indexes up to 4,000, and binary quantisation up to 64,000.

The filtering problem (the senior question)

With an approximate index, the WHERE clause is applied after the index returns candidates. The README's own arithmetic: if tenant_id = 'acme' matches 10% of rows and ef_search is 40, the index hands back about 40 candidates and only around 4 survive the filter. You asked for LIMIT 10 and silently got 4. Fixes, in the order to try them:

  1. Iterative index scans (0.8.0+): SET hnsw.iterative_scan = strict_order or relaxed_order. The index keeps scanning until enough rows pass the filter or it hits hnsw.max_scan_tuples (20,000 by default).
  2. A B-tree index on the filter column: for a small tenant the planner may prefer an exact scan of that tenant's rows, which is exact and fast.
  3. Partial indexes for a few distinct values (... WHERE (clause_type = 'termination')).
  4. List partitioning by tenant, or separate tables. The README's multitenancy note: a shared approximate index lets one tenant's vectors affect another tenant's recall and speed.

Why Postgres instead of a vector database

For a Spring Boot team the argument is operational. The chunks join to documents, tenants and ACL tables you already have; inserts and deletes are transactional with the rest of your data (delete a contract and its chunks vanish in the same commit); WAL replication, PITR, backups and Flyway migrations already work. You give up the convenience of a managed, horizontally sharded ANN service, which you need only at a scale most legal-tech tenants never reach.

Step 2: design the table

Metadata is what turns "similar text" into "similar text the user is allowed to see, from the right document, with a page to cite". Use real columns for anything you filter on; a jsonb column is fine for the rest.

CREATE TABLE contract_chunks (
    id              bigserial PRIMARY KEY,
    tenant_id       text        NOT NULL,          -- from the JWT, never the request body
    document_id     uuid        NOT NULL,
    chunk_index     int         NOT NULL,
    clause_type     text,                          -- termination, indemnity, ...
    page            int,                           -- for citations
    content         text        NOT NULL,
    content_tsv     tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    embedding       vector(3)   NOT NULL,          -- vector(1024) for voyage-4; 3 here so you can read it
    embedding_model text        NOT NULL DEFAULT 'toy-3d',
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (document_id, chunk_index)              -- makes re-ingestion idempotent
);

CREATE INDEX ON contract_chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX ON contract_chunks (tenant_id);
CREATE INDEX ON contract_chunks USING gin (content_tsv);

Why each column: embedding_model lets you re-embed with a new model side by side and never compare vectors from two models (their spaces are unrelated). UNIQUE (document_id, chunk_index) plus delete-then-insert in one transaction makes re-ingestion safe. content_tsv is there for hybrid search in the next lesson.

Step 3: query it, and read the output

SELECT id, clause_type, page, round((embedding <=> '[1,0,0]')::numeric, 4) AS cosine_distance
FROM contract_chunks
WHERE tenant_id = 'acme'
ORDER BY embedding <=> '[1,0,0]'
LIMIT 3;

--  id | clause_type | page | cosine_distance
-- ----+-------------+------+-----------------
--   1 | termination |    4 |          0.0061
--   4 | termination |    3 |          0.0369
--   3 | limitation  |    7 |          0.7592

Chunk 5 (globex) is closer to the query than chunk 3 but never appears: the tenant filter did its job. All operators on one row, against [1,0,0]:

SELECT embedding <-> '[1,0,0]' AS l2, embedding <#> '[1,0,0]' AS neg_inner,
       embedding <=> '[1,0,0]' AS cosine_dist, 1 - (embedding <=> '[1,0,0]') AS cosine_sim,
       embedding <+> '[1,0,0]' AS l1
FROM contract_chunks WHERE id = 1;

--  l2     0.1414   neg_inner -0.9000   cosine_dist 0.0061   cosine_sim 0.9939   l1 0.2000

Step 4: make sure the index is used

The planner only uses a vector index when the query has ORDER BY <distance operator> ASC and a LIMIT. Ordering by an expression such as similarity disables it. Verified on the container above (with enable_seqscan = off so a 5-row table still shows the choice):

EXPLAIN (COSTS OFF) SELECT id FROM contract_chunks ORDER BY embedding <=> '[1,0,0]' LIMIT 5;
--  Limit
--    ->  Index Scan using contract_chunks_embedding_idx on contract_chunks
--          Order By: (embedding <=> '[1,0,0]'::vector)

EXPLAIN (COSTS OFF) SELECT id FROM contract_chunks ORDER BY 1 - (embedding <=> '[1,0,0]') DESC LIMIT 5;
--  Limit
--    ->  Sort
--          Sort Key: (('1'::double precision - (embedding <=> '[1,0,0]'::vector))) DESC
--          ->  Seq Scan on contract_chunks

Compute similarity in the select list for display, order by the bare distance. In production use EXPLAIN (ANALYZE, BUFFERS).

Step 5: tune recall per query, and filter safely

BEGIN;
SET LOCAL hnsw.ef_search = 100;              -- more candidates: better recall, slower (default 40)
SET LOCAL hnsw.iterative_scan = relaxed_order; -- keep scanning until LIMIT rows pass the WHERE
SELECT id, page FROM contract_chunks
WHERE tenant_id = 'acme' AND clause_type = 'termination'
ORDER BY embedding <=> '[1,0,0]' LIMIT 10;
COMMIT;

-- IVFFlat alternative (build after loading data):
CREATE INDEX ON contract_chunks USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);
SET ivfflat.probes = 10;                     -- default 1; start near sqrt(lists)

-- Hard tenant isolation: one partition (and one ANN index) per large tenant
CREATE TABLE chunks_p (tenant_id text NOT NULL, embedding vector(1024), content text)
    PARTITION BY LIST (tenant_id);
CREATE TABLE chunks_acme PARTITION OF chunks_p FOR VALUES IN ('acme');

SET LOCAL scopes the setting to the transaction, which matters behind a connection pool such as HikariCP: a plain SET leaks to the next borrower of that connection. With relaxed_order, results can be slightly out of distance order; wrap the query in a MATERIALIZED CTE and re-sort (ORDER BY distance + 0 on Postgres 17+) if you need strict order.

Step 6: ingest PDFs from Python

uv venv && source .venv/bin/activate
uv pip install "psycopg[binary]" pgvector pypdf voyageai numpy
export VOYAGE_API_KEY=...        # Anthropic has no embedding model; its docs point to Voyage AI
python ingest_pdfs.py acme contracts/*.pdf
"""Ingest contract PDFs into pgvector: python ingest_pdfs.py acme contracts/*.pdf"""
import sys
import uuid
from pathlib import Path

import psycopg
import voyageai
from pgvector.psycopg import register_vector
from pypdf import PdfReader

DSN = "postgresql://postgres:postgres@localhost:5432/postgres"
MODEL, DIM = "voyage-4", 1024
CHUNK_CHARS, OVERLAP = 2000, 200  # ~500 tokens, 10% overlap

SCHEMA = f"""
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE IF NOT EXISTS contract_chunks (
    id              bigserial PRIMARY KEY,
    tenant_id       text        NOT NULL,
    document_id     uuid        NOT NULL,
    chunk_index     int         NOT NULL,
    page            int         NOT NULL,
    source          text        NOT NULL,
    content         text        NOT NULL,
    content_tsv     tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
    embedding       vector({DIM}) NOT NULL,
    embedding_model text        NOT NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    UNIQUE (document_id, chunk_index)
);
CREATE INDEX IF NOT EXISTS contract_chunks_hnsw ON contract_chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX IF NOT EXISTS contract_chunks_tenant ON contract_chunks (tenant_id);
CREATE INDEX IF NOT EXISTS contract_chunks_tsv ON contract_chunks USING gin (content_tsv);
"""


def chunk_page(text: str) -> list[str]:
    """Split one page into overlapping windows, preferring paragraph breaks."""
    text = " ".join(text.split("\n\n")).strip()
    chunks, start = [], 0
    while start < len(text):
        end = min(start + CHUNK_CHARS, len(text))
        if end < len(text):  # back off to the last sentence end inside the window
            cut = text.rfind(". ", start + CHUNK_CHARS // 2, end)
            end = cut + 1 if cut != -1 else end
        chunks.append(text[start:end].strip())
        if end == len(text):
            break
        start = end - OVERLAP
    return [c for c in chunks if c]


def load_pdf(path: Path) -> list[tuple[int, str]]:
    """Return (page_number, chunk_text) pairs; page numbers are 1-based for citations."""
    out = []
    for page_no, page in enumerate(PdfReader(path).pages, start=1):
        for chunk in chunk_page(page.extract_text() or ""):
            out.append((page_no, chunk))
    return out


def ingest(conn: psycopg.Connection, vo: voyageai.Client, tenant_id: str, path: Path) -> int:
    chunks = load_pdf(path)
    if not chunks:
        print(f"skip {path}: no extractable text (scanned PDF? run OCR first)")
        return 0
    # uuid5 of tenant + file name: re-ingesting the same file replaces its rows instead of duplicating them
    doc_id = uuid.uuid5(uuid.NAMESPACE_URL, f"{tenant_id}/{path.name}")
    vectors = []
    for i in range(0, len(chunks), 128):  # batch the embedding calls
        batch = [text for _, text in chunks[i:i + 128]]
        vectors += vo.embed(batch, model=MODEL, input_type="document").embeddings
    with conn.transaction():
        conn.execute("DELETE FROM contract_chunks WHERE document_id = %s", (doc_id,))
        with conn.cursor() as cur:
            cur.executemany(
                "INSERT INTO contract_chunks (tenant_id, document_id, chunk_index, page, source, content, "
                "embedding, embedding_model) VALUES (%s, %s, %s, %s, %s, %s, %s, %s)",
                [(tenant_id, doc_id, i, page, path.name, text, vec, MODEL)
                 for i, ((page, text), vec) in enumerate(zip(chunks, vectors))],
            )
    return len(chunks)


def main() -> None:
    tenant_id, files = sys.argv[1], [Path(p) for p in sys.argv[2:]]
    vo = voyageai.Client()  # reads VOYAGE_API_KEY
    with psycopg.connect(DSN, autocommit=True) as conn:
        conn.execute(SCHEMA)
        register_vector(conn)  # after CREATE EXTENSION, so the vector type exists
        for f in files:
            print(f"{f.name}: {ingest(conn, vo, tenant_id, f)} chunks")


if __name__ == "__main__":
    main()

What it does: one row per ~500-token window with 10% overlap, page numbers kept for citations, embeddings batched 128 at a time with input_type="document", and a deterministic uuid5 document id so running it twice replaces rows instead of duplicating them. I ran the chunking and database path against the container with a fake embedder: 3 chunks of 1,979 / 1,964 / 1,856 characters, and 3 rows after two runs. For a big initial load, the README recommends COPY ... WITH (FORMAT BINARY) and creating indexes after loading (CREATE INDEX CONCURRENTLY in production, and enough maintenance_work_mem for the HNSW graph to fit).

Query side, note input_type="query":

import numpy as np
import psycopg
import voyageai
from pgvector.psycopg import register_vector

DSN = "postgresql://postgres:postgres@localhost:5432/postgres"


def search(conn, vo, tenant_id: str, question: str, k: int = 5):
    q = np.array(vo.embed([question], model="voyage-4", input_type="query").embeddings[0])
    return conn.execute(
        """
        SELECT source, page, left(content, 120), embedding <=> %s AS distance
        FROM contract_chunks
        WHERE tenant_id = %s
        ORDER BY embedding <=> %s
        LIMIT %s
        """,
        (q, tenant_id, q, k),
    ).fetchall()


if __name__ == "__main__":
    with psycopg.connect(DSN) as conn:
        register_vector(conn)
        for row in search(conn, voyageai.Client(), "acme", "Can the customer terminate early?"):
            print(row)

Expected output: tuples of ('msa.pdf', 4, 'Either party may terminate ...', 0.21...), nearest first. Distances depend on your documents.

Step 7: the Spring AI equivalent with PgVectorStore

Spring AI 2.0 targets Spring Boot 4.0/4.1. Add the BOM and starters (with the Leegality build, versions come from the catalog):

dependencies {
    implementation platform("org.springframework.ai:spring-ai-bom:2.0.0")
    implementation "org.springframework.ai:spring-ai-starter-vector-store-pgvector"
    implementation "org.springframework.ai:spring-ai-pdf-document-reader"
    // plus one EmbeddingModel starter, e.g. spring-ai-starter-model-openai or -ollama
}
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/postgres
    username: postgres
    password: postgres
  ai:
    vectorstore:
      pgvector:
        index-type: HNSW            # NONE | IVFFlat | HNSW
        distance-type: COSINE_DISTANCE
        dimensions: 1536            # must equal your embedding model's output size
        initialize-schema: true     # dev only; use Flyway in prod
        table-name: vector_store

With initialize-schema: true it creates this table, which is worth knowing because interviewers ask what the abstraction hides:

CREATE TABLE IF NOT EXISTS vector_store (
    id uuid DEFAULT uuid_generate_v4() PRIMARY KEY,
    content text,
    metadata json,
    embedding vector(1536)
);
CREATE INDEX ON vector_store USING HNSW (embedding vector_cosine_ops);
@Service
public class ContractIngestionService {

    private final VectorStore vectorStore;

    public ContractIngestionService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    public void ingest(String tenantId, String documentId, Resource pdf) {
        List<Document> pages = new PagePdfDocumentReader(pdf).read();
        List<Document> chunks = TokenTextSplitter.builder().withChunkSize(500).build().apply(pages);
        List<Document> tagged = chunks.stream().map(d -> {
            Map<String, Object> meta = new HashMap<>(d.getMetadata());
            meta.put("tenantId", tenantId);
            meta.put("documentId", documentId);
            return new Document(d.getText(), meta);
        }).toList();
        vectorStore.add(tagged); // embeds via the EmbeddingModel bean, then inserts
    }
}

@RestController
class ContractSearchController {

    private final VectorStore vectorStore;

    ContractSearchController(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    @GetMapping("/contracts/search")
    @PreAuthorize("hasAuthority('SCOPE_contracts:read')")
    List<Document> search(@RequestParam String q, @AuthenticationPrincipal Jwt jwt) {
        FilterExpressionBuilder b = new FilterExpressionBuilder();
        return vectorStore.similaritySearch(SearchRequest.builder()
                .query(q)
                .topK(5)
                .similarityThreshold(0.5)
                .filterExpression(b.eq("tenantId", jwt.getClaimAsString("tenant_id")).build())
                .build());
    }
}

Use FilterExpressionBuilder rather than concatenating a tenant id into the text form ("tenantId == '" + x + "'"): string-built filters are an injection bug waiting for a tenant name with a quote in it. The text form is fine for constants: "clause_type in ['termination','indemnity'] && year >= 2024".

Production gotchas of the default store
  • Metadata lives in one json column, so tenant filters are JSON-path predicates, not a B-tree lookup. At scale, own the table (your own schema plus a custom query, or a JdbcTemplate repository) so tenant_id is a real indexed column or a partition key.
  • dimensions must match the embedding model; switching models means a new table or column and a re-embed, never mixed vectors.
  • Leave initialize-schema off in production and own the DDL in Flyway, like any other table.

Senior framing: "Start with pgvector because the hard part of enterprise RAG is permissions and freshness, and those are joins and transactions. I'd move to a dedicated engine when p95 ANN latency or index memory starts hurting the OLTP workload, and measure that with recall@k on a golden set before and after."

04How this shows up in interviews

HNSW or IVFFlat for 5M contract chunks?

HNSW. It has the better speed/recall trade-off and needs no training step, so it stays correct as data grows. Cost: slower build and more memory, so set maintenance_work_mem high enough for the graph during builds and build CONCURRENTLY. IVFFlat (lists ≈ sqrt(5M) ≈ 2,236, probes ≈ 47) is the answer if nightly rebuild time or RAM is the constraint.

After adding an HNSW index, a tenant's search returns 3 results instead of 10. Why?

Post-filtering. The index returns about ef_search (40) candidates and the WHERE tenant_id filter discards most. Fix with hnsw.iterative_scan, a higher ef_search via SET LOCAL, a B-tree on tenant_id so small tenants get an exact scan, or partitioning by tenant.

What do m, ef_construction and ef_search control?

m is the number of neighbours per node (graph density, memory). ef_construction is the candidate list size during build (graph quality, build time). ef_search is the candidate list size per query (recall vs latency), and it is the only one you can change without rebuilding. Defaults 16 / 64 / 40.

Cosine, inner product or L2?

Use whatever the embedding model was trained for, usually cosine. If vectors are unit-normalised (Voyage's are), all three rank identically, and inner product (<#>) is the cheapest. The index opclass must match the operator in the query.

Why is my vector query doing a sequential scan?

No LIMIT, ordering by an expression (1 - distance DESC), an operator that does not match the index opclass, or a table small enough that the planner rightly prefers a scan. Check with EXPLAIN (ANALYZE, BUFFERS).

How do you isolate tenants in a shared vector table?

Tenant id from the JWT is added to every query in the repository layer, never from parameters. Add row-level security as defence in depth. For large tenants, list partitions so each has its own ANN index, which also stops one tenant's data distribution hurting another's recall. Test isolation with an automated cross-tenant query that must return zero rows.

Your embedding model has 3,072 dimensions. Can pgvector index it?

Not as vector: the index limit is 2,000 dimensions. Index it as halfvec (up to 4,000) with an expression index, use binary quantisation with re-ranking, or ask the model for fewer dimensions (Matryoshka models such as voyage-4 offer 256–2048).

How do you re-embed the corpus with a new model with zero downtime?

Add a new column or table with the new dimension and embedding_model value, backfill in batches, build its index concurrently, dual-write new documents, switch reads behind a flag after recall@k on the golden set is equal or better, then drop the old column. Never compare vectors across models.

Deletes and updates: anything special?

They are ordinary MVCC rows, which is the advantage: a contract delete removes its chunks in the same transaction. Dead tuples can reduce results, and vacuuming HNSW can be slow; the README suggests REINDEX INDEX CONCURRENTLY then VACUUM after large deletes.

When would you leave pgvector?

When vector search load or index memory starts degrading the transactional workload, or the corpus outgrows a single node, at a size where Citus-style sharding is more work than a dedicated engine. Before that, read replicas for search traffic, halfvec and binary quantisation buy a lot of headroom.
