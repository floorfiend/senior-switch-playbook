News feed (Instagram / Quora / ShareChat)

After this page you can design a home feed that loads in under 200 ms for 500M users and survive the celebrity and "billions of users" follow-ups.

Time-box: 45–60 min Seen: ~8 reports, 2024–26 Probes: fan-out, celebrity problem, cursor pagination, schema
PhonePeFlipkartShareChatFreshworksGoldman SachsIntuit
In 30 seconds
  • Push new post IDs into followers' Redis feeds (fan-out on write).
  • Celebrities are pulled at read time instead: hybrid fan-out.
  • Paginate with a (createdAt, postId) cursor, never an offset.
  • The feed cache is derived data; posts and follows are the truth.
Picture it

A newspaper vendor drops the paper at each subscriber's door every morning (push). For a paper with 10 crore readers, that is impossible, so readers pick it up at the stall (pull). Your feed does both: doorstep delivery for small authors, stall pickup for celebrities.

01What the interviewer is grading

Fan-out with numbers

Push vs pull vs hybrid, justified by follower distribution and read/write ratio.

Celebrity problem

Write amplification and hot shards, fixed with a concrete follower threshold.

Clean schema

Right partition keys: posts by author, follow edges stored in both directions.

Stable pagination

Cursors, not offsets, so new posts don't shift pages.

Feed is derived

The cache can be rebuilt; posts and the follow graph are the truth.

Media path

Upload straight to object storage, serve via CDN, never through app servers.

Go deeper: what each company actually asked

The reports split into two styles. Schema-heavy: Flipkart asked for an Instagram-style feed where influencers endorse brands, users follow brands or influencers, with likes, comments, sticker reactions, and "on unfollow, remove their posts from the feed", then went deep into LLD and the database schema. Scale-heavy: PhonePe's interviewer for "Design Instagram" explicitly did not accept a message-queue fan-out because it does not scale to billions of users; Freshworks asked about sharding and the celebrity problem and what happens when the number of servers changes; Goldman Sachs went from a Twitter LLD into HLD fan-out. ShareChat asked for a paginated feed API using timestamp cursors. PhonePe's internal-Quora variant asked about DB choice, search, auth and microservice communication.

02Clarify and scope

Functional

  • Create posts with media; follow/unfollow users, brands, influencers.
  • Home feed of followed accounts, newest or ranked, infinite scroll.
  • Like, comment, react; counts on each post.
  • Profile feed (one author's posts).

Non-functional

  • 500M DAU; feed p99 < 200 ms.
  • Post visible to followers within ~5 s (eventual consistency OK).
  • Highly available reads (AP); posts never lost.
  • Read-heavy: ~100 feed reads per post written.

Out of scope

  • Stories, reels, DMs, ads auction.
  • The ranking model itself (design the plumbing, not the ML).

04API design

  1. UploadPOST /v1/media/upload-url returns a presigned URL; the client uploads directly.
  2. PostPOST /v1/posts with an Idempotency-Key, so a retry never creates the post twice.
  3. FeedGET /v1/feed?limit=20&cursor=… returns items, nextCursor, hasMore.
  4. BannerGET /v1/feed/new-count?since=… drives "new posts".

The cursor is opaque, so you can later add a ranking score or shard hint without breaking clients. Viewer identity comes from the JWT, never a userId query parameter.

05Data model

post

Partition by author_id, cluster by Snowflake post_id desc: a profile feed is one partition read.

follow + follower

Edges stored twice: by follower_id ("whom do I follow") and by followee_id ("who follows me", used by fan-out).

feed:{userId}

Redis sorted set: member = post ID, score = ms timestamp. Trimmed to 500, active users only.

recent:{authorId}

Last ~200 post IDs per author: the pull path for celebrities.

Detail that impresses

Redis sorted-set scores are doubles, which hold integers exactly only up to 253. A 64-bit Snowflake ID used as the score loses precision. Use the millisecond timestamp as the score and the post ID as the member, and break ties with the member in the cursor.

Post service

Validates, writes the post with an outbox, returns. No synchronous fan-out.

Fan-out workers

Celebrity (>100k followers)? Only recent:{author}. Otherwise page followers, keep active ones, pipeline ZADD + trim, grouped by Redis shard.

Feed service

Pushed feed + celebrity pulls, merge by time, filter blocked/deleted/unfollowed, optionally rank, hydrate with multi-get.

Counters

Likes go through Kafka, aggregated; hot count in Redis, split across N keys for viral posts.

Go deeper: every component
  • Post service. Validates, writes the post (with outbox), returns. It does not fan out synchronously.
  • Fan-out workers. Consume post.created. If the author is a celebrity (say over 100k followers), do nothing: their post goes only into recent:{author}. Otherwise page through the author's followers, filter to active users, and pipeline ZADD plus ZREMRANGEBYRANK into each follower's feed, grouped by Redis shard.
  • Feed service. Reads the user's pushed feed, fetches recent posts from the celebrities they follow (usually a small list, cached), merges by time, filters (blocked, deleted, unfollowed), optionally ranks, then hydrates post bodies, author cards and counts from caches with multi-get.
  • Graph service. Owns follow edges in both directions; publishes follow/unfollow events.
  • Counters. Likes go to Kafka and are aggregated; the hot count lives in Redis. A viral post's counter is split across N keys to avoid a hot key.
  • Search (Quora variant). Elasticsearch fed by CDC from the post store.
  • Media path. App → presigned PUT → object storage (S3) → media pipeline (resize, transcode) → CDN. Kafka carries one event per post, not one per follower.

08Design choices

How posts reach feeds

Push (fan-out on write)

  • Read is O(1): one list
  • O(followers) per post: 100M inserts for a celebrity, minutes of lag
  • Wasted writes for users who never open the app

Most authors, active followers.

Pull (fan-out on read)

  • Write is O(1), always fresh
  • Read gathers posts from up to thousands of followees at 150k reads/s

Celebrities; small internal apps.

Hybrid usual pick

  • Bounded on both sides: one list + a few celebrity pulls
  • Merge logic, threshold tuning

Default at scale; what Twitter converged on.

What the feed stores

Post IDs usual pick

  • Small cache; edits and deletes apply everywhere
  • Hydration step on read

Always.

Full posts

  • One read
  • Huge cache; stale on edit

Never at this scale.

Post store

Cassandra

  • Write throughput, multi-DC, partition-key reads
  • No joins; model per query

Very large scale.

Sharded Postgres either works

  • Familiar, transactions, constraints
  • Resharding work

Up to large scale; Instagram did it.

Go deeper: why hybrid wins

Hybrid is the expected answer, and it is what large systems converge on. Twitter's early design pushed to every follower's in-memory timeline and documented celebrities taking minutes to deliver at p99; the fix is to merge high-follower accounts in at read time.

09Deep dives

9.1 "A message queue doesn't scale to billions" (PhonePe)

Rejected: 1 message per follower

  • One celebrity post = 100M messages
  • The queue becomes the bottleneck and backlog

Defensible: 1 event per post say this

  • ~5k events/s at peak: trivial for Kafka
  • Amplification bounded by policy
  • Pull path makes the queue optional for correctness
Go deeper: the full answer

The interviewer was rejecting the picture of "for each follower, enqueue a message; consumers write it into feeds". That design puts write amplification inside the queue: one celebrity post becomes 100M messages, and the queue becomes the bottleneck and the backlog. A defensible answer:

  • The queue carries one event per post (about 5k/s at peak), never one per follower. Kafka handles that trivially.
  • Amplification is bounded by policy: no push for celebrities (pull at read), no push for inactive users (their feed is rebuilt by pull on next login), cap the pushed list at 500.
  • Writes are batched by destination shard: one worker pass groups follower IDs by Redis slot and pipelines, so 10k followers cost tens of round trips, not 10k.
  • Pull path is first-class: the feed service can compute any user's feed from recent:{author} lists if the push path lags or the cache is cold. So the queue is an optimisation for latency, not a correctness dependency.
  • Work scales with active readers, not total users. "Billions of users" is fine because most of them are not reading right now, and we spend no write work on them.

9.2 Celebrity problem and sharding (Freshworks)

Hot spotFix
Write: 100M feed insertsHybrid fan-out; celebrity flag with hysteresis (enter at 100k, leave at 80k)
Read: 50M users hit one recent:{author}Copies recent:{author}:{0..7} + in-process Caffeine cache, 1–5 s TTL
Storage: huge follower partitionBucket as (followee_id, bucket)
Adding serversConsistent hashing / Redis Cluster's 16,384 slots: ~1/N keys move. Shard by user ID, not post time
Go deeper: details and sharding vs partitioning
  • Write side: covered by hybrid fan-out. Mark accounts as celebrities by follower count with hysteresis (enter at 100k, leave at 80k) so accounts do not flip on every follow.
  • Read side hot keys: 50M users fetching one celebrity's recent:{author} or post body. Replicate that key to several Redis replicas or copies (recent:{author}:{0..7}), and keep a small in-process cache (Caffeine, 1–5 s TTL) in the feed service.
  • Storage hot partition: the celebrity's follower list as one Cassandra partition is too wide; bucket it as (followee_id, bucket).
  • Changing the number of servers: use consistent hashing with virtual nodes (or Redis Cluster's 16,384 hash slots) so adding a node moves about 1/N of keys rather than reshuffling everything. Shard by user ID, not by post time, or the newest shard takes all writes.
  • Sharding vs partitioning (they asked): partitioning splits a table into parts, possibly on one server; sharding is partitioning across machines, with routing and rebalancing concerns.

9.3 Cursor pagination (ShareChat)

Offset

  • New posts push items down: page 2 repeats page 1
  • Large offsets are slow

Keyset cursor usual pick

  • Stable under inserts, fast
  • (created_at, post_id): ID breaks timestamp ties
  • No jump to page N

All feeds.

-- Profile feed or pull path from the post store
SELECT post_id, author_id, created_at FROM post
 WHERE author_id = :authorId
   AND (created_at, post_id) < (:cursorTs, :cursorId)
 ORDER BY created_at DESC, post_id DESC
 LIMIT 20;

-- Home feed from Redis: scores are timestamps, exclusive upper bound
ZRANGE feed:{u42} 1728290000000 -inf BYSCORE REV LIMIT 0 30
-- inclusive bound: at the boundary timestamp, drop ids >= cursorId in code,
-- then keep 20; a 21st surviving item means hasMore

Pull-to-refresh uses the top item's cursor in the other direction ("newer than"). With Snowflake IDs, post_id alone is time-ordered, so post-store queries can use just the ID.

Go deeper: why timestamp-only cursors fail

Offset pagination breaks a live feed: new posts push items down, so page 2 repeats items from page 1, and large offsets are slow. Use a keyset cursor of (created_at, post_id); the post ID breaks ties when two posts share a timestamp, which a timestamp-only cursor gets wrong.

9.4 Unfollow, delete and the Flipkart schema

UnfollowFeed service filters that author at read time (follow set is cached)Async job removes IDs from the sorted set

Brand vs influencerOne account table with a type, one follow table; endorsements join posts to brands

Go deeper: the full Flipkart follow-ups
  • Unfollow must remove their posts. The pushed feed holds IDs from many authors; scanning it is fine at 500 entries. On unfollow, the feed service filters out that author immediately at read time (the follow set is cached), and an async job removes the IDs from the sorted set. Correct immediately, cleaned eventually.
  • Delete a post. Mark deleted in the post store; hydration drops it; fan-out workers do not need to chase every feed.
  • Brands vs influencers. One account table with a type, one follow table: everything is "follow an account". Endorsements are a join table between posts and brands, so a brand page can show influencer posts about it.
  • Sticker reactions. A reaction table with a type, counts aggregated per (post, type).

10Scaling, failure handling and consistency

SituationWhat happens

Go deeper: full notes, plus PhonePe's internal Quora
  • What breaks first at 10x: fan-out lag during peaks (festive season, a cricket final). Kafka absorbs the burst; feeds are a few seconds behind, which is acceptable. Lower the celebrity threshold dynamically when lag grows: more pull, less push.
  • Redis loss. A feed shard dies: affected users get their feed rebuilt by pull from recent:{author} and the post store, then repopulated. Slower, not broken. Never treat Redis as the system of record.
  • Idempotent fan-out. Kafka redelivery inserts the same post ID into a sorted set again: ZADD is idempotent by member, so duplicates are harmless.
  • Ordering. Feeds are sorted by post timestamp, not arrival time, so out-of-order fan-out is invisible.
  • Consistency. Feeds are AP and eventually consistent. Read-your-own-writes matters: the author must see their own post immediately, so the feed service merges the viewer's own recent posts into the response.
  • Multi-region. Users are homed in a region; posts replicate globally (Cassandra multi-DC); fan-out runs in each follower's home region from the replicated event.
  • Ranking at scale. Candidate generation (pushed feed + celebrity pulls + recommended posts) yields ~500 candidates, a lightweight model scores them, a heavier one re-ranks the top 50. Cache the ranked page per user for a minute.
  • Internal Quora (PhonePe). Postgres for questions, answers, votes (strong relations, moderate scale); Elasticsearch for search with CDC sync; SSO via the company identity provider (OIDC), JWT at the gateway, roles for moderators; synchronous REST/gRPC for queries, Kafka events for notifications, search indexing and reputation. A feed of "questions in topics I follow" is the same hybrid model at a much smaller scale; pull alone is fine for an internal tool.

11Mistakes that got candidates rejected

Rejected for this
  • Pure push with a message per follower, then no answer to the celebrity case or "billions of users".
  • Pure pull with a SQL IN (followees) query sorted by time, at 150k QPS.
  • Offset pagination, or a timestamp-only cursor with no tie-breaker.
  • Treating the Redis feed as the source of truth, with no rebuild path.
  • Storing full post objects in every follower's feed.
  • A schema with no thought about partition keys: one follow table that serves neither "whom do I follow" nor "who follows me" efficiently.
  • Media bytes through application servers instead of presigned uploads and a CDN.

13Quick check

An account with 80M followers posts. What does the fan-out worker do?

Celebrities are above the threshold, so their posts are pulled and merged at read time. Push would cost 80M writes and minutes of lag.

Why does the feed use a (createdAt, postId) cursor instead of ?page=2?

Keyset cursors say "older than this item", which stays correct as new posts arrive. A timestamp alone can skip or repeat posts that share a millisecond.

A Redis feed shard is lost. What happens to those users?

The feed is derived data. Posts and the follow graph are the truth, so the pull path recomputes it: slower, not broken.

Why use the timestamp, not the Snowflake post ID, as the sorted-set score?

Use ms timestamp as score, post ID as member, and break ties with the member in the cursor.

14Interview questions

Your MQ-based fan-out won't scale to a billion users. What now?

One Kafka event per post, not per follower. Push only to active followers of non-celebrity authors, batched per Redis shard; pull celebrities at read time; inactive users get feeds built on demand. Work then scales with posts and active readers, and the pull path means the queue is a latency optimisation, not a correctness dependency.

What is the celebrity problem?

A post by an account with 100M followers costs 100M feed writes under push, causing lag and hot partitions; and millions of reads hit the same keys. Fix with hybrid fan-out (pull celebrities), replicated hot keys, local caches, and bucketed follower partitions.

How do you design the paginated feed API?

GET /feed?limit=20&cursor=... with an opaque cursor of (createdAt, postId). Query "older than the cursor" ordered by time then ID. Offsets duplicate items as new posts arrive and get slower with depth. Return nextCursor and hasMore.

A user unfollows someone. Their posts must vanish now.

Filter at read time against the cached follow set, so it is correct on the next request; asynchronously remove that author's IDs from the user's sorted set. Do not block the unfollow on cleaning the feed.

What happens when you add servers to the feed cache?

With consistent hashing (or Redis Cluster slots), only about 1/N of keys move. Moved feeds are cold: the feed service falls back to pull and repopulates. Migrate slots gradually to avoid a cold-cache spike.

How do like counts work for a viral post?

Writes go to Kafka and are aggregated in small windows; counts live in Redis split across N sub-keys and are summed on read; periodically persisted. Counts are approximate in real time, which users accept.

Twitter LLD to HLD: what changes?

In LLD, a TimelineService merges the posts of followed users with a heap. In HLD that same merge becomes the pull path for celebrities; the rest is precomputed by fan-out workers into per-user caches, because a heap merge over 2,000 followees at 150k QPS is too expensive.

How do media uploads work without hurting app servers?

Client asks for a presigned URL, uploads directly to S3, the post references the media ID. An event triggers resizing and transcoding into several renditions; the CDN serves them. App servers never touch the bytes.

15Cheat sheet

Cheat sheet
  • 500M DAU → ~150k feed QPS peak, ~5k posts/s, 230k/s naive fan-out writes.
  • Hybrid fan-out: push to active followers; celebrities (>100k, hysteresis) pulled at read.
  • Kafka carries one event per post, never one per follower.
  • Feed = Redis ZSET feed:{user}, score = ms timestamp, member = post ID, trimmed to 500.
  • Store IDs, hydrate with multi-get; the cache is rebuildable, never the truth.
  • Keyset cursor (createdAt, postId), opaque base64.
  • Follow edges in both directions; bucket celebrity follower partitions.
  • Unfollow/delete: filter at read now, clean up async.
  • Media: presigned PUT to S3, CDN out.
