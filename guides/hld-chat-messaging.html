Chat / Messaging (WhatsApp, Teams)

Design one-to-one and group chat. It needs read receipts, delivery to people who are offline, several devices per user, and messages that always show in the right order.

Time-box: 45–60 min Seen: Uber (WhatsApp, Messenger, ChatGPT-like), Microsoft (Teams), Freshworks, Goldman Sachs (YouTube Live chat), Amazon (ChatGPT)
UberMicrosoftFreshworksGoldman SachsAmazon
In 30 seconds
  • Phones keep an open WebSocket to a gateway server. A registry remembers which gateway each user's device is on.
  • Give every message a number that counts up within its conversation. Use it, not timestamps, for order and catching up.
  • Save the message first, then confirm to the sender. Kafka, grouped by conversation, delivers it to the others.
  • Store messages by (conversation, time slot). Then "the last 50 messages" is one quick read.
Picture it

Think of a housing society register at the gate. Every parcel gets the next line number on that flat's page. The guard knows which wing each resident is in today. A resident who was away reads their page from the last line number they remember.

Words you'll see
WebSocket
A connection that stays open, so the server can send messages to the phone at any time. Normal HTTP only answers when the phone asks.
Gateway
A server whose only job is to hold open WebSocket connections, about 200,000 per server.
Session registry
A lookup table in Redis: "Ravi's phone is connected to gateway G3".
Sequence number (seq)
A counter per conversation: 1040, 1041, 1042. It gives the exact order, and a jump shows a message is missing.
ACK
An acknowledgement: "I received and saved it". In chat it shows up as ticks.
Fan-out
Sending one message on to many receivers, such as every member of a group.
Sync cursor
The last sequence number a device has. On reconnect it asks "give me everything after this".
Partition
One slice of the data that lives together on the same servers. Here, one conversation's messages for one time slot.

01What the interviewer is grading

Real-time transport

Why WebSocket (or MQTT)? How does a message reach a user who is connected to a different server?

Delivery guarantees

Messages may be sent more than once, and the phone hides repeats. Sent, delivered and read ticks. Delivery to offline users.

Ordering

A counter per conversation that only goes up. Know why clock timestamps fail.

Storage

Many writes, in time order, grouped by conversation. Watch for one busy chat overloading a server.

Fan-out and variants

Groups, huge live-stream chat rooms, and AI replies streamed word by word.

Go deeper: what the reports said

Uber asks for WhatsApp and Facebook Messenger. An Uber SDE-2 (Jun 2026) got "a chat application similar to ChatGPT", with starting a new chat and continuing an old one. They got stuck mid-design and were rejected. Microsoft asks for MS Teams messaging. It pushes hard on sequence numbers vs timestamps. Freshworks asked for a WhatsApp-like design, and told the candidate to go and learn how WebSockets work. Goldman Sachs asked for YouTube Live chat. Amazon asked for ChatGPT. The common grading looks like this.

  • Real-time transport: why WebSocket (or MQTT), and how a message reaches a user connected to a different server.
  • Delivery guarantees: at-least-once delivery, with the phone dropping repeats. Ack levels (sent, delivered, read). Delivery to offline users.
  • Ordering: a counter per conversation that only goes up, and why clock timestamps fail.
  • Storage: heavy writes, in time order, split by conversation. Busy chats that overload one partition.
  • Group fan-out and the variants: huge rooms (live chat) and streaming AI model (LLM) replies (ChatGPT).

02Clarify and scope

Functional

  • One-to-one and group messages (up to 1,000 members)
  • Sent, delivered and read receipts
  • Delivery after being offline, and history sync at login
  • Several devices per user; online status; photos sent as a link to stored files

Non-functional

  • When both are online, 99 out of 100 messages arrive within 500 ms (Slack quotes ~500 ms worldwide)
  • No lost messages; users never see duplicates
  • Correct order within a conversation
  • Up 99.99% of the time

Out of scope

  • Voice and video calls
  • Full-text search (mention Elasticsearch per customer)
  • Spam detection models
Go deeper: six questions to ask first
  • One-to-one only, or groups? How big can a group be? WhatsApp limits groups to hundreds, up to ~1,000. Teams channels can be bigger. Live chat has no limit. The size decides how you fan out.
  • Several devices? Each device needs its own sync cursor. So you cannot "delete from the server once delivered" unless you track every device.
  • How long are messages kept? WhatsApp keeps only undelivered messages (store-and-forward). Teams and Slack keep the full history on the server and support search.
  • End-to-end encryption? If yes, the server cannot read, index or search messages. Sharing encryption keys becomes important.
  • Photos and files? The phone uploads them to file storage through a pre-signed URL, a temporary upload link. The message only carries a link.
  • Online status and typing indicators? Very frequent, short-lived and best-effort. Losing one does not matter.

Discord stored messages in Cassandra, split by (channel_id, time bucket). Later it moved to ScyllaDB, going from 177 Cassandra nodes to 72 Scylla nodes. It also added a data service in front of busy partitions that merges identical requests into one. That is the same layout, with real numbers you can quote.

  1. The sender's gateway passes the SEND to the chat service.
  2. The chat service checks the sender is a member. It drops repeats by (sender, clientMsgId). It gives the message the next seq for the conversation, saves it and updates last_seq. It publishes to Kafka and returns the ACK. The sender sees one tick only after the message is safely saved.
  3. Fan-out workers turn the member list into a device list. They look up each device's gateway in the registry. They send through an internal call or pub/sub channel. Offline devices get a push notification. Their messages wait in the database until the next sync.
  4. Receiving devices reply DELIVERED or READ with upToSeq. That travels back to the sender as a receipt.
  5. On reconnect, a device calls /sync with its cursor for each conversation. It pulls everything with a higher seq. Pushing over the socket is only a speed-up. Sync is what guarantees correctness.

Slack's real-time system uses the same split. Gateway Servers hold the WebSocket connections in each region. Channel Servers each own a set of channels, picked by consistent hashing. A hash-ring manager replaces a failed channel server within about 20 seconds.

Per-conversation seq: gap detection

Redis INCR seq:{conv}

  • Simple; ~100k operations per second per Redis server
  • After a Redis failover, numbers can be handed out twice. Fix: reset to the highest saved number plus a gap.

Quick, common answer.

Conversation owner usual pick

  • One server owns each conversation and counts in memory
  • No extra network call per message

At scale (pick the owner by Kafka partition or consistent hashing).

DB conditional write

  • Correct (UPDATE … RETURNING or a Cassandra lightweight transaction)
  • Slower

Quiet chats.

Go deeper: why timestamps fail, and Snowflake ids

Ordering by the phone's timestamp fails because phone clocks are often wrong. Ordering by server timestamp also fails, for three reasons. Two chat servers' clocks differ slightly: NTP keeps them within milliseconds, not exactly equal. Two messages can share the same millisecond. And a message saved later can carry an earlier timestamp. You also cannot sync safely with a timestamp cursor. "Give me everything after 10:31:02.123" misses a message saved late with timestamp 10:31:02.120.

Instead, use a counter per conversation that only goes up. One authority hands out the numbers for each conversation. There are three ways to do it.

  • Redis INCR seq:{conv}: simple, about 100k operations per second per Redis server. The risk: after a Redis failover, it can hand out a number twice. So also save last_seq in the database. On recovery, set the counter to the highest saved number plus a gap.
  • Conversation owner: send all writes for a conversation to one chat server, chosen by Kafka partition or consistent hashing. It counts in memory and saves. No extra network call per message.
  • DB conditional write: UPDATE conversations SET last_seq = last_seq + 1 ... RETURNING in SQL, or a Cassandra lightweight transaction (LWT). Correct but slower. Fine for quiet chats.

The counter gives three things. A total order within a conversation. Gap detection: the phone has 1040, receives 1042, so it fetches 1041. And a perfect sync cursor. You do not need one global order across all conversations. Snowflake-style ids combine timestamp, machine and counter. They are unique and roughly sorted, but they have gaps, so they cannot detect missing messages. Use them for msg_id, not for ordering. The time shown on screen still comes from the server timestamp.

6.2 Delivery guarantees and acks

  1. Client → serverThe phone resends until it gets a confirmation, always with the same message id (clientMsgId). The server drops repeats. Sending at least once plus dropping repeats means each message appears once.
  2. Server → clientThe server pushes the message. The phone replies "delivered up to" a number. That number, saved in the database, is the truth. Catching up (/sync) fills any gaps.
  3. Group receiptsStore how far each member has read (last_read_seq). "Read by 12 of 40" is counted only when someone asks.
  4. OfflineA push notification wakes the app. The app then catches up.
Go deeper: delivery guarantees in full
  • Client → server: the phone resends SEND with the same clientMsgId until it gets an ACK. The server drops repeats, using a unique key or a short-lived Redis set. At-least-once delivery plus dropping repeats gives "effectively once".
  • Server → client: the server pushes the message, and the phone acks DELIVERED up to a seq. The server does not track each unacked message in memory. The device's cursor in the database is the truth, and /sync fills gaps.
  • Receipts in groups: store last_read_seq for each member. "Read by 12 of 40" is a count over members. It is calculated only when the sender opens message info.
  • Offline: messages stay in the conversation. A push notification wakes the app, and the app syncs. In WhatsApp-style store-and-forward, the server deletes its copy once every registered device has acked.

6.3 Group fan-out

Write once, notify usual pick

  • Store the message once in the conversation. Push to members who are online. Others fetch it when they sync.

Default for chat: every member reads the same ordered log.

Per-user inbox copy

  • Each device gets its own copy
  • One message becomes many writes

Small groups; end-to-end encryption.

Pub/sub per room, sampled

  • Each gateway subscribes once per room and passes messages to its own viewers
  • Order is best-effort

YouTube Live, Teams town halls.

For a 1,000-member group, look up all 1,000 gateways in one batch (MGET). Then send one message per gateway, listing the receivers connected to it.

6.4 Variants: YouTube Live chat and ChatGPT

YouTube Live

A million viewers. Keep one log per room and a two-level pub/sub. Send in 100–250 ms batches. Show only a sample when messages come faster than people can read. Add slow mode. Paid Super Chats take a reliable path.

ChatGPT-like

Same storage, but the other side is an AI model. Stream words back as they are generated. Save as you go. Load recent turns plus a summary. Queue GPU work by priority.

Go deeper: both variants in full

YouTube Live (Goldman Sachs). One room has a million viewers and thousands of messages per second. Sending each message to a million sockets is impossible, and nobody could read it anyway. Write messages to a room log, split by room. Each gateway subscribes once per room and passes messages to its own viewers. This is a two-level pub/sub tree. Group messages into 100–250 ms batches. When messages arrive faster than a human can read, show each viewer only a sample. Add slow mode and per-user rate limits. Order is best-effort, and there are no read receipts. Super Chats and pinned messages go through a separate, reliable path.

ChatGPT-like (Uber, Amazon). Conversations and messages are stored like any chat: partition by conversation_id, with a seq per turn. But the "other participant" is an LLM (large language model). Sending creates the user's turn and queues a generation job. Words stream back over SSE or WebSocket. SSE (server-sent events) is a simple one-way stream from server to browser. The assistant's turn is saved as it grows, or at the end with checkpoints. Then a page refresh in the middle can resume. To continue a chat, load the last N turns plus a running summary. That keeps it inside the model's context window, the most text it can read at once. Add per-user token rate limits. Put a queue with priority levels in front of the GPU servers. Support "stop generating". Make a retried turn safe by keying it on (conversation_id, turn_seq).

heartbeat 0 s30 s60 s missed90 s missedoffline

"Online" is a registry entry that expires unless renewed. The phone renews it with a heartbeat every 30 s. Mark a user offline only after 2 missed heartbeats, so a short network blip does not flicker. Send status changes only to people who have that chat open, or who are recent contacts. For huge contact lists, fetch status only when needed.

07Design choices

WebSocket usual pick

  • Both sides can send at any time; low overhead; built into browsers
  • Servers hold state, so load balancers and deploys must move connections gently

Default for chat.

Long polling / SSE

  • Works through any proxy; SSE is simple for server-to-phone messages
  • More overhead; SSE only goes one way

Fallback; streaming AI replies.

MQTT

  • Tiny messages; good on weak mobile networks
  • One more message broker to run

Mobile-first apps (Facebook Messenger used MQTT).

Cassandra / Scylla usual pick

  • Handles heavy writes, splits by conversation, scales by adding servers
  • No joins; deletes leave "tombstone" markers that slow reads; busy partitions

Message history at scale.

Postgres / MySQL (sharded)

  • Transactions; familiar
  • You split data by hand; B-tree indexes make each write cost more

Smaller scale; company chat with strict separation per customer.

Per-conversation sequence always

  • Exact order, gap detection, sync bookmark
  • Only one writer per conversation

Ordering.

Timestamps / Snowflake ids

  • No coordination needed
  • Clocks differ; cannot detect gaps

Ids and display time only.

08Scaling, failure handling and consistency

Gateway dies

200k phones reconnect after a short random wait, register again and catch up from their bookmarks. Nothing lived only in the gateway's memory.

Registry stale

If delivery to the listed gateway fails, send a push notification instead. Sync still guarantees nothing is missed.

Hot conversation

Time slots cap partition size. Merge identical reads into one (Discord). Cache recent messages in Redis.

Multi-region

Each conversation has one home region that hands out its numbers. Accept slower cross-region chats rather than two regions numbering at once.

Go deeper: full scaling notes
  • Gateway dies. Its 200k phones reconnect to other gateways. Each waits a random, growing delay, so they do not all hit at once (a "thundering herd"). They register again and sync from their cursors. No message is lost, because nothing lived only in gateway memory.
  • Registry stale. Delivery to a gateway that no longer has the device fails. The worker then sends a push notification. Correctness still comes from sync.
  • Hot conversation. A big, active group hammers one partition. Time buckets limit partition size. A read layer that merges identical requests (Discord) turns many reads into one. Recent messages are cached in Redis per conversation.
  • Kafka lag. Fan-out workers scale with the number of partitions. Order within a conversation is kept, because the key is conv_id.
  • Multi-region. Users connect to the nearest region. Each conversation has a home region that assigns seq. Members in other regions receive messages through copied Kafka topics (MirrorMaker) or calls between regions. Accept higher delay for cross-region groups, rather than letting several regions assign numbers at once.
  • 10×. Add gateways (they hold no state apart from sockets) and Kafka partitions. Cassandra grows by adding servers. The registry is the piece to split carefully.

09Mistakes that got candidates rejected

Rejected for this
  • "WebSockets and a message queue", with no explanation of how a socket works or how messages cross servers (the Freshworks feedback).
  • Ordering by timestamp, and not seeing the clock problem when the interviewer asks.
  • Keeping messages only in gateway memory or a queue, so a gateway crash loses them. No sync path.
  • One global relational messages table, with no plan for splitting it.
  • For ChatGPT-like: designing a plain chat and never covering streaming, context length or GPU capacity. Getting stuck halfway (the Uber rejection).

10Quick check

Ravi is connected to gateway G3. Asha's message lands on chat server number 12. How does it reach Ravi?

The registry says which gateway each user's device is on. If the device is not there, it is offline: send a push notification, and it will sync later.

Why is a per-conversation counter a better sync bookmark than a server timestamp?

Server clocks differ slightly. A later message can get an earlier timestamp, and "after T" would skip it forever.

A gateway crashes with 200k users connected. What stops messages from being lost?

Pushing is only a speed-up. The database and the bookmarks are the truth.

A YouTube Live room has a million viewers. What is the best way to deliver chat?

Sending to each socket separately is impossible and unreadable. A two-level pub/sub with sampling scales.

11Follow-up questions interviewers asked

How does a message reach a user connected to a different server?

The session registry maps each user and device to a gateway id. The fan-out worker looks it up. It sends the message to that gateway through an internal RPC (a server-to-server call) or a pub/sub channel per gateway. If the lookup finds nothing, the user is offline. Send a push notification and rely on sync.

Why not order messages by timestamp?

Clocks on phones and servers differ. Timestamps can collide. A timestamp bookmark can skip a message that was saved late. A per-conversation sequence from one authority gives an exact order, gap detection and a safe sync bookmark.

The phone sent a message, the network dropped, and it sends again. How do you avoid a duplicate?

The resend carries the same clientMsgId. The server sees it is already saved and returns the original msgId and seq. The app also hides repeats by clientMsgId.

How does a phone that was offline for two days catch up?

It sends /sync its last seq for each conversation, or one overall bookmark for its inbox. The server returns the conversations with a newer last_seq. It then sends messages after the bookmark, page by page. Big backlogs load lazily. Show the chat list first, and load messages when a chat is opened.

How do WebSocket servers scale and deploy without dropping users?

Use L4 load balancing, which routes raw TCP connections. Limit connections per server. Drain gently on deploy: stop accepting, tell clients to reconnect elsewhere, then wait. Clients reconnect after a random delay. Scale on connection count and memory, not CPU alone.

How would you add end-to-end encryption?

Use the Signal protocol approach. Each device publishes its identity key and pre-keys. Senders encrypt separately for each receiving device, or use shared sender keys for groups. The server only passes along encrypted text. So server-side search and content moderation are lost.

13Cheat sheet

Cheat sheet
  • WebSocket gateways, plus a Redis registry mapping user to device to gateway.
  • Send path: drop repeats by clientMsgId, assign seq, save, publish to Kafka (key conv_id), then ACK.
  • Fan-out: look up the registry, batch per gateway. Offline: push notification, then sync.
  • Seq per conversation gives order, gap detection and the sync bookmark. Timestamps are for display only.
  • Store messages by (conv_id, time bucket), sorted by seq newest first, in Cassandra or Scylla.
  • Receipts say "up to seq N". Group read counts are calculated only when asked.
  • Gateway crash: reconnect after a random wait, then /sync. Nothing lives only in memory.
  • Live chat: room pub/sub, batches, sampling. ChatGPT: stream words, save turns, GPU queue.
