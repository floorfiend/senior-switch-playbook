Chat / Messaging (WhatsApp, Teams)

Design 1:1 and group chat with receipts, offline delivery, multiple devices and correct ordering.

Time-box: 45–60 min Seen: Uber (WhatsApp, Messenger, ChatGPT-like), Microsoft (Teams), Freshworks, Goldman Sachs (YouTube Live chat), Amazon (ChatGPT)
UberMicrosoftFreshworksGoldman SachsAmazon
In 30 seconds
  • WebSocket gateways plus a session registry: user → gateway.
  • Per-conversation sequence numbers, not timestamps, for order and sync.
  • Persist, then ACK; fan out via Kafka keyed by conversation.
  • Store by (conversation, time bucket) so "last 50" is one partition read.

A housing society register at the gate. Every parcel gets the next line number in that flat's page. The guard knows which wing each resident is in today. If a resident was away, they read their page from the last line number they remember.

Go deeper: what the reports said

Uber asks WhatsApp and Facebook Messenger; an Uber SDE-2 (Jun 2026) got "a chat application similar to ChatGPT" (start a new chat, continue a previous one) and was rejected after getting stuck mid-design. Microsoft asks MS Teams messaging and specifically pushes on sequence numbers vs timestamps. Freshworks asked a WhatsApp-like HLD and told the candidate to go back and learn how WebSockets work. Goldman Sachs asked YouTube Live chat, Amazon asked ChatGPT. The common grading:

  • Real-time transport: why WebSocket (or MQTT), how a message reaches a user connected to a different server.
  • Delivery guarantees: at-least-once with client-side dedup, ack levels (sent, delivered, read), offline delivery.
  • Ordering: per-conversation monotonic sequence, why wall-clock timestamps fail.
  • Storage: write-heavy, time-ordered, partitioned by conversation; hot partitions.
  • Group fan-out and the variants: huge rooms (live chat), streaming LLM responses (ChatGPT).

02Clarify and scope

Functional

  • 1:1 and group (≤ 1,000) messages
  • Sent / delivered / read receipts
  • Offline delivery and history sync on login
  • Multi-device; presence; media by reference

Non-functional

  • Send → receive p99 < 500 ms when both online (Slack quotes ~500 ms worldwide)
  • No lost messages; duplicates hidden from users
  • Ordered within a conversation
  • 99.99% availability

Out of scope

  • Voice / video calls
  • Full-text search (mention Elasticsearch per tenant)
  • Spam ML
Go deeper: six questions to ask first
  • 1:1 only, or groups? Max group size? WhatsApp caps groups (hundreds to ~1,000); Teams channels can be larger; live chat is unbounded. Size picks the fan-out strategy.
  • Multi-device? Each device needs its own sync cursor; this rules out "delete from server once delivered" unless every device is tracked.
  • Message retention? WhatsApp stores undelivered messages only (store-and-forward); Teams / Slack keep full history server-side and support search.
  • End-to-end encryption? If yes, the server cannot index or search content; key distribution matters.
  • Media? Upload to object storage via pre-signed URL; the message carries a reference.
  • Presence and typing indicators? High-volume, ephemeral, best effort.

Discord stored messages in Cassandra partitioned by (channel_id, time bucket), later moved to ScyllaDB (177 Cassandra nodes to 72 Scylla nodes) and put a request-coalescing data service in front of hot partitions. That is the same layout, with real numbers to quote.

  1. Sender's gateway forwards SEND to the chat service.
  2. Chat service checks membership, dedupes on (sender, clientMsgId), assigns seq for the conversation, writes the message, updates last_seq, publishes to Kafka, and returns ACK. The sender sees one tick only after the write is durable.
  3. Fan-out workers expand members to devices, look up each device's gateway in the registry, and send over an internal RPC / pub-sub channel. Offline devices get a push notification; their messages wait in the DB until the next sync.
  4. Recipient devices reply DELIVERED / READ with upToSeq; that flows back as a receipt event to the sender.
  5. On reconnect a device calls /sync with its per-conversation cursors and pulls everything with seq greater than its cursor. Push over the socket is an optimisation; sync is the correctness path.

Slack's real-time stack follows the same split: Gateway Servers hold WebSocket subscriptions per region, Channel Servers own channels via consistent hashing, and a hash-ring manager replaces failed channel servers within about 20 seconds.

Per-conversation seq: gap detection

Redis INCR seq:{conv}

  • Simple, ~100k ops/s per shard
  • Failover can reissue numbers: reset to max(DB) + gap

Quick, common answer.

Conversation owner usual pick

  • One partition owns the conversation; increments in memory
  • No external call per message

At scale (Kafka partition or consistent hash).

DB conditional write

  • Correct (UPDATE … RETURNING or Cassandra LWT)
  • Slower

Low-traffic chats.

Go deeper: why timestamps fail, and Snowflake ids

Ordering by client timestamp fails because device clocks are wrong. Ordering by server timestamp fails because two chat-service instances have skewed clocks (NTP keeps them within milliseconds, not exactly), two messages can share a millisecond, and a message written later can carry an earlier timestamp. You also cannot sync with a timestamp cursor safely: "give me everything after 10:31:02.123" misses a message committed late with timestamp 10:31:02.120.

Use a per-conversation monotonic sequence, assigned by one authority for that conversation:

  • Redis INCR seq:{conv}: simple, ~100k ops/s per shard. Risk: Redis failover can reissue numbers; persist last_seq and on recovery set the counter to max(DB) + gap.
  • Conversation owner: route all writes for a conversation to one chat-service partition (Kafka partition or consistent hash), which increments in memory and persists. No external call per message.
  • DB conditional write: UPDATE conversations SET last_seq = last_seq + 1 ... RETURNING in SQL, or Cassandra LWT. Correct, slower; fine for low-traffic chats.

The sequence gives total order within a conversation, gap detection (client has 1040 and receives 1042 → fetch 1041), and a perfect sync cursor. Global order across conversations is not needed. Snowflake-style ids (timestamp + machine + counter) are unique and roughly sortable but not gap-free, so they do not support gap detection; use them for msg_id, not for ordering. Display time still comes from the server timestamp.

6.2 Delivery guarantees and acks

  1. Client → serverRetry SEND with the same clientMsgId until ACK; server dedupes. At-least-once + dedup = effectively-once.
  2. Server → clientPush MSG; client acks DELIVERED up to a seq. The cursor in the DB is the truth; /sync fills gaps.
  3. Group receiptslast_read_seq per member; "read by 12 of 40" is counted lazily.
  4. OfflinePush notification wakes the app; the app syncs.
Go deeper: delivery guarantees in full
  • Client → server: client retries SEND until ACK, with the same clientMsgId. Server dedupes (unique key or a short-TTL Redis set). At-least-once plus dedup gives effectively-once.
  • Server → client: server pushes MSG; client acks DELIVERED up to a seq. Unacked frames are not tracked per message in memory; the device's cursor in the DB is the truth and /sync fills gaps.
  • Receipts in groups: store last_read_seq per member; "read by 12 of 40" is a count over members, computed lazily when the sender opens message info.
  • Offline: messages stay in the conversation; a push notification wakes the app; the app syncs. WhatsApp-style store-and-forward deletes server copies once every registered device has acked.

Write once, notify usual pick

  • Write amplification

Small groups; E2E encryption.

Pub/sub per room, sampled

  • Gateways subscribe once per room, broadcast locally
  • Best-effort order

YouTube Live, Teams town halls.

1,000-member group: batch the 1,000 registry lookups (MGET) and send one frame per gateway listing its local recipients.

6.4 Variants: YouTube Live chat and ChatGPT

YouTube Live

A million viewers: room log, two-level pub/sub, 100–250 ms batches, sample above reading speed, slow mode. Super Chats on a reliable path.

ChatGPT-like

Same storage; the other side is an LLM. Stream tokens over SSE / WebSocket, persist incrementally, load last N turns + summary, queue GPU work by priority.

Go deeper: both variants in full

YouTube Live (Goldman Sachs). One room, a million viewers, thousands of messages per second. Per-message fan-out to a million sockets is impossible and unreadable. Write messages to a room log partitioned by room; gateways subscribe once per room (a two-level pub/sub tree) and broadcast to their local viewers; batch messages into 100–250 ms frames; sample what each viewer sees when the rate exceeds what a human can read; apply slow mode and per-user rate limits; ordering is best effort, no read receipts. Super Chats / pinned messages go through a separate, reliable path.

ChatGPT-like (Uber, Amazon). Conversations and messages are stored like any chat (conversation_id partition, seq per turn), but the "other participant" is an LLM. Send creates the user turn, enqueues a generation job, and streams tokens back over SSE or WebSocket; the assistant turn is persisted incrementally (or at completion with checkpoints) so a refresh mid-stream can resume. Continue-chat loads the last N turns plus a running summary to fit the context window. Add per-user token rate limits, a queue in front of GPU-bound inference with priority tiers, cancellation (stop generating), and idempotent retries of a turn keyed by (conversation_id, turn_seq).

Presence = registry entry with TTL refreshed every 30 s. Mark offline after 2 missed heartbeats (debounce). Publish changes only to users with that chat open or in recent contacts; fetch on demand for huge contact lists.

08Scaling, failure handling and consistency

Gateway dies

200k clients reconnect with jitter, re-register, sync from cursors. Nothing lived only in gateway memory.

Registry stale

Delivery fails → fall back to push. Sync still guarantees correctness.

Hot conversation

Time buckets bound partitions; coalesce identical reads (Discord); cache recent messages in Redis.

Multi-region

Each conversation has a home region that assigns seq. Accept cross-region latency over multi-master seq.

Go deeper: full scaling notes
  • Gateway dies. Its 200k clients reconnect (with jittered backoff to avoid a thundering herd) to other gateways, re-register, and sync from their cursors. No message is lost because nothing was only in gateway memory.
  • Registry stale. Delivery to a gateway that no longer has the device fails; the worker falls back to push notification. Correctness still comes from sync.
  • Hot conversation. A large active group hammers one partition. Time buckets bound partition size; a coalescing read layer (Discord) collapses identical concurrent reads; recent messages cached in Redis per conversation.
  • Kafka lag. Fan-out workers scale with partitions; per-conversation ordering is preserved because the key is conv_id.
  • Multi-region. Users connect to the nearest region. Each conversation has a home region that assigns seq; cross-region members receive via replicated Kafka (MirrorMaker) or inter-region RPC. Accept higher latency for cross-region groups rather than multi-master sequence assignment.
  • 10×. More gateways (stateless apart from sockets), more Kafka partitions, Cassandra scales linearly. The registry is the piece to shard carefully.

09Mistakes that got candidates rejected

Rejected for this
  • "WebSockets and a message queue" with no explanation of how a socket works or how cross-server delivery happens (the Freshworks feedback).
  • Ordering by timestamp and not seeing the skew problem when the interviewer asks.
  • Messages held only in gateway memory or a queue, so a gateway crash loses them; no sync path.
  • Relational schema with one global messages table and no partitioning story.
  • For ChatGPT-like: designing a generic chat and never addressing streaming, context length, or inference capacity; getting stuck mid-way (the Uber reject).

10Quick check

Ravi is connected to gateway G3; Asha's message lands on chat service instance 12. How does it reach Ravi?

The registry maps user and device to gateway. A miss means offline: push notification plus sync.

Why is a per-conversation seq better than a server timestamp as a sync cursor?

Skewed clocks can give a later message an earlier timestamp, and "after T" would skip it forever.

A gateway crashes with 200k users connected. What prevents message loss?

Push is an optimisation; the DB and cursors are the truth.

A YouTube Live room has a million viewers. Best delivery model?

Per-socket fan-out is impossible and unreadable. Two-level pub/sub plus sampling scales.

11Follow-up questions interviewers asked

How does a message reach a user connected to a different server?

The session registry maps user and device to a gateway id. The fan-out worker looks it up and sends the frame to that gateway via internal RPC or a per-gateway pub/sub channel. If the lookup misses, the user is offline: send a push notification and rely on sync.

Why not order messages by timestamp?

Clocks skew across devices and servers, timestamps collide, and a timestamp cursor can skip a late-committed message. A per-conversation sequence from a single authority gives a total order, gap detection and a safe sync cursor.

The client sent a message, the network dropped, it resends. How do you avoid a duplicate?

The resend carries the same clientMsgId; the server finds it already persisted and returns the original msgId and seq. The UI dedupes on clientMsgId too.

How does a phone that was offline for two days catch up?

It sends its per-conversation last seq (or a single global cursor over its inbox) to /sync; the server returns conversations with newer last_seq and pages messages after the cursor. Large backlogs page lazily: show the chat list first, load messages when a chat is opened.

How do WebSocket servers scale and deploy without dropping users?

L4 load balancing, connection limits per host, graceful drain on deploy (stop accepting, send a reconnect hint, wait), and clients that reconnect with jitter. Autoscale on connection count and memory, not CPU alone.

How would you add end-to-end encryption?

Signal-protocol style: each device publishes identity and pre-keys; senders encrypt per recipient device (sender keys for groups). The server only routes ciphertext, so server-side search and moderation of content are lost.

13Cheat sheet

Cheat sheet
  • Gateways (WebSocket) + Redis registry user → device → gateway.
  • SEND → dedupe clientMsgId → seq → persist → Kafka (key conv_id) → ACK.
  • Fan-out: registry lookup, batch per gateway; offline → push + sync.
  • Seq per conversation: order, gap detection, sync cursor. Timestamps for display only.
  • Messages partitioned (conv_id, time bucket), clustering seq DESC, Cassandra / Scylla.
  • Receipts cumulative upToSeq; group read counts lazy.
  • Gateway crash → jittered reconnect + /sync; nothing lives only in memory.
  • Live chat: room pub/sub, batch, sample. ChatGPT: stream tokens, persist turns, GPU queue.
