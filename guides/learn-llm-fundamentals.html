LLM fundamentals for engineers

An LLM (large language model) is the kind of AI behind Claude and ChatGPT. Interviewers often ask, "Explain how an LLM works." This lesson helps you answer clearly, step by step. It covers tokens, cost, attention, sampling, the KV cache, hallucinations, and when to choose RAG or fine-tuning. You do not need any machine learning background.

Time: 3 hours Prereq: high-school vectors and matrices Code: pure Python, runs offline
LinkedInAmazonAdobeMicrosoftAvaamoMastercardCapgemini
In 30 seconds
  • The model reads text in small pieces called tokens. One token is about 4 English letters. You pay for every token.
  • For each step, the model gives every possible next token a score. It picks one, adds it, and repeats.
  • Attention lets each word look back at earlier words and pull in the useful ones. The formula is softmax(QKᵀ/√d_k)·V.
  • The model will sometimes make things up. Give it real documents (RAG) and design so mistakes are easy to spot.
Picture it

Think of the word suggestions on your phone keyboard, but far more powerful. It suggests the next word from everything typed so far. You tap one, and it suggests again. It has read a huge amount of text. But nothing inside it checks whether the sentence is true.

02Tokens, context and cost

The model does not read letters or whole words. It reads tokens, which are small chunks of text. Each token has a number id, like a word in a numbered dictionary. Here is one possible split. Real splits depend on the tokenizer, the tool that cuts the text.

The␣Supplier␣shall␣indemnification␣of␣₹5,00,000

Common words are one token each. A rare word like indemnification splits into 3–4 pieces. Numbers and symbols split into many pieces.

Rule of thumb

About 4 English letters make one token. An 8,000-word contract is about 10–11 thousand tokens.

Not English? More tokens

Code, numbers, Hindi and other Indian scripts use several times more tokens for the same meaning.

Tokenizers change

Opus 4.7 and later make about 30% more tokens for the same text. Count again with count_tokens.

Why letters are hard

The model never sees single letters. So counting letters or reversing a word is hard for it.

Context window

The context window is how much text the model can see at once. Think of it as the size of its desk.

1Mtokens: Sonnet 5.5, Opus 5.5 (4.6+ models)
200ktokens: Haiku 4.5
128,000max max_tokens on Sonnet 5.5

Everything shares the window. That means your instructions, the chat so far, the tool descriptions, and the answer. A big window is not free. Send the 5 clauses that matter, not 300 contracts.

Go deeper: BPE, context windows and pricing in full

Models do not see characters or words. A tokenizer splits text into tokens from a fixed list, called the vocabulary. The list usually has tens of thousands to a few hundred thousand entries. It is built with an algorithm like byte-pair encoding (BPE). BPE starts from single bytes. It keeps joining the pair that appears side by side most often. It stops when the list reaches the target size.

So common words become one token, and rare words split into pieces. indemnification may be three or four tokens. Every token maps to a number id. Think of it as a compression dictionary, like the one a ZIP file learns from repeated byte patterns.

  • Rule of thumb for English: about 4 characters, or 0.75 words, per token. A 20-page contract of 8,000 words is roughly 10,000–11,000 tokens.
  • Non-English text, code, numbers and odd formatting use more tokens per character. Hindi and other Indian scripts often cost several times more tokens than the same meaning in English.
  • Tokenizers differ between model generations. Claude Opus 4.7 and later use a newer tokenizer. It makes about 30% more tokens for the same text. So count again when you switch models. The API has a free count_tokens endpoint for this.
  • Tokens explain some well-known failures. Counting letters in a word is hard, because the model never saw single letters. Reversing strings is hard for the same reason.

The context window is the most tokens the model can look at in one request. It includes the system prompt (your standing instructions), all messages, tool definitions, and the output it writes. Claude Sonnet 5.5 and Opus 5.5 have a 1M-token window at standard prices. So do other models from 4.6 onward. Haiku 4.5 has 200k. max_tokens caps the output part. On Sonnet 5.5 its maximum is 128,000.

A big window is not free memory. You pay for every input token on every call. The reply gets slower as the input gets longer. And models notice facts buried in the middle of very long inputs less reliably. That is why search still matters, even with 1M tokens. You send the 5 relevant clauses, not 300 contracts.

Ways to cut cost:

  • Use a smaller model where the quality is still good enough.
  • Send fewer and shorter document pieces.
  • Use prompt caching for the part of the prompt that never changes. Reading from the cache costs 10% of the normal input price on most models.
  • Use the Batch API for jobs that can wait. It is 50% off.
  • Ask for shorter answers. Output tokens cost 5× input tokens.

03How the next token is made

The model writes one token at a time. Each new token is added to the text, and the whole process runs again. This is called autoregressive decoding, which just means "each step feeds the next".

Text"The Supplier shall"→ Tokenizerids [464, 30092, 4093]→ Embeddings+ positions→ N transformer blocksattention + MLP→ Logitsone score per vocab entry→ Samplenext token↺

Figure: the generation loop. The chosen token is added to the end, and the loop runs again. It stops at an end token, at a stop word you set, or at max_tokens. The token ids are only examples.

Generating the token after "The Supplier"

How the model learns: first it practises guessing the next token on trillions of tokens. Then it is trained to follow instructions, using feedback from people and from other AI models. Nothing in that training checks whether something is true.

Go deeper: the four stages and training

A GPT-style model is a function. You give it a list of token ids. It gives back a chance for every possible next token. Writing text is just a loop around that function.

  1. Embedding: each token id is looked up in a learned table. The result is a vector, a list of thousands of numbers. Position information is added, so the model knows the order.
  2. Transformer blocks: there are dozens, stacked one after another. Each has a self-attention layer, where every token gathers information from earlier tokens. Then comes a small feed-forward network (MLP) for each position. Shortcut connections (residuals) and normalisation keep the numbers stable.
  3. Output head: the final vector at the last position is multiplied by a matrix. This gives a raw score, a logit, for every vocabulary token. Softmax turns these scores into chances.
  4. Sampling: pick one token using those chances (see section 05). Add it, and repeat.

Training starts with "predict the next token" on trillions of tokens. This is called pre-training. Then comes instruction tuning and reinforcement learning from human and AI feedback. These steps teach the model to follow instructions, refuse harmful requests, and use tools. Nothing in that goal checks truth. That matters for hallucinations.

04Attention

Here is a sentence from a contract.

"The Supplier shall indemnify the Customer, and it shall pay within 30 days."

To understand it, you look back and find "the Supplier". The model must do the same. Attention is how it looks back. Think of a student in class who hears "it" and glances back at the notes to see what "it" means.

Each row adds up to 1. The −∞ cells are the causal mask. It hides later tokens, so a token cannot peek at the future. The last row is the script's real output. 63% of what "indemnify" gathers comes from "Supplier".

Query (Q)

What this token is looking for. For example, "who is doing this?"

Key (K)

The label each token shows to others. For example, "I am a party name."

Value (V)

The information a token hands over if it is chosen.

Java analogy

A fuzzy HashMap. Compare the query with every key. Return a blend of all values, weighted by how well each key matched.

Scaled dot-product attention

Attention(Q, K, V) = softmax(Q·Kᵀ / √d_k) · V

  • Q·Kᵀ: multiply each query with each key. This gives a relevance score for every pair of tokens. For n tokens, that is an n × n table.
  • / √d_k: divide by the square root of the key length. Without this, scores grow as vectors get longer. Then softmax gives almost all weight to one token, and training stalls because the learning signal (the gradient) gets tiny.
  • softmax: turn each row of scores into weights that add up to 1.
  • · V: blend the value vectors using those weights. The blend is the token's new meaning.
  • In a GPT-style model (a decoder), a causal mask sets future scores to −∞. So token i only sees tokens up to i.
Go deeper: attention in prose

Take the same sentence again. The model needs to know that it means the Supplier. Attention lets the vector for it look back at every earlier token. It scores how relevant each one is. Then it pulls in a weighted mix of their information.

Java analogy: a soft HashMap lookup. A normal map needs an exact key match and returns one value. Here, the query is compared with every key. You get a weighted average of all values, weighted by how similar each key is.

Multi-head attention runs this several times side by side. Each copy, called a head, uses its own learned settings. One head may track grammar. Another may track which word "it" refers to. The results are then joined together.

The cost is the n × n score table. Attention work grows with the square of the text length, written O(n²). Double the text, and the work is four times bigger. That is why long inputs are expensive. It is also why so much engineering goes into making them cheaper.

05Embeddings and sampling

An embedding model turns a whole text into one list of numbers, for example 1,024 numbers. Think of it as GPS coordinates for meaning. Texts about the same thing land close together on the map. This is a separate model from the chat model. Anthropic points to Voyage AI for this, such as voyage-4, or voyage-law-2 for legal text. RAG uses it to find the document pieces whose numbers are closest to the question's numbers.

To measure "close", we use cosine similarity. It checks whether two arrows point the same way. The formula is cos(a, b) = (a · b) / (‖a‖ × ‖b‖). The result runs from −1 (opposite) through 0 (unrelated) to 1 (same direction). Below is a toy example with just three dimensions: liability, termination and payment.

Dot product0.72 + 0.02 + 0.02 = 0.760.09 + 0.09 + 0.04 = 0.22

Cosine ignores length and looks only at direction. Voyage vectors already have length 1. For such vectors, cosine equals the plain dot product. It also ranks results the same way as straight-line (Euclidean) distance.

Sampling: temperature, top-k, top-p

The model gives every token a chance. Sampling is how it picks one. Think of a weighted lucky draw. "shall" has the most tickets, but "may" can still win. These settings change how the tickets are handed out.

Temperature T

A randomness dial. Below 1, the top guess wins more often. Above 1, choices spread out. Near 0, it always picks the top token. Formula: p_i = exp(z_i / T) / Σ exp(z_j / T).

Top-k

Keep only the k most likely tokens. Rescale their chances to add up to 1. Then pick.

Top-p (nucleus)

Keep the fewest top tokens whose chances add up to p. The set is tiny when the model is sure, larger when unsure.

Current Claude models

Sonnet 5.5 and Opus 5.5 accept only the default temperature and top_p. Steer them instead with instructions, examples, structured outputs and the effort setting.

Go deeper: embeddings and sampling in prose

An embedding model turns a whole piece of text into one fixed-length vector, for example 1,024 numbers. Texts with similar meaning land close together. This is a different model from the chat model. Anthropic does not make one. It points to Voyage AI, for example voyage-4, or voyage-law-2 for legal text. RAG stores an embedding for every document piece. Then it finds the pieces closest to the question's embedding.

Cosine ignores length. So a short clause and a long clause about the same thing still match. Some vectors are scaled to length 1, and Voyage embeddings are. For those, cosine equals the plain dot product. It also gives the same ranking as Euclidean distance. So databases can use the cheaper calculation.

The model outputs raw scores (logits). Sampling decides which token to write.

  • Temperature T divides the scores before softmax: p_i = exp(z_i / T) / Σ exp(z_j / T). T below 1 makes the top choice stronger, so output is more predictable. T above 1 spreads the chances, so output varies more and has more mistakes. As T gets close to 0, it becomes greedy decoding, which always picks the top token.
  • Top-k keeps only the k most likely tokens. It rescales their chances, then picks one.
  • Top-p (nucleus) keeps the smallest group of top tokens whose chances add up to p. Then it picks one. It adapts. When the model is confident, the group is tiny. When unsure, it is larger.

The table above uses numbers from the hands-on script below. The scores are shall=3.0, may=2.0, must=1.5, banana=−2.0.

On the newest Claude models, Sonnet 5.5 and Opus 5.5, temperature and top_p are deprecated. Only the default is accepted. The current Python SDK does not even offer them on messages.create. Older models such as Haiku 4.5 accepted them. Know the ideas for interviews. In production, control behaviour with instructions, examples, structured outputs and the effort setting.

One more point: temperature 0 never promised identical outputs. GPUs process many requests together, and tiny rounding differences can change the result.

06KV cache and hallucinations

The KV cache is the model's scratch notes. Each earlier token's key (K) and value (V) is worked out once and saved. Later steps reuse the notes instead of redoing the work. The catch is that the notes take a lot of GPU memory.

≈ 0.5 MiBKV cache per token, 7B-class, fp16
2 GiBfor one 4,096-token sequence
O(n²)attention compute in sequence length

Prefill

  • Reads the whole prompt at once and fills the cache.
  • Decides how long you wait for the first word (time to first token).

Decode

  • Writes one token per step and reuses the cache.
  • Limited by memory speed. Decides how many tokens per second you get.

Why hallucinations happen

Wrong goal

It was trained to write a likely next token, not a true statement. A smooth, wrong answer scores well.

Fuzzy memory

Rare facts, like clause 12.1 of one contract, are stored poorly. The model fills the gap with a likely pattern.

Cutoff, no private data

It knows nothing after its training date, and nothing of your data. Unless you put it in the prompt.

Errors compound

One wrong token steers every token after it.

Eager to help

Training pushes it to answer instead of saying "I don't know". Unless you allow that answer.

Mitigations
  • Give it the real document text. Ask it to cite the id of each piece it used.
  • Clearly allow the answer "not found in the document".
  • Check structured outputs with code. Verify with a second pass or a tool.
  • Measure correctness on a fixed test set. Design so wrong answers are easy to spot.
Go deeper: KV cache and hallucinations in prose

Say the model is writing token 501. Attention needs the keys and values of tokens 1–500. Those do not change. So the server computes them once and keeps them in GPU memory. That store is the KV cache. Each new token then computes only its own Q, K and V, and reads the rest from the cache. Without it, every step would redo the whole prefix. The work per token would grow with the square of the length.

This gives two phases. Prefill reads the whole prompt in parallel and fills the cache. It decides the time to the first token. Decode writes one token at a time and is limited by memory speed. It decides tokens per second.

Memory estimate: 2 (K and V) × layers × kv_heads × head_dim × bytes per value × tokens. Take a 7B-class model (7 billion settings) with 32 layers and 32 heads of size 128. Use fp16, which stores each number in 2 bytes. Then 2 × 32 × 32 × 128 × 2 = 524,288 bytes, about 0.5 MiB per token. So one 4,096-token request needs 2 GiB, and every request running at the same time needs its own.

This is why long inputs are costly to serve. It is also why tricks like grouped-query attention exist; it uses fewer KV heads. Provider-side prompt caching is the same idea sold as a product. A repeated start of a prompt skips prefill, so it is cheaper and faster.

  • The training goal is "a likely next token", not "a true statement". A smooth, confident, wrong answer scores well on that goal.
  • Knowledge is squeezed into the model's weights. Rare facts are stored poorly or not at all. An example is one clause number in one contract. The model fills the gap with the most likely pattern.
  • The model has a training cutoff date. It cannot see your private data unless you put it in the prompt.
  • Sampling can pick a less likely, wrong token. Every later token builds on it, so errors compound.
  • Instruction tuning rewards being helpful. That can push the model to answer rather than say "I don't know", unless told it may.

Ways to reduce it:

  • Ground answers in fetched document text (RAG). Require citations to the piece ids.
  • Clearly allow "not found in the document".
  • Check structured outputs with code.
  • Verify claims with a second pass or a tool.
  • Measure faithfulness on a golden set, a fixed list of questions with known right answers.

You cannot get hallucination down to zero. You design so that wrong answers are easy to detect.

07RAG vs fine-tuning, BERT vs GPT

There are two ways to make a model know your stuff. RAG is an open-book exam: you hand it the right pages each time. Fine-tuning is extra coaching: you change the model itself with your examples. Open book is better for facts. Coaching is better for habits like tone and format.

RAG usual pick

  • Works for private documents that change. Gives citations. Each customer sees only their own files.
  • To update, just re-index the documents.

Use it for knowledge.

Fine-tune / LoRA

  • Teaches format, tone, or one narrow high-volume task. A small model can then match a big one.
  • A poor way to add facts, and you cannot check where an answer came from.

Use it for behaviour.

Senior framing: start with a good prompt. Add RAG for knowledge. Use fine-tuning or LoRA only for behaviour. Do it only when tests prove it helps.

Fine-tuning changes the model's weights using your examples. Weights are the millions of numbers the model learned. Full fine-tuning changes all of them. That is expensive, and each variant is a full copy of the model.

LoRA (low-rank adaptation) is the cheap version. It freezes the original weights. It learns small extra matrices that are added to some layers. In maths terms, a weight change ΔW is approximated as B·A. A and B are thin matrices of rank r, say 8 or 16. So you train well under 1% of the parameters. You can swap these small add-ons per task.

RAG changes nothing in the model. It puts the relevant documents into the prompt at question time.

Senior framing: start with prompting. Add RAG for knowledge. Add fine-tuning only for behaviour you cannot get any other way. And only once you have a test set to prove it helped. They also combine: a LoRA-tuned model can still use RAG.

The original transformer had both an encoder and a decoder, and T5 does too. It was built for translation. The encoder reads the source sentence. The decoder writes the translation while looking at it. A RAG system often uses both families. Encoder models make embeddings and re-rank results. A decoder model writes the answer.

Common mistakes
  • Guessing token counts from characters across model versions, instead of counting them.
  • Thinking "the window is 1M tokens, so I can skip search."
  • Setting temperature to 0 and expecting the exact same output every time.
  • Fine-tuning to teach facts.
  • Forgetting the √d_k or the causal mask when writing attention.

08Hands-on: compute it yourself

Cosine similarity

Show cosine.py
import math


def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))


# Toy 3-d "embeddings": dimensions loosely mean (liability, termination, payment)
query = [0.9, 0.1, 0.2]       # "cap on damages"
liability = [0.8, 0.2, 0.1]   # limitation of liability clause
termination = [0.1, 0.9, 0.2] # termination for convenience clause

print(f"query·liability   = {cosine(query, liability):.3f}")
print(f"query·termination = {cosine(query, termination):.3f}")
assert cosine(query, liability) > cosine(query, termination)
assert abs(cosine(liability, [2 * x for x in liability]) - 1.0) < 1e-12  # length does not matter

Temperature and top-p

Show sampling.py
import math


def softmax(logits: list[float], temperature: float = 1.0) -> list[float]:
    scaled = [l / temperature for l in logits]
    m = max(scaled)
    exps = [math.exp(s - m) for s in scaled]
    total = sum(exps)
    return [e / total for e in exps]


def top_p_filter(probs: dict[str, float], p: float) -> dict[str, float]:
    kept, cum = {}, 0.0
    for tok, pr in sorted(probs.items(), key=lambda kv: kv[1], reverse=True):
        kept[tok] = pr
        cum += pr
        if cum >= p:
            break
    z = sum(kept.values())
    return {t: v / z for t, v in kept.items()}


tokens = ["shall", "may", "must", "banana"]
logits = [3.0, 2.0, 1.5, -2.0]
for t in (0.2, 1.0, 2.0):
    print(f"T={t}:", {tok: round(p, 3) for tok, p in zip(tokens, softmax(logits, t))})
probs = dict(zip(tokens, softmax(logits, 1.0)))
print("top_p=0.9:", {k: round(v, 3) for k, v in top_p_filter(probs, 0.9).items()})
assert softmax(logits, 0.2)[0] > softmax(logits, 1.0)[0] > softmax(logits, 2.0)[0]
assert "banana" not in top_p_filter(probs, 0.9)

Expected output:

T=0.2: {'shall': 0.993, 'may': 0.007, 'must': 0.001, 'banana': 0.0}
T=1.0: {'shall': 0.626, 'may': 0.23, 'must': 0.14, 'banana': 0.004}
T=2.0: {'shall': 0.463, 'may': 0.281, 'must': 0.219, 'banana': 0.038}

The code subtracts the biggest score before calling exp. This stops the numbers from getting too large to store. It does not change the result.

Attention on three tokens

Show attention.py
import math


def softmax(xs: list[float]) -> list[float]:
    m = max(xs)
    e = [math.exp(x - m) for x in xs]
    s = sum(e)
    return [v / s for v in e]


def attention(Q, K, V):
    """softmax(Q K^T / sqrt(d_k)) V for small lists of row vectors."""
    d_k = len(K[0])
    out = []
    for q in Q:
        scores = [sum(a * b for a, b in zip(q, k)) / math.sqrt(d_k) for k in K]
        w = softmax(scores)
        out.append([sum(wi * v[j] for wi, v in zip(w, V)) for j in range(len(V[0]))])
        print("weights:", [round(x, 3) for x in w])
    return out


# 3 tokens: "Supplier", "shall", "indemnify". Query = the token "indemnify" asking "who?"
K = [[1.0, 0.0], [0.0, 1.0], [0.2, 0.2]]
V = [[10.0, 0.0], [0.0, 1.0], [1.0, 1.0]]
Q = [[2.0, 0.1]]
print("output:", [[round(x, 2) for x in row] for row in attention(Q, K, V)])

The query points the same way as the first key. So 63% of the output comes from the first token's value. Change Q to [[0.1, 2.0]], and the weight moves to "shall".

09How this shows up in interviews

Explain how an LLM generates a response, end to end.

First, the input is split into token ids. Each id becomes an embedding vector, with its position added. The vectors pass through stacked transformer blocks. Each block has causal self-attention (look back at earlier tokens) and an MLP, with residual shortcuts. The last position becomes logits, one score per vocabulary token. Softmax turns them into chances, and one token is sampled. It is added to the text, and the loop repeats. It stops at an end token, a stop sequence, or max_tokens. Prefill reads the prompt in parallel and fills the KV cache. Decode then makes one token per step using that cache.

Write the attention formula and explain each term.

The formula is softmax(QKᵀ/√d_k)V. Q, K and V are learned projections of the token vectors: query, key and value. QKᵀ gives a relevance score for each pair of tokens. Dividing by √d_k keeps the spread of scores stable, so softmax does not saturate. Softmax turns each query's scores into weights that add up to 1. Multiplying by V blends the value vectors. Decoders add a causal mask to hide future tokens. Multi-head attention runs several of these side by side. The cost is O(n²) in sequence length.

What is a token, and why does it matter to you as an engineer?

A token is a piece of a word from the tokenizer's vocabulary. It is about 4 characters of English. Cost, rate limits, context limits and speed are all measured in tokens. Non-English text and code use more tokens. Tokenizers change between model versions. So measure with a token counter instead of guessing from characters.

What does temperature do? What about top-p and top-k?

Temperature scales the logits before softmax. Lower makes the output sharper and more predictable. Higher makes it flatter and more varied. Top-k keeps the k most likely tokens. Top-p keeps the smallest set whose chances add up to p. Use low randomness for extraction and classification. Also mention that the newest Claude models fix these at the default. So you steer with prompts, structured output and effort instead.

What is the KV cache and what does it cost?

It stores the keys and values of earlier tokens. So each decode step computes only the new token. Memory per request is 2 × layers × KV heads × head size × bytes × tokens. That is about 0.5 MiB per token for a 7B-class model in fp16. This limits how many requests and how much context fit on one GPU. Grouped-query attention and compressed (quantised) caches reduce it. Prompt caching reuses it across requests.

Why do LLMs hallucinate and how do you reduce it?

They are trained to write likely text, not true text. They store facts in a lossy way. They have a training cutoff. And they are rewarded for being helpful. Reduce it with grounding in fetched documents and citations. Allow the answer "not found". Use structured outputs and validate them. Add checking steps. Measure faithfulness on an evaluation set. You manage hallucination; you cannot remove it.

RAG or fine-tuning for a contract Q&A product?

RAG. The knowledge is private and separate per tenant (customer). It changes daily. Answers need citations and access control. Fine-tuning would freeze one snapshot of the data into the weights. It cannot enforce per-tenant permissions, and it still hallucinates. Use fine-tuning or LoRA later, only for behaviour. One example is a cheaper model for clause classification. Do it once an eval set shows the gain.

What is LoRA and why is it popular?

LoRA means low-rank adaptation. It freezes the base weights and learns a small update ΔW = B·A on chosen layers. It trains only a tiny fraction of the parameters. It needs far less GPU memory. The adapters are small files. You can swap them per task or per tenant on one base model.

BERT vs GPT?

BERT is an encoder. Its attention looks both ways, and it is trained by masked language modelling (hide words and guess them). It produces vectors used for classification, name finding (NER), embeddings and re-ranking. GPT is a decoder. Its attention looks only backward, and it is trained to predict the next token. It writes text. In RAG, encoder-style models embed and re-rank, and a decoder writes the answer.

What are embeddings and why cosine similarity?

Embeddings are fixed-length vectors from an embedding model. Similar meaning becomes physical closeness. Cosine measures the angle between two vectors and ignores their length. So it compares meaning, not text length. On normalised vectors (length 1), it equals the dot product. It then ranks the same as Euclidean distance.

Estimate the monthly cost of a feature doing 100k requests a day.

Multiply tokens per request by the price. Take 6,000 input and 500 output tokens on Sonnet 5.5. That is $0.012 + $0.005 = $0.017 per request. It is $1,700 per day, about $51,000 per 30-day month. Then name the levers. Use Haiku for easy questions. Send fewer chunks. Use prompt caching. Use batch for offline work. Keep outputs short.

If the context window is 1M tokens, why not skip RAG and send everything?

You pay for every input token on every call. Speed drops as input grows. Details in very long inputs get missed more. And you still need per-user access control on what goes in. For a small, stable set of documents, putting it all in a cached prompt is a fair design. Anthropic's guidance says "small" means under about 200k tokens. For many tenants and thousands of contracts, use retrieval.

10Quick check

In attention, why do we divide by √d_k?

Softmax makes the weights add up to 1. The causal mask hides the future. The division keeps the scores in a steady range. Without it, softmax puts nearly all weight on one token, and training signals become tiny.

On Sonnet 5.5, a request has 6,000 input tokens and 500 output tokens. What does it cost?

Input is 6,000 × $2/1M = $0.012. Output is 500 × $10/1M = $0.005. Together that is $0.017. $0.0085 is the Haiku 4.5 price.

What work does the KV cache save while writing tokens?

The keys and values of earlier tokens never change. So each step only computes Q, K and V for the new token.

A contract Q&A product must answer each customer from their own documents, with citations. The documents change daily. What fits best?

With RAG you re-index instead of retraining. You can cite the exact pieces. And you check each customer's access at search time.

At T = 0.2, "shall" has a 0.993 chance. At T = 2.0 its chance is…

A higher temperature divides the scores by a bigger number. That spreads the chances out to less likely tokens.

12Cheat sheet

Cheat sheet
  • One token is about 4 English letters. Indian scripts and code cost more. Opus 4.7 and later make about 30% more tokens. Use count_tokens.
  • Price per million tokens, input then output: Haiku 4.5 is $1 and $5, Sonnet 5.5 is $2 and $10, Opus 5.5 is $4 and $20. Cache reads cost 10%. Batch is 50% off.
  • Loop: tokenise → embed + position → N × (attention + MLP) → logits → softmax → sample → append.
  • Attention is softmax(QKᵀ/√d_k)·V, with a causal mask and multiple heads. Cost grows as O(n²).
  • Cosine = a·b / (‖a‖‖b‖). On vectors of length 1, it equals the dot product.
  • Temperature sharpens or flattens the chances. Top-k keeps a fixed count. Top-p keeps tokens until their chances add up to p. Both are fixed at the default on Sonnet and Opus 5.5.
  • KV cache memory is 2 × layers × kv_heads × head_dim × bytes × tokens. Prefill sets the time to first token (TTFT). Decode sets tokens per second.
  • Hallucination comes from training for likely text. Ground it, cite sources, allow "not found", validate, and test.
  • Use RAG for knowledge and fine-tuning or LoRA for behaviour. BERT reads and encodes. GPT writes.
