02Concepts explained from scratch

2.1 Tokens and tokenisation

Models do not see characters or words. A tokenizer splits text into tokens from a fixed vocabulary (typically tens of thousands to a few hundred thousand entries) built with an algorithm like byte-pair encoding (BPE): start from bytes, repeatedly merge the most frequent adjacent pair, stop at the target vocabulary size. Common words become one token, rare words split into pieces (indemnification may be three or four tokens), and every token maps to an integer id. Think of it as a compression dictionary, similar to how a ZIP dictionary is learned from frequent byte sequences.

  • Rule of thumb for English: about 4 characters or 0.75 words per token. A 20-page contract of 8,000 words is roughly 10,000–11,000 tokens.
  • Non-English text, code, numbers and unusual formatting use more tokens per character. Hindi and other Indic scripts often cost several times more tokens than the same meaning in English.
  • Tokenizers differ between model generations. Claude Opus 4.7 and later models use a newer tokenizer that produces about 30% more tokens for the same text, so recount when you migrate rather than reusing old numbers. The API has a free count_tokens endpoint for exactly this.
  • Tokenisation explains classic failures: counting letters in a word or reversing strings is hard because the model never saw individual letters.

2.2 Context window

The context window is the maximum number of tokens the model can attend to in one request: system prompt + all messages + tool definitions + the output it generates. Claude Sonnet 5.5 and Opus 5.5 (and other 4.6-and-later models) have a 1M-token context window at standard pricing; Haiku 4.5 has 200k. max_tokens caps the output part, and on Sonnet 5.5 its maximum is 128,000.

A big window is not free memory. You pay for every input token on every call, latency grows with input length, and models attend less reliably to facts buried in the middle of very long inputs. That is why retrieval still matters even with 1M tokens: you send the 5 relevant clauses, not 300 contracts.

2.4 How a transformer generates text

A GPT-style model is a function: given a sequence of token ids, output a probability distribution over the vocabulary for the next token. Generation is a loop around that function.

Text"The Supplier shall"→ Tokenizerids [464, 30092, 4093]→ Embeddings+ positions→ N transformer blocksattention + MLP→ Logitsone score per vocab entry→ Samplenext token↺

Figure: autoregressive decoding. The sampled token is appended and the loop runs again until an end token, a stop sequence, or max_tokens. Token ids are illustrative.

  1. Embedding: each token id is looked up in a learned table to get a vector (thousands of dimensions). Position information is added so the model knows order.
  2. Transformer blocks (dozens of them, stacked): each block has a self-attention layer, where every token gathers information from earlier tokens, followed by a feed-forward network (MLP) applied to each position, with residual connections and normalisation around both.
  3. Output head: the final vector at the last position is multiplied by a matrix to get a logit (score) for every vocabulary token. Softmax turns logits into probabilities.
  4. Sampling: pick one token from that distribution (see 2.6), append it, repeat.

Training is "predict the next token" on trillions of tokens (pre-training), then instruction tuning and reinforcement learning from human and AI feedback to make the model follow instructions, refuse harmful requests and use tools. Nothing in that objective checks truth, which matters for hallucinations.

2.5 Attention, intuitively and exactly

Intuition: in "The Supplier shall indemnify the Customer, and it shall pay within 30 days", to process it the model needs to know it refers to the Supplier. Attention lets the vector for it look back at every earlier token, score how relevant each is, and pull in a weighted mix of their information.

Each token's vector is projected by three learned matrices into:

  • Query (Q): what this token is looking for ("who is the subject?").
  • Key (K): what each token offers as a label ("I am a party name").
  • Value (V): the information each token passes on if selected.

Java analogy: a soft HashMap lookup. Instead of an exact key match returning one value, the query is compared with every key, and you get a weighted average of all values, weighted by similarity.

Scaled dot-product attention

Attention(Q, K, V) = softmax(Q·Kᵀ / √d_k) · V

  • Q·Kᵀ: dot product of each query with each key = relevance scores (an n × n matrix for n tokens).
  • / √d_k: divide by the square root of the key dimension so scores do not grow with dimension and push softmax into saturation (tiny gradients).
  • softmax: turn each row of scores into weights that sum to 1.
  • · V: weighted sum of value vectors = the new representation of each token.
  • In a decoder (GPT), a causal mask sets scores for future positions to −∞ so token i only sees tokens ≤ i.

Multi-head attention runs this several times in parallel with different learned projections (one head may track syntax, another coreference), then concatenates the results. The cost is the n × n score matrix: attention is O(n²) in sequence length for compute, which is why long contexts are expensive and why so much engineering goes into making them cheaper.

2.6 Embeddings and cosine similarity

An embedding model maps a whole piece of text to one fixed-length vector (for example 1,024 numbers) such that texts with similar meaning land close together. This is a different model from the chat model; Anthropic does not ship one and points to Voyage AI (for example voyage-4, or voyage-law-2 for legal text). RAG stores chunk embeddings and finds the chunks nearest to the question's embedding.

Closeness is usually measured with cosine similarity, the cosine of the angle between two vectors:

cos(a, b) = (a · b) / (‖a‖ × ‖b‖), ranging from −1 (opposite) through 0 (unrelated) to 1 (same direction).

Worked example with toy 3-dimensional vectors whose dimensions loosely mean (liability, termination, payment):

Stepquery = [0.9, 0.1, 0.2] vs liability = [0.8, 0.2, 0.1]query vs termination = [0.1, 0.9, 0.2]
Dot product0.72 + 0.02 + 0.02 = 0.760.09 + 0.09 + 0.04 = 0.22
‖query‖√0.86 = 0.9270.927
‖other‖√0.69 = 0.831√0.86 = 0.927
Cosine0.76 / 0.770 = 0.9870.22 / 0.86 = 0.256

Cosine ignores length, so a short clause and a long clause about the same thing still match. If vectors are normalised to length 1 (Voyage embeddings are), cosine equals the plain dot product and gives the same ranking as Euclidean distance, so databases can use the cheaper operation.

2.7 Sampling: temperature, top-k, top-p

The model outputs logits; sampling decides which token to emit.

  • Temperature T divides the logits before softmax: p_i = exp(z_i / T) / Σ exp(z_j / T). T < 1 sharpens the distribution (more deterministic); T > 1 flattens it (more varied, more mistakes). T → 0 approaches greedy decoding (always the top token).
  • Top-k keeps only the k most likely tokens, renormalises, then samples.
  • Top-p (nucleus) keeps the smallest set of top tokens whose cumulative probability reaches p, then samples. It adapts: when the model is confident the set is tiny, when unsure it is larger.

2.8 The KV cache

When generating token 501, attention needs the keys and values of tokens 1–500. They do not change, so the server computes them once and keeps them in GPU memory: the KV cache. Each new token then computes only its own Q, K, V and attends to the cached K and V. Without it, every step would recompute the whole prefix and generation would be quadratic per token.

Two phases follow from this: prefill (process the whole prompt in parallel, fill the cache; this drives time to first token) and decode (one token at a time, memory-bandwidth bound; this drives tokens per second).

Memory estimate: 2 (K and V) × layers × kv_heads × head_dim × bytes per value × tokens. For a 7B-class model with 32 layers, 32 heads of dimension 128, in fp16: 2 × 32 × 32 × 128 × 2 = 524,288 bytes ≈ 0.5 MiB per token, so a 4,096-token sequence needs 2 GiB, per concurrent request. This is why serving long contexts is expensive and why techniques like grouped-query attention (fewer KV heads) exist. Provider-side prompt caching is the same idea exposed as a product: a reused prompt prefix skips prefill, so it is cheaper and faster.

2.9 Why hallucinations happen

  • The training objective is "plausible next token", not "true statement". A fluent, confident, wrong answer scores well on that objective.
  • Knowledge is compressed into weights. Rare facts (a specific clause number in a specific contract) are stored poorly or not at all, and the model fills the gap with the most likely pattern.
  • The model has a training cutoff and no access to your private data unless you put it in the context.
  • Sampling can pick a lower-probability wrong token, and once emitted, later tokens are conditioned on it (errors compound).
  • Instruction tuning rewards helpfulness, which can push the model to answer rather than say "I don't know" unless told it may.

Mitigations: ground answers in retrieved text (RAG) and require citations to chunk ids, explicitly allow "not found in the document", validate structured outputs, verify claims with a second pass or tool, and measure faithfulness on a golden set. You cannot drive hallucination to zero; you design so that wrong answers are detectable.

2.10 RAG vs fine-tuning vs LoRA

Fine-tuning updates model weights on your examples. Full fine-tuning updates all weights (expensive, a full model copy per variant). LoRA (low-rank adaptation) freezes the base weights and learns small low-rank matrices added to some layers: a weight update ΔW is approximated as B·A, where A and B are thin matrices of rank r (say 8 or 16), so you train well under 1% of the parameters and can swap adapters per task. RAG changes nothing in the model; it puts relevant documents into the prompt at query time.

Senior framing: start with prompting, add RAG for knowledge, add fine-tuning only for behaviour you cannot get otherwise, and only once you have an evaluation set to prove it helped. They combine: a LoRA-tuned model can still use RAG.

2.11 BERT vs GPT: encoder vs decoder

BERT (encoder-only)GPT / Claude (decoder-only)
AttentionBidirectional: each token sees left and right contextCausal: each token sees only earlier tokens
Training objectiveMasked language modelling: predict hidden tokens in the middleNext-token prediction
OutputContextual vectors for each token / the whole inputGenerated text, one token at a time
Good atClassification, named-entity recognition, embeddings, rerankers (cross-encoders)Generation, instruction following, reasoning, tool use
Size and costSmall (around 100M–350M parameters for the classic models), cheap to run on CPUBillions of parameters, GPU serving

The original transformer was encoder–decoder (T5 also is), used for translation: the encoder reads the source, the decoder generates the target attending to it. In a RAG system you often use both families: encoder models for embeddings and reranking, a decoder model to write the answer.

03Hands-on: compute it yourself

All scripts below are pure Python standard library and run offline. Create a folder and run each with python3 file.py (or uv run).

Cosine similarity

import math


def cosine(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    return dot / (math.sqrt(sum(x * x for x in a)) * math.sqrt(sum(y * y for y in b)))


# Toy 3-d "embeddings": dimensions loosely mean (liability, termination, payment)
query = [0.9, 0.1, 0.2]       # "cap on damages"
liability = [0.8, 0.2, 0.1]   # limitation of liability clause
termination = [0.1, 0.9, 0.2] # termination for convenience clause

print(f"query·liability   = {cosine(query, liability):.3f}")
print(f"query·termination = {cosine(query, termination):.3f}")
assert cosine(query, liability) > cosine(query, termination)
assert abs(cosine(liability, [2 * x for x in liability]) - 1.0) < 1e-12  # length does not matter

Expected output:

query·liability   = 0.987
query·termination = 0.256

Temperature and top-p

import math


def softmax(logits: list[float], temperature: float = 1.0) -> list[float]:
    scaled = [l / temperature for l in logits]
    m = max(scaled)
    exps = [math.exp(s - m) for s in scaled]
    total = sum(exps)
    return [e / total for e in exps]


def top_p_filter(probs: dict[str, float], p: float) -> dict[str, float]:
    kept, cum = {}, 0.0
    for tok, pr in sorted(probs.items(), key=lambda kv: kv[1], reverse=True):
        kept[tok] = pr
        cum += pr
        if cum >= p:
            break
    z = sum(kept.values())
    return {t: v / z for t, v in kept.items()}


tokens = ["shall", "may", "must", "banana"]
logits = [3.0, 2.0, 1.5, -2.0]
for t in (0.2, 1.0, 2.0):
    print(f"T={t}:", {tok: round(p, 3) for tok, p in zip(tokens, softmax(logits, t))})
probs = dict(zip(tokens, softmax(logits, 1.0)))
print("top_p=0.9:", {k: round(v, 3) for k, v in top_p_filter(probs, 0.9).items()})
assert softmax(logits, 0.2)[0] > softmax(logits, 1.0)[0] > softmax(logits, 2.0)[0]
assert "banana" not in top_p_filter(probs, 0.9)

Expected output:

T=0.2: {'shall': 0.993, 'may': 0.007, 'must': 0.001, 'banana': 0.0}
T=1.0: {'shall': 0.626, 'may': 0.23, 'must': 0.14, 'banana': 0.004}
T=2.0: {'shall': 0.463, 'may': 0.281, 'must': 0.219, 'banana': 0.038}
top_p=0.9: {'shall': 0.629, 'may': 0.231, 'must': 0.14}

Subtracting the max logit before exp is the standard numerically stable softmax; it does not change the result.

Attention on three tokens

import math


def softmax(xs: list[float]) -> list[float]:
    m = max(xs)
    e = [math.exp(x - m) for x in xs]
    s = sum(e)
    return [v / s for v in e]


def attention(Q, K, V):
    """softmax(Q K^T / sqrt(d_k)) V for small lists of row vectors."""
    d_k = len(K[0])
    out = []
    for q in Q:
        scores = [sum(a * b for a, b in zip(q, k)) / math.sqrt(d_k) for k in K]
        w = softmax(scores)
        out.append([sum(wi * v[j] for wi, v in zip(w, V)) for j in range(len(V[0]))])
        print("weights:", [round(x, 3) for x in w])
    return out


# 3 tokens: "Supplier", "shall", "indemnify". Query = the token "indemnify" asking "who?"
K = [[1.0, 0.0], [0.0, 1.0], [0.2, 0.2]]
V = [[10.0, 0.0], [0.0, 1.0], [1.0, 1.0]]
Q = [[2.0, 0.1]]
print("output:", [[round(x, 2) for x in row] for row in attention(Q, K, V)])

Expected output:

weights: [0.63, 0.164, 0.206]
output: [[6.5, 0.37]]

The query aligns with the first key, so 63% of the output comes from the first token's value. Change Q to [[0.1, 2.0]] and watch the weight move to "shall". That is all attention is, repeated across heads, layers and thousands of dimensions.

04How this shows up in interviews

Explain how an LLM generates a response, end to end.

Tokenise the input into ids, embed them with positions, pass them through stacked transformer blocks (causal self-attention + MLP with residuals), project the last position to logits over the vocabulary, softmax, sample a token, append, repeat until an end token, stop sequence or max_tokens. Prefill processes the prompt in parallel and fills the KV cache; decode generates one token per step using the cache.

Write the attention formula and explain each term.

softmax(QKᵀ/√d_k)V. Q, K, V are learned projections of token vectors. QKᵀ gives pairwise relevance; dividing by √d_k keeps the variance of scores stable so softmax does not saturate; softmax makes weights per query that sum to 1; multiplying by V mixes the value vectors. Decoders add a causal mask. Multi-head runs several in parallel. Cost is O(n²) in sequence length.

What is a token, and why does it matter to you as an engineer?

A sub-word unit from the tokenizer vocabulary, roughly 4 characters of English. Cost, rate limits, context limits and latency are all in tokens. Non-English text and code cost more; tokenizers differ across model versions, so measure with a token counter rather than estimating from characters.

What does temperature do? What about top-p and top-k?

Temperature scales logits before softmax: lower is sharper and more deterministic, higher is flatter and more diverse. Top-k keeps the k most likely tokens; top-p keeps the smallest set whose cumulative probability reaches p. Use low randomness for extraction and classification. Mention that the newest Claude models fix these at the default, so you steer with prompts, structured output and effort instead.

What is the KV cache and what does it cost?

Cached keys and values of previous tokens so each decode step only computes the new token. Memory is 2 × layers × KV heads × head dim × bytes × tokens per sequence, about 0.5 MiB per token for a 7B-class fp16 model, which limits concurrency and context length on a GPU. Grouped-query attention and quantised caches reduce it; prompt caching reuses it across requests.

Why do LLMs hallucinate and how do you reduce it?

They are trained to produce plausible continuations, store facts lossily, have a cutoff, and are rewarded for helpfulness. Reduce it with retrieval grounding and citations, permission to answer "not found", structured outputs with validation, verification steps, and measuring faithfulness on an evaluation set. You manage it, you do not eliminate it.

RAG or fine-tuning for a contract Q&A product?

RAG: the knowledge is private, per-tenant, changes daily and answers need citations and access control. Fine-tuning would bake one snapshot of data into weights, cannot enforce per-tenant permissions, and still hallucinates. Fine-tune or LoRA later only for behaviour, for example a cheaper model for clause classification, once an eval set shows the gain.

What is LoRA and why is it popular?

Low-rank adaptation: freeze base weights and learn a low-rank update ΔW = B·A on selected layers. Trains a tiny fraction of parameters, needs far less GPU memory, and adapters are small files you can swap per task or tenant on one base model.

BERT vs GPT?

BERT is an encoder with bidirectional attention trained by masked language modelling; it produces representations for classification, NER, embeddings and reranking. GPT is a decoder with causal attention trained on next-token prediction; it generates text. In RAG, encoder-style models embed and rerank, a decoder writes the answer.

What are embeddings and why cosine similarity?

Fixed-length vectors from an embedding model where semantic similarity maps to geometric closeness. Cosine measures angle and ignores vector length, so it compares meaning rather than text length. On normalised vectors it equals the dot product and ranks the same as Euclidean distance.

Estimate the monthly cost of a feature doing 100k requests a day.

Tokens per request × price. For 6,000 input and 500 output on Sonnet 5.5: $0.012 + $0.005 = $0.017 per request, $1,700 per day, about $51,000 per 30-day month. Then name the levers: Haiku for easy queries, fewer chunks, prompt caching, batch for offline work, shorter outputs.

If the context window is 1M tokens, why not skip RAG and send everything?

You pay for every input token on every call, latency grows with input, recall of details in very long inputs degrades, and you still need per-user access control on what goes in. For a small, stable corpus (Anthropic's guidance is under about 200k tokens) putting it all in a cached prompt is a valid design; for many tenants and thousands of contracts, retrieve.
