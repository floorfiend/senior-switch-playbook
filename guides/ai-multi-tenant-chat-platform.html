Multi-tenant ChatGPT-style platform

Design a chat product that many organisations share: token-by-token streamed replies, saved and searchable conversations, editable messages, strict tenant isolation, per-tenant limits and cost, and failover across LLM providers. A senior answer separates generation from the connection, treats tokens as the unit of capacity and money, and makes provider failure a normal event.

01What the interviewer is grading

Tekion's Staff (AI) round, Sep 2026, gave the full prompt: users converse with an AI assistant, replies stream token by token, conversations are saved, users search their history, many tenants each with isolated data, and users can edit messages. Microsoft's SDE-2 AI-team loop split the same space into an LLD on caching to cut AI cost plus LLM observability, and an HLD to design an AI application and then evaluate the design. Emergent Labs turned provider failover into a machine-coding problem with exact thresholds.

Streaming done right

SSE vs WebSocket, what happens on disconnect, how a reply resumes, how "stop generating" works.

Conversation model

Edits create branches; context is the path from root to the current leaf; history is trimmed or summarised to fit the window.

Isolation and fairness

Tenant from the JWT, row-level isolation, per-tenant keys, token-based rate limits so one tenant cannot starve others.

Cost and reliability

Tokens per turn in rupees or dollars, caching layers, model tiering, multi-provider routing with a circuit breaker.

02Clarify and scope

  • Who are tenants? B2B organisations whose employees chat (like an enterprise ChatGPT). Do tenants bring their own system prompts, models or API keys?
  • Search scope? A user searches only their own conversations, or also shared ones? Keyword or semantic?
  • Edit semantics? Editing an earlier message regenerates from that point. Keep the old branch (ChatGPT does) or discard?
  • Attachments and tools? Files, web search, RAG over tenant docs? (Scope out, note the hook.)
  • Retention and residency? Per-tenant retention policy, region pinning, DPDP erasure.
  • Providers? One provider or several (Anthropic, OpenAI, a self-hosted model)? Failover allowed across providers for every tenant?

Functional

  • Create conversation, send message, stream reply
  • Stop, regenerate, edit (branching)
  • List conversations, full-text search history
  • Per-tenant config: models, system prompt, limits
  • Usage and cost reports per tenant

Non-functional

  • 2,000 tenants, 1M DAU, 15 messages/user/day
  • Time to first token p95 < 1.5 s (plus provider)
  • No lost messages; reply survives a dropped connection
  • 99.95% for send/stream; search can lag a few seconds
  • Zero cross-tenant reads

Out of scope

  • Training or hosting frontier models
  • Voice and image generation
  • Real-time multi-user shared chats

        "streamUrl": "/v1/messages/m_..C/stream" }

→ id: 42  event: delta  data: {"text":" the notice"}
→ id: 43  event: done   data: {"finish":"stop","usage":{"in":5980,"out":388}}

POST /v1/messages/{mid}/cancel                 # stop generating
POST /v1/messages/{mid}/edit                   { "content": "Summarise clause 14 instead" }
→ 202 { "userMessageId": "m_..D", "assistantMessageId": "m_..E", "streamUrl": "..." }

GET  /v1/search?q=termination+notice&cursor=..

Send and stream are separate calls, so a reconnect is just another GET with Last-Event-ID. The idempotency key makes a retried send return the same message ids instead of starting a second, billed generation. Event ids are per-message sequence numbers.

Status moves PENDING → STREAMING → COMPLETE | CANCELLED | FAILED. 06High-level architecture

Workers→message.completed Kafka→ Search indexerOpenSearch Usage consumerClickHouse Summariserasync

Figure: send path, token path and post-completion fan-out. The browser connection is never on the generation's critical path.

  • API gateway: validates JWT, derives tenant and user, applies request-per-minute limits and concurrent-stream caps.
  • Chat service: writes the user message and a PENDING assistant placeholder, then emits generation.requested through an outbox. Returns 202 immediately.
  • Generation workers: build the context (system prompt, summary, branch path, recent turns), call the LLM gateway with streaming, append each delta to the Redis stream, flush partial content to the DB every ~2 s, write the final message and emit message.completed.
  • LLM gateway: per-tenant token budget, model tiering, provider routing, circuit breaker, retries before the first token only, prompt-cache markers, usage metering. Spring AI's ChatClient.stream() returning Flux<ChatResponse> fits here; LiteLLM or Portkey are the off-the-shelf equivalents in Python land.
  • Stream service: stateless SSE endpoint on Netty; reads from the Redis stream after Last-Event-ID and blocks for new entries. Any node can serve any stream, so no sticky sessions.
  • Async consumers: search indexing, usage and cost, title generation, rolling summaries, eval sampling.

07Deep dives

7.1 Streaming that survives disconnects

OptionProsCons
Proxy provider stream straight to the clientSimplest, lowest latencyTab close or mobile network switch kills generation or loses tokens; the pod holding the stream is a single point
SSE + decoupled worker + Redis Streams (chosen)Resume with Last-Event-ID; multi-device viewing; generation completes even if user leavesOne more hop (~1–3 ms); Redis memory for in-flight streams
WebSocketBidirectional (cancel, typing, presence on one socket)Harder through proxies and load balancers, manual reconnect and resume protocol; overkill for one-way token flow

Memory check: 7,200 in-flight streams × ~3 KB of tokens = ~22 MB in Redis, trivial. Cancel sets cancel:{mid}; the worker checks between deltas, aborts the upstream HTTP call (which stops billing for further output), saves the partial with status CANCELLED and bills consumed tokens. SSE runs fine over HTTP/2, which removes the browser's six-connections-per-host limit.

7.2 Editing, branching and building the context

Messages form a tree through parent_id. Editing message B (parent A) creates a new user message B' with parent A, then a new assistant reply; conversation.current_leaf_id moves to the new leaf. Old branches stay so the user can flip between "1/2" and "2/2". The context for a turn is the path from the leaf to the root, which the worker reads with one partition scan and walks in memory.

Context-window management: budget = model window − max output − system prompt − tool schemas. Strategy:

  1. Keep the last N turns verbatim (most relevant, and cheap thanks to caching).
  2. When the path exceeds ~70% of the budget, an async job writes a rolling summary of older turns into conversation.summary and records summary_upto_id. Summaries advance in large steps so the cached prefix changes rarely.
  3. Optionally embed old turns and retrieve the few relevant ones ("as I said earlier about clause 14").
  4. Order the prompt as tools → system → summary → older turns → recent turns → new message, so the provider's prefix cache (Anthropic caches in the order tools, system, messages) hits on everything but the tail.

Spring AI's MessageWindowChatMemory (default 20 messages, keeps system messages) with JdbcChatMemoryRepository is the starter version; the branching tree and summaries are what you add on top.

7.3 Provider routing and the circuit breaker (Emergent Labs)

The question: all calls go to Claude; if Claude's error rate exceeds 5%, send 95% to OpenAI; if it exceeds 90%, fail fast except for 5% to Claude and 5% to OpenAI as probes. The interviewer pushed on how to pick the provider per request; the candidate landed on hashing the request id mod 100. That is deterministic percentage bucketing, the same trick as feature-flag rollouts: stateless across gateway nodes, no coordination, and a retry of the same request id lands in the same bucket.

public final class ProviderRouter {
    public enum Mode { HEALTHY, DEGRADED, FAILING }

    private final ErrorRateWindow claude;          // 60 one-second buckets of (ok, error) counters
    private final AtomicReference<Mode> mode = new AtomicReference<>(Mode.HEALTHY);

    public ProviderRouter(ErrorRateWindow claude) { this.claude = claude; }

    public Optional<Provider> route(String requestId) {
        int bucket = Math.floorMod(Hashing.murmur3_32_fixed().hashUnencodedChars(requestId).asInt(), 100);
        return switch (mode.get()) {
            case HEALTHY  -> Optional.of(Provider.CLAUDE);
            case DEGRADED -> Optional.of(bucket < 5 ? Provider.CLAUDE : Provider.OPENAI);
            case FAILING  -> bucket < 5 ? Optional.of(Provider.CLAUDE)
                           : bucket < 10 ? Optional.of(Provider.OPENAI) : Optional.empty(); // caller returns 503
        };
    }

    public void record(Provider p, boolean success) {
        if (p != Provider.CLAUDE) return;
        claude.record(success);
        if (claude.total() < 100) return;           // too few samples to judge
        double rate = claude.errorRate();
        Mode next = rate > 0.90 ? Mode.FAILING : rate > 0.05 ? Mode.DEGRADED
                  : rate < 0.02 ? Mode.HEALTHY : mode.get();   // hysteresis band 2–5% avoids flapping
        mode.set(next);
    }
}

Patterns to name: State (the three modes), Strategy (provider clients behind one LlmProvider interface), Decorator (retry and metering around a provider). In production, keep the window per provider and per model, count only provider faults (5xx, 429, timeouts, not 400s caused by bad prompts), share counters through Redis or accept per-node windows, and alert on mode changes. Resilience4j's CircuitBreaker gives you the window and state machine for the single-provider case.

Failover is not free

Prompts tuned for one model may behave differently on another; tool-call formats differ; tenants may have contracted for one provider or region only. Store per-tenant allowed providers, keep a prompt variant per provider, and run the golden eval set on the fallback model before enabling it. Retry only before the first token is sent; after that, the user has already seen part of a reply.

7.4 Per-tenant rate limits, budgets and cost attribution

  • Limits are in tokens per minute as well as requests, because one 100k-token request costs more than a thousand short ones. Also cap concurrent streams per user and per tenant.
  • Reserve before the call: estimated input tokens (tokeniser count) + max_tokens, taken atomically from a Redis token bucket via a Lua script. Reconcile after completion with actual usage and refund the difference.
  • Provider quotas are pooled across tenants; a weighted fair queue in the gateway gives each tenant a share proportional to plan so a burst from one tenant queues behind its own quota, not everyone's.
  • Every completion emits a usage event (tenant, user, feature, model, input, cached input, output, price-table version) to Kafka, then ClickHouse. Alerts at 80% of monthly budget; at 100% either hard-stop or downgrade to a cheaper model, per tenant policy.

7.5 Search across chat history

A Kafka consumer indexes completed messages into OpenSearch with routing=tenant_id; every query carries a mandatory filter on tenant_id and user_id built server-side. Edits mark superseded branches branch_active=false (searchable but ranked lower). Lag is seconds, which is acceptable. For semantic search add a k-NN vector field and fuse with BM25; for big tenants give them their own index so a noisy tenant does not affect relevance statistics or latency. Deleting a conversation deletes from the DB, index and caches in one saga, which the DPDP erasure path reuses.

7.7 Observability and evaluating the design

  • Traces (OpenTelemetry): gateway → chat service → worker → LLM call span with model, provider, input/cached/output tokens, TTFT, finish reason, cost. Use the GenAI semantic-convention attribute names so tools understand them.
  • Metrics: TTFT p50/p95, tokens/s, provider error and 429 rates, breaker mode, cache hit rate, queue depth, concurrent streams, cost per tenant per hour.
  • Prompt and response logs: sampled, PII-redacted, retained per tenant policy, access-audited.
  • Quality: offline golden conversations scored by LLM-as-judge (calibrated against human labels) before any model or prompt change; online regenerate rate, edit rate, thumbs-down rate, abandonment mid-stream; A/B by tenant cohort.
Guardrails

Prompt injection: tenant system prompts and uploaded files are untrusted; tools that write anything need user confirmation. PII and DPDP: detect and mask identifiers (Aadhaar, PAN, phone) before logging; in-region inference for tenants that need it; zero-retention provider terms; erasure across DB, index, caches and analytics; breach reporting to the Board without delay and in detail within 72 hours once the DPDP Rules' core obligations apply (13 May 2027). Tenant isolation: tenant id only from the JWT, RLS and mandatory filters, per-tenant keys, no shared caches, automated cross-tenant leak tests.

08Scaling, failure handling and consistency

  • First to break at 10×: provider rate limits and spend. Add providers and regions, more model tiering, bigger cache share; negotiate provisioned throughput.
  • Connections: 72k concurrent SSE streams at 10× is ~10–15 Netty nodes; scale on open connections, not CPU.
  • Worker crash mid-stream: the Kafka offset is committed only after the final write. Another worker picks the request up, sees status STREAMING with partial content, and either restarts generation (emitting a reset event so clients clear the partial) or marks it FAILED with a retry button. Never silently append a second generation to the first.
  • Duplicate sends: idempotency key unique per (tenant, user, key) returns the original ids.
  • Backpressure: when provider capacity is exhausted, queue with a short deadline and tell the user ("high demand, using a faster model") rather than time out.
  • Consistency: messages strongly consistent within a conversation (single partition); search and usage eventually consistent.
  • Multi-region: tenant pinned to a home region (data residency); active-passive per tenant with async replication; providers chosen per region.

10Follow-up questions interviewers asked

Why SSE and not WebSockets?

Tokens flow one way; the user's input is a normal POST. SSE is plain HTTP, works through corporate proxies, has built-in reconnect with Last-Event-ID, and multiplexes over HTTP/2. Choose WebSockets when you need frequent client-to-server messages on the same channel (collaborative editing, voice).

The user edits a message from ten turns ago. What happens to search, context and billing?

A new branch is created from that message's parent; context is the new path, so later turns from the old branch are excluded. Old-branch messages stay in search with branch_active=false. The regeneration is billed like any turn; prompt caching still helps because the prefix up to the edit point is unchanged.

How do you count tokens before calling the provider?

Use the provider's tokeniser or token-count endpoint for an estimate, reserve estimate + max_tokens from the budget, and reconcile with the usage block the provider returns at the end of the stream. Never trust a client-side count.

One tenant runs a script that sends 10,000 long prompts. What protects others?

Tenant TPM bucket rejects or queues beyond its quota, concurrent-stream cap per tenant, weighted fair queue in the gateway so provider capacity is shared by plan weight, and a budget hard stop. Alert the tenant admin.

Why hash the request id instead of random() < 0.95?

Both give the right proportions. Hashing is deterministic, so retries and debugging are reproducible, and you can pin a request or user to a provider across gateway nodes without shared state. Hash the user or conversation id instead if you want a whole conversation to stay on one provider for consistent style and cache hits.

How would you evaluate this design? (Microsoft)

Against the requirements: TTFT and availability SLOs measured end to end, cost per turn against target, isolation verified by leak tests, quality by golden set and online signals, and a failure-mode review (provider down, Redis down, worker crash, region loss) showing each has a defined behaviour.

Redis goes down. What breaks?

Live token streaming and rate limiting. Workers keep generating and flushing partials to the DB, so clients fall back to polling the message; rate limiting fails closed for heavy tenants or falls back to per-node local buckets. Run Redis with replicas and keep it off the durability path.

11Mistakes that got candidates rejected

Rejected for this
  • Tying generation to the HTTP connection, so a dropped network loses the reply.
  • Rate limiting only by requests; ignoring tokens and cost.
  • No tenant isolation story beyond "add tenant_id"; taking tenant id from the request.
  • Treating edits as overwrites, which breaks history and the context the model saw.
  • Sending the whole history every turn with no window management, then being unable to explain the bill.
  • In the Emergent machine-coding round: spending too long on the routing debate and leaving AI-generated code with bugs. Settle the bucketing quickly, then drive the code and test the thresholds.
