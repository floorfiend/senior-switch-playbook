Multi-tenant ChatGPT-style platform

Design one shared chat product, like ChatGPT, used by thousands of companies at once. Replies appear word by word. The design must keep working when a phone loses signal, when one company floods the system, and when an AI provider goes down.

Time-box: 45–60 min Seen: Tekion, Amazon, Uber, Microsoft in 2026. A circuit breaker was also asked as a machine-coding round.
TekionAmazonUberMicrosoftEmergent Labs
In 30 seconds
  • Keep writing the reply even if the browser disconnects. A background worker writes words into Redis, and the browser reads them from there.
  • Messages form a tree. Editing an old message starts a new branch instead of overwriting history.
  • Tokens (small chunks of text) decide both load and cost. So you limit and bill by tokens.
  • AI providers fail often. A circuit breaker moves traffic to a backup provider when errors rise.
Picture it

Think of a food court with token numbers. You place your order at the counter and get a token number. The kitchen keeps cooking whether or not you stand at the window. You can collect your food from any counter by showing your token number. In this design, the token number is the Last-Event-ID, and collecting is reconnecting to the stream.

Words you'll see
Tenant
One customer company using the shared platform. Each tenant's data must stay invisible to every other tenant.
Token
A small piece of text, roughly three-quarters of a word. AI providers count, limit and charge by tokens.
LLM
Large language model. The AI model, such as Claude or GPT, that writes the replies.
SSE
Server-Sent Events. A plain HTTP connection where the server keeps pushing small messages to the browser.
Redis Streams
An in-memory, append-only list in Redis. Readers can ask for "everything after item 41".
Circuit breaker
A switch that stops sending traffic to a failing service, so users fail fast instead of waiting.
Prompt caching
The provider remembers the start of a prompt it saw recently. Sending that same start again is about ten times cheaper.
TTFT
Time to first token. How long the user waits before the first word of the reply appears.

01What the interviewer is grading

Streaming done right

Can you choose between SSE and WebSocket? Can you handle disconnects, resuming the reply, and a "stop generating" button?

Conversation model

Edits create branches. The model sees the path from the first message to the latest one. Long history gets trimmed or summarised.

Isolation and fairness

The tenant comes from the login token (JWT). Use row-level security, a separate encryption key per tenant, and limits based on tokens.

Cost and reliability

Know the cost of one question and answer. Use caching and cheaper models where possible. Fail over between providers with a circuit breaker.

Go deeper: the Tekion, Microsoft and Emergent Labs prompts

Tekion asked this in its Staff (AI) round in Sep 2026. The full prompt had six parts. Users chat with an AI assistant, and replies stream word by word. Conversations are saved, and users can search their history. Many tenants share the system, each with isolated data. Users can also edit their messages.

Microsoft's SDE-2 loop for an AI team split the same topic into two rounds. The LLD (low-level design) round covered caching to cut AI cost, plus monitoring of LLM calls. The HLD (high-level design) round asked you to design an AI application and then evaluate your own design. Emergent Labs turned provider failover into a machine-coding problem with exact error thresholds.

Go deeper: full clarifying list, requirements and capacity table
  • Who are tenants? Businesses whose employees chat, like an enterprise ChatGPT. Do tenants bring their own system prompts, models or API keys?
  • Search scope? Does a user search only their own chats, or shared ones too? Is it keyword search or meaning-based (semantic) search?
  • Edit behaviour? Editing an earlier message regenerates the reply from that point. Do we keep the old branch, as ChatGPT does, or throw it away?
  • Attachments and tools? Files, web search, or RAG over tenant documents? RAG (retrieval-augmented generation) means looking up documents and adding them to the prompt. Keep these out of scope, but mention where they would plug in.

  • Providers? One AI provider or several, such as Anthropic, OpenAI or a self-hosted model? Is switching between providers allowed for every tenant?

03API and data model

  1. SendThe browser sends the message with a unique key, so a repeat send is not processed twice. It also says which message this one replies to. The server answers "accepted, we'll process it" (HTTP 202) with the new message ids and a link to read the reply. In the API: POST …/messages, Idempotency-Key, parentId, streamUrl.
  2. StreamThe browser opens a separate connection to read the reply as it is written. After a drop, it says the last piece it saw and gets the rest (GET /v1/messages/{mid}/stream with Last-Event-ID).
  3. ControlStop a reply, edit a message (this starts a new branch), switch to another branch, or search old chats.

A reply moves through these states: PENDING → STREAMING → COMPLETE | CANCELLED | FAILED. Message text is encrypted with a separate key per tenant. When a tenant leaves, you delete its key, and all its data becomes unreadable. This is called crypto-shredding.

Go deeper: send/stream split, data model table and storage choice

Sending and streaming are two separate calls. So reconnecting is just another GET with Last-Event-ID. The idempotency key is a unique id the client attaches to each send. If the client sends the same message again, it gets the same message ids back. That stops a second, separately billed reply. Event ids are simple counters within each message.

A reply moves through PENDING → STREAMING → COMPLETE | CANCELLED | FAILED. Each tenant's content is encrypted with its own data key. That key is itself protected by a master key in KMS (a key management service). This is called envelope encryption. When a tenant leaves, deleting its key makes the data unreadable (crypto-shredding).

Discord moved trillions of messages to Cassandra and then to ScyllaDB. It stores messages grouped by channel, and that is the model for grouping by conversation here. At this guide's 16 TB per year, Postgres is also fine if you split it across servers. It is simpler if the team already knows it.

The key idea: the browser's connection never controls the reply. If the browser leaves, the reply still gets written.

Go deeper: each component's job
  • API gateway: checks the JWT and reads the tenant and user from it. It limits requests per minute (RPM) and how many streams one user can have open.
  • Chat service: saves the user's message and an empty PENDING slot for the reply. It then publishes a generation.requested event through an outbox table, so the event is never lost. It answers 202 (accepted) at once.
  • Generation workers: build the context, which is the system prompt, the summary, the branch path and recent turns. They call the LLM gateway and receive the reply piece by piece. Each piece (a delta) goes into the Redis stream. Every ~2 s they save the partial text to the database. At the end they save the full message and publish message.completed.
  • LLM gateway: one place for all provider calls. It enforces each tenant's token budget and picks the model and provider. It also runs the circuit breaker and marks prompts for caching. It retries only before the first token arrives, and it records usage.
  • LLM gateway libraries: in Spring AI, ChatClient.stream() returns a Flux<ChatResponse>, which fits here. LiteLLM or Portkey are ready-made gateways from the Python world.
  • Stream service: a stateless SSE endpoint on Netty. It reads the Redis stream after Last-Event-ID and waits for new entries. Any server can serve any stream, so the user need not return to the same server (no sticky sessions).
  • Background consumers: search indexing, usage and cost, chat titles, rolling summaries, and sampling replies for quality checks.

06Deep dives

6.1 Streaming that survives disconnects

SSE + worker + Redis Streams chosen

  • Resume with Last-Event-ID. Watch the same reply on two devices.
  • The reply finishes even if the user leaves
  • One extra network hop (~1–3 ms)

When text flows only from server to browser (almost always).

WebSocket

  • Messages flow both ways on one connection
  • Proxies often break it. You build reconnect and resume yourself.

Shared document editing or voice.

7,200 live streams × ~3 KB each is about 22 MB of Redis memory. That is tiny. To stop a reply, the app sets cancel:{mid}. The worker then stops the provider call, saves the reply as CANCELLED, and bills only the tokens used.

Memory check: 7,200 live streams × ~3 KB of tokens = ~22 MB in Redis, which is trivial. Cancel works like this. The app sets cancel:{mid}, and the worker checks it between pieces of text. When it sees the flag, it aborts the HTTP call to the provider, which stops further output charges. It saves the partial reply as CANCELLED and bills the tokens already used. SSE also works well over HTTP/2. That removes the browser's limit of six connections per website.

6.2 Editing, branching and building the context

ABreplyB′new reply

Say message B follows message A. Editing B creates a new message B′, also under A. The conversation's current_leaf_id then points to the new end. The model sees the path from that end back to the start. The prompt is built in a fixed order: tools, system prompt, summary, older turns, recent turns, then the new message. Because the start never changes, the provider's cache covers everything except the end.

Go deeper: context-window strategy and Spring AI chat memory

Each message stores its parent_id, so messages form a tree. Editing message B (whose parent is A) creates a new user message B′ with parent A. A new assistant reply follows it. conversation.current_leaf_id moves to this new end, or leaf. Old branches stay, so the user can flip between "1/2" and "2/2". The context for a turn is the path from the leaf back to the root. The worker reads the whole conversation in one partition scan and walks the path in memory.

Fitting history into the model's limit: the context window is the most text a model can read at once. Your budget is the window, minus the maximum reply length, minus the system prompt, minus the tool descriptions. The strategy:

  1. Keep the last N turns word for word. They matter most, and caching makes them cheap.
  2. When the path passes ~70% of the budget, a background job summarises older turns. It saves the result in conversation.summary and records summary_upto_id. The summary moves forward in big jumps, so the cached prompt start changes rarely.
  3. Optionally, store old turns as embeddings (number lists that capture meaning). Then fetch only the few that matter, as in "as I said earlier about clause 14".
  4. Build the prompt in this order: tools, system prompt, summary, older turns, recent turns, new message. Anthropic caches in the order tools, system, messages. So the cache hits on everything except the end.

Spring AI gives you a starter version. MessageWindowChatMemory keeps the last 20 messages by default and always keeps system messages. JdbcChatMemoryRepository stores them in a database. You add the branching tree and the summaries on top.

6.3 Provider routing and the circuit breaker (Emergent Labs)

HEALTHYClaude errors under 2%: send 100% to Claude
DEGRADEDOver 5% errors: 5% to Claude as a test, 95% to OpenAI
FAILINGOver 90% errors: 5% Claude, 5% OpenAI, the rest get 503

Pick the provider with hash(requestId) mod 100. Every server gets the same answer without talking to each other. A retry of the same request lands in the same bucket. Between 2% and 5% errors, the mode stays as it is, which stops it flipping back and forth. Wait for at least 100 results before judging.

Show Java: ProviderRouter
public final class ProviderRouter {
    public enum Mode { HEALTHY, DEGRADED, FAILING }

    private final ErrorRateWindow claude;          // 60 one-second buckets of (ok, error) counters
    private final AtomicReference<Mode> mode = new AtomicReference<>(Mode.HEALTHY);

    public ProviderRouter(ErrorRateWindow claude) { this.claude = claude; }

    public Optional<Provider> route(String requestId) {
        int bucket = Math.floorMod(Hashing.murmur3_32_fixed().hashUnencodedChars(requestId).asInt(), 100);
        return switch (mode.get()) {
            case HEALTHY  -> Optional.of(Provider.CLAUDE);
            case DEGRADED -> Optional.of(bucket < 5 ? Provider.CLAUDE : Provider.OPENAI);
            case FAILING  -> bucket < 5 ? Optional.of(Provider.CLAUDE)
                           : bucket < 10 ? Optional.of(Provider.OPENAI) : Optional.empty(); // caller returns 503
        };
    }

    public void record(Provider p, boolean success) {
        if (p != Provider.CLAUDE) return;
        claude.record(success);
        if (claude.total() < 100) return;           // too few samples to judge
        double rate = claude.errorRate();
        Mode next = rate > 0.90 ? Mode.FAILING : rate > 0.05 ? Mode.DEGRADED
                  : rate < 0.02 ? Mode.HEALTHY : mode.get();   // hysteresis band 2–5% avoids flapping
        mode.set(next);
    }
}
Go deeper: the full prompt, patterns and why failover isn't free

The question: all calls go to Claude. If Claude's error rate passes 5%, send 95% of calls to OpenAI. If it passes 90%, reject calls fast. The exception is 5% to Claude and 5% to OpenAI, as test calls (probes). The interviewer pushed on how to pick the provider for each request. The candidate settled on hashing the request id, mod 100.

This is deterministic percentage bucketing. Feature-flag rollouts use the same trick. Every gateway server computes the same answer with no coordination. A retry with the same request id lands in the same bucket.

Patterns to name: State (the three modes) and Strategy (all providers behind one LlmProvider interface). Also Decorator, which wraps retry and metering around a provider.

In production, keep a separate error window per provider and per model. Count only provider faults: 5xx errors, 429 (too many requests) and timeouts. Do not count 400 errors caused by bad prompts. Share counters through Redis, or accept that each server has its own window. Alert when the mode changes. For a single provider, Resilience4j's CircuitBreaker gives you the window and the state machine.

Failover is not free

A prompt tuned for one model may behave differently on another. Tool-call formats also differ. Some tenants have a contract for one provider or region only. So store each tenant's allowed providers, and keep a prompt version for each provider. Before enabling a backup model, run your golden test set on it. Retry only before the first word is sent. After that, the user has already seen part of a reply.

6.4 Rate limits, budgets and cost

  • Limit tokens per minute (TPM) and the number of open streams, not just requests.
  • Before the call, reserve the estimate plus max_tokens in one atomic step (a Redis Lua script). Afterwards, refund what was not used.
  • A weighted fair queue shares the provider's capacity by plan. Alert at 80% of the budget. At 100%, stop or switch to a cheaper model.
Go deeper: limits and cost attribution
  • Limit tokens per minute as well as requests. One 100k-token request costs more than a thousand short ones. Also cap the open streams per user and per tenant.
  • Reserve before the call. Count the input tokens with the tokeniser and add max_tokens. Take that amount from a Redis token bucket in one atomic Lua script. When the reply finishes, compare with the real usage and refund the difference.
  • Provider limits are shared by all tenants. The gateway uses a weighted fair queue that gives each tenant a share based on its plan. So if one tenant sends a burst, it waits behind its own quota, not everyone's.
  • Every finished reply sends a usage event to Kafka, then to ClickHouse. The event records tenant, user, feature, model, input, cached input, output and the price-table version.
  • Alert at 80% of the monthly budget. At 100%, either stop hard or move to a cheaper model, based on the tenant's policy.

6.5 Search, caching and observability

Search

Kafka feeds OpenSearch with routing=tenant_id. Every query must filter by tenant and user. Old branches are searchable but ranked lower.

Prompt cache

Cached input costs ~0.1× the normal price. Changing any early part of the prompt breaks the cache for everything after it.

Model tiering

A small classifier sends easy questions to a small model. That is 3–10× cheaper.

Traces

Each LLM call is recorded with model, tokens, TTFT and cost. Logs are sampled, with personal data hidden.

Go deeper: search, caching layers table, observability and guardrails

A Kafka consumer adds finished messages to OpenSearch with routing=tenant_id. The server adds a required filter on tenant_id and user_id to every query. Edits mark replaced branches as branch_active=false. They stay searchable but rank lower. Search lags by a few seconds, which is fine.

For meaning-based search, add a k-NN vector field (find the nearest meanings). Then merge its results with BM25, the classic keyword ranking. Give big tenants their own index. Then a noisy tenant cannot skew relevance scores or slow others down. Deleting a conversation removes it from the database, the index and the caches. This runs as one saga, a chain of steps that all finish or are undone. The DPDP erasure flow reuses it.

  • Metrics: TTFT at the median and at 95 of 100 requests (p50/p95). Also tokens per second, provider errors and 429 rates, and the breaker mode. Plus cache hit rate, queue length, open streams, and cost per tenant per hour.

Guardrails

Prompt injection is hidden text that tries to make the model disobey you. Treat tenant system prompts and uploaded files as untrusted. Any tool that changes data needs the user's confirmation.

Personal data and DPDP: find and mask IDs like Aadhaar, PAN and phone numbers before logging. Run the model in-region for tenants that need it. Use provider terms that keep no data. Erase data from the database, index, caches and analytics. The DPDP Rules' core duties apply from 13 May 2027. From then, report a breach to the Data Protection Board without delay, and in full detail within 72 hours.

Tenant isolation: take the tenant id only from the JWT. Use RLS and required search filters, and a separate key per tenant. Never share caches between tenants. Run automated tests that try to leak data across tenants.

07Scaling, failure handling and consistency

What breaks first at 10×

Provider limits and spend. Add providers, use more small models, and cache more. Buy reserved capacity (provisioned throughput).

Connections

72k open SSE streams need about 10–15 Netty servers. Scale on open connections, not CPU.

Worker crash

The Kafka offset is saved only after the final write. The next worker sees STREAMING. It restarts with a reset event, or marks the reply FAILED. Never add a second reply onto the first.

Consistency

Within one conversation, everyone sees the latest data at once. Search and usage catch up a little later.

Go deeper: duplicates, backpressure and multi-region
  • What breaks first at 10×: provider rate limits and spend. Add providers and regions, use small models more, and cache more. Negotiate reserved capacity (provisioned throughput).
  • Connections: at 10×, 72k open SSE streams need ~10–15 Netty servers. Scale on open connections, not CPU.
  • Worker crash mid-reply: the Kafka offset (the "I'm done with this event" marker) is saved only after the final write. So another worker picks the request up. It sees status STREAMING with partial text. It either restarts the reply, or marks it FAILED with a retry button. On restart it sends a reset event, so the browser clears the partial text. Never quietly add a second reply onto the first.
  • Duplicate sends: the idempotency key is unique per tenant, user and key. A repeated send gets the original ids back.
  • Backpressure (pushing back when overloaded): when the provider is full, queue the request with a short deadline. Tell the user, for example "high demand, using a faster model". Don't just let it time out.
  • Consistency: messages in one conversation live in one partition, so reads are always up to date. Search and usage are eventually consistent, meaning they catch up after a few seconds.
  • Multi-region: each tenant has a home region, to keep data in its country. Each tenant has one active region and one standby region, copied in the background. Providers are chosen per region.

09Mistakes that got candidates rejected

Rejected for this
  • Tying the reply to the HTTP connection, so a dropped network loses the reply.
  • Limiting only requests, and ignoring tokens and cost.
  • No isolation plan beyond "add tenant_id". Or worse, taking the tenant id from the request.
  • Treating edits as overwrites. That breaks history and hides what the model actually saw.
  • Sending the full history every turn with no limit, then being unable to explain the bill.
  • In the Emergent machine-coding round, debating routing for too long. The AI-generated code was left with bugs. Settle the bucketing fast, then write the code and test the thresholds.

10Quick check

The user's network drops in the middle of a reply. What happens in this design?

The reply does not depend on the connection. Words wait in Redis Streams, and partial text is saved to the database. So the browser can pick up where it stopped.

Why limit tokens per minute, and not only requests?

Tokens measure both the load on the provider and the money you pay. Request counts hide the difference.

Why use hash(requestId) mod 100 instead of random() < 0.95?

Both give the right split. But a hash gives the same result on every gateway server. So retries and debugging behave the same every time.

The main provider fails after 200 tokens were already shown. Should you retry on the backup?

The user has already read part of a reply. Gluing a second, different reply onto it would confuse them.

11Follow-up questions interviewers asked

Why SSE and not WebSockets?

Words flow one way, from server to browser. The user's message is a normal POST. SSE is plain HTTP, so it passes through company proxies. It reconnects by itself and resumes with Last-Event-ID. It also shares one HTTP/2 connection with other requests. Choose WebSockets when the browser must send many messages on the same channel, as in shared editing or voice.

The user edits a message from ten turns ago. What happens to search, context and billing?

A new branch starts from that message's parent. The context is the new path, so later turns from the old branch are left out. Old-branch messages stay in search with branch_active=false. The new reply is billed like any turn. Prompt caching still helps, because the prompt up to the edit point is unchanged.

How do you count tokens before calling the provider?

Use the provider's tokeniser, or its token-count endpoint, to estimate. Reserve that estimate plus max_tokens from the budget. When the stream ends, the provider returns a usage block with the real numbers. Settle the difference then. Never trust a count from the browser.

One tenant runs a script that sends 10,000 long prompts. What protects others?

Several layers. The tenant's TPM bucket rejects or queues anything over its quota. A per-tenant cap limits open streams. A weighted fair queue in the gateway shares provider capacity by plan. A budget hard stop ends the spend. Also alert the tenant's admin.

Why hash the request id instead of random() < 0.95?

Both give the right proportions. But hashing always gives the same answer for the same id. So retries and debugging can be repeated. You can also pin a request or user to one provider across all gateway servers with no shared state. Hash the user or conversation id instead to keep a whole chat on one provider. That keeps the style consistent and the cache warm.

How would you evaluate this design? (Microsoft)

Check it against the requirements. Measure TTFT and uptime targets (SLOs, service level objectives) end to end. Compare cost per turn with the target. Prove isolation with leak tests. Measure quality with the golden set and with live user signals. Finally, review each failure: provider down, Redis down, worker crash, region loss. Show each one has a defined behaviour.

Redis goes down. What breaks?

Live word-by-word streaming and rate limiting break. Workers keep writing and saving partial text to the database. So browsers fall back to polling the message. Rate limiting either blocks heavy tenants, or falls back to local limits on each server. Run Redis with replicas. Never make it the only copy of anything you must keep.

13Cheat sheet

Cheat sheet
  • Numbers: 600 sends per second at peak, 7,200 open streams, ~$0.011 per turn with caching.
  • Send (returns 202 and ids) and stream (GET with Last-Event-ID) are separate calls.
  • The worker writes to Redis Streams. A stateless SSE service reads from it. Partial text is saved every ~2 s.
  • Messages form a tree through parent_id. Edits create branches. The context is the path from the newest message back to the first.
  • Prompt order: tools, system prompt, summary, history, new message.
  • Gateway: reserve and refund tokens per minute, fair queue, breaker with hash buckets.
  • Isolation: tenant from the JWT, RLS, a key per tenant, required search filters.
  • Failures: retry only before the first token. After a worker crash, reset or mark FAILED.
