Do not use your employer's data or code

Build this on your own laptop, your own accounts and public contracts only. No customer documents, no internal repositories, no copied service code, no screenshots of internal tools. You can say "I work on e-signing infrastructure, so I chose a domain I understand", but the code and data must be clean-room. Interviewers ask "is this your work's code?" more often than you would expect; the answer must be an easy no.

Think of the system as three ordinary Spring services sharing one Postgres. The only unusual parts are a vector column and two calls to a model. Everything else is the backend work you already do: authentication, tenancy, idempotent ingestion, metrics, tests.

Path 1 — Ingest (async, idempotent)

POST /contractsmultipart PDF→ PagePdfDocumentReader1 Document per page→ TokenTextSplitter~500-token chunks→ EmbeddingModelbatch embed→ PgVectorStoretenant_id · contract_id · page_number

Figure 1: Ingestion. Page numbers come from the reader's page_number metadata and survive splitting because the splitter copies parent metadata onto every chunk.

The reader emits one Document per page with page_number and file_name in its metadata. TokenTextSplitter copies that metadata onto each chunk (and adds parent_document_id, chunk_index, total_chunks). You add tenant_id and contract_id before writing. Hash the PDF bytes (SHA-256) and store it on a contracts row; re-uploading the same file for the same tenant becomes a no-op. That is the idempotency story interviewers like.

Path 2 — Ask (synchronous, cited, refuses when unsure)

POST /askquestion→ JWT filtertenant from token→ Vector searchtenant_id == X, topK 6→ Threshold gateno chunk ≥ 0.55 → refuse→ claude-sonnet-5-5answer from context only→ Responseanswer + [contract, page]

Figure 2: Query path. The tenant filter is applied in the database query, never left to the prompt.

Tenant comes from the JWT claim, never from the request body. The filter expression tenant_id == 'X' goes into the similarity search, so another tenant's chunks are never even loaded into memory. If no chunk clears the similarity threshold, you return a fixed refusal ("I couldn't find this in your contracts") without calling the model: cheaper, faster and the single best hallucination defence you have. Citations are built from the retrieved documents' metadata, not parsed out of the model's prose, so they cannot be invented.

Path 3 — Flag (batch, structured output)

Contract ingestedevent / @Async→ Clause segmenterheadings + numbering→ claude-haiku-4-5.entity(RiskFlag.class)→ risk_flags tabletype · severity · page · quote→ GET /contracts/{id}/risks

Figure 3: Flagger. A cheap, fast model classifies each clause against a fixed rubric; the result is a typed Java record, persisted like any other row.

The rubric is closed and explicit. A closed list is easier to evaluate (precision and recall per type) than "find anything risky".

Step 3 — Ask path in one service

Show Java: AskService
@Service
public class AskService {

    private static final String REFUSAL = "I could not find this in your contracts.";
    private final ChatClient chatClient;

    public AskService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder
            .defaultSystem(new ClassPathResource("prompts/answer-system.st"))
            .defaultAdvisors(QuestionAnswerAdvisor.builder(vectorStore)
                .searchRequest(SearchRequest.builder().similarityThreshold(0.55).topK(6).build())
                .build())
            .build();
    }

    public AskResponse ask(String tenantId, String question) {
        ChatResponse response = chatClient.prompt()
            .user(question)
            // Text form only here: tenant id comes from the JWT and must match [A-Za-z0-9_-]+
            .advisors(a -> a.param(QuestionAnswerAdvisor.FILTER_EXPRESSION, "tenant_id == '" + tenantId + "'"))
            .call()
            .chatResponse();
        List<Document> docs = response.getMetadata().get(QuestionAnswerAdvisor.RETRIEVED_DOCUMENTS);
        if (docs == null || docs.isEmpty()) {
            return new AskResponse(REFUSAL, List.of(), true);
        }
        List<Citation> citations = docs.stream()
            .map(d -> new Citation((String) d.getMetadata().get("contract_id"),
                (String) d.getMetadata().get("file_name"),
                ((Number) d.getMetadata().get("page_number")).intValue(),
                d.getScore() == null ? 0 : d.getScore()))
            .distinct()
            .toList();
        return new AskResponse(response.getResult().getOutput().getText(), citations, false);
    }
}
  • QuestionAnswerAdvisor still calls the model below threshold; in milestone 3 search first and refuse yourself.
  • The concatenated filter is safe only because tenantId comes from the JWT. Comment it.
Go deeper: two honest caveats for your README
Two honest caveats to put in your README

First, QuestionAnswerAdvisor still calls the model when nothing passes the threshold (its default prompt then tells the model to say it does not know). In milestone 3, move the search in front of the call yourself (vectorStore.similaritySearch(...), then refuse without a model call) to save the latency and tokens; the full version is in the Spring RAG endpoint lesson. Second, tenantId comes from the validated JWT, never from user input, so the string concatenation is safe; say so in a comment, because a reviewer will ask.

Step 4 — Flagger with structured output

Show Java: FlaggerService
@Service
public class FlaggerService {

    private final ChatClient haiku;

    public FlaggerService(ChatClient.Builder builder) {
        this.haiku = builder
            .defaultOptions(AnthropicChatOptions.builder().model("claude-haiku-4-5-20251001").maxTokens(400).temperature(0.0))
            .defaultSystem(new ClassPathResource("prompts/flag-system.st"))
            .build();
    }

    public RiskFlag classify(String clauseText) {
        return haiku.prompt()
            .user(u -> u.text("Clause:\n{clause}").param("clause", clauseText))
            .call()
            .entity(RiskFlag.class);
    }
}

Verify clauseText.contains(flag.quote()) server-side and drop flags that fail. It catches most hallucinated flags.

Go deeper: the flagger system prompt

The system prompt holds the rubric table above, one short example per type, and the rule "return type NONE if no rubric item applies; quote must be copied verbatim from the clause". Verify the quote server-side with clauseText.contains(flag.quote()); drop flags whose quote does not appear. That one line catches most hallucinated flags and is a great interview detail.

05Quick check

Where must the tenant filter live?

Prompt or post-filters can leak through bugs or injection. Filtering in the query means other tenants' chunks never load.

Why build citations from chunk metadata instead of parsing the answer?

Metadata always points to a real document and page; eval citation accuracy checks that the page supports the answer.

Recall@6 is low and faithfulness is high. What do you fix first?

If the right chunk isn't in the top k, no prompt change can fix the answer.

Why Haiku for the flagger and Sonnet for answers?

The choice is data-driven (per-type precision/recall) and reversible, because the model id is config.

06Interview questions

30-second pitch

Say it like this

"I built a contract assistant in Spring Boot and Spring AI. It answers questions over a tenant's contracts with page-level citations, refuses when retrieval confidence is low, and flags six kinds of risky clauses using typed structured output. I measure it: on a held-out set it gets [X] retrieval recall and [Y] faithfulness, and a GitHub Action blocks prompt changes that regress those numbers. An answer costs about a cent."

2-minute deep dive (the order to walk through)

  1. Ingest: page-aware chunking so citations are real; content hash for idempotent re-upload.
  2. Isolation: tenant from the JWT, enforced inside the vector query, plus a test that proves it.
  3. Grounding: similarity threshold refusal before the model call; citations from metadata.
  4. Flagger: closed rubric, cheap model, schema-bound output, verbatim-quote check.
  5. Evals: golden set with unanswerables, retrieval and generation metrics, CI gate.
  6. Ops: token and cost metrics per tenant, streaming, caching, rate limits.

Numbers to have ready

Corpus size (contracts, pages, chunks), chunk size and overlap, topK and threshold and why, recall@k and MRR, faithfulness, refusal accuracy, flag precision/recall per type, p50/p95 latency, cost per answer and per contract, and one before/after delta (for example "hybrid search took recall@6 from A to B").

Why pgvector and not a dedicated vector database?

At this scale (thousands of contracts, low millions of chunks) Postgres with an HNSW index is fast enough, and I get the tenant filter, joins to contract metadata, transactions and backups from a database the team already runs. I would revisit when vector count or QPS pushes index memory beyond one node, or when I need features like built-in hybrid ranking at scale.

How do you know the citations are correct?

They are built from the retrieved chunks' metadata, so the document and page always exist. Whether the page actually supports the answer is measured: citation accuracy in the eval set checks that the cited page contains the expected answer span. The model cannot invent a page number because it never writes one.

How did you choose the similarity threshold?

Empirically. I plotted the top-1 score for answerable versus unanswerable golden questions and picked the value that maximised refusal accuracy while keeping false refusals on answerable questions under about 5%. It is a config property, re-tuned whenever the embedding model or chunking changes.

Why a different model for the flagger?

Clause classification against a fixed rubric is a narrow, high-volume task: 40 calls per contract. Haiku is cheaper and faster, and per-type precision/recall on the eval set showed it was good enough. Answers to open questions over several chunks benefit from the stronger model. The choice is data-driven and reversible because the model id is configuration.

What stops prompt injection inside an uploaded contract?

Retrieved text goes into a clearly delimited context block with an instruction that it is data, not instructions; the model has no write tools on the ask path; outputs are schema-checked; and the flagger's quote must appear verbatim in the source. I also keep injection cases ("ignore previous instructions...") in the golden set so a prompt change that weakens this is caught in CI.

What would break first at 100x tenants?

Ingestion throughput and model rate limits, before the database. I would move ingestion onto a queue with per-tenant concurrency limits, batch embeddings, add a provider fallback with a circuit breaker, and consider partitioning the vector table by tenant or moving large tenants to their own index.

Is the agentic feature actually needed?

Honestly, most of it is a workflow: search, fetch, compare. I built it as an agent only for open-ended reviews where the number of steps is unknown, with a step cap, a token budget and human approval before writes. On my eval set the fixed workflow was cheaper for the common case, so the agent is opt-in. Showing you know when not to use an agent is a senior signal.

Is this your company's code or data?

No. It is built from scratch on public contracts (CUAD and SEC EDGAR filings) on personal accounts. My day job is in e-signing infrastructure, which is why I chose the domain.

Self-check: which metric tells you whether to fix retrieval or the prompt first?

Retrieval recall@k. If the right chunk is not in the top k, no prompt change can fix the answer; improve chunking, hybrid search or re-ranking first. If recall is high but faithfulness is low, work on the prompt and context formatting.

Self-check: where must the tenant filter live, and why?

In the database query that does the similarity search, using the tenant from the validated JWT. A filter applied after retrieval or requested in the prompt can leak data through bugs or injection.

08Cheat sheet

Cheat sheet
  • Ingest: page-aware chunks, metadata copied, SHA-256 idempotency.
  • Ask: tenant from JWT, filter in the query, topK 6, refuse below 0.55 without a model call.

  • Flag: closed 6-type rubric, Haiku, entity(RiskFlag.class), verbatim-quote check.
