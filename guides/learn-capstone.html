Capstone: Contract Q&A with citations + risky-clause flagger

Over eight weeks you build one real AI feature in Java. It answers questions about contracts and points to the exact page. It flags risky clauses. It keeps each customer's data apart, and you measure how well it works. Then you learn to tell its story in an interview.

Effort: ~6–8 h/week, weeks 4–11 Stack: Java 21 · Spring Boot 4.1.1 · Spring AI 2.0.1 · Postgres + pgvector · Python evals Models: claude-sonnet-5-5 (answers) · claude-haiku-4-5-20251001 (flagging)

In 30 seconds
  • Three flows share one Postgres database. Load contracts. Answer questions with page citations. Flag risky clauses.
  • Four milestones, each one tagged in git and ready to demo: RAG, flagger, evals, production.
  • Scores measured on contracts you never tuned on are your strongest interview evidence.
  • Use public contracts only. Never your employer's code or data.

Words you'll see
RAG
Retrieval-augmented generation. Search your documents first, then let the AI answer using only what it found.
Chunk
A small piece of a document, about 500 tokens (roughly a page section), stored for search.
Embedding
A list of numbers that captures what a piece of text means. Similar meanings get similar numbers.
pgvector
A Postgres add-on that stores embeddings and finds the closest ones, so you can search by meaning.
Tenant
One customer company. Acme must never see Globex's contracts.
Structured output
Making the AI reply in a fixed JSON shape that becomes a Java record.
Evals
Automated tests that score AI answers over many questions and report pass rates.
Agent
An AI that decides its own next steps and calls your tools in a loop until the task is done.

Ingest

Read one Document per page. Split into chunks of about 500 tokens that keep the page_number. Add tenant_id and contract_id. A SHA-256 fingerprint of the PDF makes a repeat upload do nothing.

Ask

The customer filter sits inside the search query. Take the 6 closest chunks. If none scores 0.55 or more, refuse without calling the model. Page citations come from stored data, not the model's text.

Flag

Haiku sorts each clause into one of six fixed risk types and returns a typed RiskFlag record. Drop any flag whose quote is not word-for-word in the clause.

Interviewers ask "is this your work's code?" more often than you would expect. The answer must be an easy no.

Think of the system as three ordinary Spring services sharing one Postgres. Only two parts are unusual: a column that stores embeddings, and two calls to a model. Everything else is backend work you already do. Login, keeping customers apart, safe-to-repeat uploads, metrics and tests.

Path 1 — Ingest (runs in the background, safe to repeat)

POST /contractsupload the PDF→ PagePdfDocumentReaderread it page by page→ TokenTextSplittercut into ~500-token pieces→ EmbeddingModelturn each piece into numbers→ PgVectorStoresave with customer, contract and page

Figure 1: Loading a contract. The reader labels each page with its page_number. The splitter copies that label onto every piece, so page numbers survive the cut.

The reader gives one Document per page, labelled with page_number and file_name. TokenTextSplitter copies those labels onto each chunk. It also adds parent_document_id, chunk_index and total_chunks. You add tenant_id and contract_id before saving. Take a SHA-256 fingerprint of the PDF bytes and store it on a contracts row. Then uploading the same file again for the same customer does nothing. Interviewers like this "safe to repeat" (idempotency) story.

Path 2 — Ask (answers right away, cites pages, refuses when unsure)

POST /askthe question→ JWT filtercustomer from login token→ Meaning searchthis customer only, best 6→ Score checknothing scores 0.55+? refuse→ claude-sonnet-5-5answers from found text only→ Responseanswer + [contract, page]

Figure 2: Answering a question. The customer filter is part of the database query. It is never left to the prompt.

The customer comes from the login token (JWT), never from the request body. The filter tenant_id == 'X' goes into the meaning search itself. So another customer's chunks are never even loaded. If no chunk scores high enough, you return a fixed refusal: "I couldn't find this in your contracts". You do not call the model at all. That is cheaper and faster. It is also your best defence against made-up answers (hallucinations). Citations are built from the stored labels on the found chunks, not read out of the model's text. So they cannot be invented.

Path 3 — Flag (in batches, fixed JSON output)

Contract loadedtriggers a background job→ Clause splitteruses headings and numbers→ claude-haiku-4-5returns a RiskFlag record→ risk_flags tabletype, severity, page, quote→ GET /contracts/{id}/risks

Figure 3: The flagger. A cheap, fast model sorts each clause using a fixed list of risk types. The result is a typed Java record, saved like any other row.

The list of risk types is fixed and clear. A fixed list is easier to test than "find anything risky". You can measure, per type, how many flags were right (precision) and how many risks were caught (recall).

Tech stack and why each piece

Java 21 + Spring Boot 4.1.1

Your strongest stack. Records for data objects, virtual threads for slow model calls. Spring AI 2.0.x supports Boot 4.0.x and 4.1.x.

Spring AI 2.0.1

Comes with ChatClient, QuestionAnswerAdvisor, PgVectorStore, entity() for typed output, and Micrometer metrics.

Postgres + pgvector

One database for normal tables and embeddings. Customer filters and joins are plain SQL. An HNSW index makes meaning search fast. No second database to run.

Python eval harness

Ragas and charts live in Python. The harness calls your HTTP API. So it tests the real system, not a notebook copy.

Step 3 — Ask path in one service

Show Java: AskService
@Service
public class AskService {

    private static final String REFUSAL = "I could not find this in your contracts.";
    private final ChatClient chatClient;

    public AskService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder
            .defaultSystem(new ClassPathResource("prompts/answer-system.st"))
            .defaultAdvisors(QuestionAnswerAdvisor.builder(vectorStore)
                .searchRequest(SearchRequest.builder().similarityThreshold(0.55).topK(6).build())
                .build())
            .build();
    }

    public AskResponse ask(String tenantId, String question) {
        ChatResponse response = chatClient.prompt()
            .user(question)
            // Text form only here: tenant id comes from the JWT and must match [A-Za-z0-9_-]+
            .advisors(a -> a.param(QuestionAnswerAdvisor.FILTER_EXPRESSION, "tenant_id == '" + tenantId + "'"))
            .call()
            .chatResponse();
        List<Document> docs = response.getMetadata().get(QuestionAnswerAdvisor.RETRIEVED_DOCUMENTS);
        if (docs == null || docs.isEmpty()) {
            return new AskResponse(REFUSAL, List.of(), true);
        }
        List<Citation> citations = docs.stream()
            .map(d -> new Citation((String) d.getMetadata().get("contract_id"),
                (String) d.getMetadata().get("file_name"),
                ((Number) d.getMetadata().get("page_number")).intValue(),
                d.getScore() == null ? 0 : d.getScore()))
            .distinct()
            .toList();
        return new AskResponse(response.getResult().getOutput().getText(), citations, false);
    }
}
  • QuestionAnswerAdvisor still calls the model when nothing scores high enough. In milestone 3, search first yourself and refuse without the model.
  • Building the filter by joining strings is safe only because tenantId comes from the JWT. Say so in a comment.
Go deeper: two honest caveats for your README
Two honest caveats to put in your README

First, QuestionAnswerAdvisor still calls the model when nothing passes the score minimum. Its default prompt then tells the model to say it does not know. In milestone 3, run the search yourself before the call with vectorStore.similaritySearch(...). Then refuse without calling the model. That saves time and tokens. The full version is in the Spring RAG endpoint lesson. Second, tenantId comes from the checked JWT, never from user input. So joining it into the filter string is safe. Say so in a comment, because a reviewer will ask.

Step 4 — Flagger with structured output

Show Java: FlaggerService
@Service
public class FlaggerService {

    private final ChatClient haiku;

    public FlaggerService(ChatClient.Builder builder) {
        this.haiku = builder
            .defaultOptions(AnthropicChatOptions.builder().model("claude-haiku-4-5-20251001").maxTokens(400).temperature(0.0))
            .defaultSystem(new ClassPathResource("prompts/flag-system.st"))
            .build();
    }

    public RiskFlag classify(String clauseText) {
        return haiku.prompt()
            .user(u -> u.text("Clause:\n{clause}").param("clause", clauseText))
            .call()
            .entity(RiskFlag.class);
    }
}

On the server, check clauseText.contains(flag.quote()). Drop any flag that fails. This catches most made-up flags.

Go deeper: the flagger system prompt

The system prompt holds the risk table above and one short example per type. It also holds the rule: "return type NONE if no rubric item applies; quote must be copied verbatim from the clause". Check the quote on the server with clauseText.contains(flag.quote()). Drop flags whose quote does not appear. That one line catches most made-up flags. It is a great interview detail.

05Quick check

Where must the customer (tenant) filter go?

A rule in the prompt, or a filter after the search, can leak through a bug or hidden instructions. Filtering inside the query means other customers' chunks are never loaded.

Why build citations from the chunks' stored labels instead of reading them from the answer?

Stored labels always point to a real document and page. Separately, the evals check that the page really supports the answer.

Search often misses the right chunk (recall@6 is low), but answers stick to what was found (faithfulness is high). What do you fix first?

If the right chunk is not in the top results, no prompt change can fix the answer. The model never sees the evidence.

Why Haiku for the flagger and Sonnet for answers?

The choice comes from test scores (precision and recall per risk type). It is easy to undo, because the model name is a config setting.

06Interview questions

30-second pitch

Say it like this

"I built a contract assistant in Spring Boot and Spring AI. It answers questions over a customer's contracts and cites the page. It refuses when search is not confident. It flags six kinds of risky clauses as typed Java records. I measure it. On contracts I never tuned on, it gets [X] search recall and [Y] faithfulness. A GitHub Action blocks prompt changes that lower those numbers. An answer costs about a cent."

2-minute deep dive (the order to walk through)

  1. Ingest: chunks keep their page numbers, so citations are real. A file fingerprint makes re-uploads safe.
  2. Isolation: the customer comes from the JWT and is enforced inside the search query. A test proves it.
  3. Grounding: refuse before calling the model when no chunk scores high enough. Citations come from stored labels.
  4. Flagger: a fixed list of risk types, a cheap model, output in a fixed shape, and a word-for-word quote check.
  5. Evals: a golden set that includes no-answer questions, search and answer scores, and a CI gate.
  6. Ops: token and cost metrics per customer, streaming, caching and rate limits.

Numbers to have ready

Know these: how many contracts, pages and chunks. Chunk size and overlap. How many results you keep (topK), your score minimum, and why. Recall@k and MRR. Faithfulness. Refusal accuracy. Flag precision and recall per type. p50 and p95 response time (half, and 95 of 100, requests are faster). Cost per answer and per contract. And one before-and-after change, such as "hybrid search took recall@6 from A to B".

Why pgvector and not a dedicated vector database?

At this size, thousands of contracts and a few million chunks, Postgres with an HNSW index is fast enough. I also get the customer filter, joins to contract data, transactions and backups. All from a database the team already runs. I would think again when the number of embeddings or QPS (queries per second) needs more index memory than one machine has. Or when I need built-in hybrid ranking at large scale.

How do you know the citations are correct?

They are built from the found chunks' stored labels, so the document and page always exist. Whether the page really supports the answer is measured. Citation accuracy in the eval set checks that the cited page contains the expected answer text. The model cannot invent a page number, because it never writes one.

How did you choose the similarity threshold?

By measuring. I plotted the best match score for golden questions that have an answer and ones that do not. I picked the value that refused the most no-answer questions correctly. At the same time it kept wrong refusals on real questions under about 5%. It is a config setting. I tune it again whenever the embedding model or chunking changes.

Why a different model for the flagger?

Sorting clauses into a fixed list of risks is a narrow task done many times: 40 calls per contract. Haiku is cheaper and faster. Precision and recall per type on the eval set showed it was good enough. Open questions that need several chunks do better with the stronger model. The choice comes from data, and it is easy to undo, because the model name is configuration.

What stops prompt injection inside an uploaded contract?

Found text goes into a clearly marked block, with an instruction that it is data, not orders. On the ask path the model has no tools that can change anything. Replies are checked against a schema. The flagger's quote must appear word-for-word in the source. I also keep injection cases, like "ignore previous instructions...", in the golden set. So CI catches a prompt change that weakens this defence.

What would break first at 100x tenants?

Upload speed and the model provider's rate limits break before the database does. I would put uploads on a queue, with a limit on parallel jobs per customer. I would embed in batches. I would add a backup provider behind a circuit breaker, which switches over when the main one fails. I would also consider splitting the embeddings table by customer, or giving large customers their own index.

Is the agentic feature actually needed?

Honestly, most of it is a fixed workflow: search, fetch, compare. I used an agent only for open-ended reviews where the number of steps is unknown. It has a step limit, a token budget and human approval before saving. On my eval set, the fixed workflow was cheaper for the common case. So the agent is optional. Knowing when not to use an agent is a senior signal.

Is this your company's code or data?

No. I built it from scratch on public contracts (CUAD and SEC EDGAR filings), using personal accounts. My day job is in e-signing infrastructure. That is why I chose this domain.

  • There is no employer code, data, branding or screenshot anywhere in the repository or its history.
Self-check: which metric tells you whether to fix retrieval or the prompt first?

Search recall@k. If the right chunk is not in the top k, no prompt change can fix the answer. Improve chunking, hybrid search or re-ranking first. If recall is high but faithfulness is low, work on the prompt and on how the found text is laid out.

Self-check: where must the tenant filter live, and why?

Inside the database query that does the meaning search, using the customer from the checked JWT. A filter applied after the search, or a request in the prompt, can leak data through bugs or hidden instructions.

08Cheat sheet

Cheat sheet
  • Ingest: chunks keep page numbers and labels. A SHA-256 fingerprint makes re-uploads safe.
  • Ask: customer from the JWT, filter inside the query, best 6 chunks. Refuse below 0.55 without calling the model.
  • Citations come from stored labels. Evals measure citation accuracy.
  • Flag: 6 fixed risk types, Haiku, entity(RiskFlag.class), word-for-word quote check.
  • Milestones in order: v0.4-rag, v0.7-evals, v0.8-prod, v1.1-agent.
  • Cost: about $0.01 per answer and $0.06 per contract flagged.
