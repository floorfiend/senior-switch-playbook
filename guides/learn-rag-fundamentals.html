Go deeper: why RAG exists

Claude knows nothing about your tenants' contracts. You have three options. Paste everything into the prompt, which works until the corpus is too large or too expensive. Fine-tune, which teaches style, not facts, and is stale the day after. Or retrieve the few relevant passages per question and paste only those. RAG is the third option. Think of it as an Elasticsearch query whose hits go into the prompt instead of being rendered on a results page.

First question to ask: is RAG needed at all? Anthropic's own guidance in its contextual retrieval write-up: if the knowledge base is under about 200,000 tokens (roughly 500 pages), put the whole thing in the prompt and use prompt caching. One 80-page master services agreement (MSA) does not need a vector DB. Ten thousand tenants' contract libraries do.

Go deeper: embeddings and model choice in full

An embedding model maps text to a vector, for example 1,024 floats, so that texts with similar meaning point in similar directions. "Liability cap" and "aggregate liability shall not exceed" share almost no words, yet their vectors end up close together. That is the advantage over keyword search. The cost is that exact identifiers ("clause 12.2", "C-1042") are often matched worse than by keyword search, which is why hybrid search exists.

Cosine similarity measures the angle between two vectors: cos(a, b) = (a · b) / (|a| |b|). It ranges from −1 to 1, and higher means more similar. When vectors are normalised to length 1, as Voyage embeddings are, cosine similarity equals the dot product, and Euclidean distance gives the same ranking. So the choice of metric matters less than people think, provided you use the one the model was trained for and you build your index with the matching operator class.

Anthropic does not offer an embedding model. Its docs point to Voyage AI. Current Voyage text models: voyage-4-large (best quality), voyage-4 (balanced), voyage-4-lite (cheapest, lowest latency), each with 32k context and 1,024 dimensions by default (256/512/2048 also available). There is also the domain model voyage-law-2 (16k context, 1,024 dimensions), which is the natural one to benchmark for contracts. Things that matter in practice:

  • Same model for documents and queries. Vectors from different models are not comparable. Changing model means re-embedding the corpus, so store embedding_model as a column.
  • input_type. Pass "document" at ingestion and "query" at search time. Voyage prepends a different instruction for each, which improves retrieval. Never omit it.
  • Dimensions vs cost. 1,024 float32 values take 4 KB per chunk. 10M chunks is about 40 GB before the index. Smaller output dimensions or quantisation trade a little recall for a lot of RAM.
  • Language and domain. Indian contracts mix English with Hindi terms and statute references. Evaluate on your golden set, not on a public leaderboard.

Go deeper: strategies, size, overlap and top-k in full

Fixed-size

Every N tokens with M overlap. Simple and predictable. It cuts clauses mid-sentence, so "shall not exceed" ends up in one chunk and the amount in the next.

Recursive

Try to split on paragraphs, then on lines, then on sentences, then on characters, until each chunk fits. A good default for prose (LangChain's RecursiveCharacterTextSplitter; Spring AI's TokenTextSplitter, which defaults to 800 tokens, is a simpler token-based relative).

Semantic

Embed each sentence and start a new chunk where similarity to the previous sentence drops. Better topic boundaries, but ingestion costs more and the results are harder to debug.

Structure-aware

Split on the document's own structure: headings, numbered clauses, table rows. For contracts this is the clear winner. One clause per chunk, with clause number and section heading as metadata.

A sensible starting point is 300–800 tokens with 10–20% overlap for prose, or one clause per chunk for contracts with no overlap. Overlap patches over boundary cuts. Structure-aware splitting removes most of those cuts, so you rarely need overlap there. Then measure recall@k on a golden set and tune. Chunk size is a hyperparameter, not a belief.

k is how many chunks you pass to the model. Too small and you miss the carve-out in 12.2 that changes the answer. Too large and you pay for tokens, add latency, and bury the answer in noise ("lost in the middle"). Typical values are k = 3–8 straight from the vector search, or retrieve 20–50 and rerank down to 5. Add a minimum similarity score so an out-of-domain question returns nothing and the model says "not in the documents" instead of answering from loosely related clauses.

Step 2: structure-aware chunking for contracts

A regex finds 12, 12.1, 12.1.3 headings; bare headings become metadata.

Show clause_splitter.py
import re

# A clause heading: line start, number like 12 or 12.1 or 12.1.3, then a title or text.
HEADING = re.compile(r"^(?P<no>\d+(?:\.\d+)*)\.?\s+(?P<title>[^\n]+)$", re.MULTILINE)


def split_clauses(doc_id: str, text: str, max_chars: int = 1500) -> list[dict]:
    matches = list(HEADING.finditer(text))
    chunks = []
    for i, m in enumerate(matches):
        end = matches[i + 1].start() if i + 1 < len(matches) else len(text)
        body = text[m.start():end].strip()
        if "\n" not in body and "." not in m.group("no"):
            continue  # bare section heading like "12. Limitation of Liability": kept as metadata only
        top = m.group("no").split(".")[0]
        parent = next((x.group("title") for x in matches if x.group("no") == top), "")
        # ponytail: oversize clauses are cut on blank lines only; add sentence split if clauses run long
        parts = [body] if len(body) <= max_chars else [p for p in body.split("\n\n") if p.strip()]
        for j, part in enumerate(parts):
            chunks.append({
                "id": f"{doc_id}#{m.group('no')}" + (f"-{j}" if len(parts) > 1 else ""),
                "clause_no": m.group("no"),
                "section": parent,
                "text": part,
            })
    return chunks

Step 3: the whole pipeline, offline

fake_embed is a hashed bag-of-words (mechanics, not meaning); pgvector replaces the list store in the next lesson.

Show toy_rag.py
"""Offline RAG pipeline: load -> chunk -> embed -> store -> retrieve -> assemble -> generate."""
import hashlib
import os
import re

import numpy as np

from clause_splitter import MSA, split_clauses

DIM = 256


def fake_embed(text: str) -> np.ndarray:
    # ponytail: hashed bag-of-words stands in for a real model; swap for Voyage in production
    v = np.zeros(DIM)
    for word in re.findall(r"[a-z]+", text.lower()):
        v[int(hashlib.md5(word.encode()).hexdigest(), 16) % DIM] += 1.0
    n = np.linalg.norm(v)
    return v / n if n else v


class InMemoryStore:
    def __init__(self):
        self.vectors, self.chunks = [], []

    def add(self, chunks):
        for c in chunks:
            self.vectors.append(fake_embed(c["section"] + " " + c["text"]))
            self.chunks.append(c)

    def search(self, query: str, k: int = 3, min_score: float = 0.1):
        q = fake_embed(query)
        scores = np.array(self.vectors) @ q  # unit vectors: dot product == cosine similarity
        top = np.argsort(-scores)[:k]
        return [(float(scores[i]), self.chunks[i]) for i in top if scores[i] >= min_score]


def assemble_prompt(question: str, hits) -> str:
    docs = "\n".join(
        f'<source id="{c["id"]}" clause="{c["clause_no"]}">\n{c["text"]}\n</source>' for _, c in hits
    )
    return (
        f"<sources>\n{docs}\n</sources>\n\n"
        f"<question>{question}</question>\n\n"
        "Answer only from the sources. Cite every claim as [source id]. "
        "If the sources do not contain the answer, say so."
    )


def generate(prompt: str) -> str:
    import anthropic

    resp = anthropic.Anthropic().messages.create(
        model="claude-haiku-4-5-20251001",
        max_tokens=512,
        system="You answer questions about contracts for a legal team.",
        messages=[{"role": "user", "content": prompt}],
    )
    return resp.content[0].text


if __name__ == "__main__":
    store = InMemoryStore()
    store.add(split_clauses("MSA-acme", MSA))  # load + chunk + embed + store
    question = "What is the liability cap and are there exceptions?"
    hits = store.search(question, k=3)  # retrieve
    for score, c in hits:
        print(f"{score:.3f}  {c['id']}")
    prompt = assemble_prompt(question, hits)  # assemble
    print(prompt)
    if os.environ.get("ANTHROPIC_API_KEY"):
        print(generate(prompt))  # generate

Go deeper: steps 2–4 explained in full

Contracts number their clauses. Use that numbering. The regex matches headings like 12, 12.1 or 12.1.3 at the start of a line. Each match runs until the next heading. Bare section headings ("12. Limitation of Liability") are not stored as chunks; they become section metadata on their sub-clauses. Oversized clauses fall back to splitting on paragraphs.

Each chunk carries a stable id (doc#clause) for citations and idempotent re-ingestion (upsert on id), plus metadata to filter and display. In production you also add tenant_id, contract_id, page, effective_date and embedding_model.

To run without any API, fake_embed hashes words into a 256-dimensional bag-of-words vector and normalises it. It is a stand-in that shows the mechanics: normalise, then dot product equals cosine similarity, then argsort, then top-k. It is not semantic. The in-memory store is a list of vectors; pgvector replaces it in the next lesson. The section heading is embedded together with the clause text, a small form of "contextual" chunk enrichment.

Replace fake_embed with these calls: input_type="document" in add, input_type="query" in search. Batch the document calls (many texts per request) during ingestion. Voyage vectors are already unit length, so the dot product in search stays correct.

Go deeper: assembly rules and the generate step
  • Wrap each source in XML tags with an id. Claude handles XML-tagged structure well, and an id lets you require [MSA-acme#12.2]-style citations that your UI can turn into links to the PDF page.
  • Instruct a refusal path. "If the sources do not contain the answer, say so." Without it, the model fills gaps from its training data. In legal work that counts as a hallucination.
  • Put sources first and the question last. Long context goes above the instruction.
  • Validate citations after generation. Every cited id must be one you supplied. Strip or flag answers that cite ids you did not provide.
  • Keep tenant data in the user turn, not the system prompt. Retrieved text is untrusted, because a counterparty wrote it. It must not carry the authority of system instructions.

Read the scores critically, as an interviewer would. Both liability clauses rank on top, which is good: 12.2 is the carve-out, and without it the answer would be wrong. But the Definitions clause got in at 0.250 only because it shares words like "the" and "services". That is the noise in top-k failure mode in miniature. 07How this shows up in interviews

Explain RAG end to end. (Asked almost everywhere.)

Offline: load documents, chunk them, embed each chunk, store vector + text + metadata in a vector index. Online: embed the query with the same model, retrieve the top-k nearest chunks with tenant and metadata filters, assemble them into the prompt with ids, generate an answer that cites those ids, then validate the citations. Each stage has its own failure modes and its own metric.

How do you choose chunk size and overlap?

Start from the document structure: for contracts, one clause per chunk with its section heading as metadata. For prose, 300–800 tokens with 10–20% overlap. Then tune on a golden set of question → expected-chunk pairs, measuring recall@k and answer faithfulness. Smaller chunks give sharper vectors but less context; larger chunks give more context but blurrier matches and more tokens.

Cosine similarity vs dot product vs Euclidean?

Cosine compares direction only. Dot product also includes magnitude. On unit-normalised vectors, cosine equals the dot product, and Euclidean gives the same ranking. Use the metric the embedding model was trained for, and build the index with the matching operator class, or the index will not be used.

How do you pick k?

Enough to cover multi-part answers (the clause plus its carve-out), bounded by token cost and the dilution effect. In practice: retrieve 20–50 candidates cheaply, rerank to 3–8, and apply a minimum score so irrelevant questions get no context.

How do you choose an embedding model?

Benchmark candidates on my own labelled queries, not on a leaderboard. Consider domain (voyage-law-2 for contracts), language mix, dimensions × corpus size for RAM, latency and price, and whether it supports query/document input types. The model version is stored per row because switching means re-embedding everything.

RAG vs fine-tuning vs long context?

Under about 200k tokens of knowledge: put it in the prompt with prompt caching. For large or frequently changing private data with citations and per-user access control: RAG. Fine-tuning changes behaviour and format, not facts, and does not respect access control. You cannot "un-train" one tenant's contract.

How do you stop hallucinations in a RAG answer?

Retrieval quality first: if the right chunk is not in context, nothing downstream helps. Then: instruct the model to answer only from the sources and say when it cannot; require citations; validate that cited ids exist; apply a score threshold; and run faithfulness checks in offline evals. Structured citations make every claim auditable.

How do you enforce multi-tenant isolation in retrieval?

The tenant id comes from the JWT and goes inside the vector query as a WHERE filter, not as post-filtering in Java. Back it with Postgres row-level security or per-tenant partitions, so a bug in one query cannot leak data across tenants.

A user says the bot missed an obvious clause. How do you debug?

Replay the query and log the retrieved ids and scores. Was the clause chunked correctly? Is it in the index and up to date? Where does it rank, and what does the query embedding match instead? Was it filtered out? Then look at the prompt and generation. Most "LLM bugs" in RAG turn out to be retrieval or ingestion bugs.

08Quick check

The knowledge base is one 80-page MSA (well under 200k tokens). What do you build?

Anthropic's guidance: under about 200k tokens, skip RAG.

The answer about the liability cap misses the carve-out in 12.2. Most likely cause?

If the right chunk isn't in context, nothing downstream helps. Use clause chunks, larger k plus rerank.

Why pass input_type="query" at search time with Voyage?

Documents use "document" at ingestion; mismatching or omitting it hurts recall.

Where must the tenant filter run?

Post-filtering can leak or return too few rows; the database should never return another tenant's chunk.

10Cheat sheet

Cheat sheet
  • Load → chunk → embed → store (offline); embed query → retrieve → assemble → generate (online).
  • < ~200k tokens: no RAG, cache the prompt.
  • Contracts: one clause per chunk, id doc#clause, section as metadata. Prose: 300–800 tokens, 10–20% overlap.
  • Same embedding model both sides; input_type document/query; store model per row.
  • Unit vectors: cosine = dot product; pgvector <=>, <#>, <->.
  • k = 3–8, or 20–50 → rerank to 5; add a min score.
  • Sources in XML with ids, question last, "say so if not found", validate citations.
  • Tenant filter inside the vector query + RLS.
