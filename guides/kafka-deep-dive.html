Go deeper: the log in full

Kafka is a distributed, replicated, append-only log. A topic is a named stream, split into partitions. Each partition is an ordered sequence of records, each with a monotonically increasing offset. Records are not deleted when read; they are kept for a retention period (retention.ms, default 7 days) or size, and every consumer group tracks its own position.

03Brokers, replicas and acks

RF 3copies of each partition
min ISR 2writes need 2 in-sync copies
acks=alldefault since Kafka 3.0
30 slag before a follower leaves the ISR

  3. FollowersFetch from the leader and append

  5. LeaderWith acks=all, acks the producer (if ISR ≥ min ISR)
  6. ControllerIf the leader dies, KRaft elects a new one from the ISR
Common wrong answer

"acks=all means all replicas." It means all replicas currently in the ISR. If the ISR has shrunk to just the leader and min.insync.replicas=1, acks=all is effectively acks=1. That is why you set min ISR to 2.

Go deeper: replication terms and protocol

A broker is a Kafka server. Each partition has one leader replica (handles all produce and, by default, fetch requests) and followers that copy the leader's log. Cluster metadata and leader election are managed by the KRaft controller quorum; Kafka 4.0 removed ZooKeeper entirely.

TermMeaning
Replication factor (RF)Copies of each partition. RF = 3 is the production norm.
ISR (in-sync replicas)Replicas caught up with the leader within replica.lag.time.max.ms (30 s default). Only ISR members can become leader cleanly.
High watermarkThe offset up to which all ISR members have the data. Consumers only see records below it, so they never read something that could vanish on failover.
acks (producer)0: fire and forget. 1: leader wrote it; lost if the leader dies before followers copy. all (default since Kafka 3.0): every ISR member has it.
min.insync.replicasWith acks=all, the minimum ISR size for a write to succeed. RF 3 + min ISR 2 tolerates one broker down without losing acknowledged writes; with two down, producers get NotEnoughReplicasException instead of silently writing to one copy.
unclean.leader.election.enableFalse by default: an out-of-sync replica may not become leader, choosing consistency over availability.

The replication protocol

  1. Producer sends a batch to the partition leader.
  2. Leader appends to its log. Followers send fetch requests (like consumers) and append what they receive.
  3. A follower's fetch position tells the leader how far it has replicated. When all ISR members pass an offset, the leader advances the high watermark.
  4. With acks=all the leader responds once the batch is below the high watermark, provided ISR size ≥ min.insync.replicas.
  5. A follower that stops fetching or falls behind for longer than replica.lag.time.max.ms is removed from the ISR; it rejoins when caught up.
  6. If the leader dies, the controller picks a new leader from the ISR; leader epochs let followers truncate any records that never reached the high watermark.

04Producers: keys, batching, idempotence

Key picks partition

Same key, same partition (while the count is unchanged). No key: sticky partitioner fills one batch at a time.

Batching

batch.size 16 KB, linger.ms 5 ms (Kafka 4.0). Raise to 10–50 ms with lz4/zstd for throughput.

Idempotent producer

Default since 3.0. De-duplicates retried batches, not your app calling send() twice.

delivery.timeout.ms

120 s total, retries included. Then the callback fails: log, alert, decide.

Go deeper: producer details
  • Partitioning: with a key, the default partitioner uses murmur2(key) mod partition count, so the same key always lands on the same partition (while the count is unchanged). Without a key, the producer uses a sticky partitioner: it fills a batch for one partition before moving to another, which gives bigger batches than round-robin.
  • Batching: records are grouped per partition up to batch.size (16 KB default) or until linger.ms elapses. Kafka 4.0 changed the linger.ms default from 0 to 5 ms because tiny batches waste broker CPU and network. Raise it (10–50 ms) with compression.type=lz4 or zstd for throughput.
  • Idempotent producer (default since 3.0): the broker assigns a producer ID and tracks a sequence number per partition, so a retried batch is de-duplicated and ordering holds with up to 5 in-flight requests. It removes duplicates caused by producer retries, not duplicates caused by your application calling send() twice.
  • delivery.timeout.ms (120 s default) bounds the total time to get an ack, including retries. After that the callback gets an exception: log it, alert, and decide (outbox rows make this safe).

Go deeper: groups, commit strategies and rebalance protocols

Consumer groups

Consumers sharing a group.id split the partitions: each partition is read by exactly one consumer in the group at a time. Parallelism is capped by the partition count; a seventh consumer on a six-partition topic sits idle. Different groups each get every record (pub-sub).

P0P1→Consumer 1 P2P3→Consumer 2 P4P5→Consumer 3

Figure: one group, six partitions, three consumers. Adding consumers beyond six adds no parallelism.

Offsets and commit strategies

The consumer commits "I have processed up to offset N" to the internal __consumer_offsets topic. On restart or rebalance, the new owner resumes from the last committed offset. When you commit decides the guarantee:

StrategyBehaviour on crashGuarantee
Commit before processingRecords fetched but not processed are skippedAt-most-once
Commit after processingRecords processed but not committed are processed againAt-least-once (the normal choice; make processing idempotent)
Auto commit (enable.auto.commit=true, every 5 s in the plain client)Commits during poll() what the previous poll returned; with async hand-off it can commit unprocessed recordsUsually at-least-once, but easy to break
Transactional (offsets committed inside a producer transaction)Output records and offsets commit or abort togetherExactly-once for Kafka-to-Kafka processing

Spring Kafka disables the client's auto commit and commits itself according to the container AckMode: BATCH (default, after all records from one poll are processed), RECORD, MANUAL / MANUAL_IMMEDIATE (you call Acknowledgment.acknowledge()), and time or count based modes.

When a consumer joins, leaves, crashes (no heartbeat within session.timeout.ms, 45 s default) or takes longer than max.poll.interval.ms (5 min default) between polls, the group rebalances.

ProtocolHowImpact
Eager (Range, RoundRobin, Sticky assignors)Every consumer revokes all partitions, then receives a new assignmentStop-the-world: whole group pauses
Cooperative sticky (CooperativeStickyAssignor)Incremental: only partitions that must move are revoked, over two short roundsOthers keep consuming; the standard choice on the classic protocol
New consumer protocol (KIP-848, GA in Kafka 4.0)Opt in with group.protocol=consumer; the broker's group coordinator computes assignments and reconciles each member incrementally, without a global sync barrierFaster, more stable rebalances in big groups
Static membership (group.instance.id)A restarted pod with the same instance ID gets its partitions back without a rebalance, if it returns within the session timeoutRolling deploys on Kubernetes stop triggering rebalance storms

Kafka 4.0 also introduced share groups (KIP-932, "queues for Kafka"), which reached production readiness in 4.2: several consumers can read the same partition with per-record acknowledgement and delivery counts, giving queue semantics without one-consumer-per-partition. Mention it as the modern answer to "Kafka can't do work queues", but most production clusters still use classic groups.

06Ordering and delivery semantics

At-least-once realistic default

  • Producer retries + commit after processing
  • Duplicates happen

Make consumers idempotent: unique event ID, upsert, processed-messages table.

Exactly-once

  • Kafka-to-Kafka read-process-write
  • Needs transactional.id + read_committed
  • Not for DB writes, emails, payments

Stream processing inside Kafka only.

public void handle(PaymentEvent e) {
    kafkaTemplate.send("ledger-entries", e.accountId(), toLedgerEntry(e));
}
// Consumers of ledger-entries:

Key = ordering unit

envelopeId for an envelope's events, accountId for ledger entries.

Don't add partitions later

It changes hash(key) mod n. Over-provision keyed topics (12–48).

Consumers can break it

A thread pool hand-off, or a retry topic while later records continue.

Go deeper: ordering and delivery in full
  • Ordering is guaranteed only within a partition. Choose the key so that everything that must stay ordered shares it: envelopeId for an envelope's lifecycle events, accountId for ledger entries.
  • Adding partitions changes hash(key) mod n, so new records for a key may go to a different partition while old ones are still unprocessed. Over-provision partitions up front (for example 12–48) instead of increasing later on keyed topics.
  • Consumer-side ordering breaks if you hand records to a thread pool, or if a failing record is moved to a retry topic while later records for the same key continue.

Delivery semantics

At-least-once is the realistic default: producer retries plus commit-after-processing. Duplicates happen, so consumers must be idempotent (unique constraint on an event ID, upsert, or a processed-messages table).

Exactly-once in Kafka means: in a read-process-write loop from Kafka to Kafka, each input affects the output exactly once. It needs the idempotent producer, a transactional.id, the consumer offsets sent inside the transaction, and downstream consumers reading with isolation.level=read_committed so they skip aborted records. It does not extend to side effects outside Kafka (a DB write, an email, a payment API call); those still need idempotency or an outbox.

07Storage and log compaction

Segments

A partition is a directory of 1 GB segment files. Only the active one is written; offset and time indexes make seeks a binary search.

Why it is fast

Sequential appends, OS page cache, batches stored compressed as-is, zero-copy sendfile.

Compaction

cleanup.policy=compact keeps the latest record per key. A null value (tombstone) deletes the key.

k1=ak2=xk1=bk2=y
Go deeper: storage and compaction in full

Each partition is a directory of segment files (segment.bytes, 1 GB default). Only the active segment is written; closed segments are deleted or compacted as a unit. Each segment has a sparse offset index and a time index, so seeking to an offset is a binary search plus a short scan.

Why Kafka is fast: sequential appends (disks and SSDs love them), reliance on the OS page cache rather than a JVM heap cache, batching and compression end to end (the broker stores the producer's compressed batch as-is), and zero-copy transfer from page cache to socket (sendfile) when TLS is off.

With cleanup.policy=compact, Kafka keeps at least the latest record for each key and discards older ones in the background. A record with a null value (a tombstone) deletes the key after delete.retention.ms. Use compacted topics for "current state per key": user settings, a tenant's configuration, Kafka Streams changelogs, and __consumer_offsets itself. A new service can rebuild its cache by reading the compacted topic from the beginning. Compaction never reorders records and leaves the active segment alone, so recent duplicates are still visible.

        var recoverer = new DeadLetterPublishingRecoverer(template);

Common mistakes
  • Default DefaultErrorHandler: 10 instant attempts, then log and skip.
  • No ErrorHandlingDeserializer: a bad payload jams poll() forever.
  • DLT with fewer partitions than the source, or with no owner and no alert.
  • "Save then send" instead of a transactional outbox.
  • More consumers than partitions across all pods.
Go deeper: lag table, DLQ rules, concurrency and production checklist

Lag = log-end offset − committed offset, per partition. Measure it with kafka-consumer-groups.sh --describe --group X, Burrow or the client's records-lag-max metric, and alert on lag growth rate and time-lag, not a raw number.

For per-key ordering with more parallelism than partitions, process records in parallel across keys within a partition (Confluent Parallel Consumer does this) and commit only the contiguous processed offset.

Blocking retries (DefaultErrorHandler)

Re-seeks the partition and retries the same record in place. Preserves order, but blocks the whole partition while backing off. Good for short transient failures (a 500 ms DB blip). Keep total back-off well under max.poll.interval.ms.

Non-blocking retries (@RetryableTopic)

On failure, the record is published to topic-retry-0, -retry-1… with growing delays, then to a DLT. The main partition keeps flowing. Breaks per-key ordering, so use it only where order does not matter (notifications, webhooks).

  • Without configuration, DefaultErrorHandler uses FixedBackOff(0, 9): 10 attempts with no delay, then logs and skips. That is rarely what you want.
  • Deserialization exceptions, ClassCastException and a few others are non-retryable by default and go straight to the recoverer.
  • Wrap your deserializer in ErrorHandlingDeserializer; otherwise a malformed record fails inside poll() and the container can never get past it.
  • The DLT needs at least as many partitions as the source topic when the recoverer keeps the partition number.
  • A DLT is useless without an owner: alerting on DLT growth, a dashboard and a replay tool.

@KafkaListener concurrency

concurrency = "6" creates six KafkaMessageListenerContainers, each with its own consumer and thread, all in one group. Across all pods the total consumer count should not exceed the partition count: 3 pods × concurrency 6 = 18 consumers needs at least 18 partitions to be useful. Each consumer thread processes its records serially, which is what preserves per-partition order.

Production checklist

  • Topics: RF 3, min.insync.replicas=2, producers acks=all with idempotence. Create topics through infrastructure code, not auto-create.
  • Publish from the database with a transactional outbox, never "save then send" in application code (see Distributed transactions).
  • Every consumer idempotent; every event carries an eventId, a schema version and a timestamp. Use a schema registry (Avro or Protobuf) with compatibility checks for cross-team topics.
  • Add the tenant ID in a header and propagate trace context (Micrometer Tracing adds W3C traceparent headers to records).
  • Graceful shutdown: let in-flight records finish and commit before the pod dies (terminationGracePeriodSeconds above your slowest batch).

10Quick check

RF 3, acks=all, min.insync.replicas=1. Two followers fall out of the ISR. What happens to writes?

acks=all means all current ISR members. Set min ISR to 2 so writes fail instead.

A topic has 6 partitions. You run 3 pods with concurrency = "4". How many consumers do work?

Each partition goes to one consumer in the group, so parallelism is capped at 6.

Only partition 4 lags; the others are fine. Most likely cause?

Uneven lag points to skew. Key by a finer ID or salt the hot key.

You enabled Kafka transactions. Is the DB insert in your listener now exactly-once?

Side effects outside Kafka can still repeat after a rebalance.

11Interview questions with senior answers

How do you guarantee ordering for one entity's events?

Use the entity ID as the record key so all its events go to one partition, keep the partition count stable, enable the idempotent producer so retries cannot reorder, and process each partition serially on the consumer. Use blocking retries for that topic; a retry topic would let later events overtake a failed one.

What does a consumer do, and what can it not do? (Apple)

It polls records from its assigned partitions, commits offsets, seeks to any offset, and can pause and resume partitions. It cannot delete or modify records, cannot acknowledge individual records out of order on the classic protocol (commits are a position per partition), cannot read a partition another member of its group owns, and must call poll() within max.poll.interval.ms or be kicked out. Share groups (KIP-932) add per-record acknowledgement.

Consumer lag is growing. Walk me through it.

First, is it all partitions or one? One means a hot key or a poison pill stuck in retries. All means throughput. Then check rebalance logs: frequent rebalances mean polls exceed max.poll.interval.ms. Then where time goes per record: usually a synchronous DB or HTTP call. Fixes in order: batch the work, scale consumers up to partitions, tune fetch and poll sizes, and only then repartition. If the downstream database is the bottleneck, more consumers make it worse.

Can you lose messages with acks=all?

Yes, if min.insync.replicas=1 and the ISR has shrunk to the leader, which then dies; or if unclean leader election is enabled; or if the producer gives up after delivery.timeout.ms and the application ignores the failed callback; or if the consumer commits before processing. With RF 3, min ISR 2, unclean election off and a handled callback, an acknowledged write survives one broker failure.

Explain exactly-once in Kafka and its limits.

Idempotent producer removes duplicates from producer retries. Transactions let a producer write to several partitions and commit consumer offsets atomically; read_committed consumers never see aborted records. That makes consume-transform-produce exactly-once inside Kafka. Writing to Postgres or calling an API is outside the transaction, so those sinks need idempotent writes keyed by event ID.

What triggers a rebalance and how do you reduce its impact?

Members joining or leaving, missed heartbeats, exceeding max.poll.interval.ms, and partition count changes. Reduce it with the cooperative sticky assignor or the KIP-848 protocol, static membership for rolling deploys, sizing max.poll.records so a batch finishes well inside the poll interval, and committing offsets in onPartitionsRevoked.

How many partitions should a topic have?

Enough for peak consumer parallelism with headroom: target throughput divided by what one consumer handles, times 1.5–2. Then round up so keyed topics never need re-partitioning. Too many costs broker memory, file handles and longer failover; a few thousand partitions per broker is fine on KRaft but there is no reason to create 1,000 for a topic doing 200 messages per second.

How do you handle a poison message?

Classify exceptions: non-retryable (validation, deserialization) go straight to the DLT; transient ones get bounded exponential back-off. ErrorHandlingDeserializer stops a bad payload from crashing poll(). The DLT record carries the original topic, partition, offset and exception in headers, and someone owns replaying it.

What is log compaction and when would you use it?

A cleanup policy that keeps the latest record per key instead of deleting by age. Use it for state topics (configuration, latest status per entity, Kafka Streams changelogs) so a consumer can rebuild full current state by reading from the start. Tombstones (null values) delete a key.

Kafka or RabbitMQ for sending emails and SMS?

If it is a pure task queue with priorities, per-message TTL and delayed retries, RabbitMQ fits naturally. If the same events also feed analytics or audit, need replay, or the company already runs Kafka, use Kafka with a retry-topic chain and a DLT. I would not add a second broker just for notifications.

What problems did you face with Kafka in production? (Goldman)

Have one true story with numbers. A typical shape: a consumer did one HTTP call per record, a downstream slowdown pushed batch time past max.poll.interval.ms, the group rebalanced in a loop and lag climbed to hours. Fix: lowered max.poll.records from 500 to 50, moved to a batch listener with bulk writes, made the handler idempotent so redelivery after rebalances was harmless, and added a lag-rate alert.

Why is Kafka fast if it writes everything to disk?

Sequential appends, the OS page cache instead of a JVM cache, batching and compression stored as-is, and zero-copy transfer to consumers. Recent data is usually served from memory; disk is mostly for durability and replay.

Hands-on exercise (60 minutes)
  1. Start a single-node KRaft broker: docker run -d -p 9092:9092 --name kafka apache/kafka:4.1.0 (any 4.x tag works).
  2. Create a topic with 3 partitions: docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic doc-events --partitions 3.
  3. Spring Boot app with spring-kafka: a REST endpoint that publishes DocumentEvent(eventId, envelopeId, type) keyed by envelopeId, and a @KafkaListener with concurrency = "3" that logs partition, offset and thread.
  4. Publish 30 events for 5 envelope IDs. Confirm each envelope's events always appear on the same partition and in order.
  5. Make the listener throw for type = "BAD". Configure DefaultErrorHandler with 3 retries and DeadLetterPublishingRecoverer. Check the DLT with kafka-console-consumer.sh --topic doc-events-dlt --from-beginning --property print.headers=true.
  6. Add Thread.sleep(200) to the listener, publish 2,000 events and watch lag with kafka-consumer-groups.sh --describe --group audit. Switch to a batch listener with a bulk write and compare drain time.
  7. Stretch: start a second app instance and watch the rebalance in the logs; then set group.protocol=consumer and compare.

12Cheat sheet

Cheat sheet
  • Topic → partitions → offsets. Ordering only per partition; key = ordering unit.
  • RF 3, min ISR 2, acks=all, idempotent producer. KRaft, no ZooKeeper in 4.0.
  • One consumer per partition per group; partitions cap parallelism.
  • Commit after processing = at-least-once; consumers idempotent.
  • EOS = Kafka-to-Kafka only (transactional.id + read_committed).
  • Rebalance: cooperative sticky, KIP-848, static membership; keep poll work under max.poll.interval.ms.
  • Lag fixes: batch writes, scale to partitions, fix hot keys, backpressure.
  • Blocking retries keep order; @RetryableTopic does not. Always a DLT with an owner.
