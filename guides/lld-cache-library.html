Cache Library with Pluggable Eviction and TTL

Build an in-process cache library: bounded size, per-entry TTL, eviction policy you can swap (LRU, LFU, FIFO) without touching the cache, thread-safe, with stats and listeners. Seniors are separated by two things: making eviction a real abstraction, and getting the expiry races right.

Time-box: 60–120 min Seen: LRU/LFU at ~9 companies; full library at Groww, Tekion, Microsoft, Confluent

01What the interviewer is grading

The reports show three flavours of the same problem:

Open-ended library (Groww, Tekion)

Groww SDE-2 (Apr 2025): two hours, the whole statement was "build a scalable cache"; the candidate shipped add/contains/invalidate/setMaxSize with FIFO via a queue. Feedback: "This isn't scalable. FIFO isn't enough — what if we want different eviction logic?" Tekion SDE-2 (Jun 2026, selected): "design your own library of a TTL based caching system" — running code not required, "clear classes, design patterns were expected"; the candidate called it the toughest round.

Layered follow-ups (Microsoft)

Start with a key-value store, add TTL, then "what races exist on expiry?", then add LRU. Each layer must slot into the previous code without a rewrite.

Algorithmic core (Confluent, Freshworks, Razorpay)

Confluent: LRU with TTL plus "average of all active values" in the most optimised way. Freshworks: LRU cache, talk through brute force to O(1). Razorpay OA: LFU with ties broken by smallest key.

Across all of them: requirements you defined yourself, an EvictionPolicy interface (the Groww rejection in one line), correct O(1) or O(log n) structures, an honest concurrency story, an injectable clock so TTL is testable, and patterns you can name and justify.

02Clarifying questions to ask

QuestionWhy it matters
Library embedded in one JVM, or a cache service?Library means generics, no network, thread safety inside. Service means sharding and replication (an HLD conversation).
Capacity by entry count or by weight (bytes)?Weight needs a Weigher and evicting until total weight fits; count is simpler. Offer weight as an extension.
Which eviction policies? Should users plug their own?Answer before they ask: yes, via an interface. Default LRU.
TTL per entry, a default, or both? Expire-after-write or after-access?Changes what you store per entry and whether reads extend life.
Must expired entries free memory promptly, or is lazy expiry OK?Lazy-only can hold dead entries forever; add a sweeper.
Read-heavy or write-heavy? How many threads?Decides between one lock, lock striping, or Caffeine-style buffered reads.
Null keys or values allowed?Reject both: null as "absent" makes get ambiguous.
Do callers need a loader (read-through) or stats?Loader brings the thundering-herd question; stats need LongAdder.

03Requirements

Functional

  • get, put (default TTL), put with TTL, remove, size, clear.
  • Max size; on overflow evict per configured policy.
  • Expired entries are never returned.
  • Policies: LRU, LFU, FIFO; custom ones via interface.
  • Removal listener with cause (EXPIRED, EVICTED, EXPLICIT, REPLACED).
  • Stats: hits, misses, evictions.

Non-functional

  • Thread-safe; no lost updates; listener never runs under the cache lock.
  • O(1) get/put for LRU/FIFO; O(log n) acceptable for LFU and expiry bookkeeping.
  • Deterministic tests via injected Clock.
  • Builder-based configuration, immutable after build.

Out of scope

  • Distribution, replication, persistence.
  • Off-heap storage.
  • Write-behind to a database (extension only).

Caller→ InMemoryCachelock, TTL, size→ HashMapkey → Entry + EvictionPolicyLRU · LFU · FIFO + Expiry heapby expiresAt → RemovalListenerafter unlock

Figure: the cache owns data and time; the policy only owns ordering of keys; listeners hear about removals outside the lock.

Patterns and why

  • Strategy for eviction. The policy sees keys and events only, so a new policy is one class and no change to the cache. This is the exact gap the Groww interviewer called out.
  • Builder for configuration: many optional parameters, validation in build(), immutable result.
  • Observer for removal listeners and stats hooks.
  • Decorator for cross-cutting layers: LoadingCache (read-through), TransactionalCache, metrics.
  • Template / null object avoided: no abstract base class with half the logic; composition is easier to defend.

05Core code

public interface Cache<K, V> {
    Optional<V> get(K key);
    void put(K key, V value);                 // default TTL
    void put(K key, V value, Duration ttl);   // null ttl = never expires
    boolean remove(K key);
    int size();
    CacheStats stats();
}

public enum RemovalCause { EXPLICIT, REPLACED, EXPIRED, EVICTED }

@FunctionalInterface
public interface RemovalListener<K, V> {
    void onRemoval(K key, V value, RemovalCause cause);
}

/** Owns only key ordering. Called with the cache lock held, so implementations need no locking. */
public interface EvictionPolicy<K> {
    void onInsert(K key);
    void onAccess(K key);
    void onRemove(K key);
    K victim(); // next key to evict, or null if empty
}

LRU and FIFO are a LinkedHashSet: insertion order is the list, the hash gives O(1) removal. "Move to back on access" is remove + add. If the interviewer insists on the hand-rolled doubly linked list (Freshworks did), it is the same shape: HashMap<K, Node> plus head/tail sentinels.

public final class LruPolicy<K> implements EvictionPolicy<K> {
    private final LinkedHashSet<K> order = new LinkedHashSet<>(); // eldest first

    public void onInsert(K key) { order.add(key); }
    public void onAccess(K key) { order.remove(key); order.add(key); }
    public void onRemove(K key) { order.remove(key); }
    public K victim() { return order.isEmpty() ? null : order.iterator().next(); }
}

public final class FifoPolicy<K> implements EvictionPolicy<K> {
    private final LinkedHashSet<K> order = new LinkedHashSet<>();

    public void onInsert(K key) { order.add(key); }
    public void onAccess(K key) { }                       // access does not change FIFO order
    public void onRemove(K key) { order.remove(key); }
    public K victim() { return order.isEmpty() ? null : order.iterator().next(); }
}

/** LFU, ties broken by least-recently-used within the same frequency. */
public final class LfuPolicy<K> implements EvictionPolicy<K> {
    private final Map<K, Integer> freq = new HashMap<>();
    private final TreeMap<Integer, LinkedHashSet<K>> buckets = new TreeMap<>();

    public void onInsert(K key) { freq.put(key, 1); bucket(1).add(key); }

    public void onAccess(K key) {
        int f = freq.merge(key, 1, Integer::sum);
        unlink(key, f - 1);
        bucket(f).add(key);
    }

    public void onRemove(K key) {
        Integer f = freq.remove(key);
        if (f != null) unlink(key, f);
    }

    public K victim() {
        var lowest = buckets.firstEntry(); // O(log F); empty buckets are always removed
        return lowest == null ? null : lowest.getValue().iterator().next();
    }

    private LinkedHashSet<K> bucket(int f) { return buckets.computeIfAbsent(f, x -> new LinkedHashSet<>()); }

    private void unlink(K key, int f) {
        LinkedHashSet<K> b = buckets.get(f);
        b.remove(key);
        if (b.isEmpty()) buckets.remove(f);
    }
}

For the classic O(1) LFU, replace the TreeMap with a HashMap plus a minFreq int: on insert set minFreq = 1; on access, if the old bucket was minFreq and is now empty, increment it. Arbitrary removals (TTL, explicit delete) can leave minFreq stale, which is why the TreeMap version is the safer default in a library. For Razorpay's "ties go to the smallest key", make each bucket a TreeSet<K>.

public final class InMemoryCache<K, V> implements Cache<K, V> {
    private record Entry<V>(V value, long expiresAt) {
        boolean expired(long now) { return expiresAt != 0 && now >= expiresAt; }
    }
    private record Expiry<K, V>(K key, Entry<V> entry) {}
    private record Removal<K, V>(K key, V value, RemovalCause cause) {}

    private final Map<K, Entry<V>> map = new HashMap<>();
    private final PriorityQueue<Expiry<K, V>> expiries =
            new PriorityQueue<>(Comparator.comparingLong((Expiry<K, V> e) -> e.entry().expiresAt()));
    private final ReentrantLock lock = new ReentrantLock(); // ponytail: one lock; stripe into segments if contended
    private final EvictionPolicy<K> policy;
    private final int maxSize;
    private final Duration defaultTtl;
    private final Clock clock;
    private final RemovalListener<K, V> listener;
    private final CacheStats stats = new CacheStats();

    InMemoryCache(CacheBuilder<K, V> b) {
        this.policy = b.policy; this.maxSize = b.maxSize; this.defaultTtl = b.defaultTtl;
        this.clock = b.clock; this.listener = b.listener;
    }

    @Override
    public Optional<V> get(K key) {
        Objects.requireNonNull(key);
        List<Removal<K, V>> removed = new ArrayList<>();
        Optional<V> result;
        lock.lock();
        try {
            Entry<V> e = map.get(key);
            if (e != null && e.expired(clock.millis())) {
                removeEntry(key, e, RemovalCause.EXPIRED, removed); // lazy expiry
                e = null;
            }
            if (e == null) {
                stats.miss();
                result = Optional.empty();
            } else {
                policy.onAccess(key);
                stats.hit();
                result = Optional.of(e.value());
            }
        } finally {
            lock.unlock();
        }
        fire(removed);
        return result;
    }

    @Override
    public void put(K key, V value) { put(key, value, defaultTtl); }

    @Override
    public void put(K key, V value, Duration ttl) {
        Objects.requireNonNull(key);
        Objects.requireNonNull(value);
        List<Removal<K, V>> removed = new ArrayList<>();
        lock.lock();
        try {
            long now = clock.millis();
            Entry<V> fresh = new Entry<>(value, ttl == null ? 0 : now + ttl.toMillis());
            Entry<V> old = map.put(key, fresh);
            if (old == null) {
                policy.onInsert(key);
            } else {
                policy.onAccess(key);
                removed.add(new Removal<>(key, old.value(), RemovalCause.REPLACED));
            }
            if (fresh.expiresAt() != 0) expiries.add(new Expiry<>(key, fresh));
            purgeExpired(now, removed);           // prefer dropping dead entries over live ones
            while (map.size() > maxSize) {
                K victim = policy.victim();
                removeEntry(victim, map.get(victim), RemovalCause.EVICTED, removed);
                stats.eviction();
            }
        } finally {
            lock.unlock();
        }
        fire(removed);
    }

    @Override
    public boolean remove(K key) {
        List<Removal<K, V>> removed = new ArrayList<>();
        lock.lock();
        try {
            Entry<V> e = map.get(key);
            if (e == null) return false;
            removeEntry(key, e, RemovalCause.EXPLICIT, removed);
        } finally {
            lock.unlock();
        }
        fire(removed);
        return true;
    }

    /** Called by a scheduled sweeper too, so memory is reclaimed for keys nobody reads again. */
    public void cleanUp() {
        List<Removal<K, V>> removed = new ArrayList<>();
        lock.lock();
        try { purgeExpired(clock.millis(), removed); } finally { lock.unlock(); }
        fire(removed);
    }

    private void purgeExpired(long now, List<Removal<K, V>> removed) {
        while (!expiries.isEmpty() && expiries.peek().entry().expired(now)) {
            Expiry<K, V> x = expiries.poll();
            // identity check: skip heap items for entries that were overwritten or removed since
            if (map.get(x.key()) == x.entry()) removeEntry(x.key(), x.entry(), RemovalCause.EXPIRED, removed);
        }
    }

    private void removeEntry(K key, Entry<V> e, RemovalCause cause, List<Removal<K, V>> removed) {
        map.remove(key);
        policy.onRemove(key);
        removed.add(new Removal<>(key, e.value(), cause));
    }

    private void fire(List<Removal<K, V>> removed) { // outside the lock: listener may be slow or re-enter
        for (Removal<K, V> r : removed) {
            try { listener.onRemoval(r.key(), r.value(), r.cause()); } catch (RuntimeException ignored) { }
        }
    }

    @Override public int size() { lock.lock(); try { return map.size(); } finally { lock.unlock(); } }
    @Override public CacheStats stats() { return stats; }
}
public final class CacheBuilder<K, V> {
    int maxSize = 10_000;
    Duration defaultTtl;                            // null = no expiry
    EvictionPolicy<K> policy = new LruPolicy<>();
    Clock clock = Clock.systemUTC();
    RemovalListener<K, V> listener = (k, v, c) -> { };

    public CacheBuilder<K, V> maxSize(int n) { this.maxSize = n; return this; }
    public CacheBuilder<K, V> defaultTtl(Duration d) { this.defaultTtl = d; return this; }
    public CacheBuilder<K, V> policy(EvictionPolicy<K> p) { this.policy = p; return this; }
    public CacheBuilder<K, V> clock(Clock c) { this.clock = c; return this; }
    public CacheBuilder<K, V> listener(RemovalListener<K, V> l) { this.listener = l; return this; }

    public Cache<K, V> build() {
        if (maxSize <= 0) throw new IllegalArgumentException("maxSize must be positive");
        if (defaultTtl != null && (defaultTtl.isNegative() || defaultTtl.isZero())) {
            throw new IllegalArgumentException("ttl must be positive");
        }
        return new InMemoryCache<>(this);
    }
}

public final class CacheStats {
    private final LongAdder hits = new LongAdder(), misses = new LongAdder(), evictions = new LongAdder();
    void hit() { hits.increment(); }
    void miss() { misses.increment(); }
    void eviction() { evictions.increment(); }
    public double hitRate() {
        long h = hits.sum(), total = h + misses.sum();
        return total == 0 ? 1.0 : (double) h / total;
    }
}

The sweeper is one line in the demo: scheduler.scheduleAtFixedRate(cache::cleanUp, 1, 1, TimeUnit.SECONDS). Redis does the same pair: passive expiry when a key is touched, plus an active cycle that samples keys with a TTL.

06Concurrency and edge cases

Race / edgeWhat goes wrongFix in this design
Expiry vs overwrite (Microsoft's question)Thread A sees key expired and deletes it; thread B has just put a fresh value; A deletes B's fresh value.Check and delete under one lock, and the sweeper deletes only if map.get(key) == entry (the entry it scheduled). With a ConcurrentHashMap design the same idea is map.remove(key, entry), the conditional remove.
LRU reads mutate order"Reads are safe" is false: every get reorders the list. A ReadWriteLock read lock is wrong for LRU.Exclusive lock for get. At scale, Caffeine records reads into lossy ring buffers and replays them under a try-lock, so readers rarely block.
Check-then-act in callersif (!cache.contains(k)) cache.put(k, load()) loads twice.Offer get(key, loader) that computes once per key (per-key CompletableFuture in a ConcurrentHashMap), which also stops a cache stampede.
Listener re-enters the cacheDeadlock or ConcurrentModificationException if called under the lock.Collect removals, fire after unlock(); swallow and log listener exceptions.
Clock goes backwardsNTP step makes entries live longer or die early.Use System.nanoTime-based ticker for durations in production; inject a Clock/ticker so tests can advance time.
Stale heap itemsOverwrite leaves an old Expiry in the heap.Identity check on purge; heap is bounded by puts, and the sweeper drains it.
Size 0, TTL 0, null valueDegenerate behaviour.Validated in the builder; put rejects nulls.
Evicting during a burst of expired entriesLive LRU entry evicted while dead entries still occupy slots.purgeExpired runs before the eviction loop.
Scaling the lock, in the order to propose it

1) One lock, measured. 2) Segments: N independent caches selected by hash(key) % N, each with its own map, policy and lock; LRU becomes approximately global, which is usually fine (Guava did this). 3) ConcurrentHashMap for data plus buffered policy updates (Caffeine). Caffeine's W-TinyLFU also adds an admission filter so a one-hit wonder cannot evict a hot entry; its published traces show materially higher hit rates than plain LRU.

07Extensions interviewers add mid-round

"Add a new eviction policy" (Groww)

Implement EvictionPolicy; pass it to the builder. Zero changes to InMemoryCache. If they ask for TTL-aware eviction ("evict the entry closest to expiry"), that is a policy backed by a TreeSet ordered by expiresAt, which needs the expiry in onInsert; widen the signature to onInsert(K key, long expiresAt) once and every policy ignores what it does not need.

"Average of all active (non-expired) values in the best complexity" (Confluent)

Keep sum and count as fields, updated in removeEntry and put (subtract old value on replace). average() first calls purgeExpired(now), which pops only the entries that have expired, each in O(log n), then returns sum / count. Amortised O(log n) per expired entry, O(1) otherwise. If timestamps are given strictly increasing (ask, as that candidate did), the heap can be a plain FIFO deque.

"Support transactions: begin, commit, rollback, nested" (Rippling-style)

A decorator with a Deque<Map<K, Optional<V>>> of write sets (empty Optional = tombstone for delete). put/remove write to the top map when a transaction is open. get searches the stack top-down, then the base cache. commit pops the top and merges into the next layer, or applies to the base if it was the outermost. rollback just pops. Per-thread transactions: keep the stack in a ThreadLocal; isolation between threads is then read-committed.

public final class TransactionalCache<K, V> {
    private final Cache<K, V> base;
    private final Deque<Map<K, Optional<V>>> txs = new ArrayDeque<>();

    public TransactionalCache(Cache<K, V> base) { this.base = base; }

    public void begin() { txs.push(new HashMap<>()); }
    public void put(K k, V v) { if (txs.isEmpty()) base.put(k, v); else txs.peek().put(k, Optional.of(v)); }
    public void remove(K k) { if (txs.isEmpty()) base.remove(k); else txs.peek().put(k, Optional.empty()); }

    public Optional<V> get(K k) {
        for (Map<K, Optional<V>> layer : txs) { // ArrayDeque iterates from the top of the stack
            if (layer.containsKey(k)) return layer.get(k);
        }
        return base.get(k);
    }

    public void rollback() { requireTx(); txs.pop(); }

    public void commit() {
        requireTx();
        Map<K, Optional<V>> top = txs.pop();
        if (!txs.isEmpty()) { txs.peek().putAll(top); return; }
        top.forEach((k, v) -> v.ifPresentOrElse(val -> base.put(k, val), () -> base.remove(k)));
    }

    private void requireTx() { if (txs.isEmpty()) throw new IllegalStateException("no transaction"); }
}
"Read-through / write-through to a database"

LoadingCache decorator with a CacheLoader<K,V>; single-flight per key as above. Write-through: write DB then cache (or invalidate). Write-behind: queue writes and flush in batches; mention data loss on crash and ordering per key.

"Expire-after-access (sliding TTL)"

On get, replace the entry with a new expiresAt and push a new heap item; the identity check makes the old heap item harmless. Offer it as a builder option, not a second cache class.

"Max memory instead of max entries"

Weigher<K,V> in the builder, a totalWeight field, and the eviction loop runs while totalWeight > maxWeight. Reject single entries heavier than the limit.

"Make it distributed"

Different problem: consistent hashing across nodes, replication or not, and invalidation (pub/sub or versioned keys). A near-cache (this library) in front of Redis is the common real answer; TTL is the safety net for missed invalidations.

09Mistakes that got candidates rejected, and review questions

Rejected for this
  • Hard-coded FIFO with no eviction abstraction, then explaining interfaces only after being challenged (Groww: "This isn't scalable... what if we want different eviction logic?"). Put the interface in the first 20 minutes.
  • Not defining requirements when the statement is one line; the requirements are part of the grade.
  • TTL checked only on read, so the cache fills with dead entries.
  • synchronized on get with a ConcurrentHashMap inside "for safety": two mechanisms, neither reasoned about.
  • Using LinkedHashMap(accessOrder=true) and calling it a library: fine as a first step, but it cannot do LFU or TTL and the follow-up exposes that.
  • System.currentTimeMillis() scattered through the code, then Thread.sleep in tests.
Why does the policy not hold the values?

Single responsibility: the cache owns data and time; the policy owns an ordering over keys. A new policy never needs to understand TTL, listeners or stats, and the cache never needs to understand frequencies.

Why a ReentrantLock instead of synchronized?

Either is correct here. ReentrantLock gives tryLock with timeout for a sweeper that should not block callers, and fairness if needed. With virtual threads, synchronized used to pin the carrier thread before JDK 24.

Why not a ReadWriteLock?

Because LRU and LFU mutate on read. For FIFO with no access tracking, a read lock would work, but one code path for all policies is simpler.

What is the complexity of each operation?

get: O(1) map + O(1) LRU/FIFO, O(log F) LFU. put: O(1) map, O(log n) heap insert when TTL set, O(k log n) to purge k expired entries, amortised once per entry.

How do you stop a cache stampede on a hot expired key?

Single-flight loading (one loader per key, others wait on its future), plus jittered TTLs so many keys do not expire together, plus optional refresh-ahead that reloads before expiry while serving the old value.

Why are listener exceptions swallowed?

A listener bug must not break a put that already succeeded. Log it with the key and cause; in production, run listeners on an executor so a slow one cannot add latency.

10A 90-minute plan

0–10 minWrite requirements yourself: API, max size, TTL semantics, policies, thread safety, listeners, stats. Confirm in two sentences.
10–15 minClass table and the Strategy/Builder/Observer choice. Say the Groww lesson out loud: eviction is an interface.
15–30 minCache, EvictionPolicy, LruPolicy, FifoPolicy, InMemoryCache without TTL. Test LRU.
30–50 minTTL: Entry, expiry heap, lazy expiry on get, purgeExpired, cleanUp, injected Clock. Test with a mutable clock.
50–62 minLfuPolicy, builder validation, listeners fired outside the lock, stats.
62–75 minConcurrency test with 16 threads; explain the expiry/overwrite race and the identity check.
75–90 minWhatever they add: average of active values, transactions, loader. Close with the scaling ladder (segments → Caffeine-style buffers).
