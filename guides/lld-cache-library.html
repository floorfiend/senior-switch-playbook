Cache Library with Pluggable Eviction and TTL

Build a thread-safe cache library, then defend it. Users can swap the rule for what gets thrown out when it is full: LRU, LFU or FIFO. Entries can also expire after a set time (TTL), with no race bugs.

Time-box: 60–120 min Seen: LRU/LFU at ~9 companies; full library at Groww, Tekion, Microsoft, Confluent
GrowwTekionMicrosoftConfluentWalmartGoldman SachsFreshworksRazorpayRippling
In 30 seconds
  • The cache owns the data and the timing. An EvictionPolicy only decides the order of keys.
  • LRU uses a LinkedHashSet. A read moves the key to the back. Eviction takes from the front.
  • TTL: check on every read, keep a heap sorted by expiry time, and run a cleanup job.
  • Use one lock. Call listeners after unlocking. Pass in a Clock so tests control time.
Picture it

Think of a small chai stall shelf that holds 3 snacks. When a customer picks a snack, it goes back at the front. A new snack arrives and the shelf is full. The snack nobody touched for the longest time is removed. Samosas also have a "best before" time. Once stale, they go in the bin.

Words you'll see
Cache
A small, fast store that keeps recent answers, so you don't fetch them again from a slow place.
Eviction
Throwing an entry out because the cache is full.
LRU (least recently used)
Throw out the entry nobody has read for the longest time.
LFU (least frequently used)
Throw out the entry that was read the fewest times.
FIFO (first in, first out)
Throw out the oldest entry, no matter how often it was read.
TTL (time to live)
How long an entry stays valid. After that, it counts as expired and is never returned.
Strategy pattern
A rule you can swap without changing the main code. Here the eviction rule is one.
Cache stampede
A popular entry expires, and hundreds of requests rush to reload it from the database at once.

01What the interviewer is grading

Open-ended library (Groww, Tekion)

The whole task is "Build a scalable cache". A hard-coded FIFO was rejected with: "what if we want different eviction logic?"

Step-by-step follow-ups (Microsoft)

Start with a key-value store. Add TTL. Then: "what races exist on expiry?" Then add LRU. Each step must fit the earlier code without a rewrite.

Algorithm core (Confluent, Freshworks, Razorpay)

Confluent: LRU with TTL, plus the fastest "average of all live values". Freshworks: LRU, from brute force to O(1). Razorpay online test: LFU, ties go to the smallest key.

All of them want the same things. An EvictionPolicy interface. Fast structures, O(1) or O(log n). An honest story about thread safety. And a clock you can pass in.

Go deeper: the Groww and Tekion reports in full

The reports show three flavours of the same problem.

Groww SDE-2 (Apr 2025) gave two hours. The whole task was "build a scalable cache". The candidate built add, contains, invalidate and setMaxSize, with FIFO using a queue. The feedback: "This isn't scalable. FIFO isn't enough — what if we want different eviction logic?" Tekion SDE-2 (Jun 2026, selected) asked: "design your own library of a TTL based caching system". Running code was not required. "Clear classes, design patterns were expected". The candidate called it the toughest round.

All of them want the same things. You write the requirements yourself. You add an EvictionPolicy interface; that one line is the Groww rejection. You use correct O(1) or O(log n) structures. You tell an honest story about thread safety. You pass in a clock, so TTL can be tested. And you name the patterns and say why you used them.

02Clarifying questions to ask

Library or service?

A library uses generics, no network, and handles thread safety inside. A service is a system-design (HLD) talk.

Swappable eviction?

Answer before they ask: yes, through an interface. Default to LRU.

How does TTL work?

Per entry or one default. Counted from the last write, or from the last read.

Mostly reads? How many threads?

This picks the lock design: one lock, many smaller locks, or buffered reads.

03Requirements

Functional (what it does)

  • get, put (default TTL), put with TTL, remove, size, clear.
  • A maximum size. When full, evict using the chosen rule.
  • Expired entries are never returned.
  • Rules: LRU, LFU, FIFO, and custom ones through an interface.
  • A removal listener that gets the reason: EXPIRED, EVICTED, EXPLICIT or REPLACED.
  • Stats: hits, misses, evictions.

Non-functional (how well it does it)

  • Thread-safe, with no lost updates. The listener never runs while the cache lock is held.
  • O(1) get and put for LRU and FIFO. O(log n) is fine for LFU and expiry tracking.
  • Tests give the same result every run, because they pass in the Clock.
  • Set up through a builder. Settings cannot change after build.

Out of scope

  • Spreading over many machines, copies, saving to disk.
  • Storing data outside the Java heap.
  • Delayed writes to a database (extension only).

Patterns and why

Strategy

Use it for eviction. The policy only sees keys and events. So a new policy is one new class, with no change to the cache. The Groww interviewer pointed at exactly this gap.

Builder

Many optional settings. build() checks them. The result cannot change.

Observer

Removal listeners and stats hooks get told about events.

Decorator

Wrappers that add a feature: LoadingCache (loads missing keys), TransactionalCache, metrics.

No template base class

No abstract parent class holding half the logic. Building from small parts is easier to defend.

06Core code

LRU and FIFO both use a LinkedHashSet. It remembers the order keys were added in. Its hash part removes any key in O(1).

public final class LruPolicy<K> implements EvictionPolicy<K> {
    private final LinkedHashSet<K> order = new LinkedHashSet<>(); // eldest first

    public void onInsert(K key) { order.add(key); }
    public void onAccess(K key) { order.remove(key); order.add(key); }
    public void onRemove(K key) { order.remove(key); }
    public K victim() { return order.isEmpty() ? null : order.iterator().next(); }
}

Show Java: LruPolicy, FifoPolicy, LfuPolicy

LRU and FIFO both use a LinkedHashSet. It remembers the order keys were added in. Its hash part removes any key in O(1). "Move to the back on read" is remove, then add. The interviewer may insist on a hand-written doubly linked list (Freshworks did). It has the same shape: a HashMap<K, Node> plus dummy head and tail nodes.

public final class LruPolicy<K> implements EvictionPolicy<K> {
    private final LinkedHashSet<K> order = new LinkedHashSet<>(); // eldest first

    public void onInsert(K key) { order.add(key); }
    public void onAccess(K key) { order.remove(key); order.add(key); }
    public void onRemove(K key) { order.remove(key); }
    public K victim() { return order.isEmpty() ? null : order.iterator().next(); }
}

public final class FifoPolicy<K> implements EvictionPolicy<K> {
    private final LinkedHashSet<K> order = new LinkedHashSet<>();

    public void onInsert(K key) { order.add(key); }
    public void onAccess(K key) { }                       // access does not change FIFO order
    public void onRemove(K key) { order.remove(key); }
    public K victim() { return order.isEmpty() ? null : order.iterator().next(); }
}

/** LFU, ties broken by least-recently-used within the same frequency. */
public final class LfuPolicy<K> implements EvictionPolicy<K> {
    private final Map<K, Integer> freq = new HashMap<>();
    private final TreeMap<Integer, LinkedHashSet<K>> buckets = new TreeMap<>();

    public void onInsert(K key) { freq.put(key, 1); bucket(1).add(key); }

    public void onAccess(K key) {
        int f = freq.merge(key, 1, Integer::sum);
        unlink(key, f - 1);
        bucket(f).add(key);
    }

    public void onRemove(K key) {
        Integer f = freq.remove(key);
        if (f != null) unlink(key, f);
    }

    public K victim() {
        var lowest = buckets.firstEntry(); // O(log F); empty buckets are always removed
        return lowest == null ? null : lowest.getValue().iterator().next();
    }

    private LinkedHashSet<K> bucket(int f) { return buckets.computeIfAbsent(f, x -> new LinkedHashSet<>()); }

    private void unlink(K key, int f) {
        LinkedHashSet<K> b = buckets.get(f);
        b.remove(key);
        if (b.isEmpty()) buckets.remove(f);
    }
}

The classic O(1) LFU swaps the TreeMap for a HashMap plus a minFreq int. On insert, set minFreq = 1. On a read, if the old bucket was minFreq and is now empty, add one to it. Other removals, like TTL or delete, can leave minFreq wrong. That is why the TreeMap version is the safer default in a library. For Razorpay's "ties go to the smallest key", make each bucket a TreeSet<K>.

Show Java: InMemoryCache
public final class InMemoryCache<K, V> implements Cache<K, V> {
    private record Entry<V>(V value, long expiresAt) {
        boolean expired(long now) { return expiresAt != 0 && now >= expiresAt; }
    }
    private record Expiry<K, V>(K key, Entry<V> entry) {}
    private record Removal<K, V>(K key, V value, RemovalCause cause) {}

    private final Map<K, Entry<V>> map = new HashMap<>();
    private final PriorityQueue<Expiry<K, V>> expiries =
            new PriorityQueue<>(Comparator.comparingLong((Expiry<K, V> e) -> e.entry().expiresAt()));
    private final ReentrantLock lock = new ReentrantLock(); // ponytail: one lock; stripe into segments if contended
    private final EvictionPolicy<K> policy;
    private final int maxSize;
    private final Duration defaultTtl;
    private final Clock clock;
    private final RemovalListener<K, V> listener;
    private final CacheStats stats = new CacheStats();

    InMemoryCache(CacheBuilder<K, V> b) {
        this.policy = b.policy; this.maxSize = b.maxSize; this.defaultTtl = b.defaultTtl;
        this.clock = b.clock; this.listener = b.listener;
    }

    @Override
    public Optional<V> get(K key) {
        Objects.requireNonNull(key);
        List<Removal<K, V>> removed = new ArrayList<>();
        Optional<V> result;
        lock.lock();
        try {
            Entry<V> e = map.get(key);
            if (e != null && e.expired(clock.millis())) {
                removeEntry(key, e, RemovalCause.EXPIRED, removed); // lazy expiry
                e = null;
            }
            if (e == null) {
                stats.miss();
                result = Optional.empty();
            } else {
                policy.onAccess(key);
                stats.hit();
                result = Optional.of(e.value());
            }
        } finally {
            lock.unlock();
        }
        fire(removed);
        return result;
    }

    @Override
    public void put(K key, V value) { put(key, value, defaultTtl); }

    @Override
    public void put(K key, V value, Duration ttl) {
        Objects.requireNonNull(key);
        Objects.requireNonNull(value);
        List<Removal<K, V>> removed = new ArrayList<>();
        lock.lock();
        try {
            long now = clock.millis();
            Entry<V> fresh = new Entry<>(value, ttl == null ? 0 : now + ttl.toMillis());
            Entry<V> old = map.put(key, fresh);
            if (old == null) {
                policy.onInsert(key);
            } else {
                policy.onAccess(key);
                removed.add(new Removal<>(key, old.value(), RemovalCause.REPLACED));
            }
            if (fresh.expiresAt() != 0) expiries.add(new Expiry<>(key, fresh));
            purgeExpired(now, removed);           // prefer dropping dead entries over live ones
            while (map.size() > maxSize) {
                K victim = policy.victim();
                removeEntry(victim, map.get(victim), RemovalCause.EVICTED, removed);
                stats.eviction();
            }
        } finally {
            lock.unlock();
        }
        fire(removed);
    }

    @Override
    public boolean remove(K key) {
        List<Removal<K, V>> removed = new ArrayList<>();
        lock.lock();
        try {
            Entry<V> e = map.get(key);
            if (e == null) return false;
            removeEntry(key, e, RemovalCause.EXPLICIT, removed);
        } finally {
            lock.unlock();
        }
        fire(removed);
        return true;
    }

    /** Called by a scheduled sweeper too, so memory is reclaimed for keys nobody reads again. */
    public void cleanUp() {
        List<Removal<K, V>> removed = new ArrayList<>();
        lock.lock();
        try { purgeExpired(clock.millis(), removed); } finally { lock.unlock(); }
        fire(removed);
    }

    private void purgeExpired(long now, List<Removal<K, V>> removed) {
        while (!expiries.isEmpty() && expiries.peek().entry().expired(now)) {
            Expiry<K, V> x = expiries.poll();
            // identity check: skip heap items for entries that were overwritten or removed since
            if (map.get(x.key()) == x.entry()) removeEntry(x.key(), x.entry(), RemovalCause.EXPIRED, removed);
        }
    }

    private void removeEntry(K key, Entry<V> e, RemovalCause cause, List<Removal<K, V>> removed) {
        map.remove(key);
        policy.onRemove(key);
        removed.add(new Removal<>(key, e.value(), cause));
    }

    private void fire(List<Removal<K, V>> removed) { // outside the lock: listener may be slow or re-enter
        for (Removal<K, V> r : removed) {
            try { listener.onRemoval(r.key(), r.value(), r.cause()); } catch (RuntimeException ignored) { }
        }
    }

    @Override public int size() { lock.lock(); try { return map.size(); } finally { lock.unlock(); } }
    @Override public CacheStats stats() { return stats; }
}

public final class CacheBuilder<K, V> {
    int maxSize = 10_000;
    Duration defaultTtl;                            // null = no expiry
    EvictionPolicy<K> policy = new LruPolicy<>();
    Clock clock = Clock.systemUTC();
    RemovalListener<K, V> listener = (k, v, c) -> { };

    public CacheBuilder<K, V> maxSize(int n) { this.maxSize = n; return this; }
    public CacheBuilder<K, V> defaultTtl(Duration d) { this.defaultTtl = d; return this; }
    public CacheBuilder<K, V> policy(EvictionPolicy<K> p) { this.policy = p; return this; }
    public CacheBuilder<K, V> clock(Clock c) { this.clock = c; return this; }
    public CacheBuilder<K, V> listener(RemovalListener<K, V> l) { this.listener = l; return this; }

    public Cache<K, V> build() {
        if (maxSize <= 0) throw new IllegalArgumentException("maxSize must be positive");
        if (defaultTtl != null && (defaultTtl.isNegative() || defaultTtl.isZero())) {
            throw new IllegalArgumentException("ttl must be positive");
        }
        return new InMemoryCache<>(this);
    }
}

public final class CacheStats {
    private final LongAdder hits = new LongAdder(), misses = new LongAdder(), evictions = new LongAdder();
    void hit() { hits.increment(); }
    void miss() { misses.increment(); }
    void eviction() { evictions.increment(); }
    public double hitRate() {
        long h = hits.sum(), total = h + misses.sum();
        return total == 0 ? 1.0 : (double) h / total;
    }
}

The cleanup job is one line in the demo: scheduler.scheduleAtFixedRate(cache::cleanUp, 1, 1, TimeUnit.SECONDS). Redis does the same two things. It checks expiry when a key is touched. It also runs a regular job that samples keys with a TTL.

07Concurrency and edge cases

Microsoft asked: "what races exist on expiry?" Here is the one to draw.

  • Check and delete under one lock. Delete only if it is still the exact same entry object.
  • With a ConcurrentHashMap, the same idea is map.remove(key, entry).
  • An LRU read changes the order. So a ReadWriteLock read lock is wrong for get.

Scaling the lock, in the order to suggest it

1) Start with one lock, and measure. 2) Split into N small caches, chosen by hash(key) % N. Each has its own map, policy and lock. LRU is then only roughly global, which is usually fine; Guava did this. 3) Use a ConcurrentHashMap for data and buffer the policy updates, like Caffeine. Caffeine's W-TinyLFU also adds an entry filter. A key read only once cannot push out a popular one. Its published tests show clearly higher hit rates than plain LRU.

08Extensions interviewers add mid-round

New eviction rule (Groww)

Implement EvictionPolicy and pass it to the builder. The cache does not change at all.

Average of live values (Confluent)

Keep a running sum and count. Clear expired entries first, then divide.

Transactions (Rippling-style)

A decorator with a stack of pending writes. Commit merges them down. Rollback throws the top away.

Read-through and write-through

A LoadingCache decorator. Only one load runs per key at a time.

Sliding TTL

On each read, store the entry again with a new expiry time. Offer it as a builder option.

Memory limit

Add a Weigher. Evict while totalWeight > maxWeight.

Distributed

A different problem. Put this cache in front of Redis. TTL is the safety net.

Go deeper: full answers for each extension
"Add a new eviction policy" (Groww)

Implement EvictionPolicy and pass it to the builder. InMemoryCache does not change. They may ask for "evict the entry closest to expiry". That policy uses a TreeSet sorted by expiry time. It needs the expiry time in onInsert. So change the signature once to onInsert(K key, long expiresAt). Other policies simply ignore what they do not need.

"Average of all active (non-expired) values in the best complexity" (Confluent)

Keep sum and count as fields. Update them in put and removeEntry. On replace, subtract the old value. average() first calls purgeExpired(now). That removes only the expired entries, each in O(log n). Then it returns sum / count. The cost is O(log n) per expired entry, spread over time, and O(1) otherwise. Ask if timestamps always increase, as that candidate did. If yes, the heap can be a simple first-in-first-out deque.

"Support transactions: begin, commit, rollback, nested" (Rippling-style)

Write a decorator with a Deque<Map<K, Optional<V>>>, a stack of pending write sets. An empty Optional marks a delete (a "tombstone"). When a transaction is open, put and remove write to the top map. get searches the stack from the top down, then the real cache. commit pops the top and merges it into the layer below. If it was the outermost, it applies it to the real cache. rollback just pops. For one transaction per thread, keep the stack in a ThreadLocal. Then threads only see each other's committed data (read-committed).

Show Java: TransactionalCache
public final class TransactionalCache<K, V> {
    private final Cache<K, V> base;
    private final Deque<Map<K, Optional<V>>> txs = new ArrayDeque<>();

    public TransactionalCache(Cache<K, V> base) { this.base = base; }

    public void begin() { txs.push(new HashMap<>()); }
    public void put(K k, V v) { if (txs.isEmpty()) base.put(k, v); else txs.peek().put(k, Optional.of(v)); }
    public void remove(K k) { if (txs.isEmpty()) base.remove(k); else txs.peek().put(k, Optional.empty()); }

    public Optional<V> get(K k) {
        for (Map<K, Optional<V>> layer : txs) { // ArrayDeque iterates from the top of the stack
            if (layer.containsKey(k)) return layer.get(k);
        }
        return base.get(k);
    }

    public void rollback() { requireTx(); txs.pop(); }

    public void commit() {
        requireTx();
        Map<K, Optional<V>> top = txs.pop();
        if (!txs.isEmpty()) { txs.peek().putAll(top); return; }
        top.forEach((k, v) -> v.ifPresentOrElse(val -> base.put(k, val), () -> base.remove(k)));
    }

    private void requireTx() { if (txs.isEmpty()) throw new IllegalStateException("no transaction"); }
}
"Read-through / write-through to a database"

Write a LoadingCache decorator with a CacheLoader<K,V>. Only one load runs per key, as above. Write-through: write to the database, then to the cache (or remove the cache entry). Write-behind: queue the writes and save them in batches. Mention that a crash loses queued writes, and that order per key matters.

"Expire-after-access (sliding TTL)"

On get, store the entry again with a new expiry time, and add a new heap item. The same-object check makes the old heap item harmless. Offer it as a builder option, not a second cache class.

"Max memory instead of max entries"

Add a Weigher<K,V> to the builder and a totalWeight field. The eviction loop runs while totalWeight > maxWeight. Reject any single entry heavier than the limit.

"Make it distributed"

This is a different problem. You need consistent hashing to spread keys over machines. You decide whether to keep copies. You need a way to remove stale entries, such as pub/sub messages or version numbers in keys. In real systems, this library sits in front of Redis as a "near cache". TTL is the safety net when a removal message is missed.

09Tests to write

LRU removes the least recent

10Mistakes that got candidates rejected, and review questions

Rejected for this
  • Hard-coded FIFO with no eviction interface, and talking about interfaces only when pushed. Groww said: "This isn't scalable... what if we want different eviction logic?" Add the interface in the first 20 minutes.
  • Not writing requirements when the task is one line. The requirements are part of the grade.
  • Checking TTL only on read, so the cache fills up with dead entries.
  • synchronized on get with a ConcurrentHashMap inside "for safety". That is two mechanisms, and neither one is thought through.
  • Using LinkedHashMap(accessOrder=true) and calling it a library. It is fine as a first step. But it cannot do LFU or TTL, and the follow-up shows that.
  • System.currentTimeMillis() spread through the code, then Thread.sleep in tests.

Interview questions

Why does the policy not hold the values?

Each class has one job (single responsibility). The cache owns the data and the timing. The policy owns the order of keys. A new policy never needs to know about TTL, listeners or stats. The cache never needs to know about read counts.

Why a ReentrantLock instead of synchronized?

Both are correct here. ReentrantLock has tryLock with a timeout. So the cleanup job can give up instead of blocking callers. It also offers fairness if needed. With virtual threads before JDK 24, synchronized pinned the real carrier thread underneath.

Why not a ReadWriteLock?

Because LRU and LFU change data on every read. For FIFO, which ignores reads, a read lock would work. But one code path for all policies is simpler.

What is the complexity of each operation?

get: O(1) for the map, and O(1) for LRU or FIFO. LFU is O(log F), where F is the number of distinct read counts. put: O(1) for the map. Adding to the expiry heap is O(log n) when a TTL is set. Clearing k expired entries costs O(k log n), but each entry is cleared only once.

How do you stop a cache stampede on a hot expired key?

Use three things. First, single-flight loading: one loader per key, and the others wait for its result (a future). Second, add small random amounts to TTLs (jitter), so many keys do not expire together. Third, optionally refresh ahead: reload before expiry while still serving the old value.

Why are listener exceptions swallowed?

A bug in a listener must not break a put that already worked. Log it with the key and reason. In production, run listeners on an executor, so a slow listener cannot slow down callers.

12Quick check

An LRU cache holds 3 keys. You put a, b, c, then get a, then put d. Which key is thrown out?

Reading a moved it to the back. The order is now b, c, a. So b is the oldest, and it goes.

Why is a ReadWriteLock read lock wrong for an LRU get?

Two readers moving keys at the same time break the linked order. Caffeine avoids waiting by buffering reads, not by using a read lock.

The cleanup job finds key k expired. But a put has just stored a fresh value for k. How does this design avoid deleting it?

It checks, under the lock, that it is the exact same entry object. The fresh value is a new object, so it stays. With a ConcurrentHashMap, the same idea is remove(key, entry).

The Groww interviewer said "FIFO isn't enough". What should the design have had from the start?

This is the Strategy pattern. A new rule is a new class, and the cache code does not change.

Cheat sheet
  • The cache owns the map, the timing and the lock. EvictionPolicy owns only the key order.
  • LRU and FIFO use a LinkedHashSet. LFU uses a read-count map plus a TreeMap of buckets.
  • TTL: check on get, keep an expiry heap, and run cleanUp on a schedule.
  • Clear expired entries before evicting live ones.
  • Expiry race: delete only if it is the same entry object (remove(k, e)).
  • An LRU get is a write, so use an exclusive lock. To scale, split into smaller caches, then use Caffeine-style buffers.
  • Collect removals and call listeners after unlocking. Pass in a Clock.
  • Patterns: Strategy, Builder, Observer, Decorator (loading, transactions).
