Booking System with No Double-Booking

You will be able to code a booking service where two concurrent requests never both win the last seat, and say how a database enforces the same rule.

Time-box: 90 min coding + 30–45 min review Seen: ~15 reports, 2025–26 (most common prompt) Format: CLI, in-memory, or REST API
FlipkartUdaanSwiggyPostmanInMobiCREDAtlassianEightfold
In 30 seconds
  • Rooms, gym slots, train seats: same core, capacity plus no user overlap.
  • Half-open [start, end) intervals; overlap check via TreeMap.lowerEntry.
  • Check and book under one lock: user lock, then slot lock, always.
  • Retries are idempotent; in a database, constraints enforce the rule.
Picture it

The Tatkal counter at a railway station. Two clerks must not sell the last berth twice, so a clerk holds the coach's ledger while checking and writing. Late passengers go on a waitlist and move up when someone cancels.

01What the interviewer is grading

Overlap logic

Half-open intervals so back-to-back works; O(log n), not a scan.

Atomic check-and-book

Check and write under one lock or one DB constraint. Every review asks this.

Staged delivery

Finish and demo each stage before the next (Udaan says so).

Idempotency, errors, DB

Retry is harmless; typed errors; same invariant with N pods.

Go deeper: how the rounds ran and the full grading list

The variants differ in nouns but grade the same things. Flipkart's SDE-2 round gave 30 minutes to clarify and 90 minutes to build appointment booking end to end, then a 45-minute presentation where the interviewer pushed on avoiding concurrency issues while booking. Udaan's fitness-slot prompt was staged: Stage 1 (capacity, no user overlaps, back-to-back allowed) must be fully working before Stage 2 (FIFO waitlist, daily limit K, idempotent BOOK, validation). Postman wanted a meeting-room REST API callable from Postman with correct status codes and headers for success and failure. InMobi asked for pessimistic vs optimistic locking in an IRCTC design. CRED pushed into seat locks, per-seat prices and double booking across platforms. Eightfold's "Strong Hire" was meeting rooms with recurring bookings. Atlassian runs the same core as a tennis court booking problem.

  • Correct overlap logic. Half-open intervals [start, end) so back-to-back is allowed; O(log n) lookup, not a scan.
  • Atomic check-and-book. The availability check and the write happen under one lock or one DB constraint. This is the core question of every review.
  • Staged delivery. Each feature finished and demoed before the next. Udaan's prompt says this explicitly.
  • Modularity. Models, repository, service, CLI/controller in separate layers; in-memory repository swappable for JPA.
  • Idempotency and errors. Retrying BOOK is harmless; failures are typed exceptions mapped to clear messages or HTTP codes.
  • Production translation. How the same invariant holds with N app pods: row locks, version columns, exclusion constraints, holds with TTL.

03Requirements

Functional

  • Add, list, book, cancel slots.
  • Book only with capacity and no user overlap.
  • Cancel promotes the waitlist head.
  • Stage 2: waitlist, daily K, idempotent.

Non-functional

  • No overbooking, no deadlocks.
  • Per-slot and per-user locks.
  • O(log n) check; injected Clock.

Out of scope

  • Payments, auth, notifications.
  • Persistence beyond in-memory.
Go deeper: full requirement list
  • Add resource / slot (id, title, start, end, capacity); validate start < end, capacity > 0, unique id.
  • List slots by date, title substring or time window.
  • Book: succeeds only if capacity remains and the user has no overlapping booking.
  • Cancel: frees capacity; promotes the head of the waitlist.
  • List a user's upcoming bookings.
  • Stage 2: FIFO waitlist, daily limit K, idempotent book.
  • No overbooking under concurrent requests. No deadlocks; lock scope per resource and per user, never global. O(log n) availability check. Testable time (injected Clock) for "upcoming" and hold expiry.
  • Out of scope (state it): payments (stub a PaymentGateway if holds are in scope); auth, notifications, search ranking; persistence beyond an in-memory repository, unless asked.

06The race and the fix

The bug: "is there a seat?" and "take the seat" as two steps. One seat left:

TimeThread AThread BSlot S1
t1hasSeat() → truebooked={X}, cap 2
t2hasSeat() → truebooked={X}
t3booked.add(A)booked={X,A}
t4booked.add(B)3 people, capacity 2

The fix: check and write inside the slot's lock (user lock first).

TimeThread AThread BSlot S1
t1lock user A, lock S1lock user B, waits for S1booked={X}
t2hasSeat() → true, confirmwaitingbooked={X,A}
t3unlock S1, unlock Agets S1booked={X,A}
t4hasSeat() → false, waitlist2 booked, B waitlisted
Lock rules
  • One order everywhere: user, then slot. Two slots? Sort ids first.
  • A synchronized service is correct but serialises every booking. Say it.
  • Lock the Slot object from the map, never a string id.

Go deeper: every concurrency and edge case, and the full database table
  • Check-then-act. "Is there a seat?" and "take the seat" must be one critical section. Two threads passing the check before either writes is the textbook double booking.
  • Two locks, one order. Capacity lives on the slot, overlap lives on the user. Take user then slot everywhere. If a flow needs two slots (round trip, recurrence), sort slot ids and lock in that order.
  • Lock granularity. A synchronized service method is correct but serialises every booking in the system. Per-slot and per-user locks let unrelated bookings run in parallel; say this out loud.
  • Lock objects must be stable. Lock the Slot instance from the map, not a string id ("S1" literals are interned; new strings are not the same monitor).
  • Idempotency. The natural key (user, slot) makes BOOK idempotent. For REST, also accept an Idempotency-Key header, store key → response for 24 h, and replay the stored response.
  • Time. Inject Clock; "upcoming" uses clock.instant(). Store Instant; convert with the slot's ZoneId only for display and for "per day" rules. Reject bookings in the past.
  • Holds. A HELD booking carries expiresAt. Treat expired holds as free when checking capacity (lazy expiry) and sweep them with a ScheduledExecutorService. Confirm must re-check expiresAt under the lock: payment may succeed after the hold expired, which means refund or re-hold.
  • Validation. start < end, capacity > 0, unique id (putIfAbsent), unknown user/slot, cancel of a booking that does not exist.

Show value types: TimeRange, BookingStatus, Booking, exceptions 
public record TimeRange(Instant start, Instant end) {
    public TimeRange {
        if (!start.isBefore(end)) throw new IllegalArgumentException("start must be before end");
    }
    /** Half-open: [09:00,10:00) and [10:00,11:00) do not overlap. */
    public boolean overlaps(TimeRange o) {
        return start.isBefore(o.end) && o.start.isBefore(end);
    }
}

public enum BookingStatus { HELD, CONFIRMED, WAITLISTED, CANCELLED, EXPIRED }

public record Booking(String id, String userId, String slotId, TimeRange range, BookingStatus status) {}

Show Slot (capacity and FIFO waitlist) 
public final class Slot {
    final String id;
    final String title;
    final TimeRange range;
    final int capacity;
    final ReentrantLock lock = new ReentrantLock();
    // Guarded by lock:
    final LinkedHashSet<String> booked = new LinkedHashSet<>();
    final LinkedHashSet<String> waitlist = new LinkedHashSet<>();   // FIFO + O(1) contains/remove

    Slot(String id, String title, TimeRange range, int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
        this.id = id; this.title = title; this.range = range; this.capacity = capacity;
    }
    boolean hasSeat() { return booked.size() < capacity; }
}
Show UserSchedule (O(log n) overlap)

A user's confirmed bookings never overlap each other, so only the booking with the greatest start before the candidate's end can overlap it.

final class UserSchedule {
    final ReentrantLock lock = new ReentrantLock();
    private final TreeMap<Instant, Booking> byStart = new TreeMap<>();   // guarded by lock

    boolean overlaps(TimeRange r) {
        Map.Entry<Instant, Booking> before = byStart.lowerEntry(r.end());
        return before != null && before.getValue().range().end().isAfter(r.start());
    }
    long countOn(LocalDate day, ZoneId zone) {
        Instant from = day.atStartOfDay(zone).toInstant();
        Instant to = day.plusDays(1).atStartOfDay(zone).toInstant();
        return byStart.subMap(from, true, to, false).size();
    }
    void add(Booking b) { byStart.put(b.range().start(), b); }
    void remove(Booking b) { byStart.remove(b.range().start()); }
    Collection<Booking> upcoming(Instant now) { return List.copyOf(byStart.tailMap(now, true).values()); }
}
Show BookingService (lock ordering, rules, idempotency, waitlist) 
public interface BookingRule {
    void check(UserSchedule user, Slot slot);   // throws BookingRejected
}

public final class BookingService {
    private final ConcurrentHashMap<String, Slot> slots = new ConcurrentHashMap<>();
    private final ConcurrentHashMap<String, UserSchedule> users = new ConcurrentHashMap<>();
    private final ConcurrentHashMap<String, Booking> bookings = new ConcurrentHashMap<>(); // key: userId|slotId
    private final List<BookingRule> rules;
    private final Clock clock;

    public BookingService(List<BookingRule> rules, Clock clock) { this.rules = rules; this.clock = clock; }

    public void addSlot(String id, String title, TimeRange range, int capacity) {
        if (slots.putIfAbsent(id, new Slot(id, title, range, capacity)) != null)
            throw new IllegalArgumentException("duplicate slot " + id);
    }

    public Booking book(String userId, String slotId) {
        Slot slot = Optional.ofNullable(slots.get(slotId)).orElseThrow(() -> new NotFound(slotId));
        UserSchedule user = users.computeIfAbsent(userId, u -> new UserSchedule());
        // Fixed order everywhere: user lock, then slot lock. Cancel uses the same order, so no deadlock.
        user.lock.lock();
        slot.lock.lock();
        try {
            Booking existing = bookings.get(key(userId, slotId));
            if (existing != null) return existing;                // idempotent: same answer on retry
            if (slot.waitlist.contains(userId)) return waitlisted(userId, slot);
            for (BookingRule rule : rules) rule.check(user, slot);   // overlap, daily limit, ...
            if (!slot.hasSeat()) {
                slot.waitlist.add(userId);
                return waitlisted(userId, slot);
            }
            return confirm(user, userId, slot);
        } finally {
            slot.lock.unlock();
            user.lock.unlock();
        }
    }

    public void cancel(String userId, String slotId) {
        Slot slot = Optional.ofNullable(slots.get(slotId)).orElseThrow(() -> new NotFound(slotId));
        UserSchedule user = users.computeIfAbsent(userId, u -> new UserSchedule());
        String promoted;
        user.lock.lock();
        slot.lock.lock();
        try {
            if (slot.waitlist.remove(userId)) return;
            Booking b = bookings.remove(key(userId, slotId));
            if (b == null) throw new NotFound(userId + " in " + slotId);
            slot.booked.remove(userId);
            user.remove(b);
            promoted = slot.waitlist.isEmpty() ? null : slot.waitlist.iterator().next();
        } finally {
            slot.lock.unlock();
            user.lock.unlock();
        }
        // Promote outside our locks: book() takes the promoted user's lock first, keeping lock order.
        if (promoted != null) promote(promoted, slot);
    }

    private void promote(String userId, Slot slot) {
        UserSchedule user = users.get(userId);
        user.lock.lock();
        slot.lock.lock();
        try {
            if (!slot.waitlist.remove(userId) || !slot.hasSeat()) return;   // state moved on meanwhile
            try {
                for (BookingRule rule : rules) rule.check(user, slot);
                confirm(user, userId, slot);
            } catch (BookingRejected e) {
                // User booked something overlapping since joining the waitlist: skip to the next one.
                String next = slot.waitlist.isEmpty() ? null : slot.waitlist.iterator().next();
                if (next != null) Thread.ofVirtual().start(() -> promote(next, slot));
            }
        } finally {
            slot.lock.unlock();
            user.lock.unlock();
        }
    }

    private Booking confirm(UserSchedule user, String userId, Slot slot) {
        Booking b = new Booking(UUID.randomUUID().toString(), userId, slot.id, slot.range, BookingStatus.CONFIRMED);
        slot.booked.add(userId);
        user.add(b);
        bookings.put(key(userId, slot.id), b);
        return b;
    }

    private static Booking waitlisted(String userId, Slot slot) {
        return new Booking(null, userId, slot.id, slot.range, BookingStatus.WAITLISTED);
    }
    private static String key(String userId, String slotId) { return userId + "|" + slotId; }
}

The skip-to-next promotion uses a fresh thread only to avoid re-entering with locks held; in an interview a simple loop that releases and re-acquires is equally fine. Say which you chose and why.

Show rules: NoOverlapRule, DailyLimitRule 
public final class NoOverlapRule implements BookingRule {
    public void check(UserSchedule user, Slot slot) {
        if (user.overlaps(slot.range)) throw new OverlappingBooking(slot.id);
    }
}

public final class DailyLimitRule implements BookingRule {
    private final int maxPerDay;
    private final ZoneId zone;
    public DailyLimitRule(int maxPerDay, ZoneId zone) { this.maxPerDay = maxPerDay; this.zone = zone; }
    public void check(UserSchedule user, Slot slot) {
        LocalDate day = LocalDate.ofInstant(slot.range.start(), zone);
        if (user.countOn(day, zone) >= maxPerDay) throw new DailyLimitReached(day);
    }
}
Show RoomCalendar (meeting-room variant, free-form ranges) 
final class RoomCalendar {
    private final TreeMap<Instant, Booking> byStart = new TreeMap<>();

    synchronized boolean tryBook(Booking b) {
        Map.Entry<Instant, Booking> before = byStart.lowerEntry(b.range().end());
        if (before != null && before.getValue().range().end().isAfter(b.range().start())) return false;
        byStart.put(b.range().start(), b);
        return true;
    }
}

Finding any free room for a range: iterate rooms sorted by capacity (smallest that fits) and call tryBook; each call is atomic per room, so a lost race just moves on to the next room.

08Extensions interviewers add mid-round

Pessimistic or optimistic? (InMobi IRCTC)

Pessimistic Tatkal hot row

  • No retry storm when thousands hit one train
  • Blocking; keep transactions tiny

Or a single writer per train partition (Kafka key = train id).

Optimistic

  • No locks held
  • Most attempts fail and retry under contention

Off-peak, meeting rooms.

Waitlist + promotion

Already built. Trains add RAC: WL → RAC → CNF.

Daily limit K

One new DailyLimitRule; no service change.

REST (Postman)

201 + Location, 409 overlap, 400 bad input, 404, 204 delete.

Recurring (Eightfold)

Store a rule, expand in the room's zone, book all or none.

Seat hold (CRED)

HOLD with TTL and price snapshot → pay → CONFIRM.

Many pods

Move the invariant into the DB, or partition by resource.

Go deeper: full answers for each extension
Waitlist with auto-promotion (Udaan, Swiggy train booking)

Already in the design: LinkedHashSet per slot for FIFO plus O(1) removal when a waitlisted user cancels. On cancel, promote the head; if the promoted user now fails a rule (overlap, daily limit), skip to the next. For trains, add RAC as an intermediate state and promote in order WL → RAC → CNF, one berth per cancellation.

Daily limit K, configurable (Udaan)

A new DailyLimitRule(K, zone) in the rules list; no change to the service. The count is from the user's TreeMap.subMap for that local day.

REST API with correct codes and headers (Postman)

POST /rooms/{id}/bookings → 201 Created with Location: /bookings/{bookingId} and the body. Overlap → 409 Conflict with the conflicting booking id. Bad input (end before start, missing field) → 400 (or 422 for well-formed but invalid). Unknown room → 404. Replay with the same Idempotency-Key → the original 201 response. DELETE /bookings/{id} → 204. GET list → 200 with pagination. For updates, return an ETag and require If-Match (412 on mismatch) for optimistic concurrency.

In Spring: a @RestControllerAdvice maps OverlappingBooking to 409 and validation errors to 400 with a ProblemDetail body (RFC 7807 style).

Recurring bookings (Eightfold)

Store a rule (RRULE-like: frequency, interval, until/count, by-day) and expand occurrences within a horizon (for example 6 months) in the room's time zone, so 10:00 stays 10:00 across DST. Book all occurrences atomically: lock the room once, check every occurrence, then insert all or none. Report which dates conflict. Editing "this and following" splits the series into two rules. Never materialise infinite series.

Seat lock with timeout and per-seat price (CRED flights, movie and train variants)

Two-phase: HOLD (seat status HELD, hold_until, price snapshot stored on the hold) → pay → CONFIRM. The price is locked at hold time, so a later fare change does not alter what the user pays. Expiry is lazy (a held seat with past hold_until counts as free) plus a sweeper. In Redis, SET seat:{flight}:{seat} {userId} NX PX 600000 is a fast hold; the database conditional update stays the source of truth.

Other platforms sell the same seats (CRED)

You do not own inventory, so your lock is advisory. The airline's system (via the GDS) is the source of truth: you request a hold from the airline, get a PNR or hold reference with an expiry, and confirm against it. The CRED candidate's answer, "the airline locks on the platform's behalf", convinced the interviewer. Your local hold must be shorter than the upstream hold.

Pessimistic vs optimistic (InMobi IRCTC)

Tatkal opening is the textbook hot row: optimistic locking makes most of thousands of concurrent attempts fail and retry, so use pessimistic row locks with short transactions, or better, a per-train queue (single writer per train partition, for example a Kafka partition keyed by train id). Off-peak, optimistic is cheaper. Say the contention level drives the choice.

Multiple app instances

In-memory locks only protect one JVM. Move the invariant into the database (constraint or row lock), or route all requests for a resource to one instance (partition by resource id). A Redis lock (Redisson) works but needs fencing tokens or a DB check, because a paused lock holder can resume after its lease expired.

Common mistakes
  • Check and write in two unsynchronised steps, then "add synchronized" in review (Flipkart).
  • One giant synchronized with no word on throughput.
  • Closed intervals, so back-to-back fails.
  • Stage 2 half-built while Stage 1 is broken (Udaan).
  • 200 for everything, or 500 for a conflict, in REST.

Go deeper: the rejection notes in full
  • Checking availability and writing the booking in two unsynchronised steps, then hand-waving "add synchronized" in the review (Flipkart's follow-up was exactly this).
  • One giant synchronized on the service with no explanation of the throughput cost.
  • Closed-interval overlap, so back-to-back bookings fail.
  • Stage 2 features half-built while a Stage 1 feature was broken. Udaan's prompt warns against partial features.
  • Returning 200 for everything, or 500 for a conflict, in the REST variant.
  • Only entities and a class diagram with no concurrency story; Swiggy's train-booking candidate covered entities, waitlist and concurrency and was still rejected, so depth and speed both count.

12Quick check

Booked 09:00–10:00. Should 10:00–11:00 be allowed, and what check gives that?

With [start, end), 10:00 is not inside the first booking, so back-to-back is fine.

Thread 1 locks user then slot; thread 2 locks slot then user. What can happen?

A cycle in lock order is the deadlock condition. One global order removes the cycle.

Tatkal opens and 50,000 users hit one train. Which DB approach?

Under heavy contention almost every optimistic attempt fails and retries.

Why does UserSchedule.overlaps only check lowerEntry(end)?

That makes the check O(log n) instead of a scan.

13Interview questions

Why two locks? Can it deadlock?

Capacity is slot state and overlap is user state, and both must hold at commit time. Every path takes user then slot, so there is no cycle. The promotion path releases the canceller's locks before taking the promoted user's.

Why lowerEntry(end) and not a scan?

Existing bookings are disjoint and sorted, so the only candidate for overlap is the latest one starting before the new end. O(log n) instead of O(n).

How would you move this to Postgres with five pods?

Repositories become JPA. Capacity uses a conditional UPDATE … WHERE booked < capacity or SELECT … FOR UPDATE; user overlap uses an exclusion constraint on (user_id, during); idempotency uses UNIQUE(user_id, slot_id). The in-process locks go away.

What if the waitlisted user's notification fails?

Promotion is a state change committed first; the notification is an event published after commit (outbox pattern), retried independently.

Where would you add a "max 7 days ahead" rule?

A new BookingRule implementation using the injected Clock; no service change.

Cheat sheet
  • Half-open overlap: a.start < b.end && b.start < a.end.
  • Per-user TreeMap by start; lowerEntry(end) is O(log n).
  • Lock user, then slot, everywhere; promote after releasing.
  • Idempotent on (user, slot); REST adds Idempotency-Key.
  • Waitlist: LinkedHashSet; skip heads that now clash.
  • Rules as a list of BookingRule; inject Clock.
  • DB: FOR UPDATE (hot), @Version (cold), unique, exclusion constraint.
  • Holds: TTL, lazy expiry, re-check on confirm; never pay inside the lock.
