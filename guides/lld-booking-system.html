Booking System with No Double-Booking

Two people may tap "Book" for the last seat at the same moment. By the end, you can code a booking service where only one of them wins. You will also be able to explain how a database enforces the same rule.

Time-box: 90 min coding, then 30–45 min review Seen: about 15 interview reports, 2025–26 (the most common prompt) Format: command line, in-memory, or REST API
FlipkartUdaanSwiggyPostmanInMobiCREDAtlassianEightfold
In 30 seconds
  • Rooms, gym slots and train seats share one core. Respect the capacity, and never let one user book two clashing times.
  • A time range includes its start but not its end, so back-to-back bookings fit. A sorted map finds clashes quickly.
  • Check and book while holding locks. Always take the user's lock first, then the slot's lock.
  • Sending the same booking twice must not book twice. In a database, constraints enforce the rules.
Picture it

Think of the Tatkal counter at a railway station. Two clerks must not sell the last berth twice. So a clerk holds the coach's ledger while checking it and writing in it. Late passengers go on a waitlist. They move up when someone cancels.

Words you'll see
Double booking
Two people both get the same last seat. This is the bug the whole page is about.
Half-open interval
Written [start, end). It includes the start time but not the end time. So 9–10 and 10–11 do not clash.
Lock
A "one at a time" token. While one thread holds it, other threads must wait before touching the same data.
Deadlock
Two threads each hold a lock the other needs. Both wait forever.
Idempotent
Doing the same thing twice has the same effect as doing it once. If the app retries "Book", you still get one booking.
Waitlist (FIFO)
A queue for a full slot. FIFO means first in, first out: whoever joined first moves up first.
Hold with TTL
A seat kept for you for a short time while you pay. TTL (time to live) is how long until the hold expires.
Constraint
A rule the database itself enforces, such as "no two rows with the same seat". Even buggy code cannot break it.

01What the interviewer is grading

Overlap logic

Use half-open ranges so back-to-back works. Find clashes in O(log n) time, not by scanning every booking.

Atomic check-and-book

Check and write under one lock or one database constraint. Every review asks about this.

Staged delivery

Finish and demo each stage before starting the next. Udaan says so in the prompt.

Idempotency, errors, DB

A retry does no harm. Errors have clear types. The same rule holds across many servers.

Go deeper: how the rounds ran and the full grading list

The variants use different nouns but grade the same things. Flipkart's SDE-2 round gave 30 minutes to clarify. Then came 90 minutes to build appointment booking end to end. A 45-minute presentation followed. There, the interviewer pushed on how to avoid concurrency issues while booking. Udaan's fitness-slot prompt came in stages. Stage 1 had to work fully before Stage 2. Stage 1 covered capacity, no clashing bookings per user, and back-to-back allowed. Stage 2 covered a FIFO waitlist, a daily limit K, an idempotent BOOK and validation. Postman wanted a meeting-room REST API you could call from Postman. It needed correct status codes and headers for success and failure. InMobi asked about pessimistic vs optimistic locking in an IRCTC design. CRED pushed into seat locks, per-seat prices, and double booking across platforms. Eightfold's "Strong Hire" was meeting rooms with recurring bookings. Atlassian runs the same core as a tennis court booking problem.

  • Correct overlap logic. Use half-open ranges [start, end), so back-to-back is allowed. Look up clashes in O(log n), not with a scan.
  • Atomic check-and-book. The "is it free?" check and the write happen under one lock or one database constraint. This is the core question of every review.
  • Staged delivery. Finish and demo each feature before the next. Udaan's prompt says this clearly.
  • Modularity. Keep models, repository, service and the command line or controller in separate layers. You can then swap the in-memory repository for JPA.
  • Idempotency and errors. Retrying BOOK does no harm. Failures are typed exceptions, turned into clear messages or HTTP codes.
  • Production version. Explain how the same rule holds with many app servers. Talk about row locks, version columns, exclusion constraints, and holds that expire.

03Requirements

Functional

  • Add, list, book and cancel slots.
  • Book only if there is room and the user has no clash.
  • A cancel moves the first waitlisted person up.
  • Stage 2: waitlist, daily limit K, and safe retries.

Non-functional

  • Never overbook. Never deadlock.
  • One lock per slot and one per user.
  • Clash check in O(log n). The clock is passed in.

Out of scope

  • Payments, login, notifications.
  • Storage beyond in-memory.
Go deeper: full requirement list
  • Add a resource or slot with id, title, start, end and capacity. Check that start < end, capacity > 0, and the id is unique.
  • List slots by date, by part of the title, or by time window.
  • Book: succeeds only if there is still room and the user has no clashing booking.
  • Cancel: frees a place and moves the first waitlisted person up.
  • List a user's upcoming bookings.
  • Stage 2: FIFO waitlist, daily limit K, and idempotent booking.
  • Never overbook, even with many requests at once. Never deadlock. Lock per resource and per user, never one global lock. Check availability in O(log n). Make time testable by passing in a Clock, for "upcoming" and for hold expiry.
  • Out of scope (say so): payments. Stub a PaymentGateway if holds are in scope. Also login, notifications and search ranking. Also storage beyond an in-memory repository, unless asked.

06The race and the fix

The bug is doing "is there a seat?" and "take the seat" as two separate steps. Here is what happens with one seat left:

TimeThread AThread BSlot S1
t1hasSeat() → truebooked={X}, cap 2
t2hasSeat() → truebooked={X}
t3booked.add(A)booked={X,A}
t4booked.add(B)3 people, capacity 2

The fix is to check and write while holding the slot's lock. Take the user's lock first.

TimeThread AThread BSlot S1
t1lock user A, lock S1lock user B, waits for S1booked={X}
t2hasSeat() → true, confirmwaitingbooked={X,A}
t3unlock S1, unlock Agets S1booked={X,A}
t4hasSeat() → false, waitlist2 booked, B waitlisted
Lock rules
  • Use one order everywhere: user first, then slot. If you need two slots, sort their ids first.
  • A synchronized service is correct, but every booking then waits in one line. Say so.
  • Lock the Slot object from the map, never a string id.

The same invariant in a database

ApproachHowGood for
Pessimistic lockSELECT … FOR UPDATEHot rows (Tatkal)
Optimistic lock@Version; 0 rows updated → retryLow contention
Conditional updateUPDATE … WHERE status='FREE'Seats, holds
Unique constraintUNIQUE(seat_id, show_id)Discrete seats
Exclusion constraintEXCLUDE USING gist (… during WITH &&)Time ranges

An invariant is a rule that must always be true, such as "never more people than seats". A pessimistic lock blocks others while you work. An optimistic lock lets everyone try, and the loser retries. "Hot rows" are rows many users fight over at once. "Low contention" means few users compete.

Go deeper: every concurrency and edge case, and the full database table
  • Check-then-act. "Is there a seat?" and "take the seat" must run as one protected block. If two threads both pass the check before either writes, you get the textbook double booking.
  • Two locks, one order. Capacity lives on the slot. Clashes live on the user. Take the user lock, then the slot lock, everywhere. Some flows need two slots, like a round trip or a repeating booking. Then sort the slot ids and lock in that order.
  • Lock size. A synchronized service method is correct. But every booking in the system then waits in one line. Per-slot and per-user locks let unrelated bookings run side by side. Say this out loud.
  • Lock objects must stay the same. Lock the Slot object from the map, not a string id. Java shares one copy of each "S1" literal, but a newly built string is a different object, so it is a different lock.
  • Idempotency. The natural key (user, slot) already makes BOOK idempotent. For REST, also accept an Idempotency-Key header. Store each key with its response for 24 h, and send the stored response again on a repeat.
  • Time. Pass in a Clock. "Upcoming" uses clock.instant(). Store Instant. Convert with the slot's ZoneId only for display and for "per day" rules. Refuse bookings in the past.
  • Holds. A HELD booking has an expiresAt time. When checking capacity, treat expired holds as free. This is lazy expiry. Also clean them up with a ScheduledExecutorService. Confirm must check expiresAt again under the lock. Payment may succeed after the hold expired. Then you must refund or hold again.
  • Validation. Check start < end, capacity > 0 and a unique id (putIfAbsent). Handle an unknown user or slot. Handle a cancel for a booking that does not exist.

public record TimeRange(Instant start, Instant end) {
    public TimeRange {
        if (!start.isBefore(end)) throw new IllegalArgumentException("start must be before end");
    }
    /** Half-open: [09:00,10:00) and [10:00,11:00) do not overlap. */
    public boolean overlaps(TimeRange o) {
        return start.isBefore(o.end) && o.start.isBefore(end);
    }
}

Show Slot (capacity and FIFO waitlist) 
public final class Slot {
    final String id;
    final String title;
    final TimeRange range;
    final int capacity;
    final ReentrantLock lock = new ReentrantLock();
    // Guarded by lock:
    final LinkedHashSet<String> booked = new LinkedHashSet<>();
    final LinkedHashSet<String> waitlist = new LinkedHashSet<>();   // FIFO + O(1) contains/remove

    Slot(String id, String title, TimeRange range, int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
        this.id = id; this.title = title; this.range = range; this.capacity = capacity;
    }
    boolean hasSeat() { return booked.size() < capacity; }
}
Show UserSchedule (O(log n) overlap)

A user's confirmed bookings never clash with each other. So only one booking can clash with the new one. It is the booking with the latest start before the new booking's end.

final class UserSchedule {
    final ReentrantLock lock = new ReentrantLock();
    private final TreeMap<Instant, Booking> byStart = new TreeMap<>();   // guarded by lock

    boolean overlaps(TimeRange r) {
        Map.Entry<Instant, Booking> before = byStart.lowerEntry(r.end());
        return before != null && before.getValue().range().end().isAfter(r.start());
    }
    long countOn(LocalDate day, ZoneId zone) {
        Instant from = day.atStartOfDay(zone).toInstant();
        Instant to = day.plusDays(1).atStartOfDay(zone).toInstant();
        return byStart.subMap(from, true, to, false).size();
    }
    void add(Booking b) { byStart.put(b.range().start(), b); }
    void remove(Booking b) { byStart.remove(b.range().start()); }
    Collection<Booking> upcoming(Instant now) { return List.copyOf(byStart.tailMap(now, true).values()); }
}
Show BookingService (lock ordering, rules, idempotency, waitlist) 
public interface BookingRule {
    void check(UserSchedule user, Slot slot);   // throws BookingRejected
}

public final class BookingService {
    private final ConcurrentHashMap<String, Slot> slots = new ConcurrentHashMap<>();
    private final ConcurrentHashMap<String, UserSchedule> users = new ConcurrentHashMap<>();
    private final ConcurrentHashMap<String, Booking> bookings = new ConcurrentHashMap<>(); // key: userId|slotId
    private final List<BookingRule> rules;
    private final Clock clock;

    public BookingService(List<BookingRule> rules, Clock clock) { this.rules = rules; this.clock = clock; }

    public void addSlot(String id, String title, TimeRange range, int capacity) {
        if (slots.putIfAbsent(id, new Slot(id, title, range, capacity)) != null)
            throw new IllegalArgumentException("duplicate slot " + id);
    }

    public Booking book(String userId, String slotId) {
        Slot slot = Optional.ofNullable(slots.get(slotId)).orElseThrow(() -> new NotFound(slotId));
        UserSchedule user = users.computeIfAbsent(userId, u -> new UserSchedule());
        // Fixed order everywhere: user lock, then slot lock. Cancel uses the same order, so no deadlock.
        user.lock.lock();
        slot.lock.lock();
        try {
            Booking existing = bookings.get(key(userId, slotId));
            if (existing != null) return existing;                // idempotent: same answer on retry
            if (slot.waitlist.contains(userId)) return waitlisted(userId, slot);
            for (BookingRule rule : rules) rule.check(user, slot);   // overlap, daily limit, ...
            if (!slot.hasSeat()) {
                slot.waitlist.add(userId);
                return waitlisted(userId, slot);
            }
            return confirm(user, userId, slot);
        } finally {
            slot.lock.unlock();
            user.lock.unlock();
        }
    }

    public void cancel(String userId, String slotId) {
        Slot slot = Optional.ofNullable(slots.get(slotId)).orElseThrow(() -> new NotFound(slotId));
        UserSchedule user = users.computeIfAbsent(userId, u -> new UserSchedule());
        String promoted;
        user.lock.lock();
        slot.lock.lock();
        try {
            if (slot.waitlist.remove(userId)) return;
            Booking b = bookings.remove(key(userId, slotId));
            if (b == null) throw new NotFound(userId + " in " + slotId);
            slot.booked.remove(userId);
            user.remove(b);
            promoted = slot.waitlist.isEmpty() ? null : slot.waitlist.iterator().next();
        } finally {
            slot.lock.unlock();
            user.lock.unlock();
        }
        // Promote outside our locks: book() takes the promoted user's lock first, keeping lock order.
        if (promoted != null) promote(promoted, slot);
    }

    private void promote(String userId, Slot slot) {
        UserSchedule user = users.get(userId);
        user.lock.lock();
        slot.lock.lock();
        try {
            if (!slot.waitlist.remove(userId) || !slot.hasSeat()) return;   // state moved on meanwhile
            try {
                for (BookingRule rule : rules) rule.check(user, slot);
                confirm(user, userId, slot);
            } catch (BookingRejected e) {
                // User booked something overlapping since joining the waitlist: skip to the next one.
                String next = slot.waitlist.isEmpty() ? null : slot.waitlist.iterator().next();
                if (next != null) Thread.ofVirtual().start(() -> promote(next, slot));
            }
        } finally {
            slot.lock.unlock();
            user.lock.unlock();
        }
    }

    private Booking confirm(UserSchedule user, String userId, Slot slot) {
        Booking b = new Booking(UUID.randomUUID().toString(), userId, slot.id, slot.range, BookingStatus.CONFIRMED);
        slot.booked.add(userId);
        user.add(b);
        bookings.put(key(userId, slot.id), b);
        return b;
    }

    private static Booking waitlisted(String userId, Slot slot) {
        return new Booking(null, userId, slot.id, slot.range, BookingStatus.WAITLISTED);
    }
    private static String key(String userId, String slotId) { return userId + "|" + slotId; }
}

Moving to the next person in line uses a new thread. This only avoids re-entering the code while still holding locks. In an interview, a simple loop that releases and takes the locks again is just as good. Say which you chose and why.

Show rules: NoOverlapRule, DailyLimitRule 
public final class NoOverlapRule implements BookingRule {
    public void check(UserSchedule user, Slot slot) {
        if (user.overlaps(slot.range)) throw new OverlappingBooking(slot.id);
    }
}

public final class DailyLimitRule implements BookingRule {
    private final int maxPerDay;
    private final ZoneId zone;
    public DailyLimitRule(int maxPerDay, ZoneId zone) { this.maxPerDay = maxPerDay; this.zone = zone; }
    public void check(UserSchedule user, Slot slot) {
        LocalDate day = LocalDate.ofInstant(slot.range.start(), zone);
        if (user.countOn(day, zone) >= maxPerDay) throw new DailyLimitReached(day);
    }
}
Show RoomCalendar (meeting-room variant, free-form ranges) 
final class RoomCalendar {
    private final TreeMap<Instant, Booking> byStart = new TreeMap<>();

    synchronized boolean tryBook(Booking b) {
        Map.Entry<Instant, Booking> before = byStart.lowerEntry(b.range().end());
        if (before != null && before.getValue().range().end().isAfter(b.range().start())) return false;
        byStart.put(b.range().start(), b);
        return true;
    }
}

To find any free room for a time range, go through the rooms from smallest to largest that fits. Call tryBook on each. Each call is atomic for its room. So if you lose a race, you just move on to the next room.

08Extensions interviewers add mid-round

Pessimistic or optimistic? (InMobi IRCTC)

Pessimistic Tatkal hot row

  • No flood of retries when thousands hit one train
  • Others wait, so keep transactions tiny

Or let one writer handle each train, using a Kafka partition keyed by train id.

Optimistic

  • No locks are held
  • When many compete, most attempts fail and retry

Use it off-peak, or for meeting rooms.

Waitlist + promotion

Already built. Trains add RAC (shared berth) between waitlist and confirmed: WL → RAC → CNF.

Daily limit K

Add one new DailyLimitRule. The service does not change.

REST (Postman)

201 with Location on success. 409 for a clash, 400 for bad input, 404 if missing, 204 on delete.

Recurring (Eightfold)

Store a repeat rule. Expand it in the room's time zone. Book all dates or none.

Seat hold (CRED)

Hold the seat with a timer and save the price. Then pay, then confirm.

Many pods

Move the rule into the database, or send each resource to one server.

Go deeper: full answers for each extension
Waitlist with auto-promotion (Udaan, Swiggy train booking)

This is already in the design. Each slot has a LinkedHashSet. It keeps FIFO order and removes a waitlisted user in O(1) if they cancel. On a cancel, move up the first person. If that person now breaks a rule (a clash, or the daily limit), skip to the next. For trains, add RAC (Reservation Against Cancellation, a shared berth) as a middle state. Move people up in the order WL → RAC → CNF, one berth per cancellation.

Daily limit K, configurable (Udaan)

Add a new DailyLimitRule(K, zone) to the rules list. The service does not change. The count comes from the user's TreeMap.subMap for that local day.

REST API with correct codes and headers (Postman)

POST /rooms/{id}/bookings returns 201 Created, with Location: /bookings/{bookingId} and the body. A clash returns 409 Conflict with the clashing booking id. Bad input, like an end before the start or a missing field, returns 400. Use 422 for input that is well-formed but invalid. An unknown room returns 404. A repeat with the same Idempotency-Key returns the original 201 response. DELETE /bookings/{id} returns 204. GET on a list returns 200 with pagination. For updates, return an ETag (a version tag) and require If-Match. Return 412 if they don't match. This is optimistic concurrency over HTTP.

In Spring, a @RestControllerAdvice maps OverlappingBooking to 409. It maps validation errors to 400 with a ProblemDetail body, in the RFC 7807 style.

Recurring bookings (Eightfold)

Store a repeat rule, like an iCalendar RRULE. It has frequency, interval, an end date or count, and the days of the week. Expand the dates up to a limit, for example 6 months ahead. Do it in the room's time zone, so 10:00 stays 10:00 when daylight saving changes. Book all dates atomically. Lock the room once, check every date, then insert all or none. Report which dates clash. Editing "this and following" splits the series into two rules. Never create an endless series.

Seat lock with timeout and per-seat price (CRED flights, movie and train variants)

Use two steps. First HOLD: the seat status becomes HELD, with a hold_until time and a saved copy of the price. Then pay, then CONFIRM. The price is fixed when you hold. So a later fare change does not change what the user pays. Expiry is lazy, meaning a held seat whose hold_until has passed counts as free. A background sweeper also cleans up. In Redis, SET seat:{flight}:{seat} {userId} NX PX 600000 is a fast hold. The database's conditional update stays the source of truth.

Other platforms sell the same seats (CRED)

You don't own the seats, so your lock is only advisory. The airline's system is the source of truth. You reach it through the GDS, the global booking network airlines use. You ask the airline for a hold and get back a PNR or hold reference with an expiry. Then you confirm against it. The CRED candidate said "the airline locks on the platform's behalf", and that convinced the interviewer. Your local hold must be shorter than the airline's hold.

Pessimistic vs optimistic (InMobi IRCTC)

Tatkal opening is the textbook hot row. Thousands try at once. With optimistic locking, most attempts fail and retry. So use pessimistic row locks with short transactions. Better still, use one queue per train, so one writer handles each train. For example, use a Kafka partition keyed by train id. Off-peak, optimistic locking is cheaper. Say that how many users compete decides the choice.

Multiple app instances

In-memory locks only protect one JVM. Move the rule into the database, with a constraint or a row lock. Or send all requests for one resource to one server (partition by resource id). A Redis lock through Redisson also works. But it needs fencing tokens or a database check. A lock holder can pause, and wake up after its lease ran out, still thinking it holds the lock.

10Mistakes that got candidates rejected

Common mistakes
  • Checking and writing in two unprotected steps, then saying "add synchronized" in the review (Flipkart).
  • One giant synchronized block, with no word about how it slows everything down.
  • Ranges that include the end time, so back-to-back bookings fail.
  • Stage 2 half-built while Stage 1 is still broken (Udaan).
  • In REST, returning 200 for everything, or 500 for a clash.
  • Calling payment inside the transaction that holds the seat lock.
Go deeper: the rejection notes in full
  • Checking availability and writing the booking in two unprotected steps. Then waving it away with "add synchronized" in the review. Flipkart's follow-up was exactly this.
  • One giant synchronized on the service, with no explanation of how it limits throughput (bookings per second).
  • A clash check that includes the end time, so back-to-back bookings fail.

12Quick check

09:00–10:00 is booked. Should 10:00–11:00 be allowed? Which check gives that?

With [start, end), the end time 10:00 is not part of the first booking. So the new booking can start at 10:00.

Thread 1 locks the user, then the slot. Thread 2 locks the slot, then the user. What can happen?

Each thread holds one lock and waits for the other, forever. Using one fixed order everywhere makes this impossible.

Tatkal opens and 50,000 users hit one train. Which database approach should you use?

When so many compete, almost every optimistic attempt fails and retries. Waiting in line for a lock is faster overall.

Why does UserSchedule.overlaps only check lowerEntry(end)?

The user's bookings never clash and are kept sorted. So only one booking needs checking. That makes the check O(log n) instead of a full scan.

13Interview questions

Why two locks? Can it deadlock?

Capacity belongs to the slot, and clashes belong to the user. Both must still be true when you commit. Every path takes the user lock, then the slot lock. So no thread can wait in a circle. The promotion path releases the cancelling user's locks before it takes the promoted user's locks.

Why lowerEntry(end) and not a scan?

The existing bookings never clash and are sorted. So the only one that could clash is the latest one starting before the new end. That is O(log n) instead of O(n).

How would you move this to Postgres with five pods?

The repositories become JPA. Capacity uses a conditional UPDATE … WHERE booked < capacity, or SELECT … FOR UPDATE. User clashes use an exclusion constraint on (user_id, during). Idempotency uses UNIQUE(user_id, slot_id). The in-process locks are no longer needed.

What if the waitlisted user's notification fails?

Commit the promotion first, as a state change. Publish the notification as an event after the commit, using the outbox pattern. The outbox pattern saves the event in the same transaction, and a separate process sends it. The notification is then retried on its own.

Where would you add a "max 7 days ahead" rule?

Write a new BookingRule that uses the passed-in Clock. The service does not change.

Cheat sheet
  • Half-open clash test: a.start < b.end && b.start < a.end.
  • Keep a per-user TreeMap sorted by start. lowerEntry(end) is O(log n).
  • Lock the user, then the slot, everywhere. Promote only after releasing.
  • Repeats are safe because the key is (user, slot). REST adds an Idempotency-Key.
  • Waitlist: a LinkedHashSet. Skip anyone first in line who now clashes.
  • Rules are a list of BookingRule. Pass in the Clock.
  • Database: FOR UPDATE when many compete, @Version when few do, plus unique and exclusion constraints.
  • Holds: a timer, lazy expiry, and a re-check on confirm. Never pay inside the lock.
