Database isolation, locking and indexes

What actually happens inside PostgreSQL and MySQL InnoDB when two transactions touch the same rows, how an index finds a row in three page reads, and the SQL you will be asked to write live. Enough depth to survive a dedicated database round.

01Why interviewers ask this

Every backend system you will design in an interview ends at a database, and the senior signal is whether you know what the database guarantees and what it does not. Real 2025–26 reports:

  • Dream11 SDE-2 ran a round that started from the candidate's project, moved to why that database was chosen, then into concurrency control, isolation levels, locks and replication, all scenario-based, for an hour.
  • Zomato SDE-2 gave an order-state-transition table (Created → Confirmed → Reached Merchant → Reached Customer → Delivered) and asked for every order's latest state in the last hour, excluding delivered ones, then "how does this behave at scale, which indexes would you add?"
  • InMobi SDE-2 asked how to handle concurrency during seat booking: pessimistic versus optimistic locking, then the core booking code.
  • Freshworks SDE-2 asked what indexing is, how it helps query optimisation and how it works internally, plus sharding versus partitioning and the celebrity problem.
  • CRED SDE-2: the candidate mentioned indexing and got a deep dive into LSM trees, then SSTables when they mentioned BigTable. They could not explain either and were rejected. Their advice: if you name it, know how it works.
  • JPMC Lead SE: rapid fire on Cassandra replication factor, partition key versus clustering key, and tuning consistency.
  • Kotak SDE-2: what is a lock, which kinds exist, when to use one and when to avoid it.
The bar for 5 years of experience

Name the anomaly, say which isolation level prevents it in the database you actually use, and give the fix you would ship (atomic update, row lock, version column or SERIALIZABLE with retry). Generic "use transactions" answers read as junior.

02Core concepts, built up

Transactions and the five anomalies

A transaction is a unit that commits or rolls back as a whole. Isolation is the "I" in ACID: how much one in-flight transaction can see or disturb another. Full isolation (serializability) means the result equals some one-at-a-time ordering. Weaker levels trade correctness for concurrency, and each lets specific anomalies through.

Dirty readT2 reads data T1 wrote but has not committed; T1 rolls back.Payment page shows a balance credited by a transfer that later failed.
Non-repeatable readT1 reads a row twice and gets different values because T2 committed an update in between.Invoice total computed from a price that changes mid-report.

Write skewBoth read an overlapping set, each updates a different row based on what it read, and together they break an invariant.Two on-call doctors each check "someone else is on call" and both go off call.

The trap answer

"Repeatable Read prevents lost updates" is true in PostgreSQL and false in MySQL InnoDB. Same name, different engine behaviour. If you use MySQL at Repeatable Read and do SELECT then UPDATE ... SET count = ?, you can lose writes. Say which engine you mean.

The four fixes for read-modify-write

-- 1. Atomic update: let the database do the arithmetic (best when possible)
UPDATE envelope SET signed_count = signed_count + 1 WHERE id = :id;

-- 2. Conditional atomic update: encode the invariant in the WHERE clause
UPDATE seat SET status = 'HELD', held_by = :user
WHERE id = :seatId AND status = 'FREE';         -- 0 rows updated = someone beat you

-- 3. Pessimistic lock: read with a row lock, then write
BEGIN;
SELECT balance FROM account WHERE id = :id FOR UPDATE;
UPDATE account SET balance = :newBalance WHERE id = :id;
COMMIT;

-- 4. Optimistic lock: version column checked at write time
UPDATE seat SET status = 'BOOKED', version = version + 1
WHERE id = :id AND version = :versionIRead;     -- 0 rows = conflict, retry or fail

Option 2 is the one most candidates miss. For "hold this seat" it needs no explicit lock, no version column and no retry loop: the row lock taken by the UPDATE plus the predicate make it safe at any isolation level.

Pessimistic versus optimistic (the InMobi question)

Pessimistic: SELECT … FOR UPDATE

  • Takes a row lock on read; others block until commit.
  • Good when conflicts are frequent (hot seats in the first minute of a sale, one wallet row).
  • Costs: blocked threads hold DB connections; deadlock risk; never hold it across an HTTP call.
  • Use NOWAIT or a lock timeout so users get "seat taken" instead of a 30-second spinner.

Optimistic: JPA @Version

  • No lock on read; the UPDATE checks the version.
  • Good when conflicts are rare and transactions are short or span user think-time (edit form open for two minutes).
  • Loser gets an exception: retry automatically if the operation is idempotent, or show "someone changed this".
  • Under heavy contention it degrades into retry storms.
@Entity
public class Seat {
    @Id private Long id;
    private String status;
    @Version private long version;   // Hibernate adds "AND version = ?" and increments it
}

public interface SeatRepository extends JpaRepository<Seat, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)            // SELECT ... FOR UPDATE
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "0")) // NOWAIT
    @Query("select s from Seat s where s.id = :id")
    Optional<Seat> findForUpdate(@Param("id") Long id);

    @Modifying
    @Query("update Seat s set s.status = 'HELD', s.heldBy = :user where s.id = :id and s.status = 'FREE'")
    int tryHold(@Param("id") Long id, @Param("user") String user);   // 1 = held, 0 = lost the race
}

With @Version, a stale write throws OptimisticLockException, which Spring translates to ObjectOptimisticLockingFailureException. It surfaces at flush or commit, not at the save() line, so catch it outside the @Transactional method if you want to retry.

Queue-style locking: SKIP LOCKED

For a table used as a work queue (outbox relays, document-processing jobs), many workers must each grab different rows without blocking each other.

-- Each worker claims up to 50 unclaimed jobs; rows locked by other workers are skipped, not waited on
WITH next AS (
  SELECT id FROM job
  WHERE status = 'PENDING' AND run_at <= now()
  ORDER BY run_at
  LIMIT 50
  FOR UPDATE SKIP LOCKED
)
UPDATE job SET status = 'RUNNING', locked_by = :worker, locked_at = now()
FROM next WHERE job.id = next.id
RETURNING job.*;

PostgreSQL has supported SKIP LOCKED since 9.5 and MySQL since 8.0. Pair it with a partial index on pending rows (below) and a reaper that resets rows stuck in RUNNING after a lease expires.

03How it works internally

MVCC: readers do not block writers

Both engines use multi-version concurrency control: an UPDATE creates a new version of the row instead of overwriting it, and each transaction reads the version that was committed as of its snapshot.

PostgreSQL

  • Every heap tuple carries xmin (creating transaction) and xmax (deleting or updating transaction).
  • UPDATE = write a new tuple + set xmax on the old one. Old versions stay in the table until VACUUM removes them.
  • A snapshot is the set of transaction IDs that were in progress; visibility is computed per tuple.
  • Read Committed takes a new snapshot per statement; Repeatable Read takes one at the first statement.
  • Cost: table and index bloat, and long-running transactions stop VACUUM from cleaning anything newer than them.

MySQL InnoDB

  • Updates the row in place in the clustered index and writes the previous version to the undo log.
  • A read view decides visibility; older versions are rebuilt by walking undo records.
  • A purge thread discards undo once no read view needs it.
  • Locking reads and UPDATE/DELETE read the latest committed version, not the snapshot. This is why RR does not detect lost updates.
  • Cost: long transactions grow the undo history ("history list length").
T1 snapshottxid 100→ row v1xmin 90←UPDATE T2txid 101→ row v2xmin 101

Figure: T1 started before T2 committed, so T1 keeps reading v1. A new transaction sees v2. VACUUM removes v1 once no snapshot can see it.

Deadlocks

T1 locks row A then wants B; T2 locks B then wants A. Neither can proceed. PostgreSQL checks for cycles after deadlock_timeout (1 s by default) and aborts one transaction with SQLSTATE 40P01. InnoDB detects immediately (innodb_deadlock_detect, on by default), rolls back the transaction with the fewest changes and returns error 1213. SHOW ENGINE INNODB STATUS prints the latest deadlock.

  • Prevent: lock rows in a consistent order (ORDER BY id FOR UPDATE; in a transfer, always lock the lower account ID first), keep transactions short, add indexes so UPDATEs lock fewer rows (an unindexed WHERE in InnoDB locks every scanned row and gap).
  • Handle: deadlocks are normal under load. Retry the whole transaction a bounded number of times. Spring surfaces them as CannotAcquireLockException / PessimisticLockingFailureException.

B-tree indexes

Both engines use B+trees: values only in the leaves, internal pages hold separator keys and child pointers, leaves are linked for range scans. Pages are 8 KB in PostgreSQL and 16 KB in InnoDB. With a fan-out of several hundred keys per page, three or four levels reach hundreds of millions of rows, so a point lookup is three or four page reads, most from cache.

Root pagekeys 1000 | 5000→ Internal page1000 | 2000 | 3000→ Leaf pagesorted keys + pointers↔ Next leafrange scan

Figure: a lookup descends from root to leaf; a range scan walks sibling leaves.

InnoDB: clustered

The table is the primary-key B+tree; leaves hold full rows. Secondary index leaves hold the PK value, so a secondary lookup is two tree walks. Random UUIDv4 primary keys insert all over the tree and cause page splits; prefer BIGINT or time-ordered UUIDv7.

PostgreSQL: heap

Rows live in an unordered heap; every index (including the PK) points to a tuple ID (ctid). An index-only scan can skip the heap only when the visibility map marks the page all-visible, which VACUUM maintains. PostgreSQL 18 adds a built-in uuidv7().

Composite index column order

A composite index on (a, b, c) is sorted by a, then b within a, then c. It serves queries that constrain a leftmost prefix. Order columns as equality, then sort, then range:

-- Query: a tenant's pending documents, newest first
SELECT id, title FROM document
WHERE tenant_id = ? AND status = 'PENDING' AND created_at > now() - interval '7 days'
ORDER BY created_at DESC LIMIT 20;

CREATE INDEX idx_doc_tenant_status_created
  ON document (tenant_id, status, created_at DESC);   -- equality, equality, range+sort
-- (created_at, tenant_id, status) would scan every tenant's last 7 days and then filter

A range condition stops the index from narrowing later columns, because within the range the later column is no longer sorted. Higher selectivity first is a weaker rule than "equality before range". PostgreSQL 18 adds skip scan, so a B-tree on (status, created_at) can now serve WHERE created_at > … when status has few distinct values. Do not rely on it in an interview answer; design the index for the query.

Covering and partial indexes

-- Covering: the index has every column the query needs, so the table is never touched
CREATE INDEX idx_order_user ON orders (user_id, created_at DESC) INCLUDE (status, amount);  -- PG 11+
-- MySQL: put the columns in the key; EXPLAIN shows "Using index"

-- Partial (PostgreSQL): index only the rows you query; small, hot, cheap to maintain
CREATE INDEX idx_job_pending ON job (run_at) WHERE status = 'PENDING';
CREATE UNIQUE INDEX uq_active_email ON users (email) WHERE deleted_at IS NULL;  -- soft-delete-safe uniqueness

MySQL has no partial indexes; the usual workaround is a generated column that is NULL for inactive rows, indexed (NULLs do not collide in a UNIQUE index). Every index costs write throughput, storage and buffer pool, so drop the ones pg_stat_user_indexes.idx_scan shows are unused.

B-tree versus LSM tree (the CRED question)

An LSM (log-structured merge) tree optimises writes by never updating in place.

Writekey, value→ WALappend, for crash recovery+ Memtablesorted, in memory→flush when full SSTable L0immutable, sorted→compaction L1 … Lnlarger, merged

Figure: LSM write path. Reads check the memtable, then SSTables from newest to oldest, using a Bloom filter per SSTable to skip files that cannot contain the key.

  • SSTable (sorted string table): an immutable file of key-sorted records, with a block index and a Bloom filter. Because it never changes, it can be cached, copied and merged safely. Google BigTable introduced the term; Cassandra, HBase, RocksDB and ScyllaDB use the same idea.
  • Deletes write a tombstone; the data disappears only when compaction merges past it (Cassandra keeps tombstones for gc_grace_seconds so replicas learn about the delete).
  • Compaction: size-tiered merges similar-sized files (cheap writes, more space and read amplification); leveled keeps non-overlapping ranges per level (better reads, more write amplification).
B+tree (Postgres, InnoDB)LSM (Cassandra, RocksDB)
WritesRandom page writes in place, plus WALSequential appends; very high write throughput
Point reads3–4 page reads, predictableMemtable + possibly several SSTables; Bloom filters keep it cheap
Range scansExcellent (linked leaves)Good within a partition; merges several files
AmplificationWrite amplification from page rewritesWrite amplification from compaction; space amplification from obsolete versions
Choose whenTransactions, mixed reads and writes, secondary indexes, joinsWrite-heavy, append-like data: events, time series, messages, feeds

Cassandra partition key versus clustering key (the JPMC question)

CREATE TABLE audit_event (
  tenant_id  text,
  day        date,
  event_time timestamp,
  event_id   timeuuid,
  action     text,
  PRIMARY KEY ((tenant_id, day), event_time, event_id)
) WITH CLUSTERING ORDER BY (event_time DESC, event_id DESC);
  • Partition key (tenant_id, day) is hashed (Murmur3) to a token, which picks the replica nodes. All rows of a partition live together. Every query must supply the full partition key. Adding day bounds partition size (keep partitions well under ~100 MB) and stops a big tenant becoming one hot partition.
  • Clustering columns event_time, event_id sort rows on disk inside the partition, which makes "latest 50 events for tenant X today" a sequential slice.
  • Tunable consistency: with replication factor 3, writing and reading at QUORUM (2 of 3) gives R + W > N, so a read overlaps the latest acknowledged write. LOCAL_QUORUM keeps that inside one data centre.

Replication and read replicas

PostgreSQL streams WAL to standbys (physical replication); MySQL ships the binlog (row-based by default, with GTIDs). Both are asynchronous by default, which means a replica can be seconds behind.

ModeGuaranteeCost
AsyncCommit returns before any replica has the data; failover can lose recent commitsLowest latency
Semi-sync (MySQL) / synchronous_commit = remote_write or on with a sync standby (PG)At least one replica has received (or flushed) the WAL before commit returnsOne network round trip per commit; a stuck replica stalls writes unless you have several candidates
remote_apply (PG)The standby has applied it, so reads there see itHighest latency

Read-your-writes on replicas: after a user saves, the next page load may hit a lagging replica and show old data. Fixes: route that user's reads to the primary for a few seconds after a write; or record the commit LSN / GTID and only read from a replica that has passed it; or read from primary for anything the user just changed. Monitor lag with pg_stat_replication.replay_lag or Seconds_Behind_Source.

04Practical patterns and production gotchas

The Zomato query, done properly

-- order_event(id BIGSERIAL, order_id BIGINT, state TEXT, created_at TIMESTAMPTZ)
-- Latest state per order among events in the last hour, excluding delivered orders
WITH ranked AS (
  SELECT order_id, state, created_at,
         ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY created_at DESC, id DESC) AS rn
  FROM order_event
  WHERE created_at >= now() - interval '1 hour'
)
SELECT order_id, state AS latest_state, created_at
FROM ranked
WHERE rn = 1 AND state <> 'DELIVERED';

-- PostgreSQL shorthand for the same thing
SELECT DISTINCT ON (order_id) order_id, state, created_at
FROM order_event
WHERE created_at >= now() - interval '1 hour'
ORDER BY order_id, created_at DESC, id DESC;      -- then filter state in an outer query

Clarify first: "orders with any activity in the last hour" (above) or "orders whose latest state overall is not delivered and changed in the last hour"? They differ for an order delivered 2 hours ago with no new events. Use id as a tiebreaker because two events can share a timestamp.

Indexes: CREATE INDEX ON order_event (created_at) INCLUDE (order_id, state, id) makes the one-hour window an index-only range scan. If the question is "latest event per order" over all time, (order_id, created_at DESC) lets each order's latest row be the first index entry.

At scale (the follow-up): ranking every event in the window gets expensive at millions of orders per hour. The senior answer is to stop deriving current state from history on every read: keep orders.current_state updated in the same transaction as the event insert, and add a partial index ON orders (updated_at) WHERE current_state <> 'DELIVERED'. The event table stays for audit and is range-partitioned by day so old partitions can be dropped instead of deleted.

Other SQL you will be asked to write

-- Second-highest distinct salary (LeetCode 176); returns NULL if it does not exist
SELECT MAX(salary) AS second_highest
FROM employee
WHERE salary < (SELECT MAX(salary) FROM employee);

-- Nth highest per department with window functions (ties share a rank)
SELECT department_id, name, salary
FROM (
  SELECT e.*, DENSE_RANK() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rnk
  FROM employee e
) t
WHERE rnk = 2;

-- GROUP BY / HAVING: customers with more than 3 orders above 500 in 30 days
SELECT customer_id, COUNT(*) AS big_orders, SUM(amount) AS total
FROM orders
WHERE amount > 500 AND created_at >= now() - interval '30 days'   -- WHERE filters rows
GROUP BY customer_id
HAVING COUNT(*) > 3                                                -- HAVING filters groups
ORDER BY total DESC;

-- Running total and day-over-day change
SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day) AS running_total,
       revenue - LAG(revenue) OVER (ORDER BY day) AS change_vs_prev_day
FROM daily_revenue;

-- Duplicates: emails used by more than one account
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

Know the difference between ROW_NUMBER (always unique), RANK (ties share, gaps after: 1,1,3) and DENSE_RANK (ties share, no gaps: 1,1,2). Window functions run after WHERE/GROUP BY/HAVING, which is why you cannot filter on rn in the same query level.

Spring Boot gotchas

  • Self-invocation: calling a @Transactional method from another method of the same bean bypasses the proxy, so there is no transaction and no row lock lasts past the statement.
  • Long transactions: never call a payment gateway or S3 inside a transaction that holds FOR UPDATE. Locks are held until commit; one slow vendor call stalls every booking on that row and pins a Hikari connection.
  • Open Session in View is on by default in Spring Boot and keeps a connection for the whole request. Set spring.jpa.open-in-view=false.
  • Isolation per method: @Transactional(isolation = Isolation.SERIALIZABLE) only works when it starts the transaction; wrap it in a retry on CannotAcquireLockException / SQLSTATE 40001, outside the transaction.
  • Read replicas: routing with AbstractRoutingDataSource on @Transactional(readOnly = true) needs LazyConnectionDataSourceProxy, otherwise the connection is fetched before the read-only flag is known.
  • Batch deletes and updates: UPDATE ... WHERE status = 'X' without an index locks every scanned row in InnoDB at RR. Update in chunks by primary key.
  • Migrations: CREATE INDEX CONCURRENTLY in PostgreSQL (cannot run inside a transaction, so Flyway needs it in a non-transactional migration); online DDL in MySQL 8.

05Interview questions with senior answers

What isolation level does your service use, and why?

PostgreSQL's default, Read Committed. Most of our writes are single-row atomic updates or inserts guarded by unique constraints, which are safe at RC. Where we have read-then-write invariants (counting signers before completing an envelope) we take a row lock on the parent with FOR UPDATE. I would use Serializable only for a small set of transactions whose invariant spans many rows, wrapped in a retry loop, because SSI aborts add retries under contention.

Does Repeatable Read prevent phantoms?

The SQL standard allows phantoms at RR. PostgreSQL's RR is snapshot isolation, so a repeated query sees no new rows. InnoDB's RR hides them from plain SELECTs via the read view and blocks them for locking reads via next-key locks, but a plain SELECT followed by an UPDATE can still act on rows inserted after the snapshot. Neither stops write skew.

Explain write skew with an example and how to stop it.

The on-call doctor case: rule "at least one doctor on call". Alice and Bob each run SELECT count(*) WHERE on_call, see 2, and each sets themselves off call. They updated different rows, so no row-level conflict is detected and both commit with zero on call. Fixes: SERIALIZABLE in PostgreSQL (SSI detects the dependency cycle); lock the rows you read with FOR UPDATE; or materialise the conflict as one row (a shift row both must update).

How would you prevent double-booking a seat?

Simplest robust answer: a conditional update UPDATE seat SET status='HELD', held_by=?, hold_expires_at=? WHERE id=? AND status='FREE' and check the row count; plus a unique constraint on (show_id, seat_id) in the booking table as the last line of defence. For multi-seat holds, lock seats in sorted ID order with FOR UPDATE NOWAIT to avoid deadlocks and fail fast. Optimistic @Version fits when contention is low; in a flash sale it turns into a retry storm.

What is MVCC and what does it cost?

Writers create new row versions and readers read the version visible in their snapshot, so reads never block on writes. PostgreSQL keeps old tuples in the heap until VACUUM; InnoDB keeps them in undo logs until purge. The cost is bloat and the risk that one long-running or idle-in-transaction session prevents cleanup across the whole database.

How does an index make a query fast, internally?

A B+tree keeps keys sorted in pages with high fan-out, so finding a key is a root-to-leaf descent of 3–4 pages instead of reading the whole table. Leaves are linked, so range scans and ORDER BY on the index columns are sequential. In InnoDB the PK index holds the row; a secondary index holds the PK, needing a second lookup unless the index covers the query.

Index on (a, b). Does WHERE b = ? use it?

Traditionally no, because the index is sorted by a first; the planner would scan the whole index at best. PostgreSQL 18's skip scan can use it if a has few distinct values, by probing each a. The real answer: add an index led by b if this query matters.

When does the planner ignore an index you created?

When it estimates many rows match (a sequential scan is cheaper beyond a few per cent of the table); when the column is wrapped in a function or cast (WHERE lower(email) = ? needs an expression index); with a leading-wildcard LIKE; when statistics are stale; or with an OR across different columns. Check with EXPLAIN ANALYZE and compare estimated and actual rows.

B-tree or LSM tree: when would you pick each?

B-tree for transactional workloads with mixed reads and writes, secondary indexes and joins. LSM for write-heavy, append-shaped data such as events, metrics or chat messages, where sequential writes and compaction beat random page updates. An LSM read may consult several SSTables, which Bloom filters and compaction keep cheap; writes pay compaction amplification later.

How do you detect and fix deadlocks in production?

PostgreSQL logs both statements with SQLSTATE 40P01 (enable log_lock_waits too); MySQL shows the latest in SHOW ENGINE INNODB STATUS. Fix the access order so every code path locks rows in the same sequence, shorten transactions, index the WHERE clauses of UPDATEs so fewer rows and gaps are locked, and keep a bounded retry for the remaining cases.

Your read replica shows stale data right after a user saves. What do you do?

That is asynchronous replication lag breaking read-your-writes. Pin that user's reads to the primary for a short window after a write (a cookie or a request-scoped flag), or track the commit position and only use a replica that has replayed past it. Alert on replica lag and take a lagging replica out of the read pool.

Partition key versus clustering key in Cassandra?

The partition key is hashed to choose which nodes own the data and must be fully specified in queries; rows of one partition live together. Clustering columns define the sort order inside the partition, enabling efficient range slices. Design tables per query, bucket partition keys by time to keep partitions bounded, and use QUORUM reads and writes for read-after-write consistency.

Optimistic lock failed. Should you retry automatically?

Only if the operation is a pure function of current state (increment a counter, append an item) and the request is idempotent: reload, reapply, save, with a small bounded number of attempts. If the user decided based on what they saw (editing a contract field), do not retry silently; return 409 Conflict and let them review the new version.

What makes a covering index, and what is the trade-off?

The index contains every column the query reads, so the engine never visits the table: "Index Only Scan" in PostgreSQL, "Using index" in MySQL. Use INCLUDE in PostgreSQL to add payload columns without affecting sort order. Trade-off: a bigger index, slower writes, and more memory pressure.

06Hands-on exercise (45 minutes)

  1. Start PostgreSQL: docker run --rm -e POSTGRES_PASSWORD=pw -p 5432:5432 postgres:18. Open two psql sessions.
  2. Lost update. CREATE TABLE counter(id int primary key, n int); INSERT INTO counter VALUES (1, 0); In both sessions at Read Committed: BEGIN; SELECT n FROM counter WHERE id=1; then each runs UPDATE counter SET n = 1 WHERE id=1; COMMIT;. Final value is 1, not 2. Repeat with BEGIN ISOLATION LEVEL REPEATABLE READ and observe the serialization error in the second session. Repeat with SET n = n + 1 at RC and see it is correct.
  3. Write skew. Create doctor(name text primary key, on_call bool) with two doctors on call. In both sessions at Repeatable Read, count on-call doctors, then each sets a different doctor off call and commits. Both succeed. Repeat at SERIALIZABLE; one commit fails with 40001.
  4. SKIP LOCKED. Insert 10 PENDING jobs. In session A, run the claim query with LIMIT 3 and do not commit. In session B, run it again and confirm it gets three different jobs without waiting.
  5. Indexes. Generate 2 million order_event rows with generate_series and random states. Run the Zomato query with EXPLAIN ANALYZE, add (created_at) INCLUDE (order_id, state, id), run it again, and compare Buffers and execution time. Write down why the plan changed.
