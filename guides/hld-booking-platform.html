Booking platform (BookMyShow / hotels / flights)

Design a system that sells each seat or hotel room-night to exactly one person. It must stay correct even when 50,000 people want the same seats at once.

Time-box: 45–60 min Seen: ~10 reports, 2024–26 Probes: selling one seat twice, payment and booking out of sync, safe retries
PhonePeExpediaSliceAgodaFanCodeWalmartBooking.comAmazon
In 30 seconds
  • Choose the smallest thing you can lock. That is one row per seat, or one row per room type per night.
  • Reserve a seat with one database update that only succeeds if the seat is still free. The database decides who wins.
  • Reserve, then pay, then confirm. Treat these as steps with timers and refunds, not one big operation.
  • Search can show slightly old data and is cached. Booking must be exact. Use a waiting room for huge rushes.
Picture it

Think of an IRCTC Tatkal counter at 10 a.m. A guard lets people in a few at a time. That is the waiting room. The clerk marks a berth "held" in the register the moment you ask. If your UPI payment does not arrive within 8 minutes, the berth goes back on the board for someone else.

Words you'll see
Hold
A short, timed reservation. The seat is yours for a few minutes while you pay.
Conditional UPDATE
A database update with a check built in, like "mark F7 held, but only if it is still free". It changes zero rows if someone got there first.
Idempotency key
A unique ID the app sends with a request. If the same request arrives twice, the server returns the first result instead of doing the work again. Pressing "Pay" twice charges you once.
PSP
Payment service provider. The payment gateway, like Razorpay, that talks to UPI and card networks.
Webhook
A message the PSP sends to our server to say "this payment succeeded" or "failed".
TTL
Time to live. How long something lasts before it expires on its own.
Outbox
A table where we save "events to send" in the same database transaction as the booking. A separate process later sends them to Kafka, so no event is lost.
Saga
A process made of steps where each step has an "undo" action, such as a refund, instead of one big transaction.

01What the interviewer is grading

Inventory you can lock

Store one row per seat per show, or one row per room type per night. If this is wrong, nothing else works.

A safe way to stop two winners

Pick one way to let only one person win. One option is an update that works only if the seat is still free (conditional update). Others are a row lock, a no-overlap rule (exclusion constraint), or a Redis hold. Say which store holds the truth.

Reserve, pay, confirm

Model this as a set of states with timers. Do not wrap one big database transaction around the payment call.

Matching payments to bookings

Give each request a unique ID so retries are safe (idempotency keys). Listen for the payment company's callbacks (webhooks), and also ask it directly. Refund automatically when a paid booking cannot be honoured.

Reads and writes behave differently

Search is AP. Booking is CP. Saying this without being asked shows seniority.

Huge rushes

For a blockbuster opening or a flash sale, use a virtual waiting room. It lets in only as many people as the system can serve.

Go deeper: what each company actually asked

The reports are very similar. PhonePe asked for hotel booking. The round focused on the data model: "how will we model booking for each day / room / hotel". Then it moved to payments, double payment and idempotency. Expedia asked for Airbnb. They asked what happens when two users book the same property for the same dates. They asked what happens when payment succeeds but booking creation fails, and the reverse. They asked which database and why, and how to stop fake reviews. Slice asked for BookMyShow and called it "the most grilling" round. It covered concurrent requests, double booking and race conditions. Agoda asked for flights and added CAP trade-offs and testing. Walmart asked for a flash sale with optimistic locking and inventory reservation. Amazon asked about the last unit with two orders at the same time. Booking.com asked how to sync hotel availability across Booking, Airbnb, Agoda and Expedia without overselling.

02Clarify and scope

AskWhy it matters
What exactly are we selling?A specific seat, a count of identical rooms, or a whole home for some dates. Each one needs a different kind of lock.
Do we own the inventory?Cinemas and airlines may keep the true record in their own systems (theatre POS, airline GDS). Then we hold seats through their API.
How long is a hold?5–10 minutes for seats. Hotel checkout can take longer.
Is overbooking allowed?Airlines oversell on purpose. Cinemas never do. Hotels may keep a few rooms spare.
How big is the busiest moment?The opening-day rush shapes the design, not the average day.
How does payment work?UPI and cards redirect the user away. So confirmation arrives later, by webhook.

Functional

  • Search by city, date, movie or location. See what is free and the price.
  • Pick seats or rooms and hold them for a short time.
  • Pay, get confirmation, and receive a ticket or voucher.
  • Cancel and get a refund as the policy allows.
  • Reviews only from guests who really stayed.

Non-functional

  • Never sell one seat twice. The booking path must be strongly consistent.
  • Search p99 under 300 ms. Hold p99 under 500 ms. (p99: 99 of 100 requests are faster.)
  • Opening-day rush: 1 million users in 10 minutes for one event.
  • 99.95% uptime. Under heavy load, booking makes people wait in a queue instead of crashing.

Out of scope

  • Dynamic pricing and recommendations.
  • Building the payment gateway itself.
  • Screens for onboarding partners.

Say the conclusion

The total traffic is small. A Postgres database split across a few servers (sharded) handles it. The hard part is thousands of people fighting over a few rows during a rush. So the fix is a waiting room plus safe single-row updates. "More servers" does not solve it.

04API design

  1. BrowseSearch shows or hotels, then load the seat map (cached for about 1 second).
  2. HoldAsk to keep the seat for a few minutes. Send a unique request ID, so a retry never holds twice. You get the expiry time (201), or "seat taken" (409). Call: POST /v1/holds with Idempotency-Key #1.
  3. BookTurn the hold into a booking. The server answers "accepted, waiting for payment" (HTTP 202, PAYMENT_PENDING) and sends a payment page link. Call: POST /v1/bookings with Idempotency-Key #2.
  4. PSPThe payment company calls our server to say the payment worked (a webhook). We check its signature to be sure it is genuine. We ignore repeats of the same payment ID. Endpoint: /internal/payments/webhook.

Postgres / MySQL for booking usual pick

  • Updates many rows all-or-nothing (ACID). Has row locks and conditional updates.
  • Supports unique and exclusion constraints
  • Must be split by inventory owner (theatre, hotel)

Use it for inventory, bookings and payments. One booking never spans two servers.

Cassandra / DynamoDB

  • Handles huge write volumes
  • Hard to update several nights or seats all-or-nothing

A poor fit for the booking core. Use Elasticsearch for search, fed by CDC (a stream of every database change). Use Redis for caches and the waiting room.

Figure: the read side (search, seat map) is cached and may be a little out of date. The write side (hold, booking, payment) goes to the split relational database. Follow-up work like tickets flows through Kafka using an outbox.

Waiting room

One per event. You get a signed pass that shows your place in the queue. The gate lets in only as many per second as the hold service can handle. This is fairer than random errors.

Inventory / hold service

The only code allowed to change inventory. Every change is one update that works only if the seat is still in the expected state (a conditional update).

Booking service

Owns the booking status and talks to payments. In one database step, it saves the new status and an event to send later (an outbox row).

Payment service

Creates a payment order with the payment company (PSP), tagged with the booking ID. Receives its callbacks (webhooks). Matches our records against the PSP's reports.

Sweeper

Frees expired holds every few seconds. Reads also treat a hold whose time is up as free (held_until < now()). So a slow sweeper never blocks a sale.

Partner adapters

Connect to partners' own systems: cinema ticket counters (POS), airline booking networks (GDS) and hotel channel managers. When we hold a seat, we also hold it in the partner's system.

8.1 Stopping double booking: pick the right tool for each kind of inventory

TimeUser AUser BSeat F7
t1UPDATE … WHERE status='AVAILABLE' (takes row lock)AVAILABLE

For seats and simple counts, use a conditional UPDATE. For hotel nights, lock the night rows with FOR UPDATE, always in date order. For date ranges, use an exclusion constraint. They are compared in Trade-offs.

Show seat-hold SQL
UPDATE show_seat
   SET status = 'HELD', hold_id = :holdId, held_until = now() + interval '8 minutes'
 WHERE show_id = :showId
   AND seat_id = ANY(:seatIds)
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < now()));
-- if updated row count != seatIds.length then ROLLBACK and return 409

Postgres conditional update as the true record usual pick

  • Survives crashes and is transactional
  • Every loser still costs one database call

Always the final safety check.

Redis lock only

  • Very fast, turns away losers early
  • Can expire during a long garbage-collection (GC) pause. Can be lost when Redis fails over to a copy.

Only as a first filter, never alone.

Go deeper: why each tool works

Specific seats. Run one conditional update over all the requested seats. It succeeds only if every row matched. You need no separate lock, and there is no gap between "read" and "write". The WHERE clause is the check. The row lock that UPDATE takes makes competitors go one at a time. The loser waits briefly on the row. Then it re-checks the condition, matches nothing, and gets a 409.

Identical rooms over several nights. Lock the night rows in a fixed order, then reduce the count. A fixed order avoids deadlocks between two overlapping stays. Why one row per day, and not a list of bookings with overlap queries? Checking one night is a single row read. The lock covers only the nights you touch. Showing partial availability, like "3 of 4 nights", is easy. A nightly job creates the rows one year ahead.

A whole home over a date range. Two inserts for overlapping dates arrive together. One commits. The other fails with an exclusion error, which you turn into a 409. No lock in your application code can be more correct than this.

Stock that is just a count. Use the optimistic approach: UPDATE inventory SET available = available - 1, version = version + 1 WHERE sku = ? AND available > 0, then check the row count. If two orders race for the last unit, exactly one update matches. Under extreme load, put a Redis DECR gate in front. It rejects instantly once the count goes below zero, and adds back on failure. So only about as many requests as there are units reach the database. Each one creates a reservation row with a TTL that the order must confirm.

Distributed locks: when to mention them. A Redis lock (SET seat:s42:F7 holdId NX PX 480000) is a good fast filter for seat holds. Many write-ups suggest it. But it must never be the only guard. A lock can expire during a GC pause. It can also be lost when Redis fails over. Keep the Postgres conditional update as the true record. Treat Redis as a speed-up that turns away losers early.

8.2 Hold, pay, confirm: the booking states

INITIATED→ HELDseat kept for a few minutes→ PAYMENT_PENDING→ CONFIRMED
PAYMENT_PENDING→timeout / failure EXPIRED / FAILEDseat freed· PAID_BUT_EXPIRED→ REFUND_PENDING → REFUNDED

Figure: booking states. Each move happens only if the booking is still in the expected state. That is a conditional update on (booking_id, status, version). So a repeated webhook or two racing workers cannot apply the same move twice.

  • Never keep a database transaction open while calling the payment gateway. The hold is a saved record with an expiry time.
  • Make the hold last longer than the PSP's payment window, plus some margin. Then a slow UPI approval does not lose the seat.
  • The webhook confirms the payment. We check it is genuine and ignore repeats of the same payment ID (psp_payment_id). A background job also asks the PSP about orders stuck waiting for payment (PAYMENT_PENDING).

8.3 Payment succeeds but booking fails (and the reverse)

Paid, but hold expired

Retry the confirm. If that fails, grab a similar unit. If that fails too, mark it for refund (REFUND_PENDING) and refund automatically, using the booking ID so it happens once. This is an "undo" step in a saga.

Booked, but payment failed

The booking becomes FAILED, and the seats are freed in the same transaction. The user may pay again on the same booking while the hold lasts.

Double payment

Three layers stop it. Each request has a unique ID (idempotency key). Each booking has one payment order. Each payment ID can be stored only once (unique psp_payment_id). The daily matching job (reconciliation) refunds any real double charge.

Reconciliation job

Every day and every hour, match the PSP's settlement reports to our tables. Every mismatch becomes a ticket or an automatic fix.

Go deeper: the full mismatch playbook
  • Paid, but the hold expired or confirm failed. First retry the confirm. It is safe to repeat. If the seat or room is really gone, try to grab a similar one (same room type) if the policy allows. Otherwise move to REFUND_PENDING. Issue an automatic refund that uses the booking ID as its idempotency key. Tell the user right away. This is an "undo" step in a saga, and interviewers want to hear that name.
  • Booking created, payment failed. The booking moves to FAILED. The same transaction frees the inventory. The user can try paying again within the hold time. That makes a new payment attempt on the same booking.
  • Double payment. Three layers prevent it. First, the app's idempotency key on POST /bookings. Second, one PSP order per booking, so the PSP rejects a second charge on the same order. Third, a unique psp_payment_id in our table. A second payment can still land if the user paid through two UPI apps. Reconciliation then finds two charges for one booking and refunds one.
  • Reconciliation job. Every day, and every hour for fresh data, match PSP settlement reports against our payment and booking tables. Every mismatch becomes a ticket or an automatic fix. Airbnb's Orpheus write-up describes this approach. It splits payment flows into small steps that are safe to retry. Over time our records and the gateway's records agree (eventual consistency).

Go deeper: rushes and syncing many booking sites

Opening-day rush (FanCode's "global BookMyShow"). Turn on the waiting room for that event. Serve the seat map from Redis, refreshed every second. Slightly old data is fine because the hold is the real check. Split data by show so one blockbuster cannot slow other shows. Add hold-service capacity before the rush. Cap seats per user. For global scale, keep each event's inventory in its venue's region and send bookings there.

Booking.com's question: one hotel is listed on Booking, Airbnb, Agoda and Expedia. These sites are called OTAs (online travel agencies). The hotel's stock needs one true record. That is a channel manager or the hotel's property management system (PMS).

  • Each OTA sends its booking to the channel manager. It reduces the shared count in one safe step, using the per-day rows above. Then it pushes the new availability to every other OTA.
  • Pushes arrive later, not instantly. So for a moment two OTAs may both think the last room is free. Close that gap in one of three ways. (a) The OTA checks live with the channel manager before confirming, if it supports this. (b) Keep a small buffer, and stop selling the last room on less important sites. (c) Give each site a fixed share (Booking gets 5 rooms, Expedia 3), at the cost of more empty rooms.
  • Updates are safe to repeat and carry a version. Each push has a sequence number per hotel, room type and date. OTAs ignore older versions. So retries and out-of-order messages are safe.
  • If an oversell still happens, follow a set plan. Move the guest to a similar hotel at the platform's cost. Interviewers like hearing that the business process is part of the design.

09Scaling, failure handling and consistency

Search and seat map: AP

  • Cached and fast. Reading from database copies is fine.
  • Can be a second out of date

Browsing traffic.

Hold and booking: CP usual pick

  • Never sells a seat twice
  • Refuses to book if the network splits

Every write to inventory. Payments are matched up later.

What breaks at 10x

First, fights over hot show rows. Fix with the waiting room and splitting by show. Next, PSP rate limits. Fix by routing across several PSPs.

A busy server is OK

One show lives on one database server by design. It has only a few hundred seats, and the waiting room limits the rate.

Outbox

The event is saved in the same database step as the booking. So a confirmed booking always produces a ticket, even if Kafka is down for a moment.

Many holds expiring at once

When reading, treat a hold as free once its time is up (held_until has passed). The waiting room lets in the next group.

Go deeper: replicas, multi-region, fake reviews, testing
  • CAP, said plainly (Agoda). Search and the seat map are AP. They are cached and can be a second out of date. Hold and booking are CP. If the network splits, we refuse to book rather than risk selling a seat twice. Payments are matched up later.
  • What breaks first at 10x. First, fights over rows of hot shows. Then the PSP's rate limits. The waiting room and splitting by show fix the first. Several PSPs with routing fix the second.
  • Hot shard. One show lives on one database server (shard) by design. This keeps each transaction on one server. That is fine because one show has at most a few hundred seats. The waiting room limits the rate.
  • Read replicas (read-only copies of the database) serve booking history and seat maps. Never use them for hold decisions.
  • Outbox for booking events like ticket creation, email and analytics. A confirmed booking always produces a ticket, even if Kafka is down for a moment.
  • Many holds expiring at once. When thousands of holds expire together, the seat map shows those seats free again. The waiting room lets in the next group. Checking held_until at read time means the sweeper never becomes a bottleneck.
  • Multi-region. Split inventory by venue region, so each event has a home region. Users anywhere are sent there for writes. Search indexes are copied to every region.
  • Fake reviews (Expedia). Only bookings in CHECKED_OUT state can leave a review (unique booking_id on review). Rate-limit per account and device. Flag bursts from new accounts, shared IPs or the same payment card. Flag reviews with very similar text. Hold suspicious ones for a moderator. Give more weight to reviewers with a good history.
  • Testing (Agoda asked). Concurrency tests fire 100 holds at one seat at once and check that exactly one succeeds. Use Testcontainers Postgres to test the exclusion constraint. Run contract tests against the PSP sandbox. Run chaos tests that kill the booking service between payment and confirm. Run load tests that replay opening-day traffic.

10Trade-offs

Conditional UPDATE usual pick

  • One update that succeeds only if the seat is still free. Simple and correct, with no locks to manage.
  • Losers retry when many people compete

Default for specific seats (BookMyShow, flights) and for stock counts (flash sale, last unit).

SELECT ... FOR UPDATE

  • Locks the rows you read until you finish. Clear rules across many rows.
  • Others wait for the lock. Two bookings can block each other forever (deadlock) if they lock rows in different orders.

Multi-night hotel stays (PhonePe per-day model). Lock in date order.

Exclusion constraint

  • The database itself guarantees no overlap
  • Postgres only. Needs a special range index (GiST), which costs space and write time.

Date-range bookings of a single home (Airbnb, Expedia).

Redis lock / Lua hold

  • A quick claim kept in memory, often by a small Lua script. Very fast, and takes load off the database.
  • Can be lost if Redis crashes. Locks can expire at the wrong time.

First filter for flash sales and hot shows.

Version column (OCC)

  • Optimistic concurrency control: reads never wait
  • Many updates fail and retry on busy rows

Rows that few people change at once, like booking status.

11Mistakes that got candidates rejected

Rejected for this
  • "Check if the seat is free, then insert the booking", with nothing making the two steps happen as one.
  • Keeping a database transaction (or a synchronized block) open during the payment gateway call.
  • Modelling hotel bookings without one unit per night, then being stuck on overlapping stays.
  • Trusting only a Redis lock for correctness.
  • No answer to "payment succeeded, booking failed" beyond "we will retry".
  • Making search as strict as booking, or making booking as loose as search.
  • Ignoring the rush: no waiting room or entry limit for a blockbuster opening.

13Quick check

Two users try to hold seat F7 in the same millisecond, using the conditional UPDATE. What happens?

The UPDATE locks the row. The second update waits, then re-checks its condition against the saved row. It sees HELD with an expiry in the future, so it matches nothing.

How should you store hotel availability for a 3-night stay?

With one row per night, checking a night is a single row read, and the lock stays small. Locking in a fixed date order stops deadlocks between overlapping stays.

Why not rely only on a Redis lock for seat holds?

Redis is a fast filter that turns away losers. The Postgres conditional update stays the true record.

Payment succeeded, but the hold expired and the seat was sold to someone else. What should happen?

This is a saga "undo" step: PAID_BUT_EXPIRED, then REFUND_PENDING, then REFUNDED. The refund uses an idempotency key, so retries never refund twice.

Average booking traffic is only about 17 per second. Why do we still need a waiting room?

The problem is not average traffic. It is many people fighting over a few rows during a rush.

14Interview questions

Two users click the same seat at the same millisecond. Walk me through it.

Both send POST /holds. Both run the conditional UPDATE. Postgres gives the row lock to the first one. The second waits. Then it re-checks the WHERE clause against the saved row. It finds the seat HELD with an expiry in the future. It changes zero rows, rolls back, and returns 409. The first user sees an 8-minute timer. No lock in application code is needed.

How do you model hotel availability? Per booking or per day?

Per room type per night: (hotel_id, room_type_id, stay_date, total, reserved). A stay locks only its own nights. It locks them in date order to avoid deadlocks. On each night it checks total - reserved >= rooms. An availability query reads N small rows. The actual room number is assigned at check-in, not at booking.

Payment succeeded but the booking failed. What does the user see?

The booking moves to PAID_BUT_EXPIRED. We retry the confirm. If the inventory is gone, we try a similar unit. Otherwise we refund automatically. The refund is keyed on the booking ID, so it is safe to retry. We tell the user within seconds. Reconciliation catches anything the live flow missed.

How do you stop a user from being charged twice?

Four things. An idempotency key on the booking request. One PSP order per booking, so the PSP refuses a second charge. A unique PSP payment ID in our table, so repeated webhooks do nothing. And reconciliation, which refunds any real double charge.

Which database and why?

Postgres for inventory, bookings and payments. It gives transactions across several rows, conditional updates, and unique and exclusion constraints. Shard it (split it) by venue or hotel, so one booking stays on one server. Use Elasticsearch for search, Redis for caches and the waiting room, and Kafka for events.

Why not hold a distributed lock in Redis and skip the DB check?

Locks can expire during GC pauses or network stalls. Redis also copies data to its replicas asynchronously, so a failover can lose a lock. Then two people both believe they hold the seat. The database conditional update is what guarantees correctness. Redis is a speed-up that rejects most losers before they reach the database.

Flash sale of 1,000 units with 1M buyers. Design the hot path.

Start with a waiting room. Then use a Redis DECR gate on the stock count, so only about 1,000 requests get through. Each one creates a reservation row with a 10-minute TTL, using an optimistic decrement in the database. Payment confirms the reservation. If it expires, the unit goes back to both Redis and the database. Everyone else gets "sold out" from Redis in a millisecond.

How do you avoid overselling a hotel listed on four OTAs?

Keep one true record of inventory, in a channel manager or PMS. Every OTA booking reduces it in one atomic step. That triggers versioned availability updates to the other OTAs. Use live availability checks where OTAs support them. Keep a buffer, or a fixed share per site, for the last rooms. Have a plan to move the guest for the rare oversell.

15Cheat sheet

Cheat sheet
  • Unit: a show_seat row, a room_inventory row per night, or a daterange with an exclusion constraint.
  • Hold is one conditional UPDATE. If fewer rows changed than seats asked, return 409.
  • Hotel nights: FOR UPDATE in date order, then check total - reserved.
  • States: HELD, then PAYMENT_PENDING, then CONFIRMED. PAID_BUT_EXPIRED leads to a refund.
  • Two idempotency keys. Booking ID is the PSP order reference. psp_payment_id is unique.
  • Webhook, plus a poller, plus daily reconciliation.
  • Search is AP and cached. Booking is CP on sharded Postgres.
  • Waiting room and a Redis DECR gate for rushes. Redis is never the only guard.
  • Outbox to Kafka for tickets and notifications.
