Booking platform (BookMyShow / hotels / flights)

Design a system that sells scarce, time-bound inventory: cinema seats, hotel room-nights, flight seats, flash-sale units. Every variant is graded on the same thing: one unit sold to exactly one person under heavy contention, and a clean answer for what happens when payment and booking disagree.

01What the interviewer is grading

The reports are unusually consistent. PhonePe (hotel booking) spent the round on the data model, "how will we model booking for each day / room / hotel", then payments: double payment and idempotency. Expedia (Airbnb) asked what happens when two users book the same property for the same dates, when payment succeeds but booking creation fails, the reverse, which database and why, and how to stop fake reviews. Slice (BookMyShow) called its round "the most grilling": concurrent requests, double booking, race conditions. Agoda (flights) added CAP trade-offs and testing. Walmart asked a flash sale with optimistic locking and inventory reservation; Amazon asked about the last unit with two concurrent orders; Booking.com asked to sync hotel availability across Booking, Airbnb, Agoda and Expedia without overselling.

  • An inventory model you can lock. Per seat per show, or per room type per night. Get this wrong and nothing else works.
  • A correct concurrency primitive with the reason: conditional update, row lock, exclusion constraint, Redis hold. And where the source of truth lives.
  • Hold → pay → confirm as a state machine with timeouts, not one big transaction around a payment call.
  • Payment reconciliation. Idempotency keys, webhooks plus polling, auto-refund when you cannot honour a paid booking.
  • Read/write split. Search and browse are AP and cached; booking is CP. Saying this unprompted is a senior signal.
  • Hot events. A blockbuster opening or flash sale: virtual waiting room, admission control.

02Clarify and scope

Questions to ask

  • What is the unit of inventory? A specific seat (cinema, flight with seat selection), a count of interchangeable units (hotel room type, flash-sale SKU), or a whole listing over a date range (Airbnb). The concurrency design follows from this.
  • Do we own the inventory? Cinemas and airlines may hold the truth in their own systems (GDS, theatre POS); then we hold against their API. Hotels may list on several OTAs at once (the Booking.com question).
  • Hold duration? Typical 5–10 minutes for seats; hotel checkout can be longer.
  • Is overbooking ever allowed? Airlines oversell on purpose; cinemas never do. Hotels sometimes keep a buffer.
  • Scale and peaks? Steady state is easy; the design is driven by the opening-day spike.
  • Payment flow? Redirect to a gateway (UPI, cards) means asynchronous confirmation by webhook.

Functional

  • Search by city, date, movie or location; see availability and price.
  • Select seats or rooms; temporary hold.
  • Pay; confirm; ticket or voucher issued.
  • Cancel and refund per policy.
  • Reviews from verified guests.

Non-functional

  • Zero double booking (strong consistency on the booking path).
  • Search p99 < 300 ms; hold p99 < 500 ms.
  • Opening-day spike: 1M users in 10 minutes for one event.
  • 99.95% availability; booking path degrades gracefully (queue, not crash).

Out of scope

  • Dynamic pricing models, recommendations.
  • Building the payment gateway itself.
  • Partner onboarding UI.

Say the conclusion: total throughput is modest and fits a sharded Postgres; the hard part is contention on a tiny set of rows during a spike. That is why the solution is admission control plus row-level atomic operations, not "more servers".

04API design

GET  /v1/shows?city=BLR&movieId=m1&date=2026-10-10
GET  /v1/shows/{showId}/seats                 -> seat map with AVAILABLE | HELD | BOOKED (cached ~1 s)
GET  /v1/hotels/search?lat=..&lng=..&checkIn=..&checkOut=..&guests=2

POST /v1/holds
Idempotency-Key: 4f1c...                     // client-generated per checkout attempt
{ "showId": "s_42", "seatIds": ["F7","F8"] }
  or { "hotelId": "h_9", "roomTypeId": "DLX", "checkIn": "2026-10-10", "checkOut": "2026-10-13", "rooms": 1 }
-> 201 { "holdId": "hld_01J..", "expiresAt": "...+8m", "amount": 840000, "currency": "INR" }
-> 409 { "error": "SEATS_UNAVAILABLE", "seats": ["F8"] }

POST /v1/bookings
Idempotency-Key: 9a7e...                     // same key on retry returns the same booking
{ "holdId": "hld_01J..", "paymentMethod": "UPI" }
-> 202 { "bookingId": "bk_..", "status": "PAYMENT_PENDING", "paymentRedirect": "..." }

POST /internal/payments/webhook             // from PSP, signature verified, deduped by paymentId
GET  /v1/bookings/{bookingId}                -> CONFIRMED | PAYMENT_PENDING | FAILED | REFUNDED
POST /v1/bookings/{bookingId}/cancel
POST /v1/reviews   { "bookingId": "...", "rating": 4, "text": "..." }   // only after checkout

Two idempotency keys, because there are two different user actions: one for creating the hold, one for paying. The booking ID is also passed to the payment gateway as the merchant order reference, so the gateway itself refuses a second charge for the same order. That is the core answer to PhonePe's "double payment".

05Data model

TableKey fieldsNotes
showshow_id, screen_id, movie_id, starts_at, statusShard by show_id (or theatre_id)
show_seat(show_id, seat_id) PK, status, hold_id, held_until, booking_id, price_tier, versionOne row per seat per show: the lockable unit for cinemas and flights

holdhold_id, user_id, resource refs, expires_at, status, idempotency_key UNIQUETTL sweeper releases expired holds

paymentpayment_id, booking_id, psp_order_id UNIQUE, psp_payment_id UNIQUE, status, amountUnique PSP IDs make webhook processing idempotent
reviewreview_id, booking_id UNIQUE, listing_id, rating, text, created_atOne review per completed booking

Why Postgres (or MySQL) for the booking path: you need multi-row ACID transactions, row locks, unique and exclusion constraints, and conditional updates. Shard by the inventory owner (theatre, hotel) so a booking never spans shards. Elasticsearch for search (geo, filters, text), fed by CDC. Redis for seat-map caching, waiting-room tokens and optionally fast holds. Cassandra or DynamoDB is a poor fit for the booking core: conditional writes exist, but multi-row atomic updates across nights or seats do not come naturally.

06High-level architecture

App / web→ CDNposters, static→ API gatewayJWT, rate limit→ Waiting roomonly for hot events
Search service→ ElasticsearchCDC-fed· Seat-map service→ Redisseat-map cache
Inventory / hold service→ Postgres shardsshow_seat, room_inventory← Hold expiry sweeper
Booking servicestate machine→ Payment service→ PSPUPI / cards→webhook Booking service→ Kafkabooking events→ Tickets, notifications, analytics

Figure: read path (search, seat map) is cached and eventually consistent; write path (hold, booking, payment) goes to the sharded relational store; side effects flow through Kafka via an outbox.

  • Waiting room. Enabled per event. Users get a signed token with a queue position; the gate admits N per second matched to what the hold service can absorb. Protects the database from a thundering herd and is fairer than random 500s.
  • Inventory / hold service. Owns seat and room inventory and the only code allowed to change it. Every change is an atomic conditional update.
  • Booking service. Owns the booking state machine and talks to payments. Writes booking state and an outbox row in one transaction.
  • Payment service. Creates PSP orders with the booking ID as reference, handles webhooks, runs reconciliation against PSP reports.
  • Sweeper. Releases expired holds (status flip) every few seconds; holds are also treated as expired at read time via held_until < now(), so the sweeper being late never blocks a sale.
  • Partner integration (cinemas with their own POS, airlines via GDS, hotels via channel managers): an adapter layer that places a hold on the partner system as part of our hold step.

07Deep dives

7.1 Preventing double booking: pick the primitive per inventory type

Specific seats (BookMyShow, flight seat selection). One atomic conditional update over the requested seats; succeed only if every row matched.

UPDATE show_seat
   SET status = 'HELD', hold_id = :holdId, held_until = now() + interval '8 minutes'
 WHERE show_id = :showId
   AND seat_id = ANY(:seatIds)
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND held_until < now()));
-- if updated row count != seatIds.length then ROLLBACK and return 409

No explicit lock, no read-then-write gap: the WHERE is the check and the row lock taken by UPDATE serialises competitors. The loser blocks briefly on the row, re-evaluates the predicate, matches nothing, and gets 409.

Interchangeable units over nights (hotel room types, PhonePe's per-day model). Lock the night rows in a fixed order to avoid deadlocks between overlapping stays, then decrement.

BEGIN;
SELECT stay_date, total, reserved FROM room_inventory
 WHERE hotel_id = :h AND room_type_id = :rt AND stay_date >= :in AND stay_date < :out
 ORDER BY stay_date
 FOR UPDATE;
-- in Java: every night must have total - reserved >= :rooms, and row count == nights
UPDATE room_inventory SET reserved = reserved + :rooms, version = version + 1
 WHERE hotel_id = :h AND room_type_id = :rt AND stay_date >= :in AND stay_date < :out;
INSERT INTO hold (...) VALUES (...);
COMMIT;

Why per-day rows rather than a list of bookings with overlap queries: availability for a night is one row read, the lock is narrow (only the nights you touch), and partial availability ("3 of 4 nights") is easy to show. Seed the rows a year ahead with a nightly job.

Whole listing over a date range (Airbnb, Expedia's question). Let the database enforce it:

CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE reservation (
  id         bigint PRIMARY KEY,
  listing_id bigint    NOT NULL,
  stay       daterange NOT NULL,           -- [check_in, check_out)
  status     text      NOT NULL,
  EXCLUDE USING gist (listing_id WITH =, stay WITH &&)
    WHERE (status IN ('HELD', 'CONFIRMED'))
);

Two concurrent inserts for overlapping dates: one commits, the other fails with an exclusion violation, which you map to 409. No application lock can be more correct than this.

Count-only stock (Walmart flash sale, Amazon's last unit). Optimistic: UPDATE inventory SET available = available - 1, version = version + 1 WHERE sku = ? AND available > 0 and check the row count. With two concurrent orders for the last unit, exactly one update matches. Under extreme contention, put a Redis DECR gate in front (reject immediately when it goes negative, add back on failure) so only roughly as many requests as there are units reach the database, and create a reservation row with a TTL that the order must confirm.

Distributed locks: when to mention them

A Redis lock (SET seat:s42:F7 holdId NX PX 480000) is a fine fast-path filter for seat holds and is what many write-ups propose. It must not be the only guard: a lock can expire during a GC pause or be lost on Redis failover. Keep the conditional update in Postgres as the source of truth, and treat Redis as an optimisation that sheds losers early.

7.2 Hold, pay, confirm: the state machine

INITIATED→ HELDinventory reserved, TTL→ PAYMENT_PENDING→ CONFIRMED
PAYMENT_PENDING→timeout / failure EXPIRED / FAILEDrelease inventory· PAID_BUT_EXPIRED→ REFUND_PENDING → REFUNDED

Figure: booking states. Each transition is a conditional update on (booking_id, status, version), so duplicate webhooks or racing workers cannot apply it twice.

  • Never hold a database transaction open across the payment call. Holds are committed state with an expiry; the payment happens between transactions.
  • Extend the hold when the user is redirected to the PSP (hold TTL greater than the PSP's payment window plus a margin), so a slow UPI approval does not lose the seat.
  • Confirmation is triggered by the PSP webhook, verified by signature, deduped by psp_payment_id. If the webhook never arrives, a poller queries the PSP for orders stuck in PAYMENT_PENDING after a few minutes.

7.3 Payment succeeds but booking fails (and the reverse)

  • Paid, but hold expired or confirm failed. Retry confirm first (idempotent). If the inventory is genuinely gone, try to re-acquire equivalent inventory (same room type) if policy allows; otherwise move to REFUND_PENDING and issue an automatic refund with the booking ID as the refund idempotency key. Tell the user immediately. This is a compensating action in a saga, which is what interviewers want named.
  • Booking created, payment failed. Booking moves to FAILED, inventory released by the same transaction. Let the user retry payment within the hold window with a new payment attempt on the same booking.
  • Double payment. Prevented at three layers: client idempotency key on POST /bookings; one PSP order per booking (the PSP rejects a second capture on the same order); unique psp_payment_id in our table. If a second payment still lands (user paid via two UPI apps), reconciliation detects two captures for one booking and refunds one.
  • Reconciliation job. Daily (and hourly for fresh data) match PSP settlement reports against our payment and booking tables. Every mismatch becomes a ticket or an automated fix. Airbnb's Orpheus write-up describes this approach of breaking payment flows into idempotent, retryable steps and reaching eventual consistency with the gateway.

7.4 Hot events and syncing inventory across channels

Opening-day spike (FanCode's "global BookMyShow"). Turn on the waiting room for that event; serve the seat map from Redis refreshed every second (staleness is fine because the hold is the real check); shard by show so one blockbuster cannot starve other shows; pre-scale the hold service; cap seats per user; for global scale, keep each event's inventory in the region of its venue and route bookings there.

Booking.com's question: one hotel listed on Booking, Airbnb, Agoda and Expedia. There must be one source of truth for the hotel's inventory: a channel manager or the property management system (PMS).

  • Each OTA booking is sent to the channel manager, which decrements the shared pool atomically (the per-day row model above) and pushes the new availability to every other OTA.
  • Pushes are asynchronous, so a window exists where two OTAs both think the last room is free. Close it with (a) a real-time availability check from the OTA to the channel manager before confirming, where the OTA supports it, or (b) keep a small buffer and stop selling the last room on lower-priority channels, or (c) allocations per channel (Booking gets 5 rooms, Expedia 3) at the cost of utilisation.
  • Updates are idempotent and versioned (each push carries a sequence number per hotel, room type and date; OTAs ignore older versions), so retries and reordering are safe.
  • If an oversell still happens, a defined playbook: relocate the guest to a comparable hotel at the platform's cost. Interviewers like hearing that the business process is part of the design.

08Scaling, failure handling and consistency

  • CAP, said plainly (Agoda). Search and seat-map are AP: cached, can be a second stale. Hold and booking are CP: during a partition we refuse to book rather than risk selling a seat twice. Payments are reconciled eventually.
  • What breaks first at 10x: row contention on hot shows, then the PSP's rate limits. Waiting room and per-show sharding address the first; multiple PSPs with routing address the second.
  • Hot shard. A single show lives on one shard by design (keeps the transaction local). That is acceptable because one show has at most a few hundred seats; the waiting room bounds the rate.
  • Read replicas for booking history and seat maps; never for hold decisions.
  • Outbox for booking events (ticket generation, email, analytics), so a confirmed booking always produces a ticket even if Kafka is briefly down.
  • Expired-hold storms. When thousands of holds expire at once, the seat map flips back to available; the waiting room admits the next batch. Releasing via held_until at read time avoids a sweeper bottleneck.
  • Multi-region. Partition inventory by venue region (each event has a home region); users anywhere are routed there for writes. Search indices are replicated globally.
  • Fake reviews (Expedia). Only bookings in CHECKED_OUT state can review (unique booking_id on review); rate-limit per account and device; flag bursts from new accounts, shared IPs or payment instruments, text similarity across reviews; hold suspicious ones for moderation; weight by reviewer history.
  • Testing (Agoda asked). Concurrency tests that fire 100 parallel holds at one seat and assert one success; Testcontainers Postgres for the exclusion constraint; contract tests with the PSP sandbox; chaos tests killing the booking service between payment and confirm; load tests replaying an opening-day traffic shape.

10Follow-up questions interviewers asked

Two users click the same seat at the same millisecond. Walk me through it.

Both send POST /holds. Both run the conditional UPDATE. Postgres row-locks the seat for the first; the second waits, then re-checks the WHERE clause against the committed row, finds it HELD with a future expiry, updates zero rows, rolls back and returns 409. The first user sees an 8-minute timer. No application lock needed.

How do you model hotel availability? Per booking or per day?

Per room type per night: (hotel_id, room_type_id, stay_date, total, reserved). A stay locks only its nights, in date order to avoid deadlocks, and checks total - reserved >= rooms on each. Availability queries read N small rows. Individual room numbers are assigned at check-in, not at booking.

Payment succeeded but the booking failed. What does the user see?

The booking moves to PAID_BUT_EXPIRED. We retry confirm; if inventory is gone, we try an equivalent unit, otherwise auto-refund with an idempotent refund keyed on the booking ID and notify the user within seconds. Reconciliation catches anything the online path missed.

How do you stop a user from being charged twice?

Idempotency key on the booking request; one PSP order per booking so the PSP refuses a second capture; unique PSP payment ID in our table so duplicate webhooks are no-ops; reconciliation refunds any genuine double capture.

Which database and why?

Postgres for inventory, bookings and payments: transactions across several rows, conditional updates, unique and exclusion constraints. Sharded by venue or hotel so a booking stays on one shard. Elasticsearch for search, Redis for caches and the waiting room, Kafka for events.

Why not hold a distributed lock in Redis and skip the DB check?

Locks expire during GC pauses or network stalls, and Redis replication is async, so a failover can lose a lock. Then two holders write. The DB conditional update is the correctness guarantee; Redis is an optimisation that rejects most losers before they reach the DB.

Flash sale of 1,000 units with 1M buyers. Design the hot path.

Waiting room, then a Redis DECR gate on stock so only about 1,000 requests pass; each creates a reservation row with a 10-minute TTL via an optimistic decrement in the DB; payment confirms it; expiry returns the unit to both Redis and DB. Everyone else gets "sold out" from Redis in a millisecond.

How do you avoid overselling a hotel listed on four OTAs?

Single inventory source (channel manager or PMS); every OTA booking decrements it atomically and triggers versioned availability pushes to the others; real-time availability checks where OTAs support them; a buffer or per-channel allocation for the last rooms; and a relocation playbook for the rare oversell.

11Mistakes that got candidates rejected

Rejected for this
  • "Check if the seat is available, then insert the booking" with nothing making the two steps atomic.
  • A database transaction (or a synchronized block) held open across the payment gateway call.
  • Modelling hotel bookings without a per-night unit, then being unable to answer overlapping stays.
  • Relying only on a Redis lock for correctness.
  • No answer to "payment succeeded, booking failed" beyond "we will retry".
  • Treating search with the same consistency as booking, or the reverse.
  • Ignoring the spike: no waiting room or admission control for a blockbuster opening.
