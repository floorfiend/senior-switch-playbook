Evals for LLM apps

You changed a prompt. Did the contract Q&A bot get better or worse? Evals (evaluations) answer that with numbers instead of gut feeling. This lesson shows you how to build them.

Time: 4–6 hours Stack: Python 3.11+, anthropic SDK, Ragas 0.4 Capstone milestone: week 7
TekionEPAMAdobeGoogle
In 30 seconds
  • Evals are your test suite for AI answers. AI answers vary each time, so you check the pass rate over many questions.
  • Keep a "golden set" of test questions with known answers in git. Score the search step and the answer step separately.
  • Let a second AI grade each answer PASS or FAIL. First check its grades against a human expert's grades.
  • Block a release in CI if a score drops below a minimum or falls from last time. Turn real user failures into new test questions.
Picture it

Think of a board exam. The answer key is the golden set. The examiner is the AI judge that grades each answer. The moderator re-checks some answer sheets to make sure the examiner grades fairly. Results come out only if the pass rate clears the bar.

Words you'll see

01Key ideas

Evals are tests

The golden set is your test data. The AI judge is a check a human must verify. The CI gate is a failing build. Answers vary, so check pass rates, not exact text.

Search sets the limit

If the right chunk never reaches the model, no prompt can save the answer. Score search and answering separately, so you know which half broke.

Yes/no judges

PASS or FAIL with a one-sentence reason. Use one judge per kind of failure. Results repeat well, humans can label them easily, and they give a pass rate.

Trust, then verify

A judge can be wrong. Compare it to 100 expert grades. Report kappa and TNR (explained below) before you rely on it.

Close the loop

Every real bug and thumbs-down becomes a golden case. Reading 50 traces (full records of real requests) beats any clever metric.

Interview reality

Tekion asked "design an eval pipeline for a RAG system". EPAM and Adobe asked how you measure RAG quality. Google asked how to evaluate agents over golden sets. Saying "we use Ragas" (a popular eval library) is not enough. Interviewers grade your test data, why you trust the judge, and how you block bad releases.

Go deeper: outcomes and the original framing
  • Build a golden dataset for a RAG system and keep it in version control. Include questions it must refuse, and trick questions.
  • Compute recall@k, precision@k, MRR and nDCG by hand and in code. Say which one blocks a release, and why.
  • Measure faithfulness (groundedness), answer relevance and citation accuracy, with Ragas and with your own judge.
  • Write a yes/no AI judge. Check it against human grades (agreement, Cohen's kappa, TPR and TNR). Protect it from position and length bias.
  • Run evals in CI on every prompt or search change. Fail the build when a score is too low or drops. Each run costs a few dollars.
  • Use live metrics and user feedback to create new golden cases.

You already know the shape. A golden dataset is your set of test fixtures. Search metrics are unit tests for the repository layer. An AI judge is an assertion that a human must check, because it can be wrong. The CI gate is a failing JUnit build. Live metrics are your SLO dashboards (your promised service levels). The difference is that AI output changes from run to run, and "correct" is fuzzy. So you check rates over many cases, not single strings.

Quote Hamel Husain's framing. There are three levels of evaluation, from cheapest to most costly.

LevelWhatCostWhen it runs
1. AssertionsPlain code checks with fixed results. The JSON parses. Every answer cites a page. Off-topic questions are refused. No personal data (PII) leaks. Search recall@k.Near zeroEvery commit
2. Human and model evalAn AI judge grades groundedness and correctness, checked against human grades. People read traces.Dollars per run, plus hours of human time per monthEvery prompt, model or search change. Trace reading weekly.
3. A/B testingTwo versions shown to real users, compared on what users doHighestMature product with traffic

His most important advice: make it very easy to look at your data. Most wins come from reading 50 traces and spotting a pattern of failure. They rarely come from a clever metric.

03Golden datasets

Size

Start with 50 hand-written cases. Grow to 200–300. Beyond that you pay more but learn little.

Mix the types

Simple lookups, comparisons, questions needing two clauses, numbers and dates, and off-topic questions that must be refused. Tag each case, so you can score each group.

Sources

Real questions with private data removed, questions written by experts, and AI-written questions a human checked. AI-only sets are too easy.

Trick cases

Planted "ignore previous instructions" text, look-alike clauses in other contracts, and clauses that were later changed.

Versioned

Keep it in git next to the prompts. A score means nothing unless you know which version of the set produced it.

Each case holds the question and the ids of the chunks with the answer. It also has a short model answer, the (document, page) pairs to cite, and whether the bot should refuse.

Go deeper: golden set details

A golden set is a versioned file of questions, each with what "good" looks like. For contract Q&A, each case holds the question and the chunk ids that contain the answer. It also holds a short model answer, the (document, page) pairs that must be cited, and whether the system should refuse.

  • Start at 50, grow to 200–300. 50 hand-written cases catch most things that got worse (regressions). Past 300 you pay more but learn little.
  • Mix by type and difficulty. Include lookups ("what is the notice period") and comparisons ("which contracts lack a liability cap"). Add multi-step ones, like a definition in clause 1 with a duty in clause 9. Add numbers and dates, and off-topic questions that must be refused. Tag each case, so you can score each group.
  • Sources: real user questions from logs with private data removed. Questions written by a lawyer or other expert. Questions an LLM wrote from chunks, then checked by a human. AI-only sets are too easy, because the question copies the chunk's wording.
  • Trick cases: planted instructions inside a contract ("ignore previous instructions"), known as prompt injection. Questions with a look-alike clause in another contract. Questions about a clause that was later changed.
  • Keep it in git next to the prompts. A score only means something with the dataset version it came from.
  • Every real bug becomes a golden case. That keeps the set honest.

04Retrieval metrics

Retrieval is the search step. Think of a librarian who brings you 5 books. Did she bring the ones you need, and did she put them on top? Example: the right chunks are c7 and c2. The search returns c4, c7, c9, c2, c1, best first.

recall@kShare of the right chunks found in the top k. Block releases on this.
precision@kShare of the top k that is right. The rest is noise you pay for.
MRR1 divided by the position of the first right chunk.
nDCG@kHow good the order is, compared with the perfect order.

  • Use MRR and nDCG to decide if a reranker, a second step that re-sorts results, is worth the extra time.
Go deeper: ideal DCG and graded relevance

Search sets the upper limit. If the right chunk is not found, no prompt can save the answer. Score it apart from the answer step, so you know which half broke.

Ideal DCG puts both right chunks at positions 1 and 2: 1.000 + 0.631 = 1.631. You can also grade relevance in levels: 2 means it answers the question, 1 means related. Put that level on top of the fraction instead of 1. For contract Q&A, recall@k blocks releases, because missing evidence causes made-up answers or wrong refusals. MRR and nDCG tell you whether a reranker is worth its extra time.

05Generation metrics

Generation is the answer-writing step. Search may have found the right pages, but the model can still misread them or add things that are not there.

Faithfulness

Is every claim backed by the text that search found? Score = backed claims / all claims. This matters most for legal content.

Answer relevance

Does it answer the question that was asked? A true answer about the wrong clause fails here.

Correctness

Same facts as the model answer? Use a yes/no judge. Word-overlap scores like BLEU or ROUGE miss meaning.

Citations and refusal

Plain code checks: required pages cited, off-topic refused. Run them on every commit.

Go deeper: full notes on each metric, and Ragas context metrics

Faithfulness / groundedness

Is every claim backed by the found text? Ragas scores backed claims / all claims. Most important for legal content. A made-up liability number is worse than no answer.

Answer relevance

Does it answer the question asked? A true answer about the wrong clause fails here. Ragas guesses questions from the answer and compares embeddings (meaning as numbers), so it needs an embedding model.

Correctness vs reference

Does it match the golden model answer? Best checked by a yes/no judge ("same facts?"). Word-overlap scores like BLEU or ROUGE work poorly here.

Citation accuracy and refusal

Plain code: are the required (document, page) pairs cited? Were off-topic questions refused? Cheap and exact. Run on every commit.

Ragas also has context precision and context recall. These are search metrics graded by an AI. The AI decides if each found chunk fits the model answer. That helps before you have labelled which chunks are right. Once your golden set has chunk ids, use plain Python metrics instead. They are exact, free and always give the same result.

06LLM-as-judge done properly

You cannot read 300 answers by hand on every change. So a second AI grades them, like a teacher marking essays with a rubric. But a teacher can be too kind or too strict. So you first check the teacher against an expert.

PASS or FAIL usual pick

  • Same result each run. Easy for humans to label.
  • Gives a pass rate that can block a release
  • You need one judge per kind of failure

Always, when the score blocks releases.

1–10 score

  • Nobody can say what makes a 6 and not a 7
  • It shifts between runs. Averages hide failures.

Avoid it. Add another yes/no judge instead.

Position bias

When comparing two answers, judges favour one slot. Run both orders. Count a win only if it holds both times.

Length bias

Judges prefer long answers. Say in the rubric that length does not matter. Check pass rate against answer length.

Self-preference

Judges favour answers from their own model family. Judge with a different model, or prove it does not matter with calibration.

Calibration means checking the judge against an expert. An expert grades 100 real answers: 60 PASS and 40 FAIL. The judge agrees on 54 of the passes and 30 of the fails.

0.84agreement
0.661Cohen's kappa: agreement beyond luck
0.90TPR: good answers it passes
0.75TNR: bad answers it catches. 1 in 4 slips through.

Cohen's kappa should be above about 0.6. TNR (true negative rate) is the share of bad answers the judge also fails. A low TNR is the dangerous direction for legal content. So tighten the rubric, for example "any number not in the context is FAIL". Then measure again.

Go deeper: judge rules and the calibration arithmetic
  • Yes/no beats a 1–10 scale. Nobody can say what makes a 6 and not a 7. Scores shift between runs. Averages hide failures. PASS or FAIL with a one-sentence reason repeats well and is easy for humans to label. It gives a pass rate that can block a release.
  • One judge per kind of failure. "Grounded?", "Cites the right page?" and "Refuses when it should?" are separate prompts. One "is this a good answer?" judge mixes them. Then you cannot tell what got worse.
  • Check against human grades. An expert grades 100 answers PASS or FAIL. Run the judge on the same 100. Report agreement and Cohen's kappa (agreement beyond luck). Also report two rates. TPR: the judge passes what humans pass. TNR: the judge fails what humans fail. Improve the judge prompt until kappa is above about 0.6 and TNR is high. Re-check every few months, or when the judge model changes.
  • Position bias: when comparing two answers, judges favour the first (or second). Run both orders and count a win only if it holds both times. Or shuffle the order and check wins are balanced.
  • Length bias: judges prefer longer answers. Say in the rubric that length does not matter. Keep model answers short. Check whether the pass rate rises with answer length.
  • Self-preference: a judge tends to favour its own model family. Where it matters, judge with a different model. Or use calibration numbers to prove it does not matter.
  • Give the judge what it needs: the question, the found text and the answer, inside XML tags. Ask for the reason before the verdict.

Worked example: 100 answers graded by a human, 60 PASS and 40 FAIL. The judge agrees on 54 passes and 30 fails. It passes 10 that humans failed. It fails 6 that humans passed.

QuantityArithmeticValue
Observed agreement po(54 + 30) / 1000.84
Chance agreement pe0.60 × 0.64 + 0.40 × 0.360.528
Cohen's kappa(0.84 − 0.528) / (1 − 0.528)0.661

84% agreement sounds good. But a TNR of 0.75 means one in four bad answers gets through. For legal content that is the dangerous direction. So you tighten the rubric, for example "any number not in the context is FAIL". Then you measure again.

Step 3: retrieval metrics (retrieval_metrics.py)

Show Python: retrieval_metrics.py
"""Retrieval metrics over ranked chunk ids. Pure Python, no dependencies."""
import math


def recall_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    if not relevant:
        return 1.0  # nothing to find: treat as perfect (refusal cases are judged elsewhere)
    return len(set(retrieved[:k]) & relevant) / len(relevant)


def precision_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    top = retrieved[:k]
    return sum(r in relevant for r in top) / k if top else 0.0


def reciprocal_rank(retrieved: list[str], relevant: set[str]) -> float:
    for i, r in enumerate(retrieved, start=1):
        if r in relevant:
            return 1.0 / i
    return 0.0


def ndcg_at_k(retrieved: list[str], relevant: set[str], k: int) -> float:
    dcg = sum(1.0 / math.log2(i + 1) for i, r in enumerate(retrieved[:k], start=1) if r in relevant)
    ideal = sum(1.0 / math.log2(i + 1) for i in range(1, min(len(relevant), k) + 1))
    return dcg / ideal if ideal else 1.0


if __name__ == "__main__":
    # Worked example from the lesson: relevant chunks c7 and c2, retriever returned c4, c7, c9, c2, c1.
    ranked, gold = ["c4", "c7", "c9", "c2", "c1"], {"c7", "c2"}
    assert recall_at_k(ranked, gold, 3) == 0.5
    assert recall_at_k(ranked, gold, 5) == 1.0
    assert abs(precision_at_k(ranked, gold, 5) - 0.4) < 1e-9
    assert reciprocal_rank(ranked, gold) == 0.5
    assert abs(ndcg_at_k(ranked, gold, 5) - 0.6509) < 1e-3, ndcg_at_k(ranked, gold, 5)
    assert reciprocal_rank(["x"], gold) == 0.0
    print("retrieval metrics OK, nDCG@5 =", round(ndcg_at_k(ranked, gold, 5), 4))

Step 4: a binary groundedness judge (judge.py)

The judge is Haiku 4.5 with temperature 0, so it is as consistent as possible. It gives a reason before its verdict. If its reply cannot be read, the case counts as FAIL.

Show Python: judge.py
"""Binary LLM judge: one failure mode per rubric, PASS/FAIL only."""
import json

import anthropic

JUDGE_MODEL = "claude-haiku-4-5-20251001"
client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY

GROUNDED_RUBRIC = """You are grading a contract Q&A assistant. Decide ONE thing:
is every factual claim in the ANSWER supported by the CONTEXT passages?
- PASS: every claim (numbers, durations, parties, obligations) appears in or follows directly from CONTEXT.
- FAIL: any claim is missing from CONTEXT, contradicts it, or adds a number/duration not in CONTEXT.
Length, tone and style do not matter. A short correct answer passes.
Return only JSON: {"reasoning": "<one or two sentences>", "verdict": "PASS" | "FAIL"}"""


def judge_grounded(question: str, answer: str, contexts: list[str]) -> tuple[bool, str]:
    context_block = "\n\n".join(f"<passage index='{i}'>\n{c}\n</passage>" for i, c in enumerate(contexts))
    msg = client.messages.create(
        model=JUDGE_MODEL,
        max_tokens=300,
        temperature=0,
        system=GROUNDED_RUBRIC,
        messages=[{"role": "user", "content":
                   f"<question>{question}</question>\n<context>\n{context_block}\n</context>\n<answer>{answer}</answer>"}],
    )
    text = "".join(b.text for b in msg.content if b.type == "text")
    try:
        data = json.loads(text[text.index("{"): text.rindex("}") + 1])
        return data["verdict"] == "PASS", data.get("reasoning", "")
    except (ValueError, KeyError):
        return False, f"unparseable judge output: {text[:200]}"  # count as FAIL, never silently pass

Step 5: the runner and gate (run_evals.py)

The script fails (exit 1) if any score is under its minimum. It also fails if any score dropped more than 3 points from the main branch.

Show Python: run_evals.py
"""Offline eval run: golden set -> RAG endpoint -> metrics -> report.json; exit 1 on threshold or regression."""
import json
import sys
import urllib.request
from pathlib import Path
from statistics import mean

from judge import judge_grounded
from retrieval_metrics import ndcg_at_k, recall_at_k, reciprocal_rank

ENDPOINT = "http://localhost:8080/api/contracts/ask?debug=true"
K = 5
THRESHOLDS = {"recall@5": 0.85, "mrr": 0.70, "grounded": 0.90, "citation_ok": 0.95, "refusal_ok": 0.95}
MAX_DROP = 0.03  # fail if any metric drops more than 3 points vs the main-branch baseline


def ask(question: str) -> dict:
    req = urllib.request.Request(ENDPOINT, data=json.dumps({"question": question}).encode(),
                                 headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as resp:
        return json.load(resp)  # {answer, refused, citations:[{documentId,page}], retrieved:[{chunkId,text}]}


def evaluate(case: dict) -> dict:
    out = ask(case["question"])
    if case["expect_refusal"]:
        return {"id": case["id"], "refusal_ok": out["refused"]}
    ranked = [r["chunkId"] for r in out["retrieved"]]
    gold = set(case["relevant_chunks"])
    cited = {(c["documentId"], c["page"]) for c in out["citations"]}
    grounded, why = judge_grounded(case["question"], out["answer"], [r["text"] for r in out["retrieved"]])
    return {"id": case["id"], "refusal_ok": not out["refused"],
            "recall@5": recall_at_k(ranked, gold, K), "mrr": reciprocal_rank(ranked, gold),
            "ndcg@5": ndcg_at_k(ranked, gold, K),
            "citation_ok": all(tuple(m) in cited for m in case["must_cite"]),
            "grounded": grounded, "judge_reasoning": why,
            "question": case["question"], "answer": out["answer"], "contexts": [r["text"] for r in out["retrieved"]]}


def summarise(rows: list[dict]) -> dict:
    keys = ["recall@5", "mrr", "ndcg@5", "grounded", "citation_ok", "refusal_ok"]
    return {k: round(mean(float(r[k]) for r in rows if k in r), 3) for k in keys if any(k in r for r in rows)}


def main(golden_path: str, baseline_path: str | None) -> int:
    cases = [json.loads(line) for line in Path(golden_path).read_text().splitlines() if line.strip()]
    rows = [evaluate(c) for c in cases]
    summary = summarise(rows)
    Path("report.json").write_text(json.dumps({"summary": summary, "rows": rows}, indent=2))
    print(json.dumps(summary, indent=2))
    failures = [f"{k}={summary[k]} < {t}" for k, t in THRESHOLDS.items() if summary.get(k, 1.0) < t]
    if baseline_path and Path(baseline_path).exists():
        base = json.loads(Path(baseline_path).read_text())["summary"]
        failures += [f"{k} regressed {base[k]} -> {v}" for k, v in summary.items() if k in base and base[k] - v > MAX_DROP]
    for f in failures:
        print("FAIL:", f)
    return 1 if failures else 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2] if len(sys.argv) > 2 else None))

Step 6: a Ragas second opinion (ragas_faithfulness.py)

Where Ragas and your judge disagree, look closely. It is the cheapest way to find what your judge misses.

Show Python: ragas_faithfulness.py
"""Second opinion on groundedness with Ragas 0.4 Faithfulness (claims supported / total claims)."""
import asyncio
import json
import sys

from anthropic import AsyncAnthropic
from ragas.llms import llm_factory
from ragas.metrics.collections import Faithfulness


async def main(report_path: str) -> None:
    llm = llm_factory("claude-haiku-4-5-20251001", provider="anthropic", client=AsyncAnthropic())
    scorer = Faithfulness(llm=llm)
    samples = [r for r in json.load(open(report_path))["rows"] if "contexts" in r]  # answered cases only
    scores = []
    for s in samples:
        result = await scorer.ascore(user_input=s["question"], response=s["answer"], retrieved_contexts=s["contexts"])
        scores.append(result.value)
        print(f"{result.value:.2f}  {s['question'][:60]}")
    print("mean faithfulness:", round(sum(scores) / len(scores), 3))


if __name__ == "__main__":
    asyncio.run(main(sys.argv[1]))

Step 7: calibrate the judge (calibrate.py)

Show Python: calibrate.py
"""Judge vs human labels: agreement, Cohen's kappa, TPR, TNR. Input: list of (human_pass, judge_pass)."""


def calibration(pairs: list[tuple[bool, bool]]) -> dict:
    n = len(pairs)
    tp = sum(h and j for h, j in pairs)              # both PASS
    tn = sum(not h and not j for h, j in pairs)      # both FAIL
    p_o = (tp + tn) / n
    h_pass, j_pass = sum(h for h, _ in pairs) / n, sum(j for _, j in pairs) / n
    p_e = h_pass * j_pass + (1 - h_pass) * (1 - j_pass)
    return {"agreement": round(p_o, 3), "kappa": round((p_o - p_e) / (1 - p_e), 3),
            "tpr": round(tp / sum(h for h, _ in pairs), 3),           # judge passes what humans pass
            "tnr": round(tn / sum(not h for h, _ in pairs), 3)}       # judge catches what humans fail


if __name__ == "__main__":
    labels = [(True, True)] * 54 + [(True, False)] * 6 + [(False, True)] * 10 + [(False, False)] * 30
    print(calibration(labels))
    assert calibration(labels) == {"agreement": 0.84, "kappa": 0.661, "tpr": 0.9, "tnr": 0.75}

Go deeper: notes on each step

You will build five small files. You will test the Spring Boot endpoint from the RAG endpoint lesson. For evals it accepts ?debug=true, which is turned off in production. It then also returns the found chunks, best first, with their ids and text.

The golden file has one JSON object per line. Chunk ids follow the pattern <documentId>#p<page>#c<n>. The document-loading step writes that id into each chunk. So a label still works after you reload documents, as long as chunk settings stay the same. When you change chunk size, label again. Or label by (document, page) and count any chunk on that page as right.

Haiku 4.5 is the judge. It costs $1 per million input tokens and $5 per million output tokens. A yes/no decision does not need a bigger model once it is calibrated. Use temperature 0 and ask for the reason before the verdict. An unreadable reply counts as FAIL. That way a broken judge can never make the pass rate look better.

The runner asks every golden question. It computes the plain code metrics. It calls the judge for answered cases. It writes report.json. It exits with status 1 if any score is below its minimum. It also exits 1 if any score dropped more than 3 points from the saved report on main.

Your numbers will differ. What matters is the shape. Say a change lowers citation_ok from 0.967 to 0.90. You get FAIL: citation_ok regressed 0.967 -> 0.9 and exit code 1. Open report.json and read judge_reasoning on the failing rows. That is where the fix comes from.

Ragas 0.4 metrics live in ragas.metrics.collections. They take an LLM built by llm_factory, and Anthropic is supported. Use Ragas to double-check your own judge. Also use it for metrics you have not built yet. ContextRecall takes user_input, retrieved_contexts and reference. AnswerRelevancy also needs an embeddings object.

A score of 0.50 means half the claims were not found in the text. If your yes/no judge passed that same answer, read it yourself. Where the two judges disagree is the cheapest place to find blind spots.

Give it real pairs. Export 100 requests to a spreadsheet. Have an expert mark PASS or FAIL without seeing the judge's verdict. Then match them up by trace id.

Only run the costly suite when something that affects answers changes. That means prompts, search code, chunk settings, model ids, or the golden set itself. Keep the main-branch report as the one to compare against.

Cost per run for 200 cases: the bot runs on Sonnet 5.5. Each answer uses about 4,000 input and 400 output tokens. That is 200 × (4,000 × $2 + 400 × $10) / 1M = $2.40. The Haiku judge uses about 1,500 input and 150 output tokens per grade. That is 200 × (1,500 × $1 + 150 × $5) / 1M = $0.45. So under $3 per PR. To cut more, run plain code metrics on every PR, and the judge only when prompts change. On PRs, use a fixed sample of 50 mixed cases, and run the full set nightly. Cache answers by (prompt hash, model, question), so unchanged cases are not answered again.

Every week, read the thumbs-down requests and the judge's FAILs. Group them by kind of failure. Fix the biggest one. Add the cases to golden.jsonl. That loop is the real goal. The metrics just keep it honest.

Common mistakes
  • Saying "we use Ragas" with no golden set and no check of the judge.
  • Using 1–10 scores and averaging them.
  • Failing builds on 1-point swings that are just normal noise.
  • Only scoring the final answer. Then you cannot tell a search failure from an answer failure.
  • Counting an unreadable judge reply as PASS.

08Quick check

Search found all the right chunks (recall@5 is 1.0), but the groundedness judge fails the answer. Where is the bug?

The evidence reached the model, so search did its job. The answer step broke. Try re-sorting and sending only the top 3, a stricter "use only this text" prompt, or bigger chunks.

Your judge agrees with experts 84% of the time, and its TNR is 0.75. What does that mean for a legal bot?

TNR is the share of bad answers the judge catches. At 0.75 it misses one in four. Missing bad answers is the dangerous direction for legal content.

Which search metric should block a RAG release?

If the evidence never reaches the model, it makes up an answer or refuses wrongly. Precision and nDCG only help you tune noise and order.

How do you keep eval CI cheap and non-flaky?

Answers change a little each run. Run an unchanged branch 3 times to measure that wobble. Then only fail on drops bigger than it.

09Interview questions

Design an eval pipeline for a RAG system. (Tekion)

Four parts. (1) A versioned golden set of 50–300 cases, mixed by question type. Each case labels the right chunks and has a model answer, must-cite pages, and whether to refuse. (2) Search scored on its own. Recall@k blocks releases. MRR and nDCG judge rerankers. (3) The answer step. Plain code checks cover citations, refusals and format. A yes/no groundedness judge is calibrated against 100 expert grades, to a kappa above 0.6. (4) CI runs on prompt or search changes, with minimums and a comparison to main. In production, sample real requests into the same judge and collect thumbs feedback. Every week, turn failures into golden cases.

Why binary pass/fail instead of a 1–10 score?

Scales do not repeat. The same answer gets a 6 or a 7 depending on the run. Humans cannot agree on the difference either, so you cannot calibrate. Yes/no verdicts with a one-sentence reason are easy to label. They give a pass rate you can set a minimum on. They force you to define exactly what failure means. If you need more detail, add another yes/no judge for another kind of failure.

How do you know your LLM judge is right?

Calibrate it. An expert grades 100 answers without seeing the judge's grades. I compute agreement, Cohen's kappa, TPR and TNR. I care most about TNR, the share of bad answers the judge catches. I improve the rubric until the numbers are good enough. I re-check when the judge model changes. I spot-check disagreements with Ragas faithfulness.

Explain recall@k vs precision@k vs MRR vs nDCG.

Recall@k is the share of right chunks found in the top k. It tells you if the evidence reached the model. Precision@k is the share of the top k that is right. It tells you how much noise you pay for. MRR is 1 divided by the position of the first right chunk, averaged over questions. nDCG gives credit that shrinks lower in the list, divided by the perfect score. It rewards putting right chunks higher, and it handles levels of relevance. For RAG I block releases on recall@k, because missing evidence causes made-up answers.

The right document was retrieved but the answer was wrong. How do the metrics tell you that?

Recall@k is 1 for that case, but groundedness or correctness fails. So the problem is the answer step. Maybe the chunk was buried among noisy ones: low precision, and models often miss text in the middle. Maybe the prompt did not ask for quotes. Maybe the answer needed two chunks and only one was found. Maybe a chunk cut a sentence in half. I read the trace. Then I try re-sorting to the top 3, a stricter grounding prompt, or bigger chunks that overlap. Then I run the suite again.

What is faithfulness and how does Ragas compute it?

It asks whether the answer's claims are backed by the found text. Ragas uses an LLM to split the answer into single claims. It checks each claim against the text. It returns backed claims divided by all claims. It says nothing about whether the found text was the right text. Context recall and answer relevance cover that.

How do you evaluate an agent over a golden set? (Google)

An agent is an AI that takes several steps and uses tools. Score the result and the path separately. Result: did the final state or answer match the reference? Use a yes/no judge or an exact check. Path (trajectory): did it call the expected tools with valid inputs? How many steps? Any forbidden actions? Did it stop? Report task success rate, average steps, tool error rate and cost per task. Run each case several times, because agents vary run to run. Report the pass rate across repeats, not one run.

How do you run evals in CI without it being slow, flaky or expensive?

Run only when files that affect answers change. Plain code checks run on every PR. The judge runs on a fixed, mixed sample, and the full set runs nightly. Use a cheap, calibrated judge model. Cache answers by prompt hash. Only fail on drops bigger than the measured run-to-run wobble, not on any change.

What biases does an LLM judge have?

Position bias when comparing two answers. Fix it by swapping the order and requiring the same result. Length bias. Say length does not matter, and check whether pass rate rises with length. Self-preference for its own model family. Use a different judge model, or prove it does not matter with calibration. Going easy on answers that sound confident. Require evidence from the text in the reason.

Which online metrics do you watch after launch?

Thumbs up and down, with reasons. Refusal rate per tenant. How often users click citations. A groundedness judge on a sample of live answers. p95 latency and cost per answer. Each alert links to the requests behind it. Every confirmed failure becomes a golden case.

10Capstone checkpoint

This is the week 7 milestone for the contract Q&A bot and the risky-clause flagger.

Show the six week-7 tasks

11Cheat sheet

Cheat sheet
  • Golden set: grow from 50 to 300 mixed cases, kept in git. Include refusals and trick cases.
  • Search: recall@k blocks releases. MRR and nDCG judge rerankers.
  • Answers: faithfulness, relevance, correctness, citations and refusal.
  • Judge: yes/no, one per kind of failure, reason before verdict. An unreadable reply is FAIL.
  • Calibrate on 100 expert grades. Kappa should be above 0.6. Watch TNR.
  • Judge biases: position, length and self-preference.
  • CI: run only on relevant file changes. Use minimums and a comparison to main. Under $3 per PR.
  • Live: thumbs, refusal rate, sampled judge, p95 and cost. Failures become new golden cases.
