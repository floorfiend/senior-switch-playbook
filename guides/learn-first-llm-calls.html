Your first LLM calls: Python and Spring AI

In this lesson you call Claude from Python and from Spring Boot. You will show the answer word by word as it is written (streaming). You will get typed output back, like a Java record. You will log how many tokens each call used and how long it took. You will also handle the two "please slow down" errors, 429 and 529.

Time: 3–4 hours Stack: Python 3.12+, anthropic SDK 1.x; Spring Boot 4 + Spring AI 2.0 Cost: a few cents on Haiku 4.5
Messages APIStreamingStructured outputRetriesChatClient
In 30 seconds
  • The Messages API remembers nothing between calls. You send the whole chat history every time.
  • The words the model writes back (output tokens) decide most of the cost and the waiting time.
  • Stream the answer so the user sees words early. Measure the wait for the first word on its own.
  • When the API says "busy", wait a random short time and try again. Do this in one place only.
Picture it

Think of a UPI payment. Each request carries everything the bank needs. Nothing is remembered between taps. Streaming is like the "payment processing…" screen that updates live. Without it, you stare at a blank screen until the receipt appears.

Figure: one request goes in and one response comes back. The server keeps no session, so you send the history each time.

  • For a chat, add the model's reply and the user's next message to your list. Then send the whole list again. So input tokens grow every turn.

Tokens are your unit of cost and latency

A token is a small piece of text, about 4 English letters. Prices are per MTok, which means per one million tokens. Input is what you send. Output is what the model writes.

$2 / $10Sonnet 5.5, per MTok in / out
$1 / $5Haiku 4.5
$4 / $20Opus 5.5
5×output vs input price
  • usage tells you input_tokens and output_tokens. With caching it also has cache_creation_input_tokens and cache_read_input_tokens.
  • The model writes output tokens one at a time, so they are also what you wait for. 60 tokens is fast. 2,000 tokens is not.
One modern-model gotcha

Sonnet 5.5 and Opus 5.5 have three limits. temperature and top_p accept only the default. Prefilling the start of the assistant's reply returns a 400 error. Forcing a tool choice (any or tool) is not supported. Use structured outputs and output_config.effort instead.

Go deeper: statelessness, tokens and the modern-model gotcha in full

Think of it as calling another microservice that has no session. Every request carries the whole chat. That is an optional system prompt and a list of messages. The messages take turns between user and assistant. The server keeps nothing between calls.

For a chat, you add the assistant's reply and the next user message to the list. Then you send everything again. That is why long chats get slower and more expensive. Input tokens grow on every turn.

usage reports input_tokens and output_tokens. With prompt caching it also reports cache_creation_input_tokens and cache_read_input_tokens. Prices are per million tokens (MTok). Claude Sonnet 5.5 costs $2 input and $10 output. Haiku 4.5 costs $1 and $5. Opus 5.5 costs $4 and $20.

Output tokens cost five times more than input. They are also what you wait for, because the model writes them one at a time. A classification that returns 60 tokens is fast. A 2,000-token explanation is not.

The newest Claude models are Sonnet 5.5 and Opus 5.5. On them, temperature and top_p are deprecated, and only the default is accepted. Temperature is the "randomness dial" for picking words. Prefill means writing the first few characters of the assistant's reply yourself. It now returns a 400 error. Forcing a tool choice (any or tool) is not supported either.

Older tutorials set temperature=0 or prefill { to force JSON. Those will fail. Use structured outputs instead. Control depth and cost with output_config.effort (low, medium, high, …).

03Streaming, step by step

Without streaming, the user waits for the whole answer. With streaming, words appear as they are written, like a person typing in a chat app.

  1. ClientAsks for a streamed answer. This opens one HTTP request (client.messages.stream(...)).
  2. APISays "OK" (HTTP 200) and keeps the line open. It pushes small messages down it, called SSE events (server-sent events).
  3. Your codeShows each new piece of text as it arrives (a text_delta). In Java terms, it is a Flux<String>.
  4. APIEnds by saying why it stopped and how many tokens it used (stop_reason and usage).
"Explain an indemnity clause": the SSE events in order
Go deeper: the SSE event list

With streaming, the API sends SSE events as tokens are written. The order is:

  • message_start.
  • For each content block, a content_block_start.
  • Many content_block_delta events, each with a text_delta.
  • A content_block_stop.
  • Then message_delta, with the final stop_reason and usage.
  • Finally message_stop.

There are also ping events. In Java terms, it is a Flux<String> where each item is a piece of text. The user sees the first words in well under a second. Without streaming, they would wait for the full answer. That is why every chat screen streams.

Errors can arrive after HTTP 200. Once a stream has started, an overload shows up as an SSE error event. It looks like {"type": "overloaded_error"}, not an HTTP 529. Your streaming code must handle an error in the middle. And a retry after the first token would show duplicate text to the user.

04Structured output and errors

Your code needs data it can trust, not free text. Structured output is like giving the model a form with fixed boxes. It cannot write outside the boxes.

"Please reply in JSON"

  • You only hope it works. You may get prose, a draft or broken JSON.

Fallback only.

Structured outputs usual pick

  • A JSON schema in output_config.format forces the shape of the reply.
  • Python: messages.parse(output_format=Model) gives you parsed_output.
  • Spring AI: .entity(Record.class) uses BeanOutputConverter and Jackson.

Like @RequestBody binding, but on the model's output.

  • Objects need additionalProperties: false. The API does not enforce minimum or maxLength. The SDK checks those on your side.
  • Enums (a fixed list of allowed values) are supported. Use them for labels such as risk levels.

When a call fails, the HTTP code tells you whether trying again can help.

HTTPtypeRetry?
400invalid_request_errorNo. Fix the request. Examples: a bad schema, an unsupported parameter, or a chat that does not end with a user turn.
401 / 403authentication_error / permission_errorNo. Alert a person.
413request_too_largeNo. The Messages API limit is 32 MB.
429rate_limit_errorYes. Wait longer each time and respect the retry-after header. A 429 from a spending cap has no retry-after and will keep failing.
500api_errorYes, waiting twice as long each time (exponential backoff)
504timeout_errorYes, but prefer streaming for long answers
529overloaded_errorYes, with backoff and a random extra wait (jitter). Consider switching to another model.
  • The SDKs already retry connection errors, 429 and 5xx errors twice by default. They respect retry-after. Change this with max_retries or spring.ai.anthropic.max-retries.
  • Log the request-id header. In Python it is message._request_id. Support will ask for it.
Go deeper: structured output and SDK retries in full

The old way was to ask for JSON in the prompt and hope. The API now supports structured outputs. You pass a JSON schema in output_config.format. The model's reply is then forced to match it.

The Python SDK wraps this as client.messages.parse(..., output_format=MyPydanticModel). It gives you response.parsed_output. In Spring AI, .entity(MyRecord.class) builds a JSON schema from your record, using BeanOutputConverter. It then maps the reply back with Jackson. It is the same idea as @RequestBody binding, but on the model's output.

The schema has limits. Objects need additionalProperties: false. Number and length rules like minimum or maxLength are not enforced by the API. The SDK moves them into descriptions and checks them on your side. Enums are supported, which is what you want for labels such as risk levels.

The official SDKs already retry connection errors, 429 and 5xx twice by default. They wait longer each time and respect retry-after. Change it with max_retries (Python) or spring.ai.anthropic.max-retries (Spring AI). Every response also has a request-id header. In Python it is message._request_id. Log it, because support asks for it.

import logging
import time

import anthropic

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")

print(text)
u = message.usage
log.info(
    "request_id=%s model=%s stop=%s in=%d out=%d cache_read=%s latency_ms=%.0f",
    message._request_id, message.model, message.stop_reason,

Step 3: streaming, with time to first token

Show stream.py
import time

import anthropic

client = anthropic.Anthropic()

start = time.perf_counter()
first_token_ms = None
with client.messages.stream(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system="You explain contract clauses to non-lawyers.",
    messages=[{"role": "user", "content": "Explain an indemnity clause with one example."}],
) as stream:
    for text in stream.text_stream:
        if first_token_ms is None:
            first_token_ms = (time.perf_counter() - start) * 1000
        print(text, end="", flush=True)
    final = stream.get_final_message()

total_ms = (time.perf_counter() - start) * 1000
print(f"\n\nttft_ms={first_token_ms:.0f} total_ms={total_ms:.0f} "
      f"in={final.usage.input_tokens} out={final.usage.output_tokens} stop={final.stop_reason}")

Step 4: prompt templates

Keep each prompt as a named constant with a version number. Fill it with a function that fails if a variable is missing. Put the user's text inside XML-style tags, so the model can tell your instructions from their text.

Show templates.py
from string import Template

CLASSIFY_V2 = Template("""Classify the contract clause below.

<clause id="$clause_id">
$clause_text
</clause>

Return the clause type and a risk level for the party "$party".""")


def render_classify(clause_id: str, clause_text: str, party: str) -> str:
    # substitute() raises KeyError on a missing variable: fail loudly, never send a half-filled prompt
    return CLASSIFY_V2.substitute(clause_id=clause_id, clause_text=clause_text.strip(), party=party)


if __name__ == "__main__":
    out = render_classify("c-17", "  The Supplier's total liability shall not exceed fees paid in 12 months. ", "Customer")
    assert '<clause id="c-17">' in out and "$" not in out
    try:
        CLASSIFY_V2.substitute(clause_id="x")
        raise AssertionError("expected KeyError")
    except KeyError:
        pass
    print(out)

uv run templates.py prints the prompt, and the self-check passes. Log the template id (CLASSIFY_V2). Then, if quality drops, you can tie it to a prompt change.

Step 6: retries beyond the SDK

Interactive request

  • The SDK retries are enough. Raise max_retries a little and set a timeout.

Overnight batch of 50,000 clauses

  • Add an outer retry loop with full jitter (a fully random wait).
  • This stops thousands of workers from retrying at the same moment after an overload.
Show backoff.py
import logging
import random
import time
from typing import Callable, TypeVar

import anthropic
import httpx

T = TypeVar("T")
log = logging.getLogger("llm.retry")

RETRYABLE = (anthropic.RateLimitError, anthropic.OverloadedError,
             anthropic.InternalServerError, anthropic.APIConnectionError)


def with_backoff(call: Callable[[], T], attempts: int = 5, base: float = 1.0, cap: float = 30.0,
                 sleep: Callable[[float], None] = time.sleep) -> T:
    """Outer retry for batch jobs, on top of the SDK's own retries. Full jitter, honours retry-after."""
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except RETRYABLE as e:
            if attempt == attempts:
                raise
            delay = random.uniform(0, min(cap, base * 2 ** (attempt - 1)))
            response = getattr(e, "response", None)
            retry_after = response.headers.get("retry-after") if response is not None else None
            if retry_after and retry_after.isdigit():
                delay = max(delay, float(retry_after))
            log.warning("attempt=%d error=%s sleeping=%.2fs", attempt, type(e).__name__, delay)
            sleep(delay)
    raise AssertionError("unreachable")


if __name__ == "__main__":
    # Offline self-check: fake a 529 twice, then succeed. No API key, no network.
    req = httpx.Request("POST", "https://api.anthropic.com/v1/messages")
    overloaded = httpx.Response(529, request=req, headers={"retry-after": "2"})
    calls, slept = [], []

    def flaky() -> str:
        calls.append(1)
        if len(calls) < 3:
            raise anthropic.OverloadedError("Overloaded", response=overloaded, body=None)
        return "ok"

    assert with_backoff(flaky, sleep=slept.append) == "ok"
    assert len(calls) == 3 and all(s >= 2 for s in slept), slept
    print("calls:", len(calls), "sleeps:", slept)

uv run backoff.py checks itself offline. It fakes two 529 errors, then succeeds. Each wait is at least the retry-after value.

attempt=1 error=OverloadedError sleeping=2.00s
attempt=2 error=OverloadedError sleeping=2.00s
calls: 3 sleeps: [2.0, 2.0]

Retry amplification

Retries stacked in layers multiply. Retry in one layer only. Put a limit on the total time. Limit how many batch calls run at once.

Go deeper: retry amplification

Picture three layers. The SDK retries 3 times. An outer loop tries 5 times. The caller also retries 3 times. During an outage, that is up to 4 × 5 × 3 = 60 requests for one user action. So retry in one layer only. Limit the total time. Add a limit on how many batch calls run at once. It is the same rule you follow for Feign or WebClient chains between microservices.

Show Java solution: ClauseAiService
package com.example.clauses;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicBoolean;

import com.anthropic.errors.AnthropicIoException;
import com.anthropic.errors.AnthropicServiceException;
import com.anthropic.errors.InternalServerException;
import com.anthropic.errors.RateLimitException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.metadata.Usage;
import org.springframework.ai.chat.model.ChatResponse;
import org.springframework.resilience.annotation.Retryable;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Flux;
import reactor.util.retry.Retry;

@Service
public class ClauseAiService {

    private static final Logger log = LoggerFactory.getLogger(ClauseAiService.class);

    // Prompt template, versioned in code. {placeholders} are filled with .param(): never concatenate user text in.
    static final String CLASSIFY_V2 = """
            Classify the contract clause below for the party {party}.
            <clause id="{clauseId}">
            {clauseText}
            </clause>
            """;

    private final ChatClient chatClient;

    public ClauseAiService(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultSystem("You are a contracts analyst at an e-signing company. Be precise and brief.")
                .build();
    }

    // Structured output: Spring AI derives a JSON schema from the record and maps the reply onto it.
    // Outer retry for longer outages; SDK retries (max-retries) already run inside each attempt.
    @Retryable(includes = {RateLimitException.class, InternalServerException.class},
            maxRetries = 2, delay = 2000, multiplier = 2, maxDelay = 10000, jitter = 500)
    public ClauseRisk classify(String clauseId, String clauseText, String party) {
        long start = System.nanoTime();
        ClauseRisk risk = chatClient.prompt()
                .user(u -> u.text(CLASSIFY_V2)
                        .param("clauseId", clauseId)
                        .param("clauseText", clauseText)
                        .param("party", party))
                .call()
                .entity(ClauseRisk.class);
        log.info("llm.classify prompt=CLASSIFY_V2 clauseId={} latencyMs={}", clauseId, (System.nanoTime() - start) / 1_000_000);
        return risk;
    }

    // chatResponse() keeps the metadata: model, token usage, rate-limit info.
    public String summarise(String clauseText) {
        long start = System.nanoTime();
        ChatResponse response = chatClient.prompt()
                .user(u -> u.text("Summarise this clause for a non-lawyer in two sentences:\n{text}").param("text", clauseText))
                .call()
                .chatResponse();
        Usage usage = response.getMetadata().getUsage();
        log.info("llm.summarise model={} inTokens={} outTokens={} latencyMs={}", response.getMetadata().getModel(),
                usage.getPromptTokens(), usage.getCompletionTokens(), (System.nanoTime() - start) / 1_000_000);
        return response.getResult().getOutput().getText();
    }

    // Streaming: a Flux of text chunks. Retry only if nothing was sent yet, or the client sees duplicated text.
    public Flux<String> explain(String clauseText) {
        AtomicBoolean started = new AtomicBoolean();
        return chatClient.prompt()
                .user(u -> u.text("Explain this clause to a non-lawyer, with one example:\n{text}").param("text", clauseText))
                .stream()
                .content()
                .doOnNext(chunk -> started.set(true))
                .retryWhen(Retry.backoff(2, Duration.ofSeconds(1)).maxBackoff(Duration.ofSeconds(8))
                        .filter(e -> !started.get() && isTransient(e)));
    }

    static boolean isTransient(Throwable e) {
        for (Throwable t = e; t != null; t = t.getCause()) {
            if (t instanceof AnthropicServiceException ase) {
                int status = ase.statusCode();
                return status == 429 || status >= 500;   // 529 overloaded is >= 500
            }
            if (t instanceof AnthropicIoException) {
                return true;
            }
        }
        return false;
    }
}
Go deeper: what each method shows
  • classify fills a template's {placeholders} with .param(). It uses .entity(ClauseRisk.class) for typed output. Spring Framework 7's @Retryable adds an outer retry that waits longer each time, with jitter.
  • In classify, includes matches the type of the thrown exception. Your Spring AI version may wrap SDK exceptions in another type. If so, list that wrapper type, or just rely on max-retries.
  • summarise uses .chatResponse() instead of .content(). This keeps the metadata. So you can log getPromptTokens() and getCompletionTokens() with the model and the time taken.
  • explain uses .stream().content(), which returns Flux<String>. Reactor's retryWhen retries only if no piece has been sent yet.

The controller checks input where it enters your system. It caps the clause length, so no request can send a 32 MB prompt. It also switches on @Retryable.

import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Flux;

@RestController
@RequestMapping("/api/clauses")
public class ClauseController {

    public record ClauseRequest(@NotBlank String clauseId, @NotBlank @Size(max = 20_000) String clauseText,
                                @NotBlank String party) { }

    private final ClauseAiService ai;

    public ClauseController(ClauseAiService ai) {
        this.ai = ai;
    }

    @PostMapping("/classify")
    public ClauseRisk classify(@Valid @RequestBody ClauseRequest req) {
        return ai.classify(req.clauseId(), req.clauseText(), req.party());
    }

    @PostMapping(value = "/explain", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> explain(@Valid @RequestBody ClauseRequest req) {
        return ai.explain(req.clauseText());
    }

    @Configuration
    @EnableResilientMethods
    static class ResilienceConfig { }
}

Production logging checklist
  • Log the request id, model, and prompt template id and version. Log input, output and cache tokens.
  • Also log TTFT, total time, stop_reason, retry count and tenant id. Take the tenant id from the JWT (login token), never from the request body.
  • Do not log raw contract text or personal data by default. Log a hash or the document id instead.
  • Export tokens and times as Micrometer metrics, tagged with model and template. Alert when max_tokens stops or 429s rise.
Common mistakes
  • Reading content[0].text without checking the block type.
  • Reading a reply cut off by max_tokens as complete JSON.
  • Retrying a stream after the first token reached the user.
  • Stacking retry layers, which can mean 60 requests for one action.
  • Gluing user text into a template instead of using .param().
  • Setting temperature=0 on Sonnet 5.5, which returns a 400 error.

06How this shows up in interviews

Why stream, and what do you measure?

Streaming makes the wait feel shorter. The user reads the first words after TTFT, the time to first token. That is often under a second. Without it, they wait for the whole answer. Measure TTFT, total time, and output tokens per second separately. Streaming also avoids timeouts on idle connections during long answers. That is why the docs recommend it when max_tokens is large.

What is the difference between 429 and 529, and how do you handle each?

429 rate_limit_error means your own organisation hit its limit. The limit can be on requests, tokens, or spend. Back off and respect retry-after. Smooth your traffic with a rate limiter on your side. If it is a spending cap, stop retrying. 529 overloaded_error means the API is overloaded for everyone. Back off with jitter. For user-facing paths, consider a fallback model. The SDK retries both by default.

Is retrying an LLM call safe? Is it idempotent?

A plain text generation changes nothing else, so retrying is safe for correctness. But it is not idempotent in its output. Idempotent means repeating it gives the same result, and here you may get different text. You also pay for every attempt that produced tokens. If the call triggers actions, like tool calls that write data, make those tools idempotent with keys. Never retry a stream after tokens reached the user.

How do you get reliable JSON out of a model?

Use structured outputs with a JSON schema. That is output_config.format, or messages.parse with a Pydantic model, or .entity() in Spring AI. Use enums for labels. Still validate the data when it arrives. Check that stop_reason is not max_tokens. Asking "reply in JSON" in the prompt is a fallback, not a design.

Your LLM endpoint p99 is 12 seconds. What do you look at?

p99 means 99 out of 100 requests are faster than this. First, look at the output token count, because time grows with output. Then check the model choice; Haiku is enough for classification. Check the effort level. Check the prompt size, since input tokens add reading time (prefill). Use prompt caching for a large prefix that never changes. Check for retries hidden inside the SDK by logging the retry count. Ask whether the client could stream. Then set a timeout and a fallback.

What would you log for every LLM call?

Log the request id, model, prompt template version and tenant. Log input, output and cache tokens. Log TTFT, total time, stop reason, retry count, and whether validation passed. With that, you can work out cost per tenant and per feature. You can also debug quality drops after a prompt change.

Why does a multi-turn chat get more expensive per turn?

The API is stateless, so every turn sends all earlier turns again as input tokens. Cost per turn grows roughly in line with the chat length. Reduce it with prompt caching of the part that does not change. You can also summarise or trim old turns.

How is ChatClient different from calling the SDK directly?

ChatClient is a portable, fluent API on top of a provider's ChatModel. It gives you templates with parameters and advisors for logging, memory and RAG. It also handles tools, structured output via converters, and Micrometer observations. The price is an extra layer that may lag behind new provider features. For those, use provider-specific options, such as AnthropicChatOptions with effort or output schema. Or use the raw SDK.

A teammate sets temperature=0 for deterministic output and gets a 400. Why?

On the newest Claude models, temperature and top_p are deprecated. Only the default value is accepted. Even where temperature works, 0 does not promise the same output every time. For consistent answers, use structured outputs and clear instructions with examples. Then test on a fixed set of cases.

07Quick check

Turn 10 of a chat uses far more input tokens than turn 1. Why?

The server keeps no session, so you resend the whole chat each turn. Reduce it with prompt caching, or by summarising or trimming old turns.

A reply has stop_reason: "max_tokens", but the JSON happens to parse. What do you do?

It was cut off at your limit. Data may be missing, even if it parses.

An overload happens after 40 tokens have reached the user. What arrives, and should you retry?

The HTTP status was already 200, so the error comes as an event. A retry would repeat text the user already saw. That is why Spring's retryWhen filter checks !started.get().

The SDK retries 3 times, an outer loop tries 5 times, and the caller retries 3 times. What is the worst case, in requests per user action?

The layers multiply: (1 + 3) × 5 × 3 = 60. Retry in one layer only.

Exercise steps in full

The capstone is a contract Q&A service plus a tool that flags risky clauses. This lesson gives you its first two endpoints.

  1. In your capstone Spring Boot service, add POST /api/clauses/classify, which returns ClauseRisk. Add POST /api/clauses/explain, which streams text.
  2. Write 10 sample clauses, each with the label you expect. Make two each of: liability cap, uncapped indemnity, termination for convenience, auto-renewal, and governing law.
  3. Write a Python script that calls your endpoint for each clause and prints the accuracy. This is your first golden set, a fixed list of test cases with known answers. The evals lesson builds on it.
  4. Log the fields in the checklist above. From the logged tokens, work out the cost per 1,000 classifications for Haiku 4.5 and Sonnet 5.5.
  5. Turn off your network for a few seconds in the middle of a batch. Confirm the batch finishes without duplicate writes. Confirm no more than one retry layer fires.

Done when: both endpoints work, and accuracy is at least 9/10 on your golden set. You can also state the cost per 1,000 calls and your p95 TTFT from your own logs. p95 means 95 out of 100 requests are faster than this.

09Cheat sheet

Cheat sheet
  • Request fields: model, max_tokens (required), system, messages, output_config.
  • Response: content[] blocks, stop_reason, usage, request id. Join all the text blocks.
  • A max_tokens stop means the answer was cut off. Never trust it as complete.
  • Price per million tokens, in and out: Haiku 4.5 $1/$5, Sonnet 5.5 $2/$10, Opus 5.5 $4/$20.
  • Stream order: message_start → block start → deltas → block stop → message_delta → message_stop. Measure TTFT.
  • Typed output: messages.parse or .entity(). Use enums for labels.
  • Retry 429 (respect retry-after), 500, 504 and 529. Never retry 400, 401, 403 or 413. Retry in one layer only.
  • Spring: one ChatClient, .param() templates, Flux streaming. Retry a stream only before the first piece.
