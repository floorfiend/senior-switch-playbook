02Concepts explained for a Java backend engineer

The Messages API is a stateless REST call

Think of it as calling a downstream microservice that has no session. Every request carries the whole conversation: an optional system prompt and a list of messages that alternate user and assistant. The server keeps nothing between calls. If you want a chat, you append the assistant's reply and the next user turn to the list and send everything again. That is why long chats get slower and more expensive: input tokens grow on every turn.

Your servicebuilds request→ POST /v1/messagesmodel, max_tokens, system, messages→ Claudegenerates tokens→ Responsecontent[], stop_reason, usage

Figure: one request, one response. No server-side session; you resend history each time.

Request fieldWhat it isJava analogy

The response has id, model, a content array of blocks (for now only type: "text"; later you will see tool_use and thinking), a stop_reason and usage.

stop_reasonMeaningWhat your code should do
end_turnModel finished naturallyUse the answer
max_tokensCut off at your capTreat as truncated: never parse it as complete JSON; raise the cap or ask for less
stop_sequenceHit one of your stop stringsExpected if you set them
tool_useModel wants you to run a toolRun it and send a tool_result (tool-use lesson)

Tokens are your unit of cost and latency

usage reports input_tokens, output_tokens, and with prompt caching cache_creation_input_tokens and cache_read_input_tokens. Pricing is per million tokens (MTok): Claude Sonnet 5.5 is $2 input / $10 output, Haiku 4.5 is $1 / $5, Opus 5.5 is $4 / $20. Output tokens cost five times input and are also what you wait for, because the model produces them one at a time. A classification that returns 60 tokens is fast; a 2,000-token explanation is not.

Streaming is server-sent events, like a reactive Flux

With streaming the API sends SSE events as tokens are produced: message_start, then per content block a content_block_start, many content_block_delta events (each with a text_delta), content_block_stop, then message_delta (final stop_reason and usage) and message_stop. There are also ping events. In Java terms, it is a Flux<String> where each element is a chunk of text. The user sees the first words in well under a second instead of waiting for the full answer, which is why every chat UI streams.

Errors can arrive after HTTP 200

Once a stream has started, an overload shows up as an SSE error event with {"type": "overloaded_error"}, not as an HTTP 529. Your streaming code must handle an error mid-stream, and a retry after the first token would duplicate text on the client.

Structured output: from "please reply in JSON" to a schema

The old approach was to ask for JSON in the prompt and hope. The API now supports structured outputs: you pass a JSON schema in output_config.format and the model's reply is constrained to it. The Python SDK wraps this as client.messages.parse(..., output_format=MyPydanticModel) and gives you response.parsed_output. Spring AI's .entity(MyRecord.class) derives a JSON schema from your record (via BeanOutputConverter) and maps the reply back with Jackson. It is the same idea as @RequestBody binding, but on the model's output.

Schema limits matter: objects need additionalProperties: false, and numeric or string-length constraints like minimum or maxLength are not enforced by the API (the SDK moves them into descriptions and validates locally). Enums are supported, which is what you want for labels such as risk levels.

Errors you must plan for

HTTPtypeRetry?
400invalid_request_errorNo. Fix the request (bad schema, unsupported parameter, conversation not ending with a user turn).
401 / 403authentication_error / permission_errorNo. Page someone.
413request_too_largeNo. The Messages API limit is 32 MB.
429rate_limit_errorYes, with backoff, honouring retry-after. A spend-cap 429 has no retry-after and will keep failing.
500api_errorYes, with exponential backoff
504timeout_errorYes, but prefer streaming for long outputs
529overloaded_errorYes, with backoff and jitter; consider falling back to another model

The official SDKs already retry connection errors, 429 and 5xx twice by default with exponential backoff and honour retry-after. You tune that with max_retries (Python) or spring.ai.anthropic.max-retries (Spring AI). Every response also carries a request-id header; in Python it is message._request_id. Log it: it is what support asks for.

One modern-model gotcha

On the newest Claude models (Sonnet 5.5, Opus 5.5), temperature and top_p are deprecated and only the default is accepted, assistant-message prefill returns a 400, and forced tool choice (any/tool) is not supported. Older tutorials that set temperature=0 or prefill { to force JSON will fail. Use structured outputs instead, and control depth and cost with output_config.effort (low, medium, high, …).

Step 2: first call, with latency and token logging

import logging
import time

import anthropic

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
log = logging.getLogger("llm")

client = anthropic.Anthropic(max_retries=3, timeout=60.0)  # reads ANTHROPIC_API_KEY

SYSTEM = "You are a contracts analyst at an e-signing company. Answer in at most three sentences."

start = time.perf_counter()
message = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=512,
    system=SYSTEM,
    messages=[{"role": "user", "content": "What does a limitation of liability clause do?"}],
)
latency_ms = (time.perf_counter() - start) * 1000

text = "".join(block.text for block in message.content if block.type == "text")
print(text)
u = message.usage
log.info(
    "request_id=%s model=%s stop=%s in=%d out=%d cache_read=%s latency_ms=%.0f",
    message._request_id, message.model, message.stop_reason,
    u.input_tokens, u.output_tokens, u.cache_read_input_tokens, latency_ms,
)

Step 3: streaming, with time to first token

import time

import anthropic

client = anthropic.Anthropic()

start = time.perf_counter()
first_token_ms = None
with client.messages.stream(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    system="You explain contract clauses to non-lawyers.",
    messages=[{"role": "user", "content": "Explain an indemnity clause with one example."}],
) as stream:
    for text in stream.text_stream:
        if first_token_ms is None:
            first_token_ms = (time.perf_counter() - start) * 1000
        print(text, end="", flush=True)
    final = stream.get_final_message()

total_ms = (time.perf_counter() - start) * 1000
print(f"\n\nttft_ms={first_token_ms:.0f} total_ms={total_ms:.0f} "
      f"in={final.usage.input_tokens} out={final.usage.output_tokens} stop={final.stop_reason}")

Expected: text appears progressively, then a line like ttft_ms=610 total_ms=5480 in=31 out=290 stop=end_turn. get_final_message() returns the same Message object a non-streaming call would, so you still get usage. TTFT is the number users feel; total latency is what your thread pool feels.

Step 4: prompt templates

Keep prompts as named, versioned constants, and fill them through a function that fails if a variable is missing. Wrap user content in XML-style tags so the model can tell instructions from data.

from string import Template

CLASSIFY_V2 = Template("""Classify the contract clause below.

<clause id="$clause_id">
$clause_text
</clause>

Return the clause type and a risk level for the party "$party".""")


def render_classify(clause_id: str, clause_text: str, party: str) -> str:
    # substitute() raises KeyError on a missing variable: fail loudly, never send a half-filled prompt
    return CLASSIFY_V2.substitute(clause_id=clause_id, clause_text=clause_text.strip(), party=party)


if __name__ == "__main__":
    out = render_classify("c-17", "  The Supplier's total liability shall not exceed fees paid in 12 months. ", "Customer")
    assert '<clause id="c-17">' in out and "$" not in out
    try:
        CLASSIFY_V2.substitute(clause_id="x")
        raise AssertionError("expected KeyError")
    except KeyError:
        pass
    print(out)

uv run templates.py prints the rendered prompt and the self-check passes. In real projects, store the template id (CLASSIFY_V2) in your logs so you can correlate quality regressions with prompt changes.

Step 6: retries beyond the SDK

For an interactive request, the SDK's built-in retries are enough: raise max_retries a little and set a timeout. For a batch job that classifies 50,000 clauses overnight, wrap calls in an outer backoff with full jitter so that, after an overload, thousands of workers do not retry in lockstep:

import logging
import random
import time
from typing import Callable, TypeVar

import anthropic
import httpx

T = TypeVar("T")
log = logging.getLogger("llm.retry")

RETRYABLE = (anthropic.RateLimitError, anthropic.OverloadedError,
             anthropic.InternalServerError, anthropic.APIConnectionError)


def with_backoff(call: Callable[[], T], attempts: int = 5, base: float = 1.0, cap: float = 30.0,
                 sleep: Callable[[float], None] = time.sleep) -> T:
    """Outer retry for batch jobs, on top of the SDK's own retries. Full jitter, honours retry-after."""
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except RETRYABLE as e:
            if attempt == attempts:
                raise
            delay = random.uniform(0, min(cap, base * 2 ** (attempt - 1)))
            response = getattr(e, "response", None)
            retry_after = response.headers.get("retry-after") if response is not None else None
            if retry_after and retry_after.isdigit():
                delay = max(delay, float(retry_after))
            log.warning("attempt=%d error=%s sleeping=%.2fs", attempt, type(e).__name__, delay)
            sleep(delay)
    raise AssertionError("unreachable")


if __name__ == "__main__":
    # Offline self-check: fake a 529 twice, then succeed. No API key, no network.
    req = httpx.Request("POST", "https://api.anthropic.com/v1/messages")
    overloaded = httpx.Response(529, request=req, headers={"retry-after": "2"})
    calls, slept = [], []

    def flaky() -> str:
        calls.append(1)
        if len(calls) < 3:
            raise anthropic.OverloadedError("Overloaded", response=overloaded, body=None)
        return "ok"

    assert with_backoff(flaky, sleep=slept.append) == "ok"
    assert len(calls) == 3 and all(s >= 2 for s in slept), slept
    print("calls:", len(calls), "sleeps:", slept)

uv run backoff.py runs an offline self-check (no key needed): two fake 529s, then success, with sleeps of at least the retry-after value.

attempt=1 error=OverloadedError sleeping=2.00s
attempt=2 error=OverloadedError sleeping=2.00s
calls: 3 sleeps: [2.0, 2.0]
Retry amplification

SDK retries (3) inside an outer loop (5) inside a caller that also retries (3) means up to 4 × 5 × 3 = 60 requests for one user action during an outage. Retry at one layer only, cap total time, and add a concurrency limit for batch jobs. This is the same rule you apply to Feign or WebClient chains between microservices.

The service. ChatClient.Builder is auto-configured; you build one ChatClient with a default system prompt and reuse it (it is thread-safe, like RestClient).

package com.example.clauses;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicBoolean;

import com.anthropic.errors.AnthropicIoException;
import com.anthropic.errors.AnthropicServiceException;
import com.anthropic.errors.InternalServerException;
import com.anthropic.errors.RateLimitException;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.metadata.Usage;
import org.springframework.ai.chat.model.ChatResponse;
import org.springframework.resilience.annotation.Retryable;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Flux;
import reactor.util.retry.Retry;

@Service
public class ClauseAiService {

    private static final Logger log = LoggerFactory.getLogger(ClauseAiService.class);

    // Prompt template, versioned in code. {placeholders} are filled with .param(): never concatenate user text in.
    static final String CLASSIFY_V2 = """
            Classify the contract clause below for the party {party}.
            <clause id="{clauseId}">
            {clauseText}
            </clause>
            """;

    private final ChatClient chatClient;

    public ClauseAiService(ChatClient.Builder builder) {
        this.chatClient = builder
                .defaultSystem("You are a contracts analyst at an e-signing company. Be precise and brief.")
                .build();
    }

    // Structured output: Spring AI derives a JSON schema from the record and maps the reply onto it.
    // Outer retry for longer outages; SDK retries (max-retries) already run inside each attempt.
    @Retryable(includes = {RateLimitException.class, InternalServerException.class},
            maxRetries = 2, delay = 2000, multiplier = 2, maxDelay = 10000, jitter = 500)
    public ClauseRisk classify(String clauseId, String clauseText, String party) {
        long start = System.nanoTime();
        ClauseRisk risk = chatClient.prompt()
                .user(u -> u.text(CLASSIFY_V2)
                        .param("clauseId", clauseId)
                        .param("clauseText", clauseText)
                        .param("party", party))
                .call()
                .entity(ClauseRisk.class);
        log.info("llm.classify prompt=CLASSIFY_V2 clauseId={} latencyMs={}", clauseId, (System.nanoTime() - start) / 1_000_000);
        return risk;
    }

    // chatResponse() keeps the metadata: model, token usage, rate-limit info.
    public String summarise(String clauseText) {
        long start = System.nanoTime();
        ChatResponse response = chatClient.prompt()
                .user(u -> u.text("Summarise this clause for a non-lawyer in two sentences:\n{text}").param("text", clauseText))
                .call()
                .chatResponse();
        Usage usage = response.getMetadata().getUsage();
        log.info("llm.summarise model={} inTokens={} outTokens={} latencyMs={}", response.getMetadata().getModel(),
                usage.getPromptTokens(), usage.getCompletionTokens(), (System.nanoTime() - start) / 1_000_000);
        return response.getResult().getOutput().getText();
    }

    // Streaming: a Flux of text chunks. Retry only if nothing was sent yet, or the client sees duplicated text.
    public Flux<String> explain(String clauseText) {
        AtomicBoolean started = new AtomicBoolean();
        return chatClient.prompt()
                .user(u -> u.text("Explain this clause to a non-lawyer, with one example:\n{text}").param("text", clauseText))
                .stream()
                .content()
                .doOnNext(chunk -> started.set(true))
                .retryWhen(Retry.backoff(2, Duration.ofSeconds(1)).maxBackoff(Duration.ofSeconds(8))
                        .filter(e -> !started.get() && isTransient(e)));
    }

    static boolean isTransient(Throwable e) {
        for (Throwable t = e; t != null; t = t.getCause()) {
            if (t instanceof AnthropicServiceException ase) {
                int status = ase.statusCode();
                return status == 429 || status >= 500;   // 529 overloaded is >= 500
            }
            if (t instanceof AnthropicIoException) {
                return true;
            }
        }
        return false;
    }
}

What each method shows:

  • classify: a template with {placeholders} filled by .param(), and .entity(ClauseRisk.class) for typed output. Spring Framework 7's @Retryable adds an outer retry with exponential backoff and jitter. includes matches the thrown exception type; if your Spring AI version wraps SDK exceptions, list the wrapper type, or simply rely on max-retries.
  • summarise: .chatResponse() instead of .content() keeps the metadata, so you can log getPromptTokens() and getCompletionTokens() along with the model and latency.
  • explain: .stream().content() returns Flux<String>. Reactor's retryWhen retries only if no chunk has been emitted yet.

The controller, with Bean Validation at the trust boundary (cap clause length so one request cannot send a 32 MB prompt), and the configuration that switches on @Retryable:

package com.example.clauses;

import jakarta.validation.Valid;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.MediaType;
import org.springframework.resilience.annotation.EnableResilientMethods;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import reactor.core.publisher.Flux;

@RestController
@RequestMapping("/api/clauses")
public class ClauseController {

    public record ClauseRequest(@NotBlank String clauseId, @NotBlank @Size(max = 20_000) String clauseText,
                                @NotBlank String party) { }

    private final ClauseAiService ai;

    public ClauseController(ClauseAiService ai) {
        this.ai = ai;
    }

    @PostMapping("/classify")
    public ClauseRisk classify(@Valid @RequestBody ClauseRequest req) {
        return ai.classify(req.clauseId(), req.clauseText(), req.party());
    }

    @PostMapping(value = "/explain", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public Flux<String> explain(@Valid @RequestBody ClauseRequest req) {
        return ai.explain(req.clauseText());
    }

    @Configuration
    @EnableResilientMethods
    static class ResilienceConfig { }
}

Production logging checklist
  • Log: request id, model, prompt template id and version, input/output/cache tokens, TTFT, total latency, stop_reason, retry count, tenant id (from the JWT, never from the request body).
  • Do not log raw contract text or personal data by default; log a hash or the document id instead.
  • Export tokens and latency as Micrometer metrics with model and template tags; alert on the rate of max_tokens stops and 429s.

04How this shows up in interviews

Why stream, and what do you measure?

Streaming cuts perceived latency: the user reads the first words after TTFT (often under a second) instead of waiting for the whole generation. Measure TTFT, total latency, and output tokens per second separately. Streaming also avoids idle-connection timeouts on long outputs, which is why the docs recommend it for large max_tokens.

What is the difference between 429 and 529, and how do you handle each?

429 rate_limit_error means your organisation hit its own limit (requests, tokens, or spend). Back off honouring retry-after, smooth traffic with a client-side limiter, and if it is a spend cap, stop retrying. 529 overloaded_error means the API is overloaded for everyone. Back off with jitter and, for user-facing paths, consider a fallback model. Both are retried by the SDK by default.

Is retrying an LLM call safe? Is it idempotent?

A plain generation has no side effects, so retrying is safe for correctness, but it is not idempotent in output (you may get different text) and you pay for every attempt that produced tokens. If the call drives side effects (tool calls that write data), make those tools idempotent with keys. Never retry a stream after tokens have reached the client.

How do you get reliable JSON out of a model?

Use structured outputs with a JSON schema (output_config.format, or messages.parse with a Pydantic model; .entity() in Spring AI), use enums for labels, still validate on receipt, and check stop_reason is not max_tokens. Prompt-only "reply in JSON" is a fallback, not a design.

Your LLM endpoint p99 is 12 seconds. What do you look at?

Output token count first (latency scales with output), then model choice (Haiku for classification), effort level, prompt size (input tokens add prefill time; use prompt caching for a large stable prefix), retries hidden inside the SDK (log retry count), and whether the client could stream. Then set a timeout and a fallback.

What would you log for every LLM call?

Request id, model, prompt template version, tenant, input/output/cache tokens, TTFT and total latency, stop reason, retry count, and the outcome of validation. That lets you compute cost per tenant and per feature, and debug regressions after a prompt change.

Why does a multi-turn chat get more expensive per turn?

The API is stateless, so every turn resends all earlier turns as input tokens. Cost per turn grows roughly linearly with conversation length. Mitigate with prompt caching of the stable prefix, summarising old turns, or trimming history.

How is ChatClient different from calling the SDK directly?

ChatClient is a portable, fluent API on top of a provider's ChatModel: templates with params, advisors (logging, memory, RAG), tools, structured output via converters, and Micrometer observations. The cost is an abstraction layer that may lag new provider features; for those, provider-specific options (for example AnthropicChatOptions with effort or output schema) or the raw SDK are available.

A teammate sets temperature=0 for deterministic output and gets a 400. Why?

On the newest Claude models, temperature and top_p are deprecated and only the default value is accepted. Even where temperature works, 0 does not guarantee identical outputs. For consistency, use structured outputs, clear instructions with examples, and evaluation on a fixed test set.

05Exercise / checkpoint for the capstone

The capstone is a contract Q&A service plus a risky-clause flagger. This lesson gives you its first two endpoints.
