Distributed Job Scheduler

Clients schedule jobs to run at a timestamp or on a cron expression; the system fires each one on time, invokes a callback or worker, retries failures with backoff, and parks poison jobs in a dead-letter queue. The senior answer separates "find due jobs" from "run jobs", explains exactly-once honestly (at-least-once plus idempotent handlers plus fencing), and measures scheduling lag at p99.

01What the interviewer is grading

Razorpay's Lead SWE loop (Nov 2025) opened with "Design job scheduler" (Hire). Another Razorpay HLD framed it as a scheduler service where clients schedule tasks at specific timestamps with callbacks and error / retry handling. InMobi's SDE-2 bar raiser (Dec 2025) wanted high availability, durability, "exactly-once processing (or at least retry mechanisms)", job statuses (Queued, Running, Failed, Completed), SQL vs NoSQL, and retries with DLQs. Postman asked a job executor service (Senior, Feb 2026). Goldman Sachs grows it from in-memory to distributed; Microsoft L63 asked a cloud job scheduler with p99 metrics.

  • Time-based dispatch at scale without scanning the whole table every second, and surviving the "everything at 00:00" spike.
  • No job runs twice concurrently and none is lost when schedulers or workers crash: leases, heartbeats, fencing.
  • Lifecycle and retries: a clear state machine, backoff with jitter, max attempts, DLQ, manual replay.
  • Honest delivery semantics: at-least-once, and what the callback must do to make that safe.
  • Observability: scheduling lag and execution latency as histograms with p99, per tenant.

02Clarify and scope

Questions to ask

  • One-off, recurring (cron), or both? Recurring jobs need "next run" materialisation and catch-up policy after downtime (run once vs run every missed slot).
  • What does "run" mean? An HTTP callback to the client (Razorpay), a message to a queue, or executing code in our workers (Postman's executor, with containers / resource limits)?
  • Precision? Second-level ("within 1 s of the scheduled time at p99") vs minute-level. Precision drives the polling design.
  • Max execution time and payload size? Long jobs need heartbeats; large payloads go to S3 with a reference.
  • Dependencies (DAGs)? Airflow-style workflows are a big extension; confirm if in scope.
  • Multi-tenant? Quotas and fairness so one tenant's 10M jobs at midnight do not starve others.

Functional

  • Schedule at timestamp or cron; cancel, update, pause
  • Execute via callback or worker; capture result
  • Retries with backoff; DLQ; manual replay
  • Query status and history

Non-functional

  • Durable once accepted (no lost jobs)
  • Scheduling lag p99 < 1 s, p999 < 5 s
  • 99.99% availability for scheduling API
  • Scale to 100M jobs/day, 50k fires/s burst

Out of scope

  • Full DAG orchestration (extension)
  • Sandboxing untrusted code (mention containers)
  • Building a message broker

  "schedule": { "type": "AT", "at": "2026-10-07T18:30:00Z" },     // or { "type": "CRON", "cron": "0 */15 * * * *", "tz": "Asia/Kolkata" }

  "concurrencyKey": "merchant:m_42" }           // optional: at most one running per key
→ 201 { "jobId": "j_01J...", "nextRunAt": "2026-10-07T18:30:00Z", "status": "SCHEDULED" }

GET    /v1/jobs/{jobId}                → status, attempts, lastError
GET    /v1/jobs/{jobId}/executions     → history with timings
PATCH  /v1/jobs/{jobId}                → reschedule / pause / resume (version check)
DELETE /v1/jobs/{jobId}                → cancel (no-op if already running; returns state)
POST   /v1/dlq/{executionId}/replay

Callback request to the client:
POST https://svc/internal/settle
X-Job-Id: j_01J...   X-Execution-Id: j_01J...:2026-10-07T18:30:00Z   X-Attempt: 2
→ 2xx success | 4xx permanent failure (no retry) | 5xx / timeout → retry

Idempotency on create stops duplicate schedules from client retries. X-Execution-Id is stable across retries of the same run, so the callee can dedupe; that is how you get effectively-once without pretending the network is reliable.

Postgres (sharded) is the default. The access pattern "due rows for my shard, oldest first, lock them" maps directly to SELECT ... FOR UPDATE SKIP LOCKED on an index, and status transitions need conditional updates. At larger scale use Cassandra / DynamoDB with partition key (time_bucket_minute, shard) so a poller reads exactly one partition per minute per shard; you then need lightweight transactions or a lease table for claims. Splitting definitions (jobs) from occurrences (job_runs) is what makes cron clean: each recurring job keeps one future run row, created when the previous one is claimed.

06High-level architecture

Clients→ Scheduler APIvalidate, idempotency→ Job storejobs + job_runs, sharded
Job store→ Dispatchersone owner per shard, poll due runs→ Timing wheelnext ~60 s in memory→ Ready queueKafka / SQS
Ready queue→ Workerslease, heartbeat, execute→ TargetsHTTP callback / handler · DLQ · Metricslag, duration histograms
CoordinatorZooKeeper / etcd / Kafka group→ Shard → dispatcher assignment

Figure: scheduling (finding due work) is decoupled from execution (doing the work) by a queue, so slow callbacks never delay dispatch.

  • Scheduler API validates cron and target allow-list, stores the job and its first run row in one transaction, computes the shard as hash(job_id) % N (N = e.g. 1,024 logical shards).
  • Dispatchers each own a set of shards (assigned by a coordinator; a Kafka consumer group or etcd leases work). Every second, per shard, they claim runs due in the next window and put them on an in-memory timing wheel; at the exact due time they publish to the ready queue.
  • Ready queue absorbs bursts and lets workers scale independently. SQS visibility timeouts or Kafka with a per-run lease give redelivery when a worker dies.
  • Workers mark RUNNING with a lease, heartbeat for long jobs, call the target with timeouts, then record SUCCEEDED / RETRY_WAIT / DEAD. Retry is just a new due_at on the same run row, so it flows back through the dispatcher.
  • Metrics: scheduling lag (dispatched_at − due_at), queue wait, execution duration, success rate, DLQ depth, all per tenant.

07Deep dives

7.1 Finding due jobs without a full scan

-- per shard, every second, by that shard's single owner (plus SKIP LOCKED as a safety net)
WITH due AS (
  SELECT run_id FROM job_runs
  WHERE shard = ANY(:myShards) AND status = 'SCHEDULED' AND due_at <= now() + interval '60 seconds'
  ORDER BY due_at
  LIMIT 5000
  FOR UPDATE SKIP LOCKED)
UPDATE job_runs r SET status = 'QUEUED', lease_owner = :me, fencing_token = fencing_token + 1
FROM due WHERE r.run_id = due.run_id
RETURNING r.run_id, r.due_at, r.fencing_token;

The index on (shard, status, due_at) makes this a range read of only due rows. Claiming 60 s ahead and holding runs on a hierarchical timing wheel (Kafka and Netty use them) gives sub-second precision without polling the DB every 100 ms. If the dispatcher dies, runs stuck in QUEUED with an old lease are reclaimed by the new shard owner. Alternatives: Redis sorted set by due time (ZRANGEBYSCORE + Lua claim) for near-term jobs with the DB as source of truth; or Cassandra minute buckets read once per minute. Dropbox's ATF uses the same split: a task store indexed by scheduled time and status, a Store Consumer that polls it every ~2 s and pushes ready tasks onto SQS, and Controller / Executor workers that pull and heartbeat. It runs ~9,000 tasks/s with 95% starting within 5 s of their scheduled time, a useful real SLO to quote.

7.2 Exactly-once: what you can actually promise

InMobi's interviewer offered "exactly-once (or at least retry mechanisms)". The honest answer: exactly-once execution of an external side effect is impossible when the worker can crash after the callback succeeds but before recording it. Deliver at-least-once and make duplicates harmless:

  1. Single claimant. Conditional update status: QUEUED → RUNNING WHERE fencing_token = :t; a second worker with the same message gets zero rows and drops it.
  2. Leases with heartbeats. RUNNING carries lease_until; the worker extends it every 10 s. A reaper requeues runs whose lease expired.
  3. Fencing tokens. A paused worker (long GC) whose lease expired might wake and write a result. The token increments on every claim; writes with an older token are rejected. Pass the token to downstream systems that support it.
  4. Idempotent targets. The callee dedupes on X-Execution-Id. This is the part that makes it effectively-once end to end.

7.3 Retries, backoff and DLQ

  • Classify: 2xx success; 4xx permanent (except 408 / 429) → DEAD immediately; 5xx, timeouts, connection errors → retry.
  • Backoff: delay = min(maxMs, initialMs × 2^attempt) with full jitter (random(0, delay)) so 50k failures at 00:00 do not all retry at 00:00:02. Honour Retry-After.
  • After maxAttempts, mark DEAD, publish to the DLQ topic with the last error and payload ref, alert the owning team. Replay API re-creates the run with attempt reset.
  • Per-target circuit breaker: if a tenant's callback endpoint is down, stop hammering it; park its runs in RETRY_WAIT and let the breaker probe.

7.4 From in-memory to distributed (Goldman Sachs progression)

Stage 1ScheduledThreadPoolExecutor or a DelayQueue / PriorityQueue ordered by due time, a worker pool, a ConcurrentHashMap of job states. Lost on restart.
Stage 2Persist jobs to a DB; on startup load the next window into the priority queue. Single node, durable.
Stage 3Two nodes for HA: leader election (DB advisory lock, ZooKeeper, etcd lease); the standby takes over. Quartz clustered mode does roughly this with row locks.
Stage 4Throughput beyond one leader: shard the job space, assign shards to dispatchers, split execution onto a queue and worker fleet.
Stage 5Multi-tenant fairness, per-tenant quotas, DAGs, multi-region.

Walking the interviewer through this ladder, naming the failure each stage fixes, is exactly what the "in-memory → distributed" framing is grading.

7.5 p99 metrics (Microsoft)

Define the SLIs first: scheduling lag = start time − due time; end-to-end latency = completion − due; execution duration; success rate; queue depth. Record them as histograms (Micrometer timers with percentile histograms to Prometheus, or HdrHistogram), not as averages. Percentiles cannot be averaged across hosts; aggregate the histogram buckets and then compute histogram_quantile(0.99, ...). Alert on SLO burn rate (e.g. lag p99 > 1 s for 5% of the error budget in an hour), and break down by tenant and shard to find the hot one. The main lag driver is the burst at round times, which is why the dispatcher pre-claims ahead and the queue decouples workers.

08Scaling, failure handling and consistency

  • Midnight spike. Pre-claim 60 s ahead, spread with the timing wheel, scale workers on queue depth (KEDA / HPA on lag), and offer jitter windows to clients ("run between 00:00 and 00:05").
  • Hot tenant. Per-tenant token buckets in the dispatcher; weighted fair queuing across tenants; separate queues for premium tiers.
  • Dispatcher failure. Coordinator reassigns its shards within seconds; the new owner reclaims QUEUED runs with expired leases. Duplicates are blocked by fencing and idempotency.
  • Database. Sharded Postgres with a synchronous standby; partition executions by day and drop old partitions instead of deleting rows. 10×: more logical shards per DB, more DBs. 100×: move job_runs to Cassandra time buckets.
  • Clock skew. Only the DB clock (now()) or a single dispatcher's clock decides due-ness for a shard; never compare client clocks.
  • Cron correctness. Store timezone; handle DST (skip or double the 2 a.m. run by policy); after downtime apply the catch-up policy instead of firing hundreds of missed runs.
  • Multi-region. Active-passive per shard set: the job store replicates; only one region dispatches a shard. Active-active dispatch needs global leases and is rarely worth it.

10Follow-up questions interviewers asked

How do you guarantee a job is not executed twice?

You guarantee it is not claimed twice (conditional update with a fencing token, leases) and that duplicate execution is harmless (stable execution id passed to an idempotent callee). True exactly-once side effects are impossible if the worker can crash between the call and the commit.

SQL or NoSQL for job storage?

SQL by default: due-job queries are indexed range scans, claiming needs row locks or conditional updates, and status queries are relational. Move occurrences to a wide-column store with time-bucket partitions only when pending rows reach hundreds of millions and write rates exceed what sharded SQL handles.

A worker picks a job and dies. What happens?

Its lease stops being renewed. The reaper (or the queue's visibility timeout) returns the run to SCHEDULED with attempt + 1 and a new fencing token. If the old worker comes back, its result write fails the token check.

Ten million jobs are due at midnight. Walk me through it.

Dispatchers pre-claim from 23:59 onwards into timing wheels, publish at 00:00 in batches, the queue buffers, workers autoscale on lag, and per-tenant limits prevent one tenant consuming everything. Lag p99 will rise; we either accept a stated SLO for bursts or ask clients to schedule with a jitter window.

How do you implement recurring jobs?

Keep the definition in jobs and exactly one future run in job_runs. When a run is claimed, compute the next fire time from the cron in the job's timezone and insert the next run (unique on job_id + scheduled_for) in the same transaction. Missed slots follow the catch-up policy.

How would you add job dependencies (DAG)?

Store edges; a run becomes SCHEDULED only when all parents SUCCEEDED (a counter of pending parents decremented on parent completion). Failure policy per edge: skip, fail downstream, or retry. At that point recommend Airflow or Temporal rather than rebuilding them.

11Mistakes that got candidates rejected

Rejected for this
  • A single cron box polling SELECT * FROM jobs WHERE run_at <= now() with no sharding, no claim, and no answer for what happens when it dies.
  • Claiming exactly-once without leases, fencing or idempotent callbacks; or never mentioning a DLQ (InMobi asked for it directly).
  • Executing jobs inside the dispatcher, so one slow callback delays every other job.
  • Retrying immediately with no backoff or jitter, creating retry storms.
  • "We'll monitor average latency" for the Microsoft p99 question; averaging percentiles across hosts.
