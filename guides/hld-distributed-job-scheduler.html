Distributed Job Scheduler

Design a scheduler that runs 100M jobs a day on time. It must retry failures safely, and never lose a job when a machine dies.

Time-box: 45–60 min Seen: Razorpay ×2, InMobi, Postman, Goldman Sachs, Microsoft, 2025–26
RazorpayInMobiPostmanGoldman SachsMicrosoft
In 30 seconds
  • Keep "finding jobs that are due" (dispatchers) apart from "running jobs" (workers). Put a queue between them.
  • Find due jobs with a database index, and claim them so no one else grabs them. Hold the next 60 s of jobs in memory, sorted by time.
  • A job may run more than once. Make that safe with time-limited claims, claim numbers that block stale workers, and callbacks that ignore repeats.
  • Measure how late jobs start, as a 99th-percentile figure, for each customer.
Picture it

Think of Mumbai's dabbawalas. Sorters at the station (dispatchers) only decide which tiffin goes on which train, at what time. Delivery runners (workers) carry them. If a runner falls sick, the tiffin goes to another runner. The office checks the code, so nobody eats lunch twice.

Words you'll see
Dispatcher
The part that finds jobs that are due and puts them on the ready queue. It does not run them.
Worker
The part that takes a job from the queue and runs it, usually by calling the customer's URL.
Lease
A claim on a job that expires, like "Worker A owns this until 18:30:30". If A goes silent, the job is freed.
Heartbeat
A regular "I'm still working" signal. Each one extends the lease.
Fencing token
A claim number that goes up by one each time the job is claimed. A worker holding an old number is rejected.
Idempotent
Running the same thing twice has the same effect as once. A settlement job that runs twice must not settle twice.
DLQ
Dead-letter queue: a separate parking area for jobs that keep failing, so a person can look at them.
p99
99 out of 100 cases are faster than this. "Lag p99 under 1 s" means only 1 in 100 jobs starts more than 1 s late.

01What the interviewer is grading

Time-based dispatch

Find due jobs without scanning the whole table every second. Survive "everything at midnight".

None twice, none lost

Schedulers and workers crash. Handle it with leases, heartbeats and fencing tokens.

Lifecycle and retries

A clear set of statuses. Growing, randomised waits between retries. A retry limit, a DLQ and a way to re-run.

Honest semantics

Jobs run at least once. Explain what the callback must do to make repeats safe.

Observability

How late jobs start and how long they run, as p99 figures, for each customer.

Go deeper: what the reports said

Razorpay's Lead SWE loop (Nov 2025) opened with "Design job scheduler", and the result was Hire. Another Razorpay design round framed it as a scheduler service. Clients schedule tasks at exact times, with callbacks and error and retry handling. InMobi's SDE-2 bar raiser (Dec 2025) asked for several things. High availability and durability. "Exactly-once processing (or at least retry mechanisms)". Job statuses (Queued, Running, Failed, Completed). SQL vs NoSQL. Retries with DLQs. Postman asked for a job executor service (Senior, Feb 2026). Goldman Sachs grows it from in-memory to distributed. Microsoft L63 asked for a cloud job scheduler with p99 metrics.

  • Running jobs on time at scale, without scanning the whole table every second, and surviving the "everything at 00:00" spike.
  • No job runs twice at the same time, and none is lost when schedulers or workers crash. The tools: leases, heartbeats, fencing.
  • Lifecycle and retries: a clear state machine, backoff with jitter, a retry limit, a DLQ and manual re-run.
  • Honest delivery promise: at-least-once, and what the callback must do to make that safe.
  • Observability: how late jobs start and how long they take, as histograms with p99, per customer.

02Clarify and scope

Functional

  • Schedule at a time or on a repeating cron schedule; cancel, change, pause
  • Run by calling a URL or by a worker; save the result
  • Retries with growing waits; DLQ; manual re-run
  • Look up status and history

Non-functional

  • Once accepted, a job is never lost
  • Start delay: 99 in 100 under 1 s, 999 in 1,000 under 5 s
  • Scheduling API up 99.99% of the time
  • Scale to 100M jobs a day, and bursts of 50k per second

Out of scope

  • Full workflows with dependencies (DAGs, an extension)
  • Safely running untrusted code (mention containers)
  • Building a message broker
Go deeper: six questions to ask first
  • One-off, repeating (cron), or both? Repeating jobs need their "next run" created ahead of time. They also need a catch-up rule after downtime: run once, or run every missed slot?
  • What does "run" mean? An HTTP call to the client (Razorpay)? A message to a queue? Or running code in our own workers (Postman's executor, with containers and resource limits)?
  • How precise? To the second ("99 in 100 start within 1 s of the scheduled time") or to the minute? Precision shapes how often you check for due jobs.
  • Longest run time and largest payload? Long jobs need heartbeats. Large payloads go to S3, and the job keeps a link.
  • Dependencies between jobs (DAGs)? Airflow-style workflows are a big extension. Confirm whether they are in scope.
  • Many customers (multi-tenant)? You need quotas and fairness. One customer's 10M midnight jobs must not starve everyone else.

Go deeper: API notes, data model and each component

The idempotency key on create stops a client's retry from scheduling the job twice. X-Execution-Id stays the same across retries of the same run, so the receiving service can drop repeats. That is how you get "effectively once" without pretending the network never fails.

Sharded Postgres is the default. The access pattern is "due rows for my shard, oldest first, lock them". That maps directly to SELECT ... FOR UPDATE SKIP LOCKED on an index. Status changes need conditional updates, which SQL does well. At larger scale, use Cassandra or DynamoDB with partition key (time_bucket_minute, shard). Then a poller reads exactly one partition per minute per shard. But you need lightweight transactions or a lease table for claims. Keeping definitions (jobs) apart from occurrences (job_runs) makes cron clean. Each repeating job keeps one future run row. The next one is created when the current one is claimed.

  • Scheduler API checks the cron and that the target URL is allowed. It saves the job and its first run row in one transaction. It picks the shard as hash(job_id) % N, with N being e.g. 1,024 logical shards.
  • Dispatchers each own a set of shards, handed out by a coordinator. A Kafka consumer group or etcd leases can do this. Every second, for each shard, they claim runs due in the next window. They put them on an in-memory timing wheel. At the exact due time, they publish to the ready queue.
  • Ready queue absorbs bursts and lets workers scale on their own. If a worker dies, the job comes back: SQS does this with visibility timeouts, Kafka with a lease per run.
  • Workers mark the run RUNNING with a lease. They send heartbeats for long jobs. They call the target with a timeout. Then they record SUCCEEDED, RETRY_WAIT or DEAD. A retry is just a new due_at on the same run row, so it flows back through the dispatcher.
  • Metrics: start delay (dispatched_at − due_at), time waiting in the queue, run time, success rate and DLQ size. All per customer.

06Deep dives

6.1 Finding due jobs without a full scan

18:2818:29:4018:30:0018:30:0018:30:5518:31:2019:00

With an index on (shard, status, due_at), each check reads only the rows that are due. Here it is 18:29:01, and we look 60 s ahead. SKIP LOCKED lets several claimers work in parallel. Each one skips rows another claimer has already locked.

Show the claim query
-- per shard, every second, by that shard's single owner (plus SKIP LOCKED as a safety net)
WITH due AS (
  SELECT run_id FROM job_runs
  WHERE shard = ANY(:myShards) AND status = 'SCHEDULED' AND due_at <= now() + interval '60 seconds'
  ORDER BY due_at
  LIMIT 5000
  FOR UPDATE SKIP LOCKED)
UPDATE job_runs r SET status = 'QUEUED', lease_owner = :me, fencing_token = fencing_token + 1
FROM due WHERE r.run_id = due.run_id
RETURNING r.run_id, r.due_at, r.fencing_token;

Claim 60 s ahead + timing wheel usual pick

  • Under-a-second precision, without querying the DB every 100 ms
  • A hierarchical timing wheel, as used in Kafka and Netty

Default.

Poll the DB every 100 ms

  • 10× the query load
  • Still bursty at 00:00

Small scale only.

Go deeper: alternatives and Dropbox's real numbers

The index on (shard, status, due_at) turns this into a range read of only the due rows. Claim 60 s ahead and hold the runs on a hierarchical timing wheel. It works like a clock face of time slots, and Kafka and Netty both use it. This gives under-a-second precision without querying the DB every 100 ms. If the dispatcher dies, runs stuck in QUEUED with an old lease are reclaimed by the shard's new owner. There are alternatives. One is a Redis sorted set by due time for near-term jobs (ZRANGEBYSCORE plus a Lua script to claim). The DB stays the source of truth. Another is Cassandra minute buckets, read once per minute. Dropbox's ATF uses the same split. A task store is indexed by scheduled time and status. A Store Consumer checks it every ~2 s and pushes ready tasks onto SQS. Controller and Executor workers pull tasks and send heartbeats. It runs ~9,000 tasks per second, with 95% starting within 5 s of their scheduled time. That is a useful real target (SLO) to quote.

6.2 Exactly-once: what you can actually promise

TimeWorker AWorker BCallee / store
t1calls settle, gets 2xxmoney settled
t2crashes before saving the resultrun still RUNNING
t3claim expired → runs againsecond settle, unless the callee drops repeats

Running an outside action exactly once is impossible here. So run it at least once, and make repeats harmless. Four tools do this.

Single claimant

Only one worker can move a job to RUNNING. A second worker's update changes nothing: QUEUED → RUNNING WHERE fencing_token = :t.

Leases + heartbeats

The worker extends its claim (lease_until) every 10 s. A reaper puts back jobs whose claim expired.

Fencing tokens

The claim number goes up on every claim. Any write with an older number is rejected.

Idempotent targets

The service we call ignores repeats of the same X-Execution-Id. End to end, the job takes effect once.

Go deeper: the full exactly-once argument

InMobi's interviewer offered "exactly-once (or at least retry mechanisms)". The honest answer: running an outside action exactly once is impossible. A worker can crash after the callback succeeds but before saving that fact. So deliver at least once, and make repeats harmless.

  1. Single claimant. A conditional update, status: QUEUED → RUNNING WHERE fencing_token = :t. A second worker with the same message changes zero rows and drops it.
  2. Leases with heartbeats. A RUNNING job carries lease_until. The worker extends it every 10 s. A reaper puts back runs whose lease expired.
  3. Fencing tokens. A worker can freeze (a long GC pause) and lose its lease. When it wakes, it might still try to write a result. The token goes up on every claim, and writes with an older token are rejected. Pass the token on to other systems that can check it.
  4. Idempotent targets. The callee drops repeats by X-Execution-Id. This is the part that makes it "effectively once" from end to end.

6.3 Retries, backoff and DLQ

One run that keeps failing (maxAttempts 5, initial 2 s)
Go deeper: retry rules in full
  • Sort the reply. 2xx is success. 4xx (except 408 and 429) is a permanent error, so mark DEAD at once. 5xx, timeouts and connection errors are retried.
  • Backoff: delay = min(maxMs, initialMs × 2^attempt), with full jitter (random(0, delay)). Then 50k failures at 00:00 do not all retry at 00:00:02. Respect Retry-After.
  • After maxAttempts, mark DEAD. Publish to the DLQ topic with the last error and payload link, and alert the owning team. The re-run API creates the run again with the attempt count reset.
  • Circuit breaker per target: if a customer's callback endpoint is down, stop hammering it. Park its runs in RETRY_WAIT, and let the breaker test the endpoint now and then.

6.4 From in-memory to distributed (Goldman Sachs progression)

Each stage fixes the previous stage's failure
Go deeper: the original stage ladder
Stage 1ScheduledThreadPoolExecutor, or a DelayQueue / PriorityQueue sorted by due time. Add a worker pool and a ConcurrentHashMap of job states. Everything is lost on restart.
Stage 2Save jobs to a database. On startup, load the next window into the priority queue. One machine, but nothing is lost.
Stage 3Two machines for high availability. Elect a leader with a DB advisory lock, ZooKeeper or an etcd lease. The standby takes over. Quartz clustered mode does roughly this with row locks.
Stage 4More work than one leader can handle. Split the jobs into shards, hand shards to dispatchers, and move running onto a queue and worker fleet.
Stage 5Fairness between customers, per-customer quotas, job dependencies (DAGs), several regions.

Walk the interviewer up this ladder, and name the failure each stage fixes. That is exactly what the "in-memory to distributed" framing is grading.

Histograms, merged then quantiled correct

  • Record timings as histograms: counts per time range (Micrometer to Prometheus, or HdrHistogram)
  • Add up the buckets from all servers, then compute p99: histogram_quantile(0.99, …)

Alert when the error budget is being used up too fast. Break down by customer and shard.

Averages, or averaged p99s

  • Averages hide the slow tail
  • You cannot average percentiles across servers

Never.

Go deeper: SLIs and alerting in full

First define what you measure (the SLIs, service level indicators). Start delay (lag) = start time − due time. End-to-end time = completion − due. Run time. Success rate. Queue size. Record them as histograms, not averages. Use Micrometer timers with percentile histograms sent to Prometheus, or HdrHistogram. You cannot average percentiles across servers. Add up the histogram buckets first, then compute histogram_quantile(0.99, ...). Alert on how fast the error budget is being spent (the SLO burn rate). For example: lag p99 > 1 s, using 5% of the error budget in an hour. Break it down by customer and shard to find the busy one. The main cause of lag is the burst at round times. That is why the dispatcher claims ahead and the queue separates workers.

07Design choices

Postgres + SKIP LOCKED usual pick

  • Simple, transactional, easy status queries
  • Constant checking adds load; each shard is limited by one server's size

Up to ~10k jobs per second, with sharding.

Redis ZSET as the timer

  • Very fast and precise
  • Limited by memory; durability depends on its append-only file (AOF); the DB must stay the truth

A cache of the next few minutes, in front of the DB.

Cassandra time buckets

  • Huge scale, cheap writes
  • No SKIP LOCKED; claims need lightweight transactions or a lease service

Hundreds of millions of waiting runs.

Kafka delayed topics

  • No database checks for retries
  • Fixed delays only; any exact time is awkward

Retry levels (1 m, 10 m, 1 h).

Quartz clustered

  • Ready-made for Spring
  • Database lock contention; not for millions a day

Internal cron inside one service.

Temporal / Cadence

  • Durable timers, retries and workflows built in
  • A new platform to run and learn

Many-step workflows; the "buy, don't build" option.

08Scaling, failure handling and consistency

Midnight spike

Claim 60 s ahead. Add workers as the queue grows (KEDA or HPA). Let clients choose a time range like "00:00–00:05".

Hot tenant

Rate limits per customer, fair sharing between customers, and separate queues for premium customers.

Dispatcher dies

The coordinator hands its shards to another dispatcher within seconds. The new owner reclaims QUEUED jobs with expired claims.

Clock skew

Only the database clock, or the shard owner, decides when a job is due. Never a client's clock.

Cron + DST

Store each job's timezone. Decide what happens when daylight saving skips or repeats an hour. Decide how to catch up after downtime.

Go deeper: full scaling notes
  • Midnight spike. Claim 60 s ahead and spread the work with the timing wheel. Add workers as the queue grows (KEDA or HPA, scaling on lag). Offer clients time windows ("run between 00:00 and 00:05").
  • Hot tenant. Give each customer a token bucket (a simple rate limiter) in the dispatcher. Use weighted fair queuing, so each customer gets a fair share. Use separate queues for premium tiers.
  • Dispatcher failure. The coordinator hands its shards to others within seconds. The new owner reclaims QUEUED runs with expired leases. Fencing tokens and idempotency block duplicates.
  • Database. Sharded Postgres with a synchronous standby copy. Split executions into daily partitions, and drop old partitions instead of deleting rows. At 10×, add logical shards per database, then more databases. At 100×, move job_runs to Cassandra time buckets.
  • Clock skew. Only the database clock (now()), or one dispatcher's clock, decides when a shard's jobs are due. Never compare client clocks.
  • Cron correctness. Store the timezone. Handle daylight saving time (DST) by policy: skip or run twice the 2 a.m. job. After downtime, apply the catch-up rule instead of firing hundreds of missed runs.
  • Multi-region. Active-passive per group of shards. The job store is copied to the other region, but only one region dispatches a shard. Dispatching from both regions needs global leases and is rarely worth it.

09Mistakes that got candidates rejected

Rejected for this
  • One cron machine running SELECT * FROM jobs WHERE run_at <= now(). No sharding, no claiming, and no answer for what happens when it dies.
  • Promising exactly-once without leases, fencing or idempotent callbacks. Or never mentioning a DLQ, which InMobi asked for directly.
  • Running jobs inside the dispatcher, so one slow callback delays every other job.
  • Retrying at once with no growing wait or randomness, which creates retry storms.
  • Answering Microsoft's p99 question with "we'll monitor average latency". Or averaging percentiles across servers.

10Quick check

A worker freezes in a long GC pause and its claim expires. Another worker re-runs the job. The first one wakes up and writes "FAILED". What stops it?

Each claim raises the number. A worker with an old number can no longer save results.

Why should dispatchers not run the callbacks themselves?

A queue between them lets workers grow with the load, while dispatch stays on time.

The interviewer asks for exactly-once execution. What is the best honest answer?

A worker can crash after the action but before saving the result. Only the callee ignoring repeats makes the retry harmless.

You have the p99 start delay from 20 servers. How do you get the p99 for all of them together?

Percentiles cannot be averaged. Combine the full distributions first.

11Follow-up questions interviewers asked

How do you guarantee a job is not executed twice?

You guarantee it is not claimed twice, using a conditional update with a fencing token, and leases. And you make a repeat harmless, by passing a stable execution id to a callee that ignores repeats. A true exactly-once side effect is impossible if the worker can crash between the call and saving the result.

SQL or NoSQL for job storage?

SQL by default. Finding due jobs is an indexed range scan. Claiming needs row locks or conditional updates. Status queries are relational. Move the runs to a wide-column store with time-bucket partitions only at very large scale. That means hundreds of millions of waiting rows, and more writes than sharded SQL can handle.

A worker picks up a job and dies. What happens?

Its lease stops being renewed. The reaper, or the queue's visibility timeout, puts the run back to SCHEDULED. The attempt count goes up by one, and it gets a new fencing token. If the old worker comes back, its result fails the token check.

Ten million jobs are due at midnight. Walk me through it.

From 23:59, dispatchers claim jobs early into their timing wheels. At 00:00 they publish in batches, and the queue absorbs the load. Workers scale up as the queue grows. Per-customer limits stop one customer from taking everything. The p99 start delay will rise. Either agree a separate target for bursts, or ask clients to schedule within a time window.

How do you implement recurring jobs?

Keep the definition in jobs, and exactly one future run in job_runs. When a run is claimed, work out the next time from the cron, in the job's timezone. Insert the next run in the same transaction (unique on job_id + scheduled_for). Missed slots follow the catch-up rule.

How would you add job dependencies (DAG)?

Store the links between jobs. A run becomes SCHEDULED only when all its parents have SUCCEEDED. Keep a counter of unfinished parents, and lower it as each parent completes. Set a failure rule per link: skip, fail the jobs after it, or retry. At that point, recommend Airflow or Temporal instead of rebuilding them.

13Cheat sheet

Cheat sheet
  • Two tables: jobs (definitions) and job_runs (each run), split by hash(job_id) % 1024.
  • Dispatcher per shard: claim 60 s ahead with SKIP LOCKED, hold in a timing wheel, publish to the ready queue.
  • Workers: move QUEUED to RUNNING with a lease and heartbeats. A reaper puts back expired ones.
  • A new fencing token on every claim. The callee ignores repeats of X-Execution-Id.
  • Retry: 4xx goes dead, 5xx retries. Doubling waits with full jitter. After maxAttempts, DLQ and re-run.
  • Cron: one future run row. Handle timezone, daylight saving and catch-up.
  • p99 lag from merged histograms, per customer. Never average percentiles.
  • Ladder: in-memory, then DB, then leader and standby, then shards and a queue, then customers and DAGs.
