01Why interviewers ask this

For a Java backend engineer, Spring is where interviewers check that your experience is real. The questions are short and fast, and a vague answer ("Spring manages the beans") costs more than silence. From the reports:

  • Swiggy: autowiring, IoC, SOLID principles.
  • Paytm: Spring Boot, authentication, SQL.
  • Apple: IoC, Spring MVC versus Spring Boot, OAuth and JWT.
  • Truemeds: Spring Boot fundamentals in a rapid-fire format.
  • PayPal: the hiring-manager round had the candidate build Spring Boot endpoints live. The candidate was rejected for missing exception handling and idempotency. Section 04 shows both.
How to answer rapid-fire

One sentence of definition, one sentence of mechanism, one sentence of "where it bit me / how I use it". Example: "@Transactional is applied by a proxy, so a call from another method in the same class skips it; we hit this when a batch job's inner method never rolled back, and fixed it by moving the method to its own bean."

02Core concepts, from scratch

IoC and dependency injection

Inversion of control: your classes do not create their collaborators; the container (ApplicationContext) creates objects (beans), wires their dependencies, and manages their lifecycle. Dependency injection is how it wires them: through constructors, setters or fields. The payoff is that classes depend on interfaces, are testable with fakes, and cross-cutting behaviour (transactions, security, caching, metrics) can be added by wrapping beans in proxies without changing your code.

@Service
public class EnvelopeService {
    private final EnvelopeRepository repo;          // final: required and immutable
    private final Clock clock;

    public EnvelopeService(EnvelopeRepository repo, Clock clock) {   // single constructor: no @Autowired needed
        this.repo = repo;
        this.clock = clock;
    }
}

Constructor injection is the recommended default: dependencies are explicit and final, the object is never half-built, tests can call new without a container, and circular dependencies fail fast at startup. Field injection (@Autowired private Repo repo;) hides dependencies, needs reflection to test, allows nulls and makes it easy to grow a class with 12 collaborators without noticing. Setter injection is for genuinely optional dependencies.

Figure: lifecycle of a singleton bean. BPP = BeanPostProcessor.

Two consequences people get asked about: the object your other beans receive is often the proxy created in the last post-processing step, not your class; and @PostConstruct runs before that proxy exists, so calling a @Transactional method of the same bean from @PostConstruct runs without a transaction. Use an ApplicationReadyEvent listener for start-up work that needs proxies.

What @SpringBootApplication does

It combines three annotations: @SpringBootConfiguration (a @Configuration), @ComponentScan (scan this package and below) and @EnableAutoConfiguration. Auto-configuration loads the classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports of every jar on the classpath. Each is a @AutoConfiguration class guarded by conditions:

@AutoConfiguration
@ConditionalOnClass(DataSource.class)                 // only if the JDBC classes are on the classpath
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean                         // back off if the app defined its own
    DataSource dataSource(DataSourceProperties props) { ... }
}

Starters (spring-boot-starter-web, -data-jpa, -security) are dependency bundles with no code: they put the right libraries on the classpath so the conditions fire. Other conditions: @ConditionalOnProperty, @ConditionalOnBean, @ConditionalOnWebApplication, @Profile (itself a @Conditional). To see why something did or did not configure: start with --debug for the condition evaluation report, or call /actuator/conditions.

Spring MVC versus Spring Boot (Apple): Spring MVC is the web framework: DispatcherServlet, handler mappings, @Controller, message converters. Spring Boot is an opinionated layer over the whole Spring ecosystem: auto-configuration, starters, embedded Tomcat/Jetty, externalised configuration, Actuator. A Boot web app is a Spring MVC app that configured itself.

03Proxies and transactions internally

Controller→ Proxy of PaymentServiceCGLIB subclass→ TransactionInterceptorbegin / commit / rollback→ PaymentService.pay()your code→ DataSourceconnection bound to thread

Figure: a @Transactional call goes through the proxy; this.otherMethod() inside pay() does not.

Spring AOP creates a proxy around beans that have advice: a JDK dynamic proxy if you ask for interface-based proxying, otherwise (Boot's default) a CGLIB subclass. The proxy's interceptor asks the PlatformTransactionManager to start or join a transaction, binds the connection to the current thread via TransactionSynchronizationManager (a ThreadLocal), calls your method, then commits or rolls back. Everything about @Transactional's behaviour follows from that:

  • Self-invocation: this.inner() calls the target directly, so inner()'s annotation is ignored. Fixes: move the method to another bean (best), inject the bean's own proxy lazily, or use TransactionTemplate programmatically.
  • Visibility: private methods are never intercepted. Since Spring 6.0, protected and package-private methods work for class-based (CGLIB) proxies; interface proxies need public interface methods. Final methods and final classes cannot be proxied by CGLIB.
  • Thread-bound: work done in another thread (@Async, CompletableFuture.supplyAsync, a parallel stream) is outside the transaction.
  • Rollback rules: by default it rolls back on RuntimeException and Error only. A checked exception (an IOException from a vendor call) commits. Use @Transactional(rollbackFor = Exception.class) or throw unchecked. Catching the exception inside the method and not rethrowing also commits.
  • UnexpectedRollbackException: an inner REQUIRED method throws, marks the shared transaction rollback-only, and the outer method catches and carries on; at commit Spring throws UnexpectedRollbackException. Use REQUIRES_NEW or NESTED if the inner work should fail independently.
PropagationBehaviourUse for
REQUIRED (default)Join the current transaction or start oneAlmost everything
REQUIRES_NEWSuspend the current one, start an independent one on a second connectionAudit log or outbox row that must persist even if the caller rolls back. Costs a second pool connection per call; nested in a loop under load it can exhaust Hikari and deadlock the pool.
NESTEDSavepoint inside the current transaction (JDBC only, not JPA's default manager)Partial rollback of one step in a batch

MANDATORYFail if no transaction existsRepository-level methods that must be called inside one

Isolation defaults to the database's level: READ COMMITTED on Postgres, REPEATABLE READ on MySQL InnoDB. Raising it per method (isolation = Isolation.SERIALIZABLE) means you must retry on serialisation failures. readOnly = true is a hint: Hibernate sets flush mode to manual and skips dirty-checking snapshots (less memory and CPU for big reads), the JDBC connection is marked read-only (Postgres runs SET TRANSACTION READ ONLY), and a routing DataSource can send it to a replica. It does not stop you calling a write method.

04Production patterns and gotchas

JPA N+1 and how to fix it

Loading 50 envelopes and then touching envelope.getSigners() on each lazy collection runs 1 query plus 50. It hides in tests with 3 rows and shows up as p99 latency in production. Detect with spring.jpa.properties.hibernate.generate_statistics=true, a datasource-proxy query counter in tests, or APM spans.

public interface EnvelopeRepository extends JpaRepository<Envelope, Long> {
    @Query("select distinct e from Envelope e join fetch e.signers where e.tenantId = :tenantId")
    List<Envelope> findWithSigners(@Param("tenantId") Long tenantId);      // 1 query

    @EntityGraph(attributePaths = "signers")                                  // same, declaratively
    List<Envelope> findByTenantIdAndStatus(Long tenantId, Status status);
}
  • Fetch join with pagination: join fetch on a collection plus Pageable makes Hibernate fetch everything and paginate in memory, logging a warning (HHH000104 in Hibernate 5, HHH90003004 in Hibernate 6). Fix: page the IDs first, then fetch those IDs with the join; or skip the join and set hibernate.default_batch_fetch_size=50 so lazy loads go out as IN (...) batches.
  • Two collection fetch joins on one entity cause a MultipleBagFetchException or a Cartesian product. Fetch one collection per query.
  • For read-only list screens, project into a DTO or interface projection (select new ...Dto(...)): no entities, no dirty checking, only the columns you need.
  • Pagination: Page<T> runs an extra count(*); use Slice<T> when you only need "has next". Deep OFFSET scans skipped rows; for large tables use keyset pagination (where id > :lastId order by id limit 50).

Open session in view

spring.jpa.open-in-view defaults to true (Boot logs a warning about it at start-up). It keeps the persistence context and a database connection open for the whole HTTP request, including view rendering and JSON serialisation, so lazy loading "just works" in controllers. The cost: connections held during slow serialisation or downstream calls, hidden N+1 queries from Jackson walking lazy associations, and pool exhaustion under load. Set it to false, fetch what you need in the service layer, and return DTOs.

Exception handling and idempotency (the PayPal rejection)

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(EnvelopeNotFoundException.class)
    ProblemDetail notFound(EnvelopeNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());   // RFC 9457 body
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail invalid(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(e -> e.getField() + ": " + e.getDefaultMessage()).toList());
        return pd;
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex) {
        log.error("Unhandled", ex);                                                  // log once, here
        return ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR);          // no stack trace to client
    }
}

@PostMapping("/payments")
ResponseEntity<PaymentResponse> pay(@RequestHeader("Idempotency-Key") String key,
                                    @Valid @RequestBody PaymentRequest req) {
    return idempotency.execute(key, req, () -> paymentService.pay(req));
}

Idempotency in one paragraph: the client sends a unique Idempotency-Key per logical operation. The server inserts (tenant_id, key, request_hash, status=IN_PROGRESS) into a table with a unique constraint before doing the work. A duplicate key with the same hash returns the stored response; with a different hash returns 422; while still in progress returns 409. On success store the response; expire keys after 24 hours. The database constraint, not an in-memory check, is what makes it safe across instances. Mention this unprompted whenever you build a POST that moves money or sends a document.

Validation

public record PaymentRequest(
        @NotBlank String payerId,
        @Positive @Digits(integer = 12, fraction = 2) BigDecimal amount,
        @NotNull @Size(min = 3, max = 3) String currency) { }

@Valid on a @RequestBody triggers Bean Validation (Hibernate Validator from spring-boot-starter-validation) and throws MethodArgumentNotValidException → 400. Path variables and request params are validated through method validation (@Validated on the class, or built in for controllers since Spring 6.1). Custom rules: a ConstraintValidator; cross-field rules: a class-level constraint. Validation at the edge does not replace database constraints.

Spring Security filter chain and JWT

Request→ DelegatingFilterProxyservlet filter→ FilterChainProxypicks a SecurityFilterChain→ BearerTokenAuthenticationFilterverify JWT signature, exp, iss→ AuthorizationFilterURL rules→ DispatcherServlet@PreAuthorize on methods

Figure: a request through Spring Security 6 as an OAuth2 resource server.

@Configuration
@EnableMethodSecurity                                   // enables @PreAuthorize
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
                .csrf(csrf -> csrf.disable())                         // stateless API with bearer tokens
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
                .authorizeHttpRequests(a -> a
                        .requestMatchers("/actuator/health/**").permitAll()
                        .anyRequest().authenticated())
                .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))   // JWKS from issuer-uri
                .build();
    }
}
// application.yml: spring.security.oauth2.resourceserver.jwt.issuer-uri: https://auth.example.com

@PreAuthorize("hasAuthority('SCOPE_envelope:write')")
public Envelope create(...) { ... }

JWT basics: header.payload.signature, base64url-encoded, signed not encrypted. Verify the signature with the issuer's public key (RS256/ES256 via JWKS, cached and rotated by kid), then exp, nbf, iss and aud. Keep access tokens short-lived (5–15 minutes) because they cannot be revoked without a denylist; use refresh tokens for longevity. Take tenant and user identity from the validated token, never from a request parameter. OAuth2 is the delegation protocol (authorization code + PKCE for user apps, client credentials for service-to-service); JWT is just the token format often used with it.

Observability with Actuator

  • /actuator/health with liveness and readiness groups for Kubernetes probes. Do not put downstream dependencies in liveness, or a DB blip restarts every pod.
  • Micrometer metrics (http.server.requests, Hikari pool, JVM, custom counters and timers) exported via /actuator/prometheus.
  • Micrometer Tracing (replaced Spring Cloud Sleuth in Boot 3) with an OpenTelemetry or Brave bridge; trace and span IDs in the log pattern.
  • Expose only what you need: management.endpoints.web.exposure.include=health,info,prometheus, on a separate management port, behind auth. /env, /heapdump and /threaddump leak secrets and data.

Virtual threads in Spring Boot 3.2+

spring.threads.virtual.enabled=true on Java 21 runs Tomcat request handling, @Async, the application task executor and scheduling on virtual threads. Good for I/O-heavy services with blocking JDBC and HTTP clients. Caveats: the Hikari pool size is still your real concurrency limit for DB work; on Java 21 avoid synchronized around blocking calls (pinning, fixed in JDK 24); rate-limit downstream calls with a Semaphore because there is no longer a thread pool acting as an accidental limiter; check your libraries' ThreadLocal usage.

05Rapid-fire questions with senior answers

Container and configuration

1. What is IoC and why does Spring use it?

The container creates and wires objects instead of the objects creating their dependencies. It decouples classes from concrete implementations, makes them testable, and lets Spring add behaviour (transactions, security, caching) by proxying beans.

2. BeanFactory versus ApplicationContext?

BeanFactory is the basic DI container with lazy creation. ApplicationContext extends it with eager singleton creation, events, internationalisation, environment and profiles, and automatic registration of BeanPostProcessors. Applications always use ApplicationContext.

3. Constructor or field injection, and why?

Constructor: dependencies are explicit and final, the object is never partially built, unit tests need no container, and cycles fail at start-up. Field injection hides dependencies and needs reflection. With a single constructor, @Autowired is optional.

4. How do you fix a circular dependency?

Spring Boot 2.6+ refuses circular references by default, and constructor-injection cycles never resolve. Fix the design: extract the shared logic into a third bean, or replace the back-call with an application event. Tactical fixes are @Lazy on one constructor parameter (injects a proxy) or setter injection. Setting spring.main.allow-circular-references=true hides the smell.

5. Two beans implement the same interface. How does Spring choose?

It fails with NoUniqueBeanDefinitionException unless you mark one @Primary, use @Qualifier("name") at the injection point, or match by parameter name. Inject List<PaymentGateway> or Map<String, PaymentGateway> to get all of them, which is how you build a strategy registry.

6. @Component versus @Bean?

@Component (and @Service, @Repository, @Controller) marks your own class for component scanning. @Bean is a factory method in a @Configuration class, used for third-party classes or when construction needs logic. In a full @Configuration class, calls between @Bean methods are intercepted by CGLIB and return the singleton; with proxyBeanMethods = false they are plain calls.

7. What does @SpringBootApplication do?

@SpringBootConfiguration + @ComponentScan of the package and below + @EnableAutoConfiguration, which imports the auto-configuration classes listed in each jar's AutoConfiguration.imports file and applies them when their @Conditional checks pass.

8. How does auto-configuration back off when I define my own bean?

Auto-configured beans are usually guarded by @ConditionalOnMissingBean, and auto-configurations are processed after user configuration. If you define a DataSource, the auto-configured one is skipped. --debug or /actuator/conditions shows each decision.

9. What is a starter?

A dependency descriptor that pulls in a consistent set of libraries (for example spring-boot-starter-web brings Spring MVC, Jackson and embedded Tomcat). It contains no logic; it makes the auto-configuration conditions true.

10. How do you write your own auto-configuration?

An @AutoConfiguration class with @ConditionalOnClass/@ConditionalOnProperty guards and @ConditionalOnMissingBean beans, bound to a @ConfigurationProperties class, listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, shipped in a starter. That is how platform teams share an audit-logging or tenant-context library across microservices.

11. How do @Profile and profile-specific configuration work?

spring.profiles.active=prod activates application-prod.yml on top of application.yml and enables beans annotated @Profile("prod"); @Profile("!prod") negates. Use profiles for environment wiring (a fake SMS gateway locally), not for business feature flags. Secrets come from the environment or a vault, not profile files.

12. Singleton bean scope versus the Singleton pattern?

Spring's singleton is one instance per container per bean definition; you can still create others with new or define two beans of the same class. The GoF Singleton is one per class loader. Singleton beans are shared by all threads, so they must be stateless or thread-safe.

13. How do you inject a prototype bean into a singleton?

Plain injection creates it once. Inject ObjectProvider<T> and call getObject() each time, use a @Lookup method, or a scoped proxy.

14. What are BeanPostProcessor and BeanFactoryPostProcessor?

BeanFactoryPostProcessor modifies bean definitions before any bean is created (property placeholder resolution, configuration class parsing). BeanPostProcessor modifies bean instances around initialisation (@Autowired processing, @PostConstruct, AOP proxy creation).

Transactions and data

15. Why did my @Transactional method not roll back?

Usual causes, in order: it threw a checked exception (no rollback by default); the exception was caught inside the method; it was called from the same class (self-invocation bypasses the proxy); the method is private or final; the work ran on another thread; or the table engine does not support transactions.

16. When do you use REQUIRES_NEW?

When a write must commit regardless of the caller's outcome: audit records, failure logs, an idempotency-key status update. It suspends the outer transaction and takes a second connection, so never use it inside a loop on a hot path; it can exhaust the pool.

17. What does readOnly = true actually do?

Hibernate skips dirty checking and flushing, the JDBC connection is flagged read-only (Postgres enforces it), and routing datasources can send the query to a replica. It is an optimisation and a guard, not a security control.

18. @Repository versus @Service?

Both are @Component stereotypes. @Repository additionally enables persistence exception translation: a post-processor wraps the bean and converts vendor exceptions (SQLException, Hibernate exceptions) into Spring's DataAccessException hierarchy, such as DataIntegrityViolationException for a unique constraint. Spring Data repositories get this automatically. @Service is semantic only.

19. What is the N+1 problem and how do you fix it?

One query for the parents and one per parent for a lazy association. Fix with a fetch join or @EntityGraph for that use case, batch fetching (default_batch_fetch_size), or DTO projections. Never switch associations to EAGER globally; that moves the N+1 everywhere.

20. Should open-session-in-view be on?

No for APIs. It holds a DB connection for the whole request and hides lazy loading in serialisation. Turn it off, load data in @Transactional service methods, return DTOs, and fix LazyInitializationExceptions by fetching explicitly.

21. How do you paginate a large table efficiently?

Pageable with a Slice when you do not need the total, keyset pagination (where (created_at, id) < (:ts, :id) with an index) for deep pages and infinite scroll, and never a collection fetch join with a page; fetch IDs first.

22. Optimistic or pessimistic locking in JPA?

Optimistic (@Version column, OptimisticLockException on conflict, retry) for low-contention updates such as editing a document's metadata. Pessimistic (@Lock(PESSIMISTIC_WRITE), SELECT ... FOR UPDATE) when contention is high and retries are expensive, such as decrementing a credit balance. Always keep pessimistic transactions short.

Web, security and operations

23. How do you handle exceptions globally?

A @RestControllerAdvice with @ExceptionHandler methods that map domain exceptions to status codes and return ProblemDetail (RFC 9457) bodies, plus a catch-all that logs once and returns 500 without internals. Set spring.mvc.problemdetails.enabled=true so Spring's own exceptions use the same format.

24. How does request validation work?

@Valid @RequestBody runs Bean Validation and raises MethodArgumentNotValidException (400). Constraint annotations on records or DTOs, custom ConstraintValidators for domain rules, groups for create versus update. Map the errors to a field list in the advice.

25. Walk through the Spring Security filter chain for a JWT request.

DelegatingFilterProxy hands the request to FilterChainProxy, which picks the first matching SecurityFilterChain. BearerTokenAuthenticationFilter extracts the token, JwtDecoder verifies signature (JWKS) and claims, JwtAuthenticationConverter maps scopes to authorities, and the Authentication is stored in the SecurityContext. AuthorizationFilter applies URL rules, then @PreAuthorize applies method rules (enabled by @EnableMethodSecurity).

26. JWT versus server sessions; how do you log out a JWT user?

JWTs are stateless and scale without shared session storage, but cannot be revoked before expiry. Keep them short-lived, rotate refresh tokens and revoke those server-side, and for urgent revocation keep a small denylist of token IDs (jti) in Redis until expiry.

27. What is the difference between OAuth2 and JWT?

OAuth2 is an authorisation framework defining flows to obtain access tokens (authorization code with PKCE, client credentials). JWT is a token format. OAuth2 tokens are often JWTs, but they can be opaque tokens checked by introspection. OpenID Connect adds identity (the ID token) on top of OAuth2.

28. What do you expose through Actuator in production?

Health (liveness and readiness groups), info, and Prometheus metrics, on a management port, secured. Not env, heapdump, threaddump or loggers on the public port. Custom health indicators for critical dependencies go in readiness, not liveness.

29. Should we enable virtual threads in our Spring Boot service?

If it is on Java 21+, Boot 3.2+, I/O-bound with blocking JDBC/HTTP, and thread pool size is the bottleneck, yes, behind a load test. Check for synchronized around blocking I/O (pinning on Java 21), size Hikari deliberately, and add semaphores for downstream rate limits. CPU-bound or already reactive services gain nothing.

30. How do SOLID principles show up in a Spring codebase?

Single responsibility: thin controllers, services per use case. Open/closed: a new payment gateway is a new bean implementing PaymentGateway, picked from an injected map, with no edits to existing code. Liskov: implementations honour the interface's contract (same exceptions, same idempotency). Interface segregation: small ports (DocumentStore, Notifier), not one god interface. Dependency inversion: services depend on interfaces and receive implementations through constructor injection.

31. @Async: what can go wrong?

Same proxy rules as @Transactional (self-invocation is ignored), plain Spring without Boot falls back to SimpleAsyncTaskExecutor, which starts a new thread per task, exceptions from void methods are lost unless you configure an AsyncUncaughtExceptionHandler, and the async work runs outside the caller's transaction and security context unless you propagate it. Configure a bounded ThreadPoolTaskExecutor or virtual threads, and return CompletableFuture when the caller needs the result.

32. How do you publish an event only after the transaction commits?

@TransactionalEventListener(phase = AFTER_COMMIT). For guaranteed delivery to Kafka, write an outbox row in the same transaction and relay it, because an after-commit listener can still fail after the commit.

06Hands-on exercise (60 minutes)

Build a tiny Spring Boot 3 service, the PayPal HM round in miniature:

  1. POST /payments with a validated record body and an Idempotency-Key header. Store keys in a table with a unique constraint on (tenant_id, idempotency_key). Send the same request twice and confirm one payment row and identical responses.
  2. Add a @RestControllerAdvice returning ProblemDetail for not found, validation errors, duplicate key conflicts (catch DataIntegrityViolationException) and the catch-all.
  3. Write a test that proves self-invocation: a @Transactional method called through this does not roll back on a RuntimeException. Fix it by moving the method to a second bean.
  4. Create a Payment entity with a lazy List<Refund>, list 20 payments with refunds, and count queries with Hibernate statistics. Fix the N+1 with @EntityGraph and show the count drop from 21 to 1.
  5. Set spring.jpa.open-in-view=false and spring.threads.virtual.enabled=true; check /actuator/health and /actuator/prometheus.
