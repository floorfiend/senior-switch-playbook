Rate Limiter

You will be able to code a thread-safe rate limiter with swappable algorithms in 90 minutes, and explain how it scales across pods.

In 30 seconds
  • One RateLimiter interface; each algorithm is a Strategy behind it.

  • Thread safety: CAS on tiny state, per-client lock on collections.

Go deeper: how the rounds actually ran

The reports show the same pattern: a working core in the first half, then an extension or a "now make it concurrent / distributed" push. Razorpay ran it as two rounds: a 45-minute HackerRank round to implement a token bucket, then a 60-minute extension with an interviewer to make the sliding window work in a concurrent environment. Media.net gave 90 minutes in which each client owns one limiter instance and can switch algorithm at runtime, followed by scaling questions. Swiggy's bar raiser had the candidate code both sliding window and leaky bucket. Atlassian expects production-quality code with tests.

Full grading notes: Strategy interface for the algorithm, so adding a new one touches one new class and the factory. No lost updates under contention: CAS loop or a per-key lock, never a global lock across all clients. API shaped to the brief. Memory for idle keys, 429 + Retry-After, fail-open vs fail-closed, Redis + Lua for the distributed version. Explaining the trade-offs between algorithms in two sentences each, and why your code is thread-safe.

Go deeper: the longer "why it matters" notes
  • The key decides the map key and whether one client can hold several limiters.
  • Fixed window allows 2N across a boundary; sliding log is exact but O(N) memory; sliding counter is approximate in O(1).
  • Runtime changes need a swappable delegate (atomic reference) and a policy store.
  • Queueing = leaky bucket as a queue with a drain thread; fail fast = boolean result.
  • Weighted requests: add tryAcquire(int permits) early; retrofitting is awkward.

06The race and the fix

The bug: check-then-act as three separate steps. One token left, two threads:

TimeThread AThread Btokens
t1reads tokens = 11
t2reads tokens = 11
t31 ≥ 1, writes 0, ALLOW0
t41 ≥ 1, writes 0, ALLOW2 admitted for 1 token

The fix: an immutable State record swapped with CAS.

TimeThread AThread Bstate
t1cur = State(1, t0)cur = State(1, t0)State(1, t0)
t2CAS(cur → State(0, t2)) succeedsState(0, t2)
t3CAS(cur → …) fails: state changedState(0, t2)
t4retries, reads 0, returns DENY1 admitted, correct

CAS loop token bucket

  • Lock-free; state is two numbers
  • Retries under heavy contention

Use for tiny O(1) state.

Per-instance lock

  • Simple for a deque
  • Blocks within one client

Use when state is a collection (sliding log).

Razorpay's extension (sliding window, concurrent): per-client lock, lock-free AtomicLong counter, or striped cells. Details below.

Go deeper: every concurrency and edge case
  • Check-then-act race. "Read tokens, compare, write tokens minus one" as three steps lets two threads spend one token. Fix with a CAS loop over an immutable state (token bucket above) or a per-instance lock (sliding log). Both are acceptable; say why you chose each: CAS for tiny O(1) state, lock when state is a collection.
  • Never one global lock. synchronized on the registry serialises every client. Per-key locking comes for free when the lock lives inside the limiter instance.
  • computeIfAbsent vs get then put. The second creates two limiters for the same key under a race, and one client gets double quota for a while.
  • Don't do slow work inside computeIfAbsent. It holds a bin lock; a remote policy fetch there blocks other keys in the same bin. Resolve the policy first or cache it.
  • Monotonic time. System.nanoTime(), plus Math.max(now, last) because two threads can read the clock in one order and CAS in the other.
  • Permits larger than capacity. Reject immediately; otherwise a waiting implementation would block forever.
  • Long idle gaps. Cap the refill at capacity; in the counter, a gap of two or more windows zeroes the previous count.
  • Idle-key memory. One million one-off IPs leak one million buckets. Use Caffeine with expireAfterAccess(window * 2), or a periodic sweep removing limiters that are full (token bucket) or empty (window). A full bucket is identical to a fresh one, so eviction is lossless.
  • Swap semantics. Swapping the algorithm resets state. Say whether that is acceptable (usually yes) or whether to carry over "used in current window" when the window length is unchanged.
  • Virtual threads. synchronized pinned carrier threads before JDK 24 (JEP 491 removed most pinning). With very short critical sections it does not matter; ReentrantLock avoids the question.

Razorpay's extension in full: show three levels and pick one. (1) Per-client ReentrantLock around the deque, as above: simple and correct, contention only within one client. (2) Lock-free sliding counter: pack window id and count into one AtomicLong and CAS. (3) Striped: shard each client's counter into N LongAdder-like cells for very hot keys, accepting slight over-admission. Then write the 100-thread test that proves exactly limit requests pass.

Show TimeSource, RateLimiter, RateLimitPolicy

Time is in nanoseconds from a monotonic source, never System.currentTimeMillis() (wall clock can jump back on NTP sync).

public interface TimeSource {
    long nanoTime();
    TimeSource SYSTEM = System::nanoTime;
}

public interface RateLimiter {
    boolean tryAcquire(int permits);
    default boolean tryAcquire() { return tryAcquire(1); }
}

public enum Algorithm { TOKEN_BUCKET, FIXED_WINDOW, SLIDING_LOG, SLIDING_COUNTER, LEAKY_BUCKET }

public record RateLimitPolicy(Algorithm algorithm, int limit, Duration window, int burst) {
    public RateLimitPolicy {
        if (limit <= 0 || window.isZero() || window.isNegative()) throw new IllegalArgumentException("bad policy");
        if (burst <= 0) burst = limit;
    }
}
Show TokenBucket (lock-free)

Refill lazily on each call from elapsed time; no background thread. State is an immutable record swapped with CAS, so two threads cannot both spend the last token.

public final class TokenBucket implements RateLimiter {
    private record State(double tokens, long lastRefillNanos) {}

    private final double capacity;
    private final double tokensPerNano;
    private final TimeSource time;
    private final AtomicReference<State> state;

    public TokenBucket(int capacity, int refillTokens, Duration refillPeriod, TimeSource time) {
        this.capacity = capacity;
        this.tokensPerNano = (double) refillTokens / refillPeriod.toNanos();
        this.time = time;
        this.state = new AtomicReference<>(new State(capacity, time.nanoTime())); // starts full
    }

    @Override
    public boolean tryAcquire(int permits) {
        if (permits > capacity) return false;               // can never succeed; do not spin
        while (true) {
            State cur = state.get();
            // Another thread may have stored a later timestamp than the one we read; never go backwards.
            long now = Math.max(time.nanoTime(), cur.lastRefillNanos());
            double available = Math.min(capacity, cur.tokens() + (now - cur.lastRefillNanos()) * tokensPerNano);
            if (available < permits) return false;
            if (state.compareAndSet(cur, new State(available - permits, now))) return true;
            // CAS lost: someone else changed the bucket; retry with fresh state.
        }
    }

    /** For Retry-After: nanos until `permits` tokens will be available. */
    public long nanosUntil(int permits) {
        State cur = state.get();
        double available = Math.min(capacity,
                cur.tokens() + (time.nanoTime() - cur.lastRefillNanos()) * tokensPerNano);
        return available >= permits ? 0 : (long) Math.ceil((permits - available) / tokensPerNano);
    }
}

Floating-point tokens are fine at interview scope. If asked, switch to integer "nano-tokens" (scale by 109) as Bucket4j does to avoid drift.

Show SlidingWindowLog (locked per instance)

Exact. The deque never holds more than limit entries because denied requests are not recorded. The lock is per limiter, so contention is only between requests of the same client.

public final class SlidingWindowLog implements RateLimiter {
    private final int limit;
    private final long windowNanos;
    private final TimeSource time;
    private final ArrayDeque<Long> log = new ArrayDeque<>();
    private final ReentrantLock lock = new ReentrantLock();

    public SlidingWindowLog(int limit, Duration window, TimeSource time) {
        this.limit = limit; this.windowNanos = window.toNanos(); this.time = time;
    }

    @Override
    public boolean tryAcquire(int permits) {
        lock.lock();
        try {
            long now = time.nanoTime();
            while (!log.isEmpty() && now - log.peekFirst() >= windowNanos) log.pollFirst();
            if (log.size() + permits > limit) return false;
            for (int i = 0; i < permits; i++) log.addLast(now);
            return true;
        } finally {
            lock.unlock();
        }
    }
}
Show SlidingWindowCounter

Weighted estimate: prev * (1 - elapsedFraction) + curr. Two integers per key; this is what you would put in Redis at scale.

public final class SlidingWindowCounter implements RateLimiter {
    private final int limit;
    private final long windowNanos;
    private final TimeSource time;
    private long windowStart;
    private int prevCount;
    private int currCount;

    public SlidingWindowCounter(int limit, Duration window, TimeSource time) {
        this.limit = limit; this.windowNanos = window.toNanos(); this.time = time;
        this.windowStart = time.nanoTime();
    }

    @Override
    public synchronized boolean tryAcquire(int permits) {
        long now = time.nanoTime();
        long windowsPassed = (now - windowStart) / windowNanos;
        if (windowsPassed >= 1) {
            prevCount = windowsPassed == 1 ? currCount : 0;   // gap of 2+ windows: previous is empty
            currCount = 0;
            windowStart += windowsPassed * windowNanos;       // stay aligned, do not drift to `now`
        }
        double elapsed = (double) (now - windowStart) / windowNanos;
        double estimated = prevCount * (1 - elapsed) + currCount;
        if (estimated + permits > limit) return false;
        currCount += permits;
        return true;
    }
}
Show LeakyBucket and FixedWindowCounter 
public final class LeakyBucket implements RateLimiter {
    private final double capacity;
    private final double leakPerNano;
    private final TimeSource time;
    private double level;
    private long lastLeak;

    public LeakyBucket(int capacity, int leaksPerWindow, Duration window, TimeSource time) {
        this.capacity = capacity; this.leakPerNano = (double) leaksPerWindow / window.toNanos();
        this.time = time; this.lastLeak = time.nanoTime();
    }

    @Override
    public synchronized boolean tryAcquire(int permits) {
        long now = time.nanoTime();
        level = Math.max(0, level - (now - lastLeak) * leakPerNano);
        lastLeak = now;
        if (level + permits > capacity) return false;
        level += permits;
        return true;
    }
}

public final class FixedWindowCounter implements RateLimiter {
    private final int limit;
    private final long windowNanos;
    private final TimeSource time;
    private final long origin;
    private long windowId = -1;
    private int count;

    public FixedWindowCounter(int limit, Duration window, TimeSource time) {
        this.limit = limit; this.windowNanos = window.toNanos(); this.time = time; this.origin = time.nanoTime();
    }

    @Override
    public synchronized boolean tryAcquire(int permits) {
        long id = (time.nanoTime() - origin) / windowNanos;
        if (id != windowId) { windowId = id; count = 0; }
        if (count + permits > limit) return false;
        count += permits;
        return true;
    }
}

As a meter it is the token bucket mirrored. The "queue" variant (Swiggy asked for the behaviour, not just the maths) holds requests in an ArrayBlockingQueue of size capacity, and a ScheduledExecutorService drains one every 1/rate seconds. That variant shapes traffic instead of rejecting it, at the cost of added latency.

Show RateLimiterFactory, SwappableRateLimiter, RateLimiterRegistry 
public final class RateLimiterFactory {
    private final TimeSource time;
    public RateLimiterFactory(TimeSource time) { this.time = time; }

    public RateLimiter create(RateLimitPolicy p) {
        return switch (p.algorithm()) {
            case TOKEN_BUCKET    -> new TokenBucket(p.burst(), p.limit(), p.window(), time);
            case SLIDING_LOG     -> new SlidingWindowLog(p.limit(), p.window(), time);
            case SLIDING_COUNTER -> new SlidingWindowCounter(p.limit(), p.window(), time);
            case LEAKY_BUCKET    -> new LeakyBucket(p.burst(), p.limit(), p.window(), time);
            case FIXED_WINDOW    -> new FixedWindowCounter(p.limit(), p.window(), time);
        };
    }
}

/** One per client. Callers keep this reference; the algorithm behind it can change. */
public final class SwappableRateLimiter implements RateLimiter {
    private final AtomicReference<RateLimiter> delegate;
    public SwappableRateLimiter(RateLimiter initial) { this.delegate = new AtomicReference<>(initial); }
    @Override public boolean tryAcquire(int permits) { return delegate.get().tryAcquire(permits); }
    public void swap(RateLimiter next) { delegate.set(next); }   // new algorithm starts with fresh state
}

public final class RateLimiterRegistry {
    private final ConcurrentHashMap<String, SwappableRateLimiter> limiters = new ConcurrentHashMap<>();
    private final RateLimiterFactory factory;
    private final Function<String, RateLimitPolicy> policyLookup;

    public RateLimiterRegistry(RateLimiterFactory factory, Function<String, RateLimitPolicy> policyLookup) {
        this.factory = factory; this.policyLookup = policyLookup;
    }

    public boolean allow(String clientId) {
        // computeIfAbsent is atomic per key: two first requests never create two buckets.
        return limiters.computeIfAbsent(clientId,
                id -> new SwappableRateLimiter(factory.create(policyLookup.apply(id)))).tryAcquire();
    }

    public void changePolicy(String clientId, RateLimitPolicy policy) {
        RateLimiter fresh = factory.create(policy);
        limiters.compute(clientId, (id, existing) -> {
            if (existing == null) return new SwappableRateLimiter(fresh);
            existing.swap(fresh);
            return existing;
        });
    }
}

If the brief is Media.net's "every client holds its own limiter object", hand out SwappableRateLimiter directly and drop the registry from the public API. The interface stays tryAcquire() with no client id.

Go deeper: full answers for each extension
Swap the algorithm for a client at runtime (Media.net)

Already absorbed: SwappableRateLimiter.swap is one atomic reference write. In-flight calls finish on the old instance; new calls go to the new one. No caller changes.

Run it across multiple servers (Media.net, Rapido, Atlassian)

Two answers, say both. Sticky routing: consistent-hash the client key at the gateway so one pod owns each client; in-memory stays exact, but a rebalance or pod death resets counts for the moved keys, and a hot key overloads one pod. Central store: Redis. Token bucket as a Lua script (read tokens and timestamp from a hash, refill, decrement, PEXPIRE, all atomic on the server), or sliding log as a sorted set (ZREMRANGEBYSCORE, ZCARD, ZADD in one script). Key by {clientId} hash tag in Redis Cluster so a script's keys live on one shard. Use Redis server time (TIME) inside the script, not app-node clocks.

Then the production details: one Redis round trip (~0.5–1 ms) per request; decide fail-open (availability, the usual choice for API quotas) vs fail-closed (security limits such as login attempts); add a small local token cache that pre-fetches batches of tokens for very hot keys to cut Redis calls.

"How would you run a token bucket in production?" (Rapido director)

Gateway or a servlet filter / Spring HandlerInterceptor, before auth-heavy work. Bucket4j with a Redis (Redisson or Lettuce) proxy manager rather than hand-rolled Lua, unless you need custom semantics. Policies per tenant and plan stored in config, cached locally. Return 429 with Retry-After and remaining-quota headers. Metrics: allowed/denied per key and per policy, Redis latency. Dark-launch new limits in log-only mode, keep a kill switch. Multi-tenancy: key on tenant from the JWT, not on a request parameter, and give each tenant its own bucket so one noisy tenant cannot starve others.

Different limits per endpoint, or several limits at once (10/s and 1000/day)

A CompositeRateLimiter holding a list; allow only if all allow. Watch the partial-consume problem: if the second limiter denies, the first has already spent a token. Either check all then consume all under a lock, or refund (token bucket supports refund cleanly).

Block instead of rejecting

Add acquire(permits, timeout): compute nanosUntil, park for that long, retry. Guava's RateLimiter works this way (it reserves future permits). Never sleep while holding the lock.

Weighted requests (a bulk API costs 10)

Already supported by tryAcquire(int permits). Reject a cost larger than capacity.

10Mistakes that got candidates rejected

Common mistakes
  • allowRequest(clientId, timestamp) on an already per-client object (Media.net, Jan 2026, no offer).
  • HashMap + synchronized on the whole service, or no sync at all.
  • A refill thread per bucket: 10,000 clients, 10,000 threads.
  • System.currentTimeMillis() inside the algorithm: untestable without sleeping.
  • "Use Redis" with GET then SET: same race, now across pods.
  • 40 minutes on five algorithms, zero tests. Ship one, tested, first.
Go deeper: the rejection notes in full
  • API that ignores the brief: allowRequest(clientId, timestamp) on an object that is already per-client (Media.net, Jan 2026, no offer).
  • HashMap plus synchronized on the whole service, or no synchronisation at all, then failing the "make it concurrent" extension.
  • A background thread per bucket to add tokens. Ten thousand clients means ten thousand threads; lazy refill on access is the expected answer.
  • System.currentTimeMillis() called directly in the algorithm, so nothing is testable without sleeping.
  • Only fixed window, unable to explain the 2N boundary burst or the alternatives.
  • Saying "use Redis" without atomicity: GET then SET from the app has the same race as the in-memory version, now across pods.
  • Spending 40 minutes on all five algorithms with no tests. Ship one fully tested algorithm, then add others behind the interface.

12Quick check

Two threads both read "1 token left" and both get ALLOW. What fixes it with no lock?

volatile gives visibility, not atomicity. With CAS the loser retries and sees 0.

Why no background thread to refill tokens?

Lazy refill costs one multiply per call. 10,000 clients would otherwise need 10,000 threads.

Limit 100/min, fixed window. What is the worst case in any rolling minute?

Counts reset at the boundary, so two full windows can sit back to back.

Your Redis limiter does GET, checks, then SET from the app. What is wrong?

Each command is atomic; your sequence is not. A Lua script is.

13Interview questions

Why CAS in the token bucket but a lock in the sliding log?

Token bucket state is two numbers, cheap to copy into an immutable record and swap. The log is a mutable deque; making it lock-free would need a persistent structure. Per-instance locks only contend within one client, which is fine.

Can your CAS loop livelock?

Under extreme contention on one key some threads retry several times, but each failed CAS means another thread succeeded, so the system makes progress. If a single key is that hot, shard it or move to a lock with fair queueing.

Token bucket vs leaky bucket in one line each?

Token bucket limits the average rate and permits bursts up to capacity. Leaky bucket enforces a constant output rate and absorbs bursts by queueing or rejecting them.

How accurate is the sliding window counter?

It assumes requests in the previous window were evenly spread. Cloudflare reported a very small error rate on real traffic. Good enough for API quotas, not for hard security limits.

What status code and headers do you return?

429 Too Many Requests with Retry-After (seconds), plus limit / remaining / reset headers (X-RateLimit-* or the IETF RateLimit fields). Use 503 for load shedding, which is about server health rather than the client's quota.

Where does the tenant id come from?

From the authenticated principal (JWT claim), never a header or query parameter the client controls, otherwise a client rotates ids to bypass limits.

How do you stop the map growing forever?

Time-based eviction (Caffeine expireAfterAccess) or a sweep. Evicting a full token bucket loses nothing, because a new one starts full.
