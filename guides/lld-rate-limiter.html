Rate Limiter

A rate limiter decides how many requests one client may send in a given time. By the end, you can code one in 90 minutes. It will be safe when many threads call it at once. You will also be able to switch its algorithm, and explain how it works across many servers.

Time-box: 45–90 min coding, then 30–45 min of questions Seen: about 12 interview reports, 2025–26 Format: HackerRank, a shared IDE, or a whiteboard
RazorpayMedia.netSwiggyAtlassianAppleSalesforceMicrosoftAgodaRapido
In 30 seconds
  • Write one RateLimiter interface. Each algorithm is a separate class behind it, so you can swap them.
  • The token bucket adds tokens back only when a request arrives. It works out the refill from the time that passed. No background thread is needed.
  • For small state, use an atomic compare-and-set. For a list of timestamps, use one lock per client.
  • Pass the clock in from outside. Then a test with 100 threads can prove the limit holds.
Picture it

Think of a toll lane with a jar of 10 passes. Each car takes one pass. The attendant adds one pass every 6 seconds, but never more than the jar holds. Ten cars can rush through together. The 11th car must wait for a new pass.

Words you'll see
Rate limit
A cap such as "100 requests per minute" for one client. Requests over the cap are refused.
Token bucket
A bucket of tokens that refills at a steady speed. Each request spends one token. No token means the request is refused.
Window
The time period the limit counts over, such as one second or one minute.
Burst
Many requests arriving at almost the same moment, like everyone hitting "Book" when Tatkal opens.
Thread-safe
Gives correct results even when many threads call it at the same time.
CAS (compare-and-set)
Write the new value only if the old value is still the one you read. If someone changed it first, the write fails and you try again.
Strategy pattern
Put each algorithm in its own class behind one interface, so you can swap one for another.
429
The HTTP status code for "Too Many Requests". It tells the client to slow down.

01What the interviewer is grading

Correct

Tests use a fake clock. They check bursts, refills and the edges of each window.

Extensible

Adding a new algorithm means one new class and one new line in the factory.

Concurrent

Use compare-and-set or one lock per client. Never use one lock for all clients.

Fits the brief

If each client already has its own limiter object, don't ask for a clientId again.

Go deeper: how the rounds actually ran

The reports show the same pattern. You build a working core in the first half. Then the interviewer adds a feature, or says "now make it concurrent" or "now make it distributed". Razorpay ran it as two rounds. First came a 45-minute HackerRank round to build a token bucket. Then came a 60-minute round with an interviewer. There, the sliding window had to work with many threads at once. Media.net gave 90 minutes. Each client owned one limiter object and could switch algorithm while running. Scaling questions followed. Swiggy's bar raiser had the candidate code both a sliding window and a leaky bucket. Atlassian expects production-quality code with tests.

Full grading notes follow. Put the algorithm behind a Strategy interface. Then adding a new one touches only one new class and the factory. No update may be lost when many threads compete. Use a compare-and-set loop or a lock per key, never one global lock for all clients. Shape the API to match the brief. Also expect questions on these topics. How do you free memory for idle keys? Do you return 429 with a Retry-After header? Do you fail open or fail closed? How does Redis with a Lua script handle the distributed version? Explain the trade-off of each algorithm in two sentences. Explain why your code is thread-safe.

02Clarifying questions to ask

QuestionWhy it matters
What do we limit by? User, API key, IP address, or client plus endpoint?This becomes the key in your map.

Go deeper: the longer "why it matters" notes
  • The key decides the map key. It also decides whether one client can hold several limiters.
  • A fixed window can allow 2N across a boundary. A sliding log is exact but uses O(N) memory, meaning memory grows with the limit. A sliding counter is approximate but uses O(1), a fixed small amount.
  • Changing things at runtime needs a replaceable inner limiter (an atomic reference) and a place to store policies.
  • If requests should wait in line, use a leaky bucket as a queue with a thread that drains it. If they should fail fast, return a simple true or false.
  • Some requests may cost more than one unit. Add tryAcquire(int permits) early, because adding it later is awkward.

03Requirements

Functional

  • Each client gets limit requests per window, plus a burst size.
  • tryAcquire says allow or deny straight away.
  • Five algorithms, swappable while running.
  • Report the remaining quota and when to retry.

Non-functional

  • Thread-safe, with constant work per call.
  • Takes microseconds. No waiting on disk or network.
  • Remove clients that have gone idle.
  • Time comes from a clock you pass in.

Out of scope (say so)

  • Shared state across servers (discuss only).
  • Saving config to a database, or an admin screen.
  • Dropping load for the whole system.
Go deeper: full requirement list
  • Set a limit per client: limit requests per window. For the token bucket, also set the burst capacity.
  • Support five algorithms. They are token bucket, fixed window, sliding window log, sliding window counter and leaky bucket.
  • Report the remaining quota and the retry time, for response headers.
  • Be thread-safe, with O(1) work per call. Say out loud that the sliding log uses O(limit) memory.
  • Decide in microseconds. The in-memory version must not wait on disk or network.
  • Give the same result every test run. To do that, take time from a clock passed in from outside.
  • Out of scope: shared state across servers. Discuss it, but don't code it unless asked. Also out of scope are saved configuration and an admin screen. So are dropping load for the whole system and limits on parallel requests. Mention Stripe's four limiter types as background.

06The race and the fix

The bug is check-then-act done as three separate steps. Read the value, decide, then write. Here is what happens with one token left and two threads:

TimeThread AThread Btokens
t1reads tokens = 11
t2reads tokens = 11
t31 ≥ 1, writes 0, ALLOW0
t41 ≥ 1, writes 0, ALLOW2 admitted for 1 token

The fix is to keep the state in a State record that never changes. You replace the whole record using CAS. If another thread got there first, your write fails and you try again.

TimeThread AThread Bstate
t1cur = State(1, t0)cur = State(1, t0)State(1, t0)
t2CAS(cur → State(0, t2)) succeedsState(0, t2)
t3CAS(cur → …) fails: state changedState(0, t2)
t4retries, reads 0, returns DENY1 admitted, correct

CAS loop token bucket

  • No lock needed. The state is just two numbers.
  • Threads retry a lot when many hit one key.

Use it for tiny state of fixed size.

Per-instance lock

  • Simple for a queue of timestamps
  • Requests from one client wait for each other

Use it when the state is a collection, as in the sliding log.

Razorpay's extension asked for a sliding window that is safe with many threads. You have three options. Use a lock per client, a lock-free AtomicLong counter, or a counter split into several cells. Details are below.

Go deeper: every concurrency and edge case
  • Check-then-act race. Suppose you read the tokens, compare, then write tokens minus one, as three steps. Two threads can then spend the same token. Fix it with a CAS loop over a state that never changes (the token bucket above). Or use a lock per limiter object (the sliding log). Both are fine, but say why you chose each. Use CAS for tiny fixed-size state. Use a lock when the state is a collection.
  • Never one global lock. synchronized on the registry makes every client wait in a single line. If the lock lives inside each limiter object, you get one lock per key for free.
  • computeIfAbsent vs get then put. With get then put, two threads can create two limiters for the same key. One client then gets double quota for a while.
  • Don't do slow work inside computeIfAbsent. It holds a lock on part of the map. A remote policy lookup there blocks other keys that share that part. Look up the policy first, or cache it.
  • Time that never goes backwards. Use System.nanoTime(). Also use Math.max(now, last). Two threads can read the clock in one order but finish their CAS in the other order.
  • Asking for more permits than capacity. Reject at once. Otherwise a waiting version would wait forever.
  • Long quiet gaps. Stop the refill at capacity. In the counter, a gap of two or more windows sets the previous count to zero.
  • Memory for idle keys. One million one-time IP addresses leave one million buckets in memory. Use Caffeine with expireAfterAccess(window * 2). Or run a regular sweep. It removes limiters that are full (token bucket) or empty (window). A full bucket is the same as a new one, so removing it loses nothing.
  • What a swap does. Swapping the algorithm resets the state. Say whether that is fine (usually yes). The other option is carrying over "used in the current window" when the window length stays the same.
  • Virtual threads. Before JDK 24, synchronized could pin a virtual thread to its carrier thread, blocking that carrier. JEP 491 removed most of this pinning. With very short locked sections it does not matter. ReentrantLock avoids the question.

Here is Razorpay's extension in full. Show three levels and pick one. (1) A ReentrantLock per client around the queue of timestamps, as above. It is simple and correct, and only one client's requests wait for each other. (2) A lock-free sliding counter. Pack the window id and the count into one AtomicLong and use CAS. (3) Split counters. For very busy keys, split each client's counter into N cells, like LongAdder. You accept letting in slightly too many requests. Then write the 100-thread test that proves exactly limit requests pass.

Show TimeSource, RateLimiter, RateLimitPolicy

Time is in nanoseconds from a clock that never goes backwards. Never use System.currentTimeMillis(). That wall clock can jump back when the server syncs its time with NTP.

public interface TimeSource {
    long nanoTime();
    TimeSource SYSTEM = System::nanoTime;
}

public interface RateLimiter {
    boolean tryAcquire(int permits);
    default boolean tryAcquire() { return tryAcquire(1); }
}

public enum Algorithm { TOKEN_BUCKET, FIXED_WINDOW, SLIDING_LOG, SLIDING_COUNTER, LEAKY_BUCKET }

public record RateLimitPolicy(Algorithm algorithm, int limit, Duration window, int burst) {
    public RateLimitPolicy {
        if (limit <= 0 || window.isZero() || window.isNegative()) throw new IllegalArgumentException("bad policy");
        if (burst <= 0) burst = limit;
    }
}
Show TokenBucket (lock-free)

Tokens are refilled on each call, based on the time that passed. There is no background thread. The state is a record that never changes, replaced with CAS. So two threads can never both spend the last token.

public final class TokenBucket implements RateLimiter {
    private record State(double tokens, long lastRefillNanos) {}

    private final double capacity;
    private final double tokensPerNano;
    private final TimeSource time;
    private final AtomicReference<State> state;

    public TokenBucket(int capacity, int refillTokens, Duration refillPeriod, TimeSource time) {
        this.capacity = capacity;
        this.tokensPerNano = (double) refillTokens / refillPeriod.toNanos();
        this.time = time;
        this.state = new AtomicReference<>(new State(capacity, time.nanoTime())); // starts full
    }

    @Override
    public boolean tryAcquire(int permits) {
        if (permits > capacity) return false;               // can never succeed; do not spin
        while (true) {
            State cur = state.get();
            // Another thread may have stored a later timestamp than the one we read; never go backwards.
            long now = Math.max(time.nanoTime(), cur.lastRefillNanos());
            double available = Math.min(capacity, cur.tokens() + (now - cur.lastRefillNanos()) * tokensPerNano);
            if (available < permits) return false;
            if (state.compareAndSet(cur, new State(available - permits, now))) return true;
            // CAS lost: someone else changed the bucket; retry with fresh state.
        }
    }

    /** For Retry-After: nanos until `permits` tokens will be available. */
    public long nanosUntil(int permits) {
        State cur = state.get();
        double available = Math.min(capacity,
                cur.tokens() + (time.nanoTime() - cur.lastRefillNanos()) * tokensPerNano);
        return available >= permits ? 0 : (long) Math.ceil((permits - available) / tokensPerNano);
    }
}

Decimal (floating-point) tokens are fine in an interview. If asked, switch to whole-number "nano-tokens", scaled by 109. Bucket4j does this to avoid small rounding errors piling up.

Show SlidingWindowLog (locked per instance)

This one is exact. The queue never holds more than limit entries, because refused requests are not recorded. Each limiter has its own lock. So only requests from the same client wait for each other.

public final class SlidingWindowLog implements RateLimiter {
    private final int limit;
    private final long windowNanos;
    private final TimeSource time;
    private final ArrayDeque<Long> log = new ArrayDeque<>();
    private final ReentrantLock lock = new ReentrantLock();

    public SlidingWindowLog(int limit, Duration window, TimeSource time) {
        this.limit = limit; this.windowNanos = window.toNanos(); this.time = time;
    }

    @Override
    public boolean tryAcquire(int permits) {
        lock.lock();
        try {
            long now = time.nanoTime();
            while (!log.isEmpty() && now - log.peekFirst() >= windowNanos) log.pollFirst();
            if (log.size() + permits > limit) return false;
            for (int i = 0; i < permits; i++) log.addLast(now);
            return true;
        } finally {
            lock.unlock();
        }
    }
}
Show SlidingWindowCounter

It gives a weighted estimate: prev * (1 - elapsedFraction) + curr. It stores only two whole numbers per key. At scale, this is what you would keep in Redis.

public final class SlidingWindowCounter implements RateLimiter {
    private final int limit;
    private final long windowNanos;
    private final TimeSource time;
    private long windowStart;
    private int prevCount;
    private int currCount;

    public SlidingWindowCounter(int limit, Duration window, TimeSource time) {
        this.limit = limit; this.windowNanos = window.toNanos(); this.time = time;
        this.windowStart = time.nanoTime();
    }

    @Override
    public synchronized boolean tryAcquire(int permits) {
        long now = time.nanoTime();
        long windowsPassed = (now - windowStart) / windowNanos;
        if (windowsPassed >= 1) {
            prevCount = windowsPassed == 1 ? currCount : 0;   // gap of 2+ windows: previous is empty
            currCount = 0;
            windowStart += windowsPassed * windowNanos;       // stay aligned, do not drift to `now`
        }
        double elapsed = (double) (now - windowStart) / windowNanos;
        double estimated = prevCount * (1 - elapsed) + currCount;
        if (estimated + permits > limit) return false;
        currCount += permits;
        return true;
    }
}
Show LeakyBucket and FixedWindowCounter 
public final class LeakyBucket implements RateLimiter {
    private final double capacity;
    private final double leakPerNano;
    private final TimeSource time;
    private double level;
    private long lastLeak;

    public LeakyBucket(int capacity, int leaksPerWindow, Duration window, TimeSource time) {
        this.capacity = capacity; this.leakPerNano = (double) leaksPerWindow / window.toNanos();
        this.time = time; this.lastLeak = time.nanoTime();
    }

    @Override
    public synchronized boolean tryAcquire(int permits) {
        long now = time.nanoTime();
        level = Math.max(0, level - (now - lastLeak) * leakPerNano);
        lastLeak = now;
        if (level + permits > capacity) return false;
        level += permits;
        return true;
    }
}

public final class FixedWindowCounter implements RateLimiter {
    private final int limit;
    private final long windowNanos;
    private final TimeSource time;
    private final long origin;
    private long windowId = -1;
    private int count;

    public FixedWindowCounter(int limit, Duration window, TimeSource time) {
        this.limit = limit; this.windowNanos = window.toNanos(); this.time = time; this.origin = time.nanoTime();
    }

    @Override
    public synchronized boolean tryAcquire(int permits) {
        long id = (time.nanoTime() - origin) / windowNanos;
        if (id != windowId) { windowId = id; count = 0; }
        if (count + permits > limit) return false;
        count += permits;
        return true;
    }
}

As a meter, the leaky bucket is the token bucket in reverse. Swiggy asked for the queue version, meaning the behaviour and not just the maths. It holds requests in an ArrayBlockingQueue of size capacity. A ScheduledExecutorService takes one out every 1/rate seconds. This version smooths traffic instead of refusing it. The cost is extra waiting time.

Show RateLimiterFactory, SwappableRateLimiter, RateLimiterRegistry 
public final class RateLimiterFactory {
    private final TimeSource time;
    public RateLimiterFactory(TimeSource time) { this.time = time; }

    public RateLimiter create(RateLimitPolicy p) {
        return switch (p.algorithm()) {
            case TOKEN_BUCKET    -> new TokenBucket(p.burst(), p.limit(), p.window(), time);
            case SLIDING_LOG     -> new SlidingWindowLog(p.limit(), p.window(), time);
            case SLIDING_COUNTER -> new SlidingWindowCounter(p.limit(), p.window(), time);
            case LEAKY_BUCKET    -> new LeakyBucket(p.burst(), p.limit(), p.window(), time);
            case FIXED_WINDOW    -> new FixedWindowCounter(p.limit(), p.window(), time);
        };
    }
}

/** One per client. Callers keep this reference; the algorithm behind it can change. */
public final class SwappableRateLimiter implements RateLimiter {
    private final AtomicReference<RateLimiter> delegate;
    public SwappableRateLimiter(RateLimiter initial) { this.delegate = new AtomicReference<>(initial); }
    @Override public boolean tryAcquire(int permits) { return delegate.get().tryAcquire(permits); }
    public void swap(RateLimiter next) { delegate.set(next); }   // new algorithm starts with fresh state
}

public final class RateLimiterRegistry {
    private final ConcurrentHashMap<String, SwappableRateLimiter> limiters = new ConcurrentHashMap<>();
    private final RateLimiterFactory factory;
    private final Function<String, RateLimitPolicy> policyLookup;

    public RateLimiterRegistry(RateLimiterFactory factory, Function<String, RateLimitPolicy> policyLookup) {
        this.factory = factory; this.policyLookup = policyLookup;
    }

    public boolean allow(String clientId) {
        // computeIfAbsent is atomic per key: two first requests never create two buckets.
        return limiters.computeIfAbsent(clientId,
                id -> new SwappableRateLimiter(factory.create(policyLookup.apply(id)))).tryAcquire();
    }

    public void changePolicy(String clientId, RateLimitPolicy policy) {
        RateLimiter fresh = factory.create(policy);
        limiters.compute(clientId, (id, existing) -> {
            if (existing == null) return new SwappableRateLimiter(fresh);
            existing.swap(fresh);
            return existing;
        });
    }
}

Media.net's brief said "every client holds its own limiter object". In that case, hand out SwappableRateLimiter directly and remove the registry from the public API. The method stays tryAcquire() with no client id.

08Extensions interviewers add mid-round

Run it across many pods

Sticky routing

  • The gateway always sends a key to the same pod, using consistent hashing. In-memory counts stay exact.
  • Moving keys between pods, or a pod dying, resets their counts.
  • One very busy key overloads one pod.

Redis + Lua usual pick

  • One Lua script refills, subtracts and sets the expiry (PEXPIRE), all in one atomic step.
  • Use the Redis server clock (TIME), not each app server's clock.
  • Each request costs one Redis round trip, about 0.5–1 ms.

In Redis Cluster, wrap the key as a {clientId} hash tag, so all of one client's keys sit on one shard.

Swap algorithm at runtime

Already handled. swap is one atomic reference write.

In production

Use Bucket4j with Redis. Test new limits in log-only mode first. Take the tenant from the JWT login token.

10/s and 1000/day

Combine two limiters. Give tokens back if only one of them allows the request.

Block, not reject

Wait for nanosUntil, then try again.

Weighted requests

Some requests cost more. tryAcquire(int permits) already handles this.

Go deeper: full answers for each extension
Swap the algorithm for a client at runtime (Media.net)

This is already handled. SwappableRateLimiter.swap is one atomic reference write. Calls already running finish on the old object. New calls go to the new one. No caller has to change.

Run it across multiple servers (Media.net, Rapido, Atlassian)

There are two answers, and you should give both. Sticky routing: the gateway uses consistent hashing on the client key, so one pod owns each client. In-memory counts stay exact. But if keys move between pods, or a pod dies, the moved keys lose their counts. A very busy key can also overload one pod. Central store: use Redis. Write the token bucket as a Lua script. It reads tokens and timestamp from a hash, refills, subtracts and sets PEXPIRE. All of this runs as one atomic step on the Redis server. Or write the sliding log as a sorted set, with ZREMRANGEBYSCORE, ZCARD and ZADD in one script. In Redis Cluster, wrap the key as a {clientId} hash tag. Then all keys a script touches live on one shard. Inside the script, use the Redis server time (TIME), not the app servers' clocks.

Then cover the production details. Each request costs one Redis round trip, about 0.5–1 ms. Decide what happens when Redis is down. Fail-open means you let requests through. That keeps the service available, and it is the usual choice for API quotas. Fail-closed means you refuse them. Use it for security limits such as login attempts. For very busy keys, add a small local cache that fetches tokens from Redis in batches. This cuts Redis calls.

"How would you run a token bucket in production?" (Rapido director)

Put it in the gateway, or in a servlet filter or Spring HandlerInterceptor. Run it before heavy work such as authentication. Use Bucket4j with a Redis proxy manager (through Redisson or Lettuce) rather than your own Lua. Write your own only if you need special behaviour. Store policies per tenant and per plan in config, and cache them locally. Return 429 with Retry-After and remaining-quota headers. Track allowed and denied counts per key and per policy, plus Redis latency. Launch new limits in log-only mode first ("dark launch"), and keep a kill switch. For multi-tenancy, key on the tenant from the JWT, not on a request parameter. Give each tenant its own bucket. Then one noisy tenant cannot starve the others.

Different limits per endpoint, or several limits at once (10/s and 1000/day)

Use a CompositeRateLimiter that holds a list of limiters. It allows a request only if all of them allow it. Watch out for the partial-spend problem. If the second limiter refuses, the first has already spent a token. Either check all and then spend all under one lock, or give the token back. A token bucket supports giving tokens back cleanly.

Block instead of rejecting

Add acquire(permits, timeout). It works out nanosUntil, waits that long, then tries again. Guava's RateLimiter works this way, by reserving future permits. Never sleep while holding the lock.

Weighted requests (a bulk API costs 10)

This is already supported by tryAcquire(int permits). Refuse any cost larger than the capacity.

09Tests to write

Fake clock

10Mistakes that got candidates rejected

Common mistakes
  • Writing allowRequest(clientId, timestamp) on an object that already belongs to one client (Media.net, Jan 2026, no offer).
  • A HashMap with synchronized on the whole service. Or no thread safety at all.
  • A refill thread for every bucket. With 10,000 clients, that is 10,000 threads.
  • Calling System.currentTimeMillis() inside the algorithm. You can't test it without sleeping.
  • "Use Redis", but with GET then SET. That is the same race, now across pods.
  • 40 minutes on five algorithms and zero tests. Ship one tested algorithm first.
Go deeper: the rejection notes in full
  • An API that ignores the brief. One candidate wrote allowRequest(clientId, timestamp) on an object that already belonged to one client (Media.net, Jan 2026, no offer).
  • A HashMap with synchronized on the whole service, or no thread safety at all. These candidates then failed the "make it concurrent" extension.
  • A background thread per bucket to add tokens. Ten thousand clients means ten thousand threads. The expected answer is to refill only when a request arrives.
  • Calling System.currentTimeMillis() directly in the algorithm. Then nothing can be tested without sleeping.
  • Knowing only the fixed window. These candidates could not explain the 2N burst at the boundary, or the other options.
  • Saying "use Redis" without making it atomic. A GET then SET from the app has the same race as the in-memory version, now across pods.
  • Spending 40 minutes on all five algorithms with no tests. Ship one fully tested algorithm. Then add others behind the interface.

12Quick check

Two threads both read "1 token left", and both get ALLOW. What fixes this without a lock?

volatile makes threads see the latest value. It does not make read-then-write one step. With CAS, the losing thread's write fails. It retries, sees 0 tokens, and is refused.

Why is there no background thread to refill tokens?

Working out the refill on each call costs one multiplication. Otherwise, 10,000 clients would need 10,000 threads.

The limit is 100 per minute with a fixed window. What is the most that can pass in any rolling minute?

The count resets at the boundary. So two full windows can sit right next to each other.

Your Redis limiter does GET, checks the value, then does SET from the app. What is wrong?

Each Redis command is atomic on its own. Your sequence of commands is not. Another pod can act between your GET and SET. A Lua script runs as one step.

13Interview questions

Why CAS in the token bucket but a lock in the sliding log?

The token bucket's state is just two numbers. It is cheap to copy them into a record that never changes and swap it with CAS. The log is a deque, a queue that changes in place. Making it lock-free would need a special persistent data structure. A lock per limiter only makes requests from the same client wait, which is fine.

Can your CAS loop livelock?

Livelock means threads keep retrying but nobody makes progress. When many threads hit one key, some will retry several times. But each failed CAS means another thread succeeded. So the system as a whole always makes progress. If one key is that busy, split it, or move to a fair lock where threads wait in line.

Token bucket vs leaky bucket in one line each?

A token bucket limits the average rate and allows bursts up to its capacity. A leaky bucket lets requests out at a constant rate. It absorbs bursts by queueing or refusing them.

How accurate is the sliding window counter?

It assumes requests in the previous window were spread evenly. Cloudflare reported a very small error rate on real traffic. That is good enough for API quotas. It is not good enough for hard security limits.

What status code and headers do you return?

Return 429 Too Many Requests with Retry-After in seconds. Also send limit, remaining and reset headers. These are X-RateLimit-* or the IETF RateLimit fields. Use 503 for load shedding instead. Load shedding means refusing work because the server itself is overloaded, not because a client used up its quota.

Where does the tenant id come from?

It comes from the logged-in identity, as a claim in the JWT. Never take it from a header or query parameter the client controls. Otherwise a client can keep changing ids to dodge the limits.

How do you stop the map growing forever?

Remove entries after a period of no use (Caffeine expireAfterAccess), or run a regular sweep. Removing a full token bucket loses nothing, because a new one also starts full.

Cheat sheet
  • tryAcquire(int permits). Patterns: Strategy, Factory, Registry and a swappable delegate.
  • Token bucket: refill on each call with min(capacity, tokens + elapsed × rate). Use CAS on a State record that never changes.
  • Sliding log: exact, O(N) memory, one lock per limiter. Counter: prev × (1 − f) + curr, O(1) memory.
  • A fixed window allows 2N at a boundary. A leaky bucket smooths the output.
  • Registry: use computeIfAbsent, do no slow work inside it, and remove idle keys with Caffeine.
  • Pass in a TimeSource. Use nanoTime and Math.max(now, last).
  • Many pods: Redis with Lua, the Redis TIME clock, and hash tags. Fail open for quotas.
  • Return 429 with Retry-After. Take the tenant from the JWT.
