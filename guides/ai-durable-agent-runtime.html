Durable agent runtime platform

Design a platform that runs long AI agents. The agents call tools, sometimes wait for a human to approve, and share a limited pool of sandboxes. If a machine crashes, no finished work may be lost.

Time-box: 45–60 min Seen: Tekion Staff (AI) system design round, Sep 2026. Deep agent and MCP questions at EPAM, Mastercard and Deloitte.
TekionEPAMMastercardDeloitte
In 30 seconds
  • This is not a chatbot. It is a workflow engine that never forgets, with an AI model (an LLM) inside it.
  • Every step is written to a history log. After a crash, we rebuild the run by reading the log. Steps already recorded are never run again.
  • A worker may run a step more than once. A unique key per action makes sure the real effect still happens only once.
  • Sandboxes are scarce. We give each customer a quota, take turns fairly, and only start work when there is room.
Picture it

A railway reservation chart. Every booking step is written in the register before the next clerk acts. If a clerk faints mid-shift, the next one reads the register and continues from the last entry. Nobody books the same berth twice.

Words you'll see
Agent
An AI model that decides on its own which tool to call next, and when it is done.
LLM
Large language model. The AI model, such as Claude, that reads text and writes an answer.
Durable execution
Running a long job so that a crash never loses finished steps. The job continues from where it stopped.
Event history and replay
A log of everything that happened in a run. Replay means reading that log to rebuild where the run is.
Idempotency key
A unique ID sent with an action. If the same action arrives twice, the receiver sees the same key and does it only once.
Lease
A short, timed claim on a task. If the worker dies and the time runs out, another worker can take the task.
Sandbox
A sealed mini-computer where untrusted code runs. It cannot touch other customers' data or the host machine.
MCP
Model Context Protocol. A standard way for an AI app to connect to tools and data sources.

01What the interviewer is grading

Durability model

How you keep progress safe. Show a step history log, checkpoints and actions that are safe to repeat. "We retry" is not an answer.

Scheduling under scarcity

How you share a fixed pool of sandboxes. Show limits on new work, fair shares, priorities, and how sandboxes start and stop.

Agent semantics

How the agent works. Cover the agent loop, tools, human approval, memory, MCP, and limits on cost and number of steps.

Product surface

What callers use. Cover starting a run without waiting, live updates, webhooks, approvals and quality tests (evals).

Tekion's question packs six requirements into one sentence. Repeat all six back to the interviewer. Each one is checked.

Go deeper: the Tekion prompt

Tekion's question packs six hard requirements into one sentence. First, agents call tools. Second, runs are long, and a human may approve something mid-run. Third, workflows have branches, loops and fan-out (one step splitting into many parallel steps). Fourth, each run gets an isolated sandbox from a shared, limited pool used by many customers. Fifth, the caller can either start a run and forget it, or watch it live step by step. Sixth, a crash must lose no data. The same interview round then asked for an eval pipeline, a way to test the agents' quality. Interviewers check that you cover every requirement. They also check that your crash story is precise.

Functional

  • Register agents, tools and workflows, each with a version number
  • Start a run and get a run ID back at once, or start it and watch
  • Step types: LLM call, tool call, code in a sandbox, approval, branch, loop, fan-out (map) and join
  • Pause, resume, cancel, or retry from a chosen step
  • Live event stream and webhooks
  • Eval pipeline to test agents and workflows

Non-functional

  • 500 customers (tenants), 2M runs a day, 30 steps per run on average
  • After any single crash, no finished step is lost or done twice
  • When capacity is free, the first step starts within 2 seconds for 95 out of 100 runs (p95 < 2 s)
  • Fair share: no tenant goes over its sandbox quota
  • Strong isolation between tenants' code and data
  • Run history kept 30 days in fast storage (hot) and 1 year in cheap storage (cold)

Out of scope

  • Training and hosting models
  • A drag-and-drop workflow builder screen
  • An agent marketplace and billing screens

We save the event and the next task together, in one database transaction. Either the step is recorded along with its follow-up work, or nothing is saved. That is what lets you prove "no data loss".

Go deeper: API notes and data model table

Some callers start a run and forget it. They keep the run ID and receive webhooks. Each webhook is signed with HMAC (a secret-key signature that proves it came from us) and retried with growing waits if it fails. Other callers want to watch. They subscribe to the events endpoint, which can replay from any sequence number. So a watcher who joins late or reconnects still sees the whole run. The idempotency key means that if a caller sends the same start request twice, it gets back the same run.

The orchestrator decides what happens next. It never calls an LLM or a tool itself. Workers do that. Temporal splits the work the same way, into "workflows" that decide and "activities" that act. If asked "build or buy?", design the mechanism yourself, then say you would run Temporal underneath.

Go deeper: each component and build vs buy
  • Run API checks the workflow version, writes a RunStarted event and the first task, and returns the run ID.
  • Orchestrator wakes up when a task finishes. It loads the run's history and replays the workflow definition to decide the next steps. Replay always gives the same answer, because it reads recorded outputs (branch choices, loop counters, fan-out). It then appends the events and the new tasks in one transaction. It never calls an LLM or a tool. Those give different results each time, so they live in workers. Temporal splits work the same way, into workflows and activities.
  • Scheduler sends each task to the right kind of worker. LLM and web-tool tasks are cheap and mostly wait on the network. Virtual threads or reactive clients handle them well. Sandbox tasks need a free sandbox slot, so they pass through the admission gate.
  • Workers take a task on a lease and send a heartbeat (a regular "I'm still alive" signal). They run the task and report the result. If heartbeats stop, the task becomes visible again, and another worker picks it up.
  • Sandbox pool uses small virtual machines (Firecracker microVMs) or gVisor containers. There is one per run or per step, with no shared files. Outgoing traffic goes through a proxy that allows only listed sites. Secrets are injected and expire quickly. A warm pool of already-booted VMs makes start-up take under a second.
  • Event gateway serves watchers of a run. It first reads history after the sequence number they ask for. Then it follows Kafka, which is split (partitioned) by run_id, for live events.
  • Approval service creates an approval record and notifies people by email, Slack or the calling app's webhook. When someone decides, it sends a signal to the run.
Build or buy

Several products give you durable execution off the shelf. These are Temporal (its Java SDK fits a Spring team), AWS Step Functions, Restate and DBOS. LangGraph with a Postgres checkpointer gives you agent graphs that can pause (interrupts), in Python. Temporal also ships a LangGraph plugin. In the interview, design the mechanism yourself, because they want to see that you understand it. Then say you would run Temporal under the hood, unless the platform has unusual scheduling needs. On the worker side, Spring AI gives you the ChatClient, tool calling, and starters for MCP clients and servers.

06Deep dives

6.1 Durable execution: a history log of every step

  • A run's state is built by reading its events in order. Any server can rebuild a run this way. LLM and tool results are read from the log, not run again.
  • So the orchestrator code must be deterministic. It may not read the clock, use random numbers or do any I/O.
  • Each LLM turn and each tool call is its own step. A crash after 25 minutes loses only the call that was in progress.
Show Java: onTaskCompleted
sealed interface RunEvent permits RunStarted, StepScheduled, StepCompleted, StepFailed,
        ApprovalRequested, ApprovalDecided, TimerFired, RunCompleted {}
record StepScheduled(String stepId, int attempt, StepKind kind, String inputRef) implements RunEvent {}
record StepCompleted(String stepId, int attempt, String outputRef, long costMicros) implements RunEvent {}

@Transactional   // event append + next tasks + outbox row commit atomically on the run's shard
public void onTaskCompleted(TaskResult r) {
    List<RunEvent> history = events.load(r.runId());
    if (history.stream().anyMatch(e -> e instanceof StepCompleted c && c.stepId().equals(r.stepId()))) {
        return;                                    // duplicate completion from a retried worker: ignore
    }
    long seq = events.append(r.runId(), new StepCompleted(r.stepId(), r.attempt(), r.outputRef(), r.costMicros()));
    WorkflowState state = WorkflowState.replay(definitions.get(r.runId()), history, r);   // pure function
    for (StepScheduled next : state.nextSteps()) {          // branch, loop, map: decided from recorded outputs
        events.append(r.runId(), next);
        tasks.enqueue(r.runId(), next);
    }
    outbox.publish(r.runId(), seq);                         // relayed to Kafka for watchers and webhooks
}

Go deeper: replay, heartbeats and continue-as-new

A run's state is the result of reading its events in order (a "fold" over events). After a crash or a new deployment, any orchestrator server rebuilds the run by replaying its history. Recorded LLM and tool results come back from the log. They are not run again. That is why the orchestrator code must be deterministic. It may not use the clock, random numbers or I/O. Those values must come from events instead. It is also why each LLM call is a recorded step. The model would not give the same answer twice.

Long steps send heartbeats. A heartbeat extends the lease and records progress, such as the last page processed. Checkpointing inside an agent loop works because each LLM turn and each tool call is its own step. So a crash after 25 minutes loses at most the call in progress. History growth is a risk, because loops and long agents can create thousands of events. Cap the history per run. When it is full, "continue-as-new" starts a fresh history from a snapshot. Temporal does the same.

6.2 Making tool actions happen exactly once

Read-only

These tools change nothing, so retry them freely.

Idempotent writes

Retry with the key runId:stepId. The receiving system spots the repeat and ignores it.

Non-idempotent writes

Record STARTED first. On a retry, ask the receiving system if it already happened. If unsure, escalate to a human.

Go deeper: at-least-once execution

Each step runs at least once, and sometimes more. A worker can finish a tool call and then crash before reporting it. So every real-world effect must be safe to repeat (idempotent).

  • Every tool call gets the key runId:stepId, which stays the same on every attempt. We pass it to the receiving API in a header, the way Stripe does. The tool provider then ignores repeats.
  • Some tools cannot spot repeats. For those, the tool_call table records STARTED before the call. On a retry that finds STARTED but no result, the step first asks the other system, "Was envelope X sent?" Only then does it act. If it still cannot tell, it escalates to a human.
  • Sort tools into three groups. Read-only tools retry freely. Idempotent writes retry with the key. Non-idempotent writes need an approval or a check with the other system (reconciliation).

6.3 Human approval in the middle of a run

Record ApprovalRequested, start a timer, and release everything. Whichever comes first, the decision or the timer, wins. If the sandbox has files worth keeping, save a snapshot to S3.

Go deeper: LangGraph interrupts, Temporal signals, NDA example

An approval step records ApprovalRequested. It creates the approval record and a timer task, for example 48 hours. The run then releases every resource, with no thread and no sandbox held. When someone decides, the approval API records ApprovalDecided as a signal and queues an orchestrator task. Whichever arrives first, decision or timer, wins. Replay ignores the other one. If the run had a sandbox with useful files, save a snapshot of its file system to S3 first. Restore it when the run resumes.

LangGraph does the same thing with interrupt() inside a node, a checkpointer, and Command(resume=...) on the same thread_id. Be careful here. On resume, LangGraph re-runs the whole node from the start. So any code before the interrupt must be safe to repeat. Temporal uses signals and durable timers, and a waiting workflow costs nothing.

Legal-tech example

Take an NDA workflow. An LLM extracts the parties and terms. Each clause is compared with the company playbook in parallel, then the results are joined. The agent loops on redlines up to 3 times. Legal must approve before esign.send. The approval card shows the changes and the agent's reasoning. The send uses the key run:step, so a retry cannot send two envelopes.

6.4 Sharing a limited pool of sandboxes

Quotas

Each tenant gets a guaranteed share, for example 50 sandboxes. It can burst up to 200 when the pool is idle.

Fair queuing

The tenant using least compared to its share goes next. A tenant firing 100k runs waits behind its own share.

Admission and preemption

Start work only when slots are free. Pause and evict low-priority work that has a saved checkpoint.

Isolation

One Firecracker microVM per run. It boots in about 125 ms, and a warm pool helps. Outgoing traffic only to allowed sites.

Go deeper: pool details
  • Quotas: each tenant has a guaranteed share, for example 50 sandboxes at once. It also has a burst ceiling of 200, usable only when the pool is idle.
  • Fair queuing: each tenant has its own queue. The scheduler picks the tenant with the lowest usage compared to its weight. This is called deficit round robin or weighted fair queuing. Inside one tenant, it goes by priority. A tenant firing 100k runs waits behind its own share.
  • Admission control: a run starts only if its tenant has a free run slot. Otherwise it stays QUEUED, and the caller can see its place in line. Queues have a size limit. Past that backlog limit, we reply 429 (too many requests).
  • Preemption: low-priority burst work can be checkpointed and pushed out to make room for guaranteed work. This is safe, because the state lives in history and sandbox snapshots.
  • Isolation: each tenant run gets its own microVM. Firecracker boots in about 125 ms, and we keep a warm pool. Untrusted code never shares a kernel with other tenants. Each tenant has its own network rules. CPU and memory are capped with cgroups. Each run has a time budget and a token budget.

6.5 Agent loop, workflows, MCP, memory and evals

Workflow when path is known

  • Cheaper, easy to test, predictable
  • Cannot handle an unknown number of steps

Chaining, routing, fan-out, or one model checking another's work (evaluator-optimiser).

Agent (ReAct loop)

  • Handles open-ended tasks
  • Needs limits on steps, cost and time, and a check for repeats

One node of a workflow can be an agent.

  • MCP: our platform is the host. It opens one client per MCP server. Servers offer tools, resources and prompts.
  • Memory: each run has its own state, updated by merge rules (reducers). Each tenant has long-term memory. Agents hand each other summaries, not full transcripts.
  • Evals: keep a set of golden tasks with the expected tool path and forbidden actions. Block releases in CI if they fail. In production, watch how often humans reject approvals.
Go deeper: agent semantics, MCP, shared memory and the eval pipeline

Follow Anthropic's "Building effective agents". Use a workflow where the path is known. Workflow patterns include prompt chaining, routing, parallel steps, orchestrator-workers and evaluator-optimizer. Use an autonomous agent only where you cannot predict the number of steps. The platform supports both, because a workflow node can be an agent.

  • Agent step is a ReAct loop (reason, then act). The LLM proposes tool calls. The platform checks the arguments against the tool's schema. It checks the policy, such as "does this need approval?". It runs the tools as child steps, adds the results, and repeats. The loop stops on a final answer, maxSteps, the cost budget, the time limit, or the same call repeated.
  • Branches decide using recorded outputs. Loops keep a counter in state, with a hard maximum. Fan-out schedules N child steps (or child runs). A join step then waits for all of them, any one, or a quorum (enough of them). Fan-out width is capped per tenant.
  • MCP: the platform is the MCP host. For each MCP server an agent uses, a worker holds an MCP client connection. Servers offer three things. Tools are actions the model chooses to call, such as esign.send. Resources are context the app provides, such as a contract file or a schema. Prompts are reusable templates. Remote servers use Streamable HTTP with OAuth login. Local ones use stdio inside the sandbox. The 2026-07-28 spec makes the protocol stateless, with metadata on each request and a server/discover call. It deprecates sampling. It adds a Tasks extension that returns a durable handle for long-running tool calls. That fits neatly onto a waiting step.
  • Run-scoped shared state (a "blackboard"): a typed state object kept in history. Each step writes updates through reducers, which are merge rules. Examples are "append to a list", "last write wins" and "merge maps". This is LangGraph's state-plus-reducers model, which EPAM asked about. If parallel branches write the same key, use a reducer, not a race.
  • Long-term memory: each tenant (and each user or agent) has a vector store plus key-value facts. An explicit "remember" step writes to it. Retrieval reads from it at the start of a run. Scope memory by tenant ID. Never let one tenant's agent read another's memory.
  • Hand-offs between agents pass a short summary and links to files in S3, not the full transcript. This keeps the context size under control.

Offline, before release

  • Golden tasks per agent: input, expected outcome, allowed tool path, forbidden actions
  • Run them in sandboxes against recorded or fake tools, replaying from real history
  • Measure task success, tool-call accuracy, steps and cost per success, speed, and policy breaks
  • Use an LLM as judge for open-ended output, checked against human labels
  • Block CI when a prompt, model, tool or workflow version changes, comparing with the current version on the same set

Online, in production

  • Send a sample of finished runs to an eval queue for judge and human review
  • Approval rejection rate per agent, a strong quality signal
  • Retries, loops hitting their maximum, budgets running out, tool error rates
  • Release new agent versions to a small slice of runs first (canary), and roll back if metrics drop
  • For retrieval (RAG) steps, measure retrieval recall and faithfulness, as in the RAG guide

07Scaling, failure handling and consistency

FailureWhat happens
Worker diesThe lease runs out and the next attempt starts. The idempotency key stops double effects.
Orchestrator diesIt keeps no state of its own, so any server replays. Unsaved work rolls back.

Kafka downRuns continue. Watchers replay from history later.

At 10 times the load, sandbox capacity and LLM rate limits break first. The event table comes next.

Go deeper: full failure table, backpressure, multi-region, guardrails
FailureWhat happens
Worker dies mid-stepThe lease runs out and the task is queued again with attempt + 1. The idempotency key prevents double effects.
Orchestrator node diesIt keeps no state. Any server handles the run's next completion by replaying. Unsaved transactions roll back, so there is no half-finished state.
Sandbox host diesThe step fails with an error that allows retry. It resumes from the last snapshot or restarts the step.
LLM provider outageThe gateway switches provider. If it can't, tasks wait with random delays (jitter) while runs stay safely saved.
Kafka or event gateway downRuns continue. Watchers reconnect and replay from history. The outbox catches up later.
Database shard failoverA replica kept in sync takes over. Saved events survive, so no data is lost within the region (RPO 0).
Bad deploy of workflow codeWorkflow definitions have versions, and running runs keep theirs. Replay tests in CI catch code that is not deterministic.
  • First to break at 10×: sandbox capacity and LLM rate limits. Fix with more machines, smaller VMs and tighter quotas. Next is the event table. Fix with more shards by run_id, and by archiving to S3.
  • Backpressure: callers can see queue depth per tenant. Past the backlog limit, we reply 429. The scheduler never hands out more sandboxes than exist.
  • Multi-region: a run lives in one region, on its shard. Tenants are pinned to a region when the law requires data to stay there. Failover to another region uses copying that lags slightly behind. So a little recent data could be lost (a small RPO), and we accept that openly.
Guardrails

Prompt injection is the main agent risk. It means hidden instructions inside tool results or web pages that try to steer the model. Treat tool output as data, never as commands. Tools that write need policy checks and approvals. Outgoing traffic goes only to allowed sites. Secrets never enter the model's context. Personal data under DPDP (India's data protection law): show agents as little as possible. Mask personal data in logs and traces. Honour deletion requests across history and S3, by destroying each tenant's encryption keys (crypto-shredding). Run in-region where the law requires it. The DPDP Rules' core duties apply from 13 May 2027. Tenant isolation: use microVM sandboxes, credentials and memory scoped to each tenant, enforced quotas, and an audit trail of every tool call and approval. Cost: the gateway enforces a token and dollar budget per run.

08Trade-offs

Temporal default

  • Proven durability, Java SDK, signals and timers
  • Strict rules on deterministic code, and one more cluster to run

This problem, unless scheduling is what makes your product special.

Own engine on Postgres + Kafka

  • Full control of fair scheduling and sandboxes
  • Years of tricky cases, such as timers, versions and replay

You have a strong platform team.

Firecracker microVMs untrusted code

  • Isolation as strong as a virtual machine, fast boot

09Mistakes that got candidates rejected

Rejected for this
  • Running an agent as one long loop in a pod's memory and saying "we will retry the run". A crash after 40 minutes then repeats every tool call.
  • Holding a thread or a sandbox while waiting for a human to approve.
  • No plan for tools that change the real world being called twice.
  • Ignoring the shared, limited pool. No quotas, no fair scheduling, no admission gate.
  • Running untrusted code from many tenants in containers that share a kernel, with open internet access.
  • Being vague about evals. No golden tasks, no checks on the tool path, no release gate.
  • Not covering every part of the question. Tekion's question lists six requirements, and each one is checked.

10Quick check

Why must the orchestrator never call the LLM itself?

Workers call the LLM and save the result as a step event. When the orchestrator replays, it reads that saved result from history. So replay always gives the same answer.

A worker sends the envelope, then crashes before reporting. What prevents a second envelope?

A step can run more than once. The e-sign service sees the same key on the retry and does not send again. That makes the effect happen exactly once. Checking with the service (reconciliation) also works.

A run waits 48 hours for legal approval. What does it hold?

The run gives back its threads and sandboxes. If the sandbox has useful files, save a snapshot to S3 and restore it when the run resumes.

One tenant fires 100k runs. How do other tenants stay unaffected?

The big burst waits behind its own share of the pool. The admission gate and 429 (too many requests) replies keep the backlog bounded.

11Follow-up questions interviewers asked

What exactly guarantees "no data loss"?

Every change of state is an event. It is appended in the same transaction as the tasks it causes, on a replicated database. Workers run each task at least once, using leases. Results are de-duplicated by (run, step, attempt). Actions with real-world effects carry idempotency keys. Nothing important lives only in a worker's memory, a Kafka topic or Redis.

How is an agent different from a chain? When would you not use one? (Adobe, EPAM)

A chain, or workflow, follows a path fixed in advance. An agent lets the LLM choose the next tool and decide when to stop. Use workflows when the steps are known, because they are cheaper, easy to test and have predictable speed. Use agents for open-ended tasks. Give them limits on steps, cost and time, plus human checkpoints.

How does the caller watch a run live without hammering the database?

Use SSE (server-sent events, a one-way live stream over HTTP) from the event gateway. It first replays history after the client's sequence number. Then it follows Kafka, partitioned by run_id. LLM token deltas, the words as they are written, are streamed but not stored as events. Only the final output is stored. Callers who start and forget get webhooks instead.

MCP: what are host, client and server, and tools vs resources? (Mastercard)

The host is the AI application that coordinates everything. It creates one client per server connection. Servers offer capabilities. Tools are actions the model decides to call, with inputs described in JSON Schema. Resources are read-only context data that the app chooses to attach. Prompts are reusable templates that the user or app picks. For transport, local servers use stdio. Remote servers use Streamable HTTP with OAuth.

A fan-out of 500 children: what can go wrong?

The history grows too big, and 500 tasks hit the pool at once (a thundering herd). Use child runs, each with its own history. Limit how many run at once per fan-out, for example 20. Make the join count completions in a way that is safe to repeat. Decide what happens if some fail: fail fast, best effort, or quorum.

You change an agent's prompt while 10,000 runs are mid-flight. What happens?

Each run stays on the agent and workflow versions it started with. New runs get the new version once it passes the eval gate. Allow moving a run to the new version only on purpose, and only between steps.

How do you stop an agent from looping forever or burning money?

Set maxSteps. The LLM gateway checks a token and dollar budget per run before each call. Add a wall-clock timeout. Detect the same tool call repeated. When a limit is hit, escalate to a human.

13Cheat sheet

Cheat sheet
  • Numbers: 2M runs a day, 2,100 steps a second at peak, 28k open runs, 4,000 sandboxes at peak.
  • Save the event, the next task and the outbox row in one transaction on the run's shard.
  • The orchestrator replays history and always decides the same way. Workers make the LLM and tool calls.
  • Workers claim tasks with SKIP LOCKED and send heartbeats. The reaper re-queues lost tasks.
  • Tools come in three kinds. Read-only, idempotent (key run:step), and non-idempotent (approval or reconcile).
  • Approvals release all resources and set a durable timer. The decision or the timer, whichever comes first, wins.
  • Pool: quotas, weighted fair queuing, an admission gate, preemption and microVMs.
  • Build vs buy: design it yourself, then run Temporal underneath.
