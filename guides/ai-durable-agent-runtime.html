Durable agent runtime platform

Design a platform that runs AI agents for other applications: agents call tools, run for minutes to hours, pause for human approval, chain into workflows with branches, loops and fan-out, execute in isolated sandboxes on a shared, limited compute pool, and never lose progress when a component crashes. A senior answer recognises this as a durable workflow engine with an LLM inside, not a chatbot.

01What the interviewer is grading

Tekion's prompt packs six hard requirements into one sentence: tool calls, long runs with human approval mid-run, workflows with branches, loops and fan-out, isolated sandboxes on a shared limited pool across tenants, fire-and-forget or live step-by-step watching, and no data loss on a crash. The same loop then asked for an eval pipeline. Interviewers check that you hit every one of those and that your crash story is precise.

Durability model

Event-sourced step history, checkpoints, at-least-once execution with idempotent side effects. "We retry" is not an answer.

Scheduling under scarcity

Admission control, fair share across tenants, priorities, sandbox lifecycle on a fixed pool.

Agent semantics

The agent loop, tools, human-in-the-loop, memory, MCP, and bounding cost and iterations.

Product surface

Async run API, live event stream, webhooks, approvals, eval and observability.

02Clarify and scope

  • Who defines agents? Client applications register agent definitions (model, prompt, tools) and workflow graphs. Declarative DSL (JSON/YAML graph) or code (SDK)? Choose DSL for multi-tenant safety, allow code steps inside sandboxes.
  • What do tools look like? HTTP endpoints of the calling app, MCP servers, or code executed in our sandbox?
  • Run length and volume? Typical and worst case; how long can a human approval wait (hours, days)?
  • Sandbox needs? Run arbitrary code, browse the web, access the filesystem? Network egress allowed?
  • Delivery semantics? Exactly-once effects for tools such as "send payment" or "send contract for signature"?
  • Watching? Live token streaming of LLM steps, or step-level events only?

Functional

  • Register agents, tools, workflows (versioned)
  • Start run: async with run id, or sync-watch
  • Steps: LLM call, tool call, code in sandbox, approval, branch, loop, map (fan-out) and join
  • Pause, resume, cancel, retry from step
  • Live event stream and webhooks
  • Eval pipeline for agents and workflows

Non-functional

  • 500 tenants, 2M runs/day, avg 30 steps
  • No lost or duplicated committed steps after any single crash
  • Start-to-first-step p95 < 2 s when capacity is free
  • Fair share: no tenant above its quota of sandboxes
  • Strong isolation between tenants' code and data
  • Run history retained 30 days hot, 1 year cold

Out of scope

  • Model training and hosting
  • A visual workflow builder UI
  • Agent marketplace and billing UI

Conclusions: the orchestrator's write path (event appends) is a few thousand writes per second, comfortable for sharded Postgres or Cassandra. Wall time is long but CPU time is short, so runs must not hold threads or sandboxes while waiting. Sandboxes are the scarce resource, so the design needs admission control and fair queuing around them; that is exactly what "limited compute pool" in the prompt is fishing for.

Writing the event and the next task in one local transaction (same shard, keyed by run_id) is what makes "no data loss" provable: a step is either recorded with its follow-up work, or not at all.

06High-level architecture

Client appsSDK / REST→ Run APIauth, idempotency→ Orchestratordeterministic, event-sourced⇄ History + tasksPostgres shards
Task queuesper kind, per tenant→ Schedulerfair share, admission→ LLM workersvia LLM gateway Tool workersHTTP / MCP clients Sandbox poolFirecracker / gVisor
Workers→complete(task, result) Orchestrator→outbox Kafkarun.events→ Event gatewaySSE watchers Webhooks Eval + analytics

Figure: control plane (orchestrator and history), execution plane (scheduler and workers), and the event plane for watchers.

  • Run API: validates the workflow version, writes RunStarted and the first task, returns the run id.
  • Orchestrator: when a task completes, loads the run's history, replays the workflow definition deterministically to decide the next steps (branch on recorded outputs, loop counter, fan-out), and appends events plus new tasks in one transaction. It never calls an LLM or tool itself; those are non-deterministic and live in workers. This is Temporal's workflow/activity split.
  • Scheduler: dispatches tasks to workers by kind. LLM and HTTP tool tasks are cheap and I/O-bound (virtual threads or reactive clients); sandbox tasks need a sandbox slot and go through admission control.
  • Workers lease a task with a heartbeat, execute, report the result. A missed heartbeat makes the task visible again for another worker.
  • Sandbox pool: microVMs (Firecracker) or gVisor containers, one per run or per step, no shared filesystem, egress through an allow-listed proxy, secrets injected short-lived, warm pool of pre-booted VMs for sub-second start.
  • Event gateway: watchers subscribe to a run; it reads history after the requested sequence, then tails Kafka (partitioned by run_id) for live events.
  • Approval service: creates an approval record, notifies (email, Slack, the calling app's webhook), and on decision sends a signal to the run.
Build or buy

Temporal (Java SDK fits a Spring shop), AWS Step Functions, Restate or DBOS give durable execution off the shelf; LangGraph with a Postgres checkpointer gives agent graphs with interrupts in Python, and Temporal ships a LangGraph plugin. In the interview, design the mechanism yourself (they want to see you understand it), then say you would run Temporal under the hood unless the platform's scheduling needs are unusual. Spring AI provides the ChatClient, tool calling and MCP client/server starters for the worker side.

07Deep dives

7.1 Durable execution: event-sourced step history

A run's state is a fold over its events. On crash or redeploy, any orchestrator node rebuilds the run by replaying history: recorded LLM and tool results are returned from the log, not re-executed. That is why the orchestrator code must be deterministic (no clock, random or I/O; those come from events), and why an agent's LLM call is a recorded step: the model would not give the same answer twice.

sealed interface RunEvent permits RunStarted, StepScheduled, StepCompleted, StepFailed,
        ApprovalRequested, ApprovalDecided, TimerFired, RunCompleted {}
record StepScheduled(String stepId, int attempt, StepKind kind, String inputRef) implements RunEvent {}
record StepCompleted(String stepId, int attempt, String outputRef, long costMicros) implements RunEvent {}
// ...other records

@Transactional   // event append + next tasks + outbox row commit atomically on the run's shard
public void onTaskCompleted(TaskResult r) {
    List<RunEvent> history = events.load(r.runId());
    if (history.stream().anyMatch(e -> e instanceof StepCompleted c && c.stepId().equals(r.stepId()))) {
        return;                                    // duplicate completion from a retried worker: ignore
    }
    long seq = events.append(r.runId(), new StepCompleted(r.stepId(), r.attempt(), r.outputRef(), r.costMicros()));
    WorkflowState state = WorkflowState.replay(definitions.get(r.runId()), history, r);   // pure function
    for (StepScheduled next : state.nextSteps()) {          // branch, loop, map: decided from recorded outputs
        events.append(r.runId(), next);
        tasks.enqueue(r.runId(), next);
    }
    outbox.publish(r.runId(), seq);                         // relayed to Kafka for watchers and webhooks
}

WHERE task_id = (SELECT task_id FROM task
                 WHERE kind = :kind AND status = 'READY' AND visible_at <= now()
                 ORDER BY priority DESC, visible_at LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING *;

Long steps heartbeat (extend the lease and record progress, such as the last processed page). Checkpointing inside an agent loop: each LLM turn and each tool call is its own step, so a crash after 25 minutes loses at most the in-flight call. History growth: loops and long agents can create thousands of events; cap history per run and "continue-as-new" with a snapshot (Temporal does the same).

7.2 Exactly-once effects for tools

Execution is at-least-once: a worker can finish a tool call and crash before reporting. So effects must be idempotent.

  • Every tool call gets an idempotency key runId:stepId (stable across attempts) passed to the downstream API (Stripe-style header). The tool provider dedupes.
  • For tools that cannot dedupe, the tool_call table records STARTED before the call; on retry with STARTED and no result, the step queries the downstream system ("did envelope X get sent?") before acting, or escalates to a human.
  • Classify tools as read-only (auto-retry freely), idempotent writes (retry with key) and non-idempotent writes (require approval or reconciliation).

7.3 Human approval mid-run

An approval step appends ApprovalRequested, creates the approval record and a timer task (for example 48 hours), and the run releases every resource: no thread, no sandbox. The approval API appends ApprovalDecided as a signal and enqueues an orchestrator task; whichever of decision or timer arrives first wins (the other is ignored on replay). If the run had a sandbox with state, snapshot its filesystem to S3 before releasing it and restore on resume.

LangGraph models the same thing with interrupt() inside a node, a checkpointer, and Command(resume=...) on the same thread_id; note that on resume LangGraph re-runs the whole node from the start, so code before the interrupt must be idempotent. Temporal uses signals and durable timers, and a waiting workflow costs nothing.

Legal-tech example

An NDA workflow: extract parties and terms (LLM), compare with the playbook (fan-out per clause, join), loop on redlines up to 3 times, then approval by legal before esign.send. The approval card shows the diff and the agent's reasoning; the send uses idempotency key run:step so a retry cannot send two envelopes.

7.4 Shared, limited compute pool across tenants

  • Quotas: each tenant has a guaranteed share (e.g. 50 concurrent sandboxes) and a burst ceiling (200) usable only when the pool is idle.
  • Fair queuing: per-tenant queues; the scheduler picks the tenant with the lowest usage relative to its weight (deficit round robin / weighted fair queuing), then by priority within the tenant. A tenant firing 100k runs waits behind its own share.
  • Admission control: runs start only if the tenant has run slots; otherwise they stay QUEUED and the caller sees their position. Bounded queues and 429 beyond a backlog limit.
  • Preemption: low-priority burst work can be checkpointed and evicted for guaranteed work, which is safe because state lives in history and sandbox snapshots.
  • Isolation: microVM per tenant run (Firecracker boots in ~125 ms; keep a warm pool), no shared kernel for untrusted code, per-tenant network policy, CPU and memory cgroups, wall-clock and token budgets per run.

7.5 Agent loop, workflows and MCP

Follow Anthropic's "Building effective agents": use workflows (prompt chaining, routing, parallelisation, orchestrator-workers, evaluator-optimizer) where the path is known, and an autonomous agent only where the number of steps cannot be predicted. The platform supports both because a workflow node can be an agent.

  • Agent step = ReAct loop: LLM proposes tool calls, platform validates arguments against the tool schema, checks policy (approval needed?), runs tools as child steps, appends results, repeats. Stopping conditions: final answer, maxSteps, cost budget, wall-clock limit, or repeated identical calls.
  • Branches evaluate on recorded outputs; loops carry a counter in state with a hard maximum; fan-out schedules N child steps (or child runs) and a join step waits for all, any, or a quorum; fan-out width is capped per tenant.
  • MCP: the platform is the MCP host; for each MCP server an agent uses, a worker holds an MCP client connection; servers expose tools (model-invoked actions such as esign.send), resources (application-provided context such as a contract file or schema) and prompts (reusable templates). Remote servers use Streamable HTTP with OAuth; local ones stdio inside the sandbox. The 2026-07-28 spec makes the protocol stateless with per-request metadata and a server/discover call, deprecates sampling, and adds a Tasks extension that returns a durable handle for long-running tool calls, which maps neatly onto a waiting step.

7.6 Memory shared between agents (Deloitte)

  • Run-scoped shared state (blackboard): a typed state object in history; each step writes updates through reducers (append to a list, last-write-wins, merge maps). This is LangGraph's state-plus-reducers model, which EPAM asked about. Parallel branches writing the same key need a reducer, not a race.
  • Long-term memory: per tenant (and per user or agent) vector store plus key-value facts, written by an explicit "remember" step, read by retrieval at the start of a run. Scope memory by tenant id; never let one tenant's agent retrieve another's.
  • Hand-offs between agents pass a compact summary and references to artefacts in S3, not the full transcript, to control context size.

7.7 Eval pipeline (Tekion asked for one)

Offline, before release

  • Golden tasks per agent: input, expected outcome, allowed tool trajectory, forbidden actions
  • Run in sandboxes against recorded or mocked tools (record and replay from real history)
  • Metrics: task success, tool-call accuracy (right tool, valid args), steps and cost per success, latency, policy violations
  • LLM-as-judge for open-ended output, calibrated against human labels
  • Gate in CI on prompt, model, tool or workflow version change; compare with the current version on the same set

Online, in production

  • Sample completed runs into an eval queue; judge and human review
  • Approval rejection rate per agent (a strong quality signal)
  • Retries, loops hitting max, budget exhaustion, tool error rates
  • Canary new agent versions to a slice of runs; roll back on metric drop
  • For RAG steps: retrieval recall and faithfulness as in the RAG guide

08Scaling, failure handling and consistency

FailureWhat happens
Worker dies mid-stepLease expires, task re-queued with attempt + 1; idempotency key prevents double effects.
Orchestrator node diesStateless; the next completion for that run is processed by any node via replay. Uncommitted transactions roll back, so no partial state.
Sandbox host diesStep fails with a retryable error, resumes from the last snapshot or restarts the step.
LLM provider outageGateway fails over; otherwise tasks back off with jitter while runs wait durably.
Kafka or event gateway downRuns continue; watchers reconnect and replay from history; outbox drains later.
Database shard failoverSynchronous replica promotes; committed events survive (RPO 0 within region).
Bad deploy of workflow codeWorkflow definitions are versioned; running instances keep their version; replay tests in CI catch non-determinism.
  • First to break at 10×: sandbox capacity (add nodes, smaller VMs, tighter quotas) and LLM rate limits; then the event table (more shards by run_id, archive to S3).
  • Backpressure: queue depth per tenant visible to callers; 429 above backlog limits; scheduler never overcommits sandboxes.
  • Multi-region: a run lives in one region (its shard); tenants pinned for residency; cross-region failover is async replication with a small RPO, accepted explicitly.
Guardrails

Prompt injection through tool results and web pages is the main agent risk: tool output is data, write tools need policy checks and approvals, egress is allow-listed, and secrets never enter the model context. PII under DPDP: minimise what agents see, redact in logs and traces, honour erasure across history and S3 (crypto-shred per-tenant keys), in-region execution where required; the DPDP Rules' core obligations apply from 13 May 2027. Tenant isolation: microVM sandboxes, tenant-scoped credentials and memory, quota enforcement, audit trail of every tool call and approval. Cost: per-run token and dollar budgets enforced by the gateway.

10Follow-up questions interviewers asked

What exactly guarantees "no data loss"?

Every state change is an event appended in the same transaction as the tasks it causes, on a replicated database. Workers are at-least-once with leases; results are deduplicated by (run, step, attempt); side effects carry idempotency keys. Nothing important lives only in a worker's memory, a Kafka topic or Redis.

How is an agent different from a chain? When would you not use one? (Adobe, EPAM)

A chain or workflow follows a predefined path; an agent lets the LLM choose the next tool and when to stop. Use workflows when the steps are known (cheaper, testable, predictable latency); use agents for open-ended tasks, with step, cost and time limits and human checkpoints.

How does the caller watch a run live without hammering the database?

SSE from the event gateway: initial replay from history after the client's sequence number, then tail Kafka partitioned by run_id. LLM token deltas are streamed but not stored as events; only the final output is. Webhooks for fire-and-forget callers.

MCP: what are host, client and server, and tools vs resources? (Mastercard)

The host is the AI application coordinating everything; it creates one client per server connection; servers expose capabilities. Tools are actions the model decides to invoke (with JSON Schema inputs). Resources are read-only context data the application chooses to attach. Prompts are reusable templates the user or app selects. Transports: stdio for local, Streamable HTTP with OAuth for remote.

A fan-out of 500 children: what can go wrong?

History bloat and a thundering herd on the pool. Use child runs (each with its own history), cap concurrency per fan-out (e.g. 20 at a time), make the join count completions idempotently, and decide partial-failure policy (fail fast, best effort, quorum).

You change an agent's prompt while 10,000 runs are mid-flight. What happens?

Runs are pinned to the agent and workflow versions they started with; new runs get the new version after it passes the eval gate. Allow explicit migration only at step boundaries.

How do you stop an agent from looping forever or burning money?

maxSteps, per-run token and dollar budget checked by the LLM gateway before each call, wall-clock timeout, detection of repeated identical tool calls, and escalation to a human when limits hit.

11Mistakes that got candidates rejected

Rejected for this
  • Running an agent as one long in-memory loop in a pod ("we will retry the run") so a crash after 40 minutes repeats every tool call.
  • Holding a thread or sandbox while waiting for human approval.
  • No idempotency story for side-effecting tools.
  • Ignoring the shared limited pool: no quotas, no fair scheduling, no admission control.
  • Containers with a shared kernel for untrusted multi-tenant code, with open egress.
  • Hand-waving "eval": no golden tasks, no trajectory checks, no release gate.
  • Not covering every clause of the prompt; Tekion's question lists six requirements and each is checked.
