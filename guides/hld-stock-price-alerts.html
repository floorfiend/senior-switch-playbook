Stock Price Change Alert System

Users set "notify me when RELIANCE crosses ₹3,000" or "when TCS moves more than 3% today". You must match a firehose of price ticks against tens of millions of standing alerts and push each fired alert exactly once, within seconds. A senior answer inverts the problem: index alerts by symbol and threshold so that each tick does a range scan, not a table scan.

01What the interviewer is grading

An Uber SDE-2 candidate (Apr 2026, rated "Very Hard") listed the expectation verbatim: push vs pull mechanism, DB design, API design, deep dive and trade-offs. In practice the grading splits into four things:

  • The matching insight. Do you scan every alert on every tick (fails at 50M alerts × 50k ticks/s), or keep per-symbol sorted thresholds so a tick touches only the alerts it actually crosses?
  • Push vs pull at two boundaries. Market data → matcher (push, streaming) and matcher → user (push notification / WebSocket, not client polling). You must say why at each boundary.
  • Correct-once semantics. No duplicate notifications when a matcher restarts or a price flaps around the threshold; no missed alerts when a tick gaps over the threshold.
  • Hot symbols and bursts. NIFTY or RELIANCE carry millions of alerts; a market-wide crash fires millions at once. Show where the system bends and how you protect the notification pipeline.

Related rounds probe the same muscles: Groww SDE-II asked a stock order system that must place buy / sell / stop-loss orders arriving via a queue within a 10 ms SLA (the feedback criticised missing multi-exchange support and scalability), and Upstox SDE-2 asked a trailing-loss system. A stop-loss is just a price alert whose action is "place order" instead of "send push".

02Clarify and scope

Questions to ask

  • Which alert types? Absolute crossing (above / below), percentage move vs previous close, percentage move within a window, trailing. Each changes the index you need.
  • One-shot or recurring? One-shot alerts are deleted on fire, which keeps the index small. Recurring ones need re-arm rules (hysteresis) or users get spammed when price oscillates.
  • Latency target? Retail apps accept "within 1–2 seconds of the tick". A stop-loss that places orders needs milliseconds (the Groww variant).
  • Delivery channels? Mobile push (FCM / APNs), in-app WebSocket, SMS, email. Push is best-effort; you own the "fired" record, the device owns display.
  • Price source? Exchange feed (NSE / BSE multicast via a vendor) gives last traded price (LTP) ticks. Ask whether to alert on LTP or on bid / ask.
  • Market hours and halts? Pre-open session, circuit limits, corporate actions (splits change every threshold).

Functional

  • Create, list, edit, delete alerts (limit ~100 per user)
  • Fire when the condition becomes true; notify via push + in-app
  • Alert history ("fired at ₹3,001.40 at 10:31:02")

Non-functional

  • Tick → notification p99 ≤ 2 s
  • No duplicates, no misses (gaps must still fire)
  • 99.95% availability during market hours
  • Survive 10× bursts on crash days

Out of scope

  • Order placement and risk checks (mention the hook)
  • Charting and quotes streaming
  • Building the exchange feed handler

The numbers say two things. The index fits in memory, so the matcher should be an in-memory service with a durable log behind it, not a database query per tick. And the bottleneck on a bad day is the notification fan-out (33k/s against FCM quotas), not matching.

  • User id comes from the JWT, never the body. Validate the symbol against the instrument master and reject thresholds that are already true at creation ("RELIANCE above ₹2,000" when it trades at ₹2,950) or offer to fire immediately.
  • Idempotency-Key on create stops a double-tapped button producing two alerts. If-Match with a version on PATCH avoids lost updates from two devices.
  • Money as decimal strings, never floats; store as NUMERIC(12,2) or paise as BIGINT.

06High-level architecture

Exchange feedNSE / BSE vendor→ Feed handlernormalise, coalesce→ Kafka tickskey = symbol→ Matcher shardsin-memory index
Mobile app→ API gatewayJWT→ Alert serviceCRUD→ Postgresalerts + outbox→ Kafka alert-changeskey = symbol→ Matcher shards
Matcher shards→ Kafka alert-firedkey = user→ Fire recorderinsert alert_events→ Notifierrate limit, batch→ FCM / APNs / WS gateway

Figure: three flows meeting at the matcher. Ticks and alert changes share the symbol key, so one matcher partition sees both in order.

  • Feed handler turns the vendor feed into (symbol, ltp, exchange_ts, seq). It coalesces: if RELIANCE ticks 40 times in 100 ms, matching only needs the min and max in that window, not every print. Publish (min, max, last) per 100 ms per symbol.
  • Alert service is plain Spring Boot CRUD. It writes the alert and an outbox row in one transaction; Debezium streams the outbox to alert-changes. No dual write.
  • Matcher is a Kafka Streams / plain consumer app. Each instance owns a set of partitions; for each owned symbol it keeps the sorted threshold index. It consumes both topics, so creates and ticks for a symbol are processed in a single thread in order.
  • Fire recorder inserts into alert_events with a unique key and flips the alert to FIRED with a conditional update. This is the exactly-once point.
  • Notifier looks up device tokens, applies per-user rate limits and digesting ("5 of your alerts fired"), and calls FCM / APNs with retries. The in-app path goes through a WebSocket gateway.

07Deep dives

7.1 Matching: invert the query

The naive loop is "for every tick, for every alert on that symbol, check the condition". With 2.5M alerts on RELIANCE and 5 ticks/s, that is 12.5M comparisons per second for one symbol. Instead, per symbol keep:

  • above: thresholds sorted ascending. On a tick window with max price hi, fire every alert with threshold ≤ hi, i.e. pop from the head until threshold > hi.
  • below: thresholds sorted descending. Fire every alert with threshold ≥ lo.

Cost is O(log n) to find the boundary plus O(k) for the k alerts that actually fire, which you must do anyway. Using the window's min and max rather than the last price means a gap ("opened at ₹3,020 after closing at ₹2,980") still fires, and so does a spike that reverted within 100 ms.

final class SymbolIndex {                       // owned by one matcher thread: no locks
    private final TreeMap<Long, List<Long>> above = new TreeMap<>();   // paise → alertIds
    private final TreeMap<Long, List<Long>> below = new TreeMap<>(Comparator.reverseOrder());

    List<Long> onTick(long lo, long hi) {
        List<Long> fired = new ArrayList<>();
        drain(above.headMap(hi, true), fired);   // thresholds <= hi
        drain(below.headMap(lo, true), fired);   // thresholds >= lo (reverse order)
        return fired;
    }
    private static void drain(SortedMap<Long, List<Long>> hit, List<Long> out) {
        hit.values().forEach(out::addAll);
        hit.clear();                             // one-shot: removed from the index
    }
}

Percentage alerts collapse into the same structure. "TCS moves more than 3% today" against previous close ₹4,000 is two absolute thresholds, ₹4,120 above and ₹3,880 below, computed when the session opens (or when the alert is created mid-session). Re-compute them at the next session's open. Redis sorted sets (ZRANGEBYSCORE alerts:RELIANCE:above -inf hi) are an acceptable alternative if you want shared state instead of in-process memory; you trade a network hop per tick for easier failover.

The one place pull is right: a daily-close alert type ("notify me if it closes below X") can be a batch job after market close. Say this; it shows you choose per requirement, not by fashion.

7.3 Fire exactly once

Kafka gives at-least-once. A matcher can fire an alert, crash before committing its offset, restart, replay the tick and fire again. Defence in depth:

  1. Fired events carry a deterministic id: alertId + ":" + fireSeq (fireSeq increments on each re-arm, so a recurring alert fires once per arm).
  2. The fire recorder does INSERT INTO alert_events ... ON CONFLICT DO NOTHING and UPDATE alerts SET status='FIRED', version=version+1 WHERE alert_id=? AND status='ACTIVE' AND fire_seq=?. Only the first wins; the replay is a no-op.
  3. The notifier sends with the same id as a collapse key, so even a duplicate push replaces rather than stacks on the device.

Hand-wave "Kafka exactly-once" and a strong interviewer will ask what happens at the FCM call. Exactly-once delivery to a phone does not exist; exactly-once recording plus idempotent display does.

7.4 Flapping, recurring alerts and trailing stops

  • Flapping. Price oscillating around ₹3,000 must not fire 40 times. One-shot alerts avoid it. Recurring alerts re-arm only after price retreats past a hysteresis band (e.g. 0.5% below the threshold) and after a cooldown (e.g. 15 min).
  • Trailing stop (Upstox). Trigger = peak since creation × (1 − t). A per-alert peak cannot sit in a static sorted index. The trick: once the price makes a new high, every older alert on that symbol shares the same peak. So group trailing alerts into cohorts by (trail %, peak). On a new high, merge all cohorts with peak < new high into one cohort at the new high and re-key it. The index stays keyed by trigger price; updates are per cohort, not per alert.
  • Corporate actions. A 1:2 split halves every threshold. Run an adjustment job before the session opens and publish the updates through the same alert-changes topic.

7.5 The 10 ms variant (Groww stop-loss)

If the action is "place an order within 10 ms", Kafka and a DB write in the hot path are too slow. Keep the same index but run it LMAX-style: one thread per symbol shard, the feed delivered by UDP multicast or shared memory, pre-validated order templates, and journaling to a local append-only log replicated asynchronously. Persistence moves off the critical path; the risk check (margin) runs on cached balances. Mention multi-exchange (same ISIN on NSE and BSE as separate symbols with a mapping) because that is exactly what the Groww feedback said was missing.

08Scaling, failure handling and consistency

  • Hot symbols. Split a symbol's alerts into N sub-shards (RELIANCE#0..7) across matchers and broadcast its ticks to all of them. Ticks are cheap; alerts are the volume.
  • Matcher failover. State is rebuildable: on partition assignment, load the index from a compacted alert-changes topic (or Kafka Streams with a RocksDB state store and a standby replica), then resume ticks from the committed offset. Standby replicas make failover take seconds instead of a full rebuild.
  • Ordering between "create" and "tick". Because both topics share the symbol key and partition count, the matcher sees them in one ordered stream per partition. An alert created at 10:31:00.200 is not matched against a 10:31:00.100 tick.
  • Crash-day burst. Decouple via the alert-fired topic, scale notifier consumers, and digest per user. Prioritise: stop-loss actions and price-cross alerts before "3% move" alerts. FCM throttles; respect 429s with backoff and keep a per-provider token bucket.
  • Stale feed. If no tick arrives for a liquid symbol for N seconds during market hours, raise an alarm and mark data stale rather than silently missing alerts.
  • Multi-region. Run matchers active-passive per region (the feed is from India anyway). Notifications can be served from any region; alert CRUD stays single-primary.

10Follow-up questions interviewers asked

Why not let clients poll for price and evaluate alerts on the device?

Alerts must fire when the app is closed; the device is not running. Polling 3M users every few seconds is also millions of requests per second for nothing. Server-side evaluation plus push is the only design that meets both.

A tick jumps from ₹2,990 to ₹3,010. Does the ₹3,000 alert fire?

Yes. The match is "threshold ≤ window max", not "price == threshold", so gaps fire. Its fired record stores the actual price ₹3,010 so the notification is honest.

How do you avoid firing an alert that was deleted a moment ago?

Deletes flow through the same symbol-keyed stream as ticks, so ordering holds inside the matcher. If a fire races with a delete across the DB, the fire recorder's conditional update (WHERE status='ACTIVE') fails and the notification is dropped.

What happens when a matcher node dies mid-market?

Kafka reassigns its partitions. The new owner restores the index from its standby state store or the compacted alert-changes topic, then replays ticks from the last committed offset. Replayed fires are deduplicated by alertId:fireSeq. Target recovery under 30 seconds; alert during that window by replaying with window min/max so nothing is missed.

How would you support "moves more than 2% in any 15-minute window"?

That is no longer a fixed threshold. Keep a per-symbol sliding min/max over 15 minutes (monotonic deque per symbol). Alerts sorted by percentage: fire all with pct ≤ (max − min)/min. Indexing is by percentage instead of price, but the shape is the same.

How do you test that no alert is missed?

Replay a recorded trading day through the matcher and compare against a brute-force evaluator offline. Run the same comparison continuously as a shadow job on a sample of symbols in production and alert on divergence.

11Mistakes that got candidates rejected

Rejected for this
  • A cron job that runs SELECT * FROM alerts every few seconds and compares with the latest price. It does not scale and misses intra-interval moves.
  • No answer to push vs pull beyond "use WebSockets". The interviewer wanted the reasoning at each boundary.
  • Matching on equality or on the last price only, so gaps and spikes are missed.
  • Ignoring duplicates on replay or flapping; claiming "Kafka exactly-once" covers the phone.
  • Never mentioning hot symbols or crash-day bursts, which is what "scalability" means for this problem (the Groww feedback: "needed more focus on scalability").
