01Why mocks matter

Silence

You go quiet while thinking; interviewers score communication.

Time

25 minutes on clarification; code not running at minute 90.

"Why?"

You cannot explain a choice when asked.

Practice never surfaces these; only a mock does. Weeks 11–12 are not for new material. They convert what you know into consistent performance under a clock.

Go deeper: why practice overestimates you

Real rounds fail for reasons practice sessions never surface: you go silent while thinking, you spend 25 minutes on clarification, your machine-coding solution does not run at minute 90, you cannot explain a choice when asked "why". A mock is the only way to see these. The goal of weeks 11–12 is not to learn new material; it is to convert what you know into consistent performance under a clock.

02Rules for every mock

  1. ClockReal timer on screen; no pausing
  2. TalkAloud the whole time; record audio or screen
  3. UnseenA friend or random number picks the problem
  4. EnvironmentPlain editor for DSA, IDE for machine coding, Excalidraw for HLD
  5. ScoreRubric immediately; written review within 24h
Go deeper: the rules in full
  • Real clock, no pausing. Use a phone timer visible on screen.
  • Talk out loud the whole time. Record audio or screen (OBS, QuickTime, Zoom local recording).
  • Unseen problem. Pick from a list you have not solved; let a friend or a random number pick.
  • Interview environment. Plain editor for DSA (no autocomplete if the target company uses CoderPad/HackerRank), your IDE for machine coding, Excalidraw for HLD.
  • Score immediately with the rubric below, then do the written review within 24 hours.

03Self-timed DSA mocks

0–3 minRestate the problem, ask about input size, edge cases (empty, duplicates, negatives, overflow).
3–8 minBrute force with complexity, then the optimised approach with complexity, before coding.
8–22 minCode it cleanly. Meaningful names, helper methods.
22–27 minDry-run on a small example and one edge case. Fix bugs by reasoning, not by guess-and-run.
27–30 minState final complexity; mention one follow-up (streaming input, memory limit).
30–60 minProblem 2, same structure.
  • Format: two problems in 60 minutes (medium + medium-hard), like Indian product-company rounds and Amazon/Uber screens.
  • Problems: LeetCode company-tagged lists (last 6 months), weekly contests (a free unseen mock every weekend), DSA mixed set. Run on LeetCode only after the mock.
Go deeper: format and problem sources

Format: two problems in 60 minutes (one medium, one medium-hard), mirroring most Indian product-company DSA rounds and Amazon/Uber phone screens.

Sources of problems: LeetCode company-tagged lists for your targets (last 6 months), LeetCode weekly/biweekly contests (a free, timed, unseen mock every weekend), and the problems in DSA mixed set. Then run your code on LeetCode only after the mock ends.

04Machine-coding mocks with a code-review viva

0–10 minRead the problem, write requirements and out-of-scope in a README.
10–20 minEntities, interfaces, patterns; package layout.
20–75 minImplement core flows; commit every 15–20 min; keep a runnable main or tests from minute 40.
75–90 minEdge cases, thread-safety, a demo run. Stop coding at 90 regardless.
90–110 minViva: a peer (or you, using the question list below on a recording) asks review questions while reading your code.

Razorpay, Flipkart, Swiggy, PhonePe, CRED and Uber India run 90–120 minute machine coding, then an engineer reads your code and questions it (the viva). Mock both parts.

Problems: rate limiter, booking system, Splitwise, parking lot. Do one in the AI-assisted format.

Go deeper: viva questions, companies and problems

Viva questions to practise

  • Why this class split? What would you merge or split now?
  • Which pattern is this and why not a simpler alternative?
  • Show me where two threads could race. How is it prevented?
  • How would you add [new requirement] — which files change?
  • What happens on invalid input / duplicate request?
  • How would you test this class in isolation?
  • What would you change before putting this in production?

Indian product companies (Razorpay, Flipkart, Swiggy, PhonePe, CRED, Uber India) use 90–120 minute machine-coding rounds followed by a review where an engineer reads your code and questions it. Mock both parts.

Pick problems from the LLD guides: rate limiter, booking system, Splitwise, parking lot. For one of the machine-coding mocks, use the AI-assisted format from AI-assisted rounds.

08Scoring rubric

1clear no-hire signal
2lean no
3hire
4strong hire

Pass = no dimension at 1 and an average of at least 3.

Use evidence, not feelings

For each score, write one line of evidence from the recording: "minute 14: started coding before stating complexity" or "minute 32: explained why outbox over CDC". Scores without evidence drift upwards.

Go deeper: the scale and pass rule as written

Score each dimension 1–4 (1 = clear no-hire signal, 2 = lean no, 3 = hire, 4 = strong hire). A round is a "pass" if no dimension is 1 and the average is at least 3.

09How to review a failed mock

Reviewing a failed machine-coding mock
Go deeper: the five review steps in full
  1. Watch or listen to the recording at 1.5× within 24 hours. Note timestamps where you stalled, went quiet, or said something wrong.
  2. Classify each failure: knowledge gap (did not know the algorithm/pattern), execution gap (knew it, could not code it in time), communication gap (did it, did not explain it), or process gap (bad time allocation).
  3. Fix by category: knowledge → the matching lesson plus 3 similar problems; execution → re-solve the same problem from scratch 48 hours later under the clock; communication → re-record the explanation only; process → rehearse the timeline for that round type.
  4. Write a one-line rule into a "mock lessons" file: "State complexity before coding", "Commit at minute 40 with a runnable main". Read the file before every real interview.
  5. Re-mock the weak round type within 3 days.
Patterns that predict real rejections
  • Machine coding not runnable at the deadline in 2 of 3 mocks.
  • HLD with no numbers or no failure discussion.
  • Deep-dive where you cannot answer "why" for your own components.
  • DSA solved but with long silences; interviewers score communication.

If any of these persist into week 12, delay the hardest Tier 1 loops by 1–2 weeks rather than burning the attempt.

11Quick check

Scores: 4, 4, 3, 1, 4. Average 3.2. Pass?

Pass needs no dimension at 1 and an average of at least 3.

You knew the algorithm and explained it well, but ran out of time coding it. Which gap?

Knew it, could not code it in time. Fix: re-solve from scratch 48 hours later under the clock.

Why write one line of evidence per score?

"Minute 14: coded before stating complexity" keeps you honest.

Week 12, and your machine coding is still not runnable at the deadline. What now?

Don't burn a Tier 1 attempt on a pattern that predicts rejection.

Cheat sheet
  • Real clock, unseen problem, aloud, recorded.
  • DSA: 2 problems / 60 min; complexity before code; dry-run.
  • Machine coding: runnable by min 40, stop at 90, then a viva.
  • HLD: 45 min; numbers, 2 deep dives, failures.
  • Behavioural: 10-min walkthrough + 4 questions + 2 "whys" each.
  • Score 1–4 with evidence; pass = no 1s and average ≥ 3.
  • Failure → knowledge / execution / communication / process → fix → rule → re-mock in 3 days.
