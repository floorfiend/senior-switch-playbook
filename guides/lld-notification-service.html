Notification Service (LLD)

Build and defend a notification service with typed requests, provider accounts per purpose, random selection with failover, and idempotent sends.

Time-box: 90 min machine coding or 60 min LLD discussion Seen: PhonePe (offer), Adobe Express, Jupiter, Microsoft, Salesforce
PhonePeAdobeJupiter MoneyMicrosoftSalesforce
In 30 seconds
  • One record type per channel; mandatory fields checked in its constructor.
  • Provider = vendor code; account = credentials + purpose + health.
  • Pick a random active account for (channel, purpose); fail over on retryable errors.
  • putIfAbsent on request id stops duplicate sends.

01What the interviewer is grading

Model

Channel, Provider, Account, Purpose as separate concepts. Getting "provider supports many channels" and "account belongs to a purpose" right is half the PhonePe problem.

Validation in types

Mandatory fields enforced where each request type is constructed, not in a 40-line if chain in the service.

Open/closed

New channel or provider = new class plus registration. No edits to the dispatcher.

Failure handling

Failover to another account, temporarily disabling a failing one, idempotency, and knowing when not to retry.

The PhonePe statement (Mar 2025, selected) is the one to rehearse: Email/SMS/Soundbox, many providers, many accounts per provider, random active provider.

Go deeper: the PhonePe statement and other reports

The PhonePe machine-coding statement (Mar 2025, candidate selected) is the most concrete version and the one to rehearse:

  1. Handle multiple communication request types (Email, SMS, Soundbox).
  2. Different request types have different mandatory fields (Email: sender, receiver, subject, message; SMS: mobile number, message).
  3. Providers can support one or many channels; many providers per channel.
  4. Each provider can have multiple accounts, segregated for better handling (for example critical OTP traffic).
  5. Randomly select one active provider from the eligible providers for each request.

Adobe Express (2026, staff-level interviewer) ran the design-pattern version: channels Email/SMS/Push, user preferences, rate limiting per channel. The candidate used Strategy for channels, Observer for event-driven dispatch, Decorator to add retry around any channel, and a token bucket per (user, channel). The interviewer's push: "What if we need to support a new channel like WhatsApp in three months?" Jupiter Money's SDE-2 LLD covered requirements, DB schema, class diagram and enhancements. Microsoft and Salesforce variants ask for a notification library or an OS-level notification system.

02Clarifying questions to ask

Sync or queued?

Synchronous core plus an async wrapper.

Segregated by what?

Assume purpose: OTP, transactional, promotional.

Fail over?

Yes, but a timeout may already have sent it. Ask which is worse: duplicate or miss.

Raw text or template?

In India, SMS must match a DLT-registered template.

03Requirements

Functional

  • Typed requests per channel with mandatory-field validation.
  • Register providers (multi-channel) and accounts (channel + purpose).
  • Activate/deactivate accounts at runtime.
  • For each request choose randomly among active accounts for (channel, purpose); fail over on retryable errors.
  • Idempotent on caller-supplied request id.
  • Track status and attempts per request; notify listeners.
  • Rate limit per (recipient, channel).

Non-functional

  • Thread-safe under concurrent sends and admin changes.
  • OTP traffic isolated from promotional bursts (separate accounts and executors).
  • Provider calls bounded by timeouts.
  • Deterministic tests: injected Random and Clock.

Out of scope

  • Real provider HTTP clients (stub them).
  • Persistent storage (in-memory repository behind an interface).
  • Fan-out to millions (that is the HLD version).

Patterns and why

Strategy

Provider per vendor and ProviderSelector per selection rule. Both are named in the PhonePe statement as things that vary.

Adapter

Each Provider translates our request into a vendor API; vendor quirks stay out of the core.

Decorator

RetryingProvider, TimeoutProvider, RateLimitedProvider wrap any provider (Adobe's answer for retry).

Observer

DeliveryListeners for audit, metrics and client callbacks.

Sealed interface + records

The compiler knows every request type, so a switch over them is exhaustive; validation lives with the data.

Factory only if needed

A Map<Channel, Function<Map, NotificationRequest>> to build requests from a generic API payload.

public enum Channel { EMAIL, SMS, SOUNDBOX, PUSH }
public enum Purpose { OTP, TRANSACTIONAL, PROMOTIONAL }

public sealed interface NotificationRequest permits EmailRequest, SmsRequest, SoundboxRequest {
    String requestId();   // caller-supplied idempotency key
    Purpose purpose();
    Channel channel();
    String recipient();
}

final class Require {
    static String notBlank(String v, String field) {
        if (v == null || v.isBlank()) throw new IllegalArgumentException(field + " is mandatory");
        return v;
    }
}

public record EmailRequest(String requestId, Purpose purpose, String from, String to, String subject, String body)
        implements NotificationRequest {
    public EmailRequest {
        Require.notBlank(requestId, "requestId");
        Objects.requireNonNull(purpose, "purpose");
        Require.notBlank(from, "from");
        Require.notBlank(subject, "subject");
        Require.notBlank(body, "body");
        if (!Require.notBlank(to, "to").contains("@")) throw new IllegalArgumentException("invalid email: " + to);
    }
    public Channel channel() { return Channel.EMAIL; }
    public String recipient() { return to; }
}

public record SmsRequest(String requestId, Purpose purpose, String mobile, String message)
        implements NotificationRequest {
    private static final Pattern MOBILE = Pattern.compile("^\\+?[0-9]{10,13}$");
    public SmsRequest {
        Require.notBlank(requestId, "requestId");
        Objects.requireNonNull(purpose, "purpose");
        Require.notBlank(message, "message");
        if (!MOBILE.matcher(Require.notBlank(mobile, "mobile")).matches()) {
            throw new IllegalArgumentException("invalid mobile: " + mobile);
        }
    }
    public Channel channel() { return Channel.SMS; }
    public String recipient() { return mobile; }
}

public record SoundboxRequest(String requestId, Purpose purpose, String deviceId, long amountPaise, String language)
        implements NotificationRequest {
    public SoundboxRequest {
        Require.notBlank(requestId, "requestId");
        Objects.requireNonNull(purpose, "purpose");
        Require.notBlank(deviceId, "deviceId");
        if (amountPaise <= 0) throw new IllegalArgumentException("amount must be positive");
        language = language == null ? "en" : language;
    }
    public Channel channel() { return Channel.SOUNDBOX; }
    public String recipient() { return deviceId; }
}
Show Java: Provider, ProviderException, ProviderAccount
public record SendResult(String providerMessageId) {}

public class ProviderException extends Exception {
    private final boolean retryable; // 5xx / timeout-before-send: true; bad number / auth: false
    public ProviderException(String msg, boolean retryable) { super(msg); this.retryable = retryable; }
    public boolean retryable() { return retryable; }
}

public interface Provider {
    String name();
    Set<Channel> channels();
    SendResult send(ProviderAccount account, NotificationRequest request) throws ProviderException;
}

public final class ProviderAccount {
    private static final int FAILURE_THRESHOLD = 3;
    private static final Duration COOL_OFF = Duration.ofSeconds(30);

    private final String id;
    private final Provider provider;
    private final Channel channel;
    private final Purpose purpose;
    private volatile boolean enabled = true;               // admin switch
    private final AtomicInteger consecutiveFailures = new AtomicInteger();
    private volatile Instant coolOffUntil = Instant.MIN;   // simple circuit breaker

    public ProviderAccount(String id, Provider provider, Channel channel, Purpose purpose) {
        if (!provider.channels().contains(channel)) {
            throw new IllegalArgumentException(provider.name() + " does not support " + channel);
        }
        this.id = id; this.provider = provider; this.channel = channel; this.purpose = purpose;
    }

    boolean isAvailable(Instant now) { return enabled && !now.isBefore(coolOffUntil); }

    void recordSuccess() { consecutiveFailures.set(0); }

    void recordFailure(Instant now) {
        if (consecutiveFailures.incrementAndGet() >= FAILURE_THRESHOLD) {
            coolOffUntil = now.plus(COOL_OFF);  // half-open after cool-off: next request is the probe
            consecutiveFailures.set(0);
        }
    }

    public void setEnabled(boolean enabled) { this.enabled = enabled; }
    public String id() { return id; }
    public Provider provider() { return provider; }
    public Channel channel() { return channel; }
    public Purpose purpose() { return purpose; }
}
Show Java: ProviderRegistry, ProviderSelector, RandomSelector
public final class ProviderRegistry {
    private record Key(Channel channel, Purpose purpose) {}
    private final Map<Key, List<ProviderAccount>> accounts = new ConcurrentHashMap<>();

    public void register(ProviderAccount a) {
        // copy-on-write: registrations are rare, reads happen on every send
        accounts.computeIfAbsent(new Key(a.channel(), a.purpose()), k -> new CopyOnWriteArrayList<>()).add(a);
    }

    public List<ProviderAccount> eligible(Channel channel, Purpose purpose, Instant now) {
        return accounts.getOrDefault(new Key(channel, purpose), List.of()).stream()
                .filter(a -> a.isAvailable(now))
                .toList();
    }
}

public interface ProviderSelector {
    /** Order in which to try the eligible accounts; first = primary choice. */
    List<ProviderAccount> attemptOrder(List<ProviderAccount> eligible);
}

public final class RandomSelector implements ProviderSelector {
    private final Random random; // injected: seeded in tests, ThreadLocalRandom-backed in prod

    public RandomSelector(Random random) { this.random = random; }

    @Override
    public List<ProviderAccount> attemptOrder(List<ProviderAccount> eligible) {
        List<ProviderAccount> copy = new ArrayList<>(eligible);
        Collections.shuffle(copy, random); // uniform random primary, random failover order
        return copy;
    }
}
Show Java: DeliveryRecord, NotificationService
public enum Status { PENDING, SENT, FAILED, RATE_LIMITED }

public final class DeliveryRecord {
    public record Attempt(String accountId, Instant at, String error) {}

    private final String requestId;
    private final List<Attempt> attempts = new CopyOnWriteArrayList<>();
    private volatile Status status = Status.PENDING;
    private volatile String providerMessageId;

    DeliveryRecord(String requestId) { this.requestId = requestId; }

    void attempt(String accountId, Instant at, String error) { attempts.add(new Attempt(accountId, at, error)); }
    void sent(String messageId) { this.providerMessageId = messageId; this.status = Status.SENT; }
    void finish(Status s) { this.status = s; }

    public Status status() { return status; }
    public List<Attempt> attempts() { return List.copyOf(attempts); }
    public String requestId() { return requestId; }
}

public interface DeliveryListener {
    void onComplete(NotificationRequest request, DeliveryRecord record);
}

public final class NotificationService {
    private final ProviderRegistry registry;
    private final ProviderSelector selector;
    private final RateLimiter rateLimiter;
    private final Clock clock;
    private final List<DeliveryListener> listeners;
    private final Map<String, DeliveryRecord> records = new ConcurrentHashMap<>();

    public NotificationService(ProviderRegistry registry, ProviderSelector selector, RateLimiter rateLimiter,
                               Clock clock, List<DeliveryListener> listeners) {
        this.registry = registry; this.selector = selector; this.rateLimiter = rateLimiter;
        this.clock = clock; this.listeners = List.copyOf(listeners);
    }

    public DeliveryRecord send(NotificationRequest req) {
        DeliveryRecord record = new DeliveryRecord(req.requestId());
        DeliveryRecord existing = records.putIfAbsent(req.requestId(), record); // atomic idempotency gate
        if (existing != null) {
            return existing;
        }
        if (req.purpose() != Purpose.OTP && !rateLimiter.tryAcquire(req.recipient() + ":" + req.channel())) {
            return complete(req, record, Status.RATE_LIMITED);
        }
        for (ProviderAccount account : selector.attemptOrder(registry.eligible(req.channel(), req.purpose(), clock.instant()))) {
            try {
                SendResult result = account.provider().send(account, req);
                account.recordSuccess();
                record.attempt(account.id(), clock.instant(), null);
                record.sent(result.providerMessageId());
                return complete(req, record, Status.SENT);
            } catch (ProviderException e) {
                account.recordFailure(clock.instant());
                record.attempt(account.id(), clock.instant(), e.getMessage());
                if (!e.retryable()) {
                    break; // bad input fails everywhere; do not burn other accounts
                }
            }
        }
        return complete(req, record, Status.FAILED); // also covers "no active provider"
    }

    private DeliveryRecord complete(NotificationRequest req, DeliveryRecord record, Status status) {
        record.finish(status);
        for (DeliveryListener l : listeners) {
            try { l.onComplete(req, record); } catch (RuntimeException ignored) { } // listener bug must not fail send
        }
        return record;
    }
}
Show Java: TokenBucketRateLimiter
public interface RateLimiter { boolean tryAcquire(String key); }

/** Token bucket per key; refill computed lazily from the clock, no background thread. */
public final class TokenBucketRateLimiter implements RateLimiter {
    private final long capacity;
    private final double tokensPerMilli;
    private final Clock clock;
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();

    private static final class Bucket { double tokens; long lastMillis; }

    public TokenBucketRateLimiter(long capacity, Duration refillEvery, Clock clock) {
        this.capacity = capacity; this.tokensPerMilli = 1.0 / refillEvery.toMillis(); this.clock = clock;
    }

    @Override
    public boolean tryAcquire(String key) {
        long now = clock.millis();
        Bucket b = buckets.computeIfAbsent(key, k -> { Bucket n = new Bucket(); n.tokens = capacity; n.lastMillis = now; return n; });
        synchronized (b) { // per-key lock: different recipients never contend
            b.tokens = Math.min(capacity, b.tokens + (now - b.lastMillis) * tokensPerMilli);
            b.lastMillis = now;
            if (b.tokens < 1) return false;
            b.tokens -= 1;
            return true;
        }
    }
}

Async wrapper for the demo: one bounded ThreadPoolExecutor per Purpose (bulkhead), so a promotional blast cannot queue in front of OTPs. sendAsync(req) returns CompletableFuture.supplyAsync(() -> send(req), executors.get(req.purpose())); on a full queue, reject promotional traffic and keep OTP queues small with short timeouts.

Go deeper: full answers for each extension
"Add WhatsApp in three months" (Adobe)

Add WHATSAPP to Channel, a WhatsAppRequest record, and a provider adapter; register accounts. The service, registry and selector do not change. With a sealed interface you also add it to permits, which is deliberate: every exhaustive switch (for example in a template renderer) now fails to compile until it handles WhatsApp. If third parties must add channels without touching our code, make the interface non-sealed.

"URGENT goes to every channel the user has"

Add a NotificationRouter above the service: input is a channel-agnostic Notification(userId, templateId, params, priority, purpose). It loads the user's contacts and preferences, picks channels (URGENT → all available, ignoring marketing opt-outs; otherwise preferred channel with fallback), renders a template per channel, and calls send once per channel with request ids baseId + ":" + channel so each channel stays idempotent.

"Weighted or cheapest-first selection"

New ProviderSelector. Weighted: pick the primary by cumulative weight, then order the rest by weight. Health-aware: weight by recent success rate. No other class changes.

"Retries with backoff around any provider"

RetryingProvider implements Provider wrapping another; retries only retryable() failures with exponential backoff and jitter. Keep in-request retries small (one or two); larger retries belong to a queue-based worker so the caller is not blocked.

"Templates and DLT compliance"

TemplateRepository with templateId → (channel, body with {{placeholders}}, DLT template id for SMS). Rendering fails fast on missing params. For Indian SMS, the operator rejects content that does not match a registered template, so this is a validation step, not a nicety.

"User preferences and quiet hours"

A pre-send filter chain (Chain of Responsibility): OptOutFilter, QuietHoursFilter (promotional only, user's time zone), RateLimitFilter. Each can pass, drop or reschedule.

"Delivery receipts from providers"

A callback endpoint maps providerMessageId → request id and moves status SENT → DELIVERED or UNDELIVERED. Store the mapping when sent() is called; callbacks can arrive before the send call returns, so upsert, never assume order.

"Scheduled and bulk notifications"

Scheduled: persist with sendAt, a poller (or delay queue) hands due items to send. Bulk: split into batches, use promotional accounts and the promotional executor so OTP latency is untouched. Beyond one JVM this becomes the Kafka-based HLD.

10Mistakes that got candidates rejected, and review questions

Rejected for this
  • One Notification class with nullable fields for every channel and an if (type == EMAIL) chain for validation and sending.
  • Conflating provider and account, so "same provider, separate OTP account" cannot be expressed.
  • Selecting randomly from all providers, then checking active, then retrying the same dead provider.
  • new Random() or Instant.now() inside the logic, so nothing is testable.
  • Blocking sends without timeouts; one slow vendor stalls everything.
  • No answer to "new channel in three months" beyond "add an else-if".

Interview questions

Why separate Provider and ProviderAccount?

A provider is code (how to talk to the vendor); an account is configuration and state (credentials, purpose, health). One provider instance serves many accounts, and health is per account because quotas and sender ids are per account.

Why does the selector return an order instead of one account?

Failover then needs no second call and no "exclude these" parameter, and the selection policy decides both primary and backups consistently.

Why CopyOnWriteArrayList in the registry?

Reads on every send, writes only on admin registration. Snapshot iteration is safe without locks. With frequent writes I would switch to an immutable map swapped through an AtomicReference.

Where would this break at scale?

In-memory idempotency and records (move to Postgres with a unique key, or Redis with TTL), synchronous sends (move behind Kafka topics per purpose with consumer workers), and per-JVM rate limits (Redis token bucket). The class boundaries stay the same.

How do you guarantee an OTP is never sent twice?

You cannot guarantee it across a vendor timeout; you choose. For OTP a duplicate is safer than a miss, so fail over and accept rare duplicates; both carry the same code, so the user experience is fine.

12Quick check

The same vendor gives you one account for OTPs and one for promotions. How do you model that?

Provider is code; account is configuration and health. The registry indexes accounts by (channel, purpose).

The provider replies "invalid mobile number". What should the service do?

Bad input fails on every vendor. Failing over just burns other accounts and their quotas.

An OTP send times out. The vendor may or may not have sent it. What is the usual call?

The outcome is unknown. For OTP a rare duplicate is harmless (same code); for promotional you would not fail over.

How does adding WhatsApp avoid touching NotificationService?

Open/closed: the pipeline works on NotificationRequest and Provider, so a new channel is new classes plus registration.

Cheat sheet
  • Sealed NotificationRequest + one record per channel; validate in the constructor.
  • Provider (vendor adapter) ≠ account (credentials, purpose, health).
  • Registry: (channel, purpose) → CopyOnWriteArrayList of accounts.
  • Selector returns an attempt order: primary + failover in one call.
  • Pipeline: idempotency → rate limit → eligible → try in order → record → notify.
  • putIfAbsent on request id; prod: DB unique key or Redis SET NX.
