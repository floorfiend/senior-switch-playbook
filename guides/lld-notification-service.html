Notification Service (LLD)

Build a notification service, then defend it. Each channel has its own request type. Vendors have separate accounts for each purpose, such as OTPs. The service picks an account at random, falls back to another if it fails, and never sends the same message twice.

Time-box: 90 min machine coding or 60 min LLD discussion Seen: PhonePe (offer), Adobe Express, Jupiter, Microsoft, Salesforce
PhonePeAdobeJupiter MoneyMicrosoftSalesforce
In 30 seconds
  • One record type per channel. Its constructor checks the required fields.
  • A provider is the code that talks to a vendor. An account holds login details, a purpose and a health status.
  • Pick a random active account for (channel, purpose). If it fails with an error worth retrying, try the next one.
  • putIfAbsent on the request id stops the same message going out twice.
Picture it

Think of a courier desk that works with several courier companies. Each company has one counter for urgent parcels and one for bulk. The clerk picks any open urgent counter at random. If that counter is jammed, the parcel goes to the next open one. The receipt number stops the same parcel being booked twice.

Words you'll see
OTP (one-time password)
The short code a bank app sends by SMS when you log in. It must arrive fast.
Provider and account
A provider is a vendor like an SMS company. An account is one login with that vendor, kept for one purpose.
Failover
When one account fails, automatically try the next one.
Idempotent
Doing it twice has the same effect as doing it once. Sending request "otp-42" twice sends one SMS.
Retryable error
A temporary failure, like "server busy". A wrong phone number is not retryable; it fails everywhere.
Circuit breaker
After several failures in a row, stop using an account for a while, then test it with one request.
Rate limit
A cap on how many messages one person can get in a time window.
DLT (Distributed Ledger Technology)
India's telecom registry. Business SMS text must match a template registered there, or operators block it.

01What the interviewer is grading

Model

Channel, Provider, Account and Purpose are separate ideas. Half the PhonePe problem is getting two facts right. A provider can support many channels. An account belongs to one purpose.

Checks inside the types

Each request type checks its own required fields when it is created. No 40-line if chain in the service.

Open/closed

A new channel or provider is a new class plus one registration. The dispatcher code does not change.

Handling failure

Fall back to another account. Pause an account that keeps failing. Never send twice. Know when not to retry.

Practise the PhonePe task (Mar 2025, selected). It has Email, SMS and Soundbox (the speaker box at shops that reads out payments). It has many providers, many accounts per provider, and picks a random active provider.

Go deeper: the PhonePe statement and other reports

The PhonePe machine-coding task (Mar 2025, candidate selected) is the most concrete version. It is the one to practise:

  1. Handle several request types: Email, SMS, Soundbox.
  2. Each type has different required fields. Email: sender, receiver, subject, message. SMS: mobile number, message.
  3. A provider can support one or many channels. A channel can have many providers.
  4. Each provider can have several accounts, kept apart for better handling. For example, critical OTP traffic gets its own account.
  5. For each request, pick one active provider at random from those allowed.

Adobe Express (2026, staff-level interviewer) asked the design-pattern version. Channels were Email, SMS and Push, with user preferences and a rate limit per channel. The candidate used Strategy for channels and Observer for event-driven sending. They used Decorator to add retry around any channel. They used a token bucket per (user, channel) for the rate limit. The interviewer pushed: "What if we need to support a new channel like WhatsApp in three months?" Jupiter Money's SDE-2 LLD covered requirements, database tables, a class diagram and later improvements. Microsoft and Salesforce ask for a notification library, or a notification system inside an operating system.

02Clarifying questions to ask

Send now, or queue?

Build a core that sends and waits for the result. Add an async wrapper on top.

Accounts split by what?

Assume by purpose: OTP, transactional, promotional.

Fall back to another account?

Yes. But after a timeout, the message may already be sent. Ask which is worse: a duplicate or a missed message.

Raw text or template?

In India, SMS text must match a template registered with DLT.

03Requirements

Functional (what it does)

  • A request type per channel, each checking its required fields.
  • Register providers (which may cover many channels) and accounts (channel + purpose).
  • Switch accounts on and off while running.
  • For each request, pick at random among active accounts for (channel, purpose). Fall back on retryable errors.
  • Idempotent on the request id the caller sends.
  • Track status and attempts per request. Tell listeners.
  • Rate limit per (recipient, channel).

Non-functional (how well it does it)

  • Safe when many sends and admin changes happen at once.
  • OTP traffic is kept apart from promotional bursts, with separate accounts and thread pools.
  • Every call to a vendor has a timeout.
  • Tests give the same result every run, because Random and Clock are passed in.

Out of scope

  • Real vendor HTTP clients. Use fakes.
  • A real database. Use an in-memory store behind an interface.
  • Sending to millions of users. That is the HLD version.

Patterns and why

Strategy

One Provider per vendor, and one ProviderSelector per selection rule. The PhonePe task names both as things that change.

Adapter

Each Provider turns our request into the vendor's API call. Vendor quirks stay out of the core.

Decorator

RetryingProvider, TimeoutProvider and RateLimitedProvider wrap any provider to add a feature. This was Adobe's answer for retry.

Observer

DeliveryListeners handle audit logs, metrics and calls back to clients.

Sealed interface + records

The compiler knows every request type, so a switch must cover them all. Checks live next to the data.

Factory only if needed

A Map<Channel, Function<Map, NotificationRequest>> builds requests from a generic API payload.

public sealed interface NotificationRequest permits EmailRequest, SmsRequest, SoundboxRequest {
    String requestId();   // caller-supplied idempotency key
    Purpose purpose();

    String recipient();
}

final class Require {
    static String notBlank(String v, String field) {
        if (v == null || v.isBlank()) throw new IllegalArgumentException(field + " is mandatory");
        return v;
    }
}

public record EmailRequest(String requestId, Purpose purpose, String from, String to, String subject, String body)
        implements NotificationRequest {
    public EmailRequest {
        Require.notBlank(requestId, "requestId");
        Objects.requireNonNull(purpose, "purpose");
        Require.notBlank(from, "from");
        Require.notBlank(subject, "subject");
        Require.notBlank(body, "body");
        if (!Require.notBlank(to, "to").contains("@")) throw new IllegalArgumentException("invalid email: " + to);
    }
    public Channel channel() { return Channel.EMAIL; }
    public String recipient() { return to; }
}

        implements NotificationRequest {

    public SmsRequest {
        Require.notBlank(requestId, "requestId");
        Objects.requireNonNull(purpose, "purpose");
        Require.notBlank(message, "message");

public record SendResult(String providerMessageId) {}

public class ProviderException extends Exception {
    private final boolean retryable; // 5xx / timeout-before-send: true; bad number / auth: false
    public ProviderException(String msg, boolean retryable) { super(msg); this.retryable = retryable; }
    public boolean retryable() { return retryable; }
}

public interface Provider {
    String name();
    Set<Channel> channels();
    SendResult send(ProviderAccount account, NotificationRequest request) throws ProviderException;
}

public final class ProviderAccount {
    private static final int FAILURE_THRESHOLD = 3;
    private static final Duration COOL_OFF = Duration.ofSeconds(30);

    private final String id;
    private final Provider provider;
    private final Channel channel;
    private final Purpose purpose;
    private volatile boolean enabled = true;               // admin switch
    private final AtomicInteger consecutiveFailures = new AtomicInteger();
    private volatile Instant coolOffUntil = Instant.MIN;   // simple circuit breaker

    public ProviderAccount(String id, Provider provider, Channel channel, Purpose purpose) {
        if (!provider.channels().contains(channel)) {
            throw new IllegalArgumentException(provider.name() + " does not support " + channel);
        }
        this.id = id; this.provider = provider; this.channel = channel; this.purpose = purpose;
    }

    boolean isAvailable(Instant now) { return enabled && !now.isBefore(coolOffUntil); }

    void recordSuccess() { consecutiveFailures.set(0); }

    void recordFailure(Instant now) {
        if (consecutiveFailures.incrementAndGet() >= FAILURE_THRESHOLD) {
            coolOffUntil = now.plus(COOL_OFF);  // half-open after cool-off: next request is the probe
            consecutiveFailures.set(0);
        }
    }

    public void setEnabled(boolean enabled) { this.enabled = enabled; }
    public String id() { return id; }
    public Provider provider() { return provider; }
    public Channel channel() { return channel; }
    public Purpose purpose() { return purpose; }
}
Show Java: ProviderRegistry, ProviderSelector, RandomSelector
public final class ProviderRegistry {
    private record Key(Channel channel, Purpose purpose) {}
    private final Map<Key, List<ProviderAccount>> accounts = new ConcurrentHashMap<>();

    public void register(ProviderAccount a) {
        // copy-on-write: registrations are rare, reads happen on every send
        accounts.computeIfAbsent(new Key(a.channel(), a.purpose()), k -> new CopyOnWriteArrayList<>()).add(a);
    }

    public List<ProviderAccount> eligible(Channel channel, Purpose purpose, Instant now) {
        return accounts.getOrDefault(new Key(channel, purpose), List.of()).stream()
                .filter(a -> a.isAvailable(now))
                .toList();
    }
}

public interface ProviderSelector {
    /** Order in which to try the eligible accounts; first = primary choice. */
    List<ProviderAccount> attemptOrder(List<ProviderAccount> eligible);
}

public final class RandomSelector implements ProviderSelector {
    private final Random random; // injected: seeded in tests, ThreadLocalRandom-backed in prod

    public RandomSelector(Random random) { this.random = random; }

    @Override
    public List<ProviderAccount> attemptOrder(List<ProviderAccount> eligible) {
        List<ProviderAccount> copy = new ArrayList<>(eligible);
        Collections.shuffle(copy, random); // uniform random primary, random failover order
        return copy;
    }
}
Show Java: DeliveryRecord, NotificationService
public enum Status { PENDING, SENT, FAILED, RATE_LIMITED }

public final class DeliveryRecord {
    public record Attempt(String accountId, Instant at, String error) {}

    private final String requestId;
    private final List<Attempt> attempts = new CopyOnWriteArrayList<>();
    private volatile Status status = Status.PENDING;
    private volatile String providerMessageId;

    DeliveryRecord(String requestId) { this.requestId = requestId; }

    void attempt(String accountId, Instant at, String error) { attempts.add(new Attempt(accountId, at, error)); }
    void sent(String messageId) { this.providerMessageId = messageId; this.status = Status.SENT; }
    void finish(Status s) { this.status = s; }

    public Status status() { return status; }
    public List<Attempt> attempts() { return List.copyOf(attempts); }
    public String requestId() { return requestId; }
}

public interface DeliveryListener {
    void onComplete(NotificationRequest request, DeliveryRecord record);
}

public final class NotificationService {
    private final ProviderRegistry registry;
    private final ProviderSelector selector;
    private final RateLimiter rateLimiter;
    private final Clock clock;
    private final List<DeliveryListener> listeners;
    private final Map<String, DeliveryRecord> records = new ConcurrentHashMap<>();

    public NotificationService(ProviderRegistry registry, ProviderSelector selector, RateLimiter rateLimiter,
                               Clock clock, List<DeliveryListener> listeners) {
        this.registry = registry; this.selector = selector; this.rateLimiter = rateLimiter;
        this.clock = clock; this.listeners = List.copyOf(listeners);
    }

    public DeliveryRecord send(NotificationRequest req) {
        DeliveryRecord record = new DeliveryRecord(req.requestId());
        DeliveryRecord existing = records.putIfAbsent(req.requestId(), record); // atomic idempotency gate
        if (existing != null) {
            return existing;
        }
        if (req.purpose() != Purpose.OTP && !rateLimiter.tryAcquire(req.recipient() + ":" + req.channel())) {
            return complete(req, record, Status.RATE_LIMITED);
        }
        for (ProviderAccount account : selector.attemptOrder(registry.eligible(req.channel(), req.purpose(), clock.instant()))) {
            try {
                SendResult result = account.provider().send(account, req);
                account.recordSuccess();
                record.attempt(account.id(), clock.instant(), null);
                record.sent(result.providerMessageId());
                return complete(req, record, Status.SENT);
            } catch (ProviderException e) {
                account.recordFailure(clock.instant());
                record.attempt(account.id(), clock.instant(), e.getMessage());
                if (!e.retryable()) {
                    break; // bad input fails everywhere; do not burn other accounts
                }
            }
        }
        return complete(req, record, Status.FAILED); // also covers "no active provider"
    }

    private DeliveryRecord complete(NotificationRequest req, DeliveryRecord record, Status status) {
        record.finish(status);
        for (DeliveryListener l : listeners) {
            try { l.onComplete(req, record); } catch (RuntimeException ignored) { } // listener bug must not fail send
        }
        return record;
    }
}
Show Java: TokenBucketRateLimiter
public interface RateLimiter { boolean tryAcquire(String key); }

/** Token bucket per key; refill computed lazily from the clock, no background thread. */
public final class TokenBucketRateLimiter implements RateLimiter {
    private final long capacity;
    private final double tokensPerMilli;
    private final Clock clock;
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();

    private static final class Bucket { double tokens; long lastMillis; }

    public TokenBucketRateLimiter(long capacity, Duration refillEvery, Clock clock) {
        this.capacity = capacity; this.tokensPerMilli = 1.0 / refillEvery.toMillis(); this.clock = clock;
    }

    @Override
    public boolean tryAcquire(String key) {
        long now = clock.millis();
        Bucket b = buckets.computeIfAbsent(key, k -> { Bucket n = new Bucket(); n.tokens = capacity; n.lastMillis = now; return n; });
        synchronized (b) { // per-key lock: different recipients never contend
            b.tokens = Math.min(capacity, b.tokens + (now - b.lastMillis) * tokensPerMilli);
            b.lastMillis = now;
            if (b.tokens < 1) return false;
            b.tokens -= 1;
            return true;
        }
    }
}

The async wrapper for the demo uses one limited ThreadPoolExecutor per Purpose. This is a bulkhead: a promotional blast cannot queue in front of OTPs. sendAsync(req) returns CompletableFuture.supplyAsync(() -> send(req), executors.get(req.purpose())). When a queue is full, reject promotional traffic. Keep OTP queues small, with short timeouts.

Async sending uses one limited thread pool per Purpose. This is called a bulkhead. A big marketing blast can never delay your login code.

Go deeper: full answers for each extension
"Add WhatsApp in three months" (Adobe)

Add WHATSAPP to Channel. Add a WhatsAppRequest record and a provider adapter. Register accounts. The service, registry and selector do not change. With a sealed interface, you also add it to permits. That is on purpose. Every switch that must cover all types, such as a template renderer, now fails to compile until it handles WhatsApp. If outside teams must add channels without touching our code, make the interface non-sealed.

"URGENT goes to every channel the user has"

Add a NotificationRouter above the service. Its input does not name a channel: Notification(userId, templateId, params, priority, purpose). It loads the user's contacts and preferences. Then it picks channels. URGENT means all channels, even if the user opted out of marketing. Otherwise, use the preferred channel with a backup. It fills a template per channel. It calls send once per channel, with request id baseId + ":" + channel. So each channel stays safe from duplicates.

"Weighted or cheapest-first selection"

Write a new ProviderSelector. Weighted: pick the first account by running total of weights, then sort the rest by weight. Health-aware: weight by recent success rate. No other class changes.

"Retries with backoff around any provider"

Write RetryingProvider implements Provider, wrapping another provider. It retries only retryable() failures. Each wait doubles, plus a little randomness (exponential backoff with jitter). Keep retries inside a request small, one or two. Bigger retry plans belong in a queue-based worker, so the caller is not kept waiting.

"Templates and DLT compliance"

A TemplateRepository maps a templateId to its channel, its text with {{placeholders}}, and the DLT template id for SMS. Filling a template fails early if a value is missing. For Indian SMS, the operator rejects text that does not match a registered template. So this is a required check, not a nice extra.

"User preferences and quiet hours"

Run a chain of checks before sending (the Chain of Responsibility pattern). OptOutFilter respects opt-outs. QuietHoursFilter applies to promotional only, in the user's time zone. RateLimitFilter caps volume. Each one can pass, drop or delay the message.

"Delivery receipts from providers"

A callback endpoint maps providerMessageId to our request id. It moves the status from SENT to DELIVERED or UNDELIVERED. Save the mapping when sent() is called. A callback can arrive before the send call even returns. So insert-or-update, and never assume order.

"Scheduled and bulk notifications"

Scheduled: save the message with a sendAt time. A poller, or a delay queue, passes due messages to send. Bulk: split into batches. Use promotional accounts and the promotional thread pool, so OTP speed is not affected. Beyond one JVM, this becomes the Kafka-based HLD.

10Mistakes that got candidates rejected, and review questions

Rejected for this
  • One Notification class with empty-able fields for every channel, plus an if (type == EMAIL) chain for checks and sending.
  • Mixing up provider and account. Then you cannot say "same vendor, separate OTP account".
  • Picking at random from all providers, then checking if it is active, then retrying the same dead provider.
  • new Random() or Instant.now() inside the logic, so nothing can be tested.
  • Sends that wait with no timeout. One slow vendor then stalls everything.
  • No answer to "new channel in three months" except "add an else-if".

Interview questions

Why separate Provider and ProviderAccount?

A provider is code: how to talk to the vendor. An account is settings and state: login details, purpose, health. One provider object serves many accounts. Health is tracked per account, because limits (quotas) and sender ids are per account.

Why does the selector return an order instead of one account?

Then fallback needs no second call, and no "skip these" parameter. The selection rule also decides the first choice and the backups in one consistent way.

Why CopyOnWriteArrayList in the registry?

Every send reads it. Only admin registration writes to it. Looping over a snapshot is safe without locks. If writes were frequent, I would swap in a new unchangeable map through an AtomicReference instead.

Where would this break at scale?

Three places. Duplicate checks and records live in memory; move them to Postgres with a unique key, or Redis with an expiry. Sends wait for the vendor; move them behind Kafka topics per purpose, with worker consumers. Rate limits are per JVM; move them to a Redis token bucket. The class boundaries stay the same.

How do you guarantee an OTP is never sent twice?

You cannot, if the vendor times out. You must choose. For OTP, a duplicate is safer than a miss. So fall back and accept a rare duplicate. Both messages carry the same code, so the user is not confused.

12Quick check

One vendor gives you one account for OTPs and one for promotions. How do you model that?

The provider is code. An account is settings and health. The registry finds accounts by (channel, purpose).

The vendor replies "invalid mobile number". What should the service do?

A wrong number fails at every vendor. Trying others only wastes their accounts and limits.

An OTP send times out. The vendor may or may not have sent it. What is the usual choice?

We do not know what happened. For OTP, a rare duplicate is harmless because it has the same code. For promotional messages, you would not fall back.

How can you add WhatsApp without changing NotificationService?

This is the open/closed principle. The pipeline only knows NotificationRequest and Provider. So a new channel is new classes plus registration.

Cheat sheet
  • A sealed NotificationRequest with one record per channel. Check fields in the constructor.
  • A provider (vendor wrapper) is not an account (login details, purpose, health).
  • Registry: (channel, purpose) maps to a CopyOnWriteArrayList of accounts.
  • The selector returns an order to try: first choice and backups in one call.
  • Pipeline: duplicate check, rate limit, allowed accounts, try in order, save, notify.
  • putIfAbsent on the request id. In production: a database unique key or Redis SET NX.
  • Fall back only on retryable errors. 3 failures in a row means a 30 s pause, then one test request.
  • One thread pool per purpose (bulkhead). Pass in Random and Clock.
