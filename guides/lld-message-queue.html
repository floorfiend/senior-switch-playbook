In-memory Message Queue / Pub-Sub

Build a mini Kafka in one process: topics split into partitions, producers that append, consumer groups that read in order and commit offsets, all thread-safe. A senior answer shows ordering only where it is promised (per partition), a clean consumer lifecycle, and concurrency you can defend line by line in the code-review round that follows.

Time-box: 90 min code + 30 min review Seen: Flipkart SDE-3 machine coding; queue/thread-pool variants at Rubrik, Goldman Sachs, LinkedIn, CleverTap

01What the interviewer is grading

The Flipkart SDE-3 report (Oct 2025, selected) is the template: a 90-minute machine-coding round to build "a working MVP for an in-memory message streaming service supporting multiple topics, producers, and consumers" with ordering within partitions, thread safety and real-time streaming. Then a separate 30-minute evaluation round: "in-depth discussion about my solution ... modularity, OOP principles, design patterns and concurrency." So you are graded twice on the same code.

Runnable MVP

A main or a JUnit test that creates a topic, runs several producers and consumers on threads, and prints ordered output. Not running at minute 90 is usually fatal at Flipkart.

Correct ordering semantics

Ordered per partition, not per topic. Same key → same partition. One consumer per partition inside a group.

Concurrency you can explain

Where the locks are, why a Condition instead of busy-polling, what happens during rebalance, what "at-least-once" means in your commit order.

Extensibility

Partitioner as a strategy, handlers as an interface, retry/DLQ as a decorator. New requirements should add classes, not edit the broker.

The queue family shows up elsewhere in a lower-level form. Rubrik's screening round asks for a bounded blocking queue and then a thread pool built on it (submit, execute, shutdown, shutdownNow); the candidate was marked "lean hire" because shutdown() and the exceptions caught were not convincing. CleverTap's associate-director round probed Kafka brokers, topics and partitions, asked for a "generic queue system for teams to use", then a "at most two threads in parallel" exercise (a Semaphore(2)). Prepare the primitives, not only the façade.

02Clarifying questions to ask

QuestionWhy it matters
Pub-sub (every subscriber gets every message) or queue (each message to one worker)?Consumer groups give you both: different groups = broadcast, same group = load sharing. Say this and you have answered both.
Ordering: global per topic or per key?Global ordering forces one partition and kills parallelism. Per-key ordering via partitions is the standard answer.
Push (broker calls handler) or pull (consumer polls)?Pull gives natural backpressure and simple offset tracking. Push is easier to demo. I default to pull with a long-poll wait.
Delivery guarantee: at-most-once or at-least-once?Decides commit-before or commit-after processing. At-least-once is the usual answer; handlers must be idempotent.
Retention: keep messages forever, by count, or by time?Affects memory and whether a new group can replay from offset 0.
Can consumers join or leave at runtime?If yes you need rebalancing, which is where most concurrency bugs live.
Bounded memory? What happens when full?Block the producer, reject, or drop oldest. Backpressure is a senior talking point.
Failed message handling: retry how many times? Dead letter?Shapes the handler wrapper and whether a poison message blocks a partition.

03Requirements

Functional

  • Create topic with N partitions.
  • Publish (key, payload); same key goes to same partition; returns (partition, offset).
  • Subscribe a consumer to a topic under a group id with a handler.
  • Each message delivered to exactly one consumer per group; every group sees every message.
  • Order preserved within a partition.
  • Consumers can leave; partitions get reassigned.
  • Committed offsets per (group, partition); a new group can start from earliest or latest.

Non-functional

  • Thread-safe for concurrent producers and consumers.
  • No busy-waiting; consumers block until data or timeout.
  • Publish is O(1); read is O(batch).
  • At-least-once delivery.
  • Clean shutdown: no lost commits, threads terminate.

Out of scope (say so)

  • Persistence and replication (mention log segments and ISR only as follow-ups).
  • Network protocol and brokers across machines.
  • Exactly-once transactions.
  • Authentication and quotas.

Patterns and why

  • Strategy for Partitioner and the group's assignment strategy (range vs round-robin): the interviewer will ask "what if I want sticky assignment" and you add a class.
  • Observer / publish-subscribe is the domain itself; groups are the subscribers.
  • Decorator for RetryingHandler and DeadLetterHandler around the user's MessageHandler.
  • Façade (Broker) so the demo and tests touch one class.
  • Not Singleton. Inject the broker; singletons make tests share state and reviewers notice.

05Core code

Java 21. Records for value types, virtual threads for workers. The partition log is the heart; get it right first.

public record Message(String key, String payload, Instant publishedAt) {}

public record Record(String topic, int partition, long offset, Message message) {}

public interface Partitioner {
    int partition(String key, int numPartitions);
}

public final class KeyHashPartitioner implements Partitioner {
    private final AtomicInteger roundRobin = new AtomicInteger();

    @Override
    public int partition(String key, int numPartitions) {
        if (key == null) {
            return Math.floorMod(roundRobin.getAndIncrement(), numPartitions); // keyless: spread load
        }
        return Math.floorMod(key.hashCode(), numPartitions); // floorMod: hashCode can be negative
    }
}
final class Partition {
    private final String topic;
    private final int id;
    private final List<Message> log = new ArrayList<>();
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition appended = lock.newCondition();

    Partition(String topic, int id) { this.topic = topic; this.id = id; }

    long append(Message m) {
        lock.lock();
        try {
            log.add(m);
            appended.signalAll(); // wake long-polling readers
            return log.size() - 1L;
        } finally {
            lock.unlock();
        }
    }

    /** Blocks up to {@code wait} if there is nothing at {@code from}. Never busy-waits. */
    List<Record> read(long from, int max, Duration wait) throws InterruptedException {
        lock.lock();
        try {
            long nanos = wait.toNanos();
            while (from >= log.size() && nanos > 0) {
                nanos = appended.awaitNanos(nanos); // loop guards against spurious wake-ups
            }
            if (from >= log.size()) {
                return List.of();
            }
            int end = (int) Math.min(log.size(), from + max);
            List<Record> out = new ArrayList<>(end - (int) from);
            for (int i = (int) from; i < end; i++) {
                out.add(new Record(topic, id, i, log.get(i)));
            }
            return out; // copy: callers never see the live list
        } finally {
            lock.unlock();
        }
    }
}
public final class Topic {
    private final String name;
    private final List<Partition> partitions;
    private final Partitioner partitioner;

    Topic(String name, int n, Partitioner partitioner) {
        this.name = name;
        this.partitioner = partitioner;
        this.partitions = IntStream.range(0, n).mapToObj(i -> new Partition(name, i)).toList();
    }

    Record publish(Message m) {
        int p = partitioner.partition(m.key(), partitions.size());
        long offset = partitions.get(p).append(m);
        return new Record(name, p, offset, m);
    }

    Partition partition(int p) { return partitions.get(p); }
    int partitionCount() { return partitions.size(); }
    String name() { return name; }
}

The consumer group owns membership and offsets. Every structural change bumps a generation number; a worker holding a stale generation cannot commit, which is the same fencing idea Kafka uses.

final class ConsumerGroup {
    private final String id;
    private final Topic topic;
    private final Map<Integer, Long> committed = new ConcurrentHashMap<>();
    private final List<String> members = new ArrayList<>();          // guarded by this
    private volatile Assignment assignment = new Assignment(0, Map.of());

    record Assignment(int generation, Map<String, List<Integer>> byMember) {
        List<Integer> of(String member) { return byMember.getOrDefault(member, List.of()); }
    }

    ConsumerGroup(String id, Topic topic) { this.id = id; this.topic = topic; }

    synchronized void join(String member) { members.add(member); rebalance(); }

    synchronized void leave(String member) { members.remove(member); rebalance(); }

    private void rebalance() { // range assignment; swap in a strategy if asked
        Map<String, List<Integer>> next = new HashMap<>();
        for (int p = 0; p < topic.partitionCount() && !members.isEmpty(); p++) {
            next.computeIfAbsent(members.get(p % members.size()), k -> new ArrayList<>()).add(p);
        }
        assignment = new Assignment(assignment.generation() + 1, Map.copyOf(next)); // single volatile publish
    }

    Assignment assignment() { return assignment; }

    long position(int partition) { return committed.getOrDefault(partition, 0L); }

    /** Returns false if the caller's generation is stale (partition moved to someone else). */
    boolean commit(int partition, long nextOffset, int generation) {
        if (generation != assignment.generation()) {
            return false;
        }
        committed.merge(partition, nextOffset, Math::max); // offsets never move backwards
        return true;
    }
}
@FunctionalInterface
public interface MessageHandler {
    void handle(Record record) throws Exception;
}

final class ConsumerWorker implements Runnable {
    private final String memberId;
    private final Topic topic;
    private final ConsumerGroup group;
    private final MessageHandler handler;
    private volatile boolean running = true;

    ConsumerWorker(String memberId, Topic topic, ConsumerGroup group, MessageHandler handler) {
        this.memberId = memberId; this.topic = topic; this.group = group; this.handler = handler;
    }

    @Override
    public void run() {
        try {
            while (running) {
                ConsumerGroup.Assignment a = group.assignment(); // snapshot once per loop
                List<Integer> mine = a.of(memberId);
                if (mine.isEmpty()) { Thread.sleep(20); continue; }
                for (int p : mine) {
                    List<Record> batch = topic.partition(p).read(group.position(p), 100, Duration.ofMillis(50));
                    for (Record r : batch) {
                        if (group.assignment().generation() != a.generation()) {
                            break;                                              // rebalanced: stop before handling
                        }
                        handleQuietly(r);                                       // process first...
                        if (!group.commit(p, r.offset() + 1, a.generation())) { // ...then commit: at-least-once
                            break;                                              // partition was reassigned
                        }
                    }
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restore flag and exit
        } finally {
            group.leave(memberId);
        }
    }

    private void handleQuietly(Record r) {
        try {
            handler.handle(r);
        } catch (Exception e) {
            // RetryingHandler + DLQ decorate the handler; anything reaching here is logged and skipped
            System.err.printf("dropped %s-%d@%d: %s%n", r.topic(), r.partition(), r.offset(), e);
        }
    }

    void stop() { running = false; }
}
public final class Broker implements AutoCloseable {
    private final Map<String, Topic> topics = new ConcurrentHashMap<>();
    private final Map<String, ConsumerGroup> groups = new ConcurrentHashMap<>();
    private final ExecutorService workers = Executors.newVirtualThreadPerTaskExecutor();
    private final Clock clock;

    public Broker(Clock clock) { this.clock = clock; }

    public void createTopic(String name, int partitions, Partitioner partitioner) {
        if (topics.putIfAbsent(name, new Topic(name, partitions, partitioner)) != null) {
            throw new IllegalArgumentException("topic exists: " + name);
        }
    }

    public Record publish(String topic, String key, String payload) {
        return topicOrThrow(topic).publish(new Message(key, payload, clock.instant()));
    }

    public Subscription subscribe(String topic, String groupId, MessageHandler handler) {
        Topic t = topicOrThrow(topic);
        ConsumerGroup g = groups.computeIfAbsent(topic + "/" + groupId, k -> new ConsumerGroup(groupId, t));
        String memberId = groupId + "-" + UUID.randomUUID();
        ConsumerWorker w = new ConsumerWorker(memberId, t, g, handler);
        g.join(memberId);
        Future<?> f = workers.submit(w);
        return () -> { w.stop(); f.cancel(true); }; // cancel interrupts a blocked read
    }

    private Topic topicOrThrow(String name) {
        Topic t = topics.get(name);
        if (t == null) throw new IllegalArgumentException("unknown topic: " + name);
        return t;
    }

    @Override
    public void close() throws InterruptedException {
        workers.shutdownNow();
        workers.awaitTermination(5, TimeUnit.SECONDS);
    }
}

@FunctionalInterface
public interface Subscription extends AutoCloseable {
    @Override void close();
}
The demo that sells it

In main: topic "orders" with 3 partitions, two groups ("billing" with 2 consumers, "audit" with 1), 4 producer threads publishing keys order-1..order-10 with sequence numbers. Each handler asserts the sequence for its key never goes backwards. Print "OK: per-key order held across 4,000 messages". That one line answers the ordering question before it is asked.

06Concurrency and edge cases

RiskWhat goes wrongHow the design prevents it
Two producers append to one partitionLost write or two messages with one offset (ArrayList is not thread-safe)Append and offset assignment happen under the partition lock, so offset = index is unique.
Reader sees a half-built listVisibility bugs on a plain listReads take the same lock and return a copy. A ReadWriteLock is an option, but a Condition needs the exclusive lock, and the critical sections are tiny.
Consumer spins on empty partition100% CPUawaitNanos on a Condition, signalled on append; loop handles spurious wake-ups.
Rebalance while a worker is mid-batchTwo workers process the same partition; offsets regressGeneration checked before each record and fenced again on commit, plus merge(..., Math::max). A record already in a handler when the rebalance lands can still be redelivered once; that is the at-least-once contract.
Commit before processingCrash loses the message (at-most-once)Commit after handler returns. State the trade-off explicitly.
Poison messageHandler throws forever, partition stallsRetryingHandler with bounded attempts and backoff, then a DLQ topic. The offset advances.
Interrupt swallowedShutdown hangsCatch InterruptedException, restore the flag, exit. This is exactly what Rubrik's interviewer probed.
Two subscribers create the same groupTwo ConsumerGroup objects, double deliverycomputeIfAbsent on ConcurrentHashMap is atomic per key.
TimeTests depend on wall clock for retention/delaysInject java.time.Clock; tests use a mutable fixed clock.

Idempotency. At-least-once means the handler must tolerate duplicates. Offer a producer-side idempotency key in headers and an IdempotentHandler decorator that keeps a bounded set of processed message ids per partition. Kafka's idempotent producer does the broker-side equivalent with producer id and sequence numbers.

07Extensions interviewers add mid-round

"Make the queue bounded; producers should block when full."

Per-partition capacity plus a second Condition notFull. Producers await while full; consumers cannot free space in a log, so define "full" as retained-minus-slowest-committed-offset and trim. Simpler alternative the interviewer often wants: a separate bounded blocking queue, below.

public final class BoundedBlockingQueue<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    public BoundedBlockingQueue(int capacity) { items = new Object[capacity]; }

    public void put(T item) throws InterruptedException {
        Objects.requireNonNull(item);
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();
            items[tail] = item; tail = (tail + 1) % items.length; count++;
            notEmpty.signal(); // separate conditions: wake one taker, not every waiter
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T item = (T) items[head]; items[head] = null; head = (head + 1) % items.length; count--;
            notFull.signal();
            return item;
        } finally { lock.unlock(); }
    }
}

This is the same two-condition design as java.util.concurrent.ArrayBlockingQueue. For the thread-pool follow-up: workers loop on take(); shutdown() sets a flag, rejects new submits and lets workers drain then exit (enqueue one poison pill per worker or check the flag with poll(timeout)); shutdownNow() interrupts workers and returns the undrained tasks. submit wraps the task in a FutureTask so exceptions surface through Future.get() instead of killing the worker.

"Add a dead-letter queue and retries with backoff."

Decorator: new RetryingHandler(userHandler, maxAttempts, backoff, dlqPublisher). After the last failure it publishes the record plus error headers to <topic>.dlq and returns normally so the offset advances. Mention that blocking retries stall the partition; for long backoff, publish to a delay/retry topic instead.

"Consumers should be able to replay from an offset or a timestamp."

seek(partition, offset) on the group sets the committed offset. For timestamps, binary-search the partition log by publishedAt since appends are time-ordered (with an injected clock, tests stay deterministic).

"Add retention: drop messages older than X or beyond N per partition."

Keep a baseOffset per partition so logical offsets survive trimming: index = offset − baseOffset. A scheduled task trims under the partition lock. A consumer behind the base offset gets an OffsetOutOfRange and resets to earliest or latest per its policy.

"Push-based delivery instead of polling."

Keep the internal pull loop; the worker is the pusher. That gives backpressure for free (it only fetches when the handler finished). True broker-push needs per-consumer in-flight limits and acks, which is more code for no gain in one process.

"Message filtering / wildcard subscriptions."

A Predicate<Record> on the subscription, applied before the handler; offsets still advance for filtered records. Wildcards: resolve topic patterns at subscribe time and on createTopic.

"How would this become real Kafka?" (CleverTap-style)

Partition becomes a segmented append-only file with an offset index, replicated to followers; the leader acks once in-sync replicas have it (acks=all, min.insync.replicas). Group coordination moves to a coordinator broker with heartbeats and session timeouts. Offsets live in an internal compacted topic. Ordering is still only per partition.

09Mistakes that got candidates rejected, and review questions

Rejected for this
  • Weak shutdown and exception handling in the thread pool follow-up (Rubrik "lean hire": shutdown() not convincing, catching only InterruptedException and Exception was "not enough" — think about what a task's exception does to the worker thread and how callers observe it).
  • Not understanding the ask and fumbling the API for a generic queue system, then being unable to answer counter-questions about partitions and brokers (CleverTap rejection).
  • One synchronized on the whole broker: correct, but every topic serialises behind one lock, and the reviewer will ask why.
  • Busy-wait polling loops with Thread.sleep(1).
  • Claiming "global ordering" while using several partitions and several consumers.
  • No running demo at the end; code that "would work".
Why a lock per partition and not one lock for the broker?

Partitions are independent units of ordering, so they are the natural unit of mutual exclusion. Producers to different partitions never contend. The topic and group maps are ConcurrentHashMap, so lookup is lock-free.

Why not CopyOnWriteArrayList for the log?

Every append copies the array: O(n) per write, quadratic overall. It is for read-mostly lists with rare writes, the opposite of a log.

Why not just use LinkedBlockingQueue per partition?

A queue removes on take, so a second group cannot read the same message and nobody can replay. A log plus per-group offsets gives fan-out and replay for free. For a single-group work queue a BlockingQueue is fine, and I would say so.

What delivery guarantee do you give and where is it decided?

At-least-once: the worker commits offset + 1 after the handler returns. Moving the commit before the handler makes it at-most-once. Exactly-once needs idempotent handlers or transactional commit of output and offset together.

What if one partition is hot?

Ordering per key forces that key to one partition, so one consumer handles it. Options: better keys (add a sub-key if strict ordering only matters per sub-entity), more partitions, or within a consumer process different keys of the same partition in parallel while keeping per-key order (key-ordered executor).

Why virtual threads here?

Workers mostly block in awaitNanos; virtual threads make one-thread-per-consumer cheap. ReentrantLock does not pin a carrier thread the way synchronized did before JDK 24, which is another reason for explicit locks in the partition.

How do you add a new partitioning rule without touching Topic?

Implement Partitioner and pass it to createTopic. Open/closed: the topic only depends on the interface.

10A 90-minute plan

0–8 minClarify: groups, per-key ordering, pull, at-least-once, dynamic membership. Write the agreed requirements as a comment block at the top of Main.
8–15 minSketch classes (table above) and the publish and consume flow. Name the patterns aloud.
15–35 minMessage, Record, Partitioner, Partition with lock and Condition, Topic. Quick test: concurrent producers, contiguous offsets.
35–55 minConsumerGroup with range assignment and generation, ConsumerWorker poll loop, Broker façade with virtual threads.

70–82 minRetryingHandler + DLQ decorator, consumer leave and rebalance, clean close().
