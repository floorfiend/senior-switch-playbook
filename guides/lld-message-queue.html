In-memory Message Queue / Pub-Sub

Build a small, thread-safe Kafka in 90 minutes, then defend it. You need topics, partitions, consumer groups and offsets. Each idea is explained below.

Time-box: 90 min code + 30 min review Seen: Flipkart SDE-3 machine coding; queue/thread-pool variants at Rubrik, Goldman Sachs, LinkedIn, CleverTap
FlipkartRubrikGoldman SachsLinkedInCleverTap
In 30 seconds
  • A topic is split into partitions. Each partition is a list you only add to the end of.
  • The same key always goes to the same partition. So order is kept per key, not for the whole topic.
  • Each consumer group remembers its own reading position (offset) in each partition.
  • Use one lock per partition and a Condition to wait. A generation number blocks stale workers after a rebalance.
Picture it

Think of a railway booking office with several counters. Each counter is a partition. Each counter keeps a numbered register. Billing clerks and audit clerks are two consumer groups. Each group reads every register. Each group keeps its own bookmark at the last line it read. That bookmark is the offset.

Words you'll see
Topic
A named stream of messages, like "orders". Producers write to it, consumers read from it.
Partition
One slice of a topic. It is a list that only grows at the end, so its order never changes.
Offset
A message's position number inside one partition: 0, 1, 2 and so on. A group's offset is its bookmark.
Consumer group
A team of consumers that share the work. Each message goes to one member of the team.
Commit
Saving the bookmark: "we are done up to here". After a crash, reading restarts from the last commit.
Rebalance
Handing out the partitions again when a consumer joins or leaves the group.
At-least-once
A message is never lost, but it may be delivered twice after a crash.
Idempotent
Doing it twice has the same effect as doing it once. Processing an order twice ships it once.

01What the interviewer is grading

A working first version (MVP)

A main or JUnit test creates a topic and runs producers and consumers on threads. It prints output in order. At Flipkart, code that does not run by minute 90 usually fails you.

Correct order rules

Order is kept per partition, not per topic. The same key goes to the same partition. Inside a group, one consumer reads one partition.

Thread safety you can explain

Where the locks are. Why you wait on a Condition instead of checking in a loop. What happens in a rebalance. What "at-least-once" means for your commit order.

Easy to extend

The partition choice is a strategy. Handlers are an interface. Retry and the dead-letter queue are decorators. New needs should add classes, not change the broker.

You are graded twice on the same code. First come 90 minutes of coding. Then a 30-minute review covers OOP, design patterns and thread safety.

Go deeper: the interview reports behind this page

The Flipkart SDE-3 report (Oct 2025, selected) is the model. It was a 90-minute machine-coding round. The task: build "a working MVP for an in-memory message streaming service supporting multiple topics, producers, and consumers". It needed order within partitions, thread safety and real-time streaming. Then came a separate 30-minute review round. It was an "in-depth discussion about my solution ... modularity, OOP principles, design patterns and concurrency." So you are graded twice on the same code.

Other companies ask a lower-level version of the queue. Rubrik's screening round asks for a bounded blocking queue. That is a queue with a size limit, where threads wait when it is full or empty. Next, you build a thread pool on top of it (submit, execute, shutdown, shutdownNow). The candidate got "lean hire", a weak yes. Their shutdown() and the exceptions they caught were not convincing. CleverTap's associate-director round asked about Kafka brokers, topics and partitions. It asked for a "generic queue system for teams to use". Then it asked for an "at most two threads in parallel" exercise (a Semaphore(2)). Prepare the basic building blocks, not only the front class.

02Clarifying questions to ask

Pub-sub or queue?

Consumer groups give both. Different groups each get every message. Members of one group share the load.

Order for everything, or per key?

Per key. Order for everything means one partition, so nothing runs in parallel.

Pull or push?

Pull, with a wait when nothing is there. Slow consumers then simply fetch less (free backpressure).

Delivery guarantee?

At-least-once. Commit after processing. Handlers must be idempotent.

03Requirements

Functional (what it does)

  • Create a topic with N partitions.
  • Publish (key, payload). The same key goes to the same partition. Return (partition, offset).
  • Subscribe a consumer to a topic, under a group id, with a handler.
  • Each message goes to exactly one consumer per group. Every group sees every message.
  • Order is kept within a partition.
  • Consumers can leave. Their partitions are handed to others.
  • Save committed offsets per (group, partition). A new group can start from the oldest or newest message.

Non-functional (how well it does it)

  • Safe with many producers and consumers running at once.
  • No busy-waiting. Consumers sleep until data arrives or time runs out.
  • Publish takes O(1) time. A read takes time in proportion to the batch size.
  • At-least-once delivery.
  • Clean shutdown: no lost commits, and all threads stop.

Out of scope (say so)

  • Saving to disk and copying data to other machines. Mention log segments and ISR (in-sync replicas) only as follow-ups.
  • Network protocol and brokers on many machines.
  • Exactly-once transactions.
  • Login checks and usage limits.

public interface Partitioner {
    int partition(String key, int numPartitions);
}

public final class KeyHashPartitioner implements Partitioner {
    private final AtomicInteger roundRobin = new AtomicInteger();

    @Override
    public int partition(String key, int numPartitions) {
        if (key == null) {
            return Math.floorMod(roundRobin.getAndIncrement(), numPartitions); // keyless: spread load
        }
        return Math.floorMod(key.hashCode(), numPartitions); // floorMod: hashCode can be negative
    }
}
Show Java: Partition
final class Partition {
    private final String topic;
    private final int id;
    private final List<Message> log = new ArrayList<>();
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition appended = lock.newCondition();

    Partition(String topic, int id) { this.topic = topic; this.id = id; }

    long append(Message m) {
        lock.lock();
        try {
            log.add(m);
            appended.signalAll(); // wake long-polling readers
            return log.size() - 1L;
        } finally {
            lock.unlock();
        }
    }

    /** Blocks up to {@code wait} if there is nothing at {@code from}. Never busy-waits. */
    List<Record> read(long from, int max, Duration wait) throws InterruptedException {
        lock.lock();
        try {
            long nanos = wait.toNanos();
            while (from >= log.size() && nanos > 0) {
                nanos = appended.awaitNanos(nanos); // loop guards against spurious wake-ups
            }
            if (from >= log.size()) {
                return List.of();
            }
            int end = (int) Math.min(log.size(), from + max);
            List<Record> out = new ArrayList<>(end - (int) from);
            for (int i = (int) from; i < end; i++) {
                out.add(new Record(topic, id, i, log.get(i)));
            }
            return out; // copy: callers never see the live list
        } finally {
            lock.unlock();
        }
    }
}
Show Java: Topic
public final class Topic {
    private final String name;
    private final List<Partition> partitions;
    private final Partitioner partitioner;

    Topic(String name, int n, Partitioner partitioner) {
        this.name = name;
        this.partitioner = partitioner;
        this.partitions = IntStream.range(0, n).mapToObj(i -> new Partition(name, i)).toList();
    }

    Record publish(Message m) {
        int p = partitioner.partition(m.key(), partitions.size());
        long offset = partitions.get(p).append(m);
        return new Record(name, p, offset, m);
    }

    Partition partition(int p) { return partitions.get(p); }
    int partitionCount() { return partitions.size(); }
    String name() { return name; }
}
Show Java: ConsumerGroup

The consumer group owns its members and offsets. Every change to members raises a generation number. A worker with an old generation cannot commit. Kafka uses the same idea, called fencing.

final class ConsumerGroup {
    private final String id;
    private final Topic topic;
    private final Map<Integer, Long> committed = new ConcurrentHashMap<>();
    private final List<String> members = new ArrayList<>();          // guarded by this
    private volatile Assignment assignment = new Assignment(0, Map.of());

    record Assignment(int generation, Map<String, List<Integer>> byMember) {
        List<Integer> of(String member) { return byMember.getOrDefault(member, List.of()); }
    }

    ConsumerGroup(String id, Topic topic) { this.id = id; this.topic = topic; }

    synchronized void join(String member) { members.add(member); rebalance(); }

    synchronized void leave(String member) { members.remove(member); rebalance(); }

    private void rebalance() { // range assignment; swap in a strategy if asked
        Map<String, List<Integer>> next = new HashMap<>();
        for (int p = 0; p < topic.partitionCount() && !members.isEmpty(); p++) {
            next.computeIfAbsent(members.get(p % members.size()), k -> new ArrayList<>()).add(p);
        }
        assignment = new Assignment(assignment.generation() + 1, Map.copyOf(next)); // single volatile publish
    }

    Assignment assignment() { return assignment; }

    long position(int partition) { return committed.getOrDefault(partition, 0L); }

    /** Returns false if the caller's generation is stale (partition moved to someone else). */
    boolean commit(int partition, long nextOffset, int generation) {
        if (generation != assignment.generation()) {
            return false;
        }
        committed.merge(partition, nextOffset, Math::max); // offsets never move backwards
        return true;
    }
}
Show Java: MessageHandler, ConsumerWorker
@FunctionalInterface
public interface MessageHandler {
    void handle(Record record) throws Exception;
}

final class ConsumerWorker implements Runnable {
    private final String memberId;
    private final Topic topic;
    private final ConsumerGroup group;
    private final MessageHandler handler;
    private volatile boolean running = true;

    ConsumerWorker(String memberId, Topic topic, ConsumerGroup group, MessageHandler handler) {
        this.memberId = memberId; this.topic = topic; this.group = group; this.handler = handler;
    }

    @Override
    public void run() {
        try {
            while (running) {
                ConsumerGroup.Assignment a = group.assignment(); // snapshot once per loop
                List<Integer> mine = a.of(memberId);
                if (mine.isEmpty()) { Thread.sleep(20); continue; }
                for (int p : mine) {
                    List<Record> batch = topic.partition(p).read(group.position(p), 100, Duration.ofMillis(50));
                    for (Record r : batch) {
                        if (group.assignment().generation() != a.generation()) {
                            break;                                              // rebalanced: stop before handling
                        }
                        handleQuietly(r);                                       // process first...
                        if (!group.commit(p, r.offset() + 1, a.generation())) { // ...then commit: at-least-once
                            break;                                              // partition was reassigned
                        }
                    }
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restore flag and exit
        } finally {
            group.leave(memberId);
        }
    }

    private void handleQuietly(Record r) {
        try {
            handler.handle(r);
        } catch (Exception e) {
            // RetryingHandler + DLQ decorate the handler; anything reaching here is logged and skipped
            System.err.printf("dropped %s-%d@%d: %s%n", r.topic(), r.partition(), r.offset(), e);
        }
    }

    void stop() { running = false; }
}
Show Java: Broker, Subscription
public final class Broker implements AutoCloseable {
    private final Map<String, Topic> topics = new ConcurrentHashMap<>();
    private final Map<String, ConsumerGroup> groups = new ConcurrentHashMap<>();
    private final ExecutorService workers = Executors.newVirtualThreadPerTaskExecutor();
    private final Clock clock;

    public Broker(Clock clock) { this.clock = clock; }

    public void createTopic(String name, int partitions, Partitioner partitioner) {
        if (topics.putIfAbsent(name, new Topic(name, partitions, partitioner)) != null) {
            throw new IllegalArgumentException("topic exists: " + name);
        }
    }

    public Record publish(String topic, String key, String payload) {
        return topicOrThrow(topic).publish(new Message(key, payload, clock.instant()));
    }

    public Subscription subscribe(String topic, String groupId, MessageHandler handler) {
        Topic t = topicOrThrow(topic);
        ConsumerGroup g = groups.computeIfAbsent(topic + "/" + groupId, k -> new ConsumerGroup(groupId, t));
        String memberId = groupId + "-" + UUID.randomUUID();
        ConsumerWorker w = new ConsumerWorker(memberId, t, g, handler);
        g.join(memberId);
        Future<?> f = workers.submit(w);
        return () -> { w.stop(); f.cancel(true); }; // cancel interrupts a blocked read
    }

    private Topic topicOrThrow(String name) {
        Topic t = topics.get(name);
        if (t == null) throw new IllegalArgumentException("unknown topic: " + name);
        return t;
    }

    @Override
    public void close() throws InterruptedException {
        workers.shutdownNow();
        workers.awaitTermination(5, TimeUnit.SECONDS);
    }
}

@FunctionalInterface
public interface Subscription extends AutoCloseable {
    @Override void close();

07Concurrency and edge cases

Reviewers hunt for one bug. A rebalance happens while a worker is in the middle of a batch.

  • Fence: check the generation before each record, and again at commit.
  • Never go backwards: committed.merge(p, next, Math::max) keeps the larger offset.
  • A record already inside a handler can still come again once. That is at-least-once. So handlers must be idempotent.

08Extensions interviewers add mid-round

Limited size, producers wait

Add a second Condition notFull. Or use a separate bounded blocking queue (code below).

DLQ and retry with backoff

A decorator. After the last failure, publish to <topic>.dlq (dead-letter queue) and let the offset move on.

Replay from an offset or a time

seek() sets the saved offset. To find a time, binary-search by publishedAt.

Retention (deleting old messages)

Keep a baseOffset per partition. Then list index = offset − baseOffset.

Push delivery

Keep the pull loop inside. The worker does the pushing.

Filters and wildcards

Add a Predicate<Record> per subscription. Offsets still move on for skipped messages.

Make it real Kafka

Split files into segments, copy data to other machines, add a group coordinator, store offsets in a compacted topic.

Go deeper: full answers for each extension
"Make the queue bounded; producers should block when full."

Give each partition a capacity, plus a second Condition notFull. Producers await while it is full. Consumers do not remove from a log, so reading frees no space. So define "full" as messages kept minus the slowest group's committed offset. Then trim old messages. The interviewer often wants something simpler: a separate bounded blocking queue, shown below.

Show Java: BoundedBlockingQueue
public final class BoundedBlockingQueue<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    public BoundedBlockingQueue(int capacity) { items = new Object[capacity]; }

    public void put(T item) throws InterruptedException {
        Objects.requireNonNull(item);
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();
            items[tail] = item; tail = (tail + 1) % items.length; count++;
            notEmpty.signal(); // separate conditions: wake one taker, not every waiter
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T item = (T) items[head]; items[head] = null; head = (head + 1) % items.length; count--;
            notFull.signal();
            return item;
        } finally { lock.unlock(); }
    }
}

This uses two conditions, like java.util.concurrent.ArrayBlockingQueue. The thread-pool follow-up works like this. Workers loop on take(). shutdown() sets a flag and rejects new tasks. Workers finish the queued tasks, then exit. To stop them, add one "poison pill" task per worker, or check the flag with poll(timeout). shutdownNow() interrupts the workers and returns the tasks not yet run. submit wraps the task in a FutureTask. Then an exception shows up through Future.get() and does not kill the worker.

"Add a dead-letter queue and retries with backoff."

Use a decorator: new RetryingHandler(userHandler, maxAttempts, backoff, dlqPublisher). After the last failure, it publishes the record and the error headers to <topic>.dlq. Then it returns normally, so the offset moves on. Note that waiting between retries stalls the partition. For long waits, publish to a separate delay or retry topic instead.

"Consumers should be able to replay from an offset or a timestamp."

seek(partition, offset) on the group sets the saved offset. For a timestamp, binary-search the partition log by publishedAt. This works because messages are added in time order. With a clock passed in, tests give the same result every run.

"Add retention: drop messages older than X or beyond N per partition."

Keep a baseOffset per partition, so offsets keep their meaning after trimming. List index = offset − baseOffset. A scheduled task trims old messages under the partition lock. A consumer behind the base offset gets OffsetOutOfRange. It then jumps to the oldest or newest message, based on its setting.

"Push-based delivery instead of polling."

Keep the pull loop inside. The worker does the pushing. You get backpressure for free, because it fetches only after the handler finishes. Real broker push needs a limit on messages in flight per consumer, plus acks. That is more code with no gain inside one process.

"Message filtering / wildcard subscriptions."

Put a Predicate<Record> on the subscription. Run it before the handler. Offsets still move on for skipped records. For wildcards, match topic patterns at subscribe time, and again on createTopic.

"How would this become real Kafka?" (CleverTap-style)

A partition becomes a file split into segments, with an index by offset. It is copied to follower machines. The leader confirms a write once the in-sync replicas (followers that are up to date) have it. The settings are acks=all and min.insync.replicas. A coordinator broker runs the groups, using heartbeats and session timeouts. Offsets live in an internal compacted topic, which keeps only the latest value per key. Order is still only per partition.

09Tests to write

No gaps in offsets

8 threads each publish 1,000 messages to one partition. Expect offsets 0..7999 with no gaps.

Order per key

The handler sees sequence numbers for each key always going up.

Old commit rejected

With an old generation, commit returns false. The offset does not change.

Wait with latches and timeouts. Never use Thread.sleep.

Rejected for this

Interview questions

Why a lock per partition and not one lock for the broker?

Each partition keeps its own order, apart from the others. So each partition is the natural thing to lock. Producers writing to different partitions never wait for each other. The topic and group maps are ConcurrentHashMap, so lookups need no lock.

Why not CopyOnWriteArrayList for the log?

Every append copies the whole array. That is O(n) per write, and O(n²) in total. It is built for lists that are read a lot and written rarely. A log is the opposite.

Why not just use LinkedBlockingQueue per partition?

A queue removes a message when it is taken. So a second group cannot read it, and nobody can replay it. A log plus one offset per group gives fan-out (every group gets every message) and replay for free. For a work queue with only one group, a BlockingQueue is fine, and I would say so.

What delivery guarantee do you give and where is it decided?

At-least-once. The worker commits offset + 1 after the handler returns. Moving the commit before the handler makes it at-most-once. Exactly-once needs idempotent handlers. Or it needs the output and the offset saved together in one transaction.

What if one partition is hot?

Order per key forces that key onto one partition, so one consumer handles it. There are three options. Pick better keys: add a sub-key if strict order only matters per sub-item. Add more partitions. Or, inside one consumer, process different keys of the same partition in parallel. Keep order per key with a key-ordered executor.

Why virtual threads here?

Workers spend most of their time waiting in awaitNanos. Virtual threads make one thread per consumer cheap. Before JDK 24, synchronized pinned the real carrier thread underneath a virtual thread. ReentrantLock does not pin it. That is another reason to use explicit locks in the partition.

How do you add a new partitioning rule without touching Topic?

Implement Partitioner and pass it to createTopic. This is the open/closed principle: the topic depends only on the interface.

12Quick check

The interviewer wants all events for one order handled in order. What do you promise?

Order for the whole topic would force one partition. Hashing the order id picks one partition for that order. Its events stay in order, while other orders run in parallel.

You move commit before the handler call. What changes?

The bookmark has already moved past the message. After a crash, nobody reads it again.

Why use a log plus one offset per group, instead of a LinkedBlockingQueue per partition?

A log keeps every message. Each group tracks its own position. So every group gets every message, and you can replay.

A worker lost its partition in a rebalance. It now tries to commit. What stops it?

Each rebalance raises the generation. A commit carries the generation it started with. So old owners are shut out.

Cheat sheet
  • A topic has N partitions. A partition is a list that only grows at the end. Offset = list index.
  • Same key goes to the same partition (floorMod(hash, n)). Order holds only within a partition.
  • Different groups each get every message. One group shares the work, one consumer per partition.
  • One lock per partition, plus a Condition for waiting reads. No busy-waiting.
  • Process first, then commit offset + 1. That is at-least-once, so handlers must be idempotent.
  • A rebalance raises the generation. Old commits are rejected. Use merge(Math::max).
  • Patterns: Strategy (partitioner), Decorator (retry, DLQ), Façade (Broker). No Singleton.
  • Have a running demo by minute 70. Set the interrupt flag again on shutdown.
