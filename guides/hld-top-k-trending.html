Top-K / Trending Over Time Windows

Design a pipeline that counts a huge stream of events, like article shares. It must show the top N items for the last 5 minutes, the last hour and the last 24 hours.

Time-box: 45–60 min Seen: LinkedIn, eBay, Oracle (3 variants), Uber, Amazon, 2025–26
LinkedInOracleeBayUberAmazon
In 30 seconds
  • Keep counting and ranking apart. Count per item in many parallel workers. Then rank by merging their small lists.
  • Keep per-minute and per-hour counts for each item. When a time slot leaves the window, subtract it.
  • Merging each worker's top list is only correct if all events for one item go to the same worker.
  • Compute the ranking ahead of time and store it in Redis. Never sort when a user asks.
Picture it

Think of election counting in India. Each booth counts only its own ballots. Then the returning officer adds up the booth totals. Now suppose one candidate's votes were spread across booths at random. You could not just compare each booth's top-3 list. You would have to add the counts.

Words you'll see
Top-K
The K items with the highest counts. "Top 10 most-shared articles" is a top-K with K = 10.
Window
The time range we count over, like "the last 1 hour". A sliding window moves forward every minute.
Bucket
A small counter for one time slot, like "shares of article a_123 during 10:04".
Kafka partition
Kafka is a message log. A partition is one ordered lane of it. All messages with the same key go to the same lane.
Stream processor (Flink, Kafka Streams)
A program that reads events forever and keeps running totals. It saves its state regularly so it can recover after a crash.
Min-heap
A structure that always knows its smallest item. A min-heap of 100 holds the current top 100. A new item enters only if it beats the smallest.
Count-Min Sketch
A small fixed-size grid of counters that estimates counts. It uses little memory but can only overestimate.
Hot key
One item that gets a huge share of the traffic, like a viral article. It overloads the one worker that owns it.

01What the interviewer is grading

Windowing

A rolling 24-hour window, without recounting 24 hours of events every time.

Two-stage aggregation

Each worker builds its own top-K. Then one step merges them. Know when that merge gives the exact answer.

Memory discipline

Exact counts or small estimates (sketches)? If you estimate, say how big the error can be.

Read path

Compute the top-K ahead of time and serve it from a cache. Never sort when the request comes in.

Hot keys and late events

One viral article gets most of the traffic. Some phones report their events 3 minutes late.

Go deeper: the variants companies asked

All the variants share one skeleton. LinkedIn Senior (Aug 2026) asked to "maintain a Top-N leaderboard of the most-shared articles over rolling windows of 5 minutes, 1 hour and 24 hours". eBay SDE-3 asked for a top-10 items and categories dashboard. It was built on Kafka, with RocksDB state and a step that merges partitions. Oracle asked three versions. First, top-K URLs overall and in the last 24 h, with limited RAM. Second, top-100 users per hour, choosing Flink or Spark. Third, top-K services by error logs in 5 minutes. Uber asked for a trending items page. Amazon asked for personalised search suggestions with a trending top-K.

02Clarify and scope

Functional

  • Take in share events
  • Top N (N ≤ 100) for each window: 5 min, 1 h, 24 h
  • Optional filters: country, category

Non-functional

  • 99 out of 100 reads under 50 ms (p99 < 50 ms); 20k reads per second
  • Data no older than 1 min (5 min window) or 5 min (24 h window)
  • Take in 50k events per second at peak, losing none
  • Approximate counts are fine, if you state the error

Out of scope

  • Per-user ranking (discuss as an extension)
  • Spam detection models (just show where they plug in)
  • All-time history analytics
Go deeper: all six scoping questions
  • Exact or approximate? A leaderboard can live with ±0.1% count error. A billing report cannot. This one answer picks the algorithm.
  • Sliding or tumbling window? "Last 1 hour, refreshed every minute" is a sliding window that moves 1 minute at a time. A tumbling window ("each clock hour", no overlap) is cheaper.
  • How fresh? Fresh within seconds needs a streaming job. An "hourly report" can be a batch job. This is the Oracle Flink vs Spark question.
  • One global list or many segments? Separate lists per country, category or user group multiply the number of top-K lists.
  • Popular or trending? Popular means the most shares overall. Trending means growing fastest compared with normal. Trending needs a speed score.
  • Duplicates and abuse? Count one share per user per article. Filter out bots.

  • Ingest checks the event, adds the server time and sends it to Kafka keyed by article_id. It drops exact retries by remembering eventIds for a short time (TTL), in Redis or in Flink state.
  • Count stage keeps rings of time buckets per article. Each event adds 1 to the current minute bucket and to each window's running sum.
  • Local top-K keeps a min-heap of size K per window per partition. It refreshes it from the running sums of items that changed since the last output.
  • Merge stage runs as a single worker, or one per segment. It receives 64 lists of K and merges them into the global top-K. Then it writes to Redis. 64 × 100 entries is tiny.
  • Batch path recalculates exact hourly and daily top-K from S3. It feeds reports and fixes drift (the "Lambda" pattern). It is optional if the streaming state is already exact.

06Deep dives

6.1 Rolling windows without recounting

Keep buckets per item, plus a running sum. When a bucket falls out of the window, subtract it from the sum.

a_123's 5-minute window, minute by minute
Show Java bucket ring
// per article, owned by one task thread (keyed state)
long[] minute = new long[60];   // ring buffer
long[] hour   = new long[24];
long sum5m, sum1h, sum24h;

void onEvent(long tsMinute) {
    minute[(int) (tsMinute % 60)]++; sum5m++; sum1h++;
    hour[(int) ((tsMinute / 60) % 24)]++; sum24h++;
}
void onMinuteTick(long nowMinute) {      // timer: subtract buckets leaving each window
    sum5m  -= minute[(int) ((nowMinute - 5) % 60)];
    sum1h  -= minute[(int) ((nowMinute - 60) % 60)];
    minute[(int) ((nowMinute - 60) % 60)] = 0;     // slot reused for the new minute
    if (nowMinute % 60 == 0) { int h = (int) ((nowMinute / 60 - 24) % 24); sum24h -= hour[h]; hour[h] = 0; }
}
Go deeper: 24 h granularity and Flink sliding windows

Each event costs O(1). Each minute tick costs O(1) per active item. The 24 h window uses hourly buckets, so it moves forward in 1-hour steps. The interviewer may want a 24 h window that is accurate to the minute. Then use minute buckets for the newest hour and hourly buckets for the rest (a two-level ring). Items whose buckets are all zero are removed. So memory grows with recently active articles, not with every article ever.

Flink has the same idea built in: SlidingEventTimeWindows.of(Time.hours(1), Time.minutes(1)) with an incremental AggregateFunction. But Flink puts each event into 60 overlapping window copies. With many overlapping windows, the hand-written bucket ring is cheaper. You build it as a KeyedProcessFunction with timers. Knowing this is a senior signal.

6.3 Count-Min Sketch, step by step

A Count-Min Sketch is a grid of d rows × w counters. Each item is hashed to one counter in every row. To read a count, take the smallest value across its counters.

6.4 Oracle's limited-RAM variant

  1. Pass 1Read 1 TB of logs once. Hash each URL to pick one of M ≈ 2,000 files, and write it there (hash(url) % M). The same URL always goes to the same file, and each file fits in 1 GB of RAM.
  2. Pass 2Count each file with a HashMap. Push the counts into one global min-heap of size K.
  3. ResultThe exact top-K, in two passes over the disk.
Go deeper: the full Oracle answer

The question: "Top-K URLs across logs bigger than memory." The classic answer reads the logs once. It writes each URL to one of M files by hash(url) % M, so each file fits in RAM. Then it counts each file with a HashMap and keeps a global min-heap of size K. That is two passes over disk, and it is exact. It works with 1 GB of RAM for 1 TB of logs (M ≈ 2,000). For "last 24 h", add time buckets. For "top-100 users per hour", a tumbling 1-hour window is enough. So Spark on hourly data is fine, if results about an hour old are acceptable. Choose Flink if the answer must be live within seconds. Choose Spark if the window closes hourly and exactness and simplicity matter. "Top-K services by error logs in 5 min" is a tumbling 5-minute window. It has few keys (one per service), so exact counting in one Flink job is enough. The hard part is the volume of logs coming in. You solve it by adding up counts inside the log agent before sending.

6.5 Trending, not just popular

Velocity score

(count_1h − expected_1h) / sqrt(expected_1h + 1). "Expected" is the same hour last week. It measures how unusual the growth is.

Time decay

score = Σ e^(−λ·age) over buckets. Older shares count for less, so they fade out.

Personalised

Take ~100 trending candidates and re-rank them per user when they ask. Never build a top-K per user in the stream.

Go deeper: Uber and Amazon variants

Uber's trending items and Amazon's trending suggestions should not just show items that are always popular. Score each item by how fast it grows against its normal level: score = (count_1h − expected_1h) / sqrt(expected_1h + 1). "Expected" comes from the same hour last week. Or give older buckets less weight with exponential decay: score = Σ e^(−λ·age). For Amazon's personalised suggestions, compute global and per-segment trending candidates offline or in the stream. Then, when the user asks, re-rank the top ~100 using that user's features. Do not compute a top-K per user in the stream.

07Design choices

Redis ZINCRBY per event

  • Simplest, and always live
  • Removing old events needs one sorted set per bucket, combined with ZUNIONSTORE
  • 50k writes per second on popular keys

Low volume, few items.

Flink / Kafka Streams + RocksDB usual pick

  • Exact, scales out, saves checkpoints, uses the event's own time
  • More to run and operate

Default at LinkedIn or eBay scale.

Count-Min Sketch + heap

  • Small fixed memory; sketches can be merged
  • Approximate; needs a separate list of candidates

Billions of items, many segments.

Space-Saving / Misra-Gries

  • Only O(K / ε) counters; keeps every item seen more than N/m times
  • Approximate counts

Finding the most frequent items under a strict memory limit.

Batch (Spark hourly)

  • Exact, cheap, simple
  • Results are at least one window old

Reports, and Oracle's top-100 users per hour. Use Flink if it must be live mid-hour.

Lambda (stream approx + batch exact)

  • Fresh now, and exact later
  • Two code paths to maintain

When counts decide money (ads, payouts).

08Scaling, failure handling and consistency

Hot key

Add up counts per second at ingest first. Or "salt" the key (a_123#0..7) to spread it, then sum the parts by item.

Late events

Count by the event's own time. A watermark waits about 2 min for stragglers. Older events are dropped and counted in a metric.

Failure

Save RocksDB state and Kafka offsets every 30–60 s. On restart, reload and replay.

Atomic reads

Swap in a whole new list at once, so readers never see half a ranking.

10× / 100×

Plan the partition count up front. At 100× with segments, switch to sketches.

Multi-region

Send each region's partial counts, not its lists, to one global aggregator.

Go deeper: full scaling notes
  • Hot key. One viral article sends 30% of events to one partition. Fix one: add up counts in the ingest tier, per article per second, in memory, and send partial counts. Fix two: salt the key (a_123#0..7) for the count stage. Then sum the parts in a second stage keyed by article.
  • Late and out-of-order events. Count by event time, with watermarks. A watermark says "I have probably seen everything up to time T". Allow some lateness, for example 2 min. Late events still update their bucket, and the next output fixes the snapshot. Events older than the window are dropped and counted in a metric.
  • Failure. Flink saves RocksDB state to S3 every 30–60 s, together with the Kafka offsets. On restart it goes back to that checkpoint and replays. So each event affects the state exactly once. Kafka Streams restores from a changelog topic. Use standby copies so failover takes seconds.
  • Read path. 20k reads per second on ~18k small keys is easy for Redis plus a 30 s CDN cache. The merge stage writes a whole new list in one step. It uses a SET of a saved list, or RENAME of a prepared sorted set. Readers never see a half-updated ranking.
  • 10× growth. Add Kafka partitions and more count tasks. Plan the partition count up front, because changing it moves keys. The merge stays tiny. At 100× with segments, move to sketches and sample low-value events.
  • Multi-region. Count in each region. For a global board, send per-region partial counts to a global aggregator, not top-K lists.

09Mistakes that got candidates rejected

Rejected for this
  • Merging local top-K lists from randomly split data and calling the result exact.
  • Sorting when the user asks. Or using one Redis sorted set with no plan for removing old events from the window.
  • Jumping to Count-Min Sketch without numbers. Then failing to explain its error, or why it cannot list items.
  • Ignoring hot keys and late events.
  • Building 5 min, 1 h and 24 h as three separate pipelines. One counting stage with several bucket sizes is enough.

10Quick check

Events are spread at random across 64 partitions. Each partition sends its own top 100. Is the merged top 10 exact?

Merging lists is exact only when each item's whole count lives in one partition, which means keying by item. Otherwise, merge the counts.

A Count-Min Sketch says article X has 5,200 shares. What do you know for sure?

Collisions can only add to a counter, and we take the smallest counter. So the sketch never reports less than the truth.

How does the 24 h window drop old shares cheaply?

You expire buckets, not single events. The cost is one step per active item each time a bucket ends.

One article goes viral, and its partition falls behind. What is the best fix?

More partitions do not help, because the hot item still hashes to one of them. Split its counting, then combine the parts by item.

11Follow-up questions interviewers asked

Why not just run SELECT ... GROUP BY ... ORDER BY count LIMIT 10 on the events table?

At 200M events a day, that query scans tens of millions of rows per window. It does this on every refresh, for every segment. It can work on an analytics store like Pinot, with pre-computed totals, at low QPS (queries per second). For a public leaderboard, compute the ranking when events are written. Then serve a cached snapshot.

Can you merge top-K lists from different partitions?

Only if the data is split by the ranking key. Then each item's count is complete in one partition. Otherwise you must merge counts, not lists. An item that is #101 in every partition can be #1 overall.

How do you expire events from the 24 h window?

You do not expire events. You expire buckets. Each item keeps hourly buckets in a ring, plus a running sum. When an hour leaves the window, subtract that bucket and set it to zero. The cost is per active item per bucket boundary, not per event.

What error does Count-Min Sketch give, and in which direction?

It only overestimates. The error is at most εN, with probability 1 − δ. Here N is the total count, width = e/ε and depth = ln(1/δ). With N = 200M and ε = 0.01%, the error is at most 20k shares. That is fine for a top 10 of viral items. It is wrong for the long tail of small items.

Flink or Spark for top-100 users per hour?

Maybe the result is only needed when the hour ends, and nobody looks earlier. Then Spark batch on hourly data is simpler and exact. If you need a live view during the hour, or several windows at once, use Flink with keyed state. Spark Structured Streaming sits in between. It processes small batches every few seconds.

How do you stop bots from gaming the leaderboard?

Count different users per article, not raw shares. Use a HyperLogLog per article per bucket (a tiny structure that estimates unique counts). Or drop repeats of (user, article) for a while using a TTL. Also rate-limit each user. And apply a spam score from a separate model before counting.

13Cheat sheet

Cheat sheet
  • Flow: Kafka keyed by item, count stage, local top-K, merge, Redis snapshot.
  • Windows are per-item bucket rings with running sums. Subtract buckets as they leave.
  • Merge lists only when keyed by item. Otherwise merge (item, count) pairs.
  • Count-Min Sketch: width e/ε, depth ln(1/δ), take the min across rows. It only overestimates and cannot list items.
  • Hot key: add up early or salt the key, then sum by item.
  • Late events: watermarks. Crash: checkpoint, then replay Kafka.
  • Trending is speed against normal, or time decay. Personalise by re-ranking ~100 candidates.
