Top-K / Trending Over Time Windows

Design a pipeline that counts a high-volume event stream and serves the top N items for the last 5 minutes, 1 hour and 24 hours.

Time-box: 45–60 min Seen: LinkedIn, eBay, Oracle (3 variants), Uber, Amazon, 2025–26
LinkedInOracleeBayUberAmazon
In 30 seconds
  • Separate counting (per key, partitioned) from ranking (merge small lists).
  • Keep time buckets per key; subtract a bucket when it leaves the window.
  • Merging local top-Ks is exact only if Kafka is keyed by item.
  • Precompute the ranking into Redis; never sort at read time.
Picture it

Election counting in India: each booth counts only its own ballots, then the returning officer adds booth totals. If one candidate's votes were split across booths at random, you could not just compare each booth's top-3 lists. You must add the counts.

01What the interviewer is grading

Windowing

A rolling 24 h window without recounting 24 h of events.

Two-stage aggregation

Local top-K, global merge, and when that merge is exact.

Memory discipline

Exact counts vs sketches, with stated error bounds.

Read path

Precompute top-K and serve from cache. Never sort at request time.

Hot keys and late events

One viral article; clients reporting 3 minutes late.

Go deeper: the variants companies asked

The variants share one skeleton. LinkedIn Senior (Aug 2026): "maintain a Top-N leaderboard of the most-shared articles over rolling windows of 5 minutes, 1 hour and 24 hours". eBay SDE-3: a top-10 items / categories dashboard built on Kafka with RocksDB state and a partition merge step. Oracle asked three cuts: top-K URLs overall and in the last 24 h with limited RAM, top-100 users per hour (Flink vs Spark), and top-K services by error logs in 5 minutes. Uber asked a trending items page; Amazon asked personalised autosuggest with trending top-K.

02Clarify and scope

Functional

  • Ingest share events
  • Top N (N ≤ 100) per window: 5 m, 1 h, 24 h
  • Optional dimensions: country, category

Non-functional

  • Read p99 < 50 ms; 20k reads/s
  • Freshness ≤ 1 min (5 m window), ≤ 5 min (24 h)
  • Ingest 50k events/s peak, lossless
  • Approximate counts acceptable (state the bound)

Out of scope

  • Personalised ranking (discuss as extension)
  • Spam ML models (hook only)
  • All-time historical analytics
Go deeper: all six scoping questions
  • Exact or approximate? A leaderboard tolerates ±0.1% count error; a billing report does not. This single answer picks the algorithm.
  • Rolling (sliding) or tumbling? "Last 1 hour, refreshed every minute" is a sliding window with 1-minute slide. Tumbling ("each clock hour") is cheaper.
  • Freshness? Seconds-fresh is a streaming job; "hourly report" can be batch (the Oracle Flink vs Spark question).
  • Global or segmented? Per country, per category, per user segment multiplies the number of top-K lists.
  • Popular or trending? Most shares in absolute terms vs fastest growth relative to its baseline. Trending needs a velocity score.
  • Dedup and abuse? Count one share per user per article; filter bots.

  • Count stage keeps per-article bucket rings. Each event increments the current minute bucket and the window running sums.
  • Local top-K keeps a min-heap of size K per window per partition, refreshed from the running sums of keys touched since the last emit.
  • Merge stage (parallelism 1, or one per segment) receives 64 lists of K, merges into the global top-K and writes Redis. 64 × 100 entries is trivial.
  • Batch path recomputes exact hourly / daily top-K from S3 for reports and to correct drift (Lambda-style). Optional if streaming state is exact.

06Deep dives

6.1 Rolling windows without recounting

Hold buckets per key plus a running sum. When a bucket falls out of the window, subtract it.

a_123's 5-minute window, minute by minute
Show Java bucket ring
// per article, owned by one task thread (keyed state)
long[] minute = new long[60];   // ring buffer
long[] hour   = new long[24];
long sum5m, sum1h, sum24h;

void onEvent(long tsMinute) {
    minute[(int) (tsMinute % 60)]++; sum5m++; sum1h++;
    hour[(int) ((tsMinute / 60) % 24)]++; sum24h++;
}
void onMinuteTick(long nowMinute) {      // timer: subtract buckets leaving each window
    sum5m  -= minute[(int) ((nowMinute - 5) % 60)];
    sum1h  -= minute[(int) ((nowMinute - 60) % 60)];
    minute[(int) ((nowMinute - 60) % 60)] = 0;     // slot reused for the new minute
    if (nowMinute % 60 == 0) { int h = (int) ((nowMinute / 60 - 24) % 24); sum24h -= hour[h]; hour[h] = 0; }
}
Go deeper: 24 h granularity and Flink sliding windows

Each event is O(1); each tick is O(1) per active key. The 24 h window has hourly granularity, so it slides in 1-hour steps; if the interviewer wants a minute-accurate 24 h window, use minute buckets for the newest hour and hourly buckets for the rest (a two-level ring). Keys with all-zero buckets are evicted, which keeps state proportional to recently active articles, not all articles ever.

The same structure in Flink is SlidingEventTimeWindows.of(Time.hours(1), Time.minutes(1)) with an incremental AggregateFunction, but Flink assigns each event to 60 window panes. For many overlapping windows the hand-rolled bucket ring (a KeyedProcessFunction with timers) is cheaper. Knowing that is a senior signal.

A Count-Min Sketch is d rows × w counters. Each key hashes to one counter per row. To read a count, take the minimum across rows.

6.4 Oracle's limited-RAM variant

  1. Pass 1Stream 1 TB of logs; write each URL to file hash(url) % M (M ≈ 2,000) so each file fits in 1 GB RAM.
  2. Pass 2Count each file with a HashMap; push into a global min-heap of size K.

Go deeper: the full Oracle answer

"Top-K URLs across logs bigger than memory." Classic answer: stream the logs once, write each URL to one of M files by hash(url) % M so each file fits in RAM; count each file with a HashMap and keep a global min-heap of size K. Two passes over disk, exact, works with 1 GB of RAM for 1 TB of logs (M ≈ 2,000). For "last 24 h" add time buckets; for "top-100 users per hour" a tumbling window of 1 h is enough, so Spark on hourly partitions is fine if freshness of ~1 hour is acceptable. Choose Flink if the answer must be live within seconds, Spark if the window closes hourly and exactness and simplicity matter. "Top-K services by error logs in 5 min" is a tumbling 5-minute window with a small key space (services), so exact counting in one Flink job is enough; the hard part is ingest volume, solved by pre-aggregating at the log agent.

6.5 Trending, not just popular

Velocity score

(count_1h − expected_1h) / sqrt(expected_1h + 1), baseline = same hour last week.

Time decay

score = Σ e^(−λ·age) over buckets, so old shares fade.

Personalised

Re-rank ~100 trending candidates per user at request time. Never a top-K per user in the stream.

Go deeper: Uber and Amazon variants

Uber's trending items and Amazon's trending suggestions should not just show the always-popular items. Score by velocity against baseline: score = (count_1h − expected_1h) / sqrt(expected_1h + 1) where expected comes from the same hour last week, or apply exponential decay score = Σ e^(−λ·age) to buckets. For Amazon personalised autosuggest, compute global and per-segment trending candidates offline / streaming, then re-rank the top ~100 per user at request time with the user's features. Do not compute a top-K per user in the stream.

07Design choices

Redis ZINCRBY per event

  • Simplest; live
  • Expiring old events needs per-bucket ZSETs + ZUNIONSTORE
  • 50k writes/s on hot keys

Low volume, small key space.

Flink / Kafka Streams + RocksDB usual pick

  • Exact, scalable, checkpointed, event time
  • Operational complexity

Default at LinkedIn / eBay scale.

Count-Min Sketch + heap

  • Fixed tiny memory, mergeable
  • Approximate; needs candidate tracking

Billions of keys, many segments.

Space-Saving / Misra-Gries

  • O(K / ε) counters; contains every key with frequency > N/m
  • Approximate counts

Heavy hitters under a hard memory budget.

Batch (Spark hourly)

  • Exact, cheap, simple
  • Freshness ≥ window

Reports; Oracle top-100 users per hour. Flink if it must be live mid-hour.

Lambda (stream approx + batch exact)

  • Fresh and eventually exact
  • Two code paths

When counts drive money (ads, payouts).

08Scaling, failure handling and consistency

Hot key

Pre-aggregate per second at ingest, or salt (a_123#0..7) and sum partials by key.

Late events

Event time + watermarks (~2 min lateness). Too-old events are dropped and counted.

Failure

Checkpoint RocksDB + Kafka offsets every 30–60 s; replay on restart.

Atomic reads

Swap in a whole new list so readers never see half a ranking.

10× / 100×

Plan partitions up front. At 100× with segments, use sketches.

Multi-region

Ship per-region partial counts, not lists, to a global aggregator.

Go deeper: full scaling notes
  • Hot key. One viral article sends 30% of events to one partition. Pre-aggregate in the ingest tier (count per article per second in memory, emit partial counts) or salt the key (a_123#0..7) for the count stage and sum partials in a keyed second stage.
  • Late and out-of-order events. Use event time with watermarks (allowed lateness e.g. 2 min). Late events still update the bucket; the next emit corrects the snapshot. Events older than the window are dropped and counted in a metric.
  • Failure. Flink checkpoints RocksDB state to S3 every 30–60 s with Kafka offsets; on restart it rewinds to the checkpoint and replays, giving exactly-once state. Kafka Streams restores from a changelog topic; use standby replicas so failover is seconds.
  • Read path. 20k reads/s on ~18k small keys: Redis plus a 30 s CDN cache absorbs it. The merge stage writes a whole new list atomically (SET of a serialised list or RENAME a staged ZSET) so readers never see half-updated rankings.
  • 10× growth. Add Kafka partitions (plan the count up front; repartitioning moves keys), scale count tasks; merge stays tiny. At 100× with segments, move to sketches and sample low-value events.
  • Multi-region. Count per region, ship per-region partial counts (not top-K lists) to a global aggregator for a global board.

09Mistakes that got candidates rejected

Rejected for this
  • Merging local top-K lists from randomly partitioned data and calling it exact.
  • Sorting at read time, or a single Redis ZSET with no story for removing old events from the window.
  • Jumping to Count-Min Sketch without numbers, then not being able to explain its error or why it cannot list keys.
  • Ignoring hot keys and late events.
  • Treating 5 m, 1 h and 24 h as three separate pipelines instead of one counting stage with multiple bucket granularities.

10Quick check

Events are spread randomly across 64 partitions. Each partition sends its local top-100. Is the merged top-10 exact?

Merging lists is exact only when each key's whole count lives in one partition (keyed by item). Otherwise merge counts.

A Count-Min Sketch says article X has 5,200 shares. What do you know?

Collisions only add, and the minimum across rows is taken, so the sketch never underestimates.

How does the 24 h window drop old shares cheaply?

You expire buckets, not events. Cost is per active key per bucket boundary.

One article goes viral and its partition lags. Best fix?

More partitions do not help: the hot key still hashes to one. Split its counting, then recombine by key.

11Follow-up questions interviewers asked

Why not just run SELECT ... GROUP BY ... ORDER BY count LIMIT 10 on the events table?

At 200M events/day the query scans tens of millions of rows per window, every refresh, for every segment. It works on an OLAP store like Pinot with pre-aggregation for low QPS, but for a public leaderboard you precompute at write time and serve a cached snapshot.

Can you merge top-K lists from different partitions?

Only if the data is partitioned by the ranking key, so each key's count is complete in one partition. Otherwise you must merge counts, not lists. A key that is #101 everywhere can be #1 globally.

How do you expire events from the 24 h window?

You do not expire events; you expire buckets. Each key holds hourly buckets in a ring and a running sum; when an hour leaves the window, subtract that bucket and zero it. Cost is per active key per bucket boundary, not per event.

What error does Count-Min Sketch give and in which direction?

It only overestimates, by at most εN with probability 1 − δ, where width = e/ε and depth = ln(1/δ). With N = 200M and ε = 0.01%, error ≤ 20k shares, fine for a top-10 of viral items, wrong for the long tail.

Flink or Spark for top-100 users per hour?

If the result is needed when the hour closes and nobody looks before that, Spark batch on hourly-partitioned data is simpler and exact. If you need a live view during the hour, or several windows at once, Flink with keyed state. Spark Structured Streaming sits between: micro-batches of seconds.

How do you stop bots gaming the leaderboard?

Count distinct users per article (HyperLogLog per article per bucket, or dedup by (user, article) with TTL), rate-limit per user, and apply a spam score from a separate model before counting.

13Cheat sheet

Cheat sheet
  • Kafka keyed by item → count stage → local top-K → merge → Redis snapshot.
  • Windows = per-key bucket rings + running sums; subtract expiring buckets.
  • Merge lists only when keyed by item; otherwise merge (key, count).
  • CMS: width e/ε, depth ln(1/δ), min across rows, only overestimates, cannot list keys.
  • Hot key: pre-aggregate or salt, then sum by key.
  • Late: watermarks. Crash: checkpoint + Kafka replay.
  • Trending = velocity vs baseline or time decay; personalise by re-ranking ~100 candidates.
