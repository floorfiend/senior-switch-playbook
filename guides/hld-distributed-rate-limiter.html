Distributed rate limiter

A rate limiter caps how many requests one user or company can send in a given time. After this page, you can design one for hundreds of gateway servers. You will pick the counting method. You will make the Redis check safe when many servers hit it at once. And you will say what happens when Redis goes down.

Time-box: 45–60 min Seen: ~8 reports, 2025–26 Often paired with: idempotency, CAP rapid-fire
AmazonSalesforceOracleAppleMicrosoftAgodaKotak
In 30 seconds
  • A filter in the API gateway checks every request against counters kept in Redis Cluster.
  • Use the token bucket method by default. Use the exact (but costly) sliding log only for OTP and login.
  • Run one small Lua script inside Redis per request. It reads, decides and writes as one step, so two servers cannot both slip through.
  • If Redis is down, ordinary endpoints keep working with a local counter. Sensitive endpoints refuse requests instead.
Picture it

Think of a FASTag toll plaza with many lanes. Each lane is one gateway server. Before lifting the barrier, every lane checks one shared wallet, which is Redis. If the wallet server goes down, ordinary lanes keep waving cars through and keep their own rough tally. The lane for heavy trucks stays shut. Those trucks are the risky requests, like OTP and payments.

Words you'll see
Rate limit
A cap such as "100 requests per minute per user". Requests over the cap are refused.
Token bucket
Each user has a bucket of tokens. Every request takes one token. Tokens refill at a steady speed, so short bursts are allowed.
Atomic
Done as one step that nothing else can interrupt. No other request can sneak in halfway.
Lua script
A tiny program you send to Redis. Redis runs it start to finish without running any other command in between.
Fail-open / fail-closed
What to do when the limiter breaks. Fail-open lets requests through. Fail-closed refuses them.
429
The HTTP status code for "Too Many Requests". It tells the client to slow down.
Hot key
One counter that gets a huge share of the traffic. It overloads the single Redis server that holds it.
p99
99 out of 100 requests are faster than this time. It measures the slow tail, not the average.

01What the interviewer is grading

Algorithm judgement

Explain four counting methods in two sentences each. Then pick one and give a reason, such as bursts, memory or accuracy.

Atomicity

If the app does GET and then INCR, two servers can race. A Lua script or one atomic command fixes it.

Latency budget

The check runs on every request. It must be one network round trip, under 1–2 ms at p99. Have a plan for hot keys.

Failure behaviour

A limiter that takes the whole API down during a short Redis glitch is worse than no limiter. Say per endpoint whether it fails open or closed.

Distributed reality

Servers' clocks differ. Redis Cluster splits keys into slots. Copies lag behind. Quotas span regions. Staff-level interviewers push on these.

Client contract

Return HTTP 429 with a Retry-After header and remaining-quota headers. Explain how clients should wait and retry.

Go deeper: how each company asked it

The reports show two styles. Amazon asked it from first principles. They covered fixed window, sliding window and token bucket. Then they said "make it work across servers with Redis". Salesforce went deep on the distributed part. They asked about Redis Lua scripts, fail-open versus fail-closed, and multiple regions. Agoda asked for an "API rate limiter" inside a wider microservices discussion.

Go deeper: full requirements

Functional

  • For each request, check and use up quota for a combined key (for example tenant plus user).
  • Apply several rules to one request. Example: 100/min per user AND 10k/min per tenant AND 50k/s for the endpoint overall.
  • Rules are set per tenant plan and can change while running.
  • Return 429 with a hint on when to retry. Show the remaining quota.

Non-functional

  • 1M requests per second at peak across the fleet. 10M active keys.
  • Extra delay under 2 ms at p99. A limiter outage must not cause an API outage.
  • Accurate within about 1–5% for general APIs. Exact for sensitive endpoints.
  • The decision path is up 99.99% of the time. Works across multiple regions.

Out of scope

  • Blocking low-level network floods (L3/L4 DDoS). That is the CDN and WAF's job.
  • Billing and metering. Related, but they need exactly-once counts.
  • Queuing requests and smoothing traffic.

04API design

  1. Client-facingWhen a client is blocked, it gets a "too many requests" answer (429). Headers say how long to wait (Retry-After) and how much quota is left (RateLimit-Limit/Remaining/Reset).
  2. InternalOther services ask "may this request go ahead?". They send who is calling (tenant, user, endpoint) and how much it costs (POST /v1/ratelimit:check). Envoy's ratelimit service works the same way.
  3. AdminAdmins create or change a rule: which algorithm, how big, how fast it refills, and what to do if Redis is down (PUT /v1/rules/{ruleId}, failMode). Rules are saved in Postgres and cached in every gateway.

Redis for counters usual pick

  • In-memory operations take microseconds. It has atomic Lua and built-in expiry.
  • Keys are spread across servers. No need to save to disk.
  • If it is lost, users get a few extra requests for a short time.

Counters can be thrown away, so this is fine.

Postgres / DynamoDB counters

  • Data survives crashes
  • Too slow to call on every request
  • Busy rows get locked and fought over

Only for rules, never for per-request counters.

Go deeper: why Redis

Redis works in memory, so each operation takes a few microseconds. It runs Lua atomically, expires keys on its own, and splits keys across shards. The counters can be thrown away. Losing them for a minute means users get a few extra requests for a short time, which is acceptable. That is also why this cluster needs no disk persistence (AOF). It is also why a DynamoDB or Postgres counter is the wrong default. Each check would be too slow, and busy rows get fought over.

Go deeper: each box in detail
  • CDN / WAF. Applies rough per-IP limits and bot rules before traffic costs you anything. Your limiter handles limits for logged-in users and business rules.
  • Gateway filter. It reads tenant, user and plan from the JWT, which is already verified. It matches rules from an in-memory cache and builds descriptors. Then it calls Redis once with all keys for this request. In Spring Cloud Gateway this is the RequestRateLimiter filter. Its default RedisRateLimiter is a token bucket in a Lua script. You would extend it to check several rules.
  • Redis Cluster. 3 or more shards, each with replicas (copies). No disk persistence needed. Every key has an expiry. One script call per request.
  • Config service. Rules change rarely. Gateways hold the full rule set in memory and refresh it when the version number changes. Never read rules from the database while serving a request.
  • Library or service. A shared library inside the gateway saves a network hop. A central limiter service is the pattern behind Envoy's global ratelimit service. It keeps the logic in one place for teams using many languages, but adds one more hop. For a Java shop with one gateway layer, the library wins.

08Deep dives

8.1 Choosing the algorithm

Token bucket usual pick

  • Allows bursts up to the bucket size. Mobile apps often fire 10 calls on launch.
  • Only two numbers stored per key
  • Customers must understand two settings

The default for request limits.

Sliding window counter

  • Matches "100 per minute" thinking
  • Approximate

When the product team wants per-minute quotas.

Sliding window log

  • Exact
  • Uses memory for every request

Only login, OTP, password reset.

8.2 Atomic check-and-consume with Lua

TimeGateway AGateway Btokens
t1GET tokens → 11
t2GET tokens → 11
t3allow, SET 0allow, SET 02 allowed, 1 token

Redis runs a Lua script on its shard with nothing else in between. So reading, deciding and writing become one step. The script uses the Redis server's clock. That means differences between gateway clocks do not matter.

Show the Lua token bucket
-- KEYS[1] = bucket key; ARGV: capacity, refill tokens per second, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])
local t   = redis.call('TIME')
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local b      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate / 1000)

local allowed = 0
if tokens >= cost then
  tokens  = tokens - cost
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)
-- retry-after in ms when denied
local wait = 0
if allowed == 0 then wait = math.ceil((cost - tokens) * 1000 / rate) end
return { allowed, math.floor(tokens), wait }

EVALSHA

Send the script to Redis once, then call it by a short ID. This saves sending it every time. After Redis switches to a backup server, it may have forgotten the script. Then send the full script again. (Commands: SCRIPT LOAD, NOSCRIPT, EVAL.)

Hash tags

One script can only touch keys stored on the same Redis server. Putting the tenant ID in curly braces keeps that tenant's keys together ({t_481}). Global keys go in a second call, sent in the same batch.

Check all, then consume

Check every rule first, and take tokens only if all pass. Otherwise a request blocked by the tenant rule still uses up the user's token.

Go deeper: script details and Java clients

The race goes like this. Two gateway servers both read tokens=1. Both allow the request. Both write 0. Redis runs a Lua script atomically, so no other command runs on that shard in the middle. Reading, deciding and writing happen as one step. Use the Redis server time inside the script, so differences between gateway clocks do not matter.

  • Load the script once with SCRIPT LOAD and call it with EVALSHA. After a failover, if you get NOSCRIPT, fall back to EVAL.
  • To check several rules in one call, pass all the keys. In Redis Cluster every key in one script must map to the same slot. Use hash tags ({t_481}) for rules on the same tenant. Rules on other things, like a global endpoint limit, go in a second call in the same pipeline.
  • Check all rules first. Use up tokens only if all of them pass. Otherwise a request blocked by the tenant rule still uses up the user's token.
  • Sliding window counter in Lua: INCR the current bucket and GET the previous one. Compute the weighted sum. If it is over, DECR back. Or check first and increment only when allowed.

On the Java side, use Lettuce's async API with a small dedicated connection pool, or use Redisson. Set the command timeout to about 2–5 ms. Bucket4j gives you the same token bucket over Redis or Hazelcast, if you prefer not to write Lua by hand.

8.3 Fail-open vs fail-closed (the Salesforce probe)

Fail-open usual pick

  • The product stays up
  • A local bucket set to limit / nodes keeps limits roughly right
  • Abusers get a window while Redis is down

Ordinary APIs.

Fail-closed

  • No attacker gets unlimited requests
  • If the limiter is down, the feature is down

OTP, login, starting a payment, costly AI calls. Set per rule as failMode.

Protect the protector

Use a 2 ms timeout. Wrap the Redis client in a Resilience4j circuit breaker. Alert when the fallback is used often.

Go deeper: fallback behaviour

Fail-open (default)

Allow the request and record a metric. Switch to a local in-memory bucket set to limit / number_of_gateway_nodes. For ordinary APIs, keeping the product up matters more than exact quotas.

Fail-closed

Refuse with 429 or 503. Use it for OTP sends, login attempts, starting payments and costly AI calls. An attacker with no limit there costs money or security. Set per rule as failMode.

Protecting the protector

Use a short 2 ms timeout. Add a Resilience4j circuit breaker so a sick cluster is not hammered. Alert on the fallback rate. Limiter delay must never become API delay.

The local fallback is what makes fail-open safe. Limits drop to "roughly right per server" instead of "no limits at all". The server count comes from service discovery. It is fine if that count is slightly out of date.

8.4 Multi-region quotas

Say a tenant's quota is 10,000 per minute worldwide. Its traffic arrives in both Mumbai and Singapore.

Regional split usual pick

  • No calls between regions
  • Slightly less accurate

Each region enforces limit × its share (50/50, or by last hour's traffic).

Home-region routing

  • Exact, because one Redis owns the counters
  • Slower for traffic that arrives in another region

Strict global limits.

Local + async sync

  • Scales to huge global quotas
  • Can go over the limit by about the sharing gap × the request rate

Each region counts locally and shares how much it added every 100–500 ms (G-counter deltas).

Never

Never call Redis in another region while serving a request. A round trip takes 50–100 ms. If the link between regions breaks, you have an outage. Rate limiting should be AP: stay available, accept slightly loose counts.

Go deeper: multi-region options
  • Regional split. Each region enforces limit × share. The share is a fixed 50/50, or based on last hour's traffic. No calls between regions, and only a small loss of accuracy. The best default.
  • Home-region routing. Send each tenant to a home region using GeoDNS or gateway forwarding. Then one Redis owns its counters. This is exact, but traffic arriving elsewhere gets slower.
  • Count locally, sync in the background. Each region counts locally and sends its changes every 100–500 ms. This uses CRDT-style G-counters, one per region, and the global count is their sum. Overshoot is at most the sync interval × rate. Good for very large global quotas.
  • Never make a synchronous call to Redis in another region while serving a request. The 50–100 ms round trip ruins the latency budget. And if the link between regions breaks, it becomes an outage.

This is a CAP choice, and you should name it. Rate limiting is AP. When regions cannot talk, you keep serving with slightly loose limits. You do not refuse traffic.

8.5 Hot keys and token leasing

50k RPSone big tenant, one key, one shard
batch 50tokens leased per call, or 100 ms
50xless Redis traffic for that key

Token leasing usual pick

  • Each server takes a small batch of tokens from Redis and hands them out from its own memory
  • Can be off by up to batch × servers tokens

Choose the batch size based on the limit.

Sub-keys

  • Simple
  • Uneven if random picks bunch up

Split into N keys with limit/N each, and pick one at random.

Go deeper: leasing

A large tenant sending 50k requests per second on one key sends all of it to one Redis shard. The fix is leasing. Each gateway takes a batch of tokens, say 50, in one script call. It then serves from local memory until the batch runs out or 100 ms passes. Redis traffic for that key drops 50 times. The cost is that counts can be off by up to batch × nodes tokens. You choose the batch size with the limit in mind. Another option is to split the key into N sub-keys with limit/N each and pick one at random.

09Scaling, failure handling and consistency

First to break at 10x

One overloaded shard breaks first, not memory. Leasing and sub-keys fix it. Adding shards does not.

Redis failover

Copies update in the background, so a promoted replica is a few hundred ms behind. Users get a few extra requests briefly. That is acceptable.

Retries amplify load

Clients wait the Retry-After time plus a random delay (jitter). Internal callers get a fixed retry budget.

Shadow rollout

New rules first only log "would deny", without blocking. Stripe rolled out limits this way.

Observability

Track allow and deny per rule and tenant, Redis p99, and fallback rate. Alert when a rule blocks X% of a tenant.

Load shedding

A separate layer that drops low-priority traffic when the whole fleet is unhealthy.

Go deeper: the full failure list
  • What breaks first at 10x. A single overloaded shard breaks first, not total memory. It holds a big tenant or a global endpoint key. Leasing and sub-keys fix it. Adding shards does not.
  • Redis failover. Copies are updated in the background. So a promoted replica may have counters a few hundred ms old. Users get a few extra requests briefly. That is acceptable, and you should say so.
  • Lost script cache. After a failover, EVALSHA returns NOSCRIPT. The client then re-sends the script with EVAL. Lettuce and Redisson handle this if you use their script helpers.
  • Clock skew. Clock skew means server clocks disagree slightly. With redis.call('TIME') inside the script, only the shard's clock matters. If gateways compute the time, their differences make buckets refill wrongly.
  • Retries amplify load. Clients that get a 429 must wait, using Retry-After plus a random delay (jitter). Internal callers should have a retry budget, not unlimited retries.
  • Rule rollout. Ship new rules in shadow mode first. They run and log "would deny" but do not block. Stripe described rolling out limiters this way, so existing users' workflows did not break.
  • Observability. Track allow and deny counts per rule and tenant, Redis p99 latency, fallback rate and the most-blocked keys. Alert when a rule blocks more than X% of a tenant's traffic. That means an attack or a broken client.
  • Load shedding is different. Stripe keeps per-user rate limits separate from fleet-level load shedders. Those drop low-priority traffic, like analytics and webhook retries, when the system is unhealthy. Mention it as the next layer.

10Trade-offs

Centralised Redis + Lua usual pick

  • Accurate, one round trip
  • Redis sits on every request's path. Hot keys hurt.

The default for most fleets.

Local in-memory per node

  • No network cost
  • Drifts as server count changes or load is uneven

As a fallback, or to protect the server itself.

Sticky sessions

  • No shared state
  • Moving users between servers breaks limits

Rarely. Mention it only to reject it.

11Mistakes that got candidates rejected

Rejected for this
  • Explaining the algorithms well but never making the Redis check atomic. "Read the count, then increment" is a race.
  • Keeping counters in Postgres, or calling the database on every request.
  • No answer to "Redis is down". The design quietly becomes one point that can take the whole API down.
  • Using a sliding log for everything without noticing it costs memory for every request.
  • Calling counters in another region synchronously, or claiming exact global limits with no delay cost.
  • Taking the tenant or user ID from a request parameter instead of the verified login token.
  • Forgetting the client side. No 429 meaning, no Retry-After, no advice on waiting before retrying.

13Quick check

Two gateways both read tokens=1, and both allow the request. What is the standard fix?

Redis runs the Lua script as one uninterrupted step on the shard. A Java lock only protects one JVM, not the whole fleet of servers.

Redis is down. What should the endpoint that sends OTPs do?

An attacker with unlimited OTP sends costs you money and security. So OTP fails closed. Ordinary APIs fail open to a local bucket.

Why call redis.call('TIME') inside the script?

If each gateway sends its own time, their clocks disagree slightly. Then buckets refill by the wrong amount.

One tenant sends 50k requests per second to a single key. What helps most?

One key always lives on one shard, so more shards do not help. Leasing 50 tokens per call cuts that key's traffic 50 times.

14Interview questions

Why not GET the counter, check it in Java, then INCR?

Two servers can read the same value between the GET and the INCR, and both allow. One fix is a single atomic command. Call INCR, compare the returned value, and decrement if over. The other fix is a Lua script that reads, decides and writes. WATCH/MULTI optimistic transactions also work. But they retry when keys are busy, which is exactly when you are being hammered.

Redis is down. What happens to traffic?

It depends on the rule. Fail-open rules fall back to a local bucket at limit / N nodes and raise an alert. Fail-closed rules, like OTP and login, return 503. A circuit breaker stops us waiting 2 ms on every request for a dead cluster. The limiter must never be the reason the API is down.

How do you make it work across two regions?

Split the quota per region by share of traffic, and enforce it locally. For large global quotas, you can also sync counts in the background every few hundred ms. Make no synchronous calls between regions. It is an AP system. When regions cannot talk, we accept a small, bounded overshoot.

Fixed window lets 2x through at the boundary. How much does that matter?

With a 100/min limit, a client can send 100 at 0:59 and 100 more at 1:00. For daily quotas nobody cares. For per-second abuse protection it matters. The sliding window counter fixes most of it with two integers. Token bucket limits bursts to the bucket size directly.

How do you rate limit by tenant when the tenant ID is in the request body?

You do not. The tenant comes from the verified JWT claim, checked at the gateway. A client can fake anything it sends. It could spend another tenant's quota or dodge its own. Endpoints without login are limited by IP plus a device fingerprint.

Different costs per endpoint, like an expensive report export?

Token bucket handles this naturally. Pass a cost to the script, such as 50 tokens for an export and 1 for a GET. For LLM (large language model) APIs, the cost is the tokens used, known only after the call. So reserve an estimate first, then adjust with a second call.

Kotak rapid-fire: what is idempotency, and how does it relate?

An operation is idempotent if doing it twice has the same effect as doing it once. Clients that retry after a 429 or a timeout must send an Idempotency-Key on POSTs. Then the retry does not create a second payment. The limiter itself is not idempotent, because a repeated check uses quota again. That is fine for limits, but wrong for billing.

Kotak rapid-fire: where does the limiter sit in CAP?

AP, which means it stays available. When the network splits, we keep answering with possibly old counts rather than refusing traffic. A payment ledger is the opposite. It is CP and refuses rather than spend the same money twice.

How do you change a limit for one enterprise tenant without a deploy?

Add an override row in Postgres. The config service bumps the snapshot version, and gateways pull it within seconds. Existing Redis buckets use the new size on their next call. That works because capacity is a script argument, not stored state.

How would you test it?

Unit-test the script against an embedded or Testcontainers Redis, with a clock you control. Run a concurrency test with 200 parallel callers and assert exactly N are allowed. Run a chaos test that kills the Redis primary, and assert the fallback works with no API errors. Use shadow mode in production before enforcing.

15Cheat sheet

Cheat sheet
  • Gateway filter → Redis Cluster. Rules live in Postgres and a config service pushes them.
  • Token bucket by default. Sliding counter for "per minute". Sliding log for OTP and login.
  • One Lua script per request. Use Redis server time. Use hash tags to keep keys in one slot.
  • Check all rules, then consume.
  • Fail open to a local bucket (limit / N). Fail closed for OTP, login and payments.
  • 2 ms timeout plus a circuit breaker. Limiter delay must never become API delay.
  • Multi-region: split the quota per region. It is AP. No synchronous calls between regions.
  • Hot key: lease token batches. More shards do not help.
  • Client contract: 429, Retry-After, and retry after a random wait (jitter).
