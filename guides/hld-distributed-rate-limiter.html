Distributed rate limiter

Design a rate limiter that enforces per-user, per-tenant and per-API limits across hundreds of gateway nodes. A senior answer picks an algorithm for a reason, makes the check atomic in Redis with Lua, keeps it under a millisecond or two, and says exactly what happens when Redis or a region goes away.

01What the interviewer is grading

The reports show two flavours. Amazon asked it from first principles: fixed window, sliding window, token bucket, then "make it work across servers with Redis". Salesforce went in depth on the distributed part: Redis Lua scripts, fail-open versus fail-closed, and multi-region. Agoda framed it as "API rate limiter" inside a wider microservices discussion. Across all of them the interviewer is checking:

  • Algorithm judgement. You can explain four algorithms in two sentences each and choose one with a reason (burst tolerance, memory, accuracy), not because it is "the standard".
  • Atomicity. You know that GET then INCR from the application is a race, and that a Lua script (or a single atomic command) fixes it.
  • Latency budget. The limiter sits on every request. You keep the check to one network round trip, ideally under 1–2 ms at p99, and you have a plan for hot keys.
  • Failure behaviour. A limiter that takes the whole API down when Redis blips is worse than no limiter. You state fail-open or fail-closed per endpoint and justify it.
  • Distributed reality. Clock skew, Redis Cluster slots, replication lag, multi-region quotas. Staff-level interviewers push here.
  • Client contract. HTTP 429, Retry-After, remaining-quota headers, and how clients should back off.

02Clarify and scope

Questions to ask

  • Where does it run? Inside the API gateway (Spring Cloud Gateway, Envoy, Kong), as a sidecar, or as a library inside each service? Changes the deployment, not the core algorithm.
  • Limit by what? User ID, API key, tenant, IP, endpoint, or combinations. Tenant identity comes from the verified JWT, never a header the client sets.
  • How strict? Is 2% overshoot acceptable for a public API? For OTP sends or payment initiation it usually is not.
  • Burst behaviour? Should a client be allowed to burst 50 requests and then average 10/s? That decides token bucket versus window.
  • Scale. Peak RPS, number of distinct keys, number of regions.
  • Rule changes. Must limits change without a deploy? Per-tenant plans (free, pro, enterprise)?
  • Throttle or shape? Reject with 429, or queue and delay? Almost always reject at the edge; shaping belongs to queues.

Functional

  • Check and consume quota per request for a composite key.
  • Multiple rules per request (per-user 100/min AND per-tenant 10k/min AND global endpoint 50k/s).
  • Configurable rules per tenant plan, changed at runtime.
  • Return 429 with retry hints; expose remaining quota.

Non-functional

  • Peak 1M RPS across the fleet, 10M active keys.
  • Added latency p99 < 2 ms; limiter outage must not cause an API outage.
  • Accuracy within ~1–5% for general APIs; exact for sensitive endpoints.
  • 99.99% availability of the decision path; multi-region.

Out of scope

  • DDoS mitigation at L3/L4 (that is the CDN/WAF's job).
  • Billing and metering (related but needs exactly-once counts).
  • Request queuing and traffic shaping.

The punchline to say out loud: the sliding log is the most accurate but costs ~25x the memory, so it is reserved for low-volume, high-value limits (login attempts, OTP). Everything else uses token bucket or sliding window counter. Batching or leasing tokens is how you cut Redis load by an order of magnitude when one cluster is not enough.

04API design

Two surfaces: the client-facing contract and the internal decision API (if the limiter is a service rather than a library).

// Client-facing: any API, when throttled
HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 12
{ "error": "rate_limited", "rule": "user_per_minute" }

// Internal decision API (gRPC, like Envoy's ratelimit service)
POST /v1/ratelimit:check
{
  "domain": "payments-api",
  "descriptors": [
    { "tenant": "t_481", "user": "u_99" },
    { "tenant": "t_481" },
    { "endpoint": "POST /payments" }
  ],
  "cost": 1
}
-> { "decision": "OVER_LIMIT", "retryAfterMs": 12000,
     "statuses": [ { "limit": 100, "remaining": 0, "resetMs": 12000 }, ... ] }

// Admin: rules (stored in Postgres, cached in every gateway)
PUT /v1/rules/{ruleId}
{ "match": { "plan": "free", "endpoint": "POST /payments" },
  "algorithm": "TOKEN_BUCKET", "capacity": 20, "refillPerSec": 5,
  "failMode": "CLOSED" }

The check is not idempotent by nature, it consumes quota. If a gateway retries a timed-out check you may double-charge a token; that is acceptable for rate limiting, not for billing. Say so.

Why Redis: single-digit-microsecond in-memory ops, atomic Lua, native TTL, cluster sharding by key. Counters are disposable: losing them for a minute means a brief over-allowance, which is acceptable. That is also why you do not need Redis persistence (AOF) for this cluster, and why a DynamoDB or Postgres counter is the wrong default (too slow per check, and contention on hot rows).

06High-level architecture

Client→ CDN / WAFIP-level, L7 DDoS→ Load balancer→ API gatewayrate-limit filter→ Backend services
Rate-limit filterlocal rule cache + local fallback bucket→EVALSHA, 2 ms timeout Redis Clustercounters, sharded by key
Admin UI / API→ Postgresrules→ Config serviceversioned snapshot→push / long-poll Every gateway node

Figure: decision path (top two rows) and rule distribution path (bottom). Metrics on allow/deny flow to Prometheus; denials sampled to Kafka for abuse analytics.

  • CDN / WAF. Coarse per-IP limits and bot rules before traffic costs you anything. Your limiter is for authenticated, business-aware limits.
  • Gateway filter. Extracts identity from the already-validated JWT (tenant, user, plan), matches rules from an in-memory cache, builds descriptors, calls Redis once with all keys for this request. In Spring Cloud Gateway this is the RequestRateLimiter filter, whose default RedisRateLimiter is a token bucket in a Lua script; you would extend it for multi-rule checks.
  • Redis Cluster. 3+ shards with replicas, no persistence needed, keys TTL'd. One script call per request.
  • Config service. Rules change rarely; gateways hold the full rule set in memory and refresh by version number. Never read rules from the DB on the request path.
  • Library vs service. A shared library in the gateway saves a hop. A central limiter service (Envoy's global ratelimit service pattern) centralises logic for polyglot fleets at the cost of one more hop. For a Java shop with one gateway layer, the library wins.

07Deep dives

7.1 Choosing the algorithm

AlgorithmHow it worksWeaknessUse it for
Fixed window counterINCR key:minute, reject above NBoundary burst: 2N requests in 2 seconds across a minute edgeCheap coarse quotas (daily API caps)
Sliding window logSorted set of timestamps; drop older than window, countMemory and CPU proportional to trafficExact, low-volume: login, OTP, password reset
Sliding window countercount = curr + prev × (1 − elapsed/window)Approximate (assumes even spread in previous window)General per-minute API limits. Cloudflare reported it accurate enough at their scale with two integers per key
Token bucketCapacity C, refill R/s; each request takes a tokenTwo parameters to explain to customersAPIs that should allow bursts: Stripe and Spring Cloud Gateway use it
Leaky bucketQueue drained at constant rateAdds latency; queue stateShaping outbound calls to a fragile downstream (SMS vendor)

Default answer: token bucket for request limits (bursty clients are normal; mobile apps fire 10 calls on launch), sliding window counter where product wants "100 per minute" semantics, sliding log only for security-sensitive low-volume limits.

7.2 Atomic check-and-consume with Lua

The race: two gateway nodes both read tokens=1, both allow, both write 0. Redis runs a Lua script atomically (no other command interleaves on that shard), so read-compute-write happens as one step. Use Redis server time inside the script so gateway clock skew does not matter.

-- KEYS[1] = bucket key; ARGV: capacity, refill tokens per second, cost
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])
local t   = redis.call('TIME')
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local b      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or capacity
local ts     = tonumber(b[2]) or now
tokens = math.min(capacity, tokens + (now - ts) * rate / 1000)

local allowed = 0
if tokens >= cost then
  tokens  = tokens - cost
  allowed = 1
end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(capacity / rate * 1000) + 1000)
-- retry-after in ms when denied
local wait = 0
if allowed == 0 then wait = math.ceil((cost - tokens) * 1000 / rate) end
return { allowed, math.floor(tokens), wait }
  • Load once with SCRIPT LOAD, call with EVALSHA; fall back to EVAL on NOSCRIPT after a failover.
  • Multiple rules in one call: pass all keys, but in Redis Cluster every key in one script must hash to the same slot. Use hash tags ({t_481}) for rules on the same tenant; rules on different entities (global endpoint limit) go in a second pipelined call.
  • Check all rules first, consume only if all pass. Otherwise a request denied by the tenant rule still burns the user's token.
  • Sliding window counter in Lua: INCR the current bucket, GET the previous, compute the weighted sum, DECR back if over. Or check first and increment only on allow.

Java side: Lettuce's async API with a small dedicated connection pool, or Redisson; set command timeout around 2–5 ms. Bucket4j offers the same token bucket over Redis/Hazelcast if you would rather not hand-write Lua.

7.3 Fail-open vs fail-closed (the Salesforce probe)

When Redis is slow or down, every request hits a decision you must have made in advance:

Fail-open (default)

Allow the request, emit a metric, switch to a local in-memory bucket sized limit / number_of_gateway_nodes. Availability of the product beats exact quota enforcement for ordinary APIs.

Fail-closed

Deny (429 or 503). For OTP sends, login attempts, payment initiation, expensive AI inference: an unlimited attacker costs money or security. Configured per rule as failMode.

Protecting the protector

Short timeout (2 ms), circuit breaker (Resilience4j) around the Redis client so a sick cluster is not hammered, and alerting on fallback rate. Never let limiter latency become API latency.

The local fallback limiter is what makes fail-open safe: you degrade to "approximately right per node" rather than "no limits at all". Node count comes from service discovery; it is fine if it is a little stale.

7.4 Multi-region quotas

A tenant has 10,000 requests per minute globally and traffic lands in Mumbai and Singapore. Options:

  • Regional split. Each region enforces limit × share (static 50/50 or based on last hour's traffic). No cross-region calls, small accuracy loss. Best default.
  • Home-region routing. Route each tenant to a home region (GeoDNS or gateway forwarding) so one Redis owns its counters. Exact, but adds latency for traffic arriving elsewhere.
  • Local enforce, async sync. Each region counts locally and broadcasts deltas every 100–500 ms (CRDT-style G-counters per region; global count = sum). Overshoot bounded by sync interval × rate. Good for very large global quotas.
  • Never a synchronous cross-region Redis call on the request path: 50–100 ms RTT destroys the latency budget, and a WAN partition then becomes an outage.

This is a CAP choice and you should name it: rate limiting is AP. During a partition you keep serving with slightly loose limits rather than refusing traffic.

7.5 Hot keys and token leasing

A large tenant at 50k RPS on one key sends all of that to one Redis shard. Fix: each gateway leases a batch of tokens (say 50) with one script call, then serves from local memory until the batch is used or 100 ms passes. Redis traffic for that key drops 50x; the cost is up to batch × nodes tokens of imprecision, which you size against the limit. Alternatively split the key into N sub-keys with limit/N each and pick one at random.

08Scaling, failure handling and consistency

  • What breaks first at 10x. A single hot shard (big tenant or a global endpoint key), not total memory. Leasing and sub-keys fix it; adding shards does not.
  • Redis failover. Replication is async, so a promoted replica may have counters a few hundred ms stale: brief over-allowance. Acceptable; say it.
  • Script cache loss. After failover, EVALSHA returns NOSCRIPT; the client re-sends with EVAL. Lettuce and Redisson handle it if you use their script helpers.
  • Clock skew. Using redis.call('TIME') inside the script means only the shard's clock matters. If you compute time on gateways, skew between nodes makes buckets refill wrongly.
  • Retries amplify load. Clients receiving 429 must back off with jitter using Retry-After. Internal callers should use a retry budget, not unlimited retries.
  • Rule rollout. Ship new rules in shadow mode first: evaluate and log "would deny" without denying. Stripe described rolling out limiters this way so existing users' workflows are not broken.
  • Observability. Allow/deny counts per rule and tenant, Redis latency p99, fallback rate, top denied keys. Alert when a rule denies more than X% of a tenant's traffic: that is either an attack or a broken client.
  • Load shedding is different. Stripe separates per-user rate limits from fleet-level load shedders that drop low-priority traffic (analytics, webhooks retries) when the system is unhealthy. Mention it as the next layer.

10Follow-up questions interviewers asked

Why not GET the counter, check it in Java, then INCR?

Two nodes can read the same value between the GET and the INCR and both allow. Either make the operation a single atomic command (INCR then compare the returned value, decrementing if over) or put read-compute-write in a Lua script. WATCH/MULTI optimistic transactions work but retry under contention, which is exactly when you are being hammered.

Redis is down. What happens to traffic?

Per rule: fail-open rules fall back to a local bucket at limit / N nodes and raise an alert; fail-closed rules (OTP, login) return 503. A circuit breaker stops us waiting 2 ms on every request against a dead cluster. The limiter must never be the reason the API is down.

How do you make it work across two regions?

Split the quota per region by traffic share and enforce locally; optionally sync counts asynchronously every few hundred ms for large global quotas. No synchronous cross-region calls. It is an AP system: during a partition we accept bounded overshoot.

Fixed window lets 2x through at the boundary. How much does that matter?

For a 100/min limit a client can send 100 at 0:59 and 100 at 1:00. For daily quotas nobody cares; for per-second abuse protection it matters. Sliding window counter fixes most of it with two integers; token bucket bounds bursts to capacity explicitly.

How do you rate limit by tenant when the tenant ID is in the request body?

You do not. Tenant comes from the authenticated JWT claim, validated at the gateway. Anything the client sets can be spoofed to spend another tenant's quota or dodge yours. Unauthenticated endpoints are limited by IP plus device fingerprint.

Different costs per endpoint, like an expensive report export?

Token bucket handles it naturally: pass cost to the script (export = 50 tokens, GET = 1). For LLM APIs the cost is tokens consumed, known only after the call: reserve an estimate, then adjust with a second call.

Kotak rapid-fire: what is idempotency, and how does it relate?

An operation is idempotent if repeating it has the same effect as doing it once. Clients retrying after a 429 or timeout must send an Idempotency-Key on POSTs so the retry does not create a second payment. The limiter itself is not idempotent (a retried check consumes again), which is fine for limits and wrong for billing.

Kotak rapid-fire: where does the limiter sit in CAP?

AP. Under partition we prefer to keep answering with possibly stale counts over refusing traffic. A payment ledger is the opposite: CP, refuse rather than double-spend.

How do you change a limit for one enterprise tenant without a deploy?

Override row in Postgres, config service bumps the snapshot version, gateways pull within seconds. Existing Redis buckets pick up the new capacity on their next call because capacity is a script argument, not stored state.

How would you test it?

Unit-test the script with an embedded or Testcontainers Redis and a controllable time source; concurrency test with 200 parallel callers asserting exactly N allowed; chaos test by killing the Redis primary and asserting fallback and no API errors; shadow mode in production before enforcing.

11Mistakes that got candidates rejected

Rejected for this
  • Describing algorithms well but never making the Redis check atomic: "read the count, then increment".
  • Storing counters in Postgres or calling the DB on every request.
  • No answer to "Redis is down": the design silently becomes a single point of failure for the whole API.
  • Using a sliding log for everything without noticing it costs memory per request.
  • Synchronous cross-region counter calls, or claiming exact global limits with no latency cost.
  • Taking the tenant or user ID from a request parameter instead of the authenticated token.
  • Forgetting the client side: no 429 semantics, no Retry-After, no backoff guidance.
