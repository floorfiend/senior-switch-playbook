01Why interviewers ask this

Collections are the cheapest way for an interviewer to find out whether five years of Java means five years of understanding or one year repeated five times. Every service you own uses HashMap and ConcurrentHashMap; a senior engineer is expected to explain what happens on put, why a key went missing, and why a counter under load is wrong.

  • JPMC asked candidates to write an immutable class that holds a mutable Address, then asked for the HashMap size after inserting duplicate Person objects with and without equals/hashCode overridden.
  • Walmart, Intuit, LinkedIn and Apple asked HashMap internals (buckets, collisions, treeification, resize) and ConcurrentHashMap versus synchronizedMap, usually as a warm-up before an LLD or coding round.
  • The design problems here (LRU, LFU, O(1) randomised set, your own hash map) appear in coding rounds at the same companies because they test whether you can compose two structures to get O(1) everything.
What a senior answer sounds like

Not "HashMap uses hashing". Instead: "a power-of-two array of bins; the hash is XOR-ed with its upper 16 bits and masked with n - 1; a bin is a linked list that becomes a red-black tree at 8 nodes if the table has at least 64 bins; the table doubles past 0.75 load and each bin splits into a low and high list without rehashing". Then connect it to a production consequence.

The equals/hashCode contract

A hash map finds a key in two steps: hashCode() picks the bucket, then equals() picks the entry inside the bucket. The contract in Object's Javadoc follows from that:

  • If a.equals(b) then a.hashCode() == b.hashCode(). Break this and equal keys land in different buckets, so the map stores both.
  • Equal hash codes do not imply equality (collisions are allowed: "Aa" and "BB" both hash to 2112).
  • hashCode() must be stable while the object is in a hash-based collection. Mutating a field used by it orphans the entry.
  • equals must be reflexive, symmetric, transitive and consistent, and x.equals(null) is false. Using instanceof in a non-final class with subclasses that add fields breaks symmetry; make value classes final or use records.

The JPMC question: HashMap size with duplicate Person objects

Insert Person("Asha", 30) twice and Person("Ravi", 28) once. The answer depends on what Person overrides:

import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

class PersonSizeDemo {
    static class PlainPerson {                    // no equals/hashCode: identity semantics
        final String name;
        final int age;
        PlainPerson(String name, int age) { this.name = name; this.age = age; }
    }

    static class EqOnlyPerson extends PlainPerson { // equals without hashCode: contract broken
        EqOnlyPerson(String name, int age) { super(name, age); }
        @Override public boolean equals(Object o) {
            return o instanceof EqOnlyPerson p && p.age == age && p.name.equals(name);
        }
    }

    static final class Person {                   // both overridden, consistently
        final String name;
        final int age;
        Person(String name, int age) { this.name = name; this.age = age; }
        @Override public boolean equals(Object o) {
            return o instanceof Person p && p.age == age && p.name.equals(name);
        }
        @Override public int hashCode() { return Objects.hash(name, age); }
    }

    record PersonRecord(String name, int age) { } // records generate both for you

    public static void main(String[] args) {
        Map<Object, String> plain = new HashMap<>();
        plain.put(new PlainPerson("Asha", 30), "a");
        plain.put(new PlainPerson("Asha", 30), "b");
        plain.put(new PlainPerson("Ravi", 28), "c");

        Map<Object, String> eqOnly = new HashMap<>();
        eqOnly.put(new EqOnlyPerson("Asha", 30), "a");
        eqOnly.put(new EqOnlyPerson("Asha", 30), "b");
        eqOnly.put(new EqOnlyPerson("Ravi", 28), "c");

        Map<Object, String> proper = new HashMap<>();
        proper.put(new Person("Asha", 30), "a");
        proper.put(new Person("Asha", 30), "b");      // replaces value "a"
        proper.put(new Person("Ravi", 28), "c");

        Map<Object, String> rec = new HashMap<>();
        rec.put(new PersonRecord("Asha", 30), "a");
        rec.put(new PersonRecord("Asha", 30), "b");
        rec.put(new PersonRecord("Ravi", 28), "c");

        System.out.println(plain.size());   // 3
        System.out.println(eqOnly.size());  // 3 (almost always: identity hashes land in different buckets)
        System.out.println(proper.size());  // 2, and get(new Person("Asha", 30)) returns "b"
        System.out.println(rec.size());     // 2
    }
}

Immutability and defensive copies

The JPMC follow-up: make Employee immutable when it holds an Address you cannot change. final fields are not enough, because final stops reassignment, not mutation of the object the field points to. The recipe:

  1. Class is final (or constructor private with a factory) so a subclass cannot add mutable state or override accessors.
  2. All fields private final, no setters.
  3. Copy mutable inputs in the constructor (copy in), and copy mutable outputs in getters (copy out).
  4. For collections, List.copyOf/Map.copyOf produce truly unmodifiable copies. Collections.unmodifiableList(list) is only a read-only view: the caller still holding list can change what you see.
  5. "Mutators" return a new instance (withCity).
import java.util.List;

final class Address {                         // mutable class we do not own
    private String city;
    private String pin;

    Address(String city, String pin) { this.city = city; this.pin = pin; }

    String getCity() { return city; }
    String getPin() { return pin; }
    void setCity(String city) { this.city = city; }
}

final class Employee {                        // final: no subclass can add mutable state
    private final String name;
    private final Address address;
    private final List<String> skills;

    Employee(String name, Address address, List<String> skills) {
        this.name = name;
        this.address = new Address(address.getCity(), address.getPin()); // copy in
        this.skills = List.copyOf(skills);                               // unmodifiable copy (rejects nulls)
    }

    String getName() { return name; }
    Address getAddress() { return new Address(address.getCity(), address.getPin()); } // copy out
    List<String> getSkills() { return skills; }                                       // already unmodifiable

    Employee withCity(String city) {          // "mutation" returns a new object
        return new Employee(name, new Address(city, address.getPin()), skills);
    }
}

class ImmutableDemo {
    public static void main(String[] args) {
        Address addr = new Address("Pune", "411001");
        java.util.ArrayList<String> skills = new java.util.ArrayList<>(List.of("Java"));
        Employee e = new Employee("Asha", addr, skills);

        addr.setCity("Delhi");                  // caller mutates its own reference
        skills.add("Go");
        e.getAddress().setCity("Mumbai");       // caller mutates the returned copy
        System.out.println(e.getAddress().getCity() + " " + e.getSkills()); // Pune [Java]
        try {
            e.getSkills().add("Rust");
        } catch (UnsupportedOperationException ex) {
            System.out.println("skills are unmodifiable");
        }
        System.out.println(e.withCity("Noida").getAddress().getCity() + " " + e.getAddress().getCity()); // Noida Pune
    }
}

Output: Pune [Java], then skills are unmodifiable, then Noida Pune. The bonus answer: immutable objects are thread-safe without locks, and the JMM guarantees that final fields are visible to every thread once the constructor finishes, as long as this does not escape during construction.

03How it works internally

HashMap: the bucket array

key.hashCode()→ spreadh ^ (h >>> 16)→ index(n - 1) & hash→ table[index]null | Node list | TreeNode→ equals() walkhash compare first

Figure: lookup path in java.util.HashMap (JDK 8 onwards).

  • Table: a Node<K,V>[] created lazily on the first put. Default capacity 16, always a power of two (tableSizeFor rounds up the capacity you pass).
  • Hash spreading: static final int hash(Object key) { int h; return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16); }. The index uses only the low bits (hash & (n - 1)), so without spreading, hash codes that differ only in high bits (common with Float keys or small tables) would all collide. A null key always goes to bucket 0.
  • Node: final int hash; final K key; V value; Node next. Caching the hash lets the bucket walk compare ints before calling equals, and lets resize avoid recomputing hashCode().
  • Load factor and resize: threshold = capacity × 0.75 (12 for 16). When ++size > threshold the table doubles. Because capacity is a power of two, each entry either stays at index i or moves to i + oldCap, decided by one bit: (hash & oldCap) == 0. Each bucket splits into a "lo" and "hi" list, preserving order, with no rehash.
  • Treeify: when a bin reaches TREEIFY_THRESHOLD = 8 nodes it becomes a red-black tree of TreeNodes, but only if the table has at least MIN_TREEIFY_CAPACITY = 64 bins; below that the map resizes instead, because a small table is the more likely cause. A tree bin shrinks back to a list at UNTREEIFY_THRESHOLD = 6 (during resize split or removal). The gap between 8 and 6 is hysteresis, so a bin hovering at 7 does not flip back and forth. Tree bins order by hash, then by compareTo if keys are Comparable, then by a tie-break on class name and identity hash.
  • Why 8: with a good hash and 0.75 load, bin sizes follow a Poisson distribution with mean about 0.5; the source comment gives the probability of a bin reaching 8 as about 6 in 100 million. Trees only matter when hashing is bad or adversarial (HashDoS), where they cap the worst case at O(log n) instead of O(n).

ConcurrentHashMap (Java 8+)

  • Reads take no lock. The table and Node.val/next are volatile, and bins are read with Unsafe/VarHandle volatile reads, so get sees the latest completed write.
  • Insert into an empty bin: a single CAS of the new node into table[i]. No lock at all.
  • Insert into a non-empty bin: synchronized (firstNodeOfBin). Contention is per bin, so thousands of threads can write to different bins in parallel. The old "concurrency level" constructor argument is only a sizing hint now.
  • Resize is cooperative: a thread that hits a bin marked with a ForwardingNode helps move bins (in strides) instead of waiting. Reads during resize follow the forwarding node to the new table.
  • Size: a baseCount updated by CAS, plus a CounterCell[] array that threads spread across under contention (the same striping idea as LongAdder). size() sums them, so it is an estimate under concurrent modification. Prefer mappingCount() (returns long).
  • No null keys or values: with nulls, get(k) == null would be ambiguous (absent or mapped to null), and unlike HashMap you cannot follow up with containsKey because another thread may change the map in between.
  • Atomic compound operations: putIfAbsent, computeIfAbsent, compute, merge run atomically per key while holding the bin lock. get followed by put is two operations and loses updates under contention.
  • Iterators are weakly consistent: they never throw ConcurrentModificationException and may or may not reflect concurrent updates.
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

class CounterRace {
    public static void main(String[] args) throws InterruptedException {
        ConcurrentHashMap<String, Integer> racy = new ConcurrentHashMap<>();
        ConcurrentHashMap<String, Integer> atomic = new ConcurrentHashMap<>();
        ExecutorService pool = Executors.newFixedThreadPool(8);
        for (int t = 0; t < 8; t++) {
            pool.submit(() -> {
                for (int i = 0; i < 100_000; i++) {
                    Integer old = racy.get("hits");                   // check ...
                    racy.put("hits", old == null ? 1 : old + 1);      // ... then act: lost updates
                    atomic.merge("hits", 1, Integer::sum);            // one atomic read-modify-write per key
                }
            });
        }
        pool.shutdown();
        pool.awaitTermination(1, TimeUnit.MINUTES);
        System.out.println("racy   = " + racy.get("hits"));   // less than 800000, varies per run
        System.out.println("atomic = " + atomic.get("hits")); // always 800000
        if (atomic.get("hits") != 800_000) throw new AssertionError();
    }
}

One run printed racy = 622051 and atomic = 800000. ConcurrentHashMap makes each call thread-safe, not your sequence of calls.

LinkedHashMap and access order

LinkedHashMap extends HashMap and threads a doubly linked list through every entry (before/after pointers). With the constructor flag accessOrder = true, every get/put of an existing key moves that entry to the tail. After each insert it calls removeEldestEntry(eldest); return true and the head is removed. That is a complete LRU cache in ten lines:

import java.util.LinkedHashMap;
import java.util.Map;

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(16, 0.75f, true);               // accessOrder = true: get() moves the entry to the tail
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;              // called after every put; evicts the head (least recently used)
    }
}

class LruDemo {
    public static void main(String[] args) {
        LruCache<String, Integer> c = new LruCache<>(2);
        c.put("a", 1);
        c.put("b", 2);
        c.get("a");                            // order now b, a
        c.put("c", 3);                         // evicts b
        System.out.println(c.keySet());        // [a, c]
        if (!c.keySet().toString().equals("[a, c]")) throw new AssertionError();
    }
}

It is not thread-safe, and in access order even get is a structural modification. Wrapping it in Collections.synchronizedMap works for low traffic; in production use Caffeine (W-TinyLFU, concurrent, size and time bounds).

TreeMap

A red-black tree: a binary search tree with colouring rules that keep the height at most 2·log2(n+1), so get, put, remove are O(log n) with at most two rotations per insert and three per delete. Its value is the NavigableMap API: floorKey, ceilingEntry, headMap, tailMap, subMap, firstEntry, pollFirstEntry. Typical uses: rate tables keyed by effective date (floorEntry(today)), consistent-hashing rings (ceilingEntry(hash), wrap to firstEntry), interval booking checks. TreeMap uses compareTo, never equals: if compareTo returns 0 for two keys that are not equal, the map treats them as the same key. Keep comparators consistent with equals.

PriorityQueue

A binary min-heap stored in an Object[]: the children of index i are 2i + 1 and 2i + 2, the parent is (i - 1) / 2. offer appends and sifts up (O(log n)), poll moves the last element to the root and sifts down (O(log n)), peek is O(1). Gotchas interviewers probe:

  • remove(Object) and contains are O(n) linear scans. For "update priority" use lazy deletion (push the new entry, skip stale ones on poll) as in Dijkstra.
  • The iterator and toString() are in array order, not sorted order. Only repeated poll yields sorted output.
  • Building from a collection (new PriorityQueue<>(list)) heapifies in O(n), cheaper than n offers.
  • Changing a field used by the comparator while the element is inside silently breaks the heap invariant (same family of bug as the mutable map key).
  • Not thread-safe; use PriorityBlockingQueue. Comparator (a, b) -> a - b overflows for large values; use Integer.compare or Comparator.comparingInt.

04Production patterns and gotchas

The mutable-key bug

import java.util.HashMap;
import java.util.Map;

class MutableKeyBug {
    static final class Key {
        int id;                                   // mutable field used in equals/hashCode: the bug

        Key(int id) { this.id = id; }

        @Override public boolean equals(Object o) { return o instanceof Key k && k.id == id; }
        @Override public int hashCode() { return Integer.hashCode(id); }
    }

    public static void main(String[] args) {
        Map<Key, String> map = new HashMap<>();
        Key k = new Key(1);
        map.put(k, "contract-1");
        k.id = 2;                                         // mutate the key after insertion
        System.out.println(map.get(k));                   // null: searches the bucket for hash(2)
        System.out.println(map.get(new Key(1)));          // null: right bucket, but equals fails (stored key is 2 now)
        System.out.println(map.containsValue("contract-1")); // true: the entry is still there, orphaned
        System.out.println(map.size());                   // 1
    }
}

The entry still occupies bucket index(hash(1)) with a stored hash of 1, but nothing can reach it: looking up the mutated key goes to bucket index(hash(2)), and looking up a fresh Key(1) finds the node but equals now compares 1 with 2. In a long-running service this is a memory leak plus a cache that never hits. The same applies to HashSet (it is a HashMap with a dummy value) and to JPA entities whose hashCode uses a generated id that is null before persist. Fix: keys immutable (records, String, UUID), or a business key that never changes.

Presize when you know n

new HashMap<>(n) sets capacity, not entries: 100 entries in a capacity-100 map still resizes. Use HashMap.newHashMap(n) (Java 19+) which accounts for the 0.75 load factor.

ConcurrentModificationException

Fail-fast iterators check modCount. Removing inside a for-each throws even single-threaded. Use iterator.remove() or removeIf.

Do not block inside compute

computeIfAbsent on ConcurrentHashMap holds the bin lock while your function runs. A remote call inside it stalls every key in that bin. Modifying the same map inside the function can throw IllegalStateException("Recursive update").

List.of versus Arrays.asList

List.of is immutable and rejects nulls (contains(null) throws NPE). Arrays.asList is fixed-size but writable through to the array.

Unbounded maps are leaks

A static ConcurrentHashMap used as a cache with no eviction is the classic heap-growth incident. Use Caffeine with maximumSize and expireAfterWrite.

Collections.synchronizedMap

One lock for every operation, and you must still synchronise manually while iterating. Rarely the right choice over ConcurrentHashMap.

05Worked LeetCode designs

Design HashMap

leetcode.com/problems/design-hashmap. Implement put, get (return -1 if missing) and remove for int keys without the built-in hash tables. Key insight: show the interviewer the real thing in miniature, power-of-two table, spread hash, separate chaining and a resize at 0.75 load, rather than a 106-element array (which works for the constraints but teaches nothing).

class MyHashMap {
    private static final class Node {
        final int key;
        int value;
        Node next;

        Node(int key, int value, Node next) { this.key = key; this.value = value; this.next = next; }
    }

    private Node[] table = new Node[16];      // length is always a power of two
    private int size;

    private static int index(int key, int length) {
        int h = Integer.hashCode(key);
        h ^= h >>> 16;                         // spread high bits into the low bits, like java.util.HashMap
        return h & (length - 1);               // same as h % length when length is a power of two
    }

    public void put(int key, int value) {
        int i = index(key, table.length);
        for (Node e = table[i]; e != null; e = e.next) {
            if (e.key == key) {
                e.value = value;
                return;
            }
        }
        table[i] = new Node(key, value, table[i]);
        if (++size > table.length * 3 / 4) {  // load factor 0.75
            resize();
        }
    }

    public int get(int key) {
        for (Node e = table[index(key, table.length)]; e != null; e = e.next) {
            if (e.key == key) {
                return e.value;
            }
        }
        return -1;
    }

    public void remove(int key) {
        int i = index(key, table.length);
        Node prev = null;
        for (Node e = table[i]; e != null; prev = e, e = e.next) {
            if (e.key == key) {
                if (prev == null) {
                    table[i] = e.next;
                } else {
                    prev.next = e.next;
                }
                size--;
                return;
            }
        }
    }

    private void resize() {
        Node[] old = table;
        table = new Node[old.length * 2];
        for (Node head : old) {
            for (Node e = head; e != null; ) {
                Node next = e.next;
                int i = index(e.key, table.length);
                e.next = table[i];
                table[i] = e;
                e = next;
            }
        }
    }
}

Time: O(1) average per operation, amortised over resizes. Space: O(n). Edge cases: updating an existing key must not grow size; removing the head of a chain; removing a missing key. Follow-ups: thread safety (lock striping by bucket), open addressing with linear probing (tombstones on delete), treeify long chains.

LRU Cache

leetcode.com/problems/lru-cache. A fixed-capacity cache whose get and put are O(1); when full, evict the least recently used key. Insight: a hash map gives O(1) lookup, a doubly linked list gives O(1) move-to-front and remove-from-back; the map stores list nodes. Sentinel head and tail remove every null check. Interviewers usually say "without LinkedHashMap", so be ready with both.

import java.util.HashMap;
import java.util.Map;

class LRUCache {
    private static final class Node {
        int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) { this.key = key; this.value = value; }
    }

    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0);   // sentinel: most recent is head.next
    private final Node tail = new Node(0, 0);   // sentinel: least recent is tail.prev

    public LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) {
            return -1;
        }
        unlink(n);
        addFirst(n);
        return n.value;
    }

    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) {
            n.value = value;
            unlink(n);
            addFirst(n);
            return;
        }
        if (map.size() == capacity) {
            Node lru = tail.prev;
            unlink(lru);
            map.remove(lru.key);                // this is why the node stores its key
        }
        n = new Node(key, value);
        map.put(key, n);
        addFirst(n);
    }

    private void unlink(Node n) {
        n.prev.next = n.next;
        n.next.prev = n.prev;
    }

    private void addFirst(Node n) {
        n.next = head.next;
        n.prev = head;
        head.next.prev = n;
        head.next = n;
    }
}

Time: O(1) for both operations. Space: O(capacity). Edge cases: capacity 1, put on an existing key must update and refresh without evicting. Follow-ups: thread safety (one lock is honest; Caffeine-style buffered reordering scales), TTL per entry, size by bytes instead of count.

LFU Cache

leetcode.com/problems/lfu-cache. Evict the least frequently used key; break ties by least recently used. Both operations must be O(1). Insight: group keys by frequency, each group an insertion-ordered set (oldest first), and track minFreq. On access, move the key from group f to f + 1, and bump minFreq only if group f became empty and was the minimum. A new key always resets minFreq to 1.

import java.util.HashMap;
import java.util.LinkedHashSet;
import java.util.Map;

class LFUCache {
    private final int capacity;
    private final Map<Integer, int[]> entries = new HashMap<>();               // key -> {value, freq}
    private final Map<Integer, LinkedHashSet<Integer>> byFreq = new HashMap<>(); // freq -> keys, oldest first
    private int minFreq;

    public LFUCache(int capacity) {
        this.capacity = capacity;
    }

    public int get(int key) {
        int[] e = entries.get(key);
        if (e == null) {
            return -1;
        }
        touch(key, e);
        return e[0];
    }

    public void put(int key, int value) {
        if (capacity == 0) {
            return;
        }
        int[] e = entries.get(key);
        if (e != null) {
            e[0] = value;
            touch(key, e);
            return;
        }
        if (entries.size() == capacity) {
            LinkedHashSet<Integer> keys = byFreq.get(minFreq);
            int victim = keys.iterator().next();  // least frequent; ties broken by least recent
            keys.remove(victim);
            if (keys.isEmpty()) {
                byFreq.remove(minFreq);
            }
            entries.remove(victim);
        }
        entries.put(key, new int[] {value, 1});
        byFreq.computeIfAbsent(1, f -> new LinkedHashSet<>()).add(key);
        minFreq = 1;                              // a brand-new key always has the lowest frequency
    }

    private void touch(int key, int[] e) {
        int f = e[1];
        LinkedHashSet<Integer> keys = byFreq.get(f);
        keys.remove(key);
        if (keys.isEmpty()) {
            byFreq.remove(f);
            if (minFreq == f) {
                minFreq = f + 1;
            }
        }
        e[1] = f + 1;
        byFreq.computeIfAbsent(f + 1, x -> new LinkedHashSet<>()).add(key);
    }
}

Time: O(1) average. Space: O(capacity). Edge cases: capacity 0, updating an existing key counts as a use, evicting before inserting (otherwise the new key evicts itself). LinkedHashSet gives the LRU tie-break for free because iteration is insertion order and remove/add moves a key to the end.

Insert Delete GetRandom O(1)

leetcode.com/problems/insert-delete-getrandom-o1. A set with O(1) average insert, remove and uniformly random getRandom. Insight: random access needs an array; O(1) delete from an array needs swap-with-last; finding the index needs a map from value to index.

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Random;

class RandomizedSet {
    private final List<Integer> values = new ArrayList<>();
    private final Map<Integer, Integer> indexOf = new HashMap<>();
    private final Random random = new Random();

    public boolean insert(int val) {
        if (indexOf.containsKey(val)) {
            return false;
        }
        indexOf.put(val, values.size());
        values.add(val);
        return true;
    }

    public boolean remove(int val) {
        Integer i = indexOf.remove(val);
        if (i == null) {
            return false;
        }
        int last = values.remove(values.size() - 1);  // O(1): removing the tail never shifts
        if (i < values.size()) {                       // val was not the tail: move the tail into its slot
            values.set(i, last);
            indexOf.put(last, i);
        }
        return true;
    }

    public int getRandom() {
        return values.get(random.nextInt(values.size()));
    }
}

Time: O(1) average. Space: O(n). Edge case that fails most first attempts: removing the last element, where "swap with last" would re-insert the removed value into the index map. The i < values.size() check handles it. Follow-up (LeetCode 381): allow duplicates by mapping value to a set of indices.

06Interview questions with crisp answers

Walk me through HashMap.put.

Compute hash = h ^ (h >>> 16); create the table if null (16 bins); index (n - 1) & hash. Empty bin: place a node. Otherwise walk the bin (or tree): if a node has the same hash and an equal key, replace the value and return the old one. Else append at the tail; if the list reaches 8, treeify (or resize if fewer than 64 bins). Increment modCount and size; if size exceeds the threshold, double the table and split bins into lo/hi lists.

Why is the capacity a power of two?

So the index is a bitmask (hash & (n - 1)) instead of a modulo, and so a resize moves each entry to either the same index or index + oldCap based on a single bit. The cost is that only low bits pick the bucket, which is why the hash is spread with the upper 16 bits.

When does a bucket become a tree, and why not always use trees?

At 8 nodes, if the table has at least 64 bins; it reverts at 6. TreeNodes are about twice the size of Nodes and slower for small bins; with a decent hash a bin of 8 is vanishingly rare, so trees exist as protection against bad or malicious hash codes.

What happens if two threads use a HashMap concurrently?

Lost updates, lost entries during resize, a size that disagrees with contents, and in Java 7 a possible infinite loop from a cyclic list. Java 8 removed the cycle but the map is still not thread-safe. Use ConcurrentHashMap.

How does ConcurrentHashMap achieve concurrency without segments?

CAS to install the first node in an empty bin, synchronized on the bin's head node for everything else, volatile reads for get, cooperative resizing with forwarding nodes, and a striped counter for size. Lock granularity is one bin rather than one of 16 segments.

Why does ConcurrentHashMap reject null?

A null from get must mean "absent". With null values you would need containsKey to disambiguate, and that check-then-act is racy across threads. Doug Lea considered the ambiguity unacceptable in concurrent maps.

Is if (!map.containsKey(k)) map.put(k, v) safe on ConcurrentHashMap?

No, it is check-then-act: two threads can both see absent and both put. Use putIfAbsent or computeIfAbsent. For counters use merge(k, 1, Integer::sum) or a ConcurrentHashMap<K, LongAdder>.

Is ConcurrentHashMap.size() exact?

Only when no updates are in flight. It sums baseCount and the counter cells without locking, so under concurrent writes it is a moment-in-time estimate. Use mappingCount() for maps that might exceed Integer.MAX_VALUE.

How would you build an LRU cache, and how do you make it thread-safe?

LinkedHashMap with access order and removeEldestEntry, or HashMap plus a doubly linked list for the LeetCode version. Thread safety: a single ReentrantLock around both structures is correct and fine for modest traffic. At scale, use Caffeine, which records reads in striped ring buffers and applies them in batches so reads do not contend on a global lock.

What is the difference between fail-fast and weakly consistent iterators?

Fail-fast (ArrayList, HashMap) compare modCount and throw ConcurrentModificationException on a structural change not made through the iterator; best-effort, not a concurrency guarantee. Weakly consistent (concurrent collections) never throw, traverse elements as they existed at some point, and may reflect later changes.

TreeMap or HashMap for 1 million entries with range queries?

TreeMap (or ConcurrentSkipListMap if shared): range queries like "all bookings between 10:00 and 11:00" are subMap in O(log n + k). HashMap would need a full scan. If you only need point lookups, HashMap is faster and smaller.

How does PriorityQueue find the minimum, and what is slow in it?

The minimum is always at index 0 of a binary heap array. offer and poll are O(log n); remove(Object) and contains are O(n); iteration is not sorted.

Why are Strings good HashMap keys?

Immutable, final class, and the hash is computed once and cached in the object. Their equals and hashCode are consistent and well distributed for typical data.

Does a record make a class immutable?

Shallowly. Record fields are final and equals/hashCode/toString are generated, but a record holding a List or Address exposes that mutable object. Copy in a compact constructor: record Employee(String name, List<String> skills) { Employee { skills = List.copyOf(skills); } }.
