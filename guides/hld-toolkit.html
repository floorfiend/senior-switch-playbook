System design toolkit

This page gives you one plan for any 45-minute HLD (high-level design) round. You also get a set of numbers to estimate with, and a box of building blocks you can reuse in every design.

Study time: 6–8 hours Exercise: one timed 45-min mock Decides: your level, not just pass/fail

In 30 seconds
  • The system design round decides your level. A weak answer often means an offer one level lower.
  • Follow one fixed plan. Scope, estimate, API, data, diagram, deep dives, then wrap up.
  • Every box you draw needs a reason and a number. Never just say "add Redis".
  • Most designs reuse the same few blocks. Load balancer, cache, database, shards, queue and safe retries.
Picture it

Think of a big Indian wedding caterer. The same kit serves 50 guests or 5,000: stoves, helpers, vessels and a head cook. The real skill is asking first how many guests will come. Then the caterer decides how many stoves to bring. They also plan for the moment when 500 people arrive at once.

02The 45-minute plan

0–5 minClarify and scope. Ask who the users are and what they do. Pick the 3–4 core features and say what is out of scope. Then ask about scale: daily active users (DAU) and the read-to-write ratio. Ask about the latency target (SLO), availability, consistency, how long to keep data, multiple regions and legal rules. Write the answers down.
5–10 minEstimate. Work out QPS (average and busiest moment), storage per year, bandwidth and cache size. Only compute numbers that change a decision.
10–15 minAPI. Write 3–5 endpoints with request and response shapes. Add pagination for lists. Add idempotency keys on writes, so a retry does not create a duplicate.
15–20 minData model. List the main entities and how they are read and written. Choose the database. Choose the partition key, the field that decides which server holds a row.
20–30 minHigh-level diagram. Draw the boxes. Walk one read request and one write request through them, start to finish.
30–42 minDeep dives. Pick the 2–3 hardest parts yourself. Good picks are hot keys, consistency, failures and the main scale bottleneck. Compare at least two options for each.
42–45 minWrap up. Say what breaks at 10 times the traffic. Say what you would monitor. Say what you would do with more time.

05Load balancing

A load balancer spreads incoming requests across many servers. L4 and L7 are two kinds. The names come from layers of the network model.

L7 (application) usual pick

  • Reads the HTTP request, so it can route by path, host, header or cookie
  • Can unlock HTTPS, try again on failure, cap request rates, and send a small share (say 5%) to a new version to test it (canary)
  • Uses more CPU per request

AWS ALB, NGINX, Envoy, Spring Cloud Gateway. Use it at the front door for HTTP services.

L4 (transport)

  • Only looks at the address and port, not the request itself. Very fast and cheap.
  • Works with any protocol
  • Cannot route by path or header, because it never reads them

AWS NLB. Use it for raw speed, non-HTTP protocols, or to pass encrypted traffic through untouched (TLS passthrough).

  • Keep services stateless. Put session data in Redis or in a JWT. Avoid "sticky sessions" that tie a user to one server.
  • Health checks remove dead servers. Connection draining lets a server finish its current requests before a deploy stops it.
Go deeper: balancing algorithms

Here are the common ways to pick a server. Round robin takes turns, which suits servers of equal size. Weighted round robin gives bigger servers more turns. Least connections picks the server with the fewest open connections. It suits long or uneven requests, such as WebSockets. Least response time picks the fastest server. IP hash or consistent hash sends the same key to the same server, for example one cache shard per key. Power of two random choices picks two servers at random and uses the less busy one. It is nearly as good as the best choice and needs no shared state. Health checks remove dead servers. Connection draining lets deploys finish requests already in progress. Avoid sticky sessions. Keep services stateless and put session data in Redis or a JWT.

06Caching and CDNs

A cache keeps a fast copy of data. The hard part is deciding when to write to it and when to throw old data away.

Cache-aside usual pick

  • Read the cache first. If missing, read the database and fill the cache. On a write, update the database, then delete the key.
  • The first read after expiry is slow. Data can be slightly old for a short time.

The default for data that is read much more than written. Read-through is the same idea, but the cache library does the loading (Caffeine LoadingCache).

Write-through

  • The cache is never out of date
  • Writes are slower. It also caches data nobody reads.

Data that is read soon after it is written.

Write-back

  • Write to the cache and reply at once. Save to the database later, in batches.
  • Data is lost if the cache node dies before saving

Very high write rates where losing a little is fine: views, likes.

Write-around

  • Writes skip the cache, so it is not filled with unused data
  • The first read is always a miss

Data written once and rarely read again: logs, bulk imports.

Eviction

How a full cache decides what to throw out. It can drop what was used longest ago (LRU), what is used least often (LFU), or what is too old (TTL). LFU suits a few very popular items. Redis settings: allkeys-lru/allkeys-lfu. Caffeine uses W-TinyLFU.

Stampede

A popular copy expires and thousands of requests ask the database at once. Let one request reload it. Give the others the old copy meanwhile. Refresh early, and make expiry times slightly random.

Penetration

Requests for keys that do not exist always miss the cache. Cache the "not found" answer briefly, or use a Bloom filter (a small structure that says "definitely not here").

CDN

Content delivery network: servers near users that cache files. A pull CDN fetches on first request and is the common choice. Put a version in file names, so you never need to clear it.

This code stops a stampede, both inside one JVM and across many pods:

// In-process: Caffeine runs the loader once per key; concurrent callers wait for that result
LoadingCache<String, Document> local = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(30))
    .refreshAfterWrite(Duration.ofSeconds(20))   // serve stale while one async refresh runs
    .build(this::loadFromRedisOrDb);

// Across pods: only the holder of a short Redis lock rebuilds; others serve stale or retry briefly
Boolean won = redis.opsForValue().setIfAbsent("lock:" + key, podId, Duration.ofSeconds(5));
// TTL with jitter so hot keys do not expire together
Duration ttl = Duration.ofMinutes(10).plusSeconds(ThreadLocalRandom.current().nextInt(0, 120));

Eviction decides what to drop when the cache is full. LRU drops the least recently used item. LFU drops the least often used item, which works better when a few items are very popular. TTL drops items by age. In Redis, you set this with maxmemory-policy, for example allkeys-lru or allkeys-lfu. Caffeine uses W-TinyLFU.

A stampede happens when many requests miss the same popular key at once and all hit the database. There are four fixes. First, let one request load the value while the others wait (request coalescing). Caffeine does this per key inside one JVM. Across pods, use a short Redis lock with SET key NX PX. Second, serve the old value while one request refreshes it. Third, refresh popular keys a little before they expire, at a random moment. Fourth, add random jitter to TTLs so keys do not expire together.

Penetration means lookups for keys that do not exist. They always miss, so they always reach the database. Cache the "not found" result for a short time, or use a Bloom filter.

A CDN has servers close to users that cache static files and cacheable responses. A pull CDN fetches from your server (the origin) on the first miss. This is the common choice. A push CDN is loaded in advance, which suits large files and planned releases. Control caching with Cache-Control, ETag and file names that include a version, so you never need to purge. Private content, such as signed contracts, should not be public. Keep it in object storage behind the CDN and serve it through short-lived signed URLs.

07Picking a database

SQL (Postgres / MySQL) usual pick

  • Transactions, joins, any query you think of later, and constraints
  • Splitting tables and adding read copies covers most SDE-2 scales
  • Spreading data across servers later is manual work

Payments, bookings, ledgers.

Wide-column (Cassandra / ScyllaDB / DynamoDB)

  • Handles a huge volume of writes, thanks to LSM storage
  • You must know your queries up front. No joins.

Events, messages, IoT, data ordered by time.

Redis

Key lookups in under a millisecond. Counters, leaderboards, rate limits.

MongoDB or jsonb

Flexible documents that are read whole: product catalogues, form templates.

Elasticsearch

Full-text search and filters. It is fed from the main database using CDC (change data capture), which streams every change across.

Graph DB

Following relationships, like friends of friends. Recursive SQL is enough if the chains are short.

08Sharding, hot keys, consistent hashing

When one database server is not enough, you split the data across several servers. The shard key is the field that decides where each row goes.

Hash usual pick

  • Spreads data evenly
  • A range query, like "all orders this week", must ask every shard
  • Adding servers moves lots of data, unless you use consistent hashing

Range (date, ID range)

  • Range scans stay on one shard. Old data is easy to archive.
  • The newest range gets all the traffic

Directory (lookup table)

  • You can move a big tenant to its own shard at any time
  • Every request needs a lookup, so the table must be cached and always available

Geo

  • Keeps data in the user's country (India's DPDP Act) and close to them
  • Users and queries that cross regions are hard

Partitioning splits a table into pieces. Sharding puts those pieces on different servers. A good shard key has many distinct values and spreads load evenly. The common query should need only one shard.

The celebrity (hot key) problem

Sometimes one key gets far more traffic than all others, like a celebrity's post. Hashing spreads keys, not traffic, so that one key's server gets overloaded.

Hot reads

Keep a copy in each server's own memory for a few seconds. Store the post in Redis several times under different names and read a random one (post:42#0..7). Serve it from the CDN too.

#0#1#2#3

Hot writes

Split one counter into N smaller counters and add them up on read. Or collect increments in memory and save once a second.

Feeds

Push new posts to followers for normal users. For celebrities, followers pull posts when they open the feed. Merge both when reading.

Detect

Count traffic per key, or let Redis sample its busiest keys (--hotkeys). Then you can act before that server falls over.

Figure: the key is turned into a number, which is a spot on a circle. We walk clockwise to the first server marker. Each real server has many markers (virtual nodes). Copies go to the next different real servers. In Java a sorted map finds the marker quickly (TreeMap.ceilingEntry).

Show Java solution 
final class ConsistentHashRing {
    private final NavigableMap<Long, String> ring = new TreeMap<>();
    private final int vnodes;

    ConsistentHashRing(Collection<String> servers, int vnodes) {
        this.vnodes = vnodes;
        servers.forEach(this::add);
    }

    void add(String server) {
        for (int i = 0; i < vnodes; i++) ring.put(hash(server + "#" + i), server);
    }

    void remove(String server) {
        for (int i = 0; i < vnodes; i++) ring.remove(hash(server + "#" + i));
    }

    String serverFor(String key) {
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));
        return (e != null ? e : ring.firstEntry()).getValue();   // wrap around the ring
    }

    private static long hash(String s) {
        byte[] d = sha256(s);   // any well-distributed hash; MurmurHash3 in practice
        return ByteBuffer.wrap(d).getLong() & Long.MAX_VALUE;
    }
}
Go deeper: sharding and consistent hashing in prose

Partitioning splits a table into pieces. Often this happens inside one database, such as Postgres declarative partitioning by range or by hash. Sharding puts those pieces on different database servers. Freshworks asked exactly this difference.

A good shard key has many distinct values and spreads load evenly. It also keeps the common query on one shard. For a multi-tenant SaaS product (many customer companies on one system), tenant_id keeps each tenant's queries on one shard. But one huge tenant then becomes a hot shard. Use a directory so that tenant can get its own shard. Or shard large tenants by (tenant_id, document_id).

The celebrity problem is a key with far more traffic than the others. Examples are a celebrity's profile or posts, a viral product, or one giant tenant. Hashing spreads keys, not load, so that one key's shard melts.

For hot reads, add an in-process cache (Caffeine, with a TTL of a few seconds) in front of Redis. Copy the hot key under several names (post:42#0..7) and read a random copy. Serve from the CDN where you can.

For hot writes, split the counter into N sub-keys and add them up on read. Or collect increments in memory and save them every second. Or append events and total them later in the background.

For feeds, use push for normal users. Push means writing each new post into every follower's feed (fan-out on write). For celebrities with millions of followers, use pull. Pull means followers fetch the celebrity's posts when they read (fan-out on read). Merge the two at read time.

To detect hot keys, track traffic per key or sample with Redis --hotkeys. Then you can react before the shard falls over.

Now, why consistent hashing? With hash(key) mod N, changing N from 4 to 5 moves about 80% of keys. That empties every cache at once. Consistent hashing places servers and keys on a ring. A key belongs to the next server clockwise. Adding or removing a server moves only about 1/N of keys: the ones between it and the server before it. Each physical server gets 100–200 virtual nodes on the ring. This evens out the load. It also spreads a failed server's keys across many others. Cassandra and DynamoDB use it for partitioning. So do client-side memcached sharding and some load balancers. Redis Cluster uses a related idea: 16,384 fixed hash slots assigned to nodes.

09Replication and consistency

Replication means keeping copies of the data on several servers. The question is who accepts writes, and how quickly the copies agree.

Leader-follower usual pick

  • Simple. One leader takes writes. Followers serve extra reads.
  • Followers lag a little, so reads can be slightly old
  • If the leader dies, writes not yet copied can be lost

Postgres, MySQL, Redis, Kafka partitions.

Multi-leader

  • Each region writes locally, so writes are fast
  • Two regions can change the same data. You must resolve it: last write wins, merging, or CRDTs (data types that merge on their own).

Active-active regions, collaborative editors.

Leaderless (quorum)

  • No leader to fail over. You tune how many copies must agree (W and R).
  • Needs background repair when copies disagree (read repair, hinted handoff)

Cassandra, DynamoDB-style stores.

N = 3copies of the data
W = 2copies must confirm a write
R = 2copies asked on a read
R + W > Nso every read includes at least one copy with the latest write

CAP is about network partitions: a break that splits your servers into groups that cannot talk. During one, you must choose. Consistency means refusing some requests. Availability means answering, maybe with old data. PACELC adds the normal case. Else, when there is no partition, you trade speed (latency) against consistency.

Consistency first (CP) money

  • Never a wrong balance or a seat sold twice
  • Returns errors while the leader cannot be reached

Payments, reducing stock, seat booking. Postgres with a synchronous standby is PC/EC.

Availability first (AP)

  • Always answers, and answers fast
  • Data can be old until the copies catch up

Likes, view counts, feeds, online status. Cassandra and DynamoDB default to PA/EL.

Consistency models, from strongest to weakest: linearizable, causal, read-your-writes, monotonic reads, eventual. The table below explains each one.

CAP: a network partition can always happen. When it does, a system with copies must choose. It can stay consistent by refusing or blocking some requests. Or it can stay available by answering, possibly with old data. You cannot opt out of partitions. So the real choice is CP or AP during a partition. PACELC adds the everyday case. Else, with no partition, you trade latency against consistency. Synchronous copying is consistent but slower.

  • Payments, reducing stock, seat booking: choose consistency. Refuse the write if the leader cannot be reached.
  • Likes, view counts, feeds, online status: choose availability. The copies agree later.
  • Cassandra and DynamoDB default to PA/EL, and you can tune it per query. A single-leader Postgres with a synchronous standby is PC/EC.

Quorum arithmetic: there are N = 3 copies. A write succeeds after W = 2 copies confirm it. A read asks R = 2 copies and takes the newest version. Because 2 + 2 > 3, at least one copy in every read saw the latest write. W = 1 and R = 1 is fast and available, but may return old data. W = 3 is consistent, but one node down blocks all writes. Versions are compared by timestamp or by version vectors. Timestamps mean last write wins. That can drop writes made at the same time if server clocks disagree.

10Queues, idempotency, limits, observability

Backpressure

A waiting line with no size limit just hides overload until things crash. Cap the line and the worker pool. Pause reading from Kafka when behind. Tell callers "busy, retry later" (HTTP 429/503 with Retry-After). Drop low-priority work first.

Idempotency

The app attaches a unique ID to each payment or order (Idempotency-Key). The server saves that ID with the result, together with the write itself. If the same request comes again, it returns the saved result instead of charging twice.

Rate limiting

Each customer gets a bucket of allowed requests that refills over time (token bucket). The gateway checks and updates it in Redis in one step that cannot be interrupted (a Lua script). See Distributed rate limiter.

Observability

For each service, count requests, errors and time taken (RED). For each machine, measure how busy and how overloaded it is (USE). Tag every log line with one request ID (traceId) and follow requests across services (OpenTelemetry). Alert on the slowest requests (p99) and on how fast the SLO budget burns.

Common mistakes in production
  • Setting the cache after a write. Instead, delete the key after the transaction commits.
  • Reading from a replica right after the user's own write. They may not see their change.
  • Retrying at every layer. Retry at one layer only, with growing delays, randomness and a limit.
  • No timeouts. Many clients wait forever by default.
  • Taking the tenant ID from a request parameter instead of the JWT.
Go deeper: queues, idempotency, rate limiting, observability and gotchas

Queues and backpressure: a queue sits between producers and consumers and soaks up bursts. But a queue with no limit only hides overload. Sooner or later memory runs out or waits get huge. Backpressure means slowing the producer down. Use bounded queues and thread pools, such as ThreadPoolExecutor with a bounded queue and CallerRunsPolicy. Let Kafka consumers pause partitions. Return HTTP 429 or 503 with Retry-After. Drop low-priority traffic first (load shedding). Size queues with Little's law. Say consumers handle 500 per second and the SLO allows 10 s of waiting. Then a backlog over 5,000 means you must drop work or add servers.

Idempotency: networks can time out after the server has already done the work. The client then retries, and the server sees a duplicate. So make writes idempotent. The client sends an Idempotency-Key (Stripe's pattern). The server saves key → result with a unique constraint. It does this in the same transaction as the business write. For a repeat, it returns the saved result. Consumers drop duplicate events by event ID. Writes that are naturally idempotent are even better. Examples are a PUT with the full state, or SET status = 'PAID' WHERE status = 'PENDING'. See Distributed transactions for the full payment flow.

Rate limiting has five common algorithms. Token bucket allows bursts up to the bucket size and refills at a steady rate. It is the default choice. Leaky bucket sends requests out at a smooth, fixed rate. Fixed window is simple, but allows a double burst at window edges. Sliding window log is exact but uses a lot of memory. Sliding window counter blends two windows with weights. It is accurate enough and cheap. Across many servers, use a Redis Lua script that checks and updates in one atomic step. Key it by tenant or API key and enforce it at the gateway. Return 429 with Retry-After and rate-limit headers. The full design is in Distributed rate limiter.

Observability

  • Metrics: RED for services means rate, errors and duration. USE for resources means utilisation, saturation and errors. The usual tools are Micrometer → Prometheus → Grafana. Alert on percentiles such as p99, not averages.
  • Logs: structured JSON with traceId, tenantId and requestId. Never log personal data (PII) or document contents.
  • Traces: OpenTelemetry or Micrometer Tracing follows a request across HTTP and Kafka hops. It shows which service is slow.
  • SLOs: the SLI is what you measure, such as successful requests under 300 ms. The SLO is the target, such as 99.9% over 30 days. The error budget is how much failure is allowed. 99.9% allows 43.2 minutes of downtime a month. 99.99% allows 4.3 minutes. Alert on burn rate, meaning how fast you are using up the budget.

Production gotchas

  • Cache invalidation order: update the database, then delete the cache key. Do not set it. Setting can race: an older read can overwrite a newer value. Delete after the transaction commits (@TransactionalEventListener(phase = AFTER_COMMIT)). Or drive the delete from CDC.
  • Read replicas break read-your-writes: after a user writes, send their reads to the primary for a short time.
  • Retries make outages worse: three layers retrying three times is 27 calls per user click. Retry at one layer only. Use exponential back-off (longer waits each time), jitter (randomness) and a retry budget.
  • Timeouts everywhere: set connect and read timeouts on every RestClient/WebClient. Set a Hikari connectionTimeout and a Postgres statement_timeout. Many clients wait forever by default.
  • Thundering herd after recovery: when a broken service comes back, every waiting retry fires at once. Jitter and a slow ramp-up prevent a second outage. The circuit breaker's half-open state does this ramp-up.
  • Multi-tenancy: take the tenant ID from the JWT, never from a request parameter. Give each tenant its own rate limits and quotas. Then one tenant's bulk import cannot starve the others.
  • Data residency: India's DPDP Act and customer contracts can require Indian data to stay in India. Pinning shards to a region from the start is easier than adding it later.

11Quick check

You have 4 cache servers and add a 5th. You use "hash mod N" to pick a server. Roughly what happens?

"mod 4" and "mod 5" give the same answer for only about 1 key in 5. So the other 4 in 5 move. Consistent hashing would move only about 1/N.

You just updated a document row. What should the service do with the cache?

Setting the value can race with an older read, which then writes an old value back. Deleting after commit forces the next read to load fresh data.

You have 3 copies (N = 3) and each write waits for 2 (W = 2). What is the smallest R that always reads the latest write?

R + W must be bigger than N. 2 + 2 > 3, so every read includes at least one copy that has the write.

A viral post's like counter overloads one Redis shard. What is the best first fix?

More shards spread different keys. They do not split the traffic of one key. Splitting the hot key into sub-keys spreads its writes across shards.

During a network split, which of these should choose consistency over availability?

Selling the last unit twice costs money and trust, and is hard to undo. A feed or a badge count can be slightly wrong and fix itself later.

12Interview questions with senior answers

Write-through, write-back or write-around: when each? (Goldman)

Use write-through when data is read right after it is written and old data is not acceptable. The cost is slower writes. Use write-back for very high write rates where a little loss is fine, such as counters and analytics. It saves to the database in batches. Use write-around for data written once and rarely read again, so it does not fill the cache with junk. For most CRUD services, I use cache-aside. On a write, I delete the key after the commit.

What is the celebrity problem and how do you solve it? (Freshworks)

One key gets far more traffic than the rest. Its shard or cache node gets overloaded, even though keys are spread evenly. For reads, I use local caches. I also copy the key under several suffixes and read a random copy. For writes, I split counters and add them up later. For feeds, I push posts for normal users (fan-out on write). For celebrities, followers pull posts at read time (fan-out on read).

What happens when the number of servers changes?

With "hash mod N", almost every key moves to a new server. That causes a storm of cache misses or a huge data migration. Consistent hashing with virtual nodes moves only about 1/N of keys. It also spreads them across all remaining servers. Another way is to pre-split into many fixed slots, like Redis Cluster's 16,384. Then you move whole slots between servers.

Partitioning versus sharding?

Partitioning splits a dataset into pieces by some key. Sharding is partitioning where the pieces live on different machines. A Postgres table split by month on one server is partitioned but not sharded.

When do you favour consistency over availability? (Kotak)

When a wrong answer costs money or trust and is hard to undo. Examples are debiting a wallet, selling the last unit of stock, or issuing a unique ID. There I would rather return an error during a network partition. Where old data is harmless and fixes itself, I choose availability. Likes, feed order and notification counts are like that.

How do you serve a user in Germany fast when the data lives in the US? (Goldman)

Serve static and cacheable content through a CDN. For reads, use read replicas or a regional cache in the EU. Send writes to the user's home region. Or partition users by home region, so their writes stay local. Accept some replica lag, but give users read-your-writes for their own changes. Use multi-leader only if writes must be local. Then you must also design how conflicts are resolved. Mention GDPR rules on where data may be stored.

L4 or L7 load balancer?

Use L7 at the edge for HTTP services. It gives path routing, TLS termination, retries, canary releases and rate limiting. Use L4 for raw throughput or non-HTTP protocols. Also use it to keep the client's encrypted connection intact end to end (TLS passthrough). Often you use both: an L4 NLB in front of a fleet of L7 gateways.

How do you prevent a cache stampede?

Combine misses for the same key, so one request loads the value. Inside one JVM, use per-key futures. Across pods, use a short Redis lock. Serve the old value while refreshing. Refresh popular keys early. Add jitter to TTLs. For keys that do not exist, cache the "not found" result briefly.

Explain PACELC with an example.

If there is a Partition, choose Availability or Consistency. Else, choose Latency or Consistency. Cassandra at consistency level ONE is PA/EL. It stays available during partitions and is fast otherwise, but may return old data. A Postgres primary with a synchronous standby is PC/EC. It blocks if the standby cannot be reached. It also pays a network round trip on every commit.

How would you choose a shard key for a multi-tenant SaaS?

tenant_id keeps each tenant's queries on one shard. It also makes deleting a tenant and data residency easy. The risk is one giant tenant. Keep a directory that maps tenant → shard. Then big tenants can be moved or given their own shards. Inside very large tenants, split further by document ID.

Your service's p99 jumped from 200 ms to 2 s. What do you look at?

First, traces, to find which step got slower. Then check if that dependency is overloaded. Look at waits for database connections, CPU, garbage-collection pauses and thread pool queues. Check recent deploys and changes in traffic, such as one tenant's bulk job. Check slow-query logs. Check for downstream timeouts that cause retries. Fix the impact first: roll back, drop load, or raise the pool size only if the database has room. Then find the root cause.

What are SLI, SLO and error budget?

The SLI (service level indicator) is what you measure. An example is the share of requests that succeed in under 300 ms. The SLO (service level objective) is the target, such as 99.9% over 30 days. The error budget is the 0.1% you are allowed to fail. When it is used up, you slow down feature releases and fix reliability. Alert on how fast the budget is burning, not on every spike.

Cheat sheet
  • Plan: scope 5 → estimate 5 → API 5 → data 5 → diagram 10 → deep dives 12 → wrap-up 3 minutes.
  • 1 million requests a day is about 12 QPS. The busiest moment is 2–3× average (10× for flash sales). Little's law: in progress = throughput × latency.
  • L7 load balancer at the edge, L4 for raw TCP. Stateless services, no sticky sessions.
  • Cache-aside. Delete the key after commit. Stop stampedes by letting one request load, serving old data and adding jitter.
  • Postgres by default. Cassandra for huge time-ordered writes. Redis for counters and limits.
  • Shard key: many distinct values, even load, common query on one shard. A directory for giant tenants.
  • Hot key: local cache, copies of the key, split counters, push for normal users and pull for celebrities.
  • Consistent hashing moves about 1/N of keys. "mod N" moves almost all of them.
  • R + W > N for up-to-date quorum reads. Consistency (CP) for money, availability (AP) for likes.
  • Save the Idempotency-Key in the same transaction. Retry at one layer with jitter. Timeouts everywhere.
