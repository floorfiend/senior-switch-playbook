05Load balancing

L7 (application) usual pick

  • Reads HTTP: route by path, host, header, cookie
  • Terminates TLS; retries, rewrites, rate limits, canary splits
  • More CPU per request

AWS ALB, NGINX, Envoy, Spring Cloud Gateway. Use at the edge for HTTP services.

L4 (transport)

  • Routes TCP/UDP by IP and port; very fast and cheap
  • Protocol-agnostic
  • Cannot route by path or header

AWS NLB. Use for raw throughput, non-HTTP protocols or TLS passthrough.

  • Keep services stateless; put session state in Redis or a JWT, not sticky sessions.
  • Health checks remove dead backends; connection draining lets deploys finish in-flight requests.
Go deeper: balancing algorithms

Algorithms: round robin (equal servers), weighted round robin (mixed sizes), least connections (long-lived or uneven requests, such as WebSockets), least response time, IP or consistent hash (affinity, for example a cache shard per key), and power of two random choices (pick two servers at random, send to the less loaded one; near-optimal with no global state). Health checks remove dead backends; connection draining lets deploys finish in-flight requests. Avoid sticky sessions; keep services stateless and put session state in Redis or a JWT.

06Caching and CDNs

Cache-aside usual pick

  • Read cache; on miss read DB and fill. On write, update DB then delete the key
  • First read after expiry is slow; stale window

Default for read-heavy data. Read-through is the same with the loader inside the cache library (Caffeine LoadingCache).

Write-through

  • Cache never stale
  • Write latency; caches data nobody reads

Data read soon after writing.

Write-back

  • Ack from cache, flush to DB in batches
  • Data loss if the node dies before flushing

Very high write rates where small loss is fine: views, likes.

Write-around

  • Writes skip the cache; no pollution
  • First read is always a miss

Write-once, rarely re-read data: logs, bulk imports.

Eviction

LRU (recency), LFU (frequency, better for skewed popularity), TTL. Redis allkeys-lru/allkeys-lfu; Caffeine uses W-TinyLFU.

Stampede

Many misses on one hot key hit the DB at once. Coalesce loads, serve stale, refresh early, jitter TTLs.

Penetration

Lookups for keys that do not exist. Cache the negative result briefly or use a Bloom filter.

CDN

Edge servers near users. Pull CDN is the common choice; version file names so you never purge.

Stampede protection in one JVM and across pods:

// In-process: Caffeine runs the loader once per key; concurrent callers wait for that result
LoadingCache<String, Document> local = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(30))
    .refreshAfterWrite(Duration.ofSeconds(20))   // serve stale while one async refresh runs
    .build(this::loadFromRedisOrDb);

// Across pods: only the holder of a short Redis lock rebuilds; others serve stale or retry briefly
Boolean won = redis.opsForValue().setIfAbsent("lock:" + key, podId, Duration.ofSeconds(5));
// TTL with jitter so hot keys do not expire together
Duration ttl = Duration.ofMinutes(10).plusSeconds(ThreadLocalRandom.current().nextInt(0, 120));

Eviction: LRU (recency), LFU (frequency; better for skewed popularity), TTL. Redis uses maxmemory-policy such as allkeys-lru or allkeys-lfu; Caffeine uses W-TinyLFU. Stampede (many requests miss the same hot key at once and all hit the DB): request coalescing so one caller loads and others wait (Caffeine does this per key in-process; across pods use a short Redis lock with SET key NX PX), serve stale while one request refreshes, probabilistic early refresh before expiry, and random jitter on TTLs so keys do not expire together. Penetration (lookups for keys that do not exist): cache negative results briefly or use a Bloom filter.

CDNs: edge servers close to users cache static and cacheable responses. Pull CDN fetches from origin on first miss (the common choice); push CDN is pre-loaded (large files, predictable releases). Control with Cache-Control, ETag and versioned file names so you never need to purge. For private content (signed contracts), serve via short-lived signed URLs from object storage behind the CDN rather than making it public.

08Sharding, hot keys, consistent hashing

Hash usual pick

  • Even distribution
  • Range queries hit every shard
  • Resharding moves data unless consistent hashing

Range (date, ID range)

  • Local range scans; easy archival
  • Hot spot on the newest range

Directory (lookup table)

  • Move a big tenant to its own shard any time
  • Lookup on every request; must be cached and HA

Geo

  • Data residency (India's DPDP Act), low latency
  • Cross-region users and queries are hard

Partitioning splits a table; sharding puts the pieces on different servers. Good key: high cardinality, even load, one shard per common query.

The celebrity (hot key) problem

Hot reads

Caffeine (few seconds TTL) before Redis; copies post:42#0..7, read a random one; CDN.

Push for normal users, pull for celebrities, merged at read time.

Figure: lookup is a binary search over sorted vnode positions (a Java TreeMap.ceilingEntry). Replicas are the next distinct physical servers clockwise.

Show Java solution 
final class ConsistentHashRing {
    private final NavigableMap<Long, String> ring = new TreeMap<>();
    private final int vnodes;

    ConsistentHashRing(Collection<String> servers, int vnodes) {
        this.vnodes = vnodes;
        servers.forEach(this::add);
    }

    void add(String server) {
        for (int i = 0; i < vnodes; i++) ring.put(hash(server + "#" + i), server);
    }

    void remove(String server) {
        for (int i = 0; i < vnodes; i++) ring.remove(hash(server + "#" + i));
    }

    String serverFor(String key) {
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));
        return (e != null ? e : ring.firstEntry()).getValue();   // wrap around the ring
    }

    private static long hash(String s) {
        byte[] d = sha256(s);   // any well-distributed hash; MurmurHash3 in practice
        return ByteBuffer.wrap(d).getLong() & Long.MAX_VALUE;
    }
}
Go deeper: sharding and consistent hashing in prose

Partitioning splits a table into pieces (often inside one database: Postgres declarative partitioning by range or hash). Sharding places partitions on different database servers. Freshworks asked exactly this distinction.

A good shard key has high cardinality, spreads load evenly, and keeps the common query on one shard. For multi-tenant SaaS, tenant_id keeps each tenant's queries local, but one huge tenant becomes a hot shard: use a directory so that tenant can be isolated, or shard large tenants by (tenant_id, document_id).

The celebrity problem: a key with far more traffic than others: a celebrity's profile or posts, a viral product, one giant tenant. Hashing spreads keys, not load, so that one key's shard melts. Hot reads: an in-process cache (Caffeine, a few seconds TTL) in front of Redis; replicate the hot key under several names (post:42#0..7) and read a random copy; serve from the CDN. Hot writes: split the counter into N sub-keys and sum on read; buffer increments in memory and flush every second; append events and aggregate asynchronously. Feeds: push (fan-out on write) for normal users, pull (fan-out on read) for celebrities with millions of followers, merged at read time. Detect it: per-key metrics or Redis --hotkeys sampling, so you can react before the shard falls over.

With hash(key) mod N, changing N from 4 to 5 moves about 80% of keys, which empties every cache at once. Consistent hashing places servers and keys on a ring; a key belongs to the next server clockwise. Adding or removing a server moves only about 1/N of keys, the ones between it and its predecessor. Each physical server gets 100–200 virtual nodes on the ring so load evens out and a failed server's keys spread across many others. Used by Cassandra and DynamoDB partitioning, client-side memcached sharding and some load balancers. (Redis Cluster uses a related idea: 16,384 fixed hash slots assigned to nodes.)

09Replication and consistency

Leader-follower usual pick

  • Simple; reads scale on followers
  • Replica lag gives stale reads
  • Failover can lose async writes

Postgres, MySQL, Redis, Kafka partitions.

Multi-leader

  • Local write latency per region
  • Write conflicts: last-write-wins, merge, CRDTs

Active-active regions, collaborative editors.

Leaderless (quorum)

  • No failover; tunable W and R
  • Needs read repair and hinted handoff

Cassandra, DynamoDB-style stores.

N = 3replicas
W = 2acks per write
R = 2replicas per read
R + W > Nread set always overlaps the latest write

CAP: during a network partition, choose consistency (refuse some requests) or availability (answer, maybe stale). PACELC: else, with no partition, trade latency against consistency.

Consistency first (CP) money

  • Never a wrong balance or double-sold seat
  • Errors while the leader is unreachable

Payments, inventory decrements, seat booking. Postgres with synchronous standby is PC/EC.

Availability first (AP)

  • Always answers, low latency
  • Stale data until replicas converge

Likes, view counts, feed, presence. Cassandra and DynamoDB default to PA/EL.

Consistency models, strongest to weakest: linearizable, causal, read-your-writes, monotonic reads, eventual.

CAP: when a network partition happens, a replicated system must choose between consistency (refuse or block some requests) and availability (answer, possibly with stale data). Partitions are not optional, so the real choice is CP or AP during a partition. PACELC adds the everyday case: else, with no partition, you trade latency against consistency (synchronous replication is consistent but slower).

  • Payments, inventory decrements, seat booking: choose consistency; refuse the write if the leader is unreachable.
  • Likes, view counts, feed, presence: choose availability; converge later.
  • Cassandra and DynamoDB default to PA/EL (tunable per query); a single-leader Postgres with synchronous standby is PC/EC.

Quorum arithmetic: N = 3 replicas. Write succeeds after W = 2 acknowledgements; a read asks R = 2 replicas and takes the newest version. Because 2 + 2 > 3, at least one replica in any read set saw the latest write. W = 1, R = 1 is fast and available but may return stale data. W = 3 is consistent but any one node down blocks writes. Versions are compared by timestamps (last-write-wins, which can drop concurrent writes when clocks skew) or by version vectors.

10Queues, idempotency, limits, observability

Backpressure

An unbounded queue hides overload. Bound queues and pools, pause Kafka partitions, return 429/503 with Retry-After, shed low-priority traffic first.

Idempotency

Client sends an Idempotency-Key; server stores key → result in the same transaction as the write and replays it on retries.

Rate limiting

Token bucket by default; atomic Redis Lua per tenant at the gateway. See Distributed rate limiter.

Observability

RED metrics for services, USE for resources, JSON logs with traceId, OpenTelemetry traces, alerts on p99 and SLO burn rate.

Common mistakes in production
  • Setting the cache after a write instead of deleting it after commit.
  • Replica reads right after the user's own write.
  • Retrying at every layer; retry at one, with back-off, jitter and a budget.
  • No timeouts: many clients default to effectively infinite.
  • Tenant ID from a request parameter instead of the JWT.
Go deeper: queues, idempotency, rate limiting, observability and gotchas

Queues and backpressure: a queue decouples producers from consumers and absorbs bursts, but an unbounded queue only hides overload until memory or latency explodes. Backpressure means slowing the producer: bounded queues and thread pools (ThreadPoolExecutor with a bounded queue and CallerRunsPolicy), Kafka consumers that pause partitions, HTTP 429 or 503 with Retry-After, and load shedding of low-priority traffic first. Size queues with Little's law: if consumers process 500/s and the SLO allows 10 s of waiting, a backlog over 5,000 means shed or scale.

Idempotency: networks time out after the server has done the work, so clients retry and servers see duplicates. Make writes idempotent: the client sends an Idempotency-Key (Stripe's pattern); the server stores key → result with a unique constraint, in the same transaction as the business write, and returns the stored result for repeats. Consumers de-duplicate on event ID. Natural idempotency (PUT full state, SET status = 'PAID' WHERE status = 'PENDING') is even better. See Distributed transactions for the full payment flow.

Rate limiting: token bucket (burst up to bucket size, refill at a steady rate; the default choice), leaky bucket (smooth output rate), fixed window (simple, double burst at window edges), sliding window log (exact, memory-heavy) and sliding window counter (weighted blend of two windows; good accuracy, cheap). Distributed: a Redis Lua script that checks and updates atomically, keyed by tenant or API key, enforced at the gateway. Return 429 with Retry-After and rate-limit headers. Full design in Distributed rate limiter.

Observability

  • Metrics: RED for services (rate, errors, duration) and USE for resources (utilisation, saturation, errors). Micrometer → Prometheus → Grafana. Alert on percentiles (p99), not averages.
  • Logs: structured JSON with traceId, tenantId, requestId; never log PII or document contents.
  • Traces: OpenTelemetry / Micrometer Tracing across HTTP and Kafka hops to find which service owns the latency.
  • SLOs: SLI = what you measure (successful requests under 300 ms); SLO = the target (99.9% over 30 days); error budget = what you may burn. 99.9% allows 43.2 minutes of downtime a month; 99.99% allows 4.3 minutes. Alert on burn rate.

Production gotchas

  • Cache invalidation order: update the database, then delete the cache key (not set it). Setting can race: an older read can overwrite a newer value. Do the delete after the transaction commits (@TransactionalEventListener(phase = AFTER_COMMIT)), or drive invalidation from CDC.
  • Read replicas break read-your-writes: route a user's reads to the primary briefly after their write.
  • Retries amplify outages: three layers retrying three times is 27 calls per user click. Retry at one layer, with exponential back-off, jitter and a retry budget.
  • Timeouts everywhere: set connect and read timeouts on every RestClient/WebClient, a Hikari connectionTimeout, a Postgres statement_timeout. The default for many clients is effectively infinite.
  • Thundering herd after recovery: when a dependency returns, every queued retry fires at once. Jitter and gradual ramp-up (circuit breaker half-open state) prevent a second outage.
  • Multi-tenancy: tenant ID from the JWT, never from a request parameter; per-tenant rate limits and quotas so one tenant's bulk import cannot starve others.
  • Data residency: India's DPDP Act and customer contracts can require Indian data to stay in India. Region-pinned shards are easier than retrofitting.

11Quick check

You add a 5th cache server to 4. With mod-N hashing, roughly what happens?

mod 4 and mod 5 agree for only ~1 in 5 keys. Consistent hashing would move only ~1/N.

After updating a document row, what should the service do with the cache?

Setting can race with an older read that writes a stale value back. Deleting after commit makes the next read reload fresh data.

N = 3 replicas, W = 2. What is the smallest R that guarantees reading the latest write?

R + W must exceed N: 2 + 2 > 3, so every read set overlaps at least one replica that has the write.

A viral post's like counter melts one Redis shard. Best first fix?

More shards spread keys, not one key's load. Splitting the hot key spreads its writes across shards.

Which should choose consistency over availability during a partition?

A wrong answer costs money and trust and cannot be compensated cheaply. Feeds and badges can converge later.

12Interview questions with senior answers

Write-through, write-back or write-around: when each? (Goldman)

Write-through when data is read right after it is written and staleness is unacceptable, at the cost of write latency. Write-back for very high write rates where a little loss is acceptable (counters, analytics), flushing in batches. Write-around for write-once data that is rarely re-read, so it does not pollute the cache. For most CRUD services I use cache-aside with delete-on-write after commit.

What is the celebrity problem and how do you solve it? (Freshworks)

One key gets disproportionate traffic, so its shard or cache node saturates even though keys are evenly hashed. For reads: local caches plus replicating the key under several suffixes and reading a random copy. For writes: split counters and aggregate. For feeds: fan-out on write for normal users and fan-out on read for celebrities.

What happens when the number of servers changes?

With mod-N hashing nearly every key remaps, causing a cache miss storm or a massive data migration. Consistent hashing with virtual nodes moves only about 1/N of keys and spreads them across all remaining servers. Pre-splitting into many fixed slots (Redis Cluster's 16,384) achieves the same by moving whole slots.

Partitioning versus sharding?

Partitioning splits a dataset into pieces by some key; sharding is partitioning where the pieces live on different machines. A Postgres table partitioned by month on one server is partitioned but not sharded.

When do you favour consistency over availability? (Kotak)

When a wrong answer costs money or trust and cannot be compensated cheaply: debiting a wallet, decrementing the last unit of inventory, issuing a unique ID. There I would rather return an error during a partition. Where staleness is harmless and recoverable (likes, feed ordering, notification counts), I choose availability.

How do you serve a user in Germany fast when the data lives in the US? (Goldman)

Static and cacheable content through a CDN; read replicas or a regional cache in the EU for reads; route writes to the home region (or partition users by home region so their writes are local); accept replica lag and give read-your-writes for the user's own changes. Multi-leader only if writes must be local, and then design conflict resolution. Mention GDPR data-residency constraints.

L4 or L7 load balancer?

L7 at the edge for HTTP services: path routing, TLS termination, retries, canaries, rate limiting. L4 when you need raw throughput, non-HTTP protocols, or to preserve the client connection end-to-end (TLS passthrough). Often both: an L4 NLB in front of an L7 gateway fleet.

How do you prevent a cache stampede?

Coalesce concurrent misses so one request loads the value (per-key futures in-process, a short Redis lock across pods), serve stale data while refreshing, refresh hot keys early, and add jitter to TTLs. For keys that do not exist, cache the negative result briefly.

Explain PACELC with an example.

If there is a Partition, choose Availability or Consistency; Else, choose Latency or Consistency. Cassandra at consistency level ONE is PA/EL: available in partitions and low-latency otherwise, possibly stale. A Postgres primary with a synchronous standby is PC/EC: it blocks if the standby is unreachable and pays a round trip on every commit.

How would you choose a shard key for a multi-tenant SaaS?

tenant_id keeps each tenant's queries on one shard and makes tenant deletion and residency easy. The risk is a giant tenant. Use a directory mapping tenant → shard so big tenants can be moved or given dedicated shards, and inside very large tenants sub-shard by document ID.

Your service's p99 jumped from 200 ms to 2 s. What do you look at?

Traces to find which span grew; then saturation of that dependency (DB connection pool waits, CPU, GC pauses, thread pool queue); recent deploys and traffic mix (one tenant's bulk job); slow-query logs; downstream timeouts causing retries. Mitigate first (roll back, shed load, raise pool size only if the DB has headroom), then root-cause.

What are SLI, SLO and error budget?

SLI is the measured indicator (fraction of requests served successfully under 300 ms). SLO is the target (99.9% over 30 days). The error budget is the 0.1% you may fail; when it is spent, you slow feature releases and fix reliability. Alert on budget burn rate rather than every spike.

Cheat sheet
  • Plan: scope 5 → estimate 5 → API 5 → data 5 → diagram 10 → deep dives 12 → wrap-up 3.
  • 1 M/day ≈ 12 QPS; peak 2–3× (10× for flash sales); Little's law = throughput × latency.
  • L7 at the edge, L4 for raw TCP; stateless services, no sticky sessions.
  • Cache-aside, delete after commit; stampede → coalesce, stale, jitter.
  • Postgres by default; Cassandra for huge time-ordered writes; Redis for counters and limits.
  • Shard key: high cardinality, even load, query on one shard; directory for giant tenants.
  • Hot key: local cache, key copies, split counters, push/pull feeds.
  • Consistent hashing moves ~1/N keys; mod N moves almost all.
  • R + W > N for quorum reads; CP for money, AP for likes.
  • Idempotency-Key in the same transaction; one retry layer with jitter; timeouts everywhere.
