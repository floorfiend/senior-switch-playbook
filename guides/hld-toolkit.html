01Why interviewers ask this

At SDE-2 and above, the system design round sets your level. A weak HLD rarely means rejection outright; it means an offer one level down:

  • Amazon SDE-2 (Aug 2026): the candidate got "Design an inventory management system", expected LLD, realised late it was HLD, and struggled on the concurrency follow-ups (one unit left, two simultaneous orders). Result: an SDE-1 offer, because the HLD and Bar Raiser rounds did not convince the panel of SDE-2 level.
  • Atlassian P50 (8 YOE): a Web Crawler design the candidate thought went well. Feedback: down-levelled, partly for not asking enough clarifying questions. Down-levelled in two rounds, the recruiter offered P40 or withdrawal.
  • Goldman Sachs Associate: caching strategies in detail (write-back, write-through, write-around and when to prefer each), then serving a German user with low latency from a US data source: partitioning, consistent hashing, multi-master, read replicas, SQL versus NoSQL.
  • Freshworks SDE-2: what is sharding, what is the celebrity problem, what happens when the number of servers changes, and partitioning versus sharding.
  • Kotak SDE-2: when to favour consistency over availability, strong versus eventual consistency, idempotency keys for placing an order.
How down-levelling happens
  • Jumping to boxes without scoping (the Atlassian feedback). Clarifying questions are graded even when the problem feels obvious.
  • Naming components without numbers or trade-offs ("add Redis, add Kafka").
  • No depth when the interviewer pushes on one component, especially concurrency and failure.
  • Letting the interviewer drive. A senior candidate proposes the deep dives.

02Core concepts, built up

A repeatable 45-minute framework

0–5 minClarify and scope. Users and use cases, the 3–4 core features, explicit non-goals. Non-functional: scale (DAU, read/write ratio), latency SLO, availability, consistency needs, data retention, multi-region, compliance. Write them down.
5–10 minEstimate. QPS (average and peak), storage per year, bandwidth, cache size. Only the numbers that change a decision.
10–15 minAPI. 3–5 endpoints with request/response shape, pagination, idempotency keys on writes.
15–20 minData model. Entities, access patterns, database choice, partition key.
20–30 minHigh-level diagram. Walk one read and one write request end to end.
30–42 minDeep dives. Pick the 2–3 hardest parts yourself: hot keys, consistency, failure, scale bottleneck. Compare alternatives.
42–45 minWrap up. What breaks at 10x, monitoring, what you would do with more time.

Back-of-envelope estimation

Conversions

  • 1 day ≈ 86,400 s ≈ 105 s
  • 1 M requests/day ≈ 12 QPS
  • 1 B requests/day ≈ 12k QPS
  • Peak ≈ 2–3× average (10× for flash sales, IPL toss, Diwali)
  • 1 KB × 1 M = 1 GB; 1 KB × 1 B = 1 TB

Rough capacity (order of magnitude)

  • Spring Boot pod, simple I/O-bound API: 1–5k RPS
  • Redis single node: ~100k ops/s, sub-ms
  • PostgreSQL primary: several thousand to tens of thousands of simple writes/s, depending on hardware
  • Kafka broker: tens to hundreds of MB/s
  • Little's law: concurrency = throughput × latency (2,000 RPS × 0.2 s = 400 in-flight requests)

Practical translations: a Redis GET in the same zone is well under a millisecond, an indexed Postgres point query a few milliseconds, a cross-continent call from Mumbai to US East around 200 ms round trip. A 200 ms p99 budget therefore allows about one cross-region hop or dozens of in-region calls.

Load balancing

L4 (transport)

Routes TCP/UDP connections by IP and port, without reading the payload. Very fast, cheap, protocol-agnostic. Examples: AWS NLB. Cannot route by path or header.

L7 (application)

Terminates TLS and reads HTTP: routes by path, host, header, cookie; can retry, rewrite, rate-limit, and do canary splits. Examples: AWS ALB, NGINX, Envoy, Spring Cloud Gateway. More CPU per request.

Algorithms: round robin (equal servers), weighted round robin (mixed sizes), least connections (long-lived or uneven requests, such as WebSockets), least response time, IP or consistent hash (affinity, for example a cache shard per key), and power of two random choices (pick two servers at random, send to the less loaded one; near-optimal with no global state). Health checks remove dead backends; connection draining lets deploys finish in-flight requests. Avoid sticky sessions; keep services stateless and put session state in Redis or a JWT.

Caching

StrategyHow it worksUse whenRisk
Cache-aside (lazy loading)App reads cache; on miss reads DB and fills cache. On write, update DB then delete the cache key.Default for read-heavy dataFirst read after expiry is slow; stale data window
Read-throughCache library loads from DB on miss (Caffeine LoadingCache)Same as cache-aside, logic in one placeSame

Write-back (write-behind)Write to cache, acknowledge, flush to DB asynchronously in batchesVery high write rates where small loss is acceptable (view counters, likes)Data loss if the cache node dies before flushing
Write-aroundWrites go to DB only; cache is filled on readData written once and rarely re-read (logs, bulk imports)First read is always a miss

Eviction: LRU (recency), LFU (frequency; better for skewed popularity), TTL. Redis uses maxmemory-policy such as allkeys-lru or allkeys-lfu; Caffeine uses W-TinyLFU. Stampede (many requests miss the same hot key at once and all hit the DB): request coalescing so one caller loads and others wait (Caffeine does this per key in-process; across pods use a short Redis lock with SET key NX PX), serve stale while one request refreshes, probabilistic early refresh before expiry, and random jitter on TTLs so keys do not expire together. Penetration (lookups for keys that do not exist): cache negative results briefly or use a Bloom filter.

CDNs

Edge servers close to users cache static and cacheable responses. Pull CDN fetches from origin on first miss (the common choice); push CDN is pre-loaded (large files, predictable releases). Control with Cache-Control, ETag and versioned file names so you never need to purge. For private content (signed contracts), serve via short-lived signed URLs from object storage behind the CDN rather than making it public.

Say why in terms of access patterns, consistency and scale. "NoSQL scales better" alone is a red flag; Postgres with partitioning and read replicas handles most SDE-2 interview scales.

Sharding and shard keys

Partitioning splits a table into pieces (often inside one database: Postgres declarative partitioning by range or hash). Sharding places partitions on different database servers. Freshworks asked exactly this distinction.

StrategyProsCons
Range (by date, by ID range)Range scans are local; easy archivalHot spot on the latest range for time-ordered writes
Hash (hash(key) → shard)Even distributionRange queries hit every shard; resharding moves data unless you use consistent hashing
Directory / lookup tableMove a big tenant to its own shard any timeLookup service is on every request path; must be cached and highly available
GeoData residency (India's DPDP Act), low latencyCross-region users and queries are hard

A good shard key has high cardinality, spreads load evenly, and keeps the common query on one shard. For multi-tenant SaaS, tenant_id keeps each tenant's queries local, but one huge tenant becomes a hot shard: use a directory so that tenant can be isolated, or shard large tenants by (tenant_id, document_id).

The celebrity (hot key) problem

A key with far more traffic than others: a celebrity's profile or posts, a viral product, one giant tenant. Hashing spreads keys, not load, so that one key's shard melts.

  • Hot reads: an in-process cache (Caffeine, a few seconds TTL) in front of Redis; replicate the hot key under several names (post:42#0..7) and read a random copy; serve from the CDN.
  • Hot writes: split the counter into N sub-keys and sum on read; buffer increments in memory and flush every second; append events and aggregate asynchronously.
  • Feeds: push (fan-out on write) for normal users, pull (fan-out on read) for celebrities with millions of followers, merged at read time.
  • Detect it: per-key metrics or Redis --hotkeys sampling, so you can react before the shard falls over.

Consistent hashing

With hash(key) mod N, changing N from 4 to 5 moves about 80% of keys, which empties every cache at once. Consistent hashing places servers and keys on a ring; a key belongs to the next server clockwise. Adding or removing a server moves only about 1/N of keys, the ones between it and its predecessor. Each physical server gets 100–200 virtual nodes on the ring so load evens out and a failed server's keys spread across many others. Used by Cassandra and DynamoDB partitioning, client-side memcached sharding and some load balancers. (Redis Cluster uses a related idea: 16,384 fixed hash slots assigned to nodes.)

Replication

ModelHowTrade-offExamples
Leader-followerAll writes to one leader; followers replay its log; reads can go to followersSimple; replica lag gives stale reads; failover can lose async writesPostgres, MySQL, Redis, Kafka partitions
Multi-leaderSeveral leaders accept writes (often one per region) and replicate to each otherLocal write latency; write conflicts need resolution (last-write-wins, merge, CRDTs)Multi-region active-active setups, collaborative editors
Leaderless (quorum)Write to W of N replicas, read from R; if R + W > N the sets overlapNo failover; tunable; read repair and hinted handoff fix divergenceCassandra, DynamoDB-style stores

CAP and PACELC

CAP: when a network partition happens, a replicated system must choose between consistency (refuse or block some requests) and availability (answer, possibly with stale data). Partitions are not optional, so the real choice is CP or AP during a partition. PACELC adds the everyday case: else, with no partition, you trade latency against consistency (synchronous replication is consistent but slower).

  • Payments, inventory decrements, seat booking: choose consistency; refuse the write if the leader is unreachable.
  • Likes, view counts, feed, presence: choose availability; converge later.
  • Cassandra and DynamoDB default to PA/EL (tunable per query); a single-leader Postgres with synchronous standby is PC/EC.

Consistency models (strongest to weakest)

ModelGuaranteeExample need
Linearizable (strong)Every read sees the latest committed write, as if there were one copyAccount balance, unique username, leader election
CausalEffects are seen after their causes (a reply after its comment)Comment threads, chat
Read-your-writesA user always sees their own updatesProfile edits, "my documents" list after upload

EventualReplicas converge if writes stopCounters, search index, analytics

Queues and backpressure

A queue decouples producers from consumers and absorbs bursts, but an unbounded queue only hides overload until memory or latency explodes. Backpressure means slowing the producer: bounded queues and thread pools (ThreadPoolExecutor with a bounded queue and CallerRunsPolicy), Kafka consumers that pause partitions, HTTP 429 or 503 with Retry-After, and load shedding of low-priority traffic first. Size queues with Little's law: if consumers process 500/s and the SLO allows 10 s of waiting, a backlog over 5,000 means shed or scale.

Idempotency

Networks time out after the server has done the work, so clients retry and servers see duplicates. Make writes idempotent: the client sends an Idempotency-Key (Stripe's pattern); the server stores key → result with a unique constraint, in the same transaction as the business write, and returns the stored result for repeats. Consumers de-duplicate on event ID. Natural idempotency (PUT full state, SET status = 'PAID' WHERE status = 'PENDING') is even better. See Distributed transactions for the full payment flow.

Rate limiting

Token bucket (burst up to bucket size, refill at a steady rate; the default choice), leaky bucket (smooth output rate), fixed window (simple, double burst at window edges), sliding window log (exact, memory-heavy) and sliding window counter (weighted blend of two windows; good accuracy, cheap). Distributed: a Redis Lua script that checks and updates atomically, keyed by tenant or API key, enforced at the gateway. Return 429 with Retry-After and rate-limit headers. Full design in Distributed rate limiter.

Observability

  • Metrics: RED for services (rate, errors, duration) and USE for resources (utilisation, saturation, errors). Micrometer → Prometheus → Grafana. Alert on percentiles (p99), not averages.
  • Logs: structured JSON with traceId, tenantId, requestId; never log PII or document contents.
  • Traces: OpenTelemetry / Micrometer Tracing across HTTP and Kafka hops to find which service owns the latency.
  • SLOs: SLI = what you measure (successful requests under 300 ms); SLO = the target (99.9% over 30 days); error budget = what you may burn. 99.9% allows 43.2 minutes of downtime a month; 99.99% allows 4.3 minutes. Alert on burn rate.

03How it works internally

Quorum arithmetic

N = 3 replicas. Write succeeds after W = 2 acknowledgements; a read asks R = 2 replicas and takes the newest version. Because 2 + 2 > 3, at least one replica in any read set saw the latest write. W = 1, R = 1 is fast and available but may return stale data. W = 3 is consistent but any one node down blocks writes. Versions are compared by timestamps (last-write-wins, which can drop concurrent writes when clocks skew) or by version vectors.

Consistent hashing, step by step

key "doc:981"→hash position 0.37 on ring→next clockwise vnode B#17 at 0.41→ Server B+ next 2 distinct servers as replicas

Figure: lookup is a binary search over sorted vnode positions (a Java TreeMap.ceilingEntry). Replicas are the next distinct physical servers clockwise.

final class ConsistentHashRing {
    private final NavigableMap<Long, String> ring = new TreeMap<>();
    private final int vnodes;

    ConsistentHashRing(Collection<String> servers, int vnodes) {
        this.vnodes = vnodes;
        servers.forEach(this::add);
    }

    void add(String server) {
        for (int i = 0; i < vnodes; i++) ring.put(hash(server + "#" + i), server);
    }

    void remove(String server) {
        for (int i = 0; i < vnodes; i++) ring.remove(hash(server + "#" + i));
    }

    String serverFor(String key) {
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));
        return (e != null ? e : ring.firstEntry()).getValue();   // wrap around the ring
    }

    private static long hash(String s) {
        byte[] d = sha256(s);   // any well-distributed hash; MurmurHash3 in practice
        return ByteBuffer.wrap(d).getLong() & Long.MAX_VALUE;
    }
}

04Practical patterns and production gotchas

  • Cache invalidation order: update the database, then delete the cache key (not set it). Setting can race: an older read can overwrite a newer value. Do the delete after the transaction commits (@TransactionalEventListener(phase = AFTER_COMMIT)), or drive invalidation from CDC.
  • Read replicas break read-your-writes: route a user's reads to the primary briefly after their write.
  • Retries amplify outages: three layers retrying three times is 27 calls per user click. Retry at one layer, with exponential back-off, jitter and a retry budget.
  • Timeouts everywhere: set connect and read timeouts on every RestClient/WebClient, a Hikari connectionTimeout, a Postgres statement_timeout. The default for many clients is effectively infinite.
  • Thundering herd after recovery: when a dependency returns, every queued retry fires at once. Jitter and gradual ramp-up (circuit breaker half-open state) prevent a second outage.
  • Multi-tenancy: tenant ID from the JWT, never from a request parameter; per-tenant rate limits and quotas so one tenant's bulk import cannot starve others.
  • Data residency: India's DPDP Act and customer contracts can require Indian data to stay in India. Region-pinned shards are easier than retrofitting.

05Interview questions with senior answers

Write-through, write-back or write-around: when each? (Goldman)

Write-through when data is read right after it is written and staleness is unacceptable, at the cost of write latency. Write-back for very high write rates where a little loss is acceptable (counters, analytics), flushing in batches. Write-around for write-once data that is rarely re-read, so it does not pollute the cache. For most CRUD services I use cache-aside with delete-on-write after commit.

What is the celebrity problem and how do you solve it? (Freshworks)

One key gets disproportionate traffic, so its shard or cache node saturates even though keys are evenly hashed. For reads: local caches plus replicating the key under several suffixes and reading a random copy. For writes: split counters and aggregate. For feeds: fan-out on write for normal users and fan-out on read for celebrities.

What happens when the number of servers changes?

With mod-N hashing nearly every key remaps, causing a cache miss storm or a massive data migration. Consistent hashing with virtual nodes moves only about 1/N of keys and spreads them across all remaining servers. Pre-splitting into many fixed slots (Redis Cluster's 16,384) achieves the same by moving whole slots.

Partitioning versus sharding?

Partitioning splits a dataset into pieces by some key; sharding is partitioning where the pieces live on different machines. A Postgres table partitioned by month on one server is partitioned but not sharded.

When do you favour consistency over availability? (Kotak)

When a wrong answer costs money or trust and cannot be compensated cheaply: debiting a wallet, decrementing the last unit of inventory, issuing a unique ID. There I would rather return an error during a partition. Where staleness is harmless and recoverable (likes, feed ordering, notification counts), I choose availability.

How do you serve a user in Germany fast when the data lives in the US? (Goldman)

Static and cacheable content through a CDN; read replicas or a regional cache in the EU for reads; route writes to the home region (or partition users by home region so their writes are local); accept replica lag and give read-your-writes for the user's own changes. Multi-leader only if writes must be local, and then design conflict resolution. Mention GDPR data-residency constraints.

L4 or L7 load balancer?

L7 at the edge for HTTP services: path routing, TLS termination, retries, canaries, rate limiting. L4 when you need raw throughput, non-HTTP protocols, or to preserve the client connection end-to-end (TLS passthrough). Often both: an L4 NLB in front of an L7 gateway fleet.

How do you prevent a cache stampede?

Coalesce concurrent misses so one request loads the value (per-key futures in-process, a short Redis lock across pods), serve stale data while refreshing, refresh hot keys early, and add jitter to TTLs. For keys that do not exist, cache the negative result briefly.

Explain PACELC with an example.

If there is a Partition, choose Availability or Consistency; Else, choose Latency or Consistency. Cassandra at consistency level ONE is PA/EL: available in partitions and low-latency otherwise, possibly stale. A Postgres primary with a synchronous standby is PC/EC: it blocks if the standby is unreachable and pays a round trip on every commit.

How would you choose a shard key for a multi-tenant SaaS?

tenant_id keeps each tenant's queries on one shard and makes tenant deletion and residency easy. The risk is a giant tenant. Use a directory mapping tenant → shard so big tenants can be moved or given dedicated shards, and inside very large tenants sub-shard by document ID.

Your service's p99 jumped from 200 ms to 2 s. What do you look at?

Traces to find which span grew; then saturation of that dependency (DB connection pool waits, CPU, GC pauses, thread pool queue); recent deploys and traffic mix (one tenant's bulk job); slow-query logs; downstream timeouts causing retries. Mitigate first (roll back, shed load, raise pool size only if the DB has headroom), then root-cause.

What are SLI, SLO and error budget?

SLI is the measured indicator (fraction of requests served successfully under 300 ms). SLO is the target (99.9% over 30 days). The error budget is the 0.1% you may fail; when it is spent, you slow feature releases and fix reliability. Alert on budget burn rate rather than every spike.

06Hands-on exercise (one timed mock)

  1. Set a 45-minute timer and design "document upload and e-signing for 5,000 enterprise tenants, 2 M signatures/day, 99.95% availability". Follow the framework above out loud or on paper.
  2. Produce: five clarifying questions, an estimation table (QPS, storage per year, cache size), three APIs with idempotency, a data model with shard key, a diagram, and two deep dives (hot tenant; signing-step consistency).
  3. Self-review against the down-levelling list: did you scope before drawing, did every component have a reason and a number, did you volunteer the deep dives?
  4. Code the ConsistentHashRing above with 3 servers × 150 vnodes; hash 100,000 keys; print keys per server; add a fourth server and print how many keys moved (expect about 25%). Compare with mod-N (expect about 75%).
