Distributed transactions and resilience

How to keep data correct when one business operation spans several services and databases: why two-phase commit is avoided, sagas with compensations, the transactional outbox, idempotency keys for payments, and the Resilience4j toolkit that keeps one slow dependency from taking everything down.

01Why interviewers ask this

"We use microservices" on a resume invites the question "so how do you keep data consistent across them?" The reports:

  • Visa Staff SWE: how would you move a monolith to microservices (the candidate answered with the strangler fig pattern, API-gateway routing, feature flags and canary deployments), then: once data is scattered across services, how do transactions work? Answer expected: Saga. Later, cross-data-centre replication for DB and Kafka.
  • Flipkart SDE-2 hiring manager round: microservice patterns, circuit breaker, Saga, CQRS and event-driven design. The candidate's advice: be prepared to go deep, not just name-drop.
  • Apple (Java, Spring Boot, microservices): handling cascading failures, discussed around circuit breakers.
  • Zepto SDE-3: an LLD round with a two-phase commit follow-up the candidate could not explain; no feedback afterwards.
  • Kotak SDE-2: what is idempotency, how do you define an idempotency key, and how would you use it when placing an order in a food-delivery app?
  • PhonePe SDE: a deep dive on payments, double payment and idempotency.
  • Angel One SDE-2: database commits and transaction handling, partner bank failures, handling payment failures.
The senior answer in one breath

Each service owns its data and commits locally. Cross-service consistency is eventual, achieved by a saga of local transactions with compensations, events published through a transactional outbox, idempotent consumers, and idempotency keys at the API edge. Timeouts, retries with jitter, circuit breakers and bulkheads stop failures from spreading.

02Core concepts, built up

The problem: dual writes

@Transactional
public Order placeOrder(PlaceOrder cmd) {
    Order order = orderRepo.save(Order.pending(cmd));
    kafkaTemplate.send("order-events", order.id(), new OrderCreated(order));  // not part of the DB transaction
    return order;
}

If the send succeeds and the commit then fails, other services act on an order that does not exist. If the commit succeeds and the pod dies before the send, the order exists but nobody hears about it. Moving the send after the commit only swaps which failure you get. Any time code writes to two systems that do not share a transaction, one of them can be lost. Everything on this page is a way around that.

Two-phase commit, and why microservices avoid it (the Zepto question)

Coordinator→1. PREPARE Order DBwrites, locks, votes YES Payment DBwrites, locks, votes YES→2. log decision Coordinator→3. COMMIT to all Participants release locks

Figure: 2PC. Phase 1 (prepare/vote): each participant makes the change durable and promises it can commit. Phase 2 (commit/abort): the coordinator records the outcome, then tells everyone.

  • Blocking: a participant that voted YES cannot decide alone. If the coordinator crashes after the votes, participants stay "in doubt", holding row locks, until it recovers.
  • Availability multiplies down: the transaction needs every participant up; three services at 99.9% give at most 99.7%.
  • Latency and lock time: two network round trips while locks are held, which kills throughput on hot rows.
  • Support: Kafka, most NoSQL stores and third-party APIs (a payment gateway) cannot join an XA transaction. PostgreSQL supports it (PREPARE TRANSACTION) but ships with max_prepared_transactions = 0, and forgotten prepared transactions block VACUUM.
  • Three-phase commit adds a pre-commit phase to reduce blocking but still fails under network partitions. Consensus-based databases (Spanner, CockroachDB) do atomic commits internally; that is a database feature, not something you build across services.

2PC is still fine inside one system boundary that supports it. Across services you own, you choose availability and autonomy and accept eventual consistency.

Saga: a sequence of local transactions

A saga splits the business transaction into steps, each a local ACID transaction in one service. If a step fails, previously completed steps are undone by compensating transactions, which are new forward actions (refund, release), not rollbacks.

#ServiceActionCompensationType
1OrderCreate order as PENDINGMark order CANCELLEDCompensatable
2InventoryReserve items (reserved += qty, with expiry)Release reservationCompensatable
3PaymentCharge customer (idempotency key = order ID)RefundPivot: once it succeeds, the saga goes forward
4InventoryConvert reservation to allocationnone neededRetriable: retried until success
5OrderMark order CONFIRMEDnone neededRetriable

Order the steps so the hardest-to-undo action (charging money) is the pivot, with only retriable steps after it. If payment fails: release inventory, cancel the order. If payment succeeds, nothing after it is allowed to fail permanently; it retries.

Choreography versus orchestration

Choreography

Each service reacts to events and emits its own: OrderCreated → Inventory reserves → InventoryReserved → Payment charges → PaymentCompleted → Order confirms. Failures emit PaymentFailed, which Inventory and Order listen to.

  • + No central component; loose coupling; good for 2–4 steps.
  • − The flow exists only implicitly across services; hard to see the state of one order; cyclic event dependencies creep in.

Orchestration

An orchestrator (often in the Order service) holds the saga state machine and sends commands: ReserveInventory, ChargePayment, and handles replies.

  • + One place to read the flow, add timeouts, see stuck sagas and change step order.
  • − The orchestrator is a component to run and must be persistent and idempotent. Tools: Temporal, Camunda, or a state table plus Kafka.
Order saga orchestratorsaga_instance table→ReserveInventory Inventory→Reserved Orchestrator→ChargePayment Payment→Failed Orchestrator→ReleaseInventory Inventory

Figure: orchestrated saga with a payment failure; the orchestrator runs the compensation for step 2 and then cancels the order.

@Entity
class OrderSaga {
    @Id UUID orderId;
    @Enumerated(EnumType.STRING) SagaState state;   // STARTED, INVENTORY_RESERVED, PAID, COMPENSATING, DONE, FAILED
    Instant deadline;                                // a scheduler times out stuck sagas
    @Version long version;
}

@Service
class OrderSagaOrchestrator {
    @Transactional
    public void on(InventoryReserved evt) {
        OrderSaga saga = sagas.findById(evt.orderId()).orElseThrow();
        if (saga.state != SagaState.STARTED) return;                    // duplicate or late reply: ignore
        saga.state = SagaState.INVENTORY_RESERVED;
        outbox.add("payment-commands", saga.orderId, new ChargePayment(saga.orderId, evt.amount()));
    }

    @Transactional
    public void on(PaymentFailed evt) {
        OrderSaga saga = sagas.findById(evt.orderId()).orElseThrow();
        if (saga.state != SagaState.INVENTORY_RESERVED) return;
        saga.state = SagaState.COMPENSATING;
        outbox.add("inventory-commands", saga.orderId, new ReleaseInventory(saga.orderId));
    }
}

State change and outgoing command commit in one local transaction via the outbox, and every handler checks the current state so duplicate replies are harmless.

Sagas are not isolated

Other requests can see intermediate state (an order that is PENDING, stock that is reserved). Countermeasures: semantic locks (a PENDING status other operations respect), commutative updates (increment/decrement instead of set), reread before acting, and ordering steps so the visible effects of a failed saga are harmless (reserve, do not deduct).

Transactional outbox

Write the event into an outbox table in the same local transaction as the business change. A separate relay publishes outbox rows to Kafka. Either both the order and its event are committed, or neither is.

CREATE TABLE outbox (
  id            UUID PRIMARY KEY,
  aggregatetype VARCHAR(255) NOT NULL,   -- routes to topic, e.g. "order" -> outbox.event.order
  aggregateid   VARCHAR(255) NOT NULL,   -- becomes the Kafka key: per-order ordering
  type          VARCHAR(255) NOT NULL,   -- OrderCreated, OrderCancelled ...
  payload       JSONB        NOT NULL,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
@Service
@RequiredArgsConstructor
class OrderService {
    private final OrderRepository orders;
    private final OutboxRepository outbox;
    private final ObjectMapper json;

    @Transactional
    public Order placeOrder(PlaceOrder cmd) {
        Order order = orders.save(Order.pending(cmd));
        outbox.save(new OutboxEvent(UUID.randomUUID(), "order", order.getId().toString(),
                "OrderCreated", json.valueToTree(OrderCreated.from(order))));
        return order;                                   // one commit: order row + event row
    }
}

Relay option 1: polling publisher

A scheduled job selects unpublished rows ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED, sends them, marks them published. Simple, no extra infrastructure; adds polling latency and DB load; order across pods needs care.

Relay option 2: CDC with Debezium

Debezium reads the database's change log (Postgres logical replication, MySQL binlog) and publishes each inserted outbox row. No polling, low latency, and the application never talks to Kafka. Needs Kafka Connect and replication-slot monitoring.

{
  "name": "orders-outbox",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "plugin.name": "pgoutput",
    "database.hostname": "orders-db", "database.port": "5432",
    "database.user": "debezium", "database.password": "${file:/secrets/db.properties:password}",
    "database.dbname": "orders",
    "topic.prefix": "orders",
    "table.include.list": "public.outbox",
    "tombstones.on.delete": "false",
    "transforms": "outbox",
    "transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter"
  }
}

The EventRouter transform turns each outbox insert into a clean event: topic outbox.event.<aggregatetype>, key aggregateid, value payload. Because Debezium reads the insert from the WAL, you can delete the outbox row in the same transaction (or purge it daily) and the table never grows.

Inbox / idempotent consumer

Outbox relays and Kafka are at-least-once, so every consumer must tolerate duplicates. Record each processed message ID in the same transaction as the side effect:

CREATE TABLE processed_message (
  consumer   VARCHAR(100) NOT NULL,
  message_id UUID         NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, message_id)
);
@KafkaListener(topics = "outbox.event.order", groupId = "inventory")
@Transactional
public void on(ConsumerRecord<String, String> rec) {
    UUID id = UUID.fromString(new String(rec.headers().lastHeader("id").value(), StandardCharsets.UTF_8));
    int inserted = jdbc.update("""
        INSERT INTO processed_message (consumer, message_id) VALUES ('inventory', ?)
        ON CONFLICT DO NOTHING""", id);
    if (inserted == 0) return;                 // duplicate: already applied
    inventory.reserve(parse(rec.value()));     // same transaction as the dedupe row
}

Debezium's outbox router puts the outbox row's id in the id header by default. When the side effect is naturally idempotent (an upsert, a conditional status change), you can skip the table.

Idempotency keys for payments (Kotak, PhonePe)

A client calls POST /payments, times out, and retries. Without protection, the customer is charged twice. The client generates a key once per logical operation (UUID, or the order ID) and sends it on every retry as Idempotency-Key.

CREATE TABLE idempotency_key (
  tenant_id     BIGINT       NOT NULL,
  key           VARCHAR(100) NOT NULL,
  request_hash  CHAR(64)     NOT NULL,           -- SHA-256 of the canonical request body
  status        VARCHAR(20)  NOT NULL,           -- IN_PROGRESS, COMPLETED
  response_code INT,
  response_body JSONB,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, key)
);
public ResponseEntity<PaymentResponse> pay(long tenantId, String key, PaymentRequest req) {
    String hash = sha256(canonicalJson(req));
    Optional<IdemRecord> existing = idem.tryInsertInProgress(tenantId, key, hash);  // INSERT ... ON CONFLICT DO NOTHING
    if (existing.isPresent()) {
        IdemRecord r = existing.get();
        if (!r.requestHash().equals(hash)) return ResponseEntity.unprocessableEntity().build(); // key reused for a different body
        if (r.isInProgress()) return ResponseEntity.status(HttpStatus.CONFLICT).build();       // first attempt still running
        return ResponseEntity.status(r.responseCode()).body(r.responseBody());                  // replay stored result
    }
    PaymentResponse res = paymentService.charge(tenantId, req, key);  // pass the key to the PSP too
    idem.complete(tenantId, key, 201, res);
    return ResponseEntity.status(HttpStatus.CREATED).body(res);
}
  • The unique constraint, not a "check then insert", is what makes two concurrent retries safe.
  • Forward the key (or the payment ID) to the payment gateway, so its side is idempotent as well.
  • Unknown outcome: if the gateway call times out, you do not know whether money moved. Leave the payment PENDING, and let a reconciler query the gateway's status API (or wait for its webhook) before retrying or failing. Never blindly retry a charge that may have succeeded.
  • Expire keys after a window (24 hours is common) and scope them by tenant from the JWT.

CQRS

Command Query Responsibility Segregation: separate the model that handles writes (normalised, validated, transactional) from one or more read models shaped for queries (denormalised tables, Elasticsearch, Redis), kept up to date by events. Use it when read and write shapes differ a lot (a dashboard joining six services' data, search across documents) or when they scale very differently. Cost: the read side is eventually consistent, and you run two models plus a projection pipeline that must be replayable. It is not the same as event sourcing; you can do CQRS with an ordinary database as the write side.

@Service
class PspClient {
    @CircuitBreaker(name = "psp", fallbackMethod = "statusUnknown")
    @Retry(name = "psp")
    @Bulkhead(name = "psp")
    public PaymentResult charge(ChargeRequest req) {
        return restClient.post().uri("/charges")
                .header("Idempotency-Key", req.idempotencyKey())   // retries are safe only because of this
                .body(req).retrieve().body(PaymentResult.class);
    }

    private PaymentResult statusUnknown(ChargeRequest req, Throwable t) {
        return PaymentResult.pending(req.idempotencyKey());          // reconciler resolves it later
    }
}

Resilience4j applies aspects in this default order: Retry( CircuitBreaker( RateLimiter( TimeLimiter( Bulkhead( call ) ) ) ) ), so each retry attempt passes through the breaker and an open breaker stops retries quickly. Set the RestClient connect and read timeouts as well; TimeLimiter only applies to async (CompletableFuture) methods. Spring Framework 7 (Spring Boot 4) also ships core @Retryable and @ConcurrencyLimit annotations, enabled with @EnableResilientMethods, which cover simple retry and bulkhead needs without Resilience4j; it has no circuit breaker.

Distributed tracing

A trace ID created at the edge travels with every hop (HTTP traceparent header per W3C Trace Context; Kafka record headers), and each service records spans. With Spring Boot, add Micrometer Tracing with the OpenTelemetry bridge and an exporter (OTLP to Jaeger, Tempo or a vendor). RestClient and WebClient built from Boot's builders propagate automatically; for Kafka set spring.kafka.template.observation-enabled=true and spring.kafka.listener.observation-enabled=true. Put traceId in every log line and carry tenantId as baggage. For sagas, a trace shows exactly which step of which order stalled.

03How it works internally

How Debezium reads Postgres

  1. Postgres writes every change to the WAL. With wal_level=logical, a logical replication slot decodes WAL into row changes (the pgoutput plugin) for a publication.
  2. Debezium, running in Kafka Connect, streams from the slot, converts each change to an event, and the outbox router reshapes it.
  3. Debezium stores its position (LSN) in Kafka Connect offsets and confirms it to the slot, so Postgres may recycle older WAL.
  4. Delivery is at-least-once: after a crash, Debezium resumes from the last confirmed LSN and can re-emit a few events. Consumers de-duplicate on the event ID.
  5. Ordering per aggregate holds because aggregateid is the Kafka key, and WAL order is commit order.
Replication slot gotcha

If Debezium stops, the slot keeps every WAL segment since its last confirmed position, and the primary's disk fills up. Alert on pg_replication_slots retained WAL, and set max_slot_wal_keep_size to cap it.

Circuit breaker state machine

CLOSEDcalls pass; outcomes recorded→failure rate ≥ 50% OPENcalls fail fast→after 30 s HALF_OPEN5 trial calls→ok: CLOSED / bad: OPEN

Figure: the breaker evaluates only after minimum-number-of-calls, using a count-based or time-based sliding window; slow calls can count as failures.

Open state protects both sides: your threads are freed instantly instead of waiting on timeouts, and the struggling dependency gets breathing room to recover. The half-open state limits the trial traffic so recovery is not met by a full flood.

Why jitter matters

If 1,000 clients fail at the same instant and all retry after 100, 200, 400 ms, they retry in synchronised waves that re-overload the server. Full jitter, sleep = random(0, min(cap, base × 2attempt)), spreads them out; AWS's analysis showed it completes the work with far fewer calls than plain exponential back-off.

04Practical patterns and production gotchas

  • Compensations must be idempotent and retried until they succeed: a refund that fails once cannot simply be logged. Put failed compensations in a DLQ with alerting and a manual-resolution tool.
  • Every saga needs a timeout: a scheduler finds sagas past their deadline and compensates; otherwise lost replies leave orders PENDING forever.
  • Reservations need expiry: inventory holds expire after N minutes so a crashed saga does not lock stock permanently.
  • Do not retry non-idempotent calls: a retry on POST /charges without an idempotency key is a double charge waiting to happen.
  • Retry at one layer only: gateway, service and client each retrying three times gives 27 attempts per click.
  • One breaker per dependency (and per partner, for a gateway with multiple banks), not one global breaker.
  • Fallbacks must not hide data loss: returning "success" from a fallback for a write is a bug. Return "pending" and reconcile.
  • Thread-pool bulkheads lose ThreadLocal context (security context, MDC, tracing) unless you propagate it; prefer semaphore bulkheads for synchronous code.
  • Strangler fig migration (Visa): put a gateway in front of the monolith, route one capability at a time to the new service behind a feature flag, run both with CDC keeping data in sync during the cut-over, canary by tenant, then retire the monolith code path.
  • Know when not to distribute: if two pieces of data must change atomically all the time, they probably belong in one service and one database.

05Interview questions with senior answers

Explain two-phase commit and why you would not use it across microservices.

A coordinator asks every participant to prepare (make the change durable, hold locks, vote); if all vote yes it logs commit and tells everyone to commit, otherwise abort. It is blocking: if the coordinator dies after the votes, participants hold locks in doubt. It couples availability of all services, adds round trips while locks are held, and brokers and third-party APIs cannot participate. Across services I use a saga with an outbox instead.

Data is now split across services. How do transactions work? (Visa)

Each service commits locally; a saga coordinates the business transaction with compensating actions for failures. I prefer orchestration for flows of more than three steps so the state is visible and timeouts live in one place. Steps publish through a transactional outbox, and consumers are idempotent. Consistency is eventual, so the UI shows PENDING states.

Choreography or orchestration?

Choreography for short, stable flows where services naturally react to events (send a welcome email when a user signs up). Orchestration when the flow has many steps, branching, timeouts, or a business owner who asks "where is order 123 stuck?" A persisted state machine (or Temporal) answers that in one query.

What is a compensating transaction and what makes it hard?

A new action that semantically undoes a completed step: refund, release reservation, cancel. Hard parts: some actions cannot be undone (an email was sent, so compensate with a correction email), compensations must be idempotent and retried until success, and other transactions may already have seen the intermediate state. Put the irreversible step last (the pivot).

Why the outbox pattern? Why not publish after commit?

Publishing after commit loses the event if the process dies between commit and send; publishing before commit announces data that may roll back. The outbox makes the event part of the same local transaction, and a relay (polling or Debezium CDC) publishes it at least once. Consumers de-duplicate by event ID.

How do you design an idempotency key for placing an order? (Kotak)

The client generates a UUID per checkout attempt and reuses it on every retry. The server inserts (tenant, key, request hash, IN_PROGRESS) under a unique constraint before doing work; a repeat with a completed record replays the stored response, an in-progress one gets 409, a different body with the same key gets 422. The key is passed downstream to the payment gateway and expires after 24 hours.

The payment gateway timed out. Did the customer pay?

Unknown, so treat it as unknown. Mark the payment PENDING, do not retry with a new key, and resolve by querying the gateway's status API with the same idempotency key or payment ID, or by its webhook. A reconciliation job compares our ledger against the gateway's settlement report daily and flags mismatches.

How does a circuit breaker prevent cascading failure? (Apple)

Without it, a slow dependency makes every caller thread wait for the full timeout, the caller's pool fills, and the caller itself becomes slow for its own callers. The breaker tracks failure and slow-call rates; when they exceed a threshold it opens and fails calls immediately (or serves a fallback), freeing threads. After a wait it lets a few trial calls through and closes if they succeed. Combine with timeouts and a bulkhead.

Retry, circuit breaker, bulkhead: in what order, and why?

Resilience4j defaults to Retry outermost, then CircuitBreaker, RateLimiter, TimeLimiter, Bulkhead. Each retry attempt is counted by the breaker, and once it opens the retries fail fast instead of piling up. Only retry idempotent operations and only on transient errors, with exponential back-off and jitter.

What is CQRS and when is it worth it?

Separate write and read models, the read side built from events. Worth it when queries need data shaped very differently from how it is written, or reads massively outnumber writes and need their own store (search, dashboards). Not worth it for plain CRUD: you take on eventual consistency and a projection pipeline to maintain.

How do you trace one request across five services and Kafka?

W3C trace context propagated in HTTP headers and Kafka record headers, Micrometer Tracing with the OpenTelemetry bridge in every Spring service, spans exported via OTLP, and the trace ID in every log line. The trace waterfall shows which hop added the latency or failed.

How would you migrate a monolith to microservices without downtime? (Visa)

Strangler fig: a gateway in front of the monolith, extract one bounded context at a time, route its traffic to the new service behind a feature flag, keep data in sync with CDC during transition, canary by tenant with rollback, then delete the old path. Start with a low-risk, loosely coupled capability, not the core transaction.

06Hands-on exercise (60 minutes)

  1. In one Spring Boot app with Postgres (three packages standing in for Order, Inventory and Payment), add an outbox table and write OrderService.placeOrder to save the order and an OrderCreated outbox row in one transaction.
  2. Write a @Scheduled polling relay that claims rows with FOR UPDATE SKIP LOCKED, publishes to Kafka, and deletes them. Kill the app between send and delete; restart; confirm the event is re-sent.
  3. Add an Inventory consumer with the processed_message dedupe table. Publish the same event twice and confirm stock is reserved once.
  4. Implement the orchestrated saga state table with the PaymentFailed compensation path. Make payment fail for amounts over 10,000 and check the order ends CANCELLED and stock is released.
  5. Add POST /payments with the idempotency-key flow. Fire the same request concurrently from 10 threads; exactly one charge must be recorded.
  6. Wrap a fake PSP client (WireMock with a 5-second delay) in Resilience4j circuit breaker + retry + bulkhead. Watch /actuator/circuitbreakers move from CLOSED to OPEN to HALF_OPEN.
