Distributed transactions and resilience

Sometimes one business action touches several services, each with its own database. This lesson shows how to keep the data correct when that happens. It also shows how to stop one slow service from slowing down all the others.

Study time: 5–6 hours Exercise: 60 min Spring Boot Seen in: HM rounds, HLD deep dives, payments interviews
FlipkartVisaAppleZeptoKotakPhonePeAngel One
In 30 seconds
  • If you save to a database and then send to Kafka as two separate steps, one of them will fail someday.
  • Use a saga: small local steps, each with an "undo" action. Avoid two-phase commit across services.
  • Save events in an outbox table. Make every reader safe against getting the same message twice.
  • Timeouts, smart retries, circuit breakers and bulkheads stop one failure from spreading.
Picture it

You are booking a Goa trip: a train, a hotel and a cab. Each comes from a different company. Nobody can lock all three for you at the same moment. So you book them one at a time. If the cab booking fails, you cancel the hotel and the train ticket. Those cancellations are called compensations. A cancellation is a new action with its own rules, like a cancellation fee. It is not a magic undo button.

Words you'll see
Transaction
A group of database changes that all succeed together or all fail together. You never see half of it.
Saga
A long business action split into small steps. Each step commits on its own. If a later step fails, earlier steps are undone by new "undo" actions.
Compensation
The "undo" action for a saga step, such as a refund for a charge. It is a new action, not a rollback.
Outbox
A table in your own database where you save the events you want to send. Another process sends them to Kafka later.
Idempotent
Doing the same thing twice has the same effect as doing it once. Pressing "Pay" twice should charge you once.
Eventually consistent
Different services may disagree for a short time, but they all reach the same correct state soon.
Circuit breaker
A switch in your code. It stops calling a service that keeps failing, and tries again later.
Bulkhead
A limit on how many threads one dependency can use, so one slow service cannot use up all your threads.

The senior answer in one breath

Each service owns its own data and commits changes locally. Across services, the data becomes consistent a little later, not instantly. A saga does this with local steps and "undo" actions for failures. Events go out through an outbox table. Readers ignore duplicate messages. The API uses idempotency keys so a retry never charges twice. Timeouts, retries with random delays, circuit breakers and bulkheads stop failures from spreading.

This is called a "dual write": writing to two systems that do not share one transaction. One of the two writes can always be lost. The rest of this page shows ways around that.

Two-phase commit, and why microservices avoid it (Zepto)

Two-phase commit (2PC) is a protocol that tries to make several databases commit together. One "coordinator" asks everyone to get ready, then tells everyone to commit.

  1. CoordinatorAsks the Order DB and Payment DB to get ready (PREPARE)
  2. ParticipantsEach saves the change, locks the rows, and votes "yes, I can commit"
  3. CoordinatorWrites down the decision
  4. CoordinatorTells everyone to commit (COMMIT) → each one unlocks its rows

2PC (XA)

  • All databases commit together, or none do
  • Everyone gets stuck if the coordinator dies after the votes
  • Uptime multiplies down: three services at 99.9% give at most 99.7%
  • Kafka, NoSQL stores and payment APIs cannot take part

Only inside one system that supports it.

Saga across services

  • Each step is a normal local transaction
  • No locks held across services
  • Data is correct only after a short delay, and you must write "undo" steps

Services you own, each with its own database.

Go deeper: dual writes and 2PC in full

Say the Kafka send succeeds but the database commit fails. Other services now act on an order that does not exist. Now say the commit succeeds, but the pod dies before the send. The order exists, but nobody hears about it. Moving the send after the commit only changes which failure you get. Whenever code writes to two systems without a shared transaction, one write can be lost. Everything on this page is a way around that.

Coordinator→1. get ready (PREPARE) Order DBsaves, locks rows, votes yes Payment DBsaves, locks rows, votes yes→2. writes down the decision Coordinator→3. tells all to commit Everyone unlocks their rows

Figure: 2PC. In phase 1 (prepare and vote), each database saves the change safely and promises it can commit. In phase 2 (commit or abort), the coordinator writes down the result and then tells everyone.

  • Blocking: a database that voted YES cannot decide on its own. If the coordinator crashes after the votes, the databases wait "in doubt". They keep holding row locks until the coordinator comes back.
  • Uptime multiplies down: every participant must be up. Three services at 99.9% uptime give at most 99.7% together.
  • Slowness and lock time: two network round trips happen while locks are held. On busy rows, this kills throughput.
  • Support: Kafka, most NoSQL stores and outside APIs (like a payment gateway) cannot join an XA transaction. XA is the standard 2PC protocol. PostgreSQL supports it with PREPARE TRANSACTION, but ships with max_prepared_transactions = 0 (turned off). Forgotten prepared transactions also block VACUUM, Postgres's cleanup job.
  • Three-phase commit adds an extra "pre-commit" step to reduce blocking. It still fails when the network splits. Databases built on consensus, like Spanner and CockroachDB, do atomic commits inside themselves. That is a database feature, not something you build across services.

2PC is still fine inside one system that supports it. Across services you own, you pick uptime and independence. In return, you accept that data becomes consistent a little later.

Show Java: OrderSaga state machine
@Entity
class OrderSaga {
    @Id UUID orderId;
    @Enumerated(EnumType.STRING) SagaState state;   // STARTED, INVENTORY_RESERVED, PAID, COMPENSATING, DONE, FAILED
    Instant deadline;                                // a scheduler times out stuck sagas
    @Version long version;
}

@Service
class OrderSagaOrchestrator {
    @Transactional
    public void on(InventoryReserved evt) {
        OrderSaga saga = sagas.findById(evt.orderId()).orElseThrow();
        if (saga.state != SagaState.STARTED) return;                    // duplicate or late reply: ignore
        saga.state = SagaState.INVENTORY_RESERVED;
        outbox.add("payment-commands", saga.orderId, new ChargePayment(saga.orderId, evt.amount()));
    }

    @Transactional
    public void on(PaymentFailed evt) {
        OrderSaga saga = sagas.findById(evt.orderId()).orElseThrow();
        if (saga.state != SagaState.INVENTORY_RESERVED) return;
        saga.state = SagaState.COMPENSATING;
        outbox.add("inventory-commands", saga.orderId, new ReleaseInventory(saga.orderId));
    }
}

Sagas are not isolated

Other requests can see PENDING orders and held stock. Protect against this with status flags others respect, add-or-subtract updates, and reading fresh data before acting.

Every saga needs a timeout

A scheduled job undoes sagas that pass their deadline. Without it, a lost reply leaves an order PENDING forever.

Go deeper: the step table, choreography vs orchestration, isolation

A saga splits one business action into steps. Each step is a normal local transaction in one service. If a step fails, the earlier steps are undone by compensating transactions. These are new forward actions, like a refund or a stock release. They are not database rollbacks.

#ServiceActionCompensationType
1OrderCreate order as PENDINGMark order CANCELLEDCan be undone
2InventoryHold items (reserved += qty, with an expiry)Release the holdCan be undone
3PaymentCharge the customer (idempotency key = order ID)RefundPivot: once it succeeds, the saga only goes forward
4InventoryTurn the hold into a real allocationnone neededRetriable: retried until it succeeds
5OrderMark order CONFIRMEDnone neededRetriable

Order the steps so the hardest action to undo becomes the pivot. Here that is charging money. Only retriable steps come after it. If payment fails, release the stock and cancel the order. If payment succeeds, nothing after it may fail for good. It just retries.

Choreography

Each service listens for events and sends its own. The chain is OrderCreated → Inventory holds stock → InventoryReserved → Payment charges → PaymentCompleted → Order confirms. On failure, Payment sends PaymentFailed. Inventory and Order listen for it.

  • + No central boss. Services stay loosely linked. Good for 2–4 steps.
  • − The flow lives nowhere in one place. One order's state is hard to see. Circular event dependencies creep in.

Orchestration

An orchestrator, often inside the Order service, holds the saga's state machine. It sends commands like ReserveInventory and ChargePayment, and it handles the replies.

  • + One place to read the flow, add timeouts, spot stuck sagas and change step order.
  • − The orchestrator is one more thing to run. It must save its state and be safe to repeat. Tools: Temporal, Camunda, or a state table plus Kafka.
Order saga orchestratortracks progress in a table→hold stock Inventory→held Orchestrator→charge Payment→failed Orchestrator→release stock Inventory

Figure: an orchestrated saga where payment fails. The orchestrator undoes step 2 and then cancels the order.

The state change and the next command are saved in one local transaction, using the outbox. Every handler checks the current state first. So a duplicate reply does no harm.

Sagas are not isolated

Other requests can see the in-between state, like a PENDING order or held stock. There are four defences. Semantic locks are a PENDING status that other operations respect. Commutative updates add or subtract instead of overwriting a value. Reread before acting means fetching fresh data first. Finally, order the steps so a failed saga leaves only harmless traces (hold stock, do not remove it).

The fix for dual writes is simple. Save the event in an outbox table, in the same transaction as the order. A separate "relay" process later reads that table and sends the events to Kafka.

CREATE TABLE outbox (
  id            UUID PRIMARY KEY,
  aggregatetype VARCHAR(255) NOT NULL,   -- routes to topic, e.g. "order" -> outbox.event.order
  aggregateid   VARCHAR(255) NOT NULL,   -- becomes the Kafka key: per-order ordering
  type          VARCHAR(255) NOT NULL,   -- OrderCreated, OrderCancelled ...
  payload       JSONB        NOT NULL,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);
Show Java: OrderService writing the outbox
@Service
@RequiredArgsConstructor
class OrderService {
    private final OrderRepository orders;
    private final OutboxRepository outbox;
    private final ObjectMapper json;

    @Transactional
    public Order placeOrder(PlaceOrder cmd) {
        Order order = orders.save(Order.pending(cmd));
        outbox.save(new OutboxEvent(UUID.randomUUID(), "order", order.getId().toString(),
                "OrderCreated", json.valueToTree(OrderCreated.from(order))));
        return order;                                   // one commit: order row + event row
    }
}

Go deeper: outbox relays and the inbox pattern in full

Write the event into an outbox table in the same local transaction as the business change. A separate relay sends outbox rows to Kafka. Either both the order and its event are saved, or neither is.

Relay option 1: polling publisher

A scheduled job picks unsent rows with ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED. It sends them and marks them sent. It is simple and needs nothing extra. It adds polling delay and database load. Keeping order across several pods needs care.

Relay option 2: CDC with Debezium

CDC means change data capture. Debezium reads the database's change log (Postgres logical replication or the MySQL binlog). It sends each new outbox row to Kafka. There is no polling, delay is low, and your app never talks to Kafka. You need Kafka Connect and must watch the replication slot.

The EventRouter transform turns each outbox insert into a clean event. The topic is outbox.event.<aggregatetype>. The key is aggregateid. The value is payload. Debezium reads the insert from the WAL (write-ahead log, Postgres's record of every change). So you can delete the outbox row in the same transaction, or clear it daily. The table never grows.

Outbox relays and Kafka are "at-least-once". That means a message is never lost, but it can arrive twice. So every reader must handle duplicates. Save each handled message ID in the same transaction as the real work.

Debezium's outbox router puts the outbox row's id in the id message header by default. Sometimes the work is already safe to repeat, like an upsert or a "set status only if still PENDING" update. Then you can skip the table.

05Idempotency keys for payments

A customer taps "Pay" in a UPI app. The request times out, so the app sends it again. Without protection, the customer pays twice. An idempotency key stops this. It is one ID per payment attempt, sent with every retry.

TimeRetry 1Retry 2 (same key)idempotency_key
t1saves the key as "in progress"1 row
t2tries to save the same keyrejected as a duplicate (HTTP 409), no charge
t3charges via the payment gateway, saves the replydone (COMPLETED)
t4retry againgets the saved reply, no new charge
CREATE TABLE idempotency_key (
  tenant_id     BIGINT       NOT NULL,
  key           VARCHAR(100) NOT NULL,
  request_hash  CHAR(64)     NOT NULL,           -- SHA-256 of the canonical request body
  status        VARCHAR(20)  NOT NULL,           -- IN_PROGRESS, COMPLETED
  response_code INT,
  response_body JSONB,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, key)
);
Show Java: the pay() endpoint
public ResponseEntity<PaymentResponse> pay(long tenantId, String key, PaymentRequest req) {
    String hash = sha256(canonicalJson(req));
    Optional<IdemRecord> existing = idem.tryInsertInProgress(tenantId, key, hash);  // INSERT ... ON CONFLICT DO NOTHING
    if (existing.isPresent()) {
        IdemRecord r = existing.get();
        if (!r.requestHash().equals(hash)) return ResponseEntity.unprocessableEntity().build(); // key reused for a different body
        if (r.isInProgress()) return ResponseEntity.status(HttpStatus.CONFLICT).build();       // first attempt still running
        return ResponseEntity.status(r.responseCode()).body(r.responseBody());                  // replay stored result
    }
    PaymentResponse res = paymentService.charge(tenantId, req, key);  // pass the key to the PSP too
    idem.complete(tenantId, key, 201, res);
    return ResponseEntity.status(HttpStatus.CREATED).body(res);
}

Constraint, not check

A unique constraint in the database makes two retries at the same moment safe. "Check first, then insert" does not, because both can pass the check.

Forward the key

Send the same key to the payment gateway too, so its side is also safe to retry.

Unknown outcome

Did the gateway time out? Keep the payment PENDING. A reconciler job asks the gateway what happened. Never blindly retry a charge.

Go deeper: idempotency keys in full

A client calls POST /payments, times out, and tries again. Without protection, the customer is charged twice. The client creates one key per logical payment, such as a UUID or the order ID. It sends that key on every retry in the Idempotency-Key header.

  • The unique constraint makes two retries at the same moment safe. A "check, then insert" does not.
  • Pass the key (or the payment ID) on to the payment gateway, so its side is safe to repeat as well.
  • Unknown outcome: if the gateway call times out, you do not know if money moved. Leave the payment PENDING. A reconciler job asks the gateway's status API, or waits for its webhook (a callback it sends you). Only then do you retry or fail. Never blindly retry a charge that may have worked.
  • Delete keys after a time window; 24 hours is common. Scope them by tenant, taken from the JWT login token.

06Resilience: timeouts, retries, breakers

A circuit breaker works like the fuse box at home. When a service keeps failing, the breaker "opens" and stops calls to it for a while. That protects your own threads and gives the failing service time to recover.

Normal (CLOSED)calls go through and results are counted→half or more fail Blocked (OPEN)calls fail at once, no waiting→after 30 seconds Testing (HALF_OPEN)lets 5 trial calls through→if they work, back to normal; if not, blocked again

Figure: the breaker judges only after a minimum number of calls (minimum-number-of-calls). It looks at the last N calls or the last N seconds. Slow calls can count as failures too.

BulkheadOne service using up all your threadsMax calls in flight at once

@Service
class PspClient {
    @CircuitBreaker(name = "psp", fallbackMethod = "statusUnknown")
    @Retry(name = "psp")
    @Bulkhead(name = "psp")
    public PaymentResult charge(ChargeRequest req) {

                .header("Idempotency-Key", req.idempotencyKey())   // retries are safe only because of this
                .body(req).retrieve().body(PaymentResult.class);
    }

    private PaymentResult statusUnknown(ChargeRequest req, Throwable t) {
        return PaymentResult.pending(req.idempotencyKey());          // reconciler resolves it later
    }
}

Resilience4j wraps your call in this order by default: Retry( CircuitBreaker( RateLimiter( TimeLimiter( Bulkhead( call ) ) ) ) ). So every retry passes through the breaker. Once the breaker opens, retries stop quickly. Also set the connect and read timeouts on RestClient. TimeLimiter only works on async methods that return a CompletableFuture. Spring Framework 7 (Spring Boot 4) adds built-in @Retryable and @ConcurrencyLimit annotations. You turn them on with @EnableResilientMethods. They cover simple retries and bulkheads without Resilience4j. They have no circuit breaker.

The open state protects both sides. Your threads are freed at once instead of waiting for timeouts. The struggling service gets room to recover. The half-open state lets only a few trial calls through. So a recovering service is not hit by a full flood.

Why jitter matters

Say 1,000 clients fail at the same moment. They all retry after 100, then 200, then 400 ms. They retry in waves that overload the server again. "Full jitter" picks a random wait: sleep = random(0, min(cap, base × 2attempt)). That spreads the retries out. AWS measured it. It finished the same work with far fewer calls than plain exponential back-off.

07Debezium, CQRS and tracing

  1. PostgresWrites every change to its change log (the WAL) → a reader bookmark (replication slot) turns it into row changes
  2. DebeziumReads those changes → turns each new outbox row into a clean Kafka event
  3. DebeziumRemembers how far it has read (its position, called the LSN) → Postgres can delete older log files
  4. CrashRestarts from the last saved position → a few events are sent twice, so readers must skip duplicates
Replication slot gotcha

If Debezium stops, the slot keeps every WAL file since its last confirmed position. The main database's disk then fills up. Alert on retained WAL in pg_replication_slots. Set max_slot_wal_keep_size to put a cap on it.

CQRS

Keep the write model separate from read models (like Elasticsearch or Redis) that events keep updated. Reads may lag a little. This is not the same as event sourcing.

Tracing

Pass a W3C traceparent header on HTTP calls and Kafka messages. Use Micrometer Tracing with OpenTelemetry. It shows which saga step got stuck.

Go deeper: Debezium internals, CQRS and tracing in full
  1. Postgres writes every change to the WAL, its write-ahead log. With wal_level=logical, a logical replication slot turns the WAL into row changes for a publication, using the pgoutput plugin.
  2. Debezium runs inside Kafka Connect. It reads from the slot and turns each change into an event. The outbox router then reshapes it.
  3. Debezium saves its position (the LSN, a pointer into the log) in Kafka Connect offsets. It confirms that position to the slot, so Postgres can recycle older WAL.
  4. Delivery is at-least-once. After a crash, Debezium restarts from the last confirmed LSN and may send a few events again. Readers ignore duplicates using the event ID.
  5. Events for one order stay in order. That is because aggregateid is the Kafka key, and WAL order is commit order.

CQRS stands for Command Query Responsibility Segregation. It means you keep one model for writes and separate models for reads. The write model is normalised, validated and transactional. The read models are shaped for queries, like flat tables, Elasticsearch or Redis. Events keep them up to date. Use it when reads and writes look very different. One example is a dashboard joining data from six services. Another is search across documents. It also helps when reads and writes grow at very different speeds. The cost: reads may lag a little behind writes. You also run two models plus a pipeline that copies data between them, and that pipeline must be able to replay. CQRS is not event sourcing. A normal database can be the write side.

A trace ID is created when a request first arrives. It travels with every hop: in the HTTP traceparent header (the W3C Trace Context standard) and in Kafka record headers. Each service records "spans", which are timed pieces of work. In Spring Boot, add Micrometer Tracing with the OpenTelemetry bridge and an exporter (OTLP to Jaeger, Tempo or a vendor). RestClient and WebClient built from Boot's builders pass the trace on automatically. For Kafka, set spring.kafka.template.observation-enabled=true and spring.kafka.listener.observation-enabled=true. Put traceId in every log line. Carry tenantId as "baggage", extra data that travels with the trace. For sagas, a trace shows exactly which step of which order got stuck.

08Production gotchas

Common mistakes
  • An "undo" step fails once and is only logged. It must retry, or go to a DLQ (a parking area for failed messages).
  • Stock holds with no expiry. Sagas with no timeout.
  • Retrying POST /charges with no idempotency key.
  • Retries at every layer, which makes 27 calls from one click.
  • One global breaker instead of one per dependency.
  • A fallback for a write that returns "success".
Go deeper: all production rules, bulkheads, strangler fig
  • "Undo" steps must be safe to repeat and retried until they work: a refund that fails once cannot just be logged. Put failed undo steps in a DLQ (dead-letter queue, a parking area for failed messages). Add alerts and a tool to fix them by hand.
  • Every saga needs a timeout: a scheduled job finds sagas past their deadline and undoes them. Otherwise lost replies leave orders PENDING forever.
  • Stock holds need an expiry: holds expire after N minutes. So a crashed saga does not lock stock forever.
  • Do not retry calls that are unsafe to repeat: retrying POST /charges without an idempotency key is a double charge waiting to happen.
  • Retry at one layer only: if the gateway, the service and the client each retry three times, one click makes 27 calls.
  • One breaker per dependency: and one per partner bank, for a gateway with many banks. Never one global breaker.
  • Fallbacks must not hide lost data: returning "success" from a fallback for a write is a bug. Return "pending" and reconcile later.
  • Thread-pool bulkheads lose ThreadLocal data: the security context, MDC log fields and tracing are lost unless you pass them on. For normal blocking code, prefer semaphore bulkheads.
  • Strangler fig migration (Visa): put a gateway in front of the monolith. Move one feature at a time to a new service, behind a feature flag. Run both, and keep the data in sync with CDC during the switch. Roll out to a few tenants first (a canary). Then delete the old monolith code.
  • Know when not to split: if two pieces of data must always change together, they probably belong in one service and one database.

09Quick check

Why not just call kafkaTemplate.send() after the database commit?

These are two systems with no shared transaction. The outbox makes the event part of the same database commit, so it cannot be lost.

In an order saga, which step should be the pivot (the point of no return)?

The hardest action to undo should come last among the undo-able steps. Only steps that can simply be retried come after it.

The call to the payment gateway times out. What should the service do?

You do not know if money moved. A blind retry can charge the customer twice. So wait, and ask the gateway.

Why does 2PC hurt uptime across microservices?

Uptime multiplies down, because every service must be up. A crashed coordinator also leaves the others waiting while holding locks.

10Interview questions with senior answers

Explain two-phase commit and why you would not use it across microservices.

A coordinator asks every participant to prepare. Preparing means saving the change safely, holding locks and voting. If all vote yes, the coordinator logs "commit" and tells everyone to commit. Otherwise it aborts. It is blocking: if the coordinator dies after the votes, participants hold locks "in doubt". It ties every service's uptime together. It adds round trips while locks are held. Message brokers and outside APIs cannot take part. Across services, I use a saga with an outbox instead.

Data is now split across services. How do transactions work? (Visa)

Each service commits locally. A saga coordinates the whole business action, with compensating ("undo") actions for failures. For flows of more than three steps, I prefer orchestration. The state is visible and timeouts live in one place. Steps send events through a transactional outbox, and readers are idempotent (safe against duplicates). Consistency is eventual, so the UI shows PENDING states.

Choreography or orchestration?

Choreography fits short, stable flows where services naturally react to events. An example is sending a welcome email when a user signs up. Orchestration fits flows with many steps, branches or timeouts. It also fits when a business owner asks "where is order 123 stuck?" A saved state machine, or Temporal, answers that in one query.

What is a compensating transaction and what makes it hard?

It is a new action that undoes the meaning of a finished step: a refund, a stock release, a cancel. There are three hard parts. Some actions cannot be undone; if an email was sent, you send a correction email. Compensations must be idempotent and retried until they work. Other transactions may already have seen the in-between state. Put the step you cannot undo last; that is the pivot.

Why the outbox pattern? Why not publish after commit?

If you publish after commit, the event is lost when the process dies between commit and send. If you publish before commit, you announce data that may roll back. The outbox makes the event part of the same local transaction. A relay (polling or Debezium CDC) then sends it at least once. Readers drop duplicates using the event ID.

How do you design an idempotency key for placing an order? (Kotak)

The client creates a UUID for each checkout attempt and reuses it on every retry. Before doing any work, the server inserts (tenant, key, request hash, IN_PROGRESS) under a unique constraint. A repeat that finds a completed record gets the stored response again. A repeat that finds one still in progress gets 409. The same key with a different body gets 422. The key is passed on to the payment gateway and expires after 24 hours.

The payment gateway timed out. Did the customer pay?

We do not know, so treat it as unknown. Mark the payment PENDING. Do not retry with a new key. Find out by asking the gateway's status API with the same idempotency key or payment ID, or wait for its webhook. Every day, a reconciliation job compares our ledger with the gateway's settlement report. It flags any mismatch.

How does a circuit breaker prevent cascading failure? (Apple)

Without one, a slow dependency makes every caller thread wait for the full timeout. The caller's thread pool fills up. Then the caller becomes slow for its own callers, and the failure spreads. The breaker tracks the failure rate and slow-call rate. Above a threshold it opens and fails calls at once, or serves a fallback. That frees threads. After a wait, it lets a few trial calls through. If they succeed, it closes. Use it together with timeouts and a bulkhead.

Retry, circuit breaker, bulkhead: in what order, and why?

By default, Resilience4j puts Retry on the outside. Then come CircuitBreaker, RateLimiter, TimeLimiter and Bulkhead. So the breaker counts every retry attempt. Once it opens, retries fail fast instead of piling up. Only retry calls that are safe to repeat, and only on temporary errors. Use exponential back-off with jitter (random waits).

What is CQRS and when is it worth it?

CQRS keeps separate models for writes and reads. The read side is built from events. It is worth it when queries need data shaped very differently from how it is written. It also helps when reads far outnumber writes and need their own store, such as search or dashboards. It is not worth it for plain CRUD. You take on eventual consistency and a copy pipeline to maintain.

How do you trace one request across five services and Kafka?

Pass the W3C trace context in HTTP headers and Kafka record headers. Add Micrometer Tracing with the OpenTelemetry bridge to every Spring service. Export spans over OTLP. Put the trace ID in every log line. The trace "waterfall" view then shows which hop added the delay or failed.

How would you migrate a monolith to microservices without downtime? (Visa)

Use the strangler fig pattern. Put a gateway in front of the monolith. Pull out one bounded context (one business area) at a time. Send its traffic to the new service behind a feature flag. Keep data in sync with CDC during the switch. Roll out to a few tenants first, with a way to roll back. Then delete the old path. Start with a low-risk, loosely linked feature, not the core payment flow.

11Cheat sheet

Cheat sheet
  • Writing to a database and Kafka separately will lose one write someday. Use an outbox.
  • 2PC blocks, lowers uptime, and many systems cannot join it. Avoid it across services.
  • Saga: one local transaction per step, undo steps in reverse. The charge is the pivot, and only retriable steps follow it.
  • Use choreography for 2–4 steps. Use orchestration for longer flows.
  • Outbox relay: polling with SKIP LOCKED, or Debezium CDC. With Debezium, watch the replication slot.
  • Readers drop duplicates by event ID, in the same transaction as the work.
  • Use an Idempotency-Key with a unique constraint. If the outcome is unknown, mark PENDING and reconcile.
  • Timeouts, retries with jitter at one layer only, one breaker per dependency, and bulkheads.
