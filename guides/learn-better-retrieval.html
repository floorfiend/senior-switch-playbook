01The five upgrades, in the order to add them

1. Hybrid search

Vector search finds meaning; keyword search finds exact tokens like "Clause 14.2". Run both, merge by rank.

2. Rerank

A slow, accurate cross-encoder re-orders the top 20–50 candidates.

3. Contextual retrieval

At ingestion, Claude writes 50–100 tokens of context for each chunk. Cuts retrieval failures by up to 67% with reranking.

4. Query rewriting

"What about the other one?" becomes a standalone, contract-vocabulary query via a cheap model.

5. Permissions + multi-hop

Tenant and ACL filters live in the SQL. Multi-part questions get decomposed, with a hop limit.

Go deeper: setup details and why order matters

Hands-on setup: start from the contract_chunks table of the pgvector lesson and run uv pip install "psycopg[binary]" pgvector voyageai anthropic numpy. The contract_chunks table already has content_tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED and a GIN index on it. Every Python file below compiles with python -m py_compile; the SQL was run against pgvector/pgvector:pg18-trixie.

The order to add upgrades is by return on effort: hybrid (cheap, big win on exact terms), then reranking, then contextual retrieval (an ingestion cost), then rewriting for chat, then multi-hop only if your golden set has such questions.

02Hybrid search and reciprocal rank fusion

Vector search

  • "get out of the deal early" matches "termination for convenience"
  • Blurs exact tokens: clause numbers, defined terms, party names, invoice IDs

Keyword search (BM25 / ts_rank_cd)

  • Nails "Section 73 of the Indian Contract Act"
  • Misses paraphrases

Each fails where the other succeeds, so run both. Their scores are on different scales (cosine distance vs ts_rank_cd), so merge by rank with RRF:

RRF(d) = Σ over result lists  1 / (k + rank_in_that_list(d))        k = 60 by convention
Merge two ranked lists with RRF (k = 60)

Why k = 60: it damps the gap between rank 1 and rank 5 so no single list dominates. Think of it as merging two sorted feeds by vote instead of comparing raw scores.

Show SQL: hybrid search with RRF
WITH semantic AS (
    SELECT id, RANK() OVER (ORDER BY embedding <=> '[0.9,0.1,0.0]') AS rank
    FROM contract_chunks
    WHERE tenant_id = 'acme'
    ORDER BY embedding <=> '[0.9,0.1,0.0]'
    LIMIT 20
),
keyword AS (
    SELECT id, RANK() OVER (ORDER BY ts_rank_cd(content_tsv, q) DESC) AS rank
    FROM contract_chunks, websearch_to_tsquery('english', 'terminate notice') q
    WHERE tenant_id = 'acme' AND content_tsv @@ q
    ORDER BY ts_rank_cd(content_tsv, q) DESC
    LIMIT 20
)
SELECT COALESCE(s.id, k.id) AS id,
       round((COALESCE(1.0 / (60 + s.rank), 0.0) + COALESCE(1.0 / (60 + k.rank), 0.0))::numeric, 5) AS rrf_score
FROM semantic s
FULL OUTER JOIN keyword k ON s.id = k.id
ORDER BY rrf_score DESC
LIMIT 5;

-- ----+-----------

Show Python: the same query, parameterised and tenant-filtered
import numpy as np
import psycopg

HYBRID_SQL = """
WITH semantic AS (
    SELECT id, RANK() OVER (ORDER BY embedding <=> %(qvec)s) AS rank
    FROM contract_chunks
    WHERE tenant_id = %(tenant)s
    ORDER BY embedding <=> %(qvec)s
    LIMIT 40
),
keyword AS (
    SELECT id, RANK() OVER (ORDER BY ts_rank_cd(content_tsv, q) DESC) AS rank
    FROM contract_chunks, websearch_to_tsquery('english', %(qtext)s) q
    WHERE tenant_id = %(tenant)s AND content_tsv @@ q
    ORDER BY ts_rank_cd(content_tsv, q) DESC
    LIMIT 40
)
SELECT c.id, c.source, c.page, c.content,
       COALESCE(1.0 / (%(k)s + s.rank), 0.0) + COALESCE(1.0 / (%(k)s + kw.rank), 0.0) AS rrf
FROM semantic s
FULL OUTER JOIN keyword kw ON s.id = kw.id
JOIN contract_chunks c ON c.id = COALESCE(s.id, kw.id)
ORDER BY rrf DESC
LIMIT %(limit)s
"""


def hybrid_search(conn: psycopg.Connection, tenant_id: str, question: str, qvec: np.ndarray,
                  limit: int = 20, k: int = 60) -> list[tuple]:
    """tenant_id must come from the verified JWT, never from the request body."""
    with conn.transaction():
        conn.execute("SET LOCAL hnsw.iterative_scan = relaxed_order")  # tenant filter shrinks HNSW results
        return conn.execute(HYBRID_SQL, {"qvec": qvec, "qtext": question, "tenant": tenant_id,
                                         "k": k, "limit": limit}).fetchall()

The FULL OUTER JOIN keeps chunks found by only one leg; COALESCE(..., 0.0) gives them zero from the missing leg. websearch_to_tsquery accepts user-style input (quotes, or, -) without throwing syntax errors, which to_tsquery would.

I ran the Python version against the container with a second tenant's row inserted: only the acme rows came back. Each leg fetches 40, so the reranker has 20–40 candidates to work with.

Postgres full-text vs real BM25

ts_rank_cd is not BM25: it ranks by term frequency and proximity and has no inverse document frequency, so rare terms are not boosted the way BM25 boosts them. For clause-number and defined-term matching it still captures most of the benefit with no new infrastructure. If keyword quality becomes the bottleneck, a BM25 extension or OpenSearch is the upgrade; measure first.

03Reranking: bi-encoder vs cross-encoder

Bi-encoder (embeddings)

  • Document vectors precomputed once; ANN search over millions is fast
  • Never sees query and document together: misses "liability is not capped"

Stage 1: retrieve top 50 from millions.

Cross-encoder (reranker) stage 2

  • Attention across query and document: much more accurate
  • One model pass per (query, candidate) pair; nothing precomputed

Stage 2: rerank top 20–100 down to 5.

Java analogy: the bi-encoder is a precomputed hashCode(); the cross-encoder is an expensive equals() you only call on the shortlist.

import voyageai

vo = voyageai.Client()


def rerank(question: str, candidates: list[dict], top_k: int = 5) -> list[dict]:
    """candidates: dicts with a 'content' key, already tenant-filtered by the SQL."""
    result = vo.rerank(question, [c["content"] for c in candidates], model="rerank-3-lite", top_k=top_k)
    return [candidates[r.index] | {"rerank_score": r.relevance_score} for r in result.results]
Go deeper: model choices and budget

Query and document are encoded separately by a bi-encoder; relevance is a dot product. A cross-encoder puts query and one document together through the transformer and outputs one relevance score, so you only run it on the top 20–100 from the first stage. Retrieve wide and cheap, rerank narrow and expensive.

rerank-3 is Voyage's highest-accuracy reranker, rerank-3-lite the latency/cost option. Each result carries index (position in your list), document and relevance_score. Self-hosted alternative: a cross-encoder such as cross-encoder/ms-marco-MiniLM-L-6-v2 through sentence-transformers, which is what pgvector-python's hybrid example uses. Budget: rerank 20–50 candidates, not 500; the cost grows linearly with the number of pairs. Rerank only the tenant-filtered candidates; never send another tenant's text to any model.

04Query rewriting

  1. History"We're looking at the Infosys MSA"
  2. User"can they walk away early?" (embedding this retrieves noise)
  3. HaikuReturns a SearchPlan: rewritten_query "termination for convenience rights of the vendor in the Infosys MSA", keywords ["terminate", "convenience", "notice"], sub_questions []
  4. Retrievalrewritten_query feeds the vector leg; " ".join(keywords) feeds websearch_to_tsquery

Cost: about a tenth of a cent and a few hundred ms per query. Skip it for standalone questions.

Show Python: plan_search with structured output
import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic()


class SearchPlan(BaseModel):
    rewritten_query: str          # standalone, legal vocabulary, no pronouns
    keywords: list[str]           # exact terms for the full-text leg
    sub_questions: list[str]      # empty unless the question needs several lookups


REWRITE_SYSTEM = """You turn a user's question about their contracts into a search plan.
Resolve pronouns using the chat history. Use contract vocabulary
(e.g. "get out of the deal" -> "termination for convenience").
Only split into sub_questions when one search cannot answer it."""


def plan_search(question: str, history: str = "") -> SearchPlan:
    resp = client.messages.parse(
        model="claude-haiku-4-5-20251001",  # cheap and fast: this runs on every query
        max_tokens=400,
        system=REWRITE_SYSTEM,
        messages=[{"role": "user", "content": f"<history>{history}</history>\n<question>{question}</question>"}],
        output_format=SearchPlan,
    )
    return resp.parsed_output
Go deeper: what the rewriter does, variants

Users write "and what about the other one?" in turn five of a chat. A cheap model (Haiku) rewrites it into a standalone query using the chat history, maps lay language to contract vocabulary, extracts exact keywords for the full-text leg, and, if needed, splits it into sub-questions. Variants: multi-query (several paraphrases, fused with RRF) and HyDE (embed a hypothetical answer instead of the question).

messages.parse with a Pydantic model returns a validated object in resp.parsed_output (the SDK converts the model to a JSON schema and checks the response). Cost: one Haiku call of a few hundred tokens, so roughly a tenth of a cent and a few hundred milliseconds. Skip it for the first turn if the question is already standalone.

05Contextual retrieval

5.7%top-20 failure, baseline embeddings
3.7%contextual embeddings (−35%)
2.9%+ contextual BM25 (−49%)
1.9%+ reranking (−67%)
$1.02per million document tokens, one-off
  • Problem: "The Supplier's liability … shall not exceed the fees paid" names no contract or supplier.
  • Fix: before embedding and BM25 indexing, Claude writes 50–100 tokens of context per chunk, given the whole document, and prepends it.
  • Cost control: the document is identical for all its chunks, so prompt caching makes chunks 2..N cheap.
  • Shortcut: under ~200,000 tokens (~500 pages)? Skip RAG; use a cached prompt.
Show Python: contextualize with prompt caching
import anthropic

client = anthropic.Anthropic()

CONTEXT_PROMPT = """Here is the chunk we want to situate within the whole document
<chunk>
{chunk}
</chunk>
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving \
search retrieval of the chunk. Answer only with the succinct context and nothing else."""


def contextualize(document_text: str, chunks: list[str]) -> list[str]:
    """Prepend 50-100 tokens of document context to every chunk before embedding and indexing."""
    out = []
    for chunk in chunks:
        resp = client.messages.create(
            model="claude-haiku-4-5-20251001",
            max_tokens=150,
            messages=[{
                "role": "user",
                "content": [
                    # Same document block on every call -> cached after the first; later calls pay cache-read price.
                    {"type": "text", "text": f"<document>\n{document_text}\n</document>",
                     "cache_control": {"type": "ephemeral"}},
                    {"type": "text", "text": CONTEXT_PROMPT.format(chunk=chunk)},
                ],
            }],
        )
        context = next(b.text for b in resp.content if b.type == "text").strip()
        out.append(f"{context}\n\n{chunk}")
    return out
Go deeper: caching mechanics and storage

Chunking destroys context. Anthropic's measured results are on top-20 retrieval failure rate; they put the one-off cost at $1.02 per million document tokens. A single long contract often fits under the 200,000-token "skip RAG" threshold.

The quoted instruction is Anthropic's own contextualiser prompt. cache_control: {"type": "ephemeral"} on the document block marks the end of a cacheable prefix; the first call writes the cache (1.25x input price for the 5-minute cache), and each later chunk of the same document reads it at 0.1x. Check resp.usage.cache_read_input_tokens on the second call to confirm hits. Documents shorter than the model's minimum cacheable length are not cached; that is fine, they are cheap anyway. Store both the original chunk (to show users and cite) and the contextualised text (to embed and to feed into content_tsv), because the context helps the keyword leg too. Run it in the ingestion worker, not at query time, and for a large back-catalogue use the Batch API at 50% off.

Rejected for this

"We filter by tenant after retrieval" or "the client passes tenantId". Both leak: the first puts other tenants' text into the prompt and shrinks your top-k, the second lets anyone change a parameter. Say "tenant from the JWT, enforced in the query and by RLS, tested with a cross-tenant test".

Go deeper: the Spring side

Postgres row-level security makes the tenant filter impossible to forget. On the Spring side, a filter or aspect reads the tenant claim from the validated Jwt and runs SET LOCAL app.tenant_id (via set_config('app.tenant_id', ?, true) as a bind parameter) at the start of the transaction. The repository adds the group filter from the JWT's groups claim. Nothing in the request body can change either. With current_setting(..., true), a missing setting returns NULL, so the policy matches no rows: it fails closed, which I verified above.

07Multi-hop questions

  1. Question"Which vendor contracts renewed in 2025 have uncapped indemnity?"
  2. SQLStructured half via metadata: renewal_date in 2025 (most reliable).
  3. HybridSemantic half per contract: "indemnity cap".
  4. Haiku"What is missing?" Returns one new query or DONE. Max 3 hops.
  5. SonnetAnswers only from evidence, cites [source p.N].
Show Python: answer_multihop with a hop limit
from typing import Callable

import anthropic

client = anthropic.Anthropic()
MAX_HOPS = 3


def answer_multihop(question: str, retrieve: Callable[[str], list[str]], plan_search) -> str:
    """retrieve(query) -> list of chunk texts, already tenant-scoped by the caller."""
    plan = plan_search(question)
    queries = plan.sub_questions or [plan.rewritten_query]
    evidence: list[str] = []
    for hop in range(MAX_HOPS):
        for q in queries:
            evidence += retrieve(q)
        joined = "\n---\n".join(evidence)
        follow_up = client.messages.create(
            model="claude-haiku-4-5-20251001",
            max_tokens=200,
            system="Reply with ONE search query for the missing fact, or exactly DONE if the evidence suffices.",
            messages=[{"role": "user", "content":
                       f"<question>{question}</question>\n<evidence>{joined}</evidence>"}],
        )
        nxt = next(b.text for b in follow_up.content if b.type == "text").strip()
        if nxt == "DONE":
            break
        queries = [nxt]
    joined = "\n---\n".join(evidence)
    final = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1500,
        system="Answer only from the evidence. Cite as [source p.N]. If the evidence is insufficient, say so.",
        messages=[{"role": "user", "content":
                   f"<question>{question}</question>\n<evidence>{joined}</evidence>"}],
    )
    return next(b.text for b in final.content if b.type == "text")
Go deeper: approaches and production additions

"Which of our vendor contracts renewed in 2025 have uncapped indemnity?" needs at least two lookups: find contracts renewed in 2025, then check each one's indemnity clause. Approaches: decompose into sub-questions up front; iterate (retrieve, ask the model what is missing, retrieve again, up to N hops); or answer the structured half with SQL over metadata (renewal_date) and use vectors only for the semantic half. The last option is the most reliable and is the one interviewers like to hear.

The loop is bounded (MAX_HOPS = 3) so a confused model cannot spin forever and burn tokens, the cheap model decides "what is missing", and only the final answer uses Sonnet. The retrieve callback is the tenant-scoped hybrid plus rerank function, so every hop is permission-filtered. Production additions: dedupe evidence by chunk id, cap total evidence tokens, and log each hop's query for debugging.

Common mistakes
  • Adding raw cosine and BM25 scores instead of fusing ranks.
  • Reranking 500 candidates: cost grows per pair.

09Quick check

A chunk is rank 1 in the vector list and absent from the keyword list. Its RRF score with k = 60 is:

Each list contributes 1/(k + rank); the missing list contributes 0. So 1/(60 + 1) = 1/61.

Why merge with RRF instead of a weighted sum of scores?

A weighted sum needs normalisation and tuning and breaks when distributions shift. RRF uses only ranks and one parameter.

Why can't you run the cross-encoder over all one million chunks?

That is the trade-off: bi-encoders precompute document vectors; cross-encoders read the pair together, so you rerank only a shortlist of 20–50.

Where should the tenant filter be applied in RAG?

Anything later lets the model read forbidden text; a request parameter can be changed by anyone.

What keeps contextual retrieval's ingestion cost low?

The first call writes the cache; each later chunk reads it at 0.1x the input price.

10Interview questions

Bi-encoder vs cross-encoder: what is the difference and where does each go?

A bi-encoder embeds query and document independently, so document vectors are precomputed and searched with ANN: fast, scalable, less precise. A cross-encoder reads query and document together with full attention between them and outputs a relevance score: precise, but one model pass per pair and nothing precomputed. So: bi-encoder (plus BM25) retrieves the top 50 from millions, the cross-encoder reranks those 50 to the top 5.

Why hybrid search? Isn't semantic search better?

Embeddings blur exact tokens: clause numbers, defined terms, names, IDs. BM25 nails those and misses paraphrases. Running both and fusing with RRF gets both kinds of match. In legal text, a large share of questions mention an exact term, so hybrid is the first upgrade.

Why RRF instead of a weighted sum of scores?

Cosine distance and BM25 scores are on different, query-dependent scales, so a weighted sum needs normalisation and tuning and breaks when the distribution shifts. RRF uses only ranks, has one parameter (k = 60 by convention), and is robust. A weighted, normalised fusion can win once you have a golden set to tune it on.

What is contextual retrieval and what did it buy?

Prepend 50–100 tokens of Claude-generated, document-aware context to each chunk before embedding and BM25 indexing. Anthropic measured top-20 retrieval failures falling from 5.7% to 3.7% (35%), to 2.9% with contextual BM25 (49%), and to 1.9% with reranking (67%). Prompt caching on the document keeps it at about $1.02 per million document tokens.

How do you enforce per-tenant and per-document access in RAG?

In the retrieval query, before anything reaches the model: tenant from the JWT applied in SQL and by Postgres RLS (fail closed when unset), document ACL as an indexed array or join filtered by the user's groups from the token. Rerank and generate only on allowed chunks. Prove it with an automated cross-tenant test and audit-log the chunk ids used per answer.

A chat user asks "what about the second one?" How do you retrieve?

Query rewriting with the conversation history into a standalone query, using a small model with structured output (rewritten query, keywords, optional sub-questions). Embed the rewritten query, not the raw turn.

How do you answer multi-hop questions?

Prefer turning the structured part into SQL over metadata (dates, counterparties, contract type), then semantic search per result. Otherwise decompose into sub-questions or retrieve iteratively, with a hop limit, dedupe and a token cap. Evaluate multi-hop questions separately in the golden set because they fail differently.

Retrieval quality dropped after a deployment. How do you debug?

Run the golden set and compare recall@k per stage: did the vector leg, keyword leg, fusion or reranker change? Common causes: a new embedding model mixed with old vectors, a chunking change, a tokenizer or language config change in to_tsvector, a tenant filter shrinking HNSW results (iterative scan off), or the reranker timing out and being skipped silently.

Where do the top-k numbers come from?

From measurement: retrieve wide (20–50 per leg) for recall, rerank down to 3–8 for precision and context cost. Tune on a golden set by plotting recall@k and answer quality against k; more context is not free, because irrelevant chunks distract the model and cost tokens.

11Capstone checkpoint

Done when

You can say, with your own numbers, which upgrade moved recall the most on your contracts and what it cost per query.

The four checkpoint tasks
  1. Extend the golden set from the pgvector lesson to 30 questions: 10 with exact terms (clause numbers, party names), 10 paraphrased, 5 conversational follow-ups, 5 multi-hop.
  2. Measure recall@5 for: vector only, hybrid RRF, hybrid + rerank, and hybrid + rerank on contextualised chunks. Put the four numbers in a table in your README; it is a ready-made interview story.
  3. Turn on RLS with the fail-closed policy and add a test that a globex token gets zero acme chunks.
  4. For the risky-clause flagger, retrieve by clause_type metadata plus hybrid search for "uncapped liability", "unilateral termination", "auto-renewal", then rerank before asking Claude to classify.

12Cheat sheet

Cheat sheet
  • Vectors miss exact tokens; keywords miss paraphrases → hybrid.
  • RRF(d) = Σ 1/(60 + rank); missing list = 0; FULL OUTER JOIN in SQL.
  • Retrieve 20–50 per leg with bi-encoder + FTS; cross-encoder reranks to 3–8.
  • Rewrite chat turns with Haiku + structured output (query, keywords, sub-questions).
  • Contextual retrieval: failures 5.7% → 3.7% → 2.9% → 1.9%; cache the document.
  • Under ~200k tokens total: skip RAG, use a cached prompt.
  • Tenant from JWT, enforced by SQL + RLS, fails closed; ACL via allowed_groups.
  • Multi-hop: SQL for the structured half, vectors for the rest, MAX_HOPS = 3.
