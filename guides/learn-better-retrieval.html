Better retrieval: hybrid, rerank, rewrite, contextualise

The most common way a RAG system fails is simple. The right clause never reaches the model, so the model cannot quote it. RAG (retrieval-augmented generation) means "search your documents first, then let the model answer from what you found". This lesson fixes the search step with five upgrades, added in a sensible order.

  • Let a slower, more careful model re-read the top 40 results. Keep only the best 5.
  • Turn vague chat follow-ups into full questions. Add a line of context to every chunk of a document.
  • Check who may see what inside the database query. Never check after the model has already read the text.
Picture it

You are hiring for one job. A keyword filter on resumes gives one shortlist. A recruiter's gut feel gives another. Candidates who appear on both lists rise to the top. Then a slow, careful interview (the reranker) picks the final five. It only interviews people from the shortlist, because interviewing everyone would take forever.

Words you'll see
Chunk
A small piece of a long document, such as one clause or paragraph. We search chunks, not whole contracts.
Vector search
Search by meaning. Each chunk becomes a list of numbers (an embedding), and similar meanings get similar numbers. "Walk away early" can find "termination for convenience".
Keyword search (BM25)
Search by exact words, like Ctrl+F with a smart score. BM25 is the classic formula that scores how well a text matches your words.
Hybrid search
Running vector search and keyword search together, then merging the two result lists.
RRF
Reciprocal rank fusion. A way to merge ranked lists using only each item's position, not its raw score. Like combining two "top 10" charts.
Reranker (cross-encoder)
A slower model that reads the question and one chunk together and scores how well they match. Used only on a short list.
Tenant and ACL
A tenant is one customer company sharing the system. An ACL (access control list) says which users or groups may read a document.
JWT
JSON Web Token. A signed login token. The server can trust what it says, such as your company and groups.

01The five upgrades, in the order to add them

1. Hybrid search

Vector search finds meaning. Keyword search finds exact words like "Clause 14.2". Run both and merge the lists by position.

2. Rerank

A slow but accurate cross-encoder re-reads the top 20–50 results and puts them in a better order.

3. Contextual retrieval

When a document is loaded, Claude writes 50–100 tokens of context for each chunk. With reranking, this cuts search failures by up to 67%.

4. Query rewriting

A cheap model turns "What about the other one?" into a full question in contract language.

5. Permissions and multi-hop

Customer and access filters live inside the SQL. Questions with several parts get split up, with a limit on rounds.

Go deeper: setup details and why order matters

Hands-on setup: start from the contract_chunks table in the pgvector lesson. Then run uv pip install "psycopg[binary]" pgvector voyageai anthropic numpy. The table already has a text-search column, content_tsv tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED. It also has a GIN index on that column (an index built for word lookups). Every Python file below compiles with python -m py_compile. The SQL was run against pgvector/pgvector:pg18-trixie.

Add the upgrades in order of value for effort. Hybrid search comes first, because it is cheap and helps a lot with exact terms. Reranking comes next. Contextual retrieval is third, because it costs extra work when you load documents. Rewriting for chat is fourth. Add multi-hop last, and only if your test questions (your golden set) contain such questions.

02Hybrid search and reciprocal rank fusion

Vector search

  • "get out of the deal early" matches "termination for convenience"
  • Blurs exact words, such as clause numbers, defined terms, company names and invoice IDs

Keyword search (BM25 / ts_rank_cd)

  • Finds "Section 73 of the Indian Contract Act" exactly
  • Misses the same idea said in other words

Each one fails where the other one works, so run both. But their scores are on different scales. Vector search gives a cosine distance (how far apart two meanings are). Keyword search gives a ts_rank_cd number. You cannot add those fairly. So merge by rank (position in the list) with RRF:

RRF(d) = Σ over result lists  1 / (k + rank_in_that_list(d))        k = 60 by convention
Merge two ranked lists with RRF (k = 60)

Why k = 60? It makes the gap between first and fifth place small. That way, no single list can take over the result. Think of it as two judges voting on positions, instead of comparing their raw marks.

Show SQL: hybrid search with RRF
WITH semantic AS (
    SELECT id, RANK() OVER (ORDER BY embedding <=> '[0.9,0.1,0.0]') AS rank
    FROM contract_chunks
    WHERE tenant_id = 'acme'
    ORDER BY embedding <=> '[0.9,0.1,0.0]'
    LIMIT 20
),
keyword AS (
    SELECT id, RANK() OVER (ORDER BY ts_rank_cd(content_tsv, q) DESC) AS rank
    FROM contract_chunks, websearch_to_tsquery('english', 'terminate notice') q
    WHERE tenant_id = 'acme' AND content_tsv @@ q
    ORDER BY ts_rank_cd(content_tsv, q) DESC
    LIMIT 20
)
SELECT COALESCE(s.id, k.id) AS id,
       round((COALESCE(1.0 / (60 + s.rank), 0.0) + COALESCE(1.0 / (60 + k.rank), 0.0))::numeric, 5) AS rrf_score
FROM semantic s
FULL OUTER JOIN keyword k ON s.id = k.id
ORDER BY rrf_score DESC
LIMIT 5;

--  id | rrf_score
-- ----+-----------
--   1 |   0.03279      <- rank 1 in both lists: 2/61
--   4 |   0.01613

Show Python: the same query, parameterised and tenant-filtered
import numpy as np
import psycopg

HYBRID_SQL = """
WITH semantic AS (
    SELECT id, RANK() OVER (ORDER BY embedding <=> %(qvec)s) AS rank
    FROM contract_chunks
    WHERE tenant_id = %(tenant)s
    ORDER BY embedding <=> %(qvec)s
    LIMIT 40
),
keyword AS (
    SELECT id, RANK() OVER (ORDER BY ts_rank_cd(content_tsv, q) DESC) AS rank
    FROM contract_chunks, websearch_to_tsquery('english', %(qtext)s) q
    WHERE tenant_id = %(tenant)s AND content_tsv @@ q
    ORDER BY ts_rank_cd(content_tsv, q) DESC
    LIMIT 40
)
SELECT c.id, c.source, c.page, c.content,
       COALESCE(1.0 / (%(k)s + s.rank), 0.0) + COALESCE(1.0 / (%(k)s + kw.rank), 0.0) AS rrf
FROM semantic s
FULL OUTER JOIN keyword kw ON s.id = kw.id
JOIN contract_chunks c ON c.id = COALESCE(s.id, kw.id)
ORDER BY rrf DESC
LIMIT %(limit)s
"""


def hybrid_search(conn: psycopg.Connection, tenant_id: str, question: str, qvec: np.ndarray,
                  limit: int = 20, k: int = 60) -> list[tuple]:
    """tenant_id must come from the verified JWT, never from the request body."""
    with conn.transaction():
        conn.execute("SET LOCAL hnsw.iterative_scan = relaxed_order")  # tenant filter shrinks HNSW results
        return conn.execute(HYBRID_SQL, {"qvec": qvec, "qtext": question, "tenant": tenant_id,
                                         "k": k, "limit": limit}).fetchall()

The FULL OUTER JOIN keeps chunks that only one search found. COALESCE(..., 0.0) gives them a zero for the search that missed them. websearch_to_tsquery accepts input the way users type it, with quotes, or and -. It does not throw syntax errors. The stricter to_tsquery would.

I ran the Python version against the database container. I also inserted a row for a second customer. Only the acme rows came back. Each search fetches 40 results, so the reranker gets 20–40 candidates to work with.

Postgres full-text vs real BM25

ts_rank_cd is not BM25. It scores by how often your words appear and how close together they are. It does not use inverse document frequency, the BM25 idea that rare words matter more. So rare terms do not get the extra boost BM25 gives them. Still, for clause numbers and defined terms, it gets most of the benefit with no new systems to run. If keyword quality becomes the weak spot, upgrade to a BM25 extension or OpenSearch. Measure first.

03Reranking: bi-encoder vs cross-encoder

Bi-encoder (embeddings)

  • Each document's vector is computed once, ahead of time. Approximate nearest-neighbour (ANN) search over millions is fast.
  • Never reads the question and document together. It can miss "liability is not capped".

Stage 1: fetch the top 50 out of millions.

Cross-encoder (reranker) stage 2

  • Reads the question and document side by side, word against word. Much more accurate.
  • Runs the model once for every question-and-candidate pair. Nothing can be prepared ahead of time.

Stage 2: re-order the top 20–100 and keep 5.

A Java comparison helps. The bi-encoder is like a hashCode() you compute once and store. The cross-encoder is like an expensive equals(). You only call it on the shortlist.

import voyageai

vo = voyageai.Client()


def rerank(question: str, candidates: list[dict], top_k: int = 5) -> list[dict]:
    """candidates: dicts with a 'content' key, already tenant-filtered by the SQL."""
    result = vo.rerank(question, [c["content"] for c in candidates], model="rerank-3-lite", top_k=top_k)
    return [candidates[r.index] | {"rerank_score": r.relevance_score} for r in result.results]
Go deeper: model choices and budget

A bi-encoder turns the question and the document into numbers separately. The match score is then a simple dot product of the two lists of numbers. A cross-encoder feeds the question and one document together through the model. It returns one relevance score. That is slow, so you only run it on the top 20–100 from the first stage. Search wide and cheap first, then re-check narrow and expensive.

rerank-3 is Voyage's most accurate reranker. rerank-3-lite is the faster, cheaper option. Each result has an index (its position in your list), the document and a relevance_score. You can also run a reranker on your own servers. One example is cross-encoder/ms-marco-MiniLM-L-6-v2 through sentence-transformers. pgvector-python's hybrid example uses that one. Budget: rerank 20–50 candidates, not 500. The cost grows in step with the number of pairs. Rerank only candidates already filtered to this customer. Never send another customer's text to any model.

04Query rewriting

  1. History"We're looking at the Infosys MSA"
  2. User"can they walk away early?" (searching with this exact text finds junk)
  3. HaikuA small, cheap model reads the chat and writes a full question: "termination for convenience rights of the vendor in the Infosys MSA". It also lists exact words to look for: "terminate", "convenience", "notice". This question needs no splitting. (It returns these as a SearchPlan with rewritten_query, keywords and an empty sub_questions.)
  4. SearchThe full question goes to the search by meaning. The exact words go to the keyword search. (In code, rewritten_query feeds the vector search and " ".join(keywords) feeds websearch_to_tsquery.)

Cost: about a tenth of a cent and a few hundred milliseconds per question. Skip it when the question already makes sense on its own.

Show Python: plan_search with structured output
import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic()


class SearchPlan(BaseModel):
    rewritten_query: str          # standalone, legal vocabulary, no pronouns
    keywords: list[str]           # exact terms for the full-text leg
    sub_questions: list[str]      # empty unless the question needs several lookups


REWRITE_SYSTEM = """You turn a user's question about their contracts into a search plan.
Resolve pronouns using the chat history. Use contract vocabulary
(e.g. "get out of the deal" -> "termination for convenience").
Only split into sub_questions when one search cannot answer it."""


def plan_search(question: str, history: str = "") -> SearchPlan:
    resp = client.messages.parse(
        model="claude-haiku-4-5-20251001",  # cheap and fast: this runs on every query
        max_tokens=400,
        system=REWRITE_SYSTEM,
        messages=[{"role": "user", "content": f"<history>{history}</history>\n<question>{question}</question>"}],
        output_format=SearchPlan,
    )
    return resp.parsed_output
Go deeper: what the rewriter does, variants

In the fifth message of a chat, users write things like "and what about the other one?". A cheap model (Haiku) reads the chat history and rewrites this into a full question. It swaps everyday words for contract words. It pulls out exact keywords for the keyword search. If needed, it splits the question into smaller sub-questions. Two variations exist. Multi-query writes several rephrasings and merges their results with RRF. HyDE searches with an imagined answer instead of the question.

messages.parse takes a Pydantic model and returns a checked object in resp.parsed_output. The SDK turns your model into a JSON schema and checks the reply against it. Cost: one Haiku call of a few hundred tokens. That is roughly a tenth of a cent and a few hundred milliseconds. Skip it for the first message if the question already stands on its own.

05Contextual retrieval

5.7%right chunk missing from top 20, plain embeddings
3.7%with context added to embeddings (35% fewer misses)
2.9%plus context in keyword search (49% fewer)
1.9%plus reranking (67% fewer)
$1.02per million document tokens, paid once
  • Problem: a chunk says "The Supplier's liability … shall not exceed the fees paid". It never says which contract or which supplier.
  • Fix: Claude reads the whole document and writes 50–100 tokens of context for each chunk. We add it to the front of the chunk. This happens before both vector and keyword indexing.
  • Keeping cost low: every chunk sends the same document, so prompt caching makes chunks 2 onwards cheap.
  • Shortcut: all your documents under about 200,000 tokens (about 500 pages)? Skip RAG. Put them all in one cached prompt.
Show Python: contextualize with prompt caching
import anthropic

client = anthropic.Anthropic()

CONTEXT_PROMPT = """Here is the chunk we want to situate within the whole document
<chunk>
{chunk}
</chunk>
Please give a short succinct context to situate this chunk within the overall document for the purposes of improving \
search retrieval of the chunk. Answer only with the succinct context and nothing else."""


def contextualize(document_text: str, chunks: list[str]) -> list[str]:
    """Prepend 50-100 tokens of document context to every chunk before embedding and indexing."""
    out = []
    for chunk in chunks:
        resp = client.messages.create(
            model="claude-haiku-4-5-20251001",
            max_tokens=150,
            messages=[{
                "role": "user",
                "content": [
                    # Same document block on every call -> cached after the first; later calls pay cache-read price.
                    {"type": "text", "text": f"<document>\n{document_text}\n</document>",
                     "cache_control": {"type": "ephemeral"}},
                    {"type": "text", "text": CONTEXT_PROMPT.format(chunk=chunk)},
                ],
            }],
        )
        context = next(b.text for b in resp.content if b.type == "text").strip()
        out.append(f"{context}\n\n{chunk}")
    return out
Go deeper: caching mechanics and storage

Cutting a document into chunks throws away its context. Anthropic measured how often the right chunk was missing from the top 20 results. They put the one-time cost at $1.02 per million document tokens. A single long contract often fits under the 200,000-token "skip RAG" limit.

The prompt in the code is Anthropic's own. cache_control: {"type": "ephemeral"} on the document block marks where the reusable part of the prompt ends. The first call saves the cache, at 1.25x the normal input price for the 5-minute cache. Each later chunk of the same document reads it at 0.1x. Check resp.usage.cache_read_input_tokens on the second call to confirm the cache was used. Very short documents fall below the model's minimum cache size and are not cached. That is fine, because they are cheap anyway. Store two versions of each chunk. Keep the original to show users and to cite. Keep the version with context to embed and to feed into content_tsv, since the context helps keyword search too. Run this in the background job that loads documents, not when users ask questions. For a large backlog of old documents, use the Batch API at 50% off.

Rejected for this

Two answers fail in interviews. One is "we filter by customer after the search". The other is "the client sends a tenantId". Both leak data. The first puts other customers' text into the prompt. It also leaves you fewer than k results. The second lets anyone change a request parameter. Instead, say this. "The tenant comes from the JWT. It is enforced in the query and by RLS (row-level security). A test proves one customer cannot see another's data."

Go deeper: the Spring side

Postgres row-level security (RLS) adds the customer filter to every query automatically. So nobody can forget it. On the Spring side, a filter or aspect reads the tenant from the checked Jwt. At the start of the transaction it runs SET LOCAL app.tenant_id. It does this through set_config('app.tenant_id', ?, true) with a bind parameter. The repository adds the group filter, using the groups listed in the JWT. Nothing in the request body can change either value. With current_setting(..., true), a missing setting returns NULL. Then the policy matches no rows at all. It "fails closed": when in doubt, show nothing. I verified this above.

07Multi-hop questions

  1. Question"Which vendor contracts renewed in 2025 have uncapped indemnity?"
  2. DatabaseThe fact part comes from a plain table lookup: contracts whose renewal date is in 2025 (column renewal_date). This is the most reliable step.
  3. SearchFor each of those contracts, search by meaning and exact words for "indemnity cap" (hybrid search).
  4. HaikuA cheap model asks "what is still missing?". It replies with one new search, or with DONE. We allow at most 3 rounds.
  5. SonnetA stronger model answers only from what was found. It cites the document and page, like [source p.N].
Show Python: answer_multihop with a hop limit
from typing import Callable

import anthropic

client = anthropic.Anthropic()
MAX_HOPS = 3


def answer_multihop(question: str, retrieve: Callable[[str], list[str]], plan_search) -> str:
    """retrieve(query) -> list of chunk texts, already tenant-scoped by the caller."""
    plan = plan_search(question)
    queries = plan.sub_questions or [plan.rewritten_query]
    evidence: list[str] = []
    for hop in range(MAX_HOPS):
        for q in queries:
            evidence += retrieve(q)
        joined = "\n---\n".join(evidence)
        follow_up = client.messages.create(
            model="claude-haiku-4-5-20251001",
            max_tokens=200,
            system="Reply with ONE search query for the missing fact, or exactly DONE if the evidence suffices.",
            messages=[{"role": "user", "content":
                       f"<question>{question}</question>\n<evidence>{joined}</evidence>"}],
        )
        nxt = next(b.text for b in follow_up.content if b.type == "text").strip()
        if nxt == "DONE":
            break
        queries = [nxt]
    joined = "\n---\n".join(evidence)
    final = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1500,
        system="Answer only from the evidence. Cite as [source p.N]. If the evidence is insufficient, say so.",
        messages=[{"role": "user", "content":
                   f"<question>{question}</question>\n<evidence>{joined}</evidence>"}],
    )
    return next(b.text for b in final.content if b.type == "text")
Go deeper: approaches and production additions

"Which of our vendor contracts renewed in 2025 have uncapped indemnity?" needs at least two lookups. First, find contracts renewed in 2025. Then check each one's indemnity clause. There are three ways to do this. You can split the question into sub-questions up front. You can loop: search, ask the model what is missing, and search again, up to N rounds. Or you can answer the fact part with SQL over table columns like renewal_date. Then use vector search only for the meaning part. The last option is the most reliable. Interviewers like to hear it.

The loop has a hard limit (MAX_HOPS = 3). So a confused model cannot loop forever and burn tokens. The cheap model decides "what is missing". Only the final answer uses the stronger Sonnet model. The retrieve function is the hybrid search plus rerank, already limited to this customer. So every round respects permissions. For production, add three things. Remove duplicate evidence by chunk id. Cap the total evidence tokens. Log each round's search to help debugging.

Common mistakes
  • Adding raw vector and BM25 scores together, instead of merging by position.
  • Reranking 500 candidates. The cost grows with every pair.
  • Filtering by customer after the search, or trusting a tenantId parameter.
  • Searching with the raw chat message ("what about the second one?").
  • Multi-hop loops with no limit on rounds or tokens.

09Quick check

A chunk is first in the vector list. It is not in the keyword list at all. What is its RRF score with k = 60?

Each list adds 1/(k + rank). A list that does not contain the chunk adds 0. So the score is 1/(60 + 1) = 1/61.

Why merge with RRF instead of adding up the scores with weights?

A weighted sum needs the scores rescaled and the weights tuned. It breaks when the score patterns change. RRF uses only positions and one setting.

Why can't you run the cross-encoder on all one million chunks?

That is the trade-off. Bi-encoders compute document vectors ahead of time. Cross-encoders read the pair together, so you rerank only a shortlist of 20–50.

Where should the customer (tenant) filter go in RAG?

Any later step lets the model read text it should not see. And anyone can change a request parameter.

What keeps the cost of contextual retrieval low when loading documents?

The first call saves the document in the cache. Each later chunk reads it at 0.1x the normal input price.

10Interview questions

Bi-encoder vs cross-encoder: what is the difference and where does each go?

A bi-encoder embeds the question and the document separately. So document vectors are computed ahead of time and searched with ANN (approximate nearest-neighbour search). It is fast and scales well, but it is less precise. A cross-encoder reads the question and document together, with full attention between them. Attention means each word can look at every other word. It outputs one relevance score. It is precise, but needs one model run per pair, with nothing prepared ahead. So the bi-encoder (plus BM25) fetches the top 50 from millions. The cross-encoder reranks those 50 down to the top 5.

Why hybrid search? Isn't semantic search better?

Embeddings blur exact tokens such as clause numbers, defined terms, names and IDs. BM25 finds those exactly, but misses rephrasings. Running both and merging with RRF catches both kinds of match. In legal text, many questions mention an exact term. So hybrid search is the first upgrade.

Why RRF instead of a weighted sum of scores?

Cosine distance and BM25 scores use different scales, and those scales change per question. So a weighted sum needs normalisation (rescaling to a common range) and tuning. It breaks when the score patterns shift. RRF uses only ranks and has one parameter (k = 60 by convention). It is robust. A tuned, normalised weighted sum can win later. But you need a golden set (a fixed list of test questions with known answers) to tune it.

What is contextual retrieval and what did it buy?

Claude reads the whole document and writes 50–100 tokens of context for each chunk. You add that to the front of the chunk before embedding and BM25 indexing. Anthropic measured how often the right chunk was missing from the top 20. It fell from 5.7% to 3.7% (35% fewer misses). With contextual BM25 it fell to 2.9% (49% fewer). With reranking it fell to 1.9% (67% fewer). Prompt caching on the document keeps the cost at about $1.02 per million document tokens.

How do you enforce per-tenant and per-document access in RAG?

Enforce it in the retrieval query, before anything reaches the model. Take the tenant from the JWT. Apply it in SQL and with Postgres RLS (row-level security). If no tenant is set, return nothing; this is called failing closed. Store the document ACL as an indexed array or a join table. Filter it by the user's groups from the token. Rerank and generate only on allowed chunks. Prove it with an automated test where one tenant tries to read another's data. Also keep an audit log of the chunk ids used for each answer.

A chat user asks "what about the second one?" How do you retrieve?

Use query rewriting. A small model reads the chat history and turns the message into a standalone query. It returns structured output: a rewritten query, keywords, and optional sub-questions. Embed the rewritten query, not the raw chat message.

How do you answer multi-hop questions?

First, turn the structured part into SQL over metadata, such as dates, counterparties and contract type. Then run semantic search on each result. If that is not possible, decompose the question into sub-questions. Or retrieve in a loop. Either way, add a hop limit, remove duplicates and cap the tokens. Score multi-hop questions separately in the golden set, because they fail in different ways.

Retrieval quality dropped after a deployment. How do you debug?

Run the golden set and compare recall@k for each stage. Recall@k means: how often the right chunk is in the top k results. Check which part changed: vector search, keyword search, the merge, or the reranker. Common causes are these. A new embedding model was mixed with old vectors. The chunking changed. The tokenizer or language setting in to_tsvector changed. A tenant filter shrank the HNSW (vector index) results because iterative scan was off. Or the reranker timed out and was skipped without any error.

Where do the top-k numbers come from?

From measurement. Retrieve wide, 20–50 per search, so the right chunk is likely in the list (recall). Rerank down to 3–8, so what you send is relevant (precision) and cheap. Tune on a golden set. Plot recall@k and answer quality against k. More context is not free. Irrelevant chunks distract the model and cost tokens.

Done when

You can say which upgrade helped most on your contracts, using your own numbers. You can also say what it cost per question.

The four checkpoint tasks
  1. Grow the test questions from the pgvector lesson to 30. Use 10 with exact terms (clause numbers, company names) and 10 reworded ones. Add 5 chat follow-ups and 5 multi-step questions.
  2. Measure recall@5 (how often the right chunk is in the top 5) four ways. Try vector only, hybrid with RRF, hybrid plus rerank, and hybrid plus rerank on chunks with added context. Put the four numbers in a README table. It makes a ready-made interview story.
  3. Turn on RLS with the "show nothing if unset" policy. Add a test proving a globex token gets zero acme chunks.
  4. For the risky-clause checker, filter by the clause_type column. Add hybrid search for "uncapped liability", "unilateral termination" and "auto-renewal". Rerank before asking Claude to classify.

12Cheat sheet

Cheat sheet
  • Vectors miss exact words. Keywords miss rephrasings. So use both (hybrid).
  • RRF(d) = Σ 1/(60 + rank). A list that misses the chunk adds 0. In SQL, use FULL OUTER JOIN.
  • Fetch 20–50 per search with embeddings and full-text search. A cross-encoder then reranks down to 3–8.
  • Rewrite chat messages with Haiku and structured output (query, keywords, sub-questions).
  • Contextual retrieval cuts misses from 5.7% to 3.7%, then 2.9%, then 1.9%. Cache the document.
  • Under about 200k tokens in total? Skip RAG and use a cached prompt.
  • Tenant comes from the JWT. SQL and RLS enforce it, and show nothing if it is missing. ACL uses allowed_groups.
  • Multi-step questions: SQL for the fact part, vectors for the rest, MAX_HOPS = 3.
